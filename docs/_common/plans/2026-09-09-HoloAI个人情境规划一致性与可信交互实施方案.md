## 1. 产品结论

### 1.1 本次五个问题的结论

| 问题 | 产品结论 | 必须落地的改法 |
|---|---|---|
| 同一句话一次触发个人情境、一次没有 | 不符合预期。这是能力路由不稳定，不是模型“正常随机性” | 对高置信规划请求增加服务端确定性稳定层；路由决定持久化；规划失败不得静默伪装成普通回答 |
| 等待先显示三个点，退出重进后又消失 | 不符合预期。当前把“消息还在运行”和“页面当前正在请求”混成一个布尔值 | 建立持久化规划运行状态；消息按 run 状态渲染；退出重进重新挂接同一 run |
| 希望分析状态始终陪伴，且包含云端分析 | 应做，但不能展示或编造思维链 | 持续展示真实阶段事件；云端执行器产生阶段并持久化；SSE 实时推送，轮询与冷启动恢复兜底 |
| “查看依据”“你的记录”无法点击 | 不符合最终产品预期 | “查看依据”展开真实证据列表；每条“你的记录”可跳到原记录或说明不可访问原因 |
| 其他问题 | 日期、事实口径、默认全选、重进定位和重复答案都会损害信任 | 一并纳入本方案，不能拆成以后再看的视觉优化 |

### 1.2 完成后的用户体验

以“要去日本旅行，要提前做什么准备”为例：

1. 发送后立即出现一条稳定的 Holo 运行卡，而不是空消息。
2. 先显示“正在理解你的需求”；云端路由确认后显示“已识别为旅行准备规划”。
3. 后续依次显示真实发生的阶段，例如“正在查找与你有关的记录”“正在云端整理方案”“正在核对日期与依据”。
4. 用户离开 HoloAI、切到其他页面或重新进入，仍能看到最后一次已确认阶段；如任务仍运行则继续更新。
5. 完成后同一张运行卡原位转为方案卡，不额外再生成一条重复回答。
6. 用户可以展开每项依据，并从“你的记录”进入原始想法、对话、任务、财务或记忆来源。
7. 没有出发日期时只显示“出发前 3–5 天”等相对时间，不默认显示今天。
8. 未经核验的签证、护照或政策信息显示为“需要核对”，不冒充确定事实。
9. 有关键未知条件时，依赖这些条件的事项默认不勾选；用户确认后才写入待办。

## 2. 录屏事实与代码根因

### 2.1 录屏事实

- 同一句“要去日本旅行，要提前做什么准备”在同一会话中先得到普通长文本，后一次得到个人情境方案卡。
- 第二次发送后先显示三个点；退出 HoloAI 再进入时只剩 Holo 消息头和空白正文，但停止按钮仍存在。
- 最终方案一次性整块出现，没有阶段反馈。
- “你的记录”是静态标签；“查看依据”即使展开也只有二次概括，没有原始来源跳转。
- 多个日期选择器显示录屏当天 2026-09-09，与“出发前若干天”的相对时间不一致。
- 草案在未知旅行日期、目的和证件状态时已经默认全选多项任务。
- 普通回答和个性化回答同时留在会话，用户无法判断哪个才是 Holo 的稳定能力。

### 2.2 当前根因

1. `ConversationCoordinator.process` 仅在模型返回 `.contextualPlanning` 时进入个人情境规划；后端 `intentResponseStabilizer.js` 没有覆盖“为具体事件做准备/安排”的稳定规划语义。
2. 规划调用使用 `try?`；失败会被吞掉并继续普通回答，所以用户无法区分“没识别到”和“识别到但规划失败”。
3. `HoloContextPlanningCoordinator` 已有 `preparing/retrieving/generating/...`，但这些状态没有桥接到 ChatMessage。
4. `ChatViewModel` 先写入空的 streaming assistant message；重新进入页面后，全局 `isStreaming` 不从消息运行状态恢复，空消息因此失去三个点并渲染为空白。
5. `HoloContextChatPlanner` 当前通过后端执行非流式 `personal_context_planning`，云端确实参与生成，但客户端没有可恢复的云端任务身份，也没有真实阶段事件。
6. `ChatMessage` 只有最终 `contextPlanJSON`，没有规划 run 的独立持久化载荷。
7. `HoloContextPlanBasisEntry` 没有来源类型、来源实体 ID、原文片段、时间和跳转目标。
8. `ContextPlanChatCard` 使用 `confirmedDates[itemID] ?? Date()` 显示日期，但保存只提交 `confirmedDates`；界面可能显示今天，最终却保存为无日期。
9. `loadDraft()` 默认选中全部 task/checklistItem，未检查未知条件和前置条件。

## 3. 必须遵守的统一不变量

1. **同文案、同有效上下文、同后端能力版本，路由结果必须一致。** 模型可以参与边界判断，但不能让高置信规划请求随机落入两套体验。
2. **一次用户请求只有一个 `runID`、一条 assistant 占位消息和一个最终结果。** 不并行生成普通回答与个性化方案。
3. **运行状态是持久数据，不是 ViewModel 动画。** 页面销毁不等于任务消失。
4. **客户端只能显示已经发生或已经收到的阶段。** 禁止用每 2 秒切换文案的假进度营造分析感。
5. **云端是规划生成的真实执行方。** 客户端负责读取允许的本地来源、生成最小快照、展示状态、校验和保存；不得宣称本地动画就是云端分析。
6. **阶段流与结果流分离。** 阶段可以流式；最终结构化 JSON 只有完整解码并通过 validator 后才能落卡，不能边收到半截 JSON 边渲染任务。
7. **不展示思维链。** 只显示工作阶段、使用了哪些类别的数据、未知条件、证据和可验证结论。
8. **失败必须类型化。** 路由失败、来源读取失败、云端不可用、结构校验失败、用户取消分别展示，不得静默回落后假装一切正常。
9. **事实、推断、数据缺失和外部常识必须分开。** “Holo 未记录到收入”不等于“用户收入为零”。
10. **日期不允许由 UI 猜测。** 未设置就是未设置；相对时间缺少锚点就保留相对表达。
11. **证据必须能回源且受权限/遗忘控制。** 已删除、已遗忘或权限关闭后，历史卡不能继续泄露缓存原文。
12. **写入业务数据仍需用户确认。** 云端只能提出候选，不能直接创建待办。

## 4. 目标架构

```text
用户消息
  → 本地候选预判（仅决定首屏文案，不作为最终路由）
  → 后端 authoritative intent + deterministic stabilizer
  → 持久化 ContextPlanRun（messageID/runID/routeDecision/stage）
  → 读取本地允许访问的个人情境，构造最小快照
  → 创建云端 context_plan task 并上传快照
  → 云端执行器推进阶段并生成方案
  → SSE 阶段事件；断线时 GET snapshot 轮询兜底
  → iOS 完整解码 + 来源/日期/动作 validator
  → 同一消息原位切换为方案卡
  → 用户查看依据、修改选择和日期
  → 用户确认后执行，保存真实回执
```

### 4.1 为什么不直接套完整深度 Agent

个人情境规划是有限的“识别—检索—生成—校验”流程，不需要多轮自主工具循环。复用深度 Agent 的生命周期原则与后端异步任务底座，但新增独立 `context_plan` 类型和执行器分支，避免成本、Prompt、结果 schema 和错误语义互相污染。

### 4.2 第一屏与权威路由的关系

- 本地预判只用于在 100ms 内显示“正在理解你的需求”，不能提前显示“已识别为待办规划”。
- 只有后端权威路由返回 `.contextualPlanning` 后，界面才显示“已识别为旅行准备规划”等已确认文案。
- 如果权威路由判定为普通问答，同一占位消息切换到普通流式回答，不新增第二条 assistant 消息。
- 如果高置信稳定规则判定为规划，模型分类不得覆盖为普通回答；规则只定义语义结构，不维护“日本旅行”等目的地词表。

## 5. 数据与协议契约

### 5.1 扩展规划运行模型

在 `HoloContextPlanningModels.swift` 增量扩展，不另建第二套重复模型。建议契约：

```swift
enum HoloContextPlanStage: String, Codable, Sendable {
    case understandingRequest
    case planningRecognized
    case readingPersonalContext
    case uploadingContext
    case cloudPlanning
    case validatingDraft
    case needsInput
    case draftReady
    case waitingForNetwork
    case waitingForForeground
    case failed
    case cancelled
}

enum HoloContextPlanRouteSource: String, Codable, Sendable {
    case deterministic
    case model
    case ordinaryFallback
}

struct HoloContextPlanRunEnvelope: Codable, Sendable {
    var schemaVersion: Int
    var run: HoloPlanningRun
    var assistantMessageID: UUID
    var cloudTaskID: String?
    var stage: HoloContextPlanStage
    var stageRevision: Int
    var stageDisplayText: String
    var routeSource: HoloContextPlanRouteSource?
    var routeIntent: String?
    var selectedContextCount: Int?
    var startedAt: Date
    var updatedAt: Date
    var lastHeartbeatAt: Date?
    var failureCode: String?
    var canResume: Bool
}
```

约束：

- `stageDisplayText` 必须由受控文案映射生成，不接受模型自由写入。
- 同一 `runID` 的 `stageRevision` 只能递增；旧 revision 不得覆盖新状态。
- `draftReady/failed/cancelled` 为终态；终态后迟到回调不得改写。
- `selectedContextCount` 只有检索完成并有真实计数时才显示。
- `lastHeartbeatAt` 用于判断连接是否失活，不用于伪造任务进度。

### 5.2 ChatMessage 持久化

给 ChatMessage 新增可选 `contextPlanRunJSON`，同步修改：

- `Models/ChatMessage+CoreDataProperties.swift`
- `Models/CoreDataStack+ChatEntities.swift`
- `Models/ChatMessageViewData.swift`
- `Data/Repositories/ChatMessageRepository.swift`
- 所有轻量 fetch、字典快照、缓存恢复和测试夹具

不要把 run 塞入 `extractedDataJSON`：该字段已有大量旧卡片兼容职责，而且按 `[String:String]` 解码，无法安全承载版本化运行状态。

`contextPlanJSON` 继续只保存通过校验的最终草案。运行中允许 `contextPlanRunJSON != nil && contextPlanJSON == nil`；完成后两者同时保留，供来源审计和恢复使用。

### 5.3 后端云端任务扩展

复用现有：

- `HoloBackend/src/agent/cloudAnalysisTaskStore.js`
- `/v1/ai/agent/cloud/start`
- snapshot 上传、状态获取、取消、ack、过期清理、AES-256-GCM 即焚语义

新增而不是伪装：

1. task type 白名单加入 `context_plan`。
2. 新增 `contextPlanCloudExecutor` 或在现有 executor 内建立完全独立的 typed branch。
3. `context_plan` 使用 `personal_context_planning` 的 route、Prompt、额度和 validator，不使用 `agent_loop` schema。
4. 任务表增加或建立关联表保存非敏感阶段字段：`stage`、`stage_revision`、`updated_at_ms`；不得保存用户正文作为阶段文本。
5. 增加 `GET /v1/ai/agent/cloud/:id/events` SSE：
   - `event: stage`：stage、revision、updatedAt、可选非敏感计数；
   - `event: heartbeat`：taskID、serverTime；
   - `event: completed`：只通知可领取，不在事件中重复塞完整结果；
   - `event: failed/cancelled`：稳定错误码，不传内部错误原文。
6. 现有 `GET /v1/ai/agent/cloud/:id` 扩展返回当前 stage/revision，作为 SSE 断线、App 重进和冷启动恢复兜底。
7. 客户端先把结果完整落地，再调用 ack；网络回程丢失时可重复领取同一结果。

如果现有部署环境暂不支持长连接，允许首版用 1–2 秒退避轮询实现真实阶段更新，但数据契约必须按同一 event snapshot 设计，不能用客户端定时轮播代替。SSE 是本方案完成目标，轮询是传输 fallback。

### 5.4 路由决定契约

为 intent 结果补充可诊断但不含隐私正文的字段：

```json
{
  "intent": "contextual_planning",
  "routeSource": "deterministic",
  "routeReasonCode": "EVENT_PREPARATION_PLAN",
  "contextRequest": {}
}
```

后端 deterministic stabilizer 识别的是结构组合：

- 用户表达一个未来事件、目标或决策；
- 请求准备、规划、安排、注意事项、避免遗漏或拆解；
- 不是明确单项写操作；
- 不是纯事实查询或已指定数据明细查询。

必须用正负语料固定边界。禁止只添加“旅行、日本、准备”等硬编码词。

`ConversationCoordinator` 移除该路径的 `try?`，返回类型化结果：

```swift
enum ContextualPlanningOutcome {
    case routed(frame: HoloPlanningRequestFrame, routeSource: RouteSource)
    case ordinary
    case unavailable(code: String, retryable: Bool)
}
```

规划已路由但后续失败时，可以提供明确标注的基础回答作为降级，但必须保留“个性化规划暂未完成”的状态，不能把它伪装成没有触发规划。

## 6. 持续分析状态与恢复

### 6.1 用户可见状态文案

| 真实阶段 | 推荐文案 | 展示条件 |
|---|---|---|
| understandingRequest | 正在理解你的需求 | 请求已创建、权威路由未返回 |
| planningRecognized | 已识别为「旅行准备规划」 | 后端返回 contextual planning；引号内由安全的 goalSummary 截断生成 |
| readingPersonalContext | 正在查找与你有关的记录 | 本地检索确实开始 |
| uploadingContext | 正在安全发送本次规划所需信息 | 云端任务创建且最小快照上传中 |
| cloudPlanning | 正在云端整理方案 | 云端已进入 running/planning |
| validatingDraft | 正在核对日期、依据和可执行项 | 客户端或云端 validator 正在执行 |
| needsInput | 还需要你确认一个关键信息 | 该未知会实质改变方案 |
| waitingForNetwork | 网络恢复后会继续 | 有可恢复任务且网络不可用 |
| waitingForForeground | 回到 Holo 后继续完成 | 当前系统能力无法后台继续 |
| failed | 这次个性化规划没有完成 | 终态，同时给重试或基础回答 |
| cancelled | 已停止本次规划 | 用户明确停止 |

不得显示“正在读取 8 条记录”等数字，除非已有真实 selection snapshot。不得显示“正在核验签证政策”，除非系统真的调用了外部事实核验能力。

### 6.2 卡片交互

- 空 assistant message 一经创建就把 `messageType` 设置为 `.contextPlan` 或新的 `.planningRun`，并立即写入 run envelope。
- 运行态卡固定显示：当前阶段、最近更新时间、停止按钮；超过阈值无心跳时显示“连接中断，正在恢复”，不清空卡片。
- 阶段变化采用轻量过渡，上一阶段可折叠显示为已完成；不让整张卡反复跳高。
- 用户仍可离开聊天页；运行状态不应永久锁住全局输入。是否允许继续发送新消息按现有并发产品规则处理，但不能用全局 `isStreaming` 作为 run 的唯一真相源。
- 完成后同一 message 原位变成 `ContextPlanChatCard`；保留一个可折叠的“本次如何生成”阶段摘要。

### 6.3 页面退出、重进与冷启动

页面进入时：

1. 查询 `contextPlanRunJSON` 为非终态的消息。
2. 对有 `cloudTaskID` 的 run 调用 GET 获取权威状态，再订阅 SSE；不得重新创建云端任务。
3. 对本地检索阶段的 run 通过 coordinator 的 `runOrAttach` 挂接唯一 Task；不得双跑。
4. 若客户端被系统终止，重新打开后按同一 runID 恢复；旧 requestRevision 的结果直接丢弃。
5. 如果后端任务不存在或已过期，落明确失败态并给“重新规划”，不能永久保留三个点。

停止按钮必须取消具体 run：先持久化 `.cancelled` 和 revision，再取消本地 Task、调用云端 DELETE；云端取消失败不允许把 UI 重新点亮。迟到结果因终态/revision guard 被拒绝。

### 6.4 长结果的重新进入定位

- 正常完成时滚动到结果卡顶部，让用户先看到结论、未知条件和“为什么适合你”。
- 用户已经主动向下阅读时不抢滚动位置。
- 重进会话默认定位到该卡摘要头，而不是恢复到卡片中段或最底部。
- 卡片内部的展开/选择/日期编辑状态按草案 revision 保存；纯视觉展开态可本地临时保存，不影响计划真相源。

## 7. 证据与“你的记录”交互

### 7.1 扩展证据引用

在最终 draft 中引入类型化引用，不再只保存 contextID 字符串：

```swift
struct HoloContextEvidenceRef: Codable, Sendable, Identifiable {
    var id: String
    var contextID: String
    var contextVersionID: String
    var sourceDomain: String
    var sourceEntityID: String?
    var sourceRevision: String?
    var sourceCreatedAt: Date?
    var sourceEventAt: Date?
    var displayTitle: String
    var excerpt: String?
    var epistemicStatus: HoloContextEpistemicStatus
    var availability: EvidenceAvailability
}
```

`sourceDomain` 至少覆盖 thought、conversation、task、finance、habit、goal、health、memory。跳转由客户端 `HoloContextEvidenceNavigator` 根据 domain + entityID 解析，不把 SwiftUI 路由或 URL 直接交给模型生成。

### 7.2 用户界面

- “查看依据”整行可点，有展开/收起状态、点击区域和 VoiceOver label。
- “你的记录”不再是装饰性 Label；每条依据显示记录类型、时间、短摘录和“如何影响此建议”。
- 点击后优先打开原实体详情；对话证据定位到对应 message，想法打开想法详情，任务/目标/财务进入真实详情。
- 找不到原实体时显示“原记录已删除或当前不可访问”，不跳到空页面。
- 一般常识显示“通用建议”，不冒充个人记录。
- 推断显示“基于记录的推测”，允许用户纠正；不得使用“冲动消费”“自控力差”等人格化标签。

### 7.3 权限、删除与遗忘

- 卡片打开和最终保存前重新解析 evidence availability 与 access generation。
- 用户关闭某类数据授权后，不再展示对应 excerpt，也不能继续以其作为保存依据。
- 用户删除/遗忘来源时，清除可还原正文的缓存；历史卡只保留“该依据已不可用”的最小审计状态。
- 云端快照遵守已有即焚语义：任务完成/失败/取消销毁输入；结果落地并 ack 后销毁云端结果。
- 日志只记录 runID、stage、source domain 数量、错误码和耗时，不记录原始记录、摘录或用户问题。

## 8. 日期、选择与写入语义

### 8.1 日期必须三态化

```swift
enum ContextPlanDateSelection: Codable, Sendable {
    case unset
    case suggested(date: Date, basis: String)
    case confirmed(date: Date)
}
```

规则：

1. `unset` 显示“未设置日期”，不创建 DatePicker 的今天默认值。
2. 用户只说“出发前 3–5 天”但没有出发日时，保留 relativeTiming，不转换成绝对日期。
3. 已知并可验证锚点时可以生成 suggested date，但必须标“建议日期”，用户确认后才变为 confirmed。
4. 保存接口只接收 confirmed date；unset 保存为 nil，不读取控件临时值。
5. 时区、全天任务和 TodoTaskDatePolicy 继续复用任务模块的唯一日期语义，不在规划卡另写一套。

### 8.2 默认选择

- 不再默认全选所有 task/checklistItem。
- 无未决前置条件、低风险、无需猜日期且与用户请求直接相关的项目可以默认选中。
- 依赖出发时间、预算、同行人、证件状态或外部政策的项目默认不选，并明确展示“确认 X 后可加入”。
- information 与 adjustment 不作为待办写入候选。
- 保存按钮旁显示将创建的真实数量和无日期数量；数量必须来自当前 selection state。

### 8.3 执行可靠性

- 保持 `runID + draftRevision + itemID` 幂等键。
- 用户确认时再次校验草案 revision、来源权限、日期状态和选中项前置条件。
- 部分保存失败要逐项回执；重试只执行未成功项。
- 不因重新进入页面或重新展开卡片重复创建待办。

## 9. 事实口径与可信表达

### 9.1 四类信息

| 类型 | 展示 | 例子 |
|---|---|---|
| 已记录事实 | 你的记录 | “Holo 中最近没有收入记录” |
| 用户明确陈述 | 你告诉过 Holo | “你说计划在秋天出发” |
| 基于记录的推断 | 推测，允许纠正 | “这次可能需要更保守地留预算” |
| 外部规则/通用常识 | 通用建议或待核验 | “出发前核对护照、签证和入境要求” |

禁止把数据缺失表达为零值或事实。例如：

- 错误：“近期收入为零。”
- 正确：“Holo 最近没有查到收入记录；这不代表你实际没有收入。”

- 错误：“你有冲动消费历史。”
- 正确：“从 Holo 当前可用记录无法确认稳定的消费模式。”

### 9.2 外部事实核验

护照有效期、签证、入境、健康申报、航司行李规则等都可能变化：

- 未调用权威来源核验时，计划项写成“核对最新要求”，不直接声称“必须至少 6 个月”等结论。
- 若后续接入联网核验，证据需包含来源 URL、机构、核验时间和适用范围；过期后自动降为“需重新核对”。
- 模型参数知识不是“已核验”。

## 12. 测试矩阵

### 12.1 路由一致性

- 同一句录屏文案连续 100 次，route intent 与 routeSource 一致。
- 同文案退出重进、跨会话、新装首启不因 UI 生命周期改变路由。
- 同义表达覆盖旅行、搬家、考试、就医准备、项目发布、重要决策。
- 反例覆盖“帮我建一个去日本的待办”“查日本消费”“日本现在几点”“记录机票 3000 元”。
- 模型返回 ordinary 但 deterministic high-confidence 命中时，稳定层结果不被覆盖。

### 12.2 生命周期

| 场景 | 预期 |
|---|---|
| intent 未返回时退出重进 | 显示最后持久状态，不空白 |
| 本地检索时退出重进 | attach 同一 run，不创建第二个 run |
| 快照已上传后退出 | 云端继续，重进读取同一 cloudTaskID |
| SSE 断线 | GET 同步最新 revision 后重连，不倒退 |
| 结果回传时切后台 | 结果最多落地一次 |
| 用户停止与结果同时到达 | cancelled 终态胜出，迟到结果不展示 |
| 云端完成、ack 响应丢失 | 可安全重复 ack；结果不重复建卡 |
| 后端任务过期 | 明确失败并可重新规划，不永久等待 |
| App 冷启动 | 重建非终态 run 并 reconcile |

### 12.3 状态真实性

- 未开始个人记录检索时不得显示“正在查找记录”。
- 未进入云端 running 时不得显示“正在云端整理”。
- 无真实计数时不得显示读取条数。
- heartbeat 不推进业务阶段。
- stage revision 乱序时 UI 不回退。
- debug 导出不含用户原文、证据摘录、Prompt 或模型内部推理。

### 12.4 证据

- thought/conversation/task/finance/habit/goal/health/memory 各至少一个可跳转夹具。
- sourceID 不存在、版本变化、删除、遗忘、权限关闭均有明确状态。
- 一般常识没有“你的记录”标签。
- inference 有限定语且支持纠正。
- 同一来源不重复计数、不过度放大。

### 12.5 日期与保存

- unset 显示“未设置日期”，保存 nil。
- relativeTiming 无锚点不转换日期。
- suggested date 未确认不写入。
- confirmed date 按现有 Todo 日期政策落库。
- 时区切换、跨日、全天任务一致。
- 双击保存、退出重进、部分失败重试不重复创建。

### 12.6 可信表达

- 无收入记录不得生成“收入为零”。
- 数据不足不得生成“有冲动消费历史”等人格结论。
- 未联网核验不得断言签证/护照实时要求。
- 来源冲突时显示不确定性，不随意选一条。
- 无个人来源时仍可给通用方案，但明确“本次没有使用你的记录”。

### 12.7 UI 与可访问性

- Dynamic Type、深色模式、小屏、长标题和 20+ 条计划项。
- VoiceOver 可读当前阶段、依据展开状态、来源类型和保存数量。
- “查看依据”“你的记录”的点击区域至少符合项目通用可点击尺寸。
- 完成/重进时定位卡片顶部，不抢夺正在阅读用户的滚动位置。

## 15. Definition of Done

只有同时满足以下条件，才能称为“本次问题已完成”：

- 录屏原句重复 100 次均进入同一路由，正负语料通过。
- 规划失败不再通过 `try?` 静默回落。
- 运行态不是空白消息，页面退出、重进和冷启动均能恢复同一 run。
- 用户始终看到真实阶段；云端阶段来自服务端任务状态，不是定时轮播。
- 结果在同一消息原位落卡，不再同时保留一份普通答案和一份个性化答案。
- “查看依据”和每条“你的记录”可交互；来源不可访问时原因明确。
- 删除、遗忘和权限关闭后不泄露旧摘录。
- 未知日期不显示今天、不保存假日期；相对时间语义保留。
- 有未决前置条件的任务不默认勾选。
- 数据缺失、推断、个人事实和外部常识的口径通过测试。
- 停止、断网、SSE 断线、结果迟到和重复领取均不产生双任务或卡死状态。
- iOS 专项测试、相关全量测试、Debug/Release build 按项目实际能力通过；真机矩阵有记录。
- 后端改动本地测试通过，并在报告中明确“需要部署后端”；只有生产发布和真实端点验证完成后才能写“线上已生效”。
- 未回滚、覆盖或提交工作区中的无关改动。
