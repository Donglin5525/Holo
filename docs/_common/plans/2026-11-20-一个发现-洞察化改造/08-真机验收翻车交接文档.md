## 三、头号嫌疑（接手第一件事，1 分钟可验证）

**「每天最多一张」的当日消费标记挡住了展示：v4 卡已经在手机队列里，但要明天才显示。**

推理链（全部有据）：
1. 13:47 那张卡如果**没**入队（客户端解析/入队失败）→ build 60 打开发现页时队列空 + 当日尝试标记已释放（键 v3）→ **必然发出新调用**——但服务端 05:47 后零调用
2. 零调用的唯一解释：`refreshIfNeeded` 在 `guard store.queue.isEmpty` 处静默返回 = **队列里有卡**
3. 但他看不到 → `todayCard()` 被前置条件挡住。`consumedToday`（每天一张，拍板口径）为真的条件：他今天对**任何一张卡**点过按钮——四轮排障中他极可能在某轮对那张旧「日记」卡点过「对/不准」
4. 结论：**今日名额已消费，v4 卡在队列里等明天**

## 四、次级嫌疑（按概率排序）

1. **评审页 UI 刷新链**：`DiscoveryReviewSheet.reload()` 里 `todayCard` 是 @State，在 `await` 链后赋值；页面频繁刷新（通知/scenePhase）会取消进行中的 .task，若取消恰好发生在赋值前，UI 保持旧态直到下次完整 reload。查法：lldb 断点 / os_log 打点 `DiscoveryTopicStore.shared.todayCard()` 的返回与 sheet 的 todayCard 赋值。
2. **客户端解析/入队链某环节 throw**（InsightDraftParser → 终检 → CardBuilder → enqueue）：任一 throw 都会走 noCardToday 且会写当日尝试标记——但那样 build 60 会再发调用（与零调用矛盾），概率低。os_log 通道：subsystem `com.holo.app` category `DiscoveryInsight`（服务里已有完整日志点），Xcode 控制台直接过滤。
3. **卡片被 todayCard 过滤**：`rejectedTopics.contains(topicKey)`（angleKey=work_health_tradeoff×u_goal_0，是新的，不应命中）/ `windowEnd` 过期（builder 设 28 天，不应过期）——概率很低，读 UserDefaults 里 queue JSON 一眼即知：
```lldb
po UserDefaults.standard.data(forKey: "holo.discovery.topic.queue.v1").flatMap { String(data: $0, encoding: .utf8) }
```
这个 dump 同时能确认队列里到底有没有那张卡（卡体含 "version":4 与 headline）。
