# Holo 深度分析：场景提示词与可信分析链路落地方案

> 2026-09-19 · 接续《能力入口与深度分析场景规划》。状态：**产品/工程实施方案，未改业务代码、Prompt、后端或生产配置；未运行真实模型、模拟器或真机验收**。本方案据当前工作区源码和一次只读最小复现形成；线上有效 Prompt 版本与来源尚待发布前核验。

## 0. 产品结论

东林说“提示词弱”，首先指向用户点进深度分析后看到的七句预填问题：目前多是“深度分析一下最近的 X，重点看 A/B”，像功能说明，不像用户真正想解决的问题。应换成**一个明确疑问 + 一种可核对的比较/定位 + 诚实的数据边界**；内部分析方法不塞给用户。

但只改这七句会抬高期待、放大错误：目前云端实际吃通用 `agent_loop` Prompt，通用 Prompt 要求的固定工具、按月基线、跨域对齐和部分派生，云端并不完整支持；云端对时间范围和空结论的校验也不足。建议按“**先可信，再变聪明，最后更会表达**”三道门实施：

1. **P0 正确性门**：修云端工具能力与 Prompt 的冲突、时间/证据/空结论守卫；保留旧入口，不放出更强承诺。
2. **P1 场景任务门**：上线七个可编辑问题与显式分析模式，把用户选择的场景、时间和问题作为同一 `AnswerTask`，而不是靠问句是否逐字相等猜意图。
3. **P2 表达门**：在已验证结果上优化主结论、关键依据、数据缺口和可选下一步；用冻结样本盲评，不靠加长 Prompt、加 token 或换模型证明“更深”。

最终用户感知应是：**“我知道该问什么；Holo 查了我有的记录；第一屏直接答了问题；点开能看到依据；缺数据时明确说不能判断哪一部分。”**

## 1. 当前事实与根因，不把旧方案当现状

| 层 | 当前证据 | 用户影响 | 处理优先级 |
| --- | --- | --- | --- |
| 场景问句 | `AnalysisScenarioPanel.swift` 有跨域、财务、习惯、健康、任务、想法、目标复盘七个分析问句，另有“长期模式”普通问答；多数写“分析一下最近……” | 不知道点进去将得到什么结论，也难把自己的具体问题带进去 | P1 |
| 选中后的意图 | `ChatViewModel.resolveSendRoute` 只在用户文本与模板完全相同时确定性走分析 | 用户认真改写问题反而可能失去所选模式 | P1 |
| 实际生效 Prompt | 云端首轮 `cloudAnalysisExecutor.js` 注入后端 `agent_loop`，当前本地默认 v21 拼装后约 11.2k 字符；生产可能由 SQLite 最新版本覆盖 | iOS `PromptManager` 的改动不能单独影响这条云端路径；本地版本不是生产真相 | P0 发布前核验 |
| Prompt 与工具 | 通用模板自称请求 iOS 本地工具，并要求部分固定 query、90 天按月基线、跨域工具；云端主要能执行快照 `dynamicPlan`、`snapshot_rows`，快照构造未预取 statics | 模型照指令请求无法执行的工具，多轮浪费后退成笼统回答 | P0 |
| 时间与比较 | `cloudAnalysisQueryEngine.execute` 不应用 `plan.timeRange`；只对 `groupBy.type=field` 分组，baseline/linearTrend/coverage 等会拒绝 | “这个月”可能混入其他月份，月度比较可能变成全窗口总计 | P0 |
| 最终结论与依据 | `validateAgentLoopContent` 接受空 `final_claims`；主要校验 JSON 结构，不按本次工具结果验证 Evidence 数值与引用。云端返回结果的 iOS `CloudClaim` 不保留 `metricAssertions` | “完成”不等于回答；数字/依据可能无法逐项核对 | P0 |
| 叙事保真 | 当前代码已落库、领取、解码 `narrativeSummary/keyInsight/interpretation`；旧 9/15 方案写的“字段丢失”不再能当当前结论 | 不应重做一套叙事字段或第二套 Renderer，先验当前真实质量 | 保持、回归 |

只读最小复现：快照有 8 月 ¥10 与 9 月 ¥20 两条；请求 `timeRange=九月`、`groupBy=month` 后云端返回单个 `all=¥30`。另一个复现里 `final_claims` 的 `claims=[]` 被判 `valid=true`。这证明代码级契约缺口，不证明线上目前每份报告都会错。当前生产有效 Prompt 的 source/version/digest、真实模型失败率仍未知。

## 2. 七个场景的用户可见问句：可直接替换的文案

原则：用户只需表达想知道什么；统计口径、工具名、证据规则放在内部任务契约。下表是**预填的可编辑正文**，不自动发送。时间默认可由独立范围选择器提供“最近 30 天/本月/自定义”，用户改范围时更新正文或在发送前清楚展示；用户自己指定的时间始终优先。没有相关数据时不把问句伪装成已能回答的承诺。

| 场景 | 推荐预填问句 | 为什么比现行更强 | 发起条件/边界 |
| --- | --- | --- | --- |
| 跨域洞察 | “最近有哪些生活节奏是在同一段时间一起变化的？请先找最值得核对的一组，告诉我各自发生了什么、时间是否对得上，以及还有什么不能确定。” | 从“把所有数据放一起”变成一条待核对的关联 | 至少两个可比较的数据域和一致的时间窗；真正的同步/关联判断须等对齐查询能力验证通过。否则只可展示跨域并列事实，不叫“关联”。 |
| 财务分析 | “最近的钱主要花在了哪里？是少数大额支出，还是多笔小额慢慢累积？如果与上一段可比时间不同，变化主要来自哪些分类？” | 给结构、频率与变化三个可解释角度，直接服务“钱花哪了” | 有流水才能回答；无分类/预算时不说“哪类超预算”；比较能力未验收前不承诺“比上一段”。 |
| 习惯分析 | “最近哪项习惯的记录出现了明显变化？我更容易在哪些时候中断，又通常怎样重新开始？” | 从“坚持情况”转向断档与恢复两个可行动问题 | 有计划频率才判“中断”；没计划频率只说记录间隔，不把非计划日判失败。 |
| 睡眠与健康 | “最近我的睡眠时长和作息节奏有变化吗？哪些天与平时不同，现有记录能说明到什么程度？” | 将“健康状况”收窄到可观察的睡眠与作息 | 只在授权且有对应观测时分析；无阶段数据不推“睡眠质量”，不作医疗诊断。 |
| 任务效率 | “最近完成了哪些任务，还有哪些重要任务尚未推进？从已有的截止时间看，最值得我先处理的是哪一件？” | 直接形成下一步决策，而非泛说“拖延模式” | 需有任务状态/日期证据；没有历史状态就不说“一直停滞”，没截止日不判逾期，也不能从未完成推断心理性拖延。 |
| 想法洞察 | “最近我反复记下了哪些主题？哪些想法在变化，哪些只是重复出现但还没有结论？” | 将“想法走向”变成可引用、可比较的主题演变 | 必须有可访问的想法记录；引用受权限/遗忘约束，不给人格/心理标签。 |
| 目标复盘 | “我选的这个目标现在走到哪一步？哪些已完成的行动真的推动了它，下一步该继续、调整，还是先暂停？” | 与“一起想清楚新目标”区分：这里复盘已有目标 | 先选 Goal；P0 无已实现的重规划写回时只给分析与建议，不能暗改目标/任务。 |

第一屏只露 2–3 条推荐问题及“更多分析场景”，推荐必须基于**可验证数据**；没有可用数据时提示“这些问题需要记录才能回答”，提供普通提问或补记录路径。长期模式继续作为普通问答/记忆入口，不显示在“消耗深度分析额度”的目录中。跨域、比较等当前不可靠的承诺，在 P0 完成前保持旧文案或置为“待支持”，不能先上新入口文案再补底层。

## 3. 内部 Prompt 的新分工：短任务、真工具、硬校验

### 3.1 三层输入，不再让一句自然语言承担所有职责

1. **用户可见问题**：上表正文，用户可自由改写；保留原话。它只描述意图，不嵌工具指令。
2. **确定性 `AnalysisAnswerTaskV1`**：由客户端现有时间语义解析/用户选择与后端能力目录共同形成；至少含 `scenarioID?`、`userQuestion`、`questionKind`（事实/比较/诊断/关联/决策）、`primaryTimeRange`、`baseline?`、`snapshotCutoffAt`、`requestedDomains`、`answerChecklist`、`runtimeCapabilities`、`availableSources`。缺字段先用 `unknown`，不让模型补猜。问题可能包含多个子问，清单逐一标明“可回答/缺证据”。旧客户端只传 question 时，后端建保守默认任务；不破坏旧版本。
3. **模型任务层**：只负责选择目录内可执行的工具、比较已验证证据、用自然中文解释；数字、时间、建议优先级和是否可交付由代码/Verifier 决定。`PROMPT_GUIDELINES.md` 的 Persona Preamble 保持唯一来源，不在分析 purpose 重写人格。

`AnalysisAnswerTaskV1` 不是另建一套通用 Agent，也不复制长期记忆。它是当前云端任务在一次分析中需要的最小权威范围与回答目标；数据快照仍沿用现有加密/即焚通道。若未来需要跨设备个人情境，另按授权与最小注入决策，不在这次 Prompt 优化中擅自上传更多原文。

### 3.2 `agent_loop` 下一版的具体改写原则

- **删掉或条件化 v21 的无条件命令**：不再“凡分析题首轮都查近 90 天按月”“财务/睡眠至少 3 维”“总要串出跨维度金句”“预算/健康都做月底推算”。只有问题确实需要趋势、数据与工具支持、范围允许时才查。没有真综合发现时 `keyInsight=null`。
- **共用骨架改为运行环境中性**：把“本地 iOS 工具”改成“只使用本轮 `runtimeCapabilities`/工具目录列出的能力”；固定 query 仅在当前目录显式支持时可调用。云端目录明确列“已支持 / 未支持 / 数据缺失”，不能靠 appended 文本去覆盖前文相反命令。
- **先回答问题，再追加探索**：先把用户的子问映射到最少的可执行查询；第一轮无需因为“深度”而泛查所有域。若要解释变化，再申请同口径比较与足量样本；若有足够证据才提出一条最重要发现。用户没要建议时，不强送行动数字。
- **给模型 3–5 个真实边界范例**：例子覆盖“财务有流水无预算”“健康只有时长无阶段”“目标有进度但无行动关联”“跨域仅时间并列而无对齐证据”“用户只问一项数字”。示例必须标明是合成演示，不能让例子数字流入结果；每例包含期望工具选择、可回答部分、缺口与禁止断言。
- **硬 JSON 契约保持独立**：`need_tools`、`need_more_analysis`、`final_claims` 的 schema、Evidence ID 与 metricAssertion 仍在合同段；不要再将工具规范、人格、领域菜单、示例和输出格式混成一个长段。沿用现有附录注册机制，但用新的 vNext 段**替换**互相矛盾的 v21/旧固定工具指令，不是直接再追加第七段。

建议的任务段文案骨架（供实施者合并进当前模板；不是可直接上线的完整 system prompt）：

```text
【本轮任务】
优先回答用户此刻提出的问题。先识别明确的子问题和用户指定的时间、对象；只查询回答它们所需的数据。
本轮可用能力以随请求提供的工具目录与运行能力清单为准。未列出的工具、计算、数据域都视为不可用；工具返回错误时，不把失败或空值写成“用户没有这类数据”。
对每个子问题：能用当前证据回答就给直接结论；只有部分证据就缩小结论并说缺哪项；关键证据不存在就明确不能判断。不要为凑分析维度查询无关记录。
比较必须使用同口径、同长度且落在快照内的两个时间窗；趋势至少有足够多的可比时点。只把同现/相关说成同现/相关，不宣称原因。预算、健康阶段、目标进度等字段不存在时，不补猜。
最终先给一个直接答案，再给最多三项真正支撑它的发现；仅用户要求行动或存在明确风险时提出证据化下一步。没有可验证的跨维度综合发现时 keyInsight 为 null。
```

这段只告诉模型“如何在真数据里工作”。云端能力清单、范围和最终数值核验由代码生成/执行，不靠模型承诺。专业/陪伴/日常语气仍由统一 Persona 处理。[Anthropic 官方提示词指南](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-templates-and-variables)关于清晰任务与多样范例的建议可作写法参考，但是否适合当前模型必须由 Holo 冻结样本验证。

### 3.3 云端运行能力必须与 Prompt 同一真相源

P0 先选**不新增第二个 purpose**的低风险路线：继续用 `agent_loop` 的现有路由/额度与服务端 Persona；把通用模板改为环境中性，云端执行器从查询引擎的能力定义生成专属目录。本地 Agent 仍使用本地工具目录。若后续证明两个运行环境的任务规则长期分歧，再评审拆 `cloud_agent_loop` purpose；本轮不默认增加新的计费、Prompt、日志与版本面。

云端能力最小表：

| 能力 | P0 处理 |
| --- | --- |
| `dynamicPlan` 基本聚合、字段分组、`snapshot_rows` | 保留，目录和错误码与执行器共用定义；验证参数中的 dataset/field/type |
| `timeRange`、快照截止、日/周/月分组 | 实现/修复确定性过滤与分组；用户范围优先，截断未来数据；单元测试先于 Prompt 放量 |
| `baseline` 与 difference/percentageChange | 要么实现为确定性、可对账的工具指标并测试，要么把“与上一段比较”从 P1 问句/目录中下线；不能继续让 Prompt 要求而工具返回不支持 |
| 固定 query、`cross_domain.aligned_analysis`、linearTrend/coverage/expression | 未实现时从云端目录和云端方法学中排除；跨域同步类场景暂不许诺“找到关联”。要上线须补对齐工具、样本/覆盖规则、证据与回归 |
| `statics` | 设备快照确有预取数据才列；当前快照构造只包含 `datasets`，目录不可暗示固定块总存在 |

时间契约：`primaryTimeRange=[start,endExclusive)`、`snapshotCutoffAt` 在 Job 冻结；引擎对 `occurredAt` 先过滤再聚合，时区为用户选择/设备传入的明确时区，历史查询 `end=min(requestedEnd,snapshotCutoffAt)`；组桶与范围标签都从同一冻结任务生成。发生在未来的分期/待办不得进入已发生的历史结论。`eventRecords`（交易/任务/想法）不能按日历空白天数报“覆盖率低”，`dailyObservations`（睡眠/步数）才可以按观测天数说明趋势可信度；复用现有覆盖策略，不在云端另写一套比例阈值。

### 3.4 结果交付不是“JSON 合法”

在 `final_claims` 落库、提交额度、推送“完成”之前增加云端专用交付核验：

- 非空直接答案；每个已声明可回答的子问题被回答，不能用一堆数据绕开主问题。实在不能回答时产出**可解释的缺口终态**，不是空 `claims` 却 `completed`。
- 每条数字型 claim 的 `metricAssertions` 与本次工具 Ledger 的 `metricKey/value/unit/range` 一致；Evidence ID 使用单一 canonical ID，不再让工具事件 ID、metricKey 和 UI 引用彼此不匹配。重复血缘不算两条独立证据。缺失引用时拒绝或降级，不回退为“把整个证据池都当依据”。
- `keyInsight`、`narrativeSummary`、`interpretation` 只能概括已过核验的 claim；与 claim 冲突的数字、范围、因果或人格判断直接清空该叙事字段并安全回退。保留当前字段保真链路与旧结果的可读兼容。
- iOS 的 `CloudClaim` 需接收必要的结构化指标/来源范围，或后端完成核验后返回可验证的 compact receipt；不能只把 `displayText` 当成数字真相。卡片和报告详情消费同一已核验结果，不再各自猜事实/建议层级。

此步骤沿用 `Holo-Agent研发与验收规范.md` 和已采纳的统一答案 ADR：Verifier 决定可交付，Renderer 决定呈现，模型不能用自然语言绕过。对“缺数据”可降级但不惩罚用户；对范围/金额/证据冲突不包装成普通完成。

### 3.5 一条完整样例：财务问题如何真正变“深”

以下金额均为**合成示例，不代表用户数据**。用户选择“财务分析”，将问句改成“8 月的外卖是不是比 7 月花得多？主要是次数多了还是每次更贵？”并发送：

1. `AnalysisAnswerTaskV1` 固定 7 月 1 日至 8 月 1 日、8 月 1 日至 9 月 1 日两个不重叠自然月；检查时区、快照截止和“外卖”分类是否可识别，保留用户原话与两个子问。
2. 云端分别取两个范围的外卖**总额、笔数、均笔金额**，每个数字来自同一口径的流水 Ledger；如果部分交易未分类，只能报告“已分类外卖记录”的结果及遗漏范围。
3. 假设 7 月 10 笔共 ¥300，8 月 12 笔共 ¥420，则可答：“按已分类的外卖记录，8 月比 7 月多花 ¥120；笔数从 10 笔增至 12 笔，均笔从 ¥30 增至 ¥35，因此次数和单笔金额都上升。”每个数字带范围、单位与可下钻的 canonical Evidence ID。若原始流水不支持均笔计算，退回总额/笔数事实，不编造“主要原因”。
4. 若缺 7 月流水、用户改问尚未结束的 9 月却没同意按相同已过天数比较、或“外卖”混用多个分类，就明确说明哪一问无法比较，给出可选的同口径分析路径；不能输出“8 月外卖增长 40%”再附一句含糊免责声明。

这条样例是验收合同：**直接回答两个子问、比较范围一致、可核对每个数字、知道何时不答**。更长的分析文字本身不是成功标准。

## 5. 冻结评测与 Go/No-Go

建议 40 条新增冻结题：七场景各 4 条（正常、有部分数据、零数据、用户改写/范围边界）=28；另 12 条对抗题覆盖“明确月份 vs 快照 180 天”“月比月”“未来分期”“无预算问超支”“只有睡眠时长”“任务无截止日”“目标无关联行动”“跨域仅 3 天对齐”“重复 Evidence”“错误 Evidence ID”“空 final_claims”“用户不想要建议”。冻结前按数据与能力目录给每题标注 `answerable / partial / unavailable / invalid` 的**预期类别和正确答案要点**，不能让模型自行决定“不可回答”就算过。和已有 29 条离线素材分开记录，不能用调 Prompt 的样本冒充未见集。测试数据仅合成/脱敏，不含真实原文。

| 层级 | 必须看到的证据 | Go 门槛 |
| --- | --- | --- |
| 纯逻辑/组合 | 云端 Query Engine→Ledger→Verifier；数值、时间、单元、范围、证据 ID 测试 | 上述 P0 事故复现全部通过；空结论、错误引用、未来历史混算 **0 容忍** |
| Prompt 协议 | 有效 source/version/digest、支持工具请求率、JSON 恢复、7 场景子问覆盖；分别统计预标的可回答题与边界题 | 可回答题直接答案与子问覆盖率目标 ≥90%；边界题的拒假/正确降级 100%；不得靠一律称“缺数据”凑通过；不支持的固定工具请求不能当成功完成 |
| 真实模型盲评 | 同模型/同快照旧版与新版随机遮蔽比较，至少两人按“直接回答、洞察价值、克制、可读”评分，分歧复核 | 新版总体偏好率目标 ≥70%；任一场景若事实/安全退化则 No-Go，不用平均分掩盖 |
| 性能/成本 | 每题轮次、请求 token、成功成本、p50/p95 耗时与失败/取消率对比 | 必须报告分布与原因；若明显劣于基线，先缩无关探索，不直接加 token 或换模型 |
| iOS 旅程 | 选场景→改问题→发起→锁屏/返回→同一报告→证据下钻；额度/拒绝云端/缺数据/中途取消 | 明确“已完成”只对应真结果；专项测试有非零断言，模拟器与真机分层通过 |
| 生产 | `/v1/release/status`、`/v1/prompts/meta`、Prompt source/digest、目标版本和至少一条已授权真实请求 | 与本地评测的 Prompt/路由一致；仅 health 200、提交或 push 不算上线 |

回滚先让新场景文案/任务元数据回到旧入口，保留旧客户端兼容；Prompt 要在 **SQLite `prompt_versions` 中按历史版本回滚/另建回滚版本**并核对 source/digest，不能以为只回退 Docker 镜像就覆盖数据库中的有效 Prompt。云端正确性修复（时间过滤、证据拒假）不因表达 A/B 输了而回退；若它们有兼容事故，再单独回退至上一已验证后端版本，保留已保存报告和用户数据。跨域/比较能力用独立开关或可见状态降级，不强行回到假关联。
