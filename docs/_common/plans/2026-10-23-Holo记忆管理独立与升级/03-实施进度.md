## M03-b 前置备份口径（2026-10-23 核实并拍板）

红线原文写的是「App 内全量导出备份」，但**App 目前没有全量导出功能**（DataExportService 仅财务交易 CSV/JSON；CloudRepull 的备份是重拉流程内的回滚件，不能独立触发）。与东林确认的实际口径：

- **东林操作**：iPhone 用 Finder 做一次**加密备份**（数据线连 Mac → Finder 选设备 → 备份到此电脑 + 勾选加密 → 立即备份）。这是今天最实在的全量保险，不需要给我 CloudKit 或任何账号权限（CloudKit 控制台对本项目是禁入红线，我也从不需要它）。
- **兜底事实**：数据真源本就在 CloudKit Development 容器（云端始终有）；M03-b 纯增量（新表+可选字段），Core Data 迁移失败的模式是拒绝打开旧库（保守失败），不会清库；隔离容器全量演练绿后才装包。
- **顺带记录的产品债**：全量导出/备份功能缺失，可作为后续独立任务立项。

## M03-b 交付清单（2026-10-23 东林质询「其他用户怎么办」后修订）

**背景**：东林指出备份口径只覆盖开发者本人（Finder 备份），上架用户无备份路径。重新审视后确认：迁移保护链本身不依赖备份（见下），但存在一个真空白——「迁移后库能打开但数据不对」时云端副本会被污染。修订如下：

**新增交付：迁移前自动快照（对所有用户自动生效，零操作）**
- App 检测到 Core Data 模型版本变化时，加载前先把本地库文件整份备份（复用 CloudRepull 已有的文件级备份机械 `backupAndRebuildStoreForCloudRepull` 一族）。
- 快照保留至确认新版本运行健康（固定观察期），期间可通过现有恢复门（StoreConflictRecoveryGate）提供「回到升级前」入口。
- 验收矩阵补充：A31 之外加「迁移后数据异常 → 快照恢复」用例；隔离容器演练「新库写入后回滚快照不丢旧数据」。

**既有保护链复核（2026-10-23 代码核证，均为现状而非新承诺）**：
1. 轻量自动迁移已开启（CoreDataStack:104-105 NSMigratePersistentStores + NSInferMapping 两选项）。
2. 迁移失败 = 可恢复失败状态，保留原库等待救援（R01 改造，CoreDataStack:121-124）；**全项目唯一 destroy 路径是开发调试 reset()**，用户路径无删库兜底。
3. 数据云端完整副本（iCloud），本地损坏可重拉（CloudRepull 通道已存在）。
4. 发版流程含 CloudKit 生产 schema 先部署 + 模拟器门禁 + App Store 分阶段发布。
5. 事实佐证：1.0→1.1.3 已完成十几次加表类迁移，上架用户零迁移丢数据事故。

**定位澄清**：全量导出 ≠ 迁移保险（用户不会恰好在升级前导出；且云端副本已覆盖本地损坏场景）。它的定位是「数据主权」产品能力，维持独立任务立项不动。

**东林个人备份（2026-10-23 再修订：从「开工前置」降级为「个人建议」）**：东林质询「普通用户不需要、我也不需要？」——推理成立：自动快照随 M03-b 构建生效，他的设备做迁移那一刻已与普通用户受同一套自动保护。Finder 备份不再是开工闸门，降级为纯个人建议（10 分钟性价比高：他是第一个用真实数据跑新代码的人，且 Development 容器单租户无第二份）。**工程侧两道硬保证取代人肉闸门**：①快照完整性先行——快照失败即拒绝迁移、原样退出（沿用 CloudRepull「失败即回滚」护栏哲学）；②隔离容器全量迁移演练 + 模拟器门禁先行，全绿才谈装包。
