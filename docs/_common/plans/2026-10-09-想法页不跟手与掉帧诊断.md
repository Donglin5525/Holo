## 产品结论

“滑动不跟手”需要同时检查交互规则与帧更新耗时。当前源码存在明确的侧栏手势连续性缺陷，另有主线程数据读取、长文预览首次计算和高频页面更新等性能风险。建议先固定真机基线，修复手势规则，再根据 trace 收敛性能热点。不能只调整动画时长或把所有任务包进 Task。

## 1. 已确认的侧栏手势规则问题

### 1.1 拖到展开边界会取消当前拉出手势

证据：

- `Views/Thoughts/ThoughtsView.swift:121`：位移达到宽度减 0.5 时视为停靠展开。
- `ThoughtsView.swift:200`：拉出识别器在停靠展开时停用。
- `Views/Thoughts/ThoughtSidebarSupport.swift:359`：更新 UIView 时直接设置识别器 isEnabled。
- `ThoughtSidebarSupport.swift:407`：拉出识别器的 cancelled 分支调用 onEnd(0, 0)。
- `ThoughtsView.swift:203`：零位移、零速度按“不展开”结算。

Apple 明确规定：识别期间把 isEnabled 改为 false，识别器会进入 cancelled。由这些分支可推导：手指还在拖动、侧栏刚到展开边界时，下一次识别器更新可能让侧栏反向收回。这是明确的源码逻辑缺陷；它是否发生在录屏里的某一次拖动，仍需手势事件日志或真机复现确认。

### 1.2 从部分展开位置继续拖动，位移基准不连续

证据：`ThoughtsView.swift:188` 关闭计算固定使用 sidebarWidth + translation；拉出计算固定使用 translation。两条手势没有记录起手时的可见位移。

当关闭手势从部分展开处接管时，以宽度 340、起点 120、左拖 10 为例：当前公式得到 330，连续跟手应为 110，差 220。该数值是条件场景下的公式回放，不是录屏测量。

快速反向、松手回弹中再次接管等场景，需要从当前可见位置继续，不能重新假设起点为完全开/完全关。SwiftUI 的动画目标值也不能直接当成屏幕上的实际位置。

### 1.3 起步存在二次方向确认

拉出手势使用 `Utils/HorizontalGestureLock.swift` 默认横向确认距离 12pt；关闭手势使用 4pt。它们在 UIPan 已识别后还等待 changed 回调进行确认，部分起步延迟来自手势规则，不代表 GPU 掉帧。

距离阈值有防误触价值；应在统一仲裁后校准，不能简单全改成零。卡片归档/删除、照片横滚、侧栏开合、左缘返回必须保留明确的让位关系。

## 3. 推荐实施顺序

### 第一步：建立同源真机基线

核对安装包版本、构建号、源码版本与编译优化设置；用实际 Release 优化的 Profile 包。不要把 Release + -Onone 当成发布性能。

在同一 iPhone、同一数据集、相近温度和电量状态下，分别录：

1. 首次进入想法页，随后立刻拖侧栏。
2. 快速开合二十次；到边界不松手；拖动中反向；回弹中重新接管。
3. 纯纵向快速滚动，分别覆盖首次浏览与重复浏览。
4. 长文、多标签、图片卡片；搜索结果与标签筛选。
5. AI 整理或同步期间重复上述操作。

用 SwiftUI instrument + Time Profiler 查更新范围、耗时调用栈；用 Hitches / Animation Hitches 区分应用提交与呈现阶段。必要时加入窄范围 os_signpost，标记手势开始/取消/结束、数据加载、预览准备与测量，不逐帧 print。

60Hz 每帧周期约 16.7ms，120Hz 约 8.3ms，且框架与系统共享预算。不能等业务代码花满整个周期才算超限。记录 hitch 次数、总延迟、P95/P99 更新耗时以及最慢调用栈；平均 FPS 不能单独做验收。

### 第二步：统一侧栏交互

- 用一个明确的手势所有者管理一次拖动；记录起手可见位移，以 startOffset + translation 连续计算，支持反向。
- “是否接收下一次手势”和“是否终止当前手势”分开；到边界只夹住位移，不通过禁用识别器取消正在进行的手势。
- ended、cancelled 与动画打断各自明确定义；取消也保留真实位置，不能把 onEnd(0,0) 当统一退出入口。
- 确认侧栏手势所有权后，卡片操作让位；纵向滚动、照片横滚、左缘返回保留原契约。
- 单独验证开到边界、部分展开再拖、边界反向、快速交替、回弹打断，补有意义的状态机测试。

### 第三步：缩小滚动和拖动时的主线程工作

以测得的热点为准，按以下顺序收敛：

- 连续位移尽量只影响容器变换、裁切和遮罩；列表只接收浏览范围、数据版本和离散交互状态，避免让完整内容准备跟着位移更新。
- 首次加载只有一个所有者。分页读取、批量预取展示所需关系；通知按变化 ID 增量更新，必要时合并到拖动结束后应用，但不能丢更新。
- 在后台 Core Data context 读取并生成不可变展示快照；主线程应用结果。禁止直接把 viewContext 对象丢入 detached task。
- 将内容节点、预览信息和标签/主题展示投影按内容版本准备一次；缓存必须覆盖内容、关系、宽度、字号等失效条件，不用无条件 Equatable 隐藏真实变更。
- 尽量让长文预览的工作量受显示需求约束，同时保持中文折行、Markdown、Token 和“查看全文”正确。解析与 UIKit 排版分工，UITextView 相关操作仍遵守主线程要求。
- 若 trace 证明正文版本 hash 是热点，统一按版本复用；不得以跳过 hash 验证换取速度，否则旧 AI 关系会错误继续展示。

### 第四步：按呈现证据优化视觉成本

只有提交阶段变轻后仍存在呈现热点，再对比固定内容宽度 + 变换/遮罩、独立阴影形状与当前整层阴影等方案。不盲目加 drawingGroup / rasterization：快照、纹理占用、失效与文字清晰度都有成本。

新行浏览若被渐显拖慢感知，可将错峰入场限定为页面首次可见行。保留首页光球等品牌资产；本次录屏没有证明它们是主因。

## 4. 验收与长期防回退

- 手指拖动期间侧栏连续、可反向；无因自身到边界造成的取消收回；动画被打断时从可见位置继续。
- 相同版本内容的稳态侧栏拖动不重新执行数据库全量读取、正文解码或整批投影；用 trace / 计数证据验收。
- 冷缓存、热缓存、长文、小数据与大数据分别测；不能只重复滚动同几张卡片。
- 优化前后使用同设备、同数据、同构建设置和同操作；保留 trace 对比，优先检查最长卡顿和 P95/P99，不以 build succeeded 代替性能验收。
- 无卡片误归档/删除，无照片横滚冲突，纵向滚动与边缘返回正常；Dynamic Type、iPad 布局、标签/主题实时变化不回退。
- 在固定测试库上建立滚动和侧栏操作基线，核心页面复用这套方法。生产用 Xcode Organizer / 系统性能指标看版本趋势；自定义侧栏与 UIScrollView 滚动需要分别取证。
