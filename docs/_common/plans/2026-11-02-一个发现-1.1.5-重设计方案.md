# 「一个发现」1.1.5 重设计：快模型 + 候选异步化 + 失败不烧名额

> 2026-11-02 · 分支 `1.1.5` · 根因调研见同目录 `2026-11-02-一个发现-根因调研与1.1.5方案.md`
> 本文是设计说明；**接口形状真源仍是 `HoloBackend/src/discovery/discoveryController.js` 的 `context.json(...)`**（跨端契约规范 §一）。

## 0. 为什么要改（一句话）

真机上候选阶段用的 qwen3.7-flash 开着思考，**每次 60–71 秒**。整条链路又要求 App 一直开在前台等结果，中途锁屏或切走，结果就丢了，当天名额也一起烧掉。修复分三层：

1. 换快模型，补上格式修复层；
2. 候选生成改成服务器后台任务，结果加密落库，不怕断连和重启；
3. 服务端原因导致的失败不再烧掉当天名额。

## 2. 新端点契约（S3）

两个端点返回**同一种形状**：`CandidateJobStatus`。字段固定齐全，不适用的字段给 `null`，不做双形状。

```jsonc
{
  "runID": "run-…",
  "stage": "candidates",
  "jobStatus": "running" | "completed" | "failed",
  "pollAfterSeconds": 3,          // running 时为整数，其余为 null
  "leaseExpiresAt": 1730000000000, // run 租约到期（毫秒），客户端据此放弃
  "result": null | { /* 与同步 POST /candidates 的 200 响应体逐字段相同 */ },
  "error": null | { "code": "DISCOVERY_MODEL_OUTPUT_INVALID", "reason": "time_range_value" | null },
  "retryAvailable": false,        // failed 且当天还有尝试次数时为 true
  "replayed": false
}
```

### 2.1 `POST /v1/discovery/runs/:id/candidates/async`

- 请求体和同步 `/candidates` **完全相同**：`{ runToken, data, requestID?, profileBrief? }`。
- 闸门和同步一致：身份 → run 归属 → token → 租约 → 控制/范围代数 → 限流 → `data.runID` 一致 → 阶段 hash 不可变登记。
- 通过闸门后把租约延长到 `now + asyncLeaseSeconds`（默认 24h），写入作业 `running`，然后在**进程内后台**发起模型调用，响应立即返回 `jobStatus=running`。
- 同 run 同 body 重放：返回当前作业状态（`replayed=true`），不会重复调用模型。同 run 换 body 返回 409 `DISCOVERY_STAGE_CONFLICT`。
- 密钥不可用：返回 503 `DISCOVERY_ASYNC_UNAVAILABLE`，客户端回落同步端点。

### 2.2 `POST /v1/discovery/runs/:id/candidates/result`

- 请求体：`{ runToken }`。用 POST 是为了不让 token 出现在 URL 和访问日志里。
- 核对 run 归属（subject + device）和 token。作业不存在返回 404 `DISCOVERY_JOB_NOT_FOUND`。
- 限流：独立的 `discovery_poll` 桶（每分钟 30 次、每天 600 次），不占聊天额度。
- `completed` 时，`result` 和同步响应同形，包括 `candidatesHash` 和 `replayed`。

### 2.3 核验阶段如何拿到候选包

`/verify` 比对候选包 hash（T34）时，先读内存缓存；没命中再读加密落库的作业结果，所以重启以后也能核验。核验成功后删除作业密文（即焚）。

## 3. 名额状态机（S6）

```
createRun ──► active ──candidates 成功(有候选)──► active ──verify 成功──► completed（当天用掉）
   │             ├─candidates 成功(无候选)──────────────────────────► completed（当天用掉）
   │             ├─服务端原因失败（格式/上游/中断/核验失败）──► cancelled + retryable=1
   │             │       └─ 同日 createRun：attempt_count < attemptsPerDay → 替换该行，attempt_count+1
   │             ├─用户取消/关闭/改范围 ──► cancelled（retryable=0，当天用掉）
   │             └─未 dispatch 即取消/过期 ──► 删行（名额释放，原口径）
```

- migration #26：`discovery_runs` 增加 `attempt_count INTEGER NOT NULL DEFAULT 1` 和 `failure_retryable INTEGER NOT NULL DEFAULT 0`，用 ALTER ADD COLUMN，存量行不受影响。新表 `discovery_stage_jobs` 只存元数据加密文，不存明文。
- 成本上限：每天最多 3 次尝试 × 每次最多 3 次格式重试 × deepseek 约 ¥0.02，每人每天约 ¥0.2，另有全局后台预算兜底。

## 4. 客户端改动（1.1.4 封板合入后实施）

1. capabilities 里有 `features.asyncCandidates=true` 时走异步：建 run → `candidates/async`（不到 1 秒返回）→ 把 `{runID, runToken, dayKey, 证据包}` 落本地（Application Support，`completeUntilFirstUserAuthentication`）→ 前台每 `pollAfterSeconds` 取一次件。
2. **每次前台激活先取件**；冷启动不再把待取件的 run 标为取消。
3. 取到 `completed` 后：本地门禁 → 反例召回（只能在本地做，隐私设计）→ `/verify`。核验包在 `beginBackgroundTask` 里，切走也能跑完。
4. `failed && retryAvailable` 时不锁当天，下次前台重新准备。
5. 热让位只在 `.serious/.critical` 生效（手机端只做一次本地扫描加网络等待）。
6. 契约测试：新增 `CandidateJobStatus` 三态字面量（抄 controller）+ capabilities 新字段；双端夹具新增「纯日期+偏移→修复」用例，自动进入 iOS 对拍。

## 7. iOS 端实施状态（2026-11-02 11:30）

提交 `c2a647d6b`（1.1.5 分支，未推送）。按东林的思路落地：**候选交给服务端后台算、算完缓存在服务端；手机交完材料就可以走，回来取件；取到候选后，反例召回、回源核版本、结构门禁全部在手机本机做**。服务端始终只看到本次批次已经上行的那部分证据，不需要把用户全部记录传上去。

| 环节 | 在哪里做 | 说明 |
|---|---|---|
| 扫描本机记录、挑材料 | 手机 | 与 1.1.4 相同 |
| 生成候选（最慢的一步） | 服务端后台 | `candidates/async` 交材料即返回；结果加密落库，重启不丢 |
| 取件 | 手机 | 前台约每 3 秒问一次，单次前台最多等约 4 分钟；没等到就留着下次取 |
| 门禁、找反例、回源核版本 | 手机 | 逻辑原样复用（抽成 `continueAfterCandidates`），只把挑出的反例块随核验上行 |
| 核验（约 1 秒） | 服务端 | 用落库的候选包比对 hash |

**被系统回收也能续上**：交材料前先把本次 run 的冻结信息和材料包写进本机 `Application Support/Discovery/pending-candidate-job.json`（首次解锁后可读、不进 iCloud 备份、run 结束即删、关闭发现即删）。下次打开 App 先看这张"取件单"，接着取，不重新扫描、不重开 run、不另占名额。

**失败不再白白烧掉一天**：候选作业失败时以服务端 `retryAvailable` 为准，可重试就 2 分钟后新开一批（本机同日最多再试 2 次兜底）；服务端说当天次数用完才关闸。

**与 §4 的差异**：没有读 capabilities 的 `features.asyncCandidates` 开关，而是直接试异步端点，老服务端（无路由 404）或密钥未配（503）即回落同步，本进程不再探测。少一个依赖，效果相同。§4 第 5 条资源让位阈值未改，不影响"算不出来"，留作后续体验优化。

**验收**：发现模块 iOS 测试 174/174；全量 2321 例中 9 处失败与未改动基线逐条一致（Moze 样本文件缺失、日期相关、文案「任务/待办」，均与发现无关，属 1.1.4 遗留）；变异检查确认新用例能抓到回归。
