## 0. 一句话需求与用户的真实期望

用户开启后，Holo 每天自动从其授权的**想法/任务/习惯**记录中，用 AI 找出「值得留意的变化与联系」，在对话页呈现一条，引用必须逐字可溯源，**宁可不发不可编造**。

东林的实际期望（多轮对话中反复确认）：**开着就不用管，某天打开 App 能看到一条有意思的发现**。他可以接受某天没有发现，但不能接受「功能开了却永远看不到第一条」「状态提示与真实原因不符」「连续多天反复修不好」。

**当前现实**：该功能自 10-26 上线以来，截至 11-02 凌晨，**用户真机零产出**。链路上每一个确定性故障已逐一修复（见 §5），最后一个已知拦截是 iOS 真机的热让位（thermal yield，§6.1）——但这暴露的是形态层面的根本问题（§7），不是再修一层能解决的。

## 2. 系统完整地图

### 2.2 服务端（Node/Hono，`HoloBackend/src/discovery/`）

## 3. 当前全链流程（9 步 4 闸，重设计时按需推翻）

```
[触发] App 启动/前台激活 → refresh()
  ↓ 调度状态机（内存：firstRunPending/dirtyMarks(恒空)/budgetResetAt/dailyBatchAvailable；
    持久：processedRecord；环境：资源让位{热/低电/输入中/手动AI/低数据}/网络探针{冷启动竞态,30s补查}）
[1] 扫描本地 CoreData 三域 90 天窗 → evidence 块
[2] POST /runs（日配额；429=DAILY_BATCH_USED 且 classify 锁当日——见 §5 问题A）
[3] POST /candidates：服务端调模型（qwen）→ 严格校验+修复层 →（失败自动重试至3次带拒因）
    60-180s 长同步 HTTP ← 网络层 60s 无字节会被掐（§6.2）
[闸1] 客户端八条门禁（quote 对齐/数字纪律/时间窗/敏感/否定指纹/引用在批/…）
[4] 反例召回 + 回源核版本（CoreData 二次读）
[闸2] verify（deepseek）判每 claim supported/unsupported；
    客户端：accept 或（title+≥1body supported 的修剪发布，publishEligibleAfterTrim）
[闸3] 知识库去重（同语义已确认不重复推）
[闸4] 发布策略：two_episodes 需≥2 个带日期独立事件；bounded_pattern 需跨度达标…
[5] 落本地库 + 对话页胶囊
```

## 4. 质量闸规则清单（重设计必须知道每条为什么在）

| 闸 | 规则 | 来源/动机 | 现状 |
|---|---|---|---|
| 服务端 schema | 40+ 拒因（结构/枚举/ID/数量/引用 1-6 条/counterSearch 形状/RFC3339…）| 防编造的第一层 | 已配修复层消化机械错 |
| 客户端门禁·quote 对齐 | 引用归一化后必须是证据原文子串 | **反编造命门，不可删** | 服务端有锚定修复辅助 |
| 客户端门禁·数字纪律 | claim 文本含数字（含中文数字）需≥2 引用或挂 computedFact；禁百分比/相关系数 | 防捏造量化结论 | 与服务端 prompt ⑤联动 |
| 客户端门禁·claims 覆盖 | title+body 必须覆盖全部 claims | 不允许游离在核验外的句子 | 服务端已同口径（丢弃游离）|
| verify | 模型判支持度，全 supported 才 accept；修剪分支允许部分支持发布 | 宁缺毋滥 | qwen 摇摆已换 deepseek |
| 发布策略 | 独立事件计数/日期/跨度/敏感度/否定指纹 | 防单事件过度概括 | two_episodes 需 2 个带日期事件 |

## 5. 两天事故全记录（每条：现象→根因→修复状态）

### 第一晚（10-30）：五层洋葱
1. **预算连坐**：发现与后台整理共池（月限¥2），后台整理 10-15~22 烧了 ¥200 → 发现首跑 429。✅已修：独立分池上线
2. **首跑待办内存丢失**：firstRunPending 纯内存，重启丢+快路径永久拦截。✅已修：init 从 enabled&&processedRecord==nil 推导恢复
3. **dirty 接线缺失**：markDirty 全库零调用方（三域变更事件从未接）。✅已修：跨天日历资格替代（每天首查扫材料自比 digest）
4. **蜂窝永久让位**：isExpensive 算成本敏感 → 无 Wi-Fi 永不跑。✅已修：只认 isConstrained
5. **qwen 候选格式不合格**：试评在 deepseek 上做过、切 qwen 未重评。✅已修：prompt v4→v6 自检清单+修复层+deepseek 核验混合路由

### 第二晚（10-31~11-01）：协议与调度深水区
6. **日配额不退**：candidates 已 dispatch 的失败烧掉当天名额 → 当天报废+客户端锁次日。✅部分修：服务端格式失败重试在同一 run 内消化（不烧新名额）；运维手段=删 cancelled run 行还名额（做过多次，**这不是产品解**）
7. **长连接 60s 掐断**：QUIC/NAT 对 60s+ 无字节连接掐断（-1005），URLSession 换连接重发撞在途 410，服务端完成的 200 无人收。✅已修：服务端在途共享（同 run+stage+hash 并发请求共享 Promise）+ 终态结果重取（completed 后同摘要重放读缓存，T50/T51/T52 测试）。**但客户端批任务被首连接错误先行终止的竞态未根治**（13:17 事故复盘）
8. **冷启动探针竞态**：启动瞬间 NWPathMonitor 未就绪 → refresh skip 且无后续。✅已修：skip 排 30s 补查（真机已实证触发）
9. **verify「2支持1反对」整单作废**：✅已修：修剪发布（publishEligibleAfterTrim 与原始结论分离——注意首轮实现曾把原 reject 传给发布闸造成必拒，Codex 独立诊断报告抓出，已修+测试）
10. **processedToday 不按天过滤**：四天前的终态仍拦今天。✅已修：按自然日过滤
11. **prompt 版本不回填**：后端升 prompt 客户端不知道→永不重评估。✅已修：StageResponse.promptVersion 回填
12. **成功终态重放拿不回**：completeRun 后重放被 RUN_CLOSED 拒。✅已修（见 7）

### 未解决（当前最后拦截）
- **A. 热让位**：真机 `thermal=true` 持续让位（整夜充电+亮屏发热）。设计上「fair 即让位」对**一次几分钱、60 秒的任务**过于保守——但更深层是：同步长任务形态迫使用户亮屏等待，才放大了这个问题（§7）
- **B. 同步长任务形态**：candidates 60-180s 同步 HTTP + 必须前台 = 用户开 App 拿着等 2-3 分钟，锁屏即冻结。**这是当前体验崩坏的根源**，两晚的补丁（重试/共享/重取）都在维持这个先天不稳的形态
- **C. 端到端产出率未证实**：模拟器合成材料 verify accept ~1/3；真机真实材料 8 次 candidates 成功 0 次 verify（全部死于下游故障，未到质量层）。**修完 A/B 后需真机连续观察验证**（报告建议的验收：技术链路完成率与有价值发现产出率分开统计）

## 7. 重设计建议（可全部推翻，但请给出理由）

1. **异步任务化（最高优先）**：POST 创建任务立即返回 taskId → 客户端可退后台，按需轮询/推送取结果 → 前台呈现。彻底消灭：60s 掐断、前台冻结、在途共享、终态重取的全部补丁必要性。服务端已有 `agent_cloud_analysis_tasks`（云端异步分析，含密文落存与即焚）可评估复用（独立诊断报告 §4 亦建议评估而非直接套用）
2. **闸门收敛为两层**：服务端 schema+修复层保留（已稳）；客户端只留「quote 是原文子串」程序校验+发布策略；数字纪律/引用计数并入 prompt 与服务端校验（当前跨三处口径难维护）
3. **调度极简**：持久化「上次成功终态时间+材料指纹」两个字段；每次前台激活：>24h 或指纹变→尝试。删七个内存变量
4. **日配额语义重审**：「已 dispatch 不退」防滥用 vs「格式失败烧掉一天」伤体验——建议失败重试期内不占新配额（已部分实现）+ 当天多次尝试小额计费
5. **模型策略给东林拍板**：全 qwen（便宜，格式靠修复层，verify 摇摆→产出率低）/全 deepseek（~¥0.1/天，稳）/当前混合。附实测：qwen candidate 真实材料单次通过率 ~60%（修复层加持后），verify deepseek 接受率未测
6. **thermal 让位放宽**：nominal 之外让位→「fair 仍可跑，serious 及以上才让」——发现任务 60s/几分钱不应与重度后台任务同标准

## 8. 红线（重设计不可违反）

- CloudKit 开发库=东林生产数据，禁重置；模型改动增量兼容（AGENTS.md）
- 引用逐字真实性（quote=原文子串）不可删——这是功能的立身之本
- 不读取健康/财务记录；「不参与 AI」标签排除；撤权即停且派生数据下线
- metadata-only 日志纪律：用户正文不进服务端日志（rawTail 300 字仅供格式调试，**重设计时建议改为仅 reason 不带原文**，进一步收紧）
- 发现池预算独立（不再与后台整理共池）
- 后端发版只走 `holo-backend-deploy` skill；模拟器无头跑；真机验收前必须核对 UA build 号（已三次装错包事故）

## 9. 给接手者的教训清单（血泪）

1. **任何「用户设备跑过/成功」的结论必须先按 device_id 归属核实**（曾把模拟器调用当真机结论被用户抓）
2. **测试绿≠链路通**：各层测试全绿时，跨端契约缝隙/网络形态问题照样让端到端为零。双端共用夹具对拍（§2.4）是目前最有效的防线
3. **修一层测一层再上真机**，每次真机验证前核对：包版本（UA）→名额（runs 表）→锁（手机日志 budgetResetAt）→让位（yield detail）
4. 长会话调试时**不要在批次在途时重启 App**（杀过自己两次）；30 分钟模拟器自动关灯 agent 会杀无头模拟器
5. 用户正文与凭据不落日志/不打印；服务端 secret 不 cat
6. 东林是产品经理：给结论先给状态（已上线/证据），再给细节；不接受「应该可以了」——只接受带证据的「已验证」
