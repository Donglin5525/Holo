## 0. 目标、范围和完成定义

**目标**：让用户在 Holo 中把模糊愿望变成经自己确认的目标：Holo 只问影响决策的问题；有真实取舍时给路径选择；用户确认目标定义、路径和行动后，系统可靠保存并可继续回看、调整。

**技术路线**：新增独立 `GoalWorkshop` 流程与后端 `goal_workshop` purpose，旧 `GoalPlanningCoordinator` 暂保留供灰度回退。结构化会话和目标决策版本存在现有 Core Data/CloudKit 私有库；模型只产出候选，客户端状态机和校验器决定下一步；保存由单次数据库事务完成。P0 完成新目标闭环，P1 完成已有目标重规划，P2 在效果得到验证后增强个人情境。

**技术栈与约束**：Swift/SwiftUI、iOS 17+、程序化 Core Data 模型、CloudKit 私有同步；后端 Hono/Node.js。现有 Xcode 工程有 `HoloTests` 和 `HoloUITests` target。新 Swift 文件要检查并登记到 `Holo.xcodeproj/project.pbxproj`，不能以文件存在当作已经编译。

**整体完成定义**：P0、P1、P2 各自有独立完成门槛；在任何阶段不得把“方案生成”“用户确认”“数据库保存”“生产生效”混称为完成。未获授权时只做到本地实现与验收证据，不执行生产发版。

## 2. 全局数据与交互契约（所有任务按此实现）

### 2.1 会话状态

`understanding → exploring → choosing → reviewing → saved`；任何未保存状态可到 `abandoned`。只有用户操作或通过校验的模型结果才能推进状态。客户端在收到迟到的模型结果时，P0/P1 比对 `sessionID + revision` 并复查当前 AI 数据处理同意；P2 引入来源权限代际后再比对 `accessGeneration`。不匹配即丢弃，不覆盖用户较新的编辑或权限变化。

`GoalWorkshopSessionV1` 至少包含：`id: UUID`、`goalID: UUID?`、`phase`、`revision: Int`、`originalText`、已确认事实、推断/未知、当前单个问题、路径选项、选中路径 ID、目标定义、草案、`createdAt/updatedAt`、`appliedGoalID: UUID?`。新建时 `goalID=nil`；P0 的已有目标入口只给建议，P1 才允许写回。会话只存完成恢复所需的结构化摘要，不复制完整聊天记录。

事实对象需区分 `userStated`、`authorizedRecord`、`inference`、`unknown`；`authorizedRecord` 必须有稳定 `sourceID/sourceRevision`，推断必须可纠正。P0 只使用本轮用户输入和用户主动打开的目标快照，P2 才接入更广的个人情境。用户本轮明确表达优先于旧资料。

### 2.2 模型请求与响应

后端只新增一个 purpose：`goal_workshop`。客户端请求为版本化 JSON，包含 `schemaVersion=1`、`sessionID`、`revision`、`operation=understand|propose_options|build_plan|replan`、本轮输入、精简的已确认会话快照、经授权的上下文引用。不得把完整 `UserContext`、未授权目标或全部聊天原文默认塞进请求。

模型响应使用一个判别字段 `kind=question|options|plan`：

```json
{
  "schemaVersion": 1,
  "sessionID": "UUID",
  "revision": 3,
  "kind": "options",
  "assistantText": "我理解你想在工作会议中更敢开口。",
  "question": null,
  "options": [
    {"id":"route-1","title":"先练会议听说","fit":"下周就要参会","effort":"每天20分钟","tradeoff":"基础语法需边用边补","reason":"更贴近当前用途"},
    {"id":"route-2","title":"先补语言基础","fit":"近期没有会议压力","effort":"每天20分钟","tradeoff":"进入真实会议较慢","reason":"先减少基础障碍"}
  ],
  "recommendedOptionID": "route-1",
  "plan": null
}
```

`question` 只允许一个，包含 `text` 和 `whyItMatters`；`options` 仅在确有实质分歧时给 2–3 个，路径明显时允许单一推荐及理由；`plan` 包含现有 `GoalDraft`、`successEvidence`、`milestones[]`、`firstActionID?`、`assumptions[]`、`reviewDate?`。行动可为零习惯。`recommendedOptionID`、`firstActionID` 只能引用同一响应内实际存在的 ID。模型不能输出 `saved=true` 或任何执行结果。

客户端校验：JSON/枚举/版本正确；必填标题非空；路径和行动 ID 不重复；日期按用户时区严格解析且不可凭空补日历日；引用 ID 属于本次授权输入；不允许不存在的目标/任务关联；生成行动不与现有行动重复。失败最多做一次受控重试；仍失败保留会话并展示可编辑初稿或错误，不写业务数据。

### 2.3 决策与额度

最多追问 3 个**会改变目标或路径**的问题，但不按第一/第二/第三轮固定内容；事实已足够时零追问，用户随时可跳过。一个完整会话最多 5 次模型请求（最多 3 次理解/追问 + 选路径 + 产草案），每次请求沿用 chat 额度池，单独记录用量。开始前检查是否至少可支持“路径 + 草案”两次请求，额度不足时不诱导用户开始；由于跨设备消耗无法完全预留，过程中若额度耗尽则保存进度并说明何时可续，不宣称保证完成。

确认页必须展示并允许修改：期望结果、成功证据、动机、期限、所选路径及其代价、关键假设、里程碑、第一步、所选任务/习惯、AI 可见性。第一步优先能在 48 小时内开始；不适合时写明依赖与最早可行时间。`allowAIContext` 在保存时才决定后续目标上下文使用；新流程本身的云端处理仍遵守现有 AI 数据处理同意。

### 2.4 持久化与一次性提交

在现有程序化 Core Data 模型中新建 `GoalWorkshopSessionMO` 和 `GoalPlanRevisionMO`，使用同一私有 CloudKit store，不另建数据库。前者保存会话元数据与 `payloadJSON`；后者保存 `goalID`、`sourceSessionID`、版本号、决策摘要 JSON、时间戳。新字段遵守 CloudKit 可迁移约束：非可选属性有默认值；JSON schema 版本化；不设置 CloudKit 不支持的 uniqueness constraint。旧 Goal 无版本记录时仍正常显示。

保存使用 `CoreDataStack.shared.newBackgroundContext()`：先重查会话 revision、授权、选中路径和关联实体；在同一 context 内构造 Goal、任务、习惯、决策版本和会话应用回执，**只调用一次 `context.save()`**。把任务/习惯仓库的创建规则抽成可接收 context、暂不保存的构造方法，旧公开创建 API 再调用该方法并保存，避免复制业务规则。保存成功后才刷新列表、发数据变更通知、安排提醒、把新习惯加入看板；失败 rollback 并保留待确认草案。

新建 Goal 的逻辑 ID 使用 session ID；任务/习惯的逻辑 ID 由 `sessionID + draftItemID` 稳定计算，决策版本由 `sessionID + revision` 稳定计算。同一会话重复点击或重试先查 `appliedGoalID` 并返回已有回执，不能再创建一套行动。双设备同时确认属于独立冲突场景：按这些逻辑 ID 检测、归并同义副本；不同草案版本冲突时暂停自动合并并交用户复核，绝不能靠页面按钮禁用当作幂等保证。用户放弃草案可删除会话；自动清理或保留时长不在本轮擅自新增。
