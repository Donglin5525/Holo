# Holo 用户反馈通道方案

日期：2026-08-19
状态：待东林评审（HTML 原型已出，见 `docs/design-mockups/user-feedback-channel.html`）

## 1. 一句话概述

在设置页加「反馈给开发者」入口，用户填一张表单（类型 + 描述 + 可选联系方式）提交到 ECS 后端，东林在管理后台的「用户反馈」页面查看和处理。

```
iOS 设置页入口 → 反馈表单（sheet）→ POST /v1/feedback → user_feedback 表（SQLite）
                                                                    ↓
              东林浏览器（SSH隧道）→ /admin/feedback 管理页（筛选/标记已处理）
```

整条链路与现有「AI 内容举报」功能（App Store 1.2 合规时做的）完全同构，后端接口、建表、管理页、iOS 表单四处全部有现成模板可照抄，**不引入任何新模式**。

## 2. 表单设计（对应 HTML 原型屏2）

| 字段 | 必填 | 规则 | 说明 |
|---|---|---|---|
| 反馈类型 | ✅ | 功能建议 / 问题反馈 / 其他，默认「功能建议」 | 卡片式三选一，带图标 |
| 详细描述 | ✅ | 1–500 字（前端计数，超 500 禁止提交；后端 2000 硬截断） | placeholder 引导写具体（哪个页面、什么操作） |
| 截图 | ⛔ 选填 | 最多 3 张；App 端选图后统一重编码为 JPEG 并压缩至 ≤ 1MB/张；重编码同时去除位置信息（EXIF/GPS） | 缩略图行（＋添加 / ✕删除，满 3 张＋置灰）；提示文案「图片会自动去除位置信息」 |
| 联系方式 | ⛔ 选填 | 类型四选一：**微信（默认）** / QQ / 邮箱 / 手机；内容：微信号/QQ号/邮箱 ≤ 60 字，手机 11 位纯数字（数字键盘） | 类型切换**内嵌在输入框左侧**（「💬 微信 ▾」标签，点按弹出 iOS Menu），四档选项不额外占行；附动机文案「建议被采纳、问题修复时第一时间找到你」 |
| 自动附带 | — | App 版本、系统版本、设备标识 | 表单内透明展示（蓝色信息条），设备号脱敏显示（8F3…D21）；请求头自动携带，用户无需填写 |

提交成功后整页切换成功态（对勾动画 +「会通过你留下的微信与你联系」），点「好的」关闭。

### 设计上的三个刻意选择

1. **联系方式四类、切换藏进输入框**：东林的核心诉求是能跟进用户，支持微信/QQ/邮箱/手机四类；不做四档横排（占空间且拥挤），而是输入框左侧类型标签 + iOS Menu 弹出切换，微信为默认档，选手机自动切数字键盘。入口副标题同步说「留个联系方式我们能找你」。
2. **诊断信息透明展示**：不在用户不知情时偷传信息，表单里明说「仅用于定位问题」。隐私政策第九条「联系我们」已有对应口径，合规无新增风险。
3. **管理后台联系方式四色徽章**：微信绿 / QQ 蓝 / 邮箱蓝 / 手机橙，与普通元数据区分，一眼识别、方便复制去联系。
4. **截图重编码去位置信息**：相册照片自带拍摄地点，App 端统一重压缩导出 JPEG 时一并抹除，并在表单里明说——隐私上是「用户主动传图 + 平台主动去敏感元数据」的双重稳妥。

### 表结构

```sql
CREATE TABLE user_feedback (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  device_id TEXT NOT NULL,
  category TEXT NOT NULL,            -- suggestion | issue | other
  content TEXT NOT NULL,             -- ≤2000，App 端限500
  contact_type TEXT,                 -- wechat | qq | email | phone | NULL
  contact_value TEXT,                -- ≤60
  images TEXT,                       -- JSON 数组，如 ["1-0.jpg","1-1.jpg"]，≤3
  app_version TEXT,
  os_version TEXT,
  status TEXT NOT NULL DEFAULT 'new',-- new | done
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_user_feedback_created ON user_feedback(created_at DESC);
CREATE INDEX idx_user_feedback_device ON user_feedback(device_id);
```

### 图片的存储与传输

- **传输**：随 `POST /v1/feedback` 以 base64 JSON 数组提交（3×1MB → 请求体约 4MB）。不引入 multipart 新解析路径，现有 `readJson` + 字段校验 + 限流全部复用。
- **存储**：解码后写入 Docker 挂载卷 `/data/feedback-images/{feedbackId}-{n}.jpg`（与 SQLite 同卷，容器重建不丢），表里只存文件名数组，数据库本体不膨胀（migration 前自动备份逻辑不受影响）。
- **查看**：新增 `GET /admin/feedback/images/:name` 静态文件路由，走现有 admin 鉴权，管理页 `<img>` 引用 + 点击放大。
- **量级评估**：按每天个位数反馈 × 3 张 × ≤1MB，一年约几 GB，ECS 本地盘足够；不引入 OSS 新依赖与费用，量级上来后再迁移成本也低。

### 接口

- `POST /v1/feedback`：鉴权沿用 `X-Holo-Device-Id` 请求头（与举报接口一致，无需登录态）。Body：`{ category, content, contactType?, contactValue?, appVersion, osVersion }`，返回 `{ ok: true }`。
- 限流：`purpose="feedback"`，**每分钟 1 次 / 每天 5 次**（比举报的每分钟 5 次更严，防刷屏灌水；env 可覆盖调整）。
- `GET /admin/feedback`：HTML 列表页（类型/状态筛选、统计条、标记已处理按钮），走现有 admin 登录鉴权，SSH 隧道访问。

## 5. 发版与上线顺序

1. **后端先行**（需要发版）：跑一键部署脚本，migration 随容器启动自动执行，新接口上线。旧版 App 没有入口不会调用，先上无任何副作用。
   - ⚠️ **发版时必须同步调大 nginx 请求体限制**：ECS 宿主机 nginx 默认 `client_max_body_size 1m`，图片上传会被 413 直接拦掉。需调到 `8m` 并 `nginx -s reload`。此配置在宿主机（不在容器/仓库内），按 [[backend-deploy-pitfalls]] 流程操作后要用 curl 大 body 实测验证。
2. **iOS 随下个版本**提交 App Store。反馈功能本身不涉及 Apple 审核敏感点（用户主动留联系方式、主动传截图、诊断信息透明告知）。

## 6. 工作量与风险

- 后端约半天～1 天（含图片接收/存储/静态路由与测试），iOS 约 1 天（表单 + PhotosPicker 压缩导出），合计 1.5～2 天交付编译通过版本。
- 风险低：全链路照抄已验证的举报功能；SQLite 单表 + 文件系统存图，migration 自动备份不受影响；限流 fail-closed 沿用现成机制。
- 已知注意点：nginx body 限制（见 §5）；Docker 挂载卷确认 `/data` 持久化（现有 SQLite 同卷，已验证）。
