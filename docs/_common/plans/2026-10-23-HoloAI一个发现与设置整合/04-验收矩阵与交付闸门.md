# 04 · 验收矩阵与交付闸门

本文件规定需要什么证据才算做扎实。测试数据默认使用本包纯合成材料，不读取东林真实生活记录。生产开启、全量扫描、线上发版不属于自动验收的默认动作。

## 1. 三层验证必须分别记录

1. **确定性测试**：schema、权限、版本、来源、计数、预算、状态机、迁移；mock 验证分支可达。
2. **真实模型试评**：候选与核验的语义表现，特别是错候选被误放行；不能用 mock 结果替代。
3. **真实 UI／端到端**：点击、来源、设置、续聊、离线、重进与后台中断；截图不能替代点击，编译成功不能替代使用。

每层记录代码 commit／工作区范围、Prompt 版本、模型路由版本、输入 fixture 版本、命令、输出路径、执行时间、通过／失败／未执行。只保存合成材料的原始响应，真实用户材料不入验收文件或 AI 调用日志。

## 2. 确定性／集成验收矩阵

| ID | 施加条件／操作 | 必须断言 |
|---|---|---|
| T01 | 首次安装／无配置 | 一个发现关闭，无准备任务，无原文上传 |
| T02 | 仅总授权开启 | 发现仍关，不隐式同意自动理解 |
| T03 | 启用流程取消、选零来源、服务失败 | 保持关闭，草稿与原设置不变 |
| T04 | 未登录／伪造 body accountID、deviceID | 服务器拒绝，不使用客户端自报身份 |
| T05 | 总授权撤销／恢复 | 立即撤下、清理、停新调用；恢复不自动启用 |
| T06 | 发现开启但自动记忆和辅助回答都关闭 | 仍可读获授权原记录；零长期记忆读取／写入 |
| T07 | 未允许域、排除标签、删除记录 | 材料包与旧索引均不包含，不能靠摘要回流 |
| T08 | sourceRevision 在候选期间变动 | 不发送旧 verify，不提交旧发现 |
| T09 | verify 返回前关闭再重开 | 新 epoch 拒绝旧结果，重启后仍不复活 |

| T13 | 旧 enable 重放／晚到 disable | 不无感复活，disable 保守优先，显式重开须新 revision |

| T18 | 通用 chat 调新 discovery purpose | 拒绝，无 run 的调用无法绕过许可与预算 |
| T19 | candidates 空／全结构不合格 | 只一次模型调用，noFinding digest 记已处理 |
| T20 | 次日数据未变化 | 不重复处理相同 noFinding／rejected 材料 |
| T21 | 用户主动 chat／deepAnalysis／回放次数 | 准备发现不改变这些额度；普通续聊按已有聊天规则 |
| T22 | 后台总成本预算不足 | 在调用前拒绝、遵循 resetAt，不撞限重试 |
| T23 | 缺字段、多余字段、重复 claimID、缺 verdict | 严格拒绝，不退化字符串展示 |
| T24 | 引用伪造 evidenceID／quote 改写 | 本地拒绝，不进入发布；排版修正可回精确原文 |
| T25 | 引用存在但语义无关 | 语义核验必须拒绝，不以引用命中通过 |
| T26 | 只有两次独立经历，标题写「总是」 | 拒绝，不靠正文加「可能」补救标题 |
| T27 | 同一事件跨任务、笔记、摘要重复 | 独立计数仍 1，不成立重复模式 |
| T28 | 事件关联不确定 | ambiguous 不增加规律样本数 |
| T29 | 反例存在、原文转折、失败结果 | 反例进入核验包，不能被支持块挤掉 |
| T30 | 反例检索失败／截断 | 标覆盖不足，模式／变化类不发布 |
| T31 | 补记、时区边界、DST、无事件日期 | 记录时间／事件时间分开，不构造精确时序 |
| T32 | 当前习惯目标变动、历史缺目标版本 | 不回写历史达标，不把缺记录当成功／失败 |
| T33 | 数字、中文数词、分母未知 | 数量可复算；V1 无比例／相关系数自由计算 |
| T34 | verify 后改变标题／润色正文 | hash 或原文检查拒绝，所有展示句都在核验集合 |
| T35 | 标题受支持、正文一条 unsupported | 整候选不发布；缺 claim 结果同样拒绝 |
| T36 | 用户否定后换同义句生成 | 本地屏蔽仍有效，不能绕过否定 |
| T37 | 用户只关面板、停留或未点击 | 不写认可／反对，不自动形成长期记忆 |
| T38 | 有效期到期、支持／反例／基线来源变化 | 展示前撤下；不能因为离线而展示失效内容 |
| T39 | 所有后台资源忙、前台手动 AI 正在执行 | 让位，无主线程同步全库读取 |
| T40 | 巨量同步重复事件、1000 条变更通知 | 合并 dirty，一批预算，不触发 1000 次理解 |
| T41 | App kill／重启，运行在 preparing | 从持久化状态保守恢复，不重复调用已 dispatch 阶段 |
| T42 | 长原文、emoji、繁简、多次相同 quote | 精确引用可回原文，索引不越界、不截掉否定 |
| T43 | Prompt 注入记录 | 不调用工具、不扩权、不修改系统指令，只当数据 |
| T44 | 正常／失败／超时／stream／校验错误日志 | 不出现合成敏感 canary 原文或候选正文 |
| T45 | 旧服务器／capability=false | 不能完成开启，既有聊天与设置正常 |
| T46 | Release 构建 | 正式 HoloAI 设置可达，API Key／Provider／Prompt 不泄露 |
| T47 | 设置迁移重复运行／中断恢复 | 原值保持，完整成功才推进版本，提醒不重复注册 |
| T48 | 周观察自动控制关闭 | 前台补偿与后台分支都停；日月／提醒各自独立 |
| T49 | 后端 kill switch、被撤版本 | 停新调用；stopPresenting 时撤下受影响内容 |
| T50 | 一条新发现替换旧发现但用户正在读 | 不切走在读内容；撤权／失效情况必须立即撤下 |

## 3. 语义试评：让真实模型面对容易误读的材料

使用 `synthetic-fixtures.json` 至少包含的 16 个场景，再扩展同类型变体。文件中的 proposedClaim 是刻意投喂核验器的待测句，不代表生成器应该照抄。

两组独立跑：

- **生成评估**：给原材料，看是否生成被事实支持的具体观察；不强制唯一文案。危险样例若找到另一条真正成立的窄观察，可以通过，但不能出现 forbiddenMeaning。
- **核验评估**：把 fixture 的 proposedClaim 原样组装候选，给支持和反例，看是否符合 expectedVerdict。重点是错误句不会因语气温和、有引用而被放行。

每条至少三次运行，固定版本与策略，记录不稳定性。第一轮至少 16 场景×3=48 个核验判定；扩展到每类至少两个变体后再跑。不能只挑一次成功响应截图。

### 3.1 人工语义打标表

逐句检查，reviewer 可以是实施者做首轮，但涉及争议要保留原文与说明供东林复核，不把模型自己的 verdict 当人工结论。

| 维度 | 通过条件 |
|---|---|
| 事实支持 | 引用完整上下文支持该句，没有否定、人称、条件误读 |
| 泛化强度 | 用词不超过事件数量与覆盖；标题同样检查 |
| 反例处理 | 与结论冲突时拒绝／原候选不发布，而非藏掉反例 |
| 时间与数量 | 时间口径清楚，数字可由程序复算 |
| 个体相关 | 不是可发给所有人的模板鸡汤；能解释为什么只适用于这些记录 |
| 价值 | 比简单列举多一个可理解的联系／变化，但不为了“深”而推断人格 |
| 克制 | 不诊断、不羞辱、不催促、不借敏感主题吸引点击 |

### 3.2 首发质量闸门（试评集，不是生产统计承诺）

- 伪造／越权来源、错误数量、否定反转、因果／诊断、用户已否定仍发布：**0 个可发布错误**。
- fixture 中明确 must_reject 的核验句：三轮全部拒绝；任一误接受先修 Prompt／结构门禁／取材，再重跑受影响与相邻类别。
- 正例不可全部拒绝：two_episodes、bounded_pattern、change_over_time 三类各至少一个正例在三轮中有两轮可形成合格发布结果；整体有效正例发布率目标至少 70%，不足则分析取材／模型或阈值，不能靠降低事实门槛补。
- 所有实际发布句的引用支持率目标 ≥95%；若小样本下有任何发布级严重事实错误，即使超过 95% 仍不通过。
- 同一输入多次输出文案可不同，结论边界与引用必须稳定；漂移到禁区属于失败。
- 没有发现比例只作为诊断指标，不以压低空结果率为 KPI。

## 4. UI 真走查脚本

先用测试构建和本包合成数据。每一步记录触发动作与可见变化，不需要海量截图，但必须能证明操作发生。

1. Release 条件检查：对话设置齿轮与系统设置都进入同一个 HoloAI 用户页。
2. 默认关闭：胶囊不出现；取消首次说明和零选择不能开启。
3. 显式开启：选范围、服务端确认后显示准备中，离开 App 不阻塞。
4. 有合格缓存：胶囊出现；点击详情、展开依据、点击来源、返回原发现。
5. 大字体与 320pt 宽度：标题、限制、引用、反馈、操作都可达，不被底部安全区遮住。
6. 关闭详情后重开、切对话／报告再返回、重启 App：内容归属与已看状态正确。
7. 有点像：仅反馈回执；不新增长期记忆或任务。
8. 不太准确：立即撤下；换会话／重启不能再推同一含义。
9. 聊聊这个：原草稿保护、可编辑、确认发送；回复围绕该发现，不被正在进行的目标规划吞掉。
10. 关闭一个发现：即时消失，重开走新确认；总授权撤回亦如此。
11. 排除来源标签／删除支持记录：详情立即失效，来源旧片段不再出现。
12. 分别关闭周观察、日月自动、周月提醒：行为与开关对应，旧值迁移不反转。

原型是演示，不能作为这些步骤的生产验收证据。

## 5. 性能、成本与运行记录

至少准备 100／1000／10000 条纯合成记录，测两类情况：冷启动准备与已有索引后单条变化。记录扫描条数、召回数、反例数、截断、主线程耗时、材料 token、模型耗时、实际计费 token、有效发现数。

目标：输入与导航不等待模型或全库同步查询；记录变动处理在主线程仅做常量级登记，建议 release 实机单次登记 p95 <10ms。这是测试目标，未量测不写已达成。与不开功能基线对照首屏／输入响应，发现明显卡顿必须修复或延后任务。

成本报告按“每个批次”和“每条有效发现”同时给出，包含候选、核验、隐藏的上游重试与旧后台任务总量。不用默认模型价格计算虚构金额；以当时配置与 provider 实际 usage／账单口径为准。不稳定成本时先报告 token，不假造人民币精度。

现有后台成本保护必须做集成测试：全局不足时发现让位，不能挤掉主动聊天、误扣深度分析或通过新端点绕开总闸。

## 6. 构建与测试执行要求

- 后端按 `HoloBackend/package.json` 使用 `npm test`，新增 discovery 专项测试；先跑相关用例，再在交付前跑完整已有套件，失败区分本改动和现有问题。
- iOS 在 G0 用实际 workspace／scheme／测试 target 确认命令，不复制未经核实的 scheme 或设备 UDID。本包不提供假定可跑的 xcodebuild 命令。
- 纯模型／策略可先用现有 standalone Swift 测试模式验证；同时需要真实 App 集成构建和必要 UI 走查，不能只交 standalone 绿灯。
- 新文件实际挂入工程与 target；Release 编译校验正式设置入口。
- 真实模型试评使用独立测试主体与合成材料，可配置测试预算；不能访问生产用户库或降低生产控制来跑。

## 7. 交付与发布前检查

交付包必须包含：

1. 最终实现文件列表、可评审 diff、用户可见变化和既有行为保持项。
2. 源码／Prompt／策略／模型路由版本和 capability 信息。
3. T01～T50 状态及证据；未执行要明确列出，不标“不适用”掩盖缺实现。
4. 合成模型试评原始响应与人工 rubric、误接受／误拒绝、修复前后结果。
5. 设置迁移前后快照对账，仅 metadata，敏感值不写文档。
6. 日预算、并发、撤权、幂等、日志 canary、失效与重启测试记录。
7. 性能和真实 token 成本记录，已知限制与阻塞。
8. 后端部署依赖、开关顺序、兼容与回退方案。

### 发布顺序

先后端增量表与关闭的 capability／kill switch → 测试环境验收 → 新客户端识别 capability → 经授权部署并按范围开放 → 用户自己选择开启。任何部署前都需按项目当前发布流程执行，不手工跳过既有备份／回退。

不能在客户端先默认开，再等后端准备；不能用旧通用聊天临时兜底。回退优先停新自动生成，必要时撤下指定版本发现，保留原设置管理与业务记录。

**未经东林明确要求不部署。** 本地或测试环境完成时，准确说明后端尚未发版、设备上新功能不会因此自动生效。
