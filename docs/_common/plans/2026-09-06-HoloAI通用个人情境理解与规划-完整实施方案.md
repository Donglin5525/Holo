## 3. 技术选择（确定的实施默认）

- 复用现有记忆 Repository、权限、遗忘和版本机制；用可选载荷扩展，不建立第二份个人档案。
- 新情境记录使用现有枚举值和独立的程序生成锚点；旧记忆 ID、旧字段含义、已有跨域融合均保持兼容。
- 同来源域的关系/规律可持久化；跨来源域的复合推断第一版在本次运行中组合并引用各自来源，不为它滥用旧 crossDomain 记录协议。用户跨域纠正按涉及的关系分别更新。
- 新记录默认处于 candidate，允许通过专用建议读取政策使用；用户确认后可 active。普通记忆消费者仍按原规则读取。
- 第一版新情境派生记录放入现有不经 CloudKit 同步的本地记忆存储，沿用 Repository 契约；不能因选择本机存储而把内容的语义敏感等级改低。原始想法/既有记忆沿原同步机制，其他设备按可访问来源重建。把新情境直接同步云端不属于首版默认，避免旧客户端重写未知载荷；用户控制/遗忘仍使用现有同步控制机制并扩展稳定来源抑制键。
- 语义召回复用现有 embedding 网关基础，采用客户端混合召回与模型选择；向量不决定事实是否成立。
- 后台自动萃取复用调度生命周期；规划关键路径不等待全历史补建。
- 先做有限的“理解目标—检索—生成—校验”过程，最多一次补查，不建无限自主循环。
- 共享模块均通过协议注入 clock、store、provider、sourceReader，Core Data 对象不跨 actor，传不可变 DTO。

## 4. 数据契约

以下是语义契约，不要求照抄未编译的伪代码。所有新增持久化字段均使用 `decodeIfPresent` 或带明确版本的自定义解码；未知版本不得使整个记忆库读取失败。

### 4.1 原始来源 `HoloContextSourceSnapshot`（新增）

字段：`sourceID`、`sourceDomain`、`revisionDigest`、`sourceCreatedAt`、`sourceUpdatedAt`、`plainText`、`sourceKind`、`sensitivity`、`accessGeneration`。可选 `eventTime`、结构化业务状态和既有对象 ID。

- 想法采用统一富文本转纯文本路径，覆盖整段文本、列表和可提取的正文；不可解析附件仅标记覆盖缺口，不编造 OCR 内容。
- 引用使用上传的规范化/脱敏文本的 UTF-16 范围，加 `quote`；保留映射以回到本地原文。不能拿原始文本偏移去校验另一份处理后的文本。
- 消息 role 必须保留。助手回复、AI 摘要、自动标签不可成为独立用户事实。
- `eventTime` 与记录日期分开；“补记上个月”不能按今天算新事件。
- `revisionDigest` 用规范化正文+必要业务状态的稳定摘要，UI 样式调整不触发重学。

### 4.2 `HoloPersonalContextPayloadV1`（新增，挂到 `HoloMemoryRecord.personalContext` 可选字段）

| 字段 | 含义与约束 |
|---|---|
| schemaVersion | 首版 1；未知版本不参与新能力 |
| contextID | 程序分配 UUID；模型不能任意指定本地身份 |
| statement | 可独立理解的克制命题，保留必要条件，不只是标签 |
| subjects / objects | `ref + label + scope`，可关联已有 ID，也允许未消歧对象；未知不得自动视为用户本人 |
| relationText | 开放文本关系，不能限定为场景枚举 |
| facets | 可选检索视角 responsibility/time/dependency/constraint/preference/state/other；other 必须保留 statement，不丢弃 |
| epistemicStatus | declared / observed / inferred；与是否经用户确认分开 |
| applicability | 作用范围与条件表达，包含主体、项目/地点等可选引用；不强制每项齐全 |
| temporal | 见 4.3；不把观察窗口复制成规则生效期 |
| basis | 源 evidenceID、quote/range、eventID、support/contradiction、来源版本；同源派生去重 |
| linkedContextIDs | 关系依赖；存在、可访问、无循环才采用；持久化引用同时进入 upstreamMemoryIDs |
| openQuestions | 当前未知，不能被模型填成事实 |
| admission | 未审核 / 可作建议背景 / 仅待确认 / 禁止使用，附 policyVersion；由程序和验证结果决定 |

载荷不包含自动执行指令、工具名、收款信息或提示词规则。来源中的命令仅作为数据。

映射旧字段：显式事实用 observedFact/explicitPreference；多次观察规律用 recurringPattern；推断用 hypothesis。不要为了过自动采用门槛改写 claimKind。候选摘要对推断保留“从记录看/可能/目前”等必要限定，不把概率打印给用户。

### 4.3 时间、规则与实例

`HoloContextTemporalV1`：`kind`（event/ongoing/recurring/conditional）、`originalExpression`、`precision`、`validFrom/validTo`、可选 `recurrence`、`triggerText`、`exceptions`。

`recurrence` 可结构化明确的日/周/月/年频率、interval 和明确锚点；未知锚点为空。月初、工作日、节假日等不擅自转成固定日期，除非相应日历语义与依据已就绪。

周期实例 `HoloContextOccurrence` 保存在规划 DTO 或关联已有任务状态中：`contextID + periodKey + status + evidenceRefs`。没有完成证据时状态 unknown，不能默认 pending。

- 本月完成只更新实例；本次延期是 exception；以后换频率才生成新规则版本。
- 同一事件写多次不是多个周期。明确表述一次即可支持明确规律；观察归纳必须验证独立周期和范围，不能固定“凑三次”。
- 所有精确日期计算使用注入的 Calendar/timezone，并测试月末、跨年和时区变化。
- 推荐某时段不等于拥有日程；未经确认不得将周期记忆展开成无限待办。

### 4.4 身份、合并与旧客户端兼容

新关系至少包含一个 `.userTheme` 锚点，值为 `personal-context:<contextID>`。该锚点由程序生成并持久保存；沿用现有 identity 算法，避免引入旧端不能解码的 anchor 枚举。

模型新输出只能给出本次 `candidateRef` 或匹配输入候选的 `existingRef`。程序映射到真实 ID。匹配要求主体、对象、范围和命题一致；只有主题相同不得合并。

同一领域中不同命题有不同 contextID；同一命题新证据复用 ID，更新版本。claimKind 或身份组成需要变化时创建替代记录并明确 supersede，不改旧 ID 算法。新旧冲突不覆盖较新的用户纠正。

批处理使用 `source revision + extractorVersion + policyVersion + batchKey` 幂等标识；接受后的响应先与 observation receipt 原子落库，再推进游标。重复请求复用已保存结果，不因模型输出顺序变化创建重复关系。

**旧端安全门**：新情境记录默认 candidate（包括 declared），只有新 advice 入口能按 admission 读取；旧 active 查询不会自动使用推断。用户明确确认可进入 active。旧端读写剥掉未知载荷后，新端必须停止把它当结构化情境，并按源记录重建，不能猜恢复。不得让 old-reader round-trip 擦除用户控制或伪造规则。

原始字段继续是兼容摘要，payload 不是唯一证据。未知 schema 单条隔离、保留原数据，不使整库失败；混合新旧版本同步须进入验收门禁。

实现上为 personalContext 使用版本信封：先读 schemaVersion，再解已支持载荷；未知版本保留原始 JSON 供无损重编码，禁止降为 nil 后覆盖存储。需要改 Repository 批量 decode，使单条问题可报告并跳过新能力，而不是整批 `try map` 失败；不得删除无法识别的原对象。

新情境 namespace 不进入旧领域萃取的 existingMemories、旧跨域融合和普通自动摘要二次学习。识别依据同时看程序生成的 namespace 锚点与 payload，防止旧端载荷丢失后又被旧观察器当新证据加工。原文始终保持独立真源。

本机存储规则在 `CoreDataHoloMemoryRepository.requiresSensitiveLocalStorage` 同级存储分流处实现，并覆盖单条 upsert、批量写、迁移与用户控制写路径；存储分流和 sensitivity 的使用门槛分别测试。来源含有敏感证据时仍按最高敏感级别处理。

## 5. 访问政策与遗忘

新增 `HoloContextAccessPolicy`，复用 `HoloMemoryAccessPolicy` 与 controlState 的决定，不自创第二套用户开关。

| 状态 | 背景萃取 | 本次建议读取 |
|---|---|---|
| 自动形成记忆关，辅助回答开 | 不持久化新萃取结果、不补建 | 可用既有合规记忆；允许的原文仅用于本次，结束后不沉淀 |
| 辅助回答关 | 仅按原自动形成设置处理 | 不调用新情境读取或原文兜底；普通明确提供的本轮内容仍可用 |
| AI 数据处理未同意 | 不外发文本或向量输入 | 仅已有本地能力，不偷换 Provider 绕过 |
| candidate 且 inferred | 原状态保持 | 仅通过 advice 政策：来源有效、验证已通过、非敏感/非高影响结论、无当前矛盾时可用限定表达 |
| 敏感或高影响、来源冲突、未知版本 | 保持待确认/不可用 | 不能借 raw fallback 重新推断并作为事实使用 |
| forgotten/rejected/markedIrrelevant/失效 | 禁止再激活 | 记忆、原文兜底、目录、向量、草案和缓存均受抑制 |

`prepareAdviceContext` 查询 candidate 与 active 必须封装在新策略中；不得把 Repository.query(.all) 的结果直接注入聊天。

忘记/清空先更新 suppression/controlGeneration，再清理衍生内容；进行中的请求携带 generation，返回前复查，旧结果丢弃。保留现有 learningBaselineAt：用户清空之前的资料不能由升级补建偷偷读回，历史重扫走现有确认机制。

新界面的 `HoloMemoryUserVisibility`、确认队列计数和明细入口统一区分“仅作为观察/建议背景”的 candidate 与真正需要用户决策的 candidate：前者不批量进入“想和你确认的”收件箱。不要以弹出大量确认代替自动理解。后台原始候选不逐条发通知。

在现有墓碑保留新 context anchor 之外，还关联非正文的源 ID、修订/片段指纹与已知语义别名，用于阻止换一个 contextID 重生。同主题不同命题不能一刀切压制；语义无法消歧时保守停用相关派生、记录 coverage，不声称可以完美解决近义遗忘。测试必须覆盖改写后重生与误伤无关关系。

首版 suppression 键使用现有 tombstone 的 `anchorKeys: [String]` 载体中带独立前缀的非正文键（例如 ctx-source-span/ctx-alias 的稳定摘要），避免先增加 CloudKit 列。键由程序按来源片段/已验证关系别名生成，不让模型决定哪些用户记录被禁用；扩展 matcher 时不把这些键当普通业务 anchor。跨设备 contextID 可不同，但同一底层来源和已知别名须得到相同抑制键。对从未见过的语义改写不能保证完美匹配，留出测试和保守兜底是公开前门槛。

原文删除/修改通过 `HoloMemoryForgettingService.invalidateMemories` 和 upstream 依赖失效传播；向量、检索目录、运行中 DTO 同步失效。删除账户清理新增缓存。敏感性继承底层证据最高级别，不能因来源是 thought 就将内容降为普通信息。

## 6. 萃取与历史补建

新增 `HoloPersonalContextExtractor`，由现有 observation coordinator 触发，使用专用 payload；不放宽旧单域观察器的统计/跨域护栏。输入只读，输出候选，不执行任务。

步骤：

1. 稳定分页 source DTO，检查权限、学习基线、修订与 suppression。
2. 切分长文，按段落保留上下文并适度重叠；记录 source ID、UTF-16 范围，跨片引用只算同一来源。
3. 提供同对象的少量已有候选供合并，输出新观察、关系、周期、反证、例外与未知。
4. 结构校验：JSON、长度、ref、quote/range、时间精度、来源修订、领域、循环依赖、禁止动作字段。
5. 语义校验：原文是否支持主体/关系/范围；推断是否跨过关键缺口；是否只是引用、他人经历或假设。确定性检查不能替代语义判断。
6. 对所有自由文本萃取出的候选（包括模型标成 declared/observed 的内容）用独立验证 prompt 批量检查 supported/qualified/unsupported；只有直接来自确定性结构化业务值的字段可以走确定性验证。模型自报 declared 不是免审通行证。输出只含 verdict、来源 ref 与简短可审计理由；不落库内部推理长文。同模型第二次判断不是独立真相，仍受盲测约束。
7. 经 admission policy 转为 candidate，原子写入后推进游标。矛盾时保留分歧和时间，不由最后返回的请求抢写。

分页新增 `fetchContextSourcePage(after:limit:baseline:)`：以 `(updatedAt, sourceID)` 排序；固定批次 watermark，批次期间新修改进入下一批；删除由通知/失效路径处理。游标存在受保护的本地状态，不从 UI 的 fetchAll(limit:200) 推断资料覆盖。

来源变更入口必须统一接入队列与失效协议，不能只监听编辑页：新建/编辑将新修订入队；批量导入按源 ID/修订去重后入队；删除先失效再清理；回收站恢复重新检查权限、学习基线和 suppression，不自动撤销用户遗忘。远端同步可能保留旧 updatedAt，因此通过存储变更记录/通知收集受影响源 ID，不能只靠时间游标发现。应用重启或变更游标失效时，分批对账源 ID/修订目录并补漏，复用已有 receipt 避免重复 LLM 调用；对账完成前如实标注覆盖状态。事件接线由 P0 核实实际 Repository、导入、恢复及同步入口，在 P4 完成，读取和保存前的修订复查仍保留。

历史补建首版提供内部进度：总扫描量、已处理修订、待处理、失败与索引覆盖。前台/后台使用同一队列，同一 source revision 单飞；后台执行只做 best-effort，回前台续跑，不承诺 iOS 后台一定完成。

当前 Repository 批量观察写入要求同一存储分区。新本机情境与旧普通领域记录必须分包，分区各自有稳定 receipt；总游标只能在本批所有必需分区成功或明确记录待重试后推进，不能成功一半就标整批完成。源修订或用户控制在 LLM 返回前变化时，拒绝过期批次并重新排队。

初始可配置预算：源分页 50；每个 LLM 包最多 12 段、合计 12,000 字符；段上限 1,800 字符；候选每包最多 16；每次前台补偿最多 2 包，背景预算不足则保存游标。不是产品精度指标，可按压测改，但不得静默截断后宣称全覆盖。

现有领域萃取/洞察对同一原文产生的重复摘要只能补充检索，不能增加独立支持次数。先保留旧能力，避免双重推断被重复展示；新旧语义相同内容按底层来源归组。

## 7. 检索：覆盖语义、条件与当前状态

新增 `HoloContextRetrievalService`，输入 `HoloPlanningRequestFrame`：本轮目标、成功条件、范围、时间、已有安排、未知和最多 4 个开放语义检索方向。检索方向由模型根据目标提出，不用场景词表。

### 7.1 混合候选流程

1. 应用访问策略并读取有效的 context catalog，包含简短命题、时间/条件、引用，不重复整个档案。
2. 合并候选：语义向量候选、明确主体/对象匹配、与计划时间重叠的职责/规则、条件及依赖匹配、当前会话明确相关来源。各路去重后最多 40 条；为时间/条件候选保留份额，不让向量热度占满。
3. 生成阶段从候选中选择最多 8 条真正影响方案的情境；必须给出它改变哪部分结果。不要求补满 8 条。
4. 检查相反/更新记录与本周期的实际任务完成状态。用时点和 source revision 获取快照，不能拿旧统计推断本月未做。
5. 缺口重要时允许一次原文补查，最多 4 段、8,000 字符；再次不足则明确条件，不继续自动循环。

### 7.2 向量实现

复用后端 `/v1/ai/embeddings` 的 transport/provider，新增 `personal_context_embedding` purpose 与路由，不借用 thought_embedding 的“已经过审核”假设。

新增 `HoloContextEmbeddingStore`，不要把 contextID 写进 `ThoughtEmbeddingStore` 的 thoughtId 空间。缓存键包含 source/context ID、contentHash、模型 ID、模型版本、维度、policyVersion、accessGeneration。返回数量、有限数值、非零范数、维度及模型版本全部验证；不匹配的候选先排除再重建。

允许复用已有想法向量，仅限同一规范化文本、模型、版本与当前权限吻合；现有 topNeighbors 未充分检查每个 entry 的 modelVersion，新能力不可直接无条件调用。

向量和目录只存本机受保护缓存，可丢弃重建，不进入 CloudKit；淘汰保留覆盖指标。首版参考 5,000 条分段向量上限；超过后结合分页原文/词法搜索，不能等同资料不存在。

查询向量无网络时，用对象、时间、条件和多查询词法召回；标记 semanticCoverage=degraded，仍返回基础方案。这是降级，不算正常通用召回已验收。

## 8. 规划运行与输出契约

### 8.1 运行输入与生命周期

新增 `HoloPlanningRun`：runID、parentMessageID、requestRevision、state、frame、accessGeneration、retrievalSnapshot、draftRevision、budget、createdAt/updatedAt。state 为 preparing/retrieving/generating/needsInput/draftReady/failed/cancelled。

每轮新需求有新的 requestRevision；同一 run 的追问回复更新 frame 并重新判定适用性。旧回调同时核对 runID、requestRevision、accessGeneration；取消后不落新草案。重要状态在现有聊天持久化载荷中保存，不只存在 ViewModel 内存。

持久化 checkpoint 仅保存必要的 frame、来源 refs/版本、已验证草案与预算状态，候选原文和内部验证推理不复制进聊天。恢复时重新获取允许访问的来源；原文不可用则降级该部分，不用 checkpoint 恢复已忘记的正文。消息展示保持可读的普通 answerText 兜底，结构化 payload 缺失/未知时仍能阅读已有回复。

### 8.2 `HoloContextPlanDraft`（新增）

- `schemaVersion`、`runID`、`draftRevision`、`goalSummary`、`answerText`。
- `usedContextRefs[]`：实际采用的情境 ID/版本与来源；不可用 ID 必须剔除。
- `items[]`：稳定 itemID、title、kind(task/checklistItem/adjustment/information)、reason、basis(personalEvidence/generalKnowledge/inference)、sourceRefs、preconditions、relativeTiming、可选 confirmedDate、selected。
- `unknowns[]`：question、为什么影响结果、哪些部分不依赖答案。最多优先展示 2 个真正影响安排的问题。
- `dependencyEdges[]`：前置 itemID 到后续 itemID，必须为无环图；未满足前置条件不能伪装执行完成。
- `coverage`：已读取来源、缺失范围、外部事实是否验证；给用户自然表达，不露内部评分。

普通建议、问题列表也可只有 answerText 和 information/adjustment 项，不强制有任务或长期目标。相对时间必须保留为相对时间，缺少锚点不能伪造日历日期。

### 8.3 生成与校验

专用生成 prompt 完成：确认当前目标→审查成功条件→选择相关背景→考虑替代解释与缺口→生成可用方案。后台内部推理不展示给用户，输出仅为 JSON 契约及可见文案。

`HoloContextPlanValidator` 校验来源、源版本、事实/建议区别、日期精度、已完成事项、循环依赖、重复项、非法动作和敏感边界。个性化事实必须有证据；一般准备知识允许没有个人来源，但不能伪装已知用户状态或实时外部事实。

失败允许一次结构修复/补查后的再生成，所有调用计入预算；仍失败则给原请求的基础回答并说明无法可靠使用的部分，不写任何业务事项。不可把失败 JSON substring 恰好解析成功当作语义通过。

## 9. 三个入口的具体接线

### 9.1 自然语言聊天

在 `IntentDescriptor.swift` / `AIModels.swift` / 对应 Prompt 中注册语义意图 `contextual_planning`（query 类、只读），覆盖规划、准备、决策前需了解什么、调整方案等语义，不依赖固定关键词。

为意图输出增加可选 `contextRequest`（frame 的轻量版本），兼容旧解析；不向意图识别注入私密背景或候选事项。已有意图识别调用生成初始检索方向，避免每轮额外增加一次独立 planner 调用。

`ConversationCoordinator.process` 在所有写执行之前识别该只读路由，返回 `planningRequest`；`ChatViewModel` 调用新 coordinator 生成结构化草案。明确单动作执行、精确明细查询、已有深度分析承接优先走原路。请求同时包含规划与写动作时维持现有澄清/确认边界。

旧后端不支持新意图/字段时回退普通聊天，记录 capabilityUnavailable；不得悄悄让未注入新能力的回答显示“已结合个人情境”。

### 9.2 目标规划入口

`GoalPlanningCoordinator` 的每轮问题和草案使用共享 preparedContext，不再只用通用 todayState 摘要。第一轮没有 seed 先询问目标；有足够内容时直接生成，不强行走三轮仪式。

`GoalPlanningPromptBuilder` 允许零习惯，并在适合长期目标时才生成 GoalDraft。一次事件返回 ContextPlanDraft；`GoalModels.swift` 增加兼容的结果区分，不让普通清单保存时强制创建 Goal。

显式入口没有 intent parser 时，通过新增 `personal_context_request` 小调用生成 frame，再使用同一检索与生成流程。已有 goal quota 预检要按真实预算更新，不能保留“至少两次调用够用”的错误假设。

### 9.3 深度 Agent

`HoloLocalAgentRuntime` 的规划/建议任务接入新 context tool 或 preparedContext。优先在既有 agent loop 的工具选择中生成 frame，不再启动另一个无限循环或重复计一轮会员额度。

新 tool 返回已筛选的事实、限定推断和未知，保留真实 evidence ID；不得把一般建议伪造成 `metricAssertion` 或确切统计。按现有 verifier 处理事实，建议内容由 plan validator 处理。正常查询明细仍不以记忆替代原始数据。

Agent Job 已拥有消息时，结果更新继续由当前 job/runID 负责，普通 Chat 不抢写；续问和恢复必须按新 requestRevision 重新核对背景权限与来源。

三入口通过同一 `HoloContextPromptRenderer` 生成上下文，去掉 UserContext 里重复的旧记忆注入；保留必要档案，但同一来源只出现一次。

## 10. 用户界面与执行

复用聊天卡和草案审阅风格，新建 `ContextPlanChatCard` / `ContextPlanReviewView`，支持普通说明、清单、待办、调整和关键问题。

展示相关事项的短理由；“查看依据”只展示实际读取且仍允许访问的来源。没有使用到的记忆不能出现在 attribution badge 中。涉及他人偏好明确指向该对象。

支持“已安排好 / 本次不用 / 情况变了”：前两者改变本次草案；情况变化再区分本次例外和持续更新，复用记忆纠正，不把不采纳当成事实错误。

新建 `HoloContextPlanExecutionAdapter`，把已选 task/checklistItem 转为现有 pending task DTO（结构化映射，不把整个计划重新丢回意图识别模型）。保存仍走现有确认/Repository 规则。

幂等键绑定 `runID + draftRevision + itemID`，落到现有来源标记/回执体系；先持久化 confirming，再写实体，恢复按键对账。双击、部分失败重试和 App 中断不得重复创建。内容相似的其他任务只能提示可能重复，不直接修改或合并。

最终确认保存时再次检查 accessGeneration、source revision 与 draftRevision；生成后才被忘记/更改的背景不能继续用于保存。已有同一逻辑 item 的成功回执须跨 draftRevision 对账：新版本未实质改变的事项复用 logicalItemID，不因编辑另一项就重复创建它；实质改变则生成清楚的变更候选，禁止只靠新 revision 躲过去重。

旧草案已保存后用户改计划：生成明确变更草案，原业务事项不静默删除。只允许本次确实创建且未被其他操作修改的事项按现有撤销规则撤回。

## 11. Provider、后端与 Prompt

新增调用方法必须声明在 `AIProvider` 协议本体，避免只有 extension 导致静态派发：`extractPersonalContext`、`verifyPersonalContext`、`prepareContextRequest`、`generateContextPlan`；embedding 用可选能力协议 `HoloContextEmbeddingProvider`。

`HoloBackendAIProvider` 使用服务端 purpose；`OpenAICompatibleProvider` 使用同样的 iOS 后备契约。不支持 embedding 的 Provider 可降级混合词法检索，不能悄悄把用户选定 Provider 的原文改发另一家。

新增 purposes/prompts：

| 名称 | 用途 | 预算默认 |
|---|---|---|
| personal_context_extraction | 领域内开放关系萃取 | 无新增会员池；独立 minute/day 和 token 限额 |
| personal_context_verification | 候选语义核验 | 同上，批量且有候选上限 |
| personal_context_request | 显式入口无 frame 时准备目标框架 | 归 chat；仅需要时调用 |
| personal_context_planning | 本次方案生成 | 归 chat；Agent 内复用 agent_loop 原预算 |
| personal_context_embedding | 语义向量 | 独立限流/日上限，不默认为无限 |

修改位置：`HoloBackend/src/app.js` 的 purpose 校验、quotaTypeForPurpose、请求限制、embedding allowlist；`src/config.js` routes；`src/prompts/serverPromptPolicy.js` 映射与语言策略；`src/prompts/promptRegistry.js` 版本；`defaultPrompts.json` 模板；iOS `PromptManager.swift` 的所有对应 PromptType 映射/后备版本；`HoloBackendAIProvider.swift` purpose 枚举和协议。

不要硬编码当前版本号，基于实施时 registry 递增。新增 purpose 缺路由或 prompt 时应明确降级，不能落入未知类型的无额度路径。遵循所选 Provider 对结构化输出的真实能力：JSON parser + validator 必须存在，不假定 DeepSeek 支持 response_format=json_object。

成本口径：一次正常自然语言规划复用既有 intent frame，新增一次 chat 生成；显式无 frame 入口最多多一次 request 调用。修复/再生成是额外调用，如成功消耗额度须真实反映。仅网络重传同一请求可复用 usageActionId；改变 prompt/输入的修复是新 action ID，不能用固定 ID 无限免计量。复用 `quotaActionLedgerStore` 的成功/失败语义，并测试不重复扣同一网络重试、不同调用不误去重。

初始服务端上限（作为配置初值，非已验证成本）：萃取/核验每设备各 4 次/分、60 次/日；单包最多 12,000 字符，输出最多 4,000 tokens；planning 继承 chat 会员池且每 run 最多 2 次生成；embedding 每批 16 段、每段 2,000 字符，20 次/分、120 次/日。客户端还需预算，无权放大服务端上限。大量历史补建耗尽当日预算时次日续跑，不占满交互队列。

后台萃取不得改变现有订阅权益文案或新增独立收费；如实测无法承受初始预算，保留内部灰度并向东林报告成本证据后调整公开范围，不借调试参数无限运行。

## 12. 隐私与日志必须随新链路接入

`adminLogStore.js` 强制 metadata_only 加入所有 personal_context 文本 purposes；管理员开启抓取也不能放开正文。embedding 不记录文本或向量。

Agent 接入后 `agent_loop` 也可能携带原始想法和新情境，首版将其请求/响应正文日志整体收敛为 metadata_only，并同步客户端日志。接受诊断正文减少的取舍，用合成夹具和脱敏状态事件定位问题，不仅保护新 purpose 而漏掉既有 Agent 通道。目标规划含新情境时改走专用 planning 方法，不再从普通 chat 日志通道旁路。审核失败和异常处理中同样不能回显请求正文。

客户端 `HoloBackendAIProvider.chat(messages:purpose:)` 当前会把请求/响应放进 `lastCallLog`，新 methods 不能直接无条件继承此行为；对新目的仅记录 requestID、purpose、版本、长度、token、时长、结果码。检查 Debug 导出和内部日志不会再次保存全文。

日志只允许 refs/count/status，不打印关系对象名字和来源片段。新规划明确的可见回答可以正常保存在用户聊天记录中；内部候选/原文不重复塞入聊天正文或诊断文件。

原文进入新 embedding 通道时不能依赖旧 thought_organization 审核已经发生。复用后端现有输入审核设施，按相同规范化 revision 去重；失败则跳过外发向量，走受限检索，不绕过。

### 15.2 模型评测与泛化门禁

先创建 fixture schema：sources、currentRequest、expectedSupportedRelations、unknowns、expectedPlanEffects、forbiddenClaims、counterfactualVariants。使用合成内容或已获准的脱敏内容，不批量上传真实用户私密资料做测试。

开发集可包含探索稿已公开的七类场景。它们不能再叫未见测试。实施前单独生成并冻结不少于 40 组留出情境，覆盖不同领域与组合；提示词调试不可读取其逐题答案。跑最终评测后若据错误改 Prompt，该集合转为回归集，下次泛化评估换新留出集。

最低候选发布目标（目标而非已通过）：

- 留出集中关键计划影响召回率 ≥85%，每个内容领域 ≥75%。
- 输出的个性化断言有来源支持或适当限定的比例 ≥95%。
- 无关个人补充率 ≤10%；反事实变体中应改变的建议正确变化 ≥90%。
- 忘记/越权引用、伪造来源、未经确认执行、把本次完成当永久取消：固定回归集零次。
- 至少 20 个关键样例各跑 3 次，单独报告不稳定例；其他样例至少 1 次。报告分子/分母、Provider/模型/Prompt版本，不能只给平均评分。

使用盲化的结构化人工/独立评审标准核对结果；LLM judge 仅作辅助，不以同一个生成器“自评通过”作为结论。如果无法维持评测隔离，标记为公开回归，不声称未见泛化。

### 15.3 性能与真实入口

在 0/100/1000/5000 条合成来源上测本地筛选/缓存/检索耗时、内存、索引覆盖及 rebuild 成本；以设备实测报告 p50/p95。初始目标：warm 本地召回 p95 ≤200ms，主线程不执行数据库全量扫描或向量计算；达不到则保持灰度，不能直接把上限缩到漏掉历史还称通过。

分别报告首轮冷启动、已建索引、需补查、离线、429 和取消的完整耗时及调用数量。端到端时延由真实 Provider 决定，本方案不预报固定秒数。

真实 Simulator/真机点穿：写入想法→萃取→退出重进→从聊天/规划入口提问→显示正确来源→纠正→更新草案→选择保存→对应任务可见→重试不重复。新/旧客户端兼容、用户清空后和长期未打开后的续跑另测。

## 16. 发布控制、兼容与回滚

新增内部控制 extraction / retrieval / planningInjection / rawFallback，默认仅内部账号启用；总闸仍与用户记忆开关、AI consent 相与。retrieval 开、injection 关时只做脱敏计数，不在用户回答中显性使用。

部署顺序：

1. 本地后端与 iOS 契约测试完成，新旧 payload 混合兼容。
2. 准备并验证后端新 purpose、Prompt 版本、限流/配额与 metadata 日志；获得部署授权后发布后端，老客户端继续原路。
3. 核对 `/v1/release/status`、`/v1/prompts/meta`，用合成源跑真实请求验证版本、响应、额度和日志；仅健康检查不算功能生效。
4. 发布可兼容的新客户端，内部开关开启，点穿与成本观察合格后再小范围灰度。
5. 如实际引入新的 CloudKit schema 变更，Development 与 Production 分开验收，Production 部署另获最终确认。按本文默认载荷扩展无需先增 CloudKit entity，不因此跳过混合客户端测试。

回滚先关闭新回答注入和原文兜底，再按需停萃取；保留原文、用户控制、来源和旧记忆，不能全量清库。新缓存可销毁重建；失败迁移有 journal/备份才回滚。后端保留已发布 purpose 的兼容响应，不先删除新客户端仍在调用的路由。

部署前按现有 `holo-backend-deploy` skill 与项目流程操作；核对目标仓库、环境和生产保护文件。本次 GLM 交付时明确本地实现、后端是否部署、客户端是否发布三层状态。

## 18. 方案自审记录

本节在首稿完成后进行二次走查并补充。审查的是实施方案的可执行性，不是功能已通过测试。

自审结论：本文已从产品探索细化到可执行工单，发现的方案缺口已在对应章节修正；可以交给 GLM 开始 P0。这里的“已修正”只指规格，所有实现/模型/生产门禁仍需实际完成。

| 审查问题 | 首稿风险 | 本版处理与复验点 |
|---|---|---|
| 是否仍在枚举场景 | 把公共 facets 当白名单也会过拟合 | relationText 开放，other 保留原文；检索方向来自目标；公开例子不计留出集 |
| 新语义身份是否会覆盖旧内容 | 仅修改 subjectKey 不影响现有 ID | 程序分配 contextID 锚点、严格归并、旧 ID 算法不动；P1 碰撞与重放测试 |
| 旧客户端是否剥掉载荷 | 可选字段只能保证能读，不能保证旧写保留 | 首版新派生记录本机存储；未知版本信封保留；降级/混合版本测试明确区分 |
| 是否把存储位置误当敏感等级 | 为留本机把记录伪标 sensitive 会使建议全部失效 | 存储分流与语义 sensitivity 分开，四种写路径同规则 |
| 语义验证是否能被自报类型绕过 | 首稿仅强制验证 inferred，模型可误标 declared | 所有自由文本候选批量验证，结构化字段才允许确定性通道 |
| 后台批次是否会漏半批 | 现有 Repository 不接受跨存储分区混写 | 分区 receipt 与总游标收口；部分失败与源版本竞态测试 |
| 来源更新是否覆盖全部入口 | 只监听编辑页或 updatedAt 会漏导入、恢复和远端旧时间戳 | 统一变更队列、恢复不撤销遗忘、源修订目录分批对账；P4 接线与入口回归 |
| 是否形成大量确认打扰 | 所有 candidate 会进入原“待确认”队列 | advice 背景与真正待确认分开，计数/列表同一政策 |
| 遗忘能否被新检索绕过 | 原文、向量或另一个设备可重新推导 | generation、学习基线、源片段抑制键、跨设备与改写回归；未知改写能力不虚报 |
| 隐私是否只保护了新 purpose | Agent/旧 chat 仍可记录新情境原文 | agent_loop 与新目的 metadata_only；目标新链路避免旧 chat 旁路；测试异常日志 |
| 多入口是否真正接到执行前 | Router 可能先执行扩展动作 | contextual_planning 为只读 query，在写入前分流；纯执行保留旧规则 |
| 计划生成后权限变化怎么办 | 回调时检查一次不够 | 保存前再次核对 source/access/draft 版本；checkpoint 不留可恢复的私密正文 |
| 跨草案版本是否重复创建 | 单纯 run+revision+item 幂等无法跨版本去重 | logicalItemID 与成功回执对账；已创建项目变化单独生成变更候选 |
| 调用次数和额度是否自洽 | 多轮 repair 可能免费无限跑或额外扣量不明 | 真实调用预算、新输入新 action ID、网络重试同 ID、前台预检按真实路径更新 |

| 是否把计划当作 AGI 证明 | 纸面推演、自评、关键词命中容易虚高 | 冻结留出集、分域指标、反事实与重复运行、真实三入口点穿 |

实施时必须保留的风险门禁：模型语义准确性、对陌生关系的召回、语义遗忘的边界、真实成本/时延与混合版本行为。它们不能仅靠文档消除；如未达到第 15 节门槛，交付内部可测版本与明确失败证据，不能宣称已完成公开发布。

自审后的范围取舍：首版复用记忆持久化与现有向量网关，不新建图数据库；新情境先本机存储；关系跨域组合先在本轮形成；全部入口共享读取与输出规则。以上是为了控制实现复杂度，不以牺牲原文覆盖、权限或核心推演验收来缩减范围。
