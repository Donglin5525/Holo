# Holo 目标闭环：最终方案与 GLM 实施交接

日期：2026-10-20。状态：最终实施规格，待 GLM 实施；本轮只核实代码、整理方案及标注原型，没有修改 App、模型或后端。

本文件是本轮唯一实施依据。用户认可了旅程逻辑，同时明确要求沿用现有产品布局。此前 HTML 只说明流程和异常分支，不是页面、导航或组件排列的定稿；不得按 HTML 重做 Holo 界面。本文件与旧方案或 HTML 有差异时，以本文件为准。

## 1. 产品结论与不可改变的边界

要补齐的是：Holo 能把不同愿望转为现有模块中的可执行安排，并结合真实记录持续分析、修正同一个目标。不是新增一套包揽所有记录的目标工作台。

完整链路为：

**设置目标 → AI 拆解 → 用户确认建立或关联任务、习惯、可选预算及结果来源 → 回各原模块执行 → 目标分析寻找差距 → 用户确认修正 → 继续执行、再次验证 → 达成或结束。**

以下为本期固定决策，GLM 不应再自行改变：

1. 保留现有主导航、模块首页、个人页入口和 HoloAI 页结构。目标仍从现有「个人 → 我的目标 → 目标管理」进入；不增加主导航中的目标 Tab，不把目标列表搬进任务首页。
2. 记账、账户余额核对和预算管理在财务；打卡、数值习惯记录在习惯；任务安排与完成在任务；健康观测和想法分别留在原模块。目标详情只展示摘要、关联关系和跳转入口。
3. 目标分析在「目标详情」和「HoloAI」承载。两处读取同一份持久化报告，使用现有报告详情与追问能力。不是两份分别生成的报告。
4. 目标和 HoloAI 可以在确认计划时协调创建、关联或调整原模块对象。用户确认的是计划变化；实际对象仍归原模块管理，后续日常记录回原模块。
5. 目标结果、行动执行、预算或行为限制分别判断，不合成为一个看似精确的成功率。打卡成功不等于存够钱、体重改变或英语能力提升。
6. 默认一个主要结果、少量必要行动、按需限制，不要求每个目标凑齐五大模块。AI 自动提出拆解，用户只补会影响计划的关键信息。
7. 修正继续使用原 goalID，保留历史记录与原成功标准。优先调整方法、安排和负担；改变成果、金额总额或截止时间必须单独明确确认。
8. 首期就交付三类目标的完整闭环；不能只做新建和报告，把「采纳后真的改变原模块安排」留到下一期。

## 2. 现有界面怎样承接

### 2.1 页面与职责

| 现有位置 | 本期增量 | 不能出现的变化 |
|---|---|---|
| 个人 → 我的目标 → 目标管理 | 保留目标列表卡片与新建菜单；卡片可加一条待回顾/待确认状态 | 新主导航、目标和任务合并、新目标首页框架 |
| 现有「一起想清楚 / 让 HoloAI 规划」流程 | 在现有对话和确认页补成功标准、来源、执行项、可选限制、下次回顾摘要 | 长表单向导、强制五模块配置、另起一套规划入口 |
| 现有目标详情 | 原位增加「目标分析」区及计划版本入口；保留已有概览、关联任务/习惯、设置及权限功能 | 内嵌财务/习惯/任务的子 Tab、记账表单、打卡面板、另一份任务列表首页 |
| 现有财务、习惯、任务、健康、想法 | 使用原页面完成记录和对象编辑；必要时加轻量「关联目标」标识 | 各模块新增独立报告中心、目标页复制记录入口 |
| HoloAI 对话 | 带目标上下文发起分析、显示分析消息、追问、进入修正确认 | 用户每次重述目标、单独目标聊天系统 |
| HoloAI 现有「报告」Tab | 归档目标报告、使用目标筛选、进入同一详情；保持原有收藏/搜索/追问 | 新增第二个目标报告 Tab；把现有只读归档页改成生成向导 |

目标详情的新增内容用当前卡片、字体、间距和操作样式，放在现有概览之后、详细关联内容之前；现有区块内部排序和功能不重做。宽屏继续使用当前适配方式，不照搬原型手机壳或评审侧栏。

### 2.2 目标详情的「目标分析」区

只显示最新一份有效报告的简短结论、生成时间、分析范围和状态；没有报告时显示下次回顾时间及「分析目标」。存在历史报告时提供「查看报告」「历史分析」；有可采纳建议时显示「查看调整」。

状态与动作：

| 状态 | 用户看见与可以做什么 |
|---|---|
| 首次、尚未到期 | 下次回顾日期；可主动分析，不强制等待 |
| 到期或发现值得关注的变化 | 一条「该回顾一下了」提示；分析或稍后；不在每次打开时重复弹出 |
| 生成中 | 显示现有分析任务进度；可离开、回到 HoloAI、按既有规则取消；重复点击回到同一任务 |
| 完成 | 最新结论、证据范围、查看完整报告；同一 reportMessageID 在 HoloAI 可见 |
| 无数据或部分数据 | 显示哪些已知、哪些未知；补最少信息或先试行，不判用户失败 |
| 失败、离线或额度不足 | 原计划继续有效；显示真实原因，保留上下文，允许重试或稍后 |
| 建议待确认 | 进入现有共创/草案确认样式的修正单，不能直接执行报告正文中的自然语言 |
| 依据或计划已变化 | 历史报告仍可读，调整标记待刷新；刷新后重新确认 |

「去记录」根据来源跳转原模块，不在此区弹出另一套记录表单。保留旧有通用手动目标记录的兼容能力；新规划的财务和数值习惯目标不再借通用手填入口复制原模块事实。

HoloAI中的待回顾提示放在现有对话流的目标卡片样式中：同一reviewID更新一条本地提示，不新增看板/页签，也不自动替用户发送分析请求。目标列表和目标详情读取同一待回顾状态；报告Tab只归档已经完成的真实报告。

### 2.3 两个报告入口与返回路径

- 目标详情「查看报告」：在现有导航容器内打开共用的 ReportDetailRoute；返回原目标及原滚动位置。
- HoloAI 对话分析卡、HoloAI 报告档案：打开同一 ReportDetailRoute、同一 reportMessageID，展示关联目标并可返回目标详情。
- 从报告去看账单、预算、任务、习惯：沿现有 DeepLinkState 和各模块消费者跳转；保留必要的目标/报告来源用于返回，不建立第二个 HomeView。
- HoloAI 报告 Tab 负责归档；「分析目标」从目标详情或 HoloAI 对话发起。目标发起可直接启动现有分析链，并在对话中落同一消息，不额外要求用户再发一次同样的问题。
- 在普通 HoloAI 对话中提到目标：能唯一识别且已授权时绑定；有歧义只澄清具体目标。不靠标题猜测后写入另一个目标。

## 3. 统一的用户旅程

### 3.1 设置和 AI 拆解

用户用自然语言表达想做的事。AI 给出一份可修改的轻量计划：想得到什么结果、怎样判断、准备做什么、结果从哪里读、有哪些限制、何时回顾。没有明确成功标准时帮助定义一个可观察成果，不强迫所有愿望数字化。

优先复用用户授权的现有习惯、任务、财务来源和预算。没有合适对象时在同一确认单中建议创建；需先在财务完善账户等设置时给一个原模块跳转，计划可先建立，来源标记「待补齐」。不要求用户分别完成五个设置向导后才能开始。

确认页使用现有草案列表样式，按「结果 / 执行安排 / 可选限制 / 回顾」呈现摘要；每项可取消、编辑、选择已有对象。默认只展开关键差异，详细设置继续使用原模块现有编辑器。默认展示最有价值的一至三项行动，其余可展开；不是硬性数据上限。

首次确认后一次提交目标、计划版本及所选原模块对象。失败不得出现「目标创建成功，但习惯或预算漏了」；成功回执说明建了什么及到哪里执行，不跳到新目标工作台。

现有「一起想清楚」「让 HoloAI 规划」均接同一计划契约与提交规则，不能新流程正确、旧入口仍绕过来源和版本验证。手动创建保留；其后首次使用分析时补齐必要的结果/回顾约定，不强迫重新跑完整 AI 共创。

### 3.2 原模块执行与数据回流

日常只在原模块记录一次。目标分析按已确认的关联读取数据：

| 内容 | 记录与维护位置 | 目标读取的含义 |
|---|---|---|
| 消费、收入、余额核对 | 财务 | 真实资金状态、相关支出变化；不是习惯完成率 |
| 预算 | 财务现有预算设置/详情 | 约定上限及已发生支出；预算降低不代表已省下钱 |
| 体重、练习量、运动量等数值习惯 | 习惯 | 最新观测、窗口趋势或累计量，按指标语义计算 |
| 任务 | 任务 | 已安排、已完成、延期；计划时间和截止时间分别保存 |
| 健康数据 | 健康 | 已授权、确有支持的观测，说明来源与覆盖；不虚构自动取数能力 |
| 想法和用户反馈 | 想法；本次复盘的主观反馈可在目标/HoloAI | 原因线索、环境变化、成果自评；不自动升级为客观事实 |

数字习惯全局的「今天有记录即算完成」规则保持不变。比如记录 3 杯奶茶可以完成了记录动作，同时不满足本目标的每周上限；目标限制的判断从原始数量另算，不改习惯模块的通用完成规则。

### 3.3 分析寻找差距

报告优先回答五件事：

1. 当初想达到什么、这轮按哪个计划执行。
2. 行动做了多少，结果变化多少，限制有没有被突破；各自来源和观测时间。
3. 差距主要在哪里：执行没跟上、方法未见效、负担/资源或环境变化、限制冲突，还是证据暂缺。
4. 哪些原因有证据，哪些只是待确认线索；需要用户补的最关键问题是什么。
5. 下一步继续什么、建议改什么、预期观察什么、何时复查。

未知不是零。只有任务完成但缺近期体重/资金/交流反馈时，明确「能看执行，暂不能判断成果」。已有证据足以支持低成本调整时，允许先试行，并写清观察窗口与停止条件。进展顺利则建议保持，不为了有建议而加任务。

计算、时间窗口、金额、次数、进度及规则由代码确定；模型解释证据、提出假设和行动建议。不得把相关性直接写成确定因果，例如只有餐饮总额不能断言奶茶和宵夜分别多了；需要明细标签、习惯记录或用户确认。

### 3.4 确认修正与再验证

报告中的「查看调整」打开结构化差异单：当前安排 → 建议安排 → 原因 → 适用期限 → 影响对象。用户可逐项取消和编辑，确认后真实更新原目标及所选对象。只点阅读、追问或离开均不改计划。

修正可以是：改任务安排、调习惯频次、替换行为、增删本目标阶段要求、调整预算、切换结果来源、改变回顾节奏。只有明确选中并单独确认时，才修改成果标准、总目标金额或截止时间。默认不因落后而自动加码；用户可拒绝不可承受的追赶方案并继续讨论。

预算是财务模块的全局约定，不能把目标的局部偏好静默覆盖到既有预算。修改已有预算须单独展示影响范围、起效周期、当前周期已花与剩余额度并确认；不回改历史支出。阶段结束只结束本目标的临时限制绑定，不自动删除/恢复一个后来已被用户调整的财务预算。

行为含义不变的频次/时段调整可更新原对象；行为含义改变时结束旧阶段关联、创建或关联替代行为，保留旧记录的原意。共享对象只改本目标绑定和要求，不能为了一个目标全局暂停、改名或重设其他目标正在使用的习惯。

调整后约定下次看什么。再次分析同时比较「调整是否执行」和「主要结果是否改善」，没有改善继续下一轮，不凭新增打卡宣布修正有效。

暂停/完成目标后停止目标专属回顾。阶段到期默认结束该目标的临时要求和专属提醒，不自动续期；独立习惯、共享任务和真实记录仍保留。恢复时从当前事实重估，不一次性补发全部错过回顾。

## 4. 三类场景用同一条链路验收

### 4.1 北海道旅行资金

示例只使用合成数字，不表示当前 App 已有独立「存钱」功能：用户确认旅行预算 18,000 元、六个实际存入期次、每期 3,000 元、明确的出发前资金截止日期。将「过年」解析成用户确认的具体日期和日历期次，不能始终假设某年春节或简单按天数除以 30。

**结果来源决策：资金事实仍由财务提供。**

- 若用户有确实用于旅行的财务账户，本期补齐目标对所选单一账户余额的读取。用户确认账户确实代表可用旅行资金；目标只做绑定和展示，余额记录及核对仍在财务。首期不自动创建账户或替用户划款。
- 若用户选择「全账本净结余增加」，界面必须使用这个真实名称，并确认它符合本目标的衡量方式。它不是专项旅行资金，不能在报告中改称已存入专款。
- 没有可靠来源则结果待补齐，继续安排可执行行动，并跳转财务完善。禁止在目标页新建旅行收支账或用「存钱习惯打卡」填充财务结果。旧 HTML 的「自报旅行资金」不能照搬为新产品入口。
- 本期不做多目标资金分配、投资收益、真实转账、独立存钱模块；需要专项分配但现有账户无法真实表达的情形保留未覆盖边界，不伪造已支持。未来储蓄能力仍在财务扩展。

两期后，可靠财务来源显示当前旅行资金 4,800 元；期次计划应有 6,000 元，少了 1,200 元，剩余四期：`(18,000 - 4,800) / 4 = 3,300`。若账户已有起始资金，它计入可用资金；先确认口径，不把起始资金重复累加。

报告可以同时显示餐饮支出上升；有明细或用户确认后，才能提出「近期外食、宵夜、奶茶变多」这一线索。建议试行四周的奶茶/宵夜上限习惯、可选餐饮预算及每期 3,300 元安排。上限数值和频率由用户确认，不替用户下健康结论。这里改的是后续资金安排，不把总目标从 18,000 元自动降低。

现有每期实际均值为 2,400 元，新安排比它高 900 元；若预计控制消费只能释放 600 元，仍有 300 元未覆盖。必须提示可行性，允许继续找方法、拒绝预算变更或明确调整原目标；不能把预计节省直接记成资金到账。补记资金至 6,000 元后，旧的 3,300 建议应失效并重算为 3,000。

### 4.2 减重或其他身体指标

用户确认自己的结果标准与期限。体重放在数值习惯记录，目标读取最新真实观测和约定窗口趋势；运动为行动习惯，预约课程是任务，课程预算可选。首次没测量时是未知，不是 0kg；体重不能按 sum 相加。

行动少时先调难执行的时间安排；行动有记录但结果未变时先核对测量覆盖、方法和负担，提出少量试行调整。不按剩余体重差额线性均摊为必须加速的任务，不自动压低饮食或提高运动量。改方法与改成果标准分开确认。

再次回顾检查调整后是否更能执行、结果趋势是否变化；没有足够观测则保留未知，不能由打卡代替结果。

### 4.3 学英语等成果型目标

例如用户想在工作交流中独立表达方案。结果可以是约定场景的真实尝试及简短自评，不必捏造分数；每日听读是行动，参加一次会议是任务，课程预算可选。

如果听读做了但表达仍卡顿，先用真实尝试或用户反馈定位问题，试行两周的场景口语练习；结束本目标旧阶段要求，保留原听读习惯与历史。新的口语练习不得通过给听读改名来继承旧次数。

再次用相同场景标准反馈判断能力变化。没有真实交流样本时，可以先试行，但不能宣称英语能力已提升。报告与确认机制与存钱、减重完全相同。

## 5. 本期必须补齐的六项能力

| 能力 | 已有基础 | 本期补齐 |
|---|---|---|
| AI 拆解 | 共创、草案、目标/任务/习惯首次保存 | 成功标准、授权来源选择、复用对象、可选预算、回顾规则一并确认 |
| 原模块关联 | Goal.tasks / Goal.habits，manual/habit/ledger 指标 | 区分结果、行动、限制、背景；支持预算与原模块来源的逻辑绑定、原模块跳转 |
| 统一事实 | 量化目标计算器、任务/习惯执行统计 | 同一事实快照供目标概览、分析、风险提醒使用；量化目标不再用任务60%+习惯40%冒充成果 |
| 目标报告 | HoloAI 分析、报告档案、统一详情 | 明确 goalID 和计划版本，双入口同报告，历史与失效状态可见 |
| 修正写回 | 首次共创保存和版本快照 | 更新同目标、真实差异单、原子提交、幂等、过期校验、共享对象保护 |
| 持续回顾 | 目标风险/截止提醒 | 周期回顾到期、变化去重、阶段到期、调整后再验证；暂停和完成时停止 |

「定期回顾」首期默认每周一次，可按目标调整或关闭；首次计划与执行时点明确时可推荐更适合的周期。到期先产生轻量待回顾状态，用户主动点击才调用模型。值得关注的变化可提前标记，同一目标只保留一个待回顾入口；不每次新增数据就生成报告。系统通知必须遵守现有权限与偏好，不能为此新增必开的通知授权。

自动后台生成报告不列为首期闭环必需。以后若做，必须走现有调度、授权、后台成本闸门和去重；本期不得另设无限制轮询或直接模型请求。

生成去重使用用户范围内的goalID、planRevisionID、标准化观察窗口和sourceDigest；同依据的生成中任务直接恢复，同依据已完成时优先打开已有报告。用户明确要求重新分析才新建reviewID；不能把每次点击的当前时间当作去重键而失效。目标页和HoloAI并发点按也只创建一个实际job。

### 6.2 财务、习惯与时间口径

- `ledgerScope` 现有字段尚未兑现范围语义。本期用兼容 payload 明确 `whole_ledger_delta` 或 `account_balance`；老目标空值仍按旧的全账本净结余增量解释，不能静默切为账户余额。
- `account_balance` 首期只选一个真实财务资产账户；读取财务既有截止时点余额查询并补齐可靠的错误/缺失区分。账户不存在、软删除、查询失败不是 0 元。没有可用来源时标未知；信用负债账户不能被默认为旅行专款。
- 财务金额使用 Decimal，保留原有发生时间、退款、对账调整及余额口径。余额可含核对调整，但解释消费原因时对账调整不得混入餐饮消费；来源修订触发依据更新。不要在目标服务重新手写另一份财务收支计算器。
- 资金安排保存明确的应存日期与金额；剩余期数取未来未过期的实际期次，截止当日/已过截止/无剩余期次分别处理。除零和把过去期次再次分配均不允许。
- habit 来源按用途：体重取 latest/约定趋势，练习时长可 sum，限制按原始数值和适用窗口计算。新建草案必须允许正确 aggregation，不能沿用构造器固定 sum。以显式记录的 0 区分「没喝」与「没记录」。
- 时间范围统一为 `[start, min(endExclusive, snapshotCutoffAt))`，携带时区。阶段规则只对生效后的记录解释，历史记录不按新规则重新命名或重算成新行为。
- 覆盖判断区分事件记录、按日观测、当前快照；不能用「每天都记账」评价财务完整性。

### 6.3 同一个目标事实快照

建议新增纯值类型 GoalEvaluationSnapshot，由同一服务读取目标当前生效计划与授权来源，分别产生 result / execution / constraints / coverage / reviewStatus。供目标页、GoalAnalysisContextBuilder、GoalRiskEvaluator、GoalNotificationService 及 HoloGoalTool 使用。

结果包含真实观测时间和状态（observed / missing / stale / unavailable），不能用 baseline 自动伪装成最新观测。过程型目标可以展示执行情况；没有结果量时不输出虚假成果百分比。保留既有执行评分的适用范围，明确标为执行，不用它做量化目标达成判断。

预测按指标类型启用；存钱可算期次缺口，身体指标和英语成果不能照搬资金直线追赶。暂停、任务计划/截止、缺测、过期来源的规则与通知统一，防止页面说未知、通知却说必然失败。

### 6.4 报告身份与目标范围

沿用当前 cloud `deep_analysis` 任务类型、现有持久化消息和报告渲染链。目标复盘是带明确目标范围的分析，不新建孤立的 `goal_review` 网络流水线。

在现有 AnswerTask/请求、客户端冻结快照、后端验证、结果和消息归档的完整路径透传可选 typed goalScope。至少包含：

```json
{
  "schemaVersion": 1,
  "goalID": "10000000-0000-0000-0000-000000000001",
  "planRevisionID": "20000000-0000-0000-0000-000000000001",
  "reviewID": "30000000-0000-0000-0000-000000000001",
  "windowStart": "2026-10-01T00:00:00+08:00",
  "windowEndExclusive": "2026-10-15T00:00:00+08:00",
  "snapshotCutoffAt": "2026-10-15T09:00:00+08:00",
  "timeZoneID": "Asia/Shanghai",
  "sourceDigest": "opaque-source-revision-digest"
}
```

范围由用户请求和代码生成，模型不得改写；goalID 必须来自当前用户可访问且已授权的真实对象。指定单个目标时不能只扫活跃目标前 20 个，也不能把全部目标和生活记录当作默认上下文。只读取与当前判断有关且已授权的记录及必要比较窗口。

完成后以 **ChatMessage.id（reportMessageID）作为两个入口共用的报告身份**；HoloAgentResult.id / jobID 保留各自原义，不能混用。云端结果现有永久正文在 ChatMessage.agentResultJSON，继续沿用。需要快速反查时，增加轻量 GoalReviewLink 持久关联：goalID、planRevisionID、reviewID、reportMessageID、cutoff、生成状态/时间；只存索引和状态，不复制正文或财务记录。

现有结果模型增加可选 goalScope，并按当前已存在的报告扩展机制携带有类型的 adjustmentDraft；旧报告字段缺失应正常解码。goalScope 是权威归类，HoloAI 报告档案优先标为「目标」，再允许领域信息作副标签；不继续用「存钱」关键词把这份目标报告归到财务而在目标筛选中消失。用户问句的泛用归类保留旧行为。

报告详情复用现有内容块、证据、追问和推荐渲染；目标扩展只增加关联目标/版本提示和进入修正单的标准动作，不做另一份 HTML 或 Markdown 报告解析器。追问默认继承该目标范围，明确改变范围时才重建。

历史报告冻结原快照、原标准及原结论。新事实出现后标记建议待刷新，不回写改造旧报告；新的回顾形成新报告并保留 lineage。删除报告遵守现有报告与聊天删除语义，目标关联标记不可用或移除引用，不从缓存复活正文。删除目标不删真实生活记录；报告访问与保留沿现有删除/隐私契约处理，不能借 GoalReviewLink 恢复已删内容。

### 6.5 修正草案与提交

调整草案至少含 draftID、goalID、baseRevisionID、sourceReportMessageID、sourceDigest、createdAt、expiresAt、typed operations、预期观察结果。操作白名单包括：create/reuse/update 本目标可编辑对象、replace binding、end binding、update review、显式 change success criteria。禁止任意字段 patch、模型生成未知 ID、直接执行报告自然语言。

新对象先使用 draftRef，创建成功后解析为真实 ID；已有对象只能引用当前候选白名单内的 ID。结果来源、预算范围、习惯聚合、任务日期和可编辑权限都先本地验证。纯建议不能附带账单入账、替用户完成任务或补造打卡的操作。

确认过程必须：

1. 重新读取生效 revisionID 及所依赖记录的修订摘要，不依赖界面打开时的缓存。检查对象存在/权限/共享/冲突/到期。
2. 依赖事实改变、计划已改或草案过期时停止应用，保留用户选项，刷新差异后再确认。只比较相关数据，不让无关记录使每份建议失效。
3. 金额、期次等确定性内容在代码内重算；结果/期限改动有单独确认。用户取消的预算/习惯不得偷偷提交。
4. 在隔离的、指向同一持久化 store 的 context 中，写入所有选中变更、计划新版本、提交回执，一次 save。失败 rollback 本次隔离 context，不能 rollback 共享 viewContext 丢掉别处未保存的输入。
5. 成功后才发布原模块刷新和提醒重排；界面读取真实保存结果。幂等键 operationID 保证重复点按、超时重试和恢复不多建对象、不重复升版。

现有 BudgetRepository 的公开 add/update 会各自 save；现有共创提交也总是 Goal.create。因此不能直接循环调用这些方法实现上述语义。抽出接受注入 context、不单独 save 的构造/校验与变更函数供统一提交器使用；原模块公开 CRUD 保持当前行为。目标首次创建和既有目标调整要有不同明确分支。

任务/习惯/预算跨模块必须在同一兼容配置的 Core Data store 中才能承诺一次保存。GLM 第一步核查配置；若不满足，先实现可恢复的提交协调和明确的未生效态，未完成前不得开放「全部已应用」交互，不能把半成功伪装成完成。

CloudKit 多设备不是本地互斥锁：用 baseRevisionID 识别并发分支；发现同一父版本有不同已提交 revision 时先保留分支、暂停后续自动应用，重新核对实际模块对象并展示合并差异。不可只把 revisionNumber+1 或 updatedAt 当全局顺序。专属新建对象用稳定 operation/item ID 去重，冲突解决只处置本次新建对象；不自动删共享项或已被用户记录的习惯。多设备收敛前不能显示已无冲突，必须作为发布验收项。
