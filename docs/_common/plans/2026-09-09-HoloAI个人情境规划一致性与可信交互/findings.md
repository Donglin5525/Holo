# Findings：HoloAI 个人情境规划一致性与可信交互

## 录屏事实

- 同一句“要去日本旅行，要提前做什么准备”在同一会话内先得到普通长文本，后一次得到个人情境方案卡。
- 第二次发送后先显示三个点；退出 HoloAI 再进入时只剩 Holo 消息头和空白正文，但停止按钮仍存在。
- 最终方案一次性整块出现，没有中间阶段反馈。
- 方案中的“你的记录”标签不可点；“查看依据”按代码应展开，但依据没有原始来源跳转。
- 多个日期选择器显示当天，与条目相对时间不一致。

## 当前代码根因

- `ConversationCoordinator` 只有模型返回 `contextual_planning` 才进入规划器；规划失败被 `try?` 吞掉并静默回退普通聊天。
- 后端确定性意图稳定器没有覆盖“为具体事件做准备/安排”的规划句式。
- `HoloContextPlanningCoordinator` 已有 `preparing/retrieving/generating/...` 状态，但未桥接到 ChatMessage。
- Chat 页面重建后，全局 `isStreaming` 不从消息恢复；空 streaming 消息因此以非流式空文本渲染。
- ContextPlan 的云端调用是非流式完成请求；当前没有可恢复的云端规划 job 或阶段事件。
- `HoloContextPlanBasisEntry` 只有 contextID、statement、认识状态和周期状态，没有来源类型、来源 ID、时间、原文片段和跳转目标。
- DatePicker 用 `confirmedDates[itemID] ?? Date()` 显示当天，但保存请求只使用 `confirmedDates`，造成视觉日期与实际保存日期可能不一致。
- 草案默认选中全部 task/checklistItem；未知条件尚未回答时仍可一键批量写入。
- ChatMessage 已有独立 `contextPlanJSON`，但没有规划运行载荷；应新增独立的 `contextPlanRunJSON`，不挤占已经承担多种旧卡片兼容的 `extractedDataJSON`。
- 后端已有加密、可恢复、可取消和领取确认的云端异步分析任务底座，但任务类型白名单和执行器只支持深度分析、周期回放与摘要；可扩展 `context_plan`，不能直接把个人情境规划伪装成 `deep_analysis`。

## 产品风险

- 能力随机出现会让用户认为个人情境只是偶发效果。
- 状态丢失会同时破坏等待信任和停止语义。
- 二次提炼的命题如果不能回到原始记录，不构成用户可验证的证据。
- “没有收入记录”若表达为“收入为零”，属于数据缺失与事实混淆。
- 护照、签证等外部规则未联网核验时显示为确定要求，有事实过期风险。

## 与既有方案的关系

- 本方案不重做个人情境底座，而是在 2026-09-06 通用规划方案和 2026-09-07 产品化方案之上，补齐本次视频暴露的路由、可见状态、证据交互、日期与信任问题。
- 既有方案已明确：重要运行状态必须进入聊天持久化载荷；相对时间缺少锚点时不能伪造日历日期；实时外部事实未核验时只能生成待核验事项。
- 既有 Agent 稳定性方案提供可复用的不变量：一个运行只有一个执行权、状态需持久化、旧回调不得覆盖新状态，取消、恢复和失败都必须可解释。本次轻量规划无需强行升级成完整深度 Agent，但必须遵守同一套生命周期原则。
- 云端异步底座只返回 queued/running 等粗状态；面向用户的语义阶段仍需由 context plan 执行器产生并持久化，客户端不能用定时器虚构“正在检索记录”等进度。
