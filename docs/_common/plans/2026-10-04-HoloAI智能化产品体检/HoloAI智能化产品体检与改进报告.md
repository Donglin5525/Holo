# HoloAI 智能化产品体检与改进报告

**日期：2026-10-04｜对象：HoloAI 与记录、Today、规划、记忆、洞察的实际接线｜用途：版本取舍与整改依据**

东林，核心判断是：**Holo 已经具备广泛的数据访问和不少智能组件，但用户还没有稳定地得到“它理解我现在的处境，替我减少一个决策，并记得后续结果”的体验。** 数据联通为理解提供了原料；用户真正感知的智能，来自这些原料怎样改变判断、怎样成为可执行的调整、下次回来是否继续原来的事情。

建议把下一阶段的产品承诺收敛为：**“从你的记录里发现一处值得调整的地方，结合你的实际情况给出一个小行动，并在之后帮你回看。”** 首轮以消费回顾闭环落地；已有“今天减负”作为第二条验证场景，先补输入约束、采用与继续的体验。跨域数据在确实能改变建议时参与，不要求用户先记录满所有模块。

本次发现了三个明确的工程断点：正式配置下个人情境规划仍有内部账号门槛；默认 Today 减负输入没有真实日程约束和任务时长；行动回看存储缺少基线及业务调用方。同时，本地合成执行确认，**存在合法引用的错误金额，以及没有证据的定性判断，仍可能被云执行器交付为 completed。** 可信度和正式版可达性需要先过门槛。

## 2. 为什么“数据已经联通”，仍然像普通工具

用户可以自然说一句话，Holo 替他记一笔账、建几项待办，这已经省去了输入步骤。但同类工具也在降低录入负担。进一步的差异，需要发生在三个时刻：

1. **我还没想到该问什么，它已经发现一件值得关注的事。** 有意义的变化直接出现在原来的页面，且能说明依据。
2. **我说了当前的困难，它会改变建议。** 时间少、预算紧、已经做过、不想被催等条件，会影响行动内容；相关记忆不只是出现在开场白。
3. **我采用之后，它会继续。** 系统知道采用了什么、有没有实际执行、到了什么观察时间、这次能否判断变化。

目前较多体验仍是“用户发问 → 查询数据 → 生成报告 → 用户自己决定下一步”。一次报告可以准确、好看、有温度，但这些价值需要用户每次主动发起。**最缺的是持续接手一件小事的产品链路。** 这解释了为什么增加数据域、延长推理轮次、增加报告字数，未必会增加感知智能。

### 智能化能力应分层评估

| 层次 | 用户可感知的结果 | 当前判断 |
|---|---|---|
| 记录 | 说一句话，准确保存并能纠错 | 已有批量解析、卡片和保存基础；本轮未实模验收准确率 |
| 找回与计算 | 问一句话，找到正确记录、得到准确口径 | 动态查询、时间窗、证据基础较丰富；仍有交付防线缺口 |
| 理解处境 | 同一个问题，因为我当前条件不同而得到不同建议 | 记忆/情境基础存在，正式版门槛和云本地路径不一致影响体验 |
| 选择下一步 | 不只列出数据，能给少量可开始的行动 | Today、个人规划和目标共创已有组件；输入与行动范围有缺口 |
| 主动发现 | 合适的时候看见相关变化，少自己找 | 回放、通知、Observer 已有基础，机会触发和用户可见链路仍分散 |
| 持续推进 | 采用后可以继续、调整、撤销、回看 | 有执行回执与回看存储，但尚不能据源码确认统一闭环成立 |
| 从结果学习 | 纠正一次以后不再重复同类误判 | 有反馈和偏好学习组件；正式配置、结果学习和验收仍需收口 |

这里不使用“智能得分 65/100”这类总分。缺少真实旅程样本和用户价值数据，精确总分会造成误导。

由这些机制可以推断：**同类产品都在争取让 AI 直接减少某个工作步骤，而不是让用户多使用一个 AI 页面。** Holo 的多域记录提供了进一步优势，但优势必须体现为更合适的建议，不能仅体现为报告同时出现五个模块。

### Holo 值得争取的差异

“我最近外卖花得多”可以被普通记账软件发现；“我有很多待办”可以被普通任务软件发现。Holo 的机会是：在有授权、有相关记录和可靠依据的情况下，知道用户当前关心什么、什么条件限制了他，因此提出更适合的一步，并继续观察。

例如用户明确说“这个月项目赶工，先别让我做复杂的省钱计划”。系统应先区分一次性支出和持续开销，再给低负担调整，允许本周不调整。即使健康或想法没有记录，这个场景仍然有价值。**多域理解应提高建议适配度；单域数据也必须足以得到帮助。**

## 4. 需要保留、复用的基础

- 动态数据目录覆盖财务、任务、习惯、想法、目标、记忆、对话、纪念日、洞察、档案与健康等域；不能再说 HoloAI 只读财务。
- 记忆全局 rollout 已是 full，回答注入仍尊重用户“记忆辅助回答”开关；不是此前默认 shadow 的状态。
- 报告追问已有父结果身份、显式锚定和相邻追问路由；不能再把“完全没有连续追问”作为当前结论。
- 已有个人情境的检索、验证、规划草案、执行回执；已有 Today 减负的 proposal、ID 校验、采用和撤销基础。
- 已有证据展示、范围冻结、数字对账、云端任务和诚实失败基础；本轮发现的是防线不完整，并非所有结论都毫无核验。
- 反馈、偏好排序、Observer、行动候选、效果回看均有组件。应明确接线和正式可达范围，继续复用现有任务、Matter、记忆和保存规则。

因此，下一阶段的工作以**收口体验链路**为主，新增组件只服务于确实缺少的契约。首页品牌光球等已有资产继续保留；无须通过大改导航来证明智能化。

## 6. 六个最重要的断点

### 6.1 正式用户与开发体验不一致

**产品结论：** 开发环境里的“更懂我”不能直接视为正式用户得到的体验。

普通记忆 rollout 为 full；但 `HoloPersonalContextControls` 的萃取、检索和规划注入都要求内部账号。内部身份在 Debug / INTERNAL_DIAGNOSTICS 为 true，在普通 Release 为 false。个人情境规划和异步云规划读取同一身份。洞察反馈、学习和行动候选的默认值也按 DEBUG 区分，普通 Release 默认 false。

**产品决策：** 先形成一张正式版本能力清单，说明每条能力的用户授权、灰度、可用范围和回退。在质量门槛通过后逐条放量。不能为“立刻变聪明”直接将所有开关改为 true，也不能把开发包可用当商店版可用。

**技术证据：** E01–E03、E11；普通 Release 二进制的安装行为仍需验收。

### 6.2 结论有引用，仍不一定有依据

**产品结论：** 用户最在意的个人数字和判断，仍可能得到看似可信的错误结论。

本地执行器实际复现：两条合成消费合计 74 元，模型正文写“最近总支出 9999 元”，引用一个存在的汇总证据后，任务 completed，错误正文被保留。即使金额断言对账失败，合法引用仍可让正文留下。空数据下“支出以餐饮外卖为主”也能 completed，只带 `NO_TOOL_EVIDENCE` 警告。客户端所审阅的组合方法仍会消费这些正文。

**产品决策：** 每条事实需要“该证据能支持该结论”，而不只是“引用 ID 存在”。数值与数据口径交给确定性计算，模型负责解释和建议。定性事实、用户陈述、假设、建议、诚实的数据不足分别标明来源类型；对账失败不得保留原来的事实措辞。不要只继续扩充数字正则。

**技术证据：** E05、E06、E17 与 4 场景合成执行。没有用真实模型证明出错比例，没有对生产投放对抗请求。

### 6.3 能查所有数据，仍不等于每次得到相关情境

**产品结论：** 一份长报告可能用到了很多数据，却没有用到真正改变建议的那个条件。

首次普通深度分析走云端，周计划和报告续问仍走本地。云端有 memory/profile 数据目录，可按工具请求读取；本地另有相关记忆预取、个人档案和互动策略注入。所审阅的云端普通执行入口没有同等的相关情境预取注入。不能把它说成“云端没有任何记忆”，但也不能假定两个入口总能得到同样的个人理解。

**产品决策：** 普通回答、深度分析、续问、Today 和规划使用同源的相关情境选择规则。对输出记录“用到了什么条件、怎样改变建议”，例如避免高成本步骤、尊重当前家庭责任、减少提醒。只展示确实使用的来源，不能用“读取了 30 条记忆”证明个性化。

**技术证据：** E04、E05、E07、E15。云本地相同问题的真实模型差异需配对评测。

数据完整性也要连到答案：快照已经增加总行数和覆盖下界，但当前查询引擎尚未找到消费这些字段的逻辑。默认 180 天、每个数据集 2000 行的明细限制仍在。年度与高记录量问题需使用完整聚合或明确降级，不能把“字段已补”视为整条统计链已验收。E19，C 证据。

### 6.4 当前处境尚未成为完整的行动约束

**产品结论：** “今天减负”已有可用设计基础，但不能据此承诺知道用户一天到底有没有时间。

默认 context builder 的 `constraints` 为空，日历只有 authorized/notAuthorized 状态，任务 durationMinutes 为 nil。模型能依据用户当次输入和任务标题挑选、减负，但真实会议、空档和耗时没有进入默认请求。

**产品决策：** 首轮保留减负定位：挑少量任务、明确一项开始步骤、允许先放下。需要安排时段时才补真实日程与可信时长；没有时长就询问一个必要条件或只给排序，不伪造精确安排。日程变化后将旧建议标为需复核，采用前重新校验事实。

**技术证据：** E08。现有 proposal、ID 校验、采用与撤销机制值得复用。

### 6.5 主动能力尚未围绕“有帮助的机会”收敛

**产品结论：** 有回放和通知，不等于每次主动出现都能解决当下问题。

Observer 的 Tier2 当前根据目标信号数量决定升级，多项评分输入是常量或由距上次触发时间推导。它已正确设置 `userAuthorized: false`，不能沿用“伪造通知授权”的旧指控。当前结构较难直接回答“这个消费变化是否重要、用户是否已处理、现在出现是否有帮助”。

**产品决策：** 先做 App 内一条高质量机会，再考虑推送。选择变化是否可靠、是否与当前关注相关、用户能否行动、是否重复、是否已解决；在财务页或 Today 原有入口出现。拒绝与忽略应影响同类机会再出现的频率。

**技术证据：** E12。不要重新建立第二套洞察和通知系统；应把机会生命周期接入已有链路。

### 6.6 建议、执行与回看还未承担同一件事

**产品结论：** Holo 能生成建议，也能创建任务，但还缺少对“这个调整后来怎样了”的持续负责。

回看存储保存 actionID、指标键和执行时间等字段；没有冻结前值、统计窗口、证据或数据完整性。扫描 App Swift 源码，只找到记忆洞察卡记录执行的调用，没有找到 pendingReviews / generateReview 的外部调用。现有行动候选主要是少量规则，其中“逾期多 → 再创建清理待办”还可能加重负担。

**产品决策：** 采用时记录为什么做、基线、观察时间、实际保存的实体或轻量关注约定。到期重读数据，判断继续、调整、停止或无法判断。消费调整不必强制变成 Todo；“本周留意外卖，下周一起回看”可以复用已有事项/关注载体。Todo 的创建成功与用户实际执行必须分别记录。

**技术证据：** E09、E10、E16。回看不能把变化自动归因于建议，也不能把未执行理解为用户不配合。

## 7. 整改清单：可直接用于排期

**P1**：影响本阶段智能承诺或信任，先处理；**P2**：在首个闭环成立后深化。P1 不表示每项必须同时做，应按第 10 节顺序推进。

| AI01 | 正式版本能力与授权清单 | P1 / C+V | 用户知道哪些帮助可用；灰度内能真实使用个人情境 | 产品+iOS |

| AI06 | 建议采用的统一状态与回执 | P1 / C+J | 草案、已保存、执行中、已取消、待回看含义明确 | iOS+数据 |

| AI10 | 情境时效、人物归属与冲突 | P2 / C+V | 临时状态会失效，他人的情况不变成自己的档案 | 记忆+数据 |

| AI13 | 追问、纠正、换话题持续性 | P2 / C+V | 继续原结论时保留依据，换话题时不错误承接 | 对话+AI |
| AI14 | 最小必要数据与完整统计 | P1 / C+V | 只读相关域；历史、截断和不可用范围如实呈现 | 数据+后端 |
| AI15 | 等待、取消与结果恢复 | P1 / C+V | 长任务可离开，可取消，成功结果重启仍能找回 | iOS+后端 |
| AI16 | 单次帮助的延迟与成本 | P2 / V | 轻问题尽快答，复杂问题才深分析；费用可管理 | AI+后端 |
| AI17 | 面向真实帮助的评测门槛 | P1 / C+J | 质量升级有配对样本和独立留出集证明 | 产品+QA |
| AI18 | 冷启动与价值事件验证 | P1 / J+V | 第一天就省一步；第七天回来能接着用 | 产品+增长 |

### 全局整改规则

- 事实计算、日期、任务 ID、保存和副作用继续使用现有统一规则；模型输出 proposal，客户端守住真实实体。
- 当前用户表达优先于历史推断，确认事实优先于旧模式；允许用户轻松纠错和关闭。
- 自动发现、取相关情境等只读帮助在授权范围内低负担完成；采用涉及修改的计划时有具体预览和清楚的撤销边界。
- 已经存在的数据授权与灰度门槛应讲清价值后设置，不能把它们隐藏或绕过。
- 主动提醒先过真实性、授权、相关性、重复、过期和时机门槛，再评分；高分不能抵消硬性缺口。
- 新增关注状态复用已有 Matter、任务、记忆及规范；保持一个执行真相源，避免“AI 认为完成、任务仍未完成”。

## 8. 下一版应该给用户什么具体体验

### 8.1 主场景：消费记录到下周回看

推荐首轮覆盖一个用户问题：**“我知道最近花得有点多，但不想为此再管理一套复杂计划。”** 与已有全面产品体检的财务入口方向一致；仍是市场假设，需要真实使用验证。

| 时刻 | 应出现的体验 | 成立条件 |
|---|---|---|
| 第一笔 | 自然输入、准确保存、能修改分类/备注 | 保存回读一致，不需完整个人档案 |
| 数据渐多 | 展示一条范围明确、可核对的变化 | 有可比记录；少量记录只给事实，不硬给规律 |
| 用户愿意了解 | 一句话说明变化驱动因素，允许澄清一次性支出 | 依据可靠，比较口径一致 |
| 用户想调整 | 结合“时间少、替家人买、预算安排”等条件给一个轻行动 | 相关情境确实改变行动；不默认所有消费都该减少 |
| 采用 | 显示“这周关注什么，下次什么时候看”，可修改/停止 | 基线、范围与回执保存成功 |
| 下周 | 直接看到上次关注事项的变化，能继续或停止 | 重新读取真实数据；覆盖不足明确说明 |

以下为**目标交互示例，金额均为虚构演示**：

> 这周记录的餐饮支出比上周多 160 元，主要来自两次聚餐。你说这两次是给朋友庆生，所以我先把它们作为一次性支出看待，暂不建议压缩日常餐费。要不要只观察下周工作日的外卖？

这里的智能来自选择了更合适的口径、避免不必要的调整，并提供继续入口。需要上周和本周的实际记录，以及用户对聚餐的明确说明；不能凭消费名称补造原因。

### 8.2 第二场景：今天太满，只想推进一点

复用正在建设的 Today 减负：用户告诉 Holo“今天只有 20 分钟”。系统根据真实截止和已有步骤，挑一个可以开始的动作，说明其他任务为何先放下；采用后 Today 按同一计划显示，允许撤销。未知时长时不承诺能完成整项任务。

后续可逐步补日程约束与任务耗时。健康记录只能作为用户同意且确有意义的弱情境，不能从一次睡眠值推断心理状态或替用户决定一天。

### 8.3 长期场景：把反复出现的事情接起来

当用户反复记录装修、备考、照顾家人等一件事，Holo 应能找到已有记录，给当前相关下一步；之后打开同一个 Matter 或原页面可以继续。原想法、消费、任务保留各自事实，并通过现有连接关联。先确认主体和当前责任，再建议行动，避免“见到相关词就自动创建事项”。

这是后续差异化方向。首轮不同时铺开所有主题、联网准备和自动通知，先证明消费或 Today 的一个闭环。

## 9. HoloAI 页面应怎样调整

HoloAI 继续承担自然对话和复杂判断；日常收益更靠近原来的页面。

| 现有位置 | 推荐变化 | 验收焦点 |
|---|---|---|
| HoloAI 空态 | 按已有数据给最多三条具体问题，如“这周哪类开销变化最大”“今天先推进哪件事” | 点击后的能力在当前版本真实可用；无数据时给录入/找回等即时价值 |
| 常驻能力入口 | 常用帮助优先，额度说明放在真正需要消耗时；专业分析仍可访问 | 用户能凭问题完成任务，不必先理解四种内部流程 |
| 财务交易/回顾页 | “解释这次变化”“这笔分类不对”等带范围和实体上下文的入口 | 不重新上传全部无关域，不让用户重复说明对象 |
| 任务详情 / Today | “这一步怎么开始”“今天只保留几件” | 复用任务完成语义，不创建第二份任务状态 |
| 想法保存/找回 | 相关旧想法和“继续这件事” | 来源可回读，无可靠结果时安静留空 |
| 报告首屏 | 直接答案、一个建议、少量依据、继续入口 | 带可核对范围；问数字时不过度附送建议 |
| 已采用后的原页面 | 显示当前关注与下一次回看，允许停止 | 来自同一持久状态，不靠聊天文本猜进度 |

页面整理应减少用户决策，保留现有品牌与导航。没有必要先为这些能力建一个全新的“智能中心”。

## 10. 四阶段推进顺序

以下是排期建议，**按一个主要开发者估计约 4–6 周，包含评测与小样本使用；不是承诺工期**。前期核对数据契约和正式配置后重新估算。每阶段结束都有可观察的用户结果。

| 阶段 | 核心工作 | 交付与退出条件 |
|---|---|---|
| G0：可信与可达，约 3–5 工作日 | AI01、AI02；核对生产身份、用户授权、正式开关；冻结评测基线 | 合成坏事实拒绝；合法事实保留；正式测试包能力与清单一致 |
| G1：第一次有用，约 5–8 工作日 | 选消费一个变化场景；AI03、AI05、AI08、AI14、AI18 首切片 | 原页面看见可靠变化，条件改变建议，用户能选择一个小调整 |
| G2：采用后接得上，约 5–8 工作日 | AI06、AI07；完善 AI15 的该旅程恢复与结果回读 | 采用只产生一份有效状态；重启可恢复；到期重读数据并回看 |
| G3：检验与收口，至少覆盖 7–14 天观察 | AI17、AI18；负反馈、延迟/成本记录；正式真机矩阵 | 达到约定质量门槛，有用户独立再次使用的证据；未通过则修当前闭环 |

AI04 的完整日程排程、AI09–AI13 的深入能力和 AI16 的进一步优化，按首轮失败类型推进。已有 Today 实施继续完成自己的约束和验收；不要因这份报告同时展开七个大型工程。

### 具体依赖与回退

- G0 事实门槛不过，暂停扩大自动发现与通知范围；正常记录、查找等能力保持可用。
- G1 不先推出空洞的“每周总结”，只推出数据足够时的一条具体发现。达不到相关性门槛则隐藏该发现，不降低证据要求。
- G2 采用前冻结观察规则；停止关注时取消后续提醒，保留用户已经保存的原始数据；撤销能撤销到哪一步必须明确。
- 推进个人情境的正式灰度前，补授权、删除/遗忘、时效和最小必要外发验证；不以修改内部账号判断替代完整灰度。
- 涉及 Prompt、后端协议和云任务的实现，须双端同步、版本更新、后端发版和真实线上行为验证。本轮没有修改后端代码；未来本地提交或 push 不能替代部署。

## 11. 怎样证明 Holo 真的变聪明了

### 北极星与过程指标

**北极星：每周得到至少一次有效帮助并主动再次使用的用户数/占比。** “有效帮助”必须有看见结果，以及少一次查找/决策、实际采用或用户确认有帮助等信号；不能仅统计模型返回 completed。

单独记录“到期闭环完成率”：有真实采用、观察窗口已到期、完成回看或诚实无法判断，并有继续/调整/停止决策。开了报告、点了采用、创建了任务、实际执行了任务，是四个不同事件。

| 维度 | 应测什么 | 不应作为替代证明 |
|---|---|---|
| 事实可信 | 数值/范围/单位/引用与真实数据一致，定性事实有支持 | JSON 合法、拥有引用 ID |
| 个人适配 | 关键条件改变时，建议的内容/时机确实改变 | 提到昵称、复述旧记忆 |
| 克制 | 无关信息不改变建议，缺证据不强行出结论 | 回答长度、跨域数量 |
| 行动 | 预览、保存、撤销、执行和回读一致 | “已为你创建”文字 |
| 连续 | 冷启动、隔日回来能继续同一件事 | 单次对话工具调用多轮 |
| 主动价值 | 出现率、查看后有帮助比例、重复率和关闭原因 | 通知点击率单项 |
| 商业成本 | 每次有效帮助的耗时、调用、实际成本与退款/失败 | 单次模型价格或 token 更多 |

### 建议的首轮门槛

这些是项目验收目标，**不是行业基准或当前达成率**：

- 固定对抗集中的严重无证据事实、错误金额和越权动作：0 项漏交付；任一漏交付阻断扩大范围。
- 真实模型独立留出样本至少 60 个，每个 3 次；事实与范围正确率目标 ≥95%，同时要求高风险/严重错误为 0。
- 关键条件变化的 20 组配对场景：至少 16 组建议发生正确变化；无关信息变化至少 18 组保持核心建议。
- “帮我继续上一件事”含隔日、冷启动、删除来源、取消等样本全部有正确归属和状态。
- 轻查询首个有用结果 P95 目标 ≤8 秒；复杂分析按实际延迟给可离开、可恢复的状态，首轮测量后再定完整耗时目标。
- 小样本招募 10 位有真实记录需求的用户，至少观察两个使用周期；暂以 6 位完成首次价值、4 位在不同日期主动再次使用并能说出具体收益为推进信号。样本太小，不用于估算全市场留存。

评测必须针对正式路径和生产 Prompt；开发测试强制开启开关、评测脚本附加了生产没有的要求、损坏样本被跳过，都要单独披露。

## 12. 现有评测该怎样利用

项目已经有意图语料、个人情境测试和 A/B 评测脚本，值得保留。仓库中的 **2026-09-07 历史汇总**记录 24 个目标，个人影响字段有 21/24；模型判分的无关信息稳健性为 12/18，另有 6 个损坏/跳过样本。它提示应关注“无关信息干扰”和样本丢失，但**不能当作当前模型、正式 App 的成功率**。

现有 A/B harness 的输入构造、额外输出要求和评测身份，还需要按当前生产契约收口。尤其不能采用轮换设备编号绕过额度或限流来做正式验收。应使用授权的内部评测身份、独立预算和可追踪 release/prompt/model。

本轮 82 项后端测试全绿，但其中已有用例将“断言对账失败、正文保留”视为预期通过，说明测试可能固化了不合适的产品规则。先明确要给用户什么可信结果，再调整断言；不能通过维持旧期望来保住全绿。

## 13. 现在不值得优先投入什么

| 投入方向 | 本阶段价值判断 |
|---|---|
| 更长的报告、更多分析轮次 | 未证明能提高决策质量；先测当前结论的可信与采用 |
| 全域每日自动深度分析 | 数据量、隐私外发和成本上升；首轮只做有触发理由的一条发现 |
| 每条记忆都要求用户确认 | 会把智能变成维护负担；只在影响当前建议的重要歧义处澄清 |
| 先换最贵模型或做微调 | 可以配对试验；正式能力不可达、缺日程和缺回看不会靠换模型解决 |
| Avatar、更多陪伴话术或通知频次 | 不能替代实际理解与持续处理；需有用户价值后再判断 |
| 新建第二套 Agent/任务/个人档案 | 提高一致性成本；优先复用当前架构与事实源 |
| 把任何异常都转换成新 Todo | 容易增加负担；允许先观察、调整、停止，按原业务语义落地 |

## 14. 给下一轮实施的明确建议

推荐按 **AI02 事实门槛 → AI01 正式可达清单 → 消费一条高价值发现 → 采用与回看闭环 → 正式路径和真实用户验证** 排序。

这一轮应让用户能具体说出：**“它知道这次消费为什么不同，没有给我泛泛的省钱建议；我采用了一项调整，下周它还记得一起看。”** 达成这个体验之后，Holo 的多域数据才会从后台能力，变成用户愿意持续记录和回来使用的理由。
