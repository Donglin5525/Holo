# HoloAI 智能化体检：纳入判断与 G0 实施方案

日期：2026-10-04。基于[产品报告](HoloAI智能化产品体检与改进报告.md)与[技术证据](技术证据与复现清单.md)，经独立只读核实（六断点全属实）后形成的实施准备。**本文档为方案，尚未动任何代码。**

## 1. 结论先行

- 报告可信：六个关键代码断点独立核实全部属实，可作实施依据。
- **本轮纳入三件事（对应报告 G0）**：AI02 逐条事实交付门槛（先堵实锤漏洞）、AI01 正式版本能力清单、E19 截断元数据消费补全。
- 其余整改项（AI03–AI18 中的大件）按报告的依赖规则暂缓：**事实门槛不过，不扩大自动发现与通知范围**。
- **AI02 与 E19 需要后端发版**；iOS 侧有一处小改（消费后端 warnings），随下个 iOS 版本走。

## 3. 本轮实施范围与设计

### 3.1 AI02 第一步：堵住三个实锤漏洞（后端为主）

**策略：先堵已实锤的洞，再做语义分层。** 报告警告「不能用阻断所有无数字 claims 的粗规则替代语义契约」，因此第一步不新增协议字段、不动提示词，只收紧交付核验；factRole 语义分层作为第二步（见 §6）随 G1 推进。

改动点（均在 `HoloBackend/src/agent/cloudAnalysisExecutor.js` 的 `verifyDelivery`，157-268 行）：

**A. displayText 纳入数字闸门（堵 R02）**

现状：displayText 从不做数字一致性复核。
改法：displayText 中的可核对数字，必须满足其一才保留——
1. 有对应合法 metricAssertion 且对账通过；
2. 与 ledger 中某指标值一致（含 ±2% 容差，容差按指标舍入规则审查）；
3. 数字本身在「不可核对」白名单（如年份、样本数、百分比的分母等，实施中以固定对抗集校准）。

不满足 → 该 claim 整条撤回（进入修复轮重生成），而非保留正文只剥断言。

**B. 对账失败同步撤回正文（堵 R03）**

现状：METRIC_MISMATCH 只剥离断言，displayText 里同样的错误数字照交。
改法：断言对账失败时，若 displayText 含该断言对应数值（或近似值），视同 A 的失败处理——整条撤回进修复轮；重生成仍失败则该 claim 不交付。

**C. 空台账定性事实拦截（堵 R01）**

现状：`metricLedger.size === 0` 时只挂 NO_TOOL_EVIDENCE 警告，任务照常 completed。
改法：无任何指标入账时，含定性规律表述（「主要来自」「最多」「持续上升」等模式词）且无证据 IDs 支撑的 claims 不交付；允许保留的是诚实降级表述（「记录不足，无法判断」）与一般性建议。判定用模式词 + 证据缺失的组合，不做「无数字即拒绝」的粗规则。

**D. 测试期望修正（修 E17）**

`cloud-analysis-executor.test.js:959-1002` 用例改写为：错误金额正文不得交付（撤回或降级），用例名与断言一致。相邻 S02 用例（1004-1036 行）保持。
新增三条验收用例 = 把 R01/R02/R03 复现场景翻转为「必须拒绝」断言。合成复现入口（`evidence/合成对抗复现入口.mjs`）重跑，三场景期望翻绿为「拒交付」。

**iOS 侧小改（一处）**

`HoloCloudAnalysisService.swift` 消费 `result.warnings`：按 snapshotCoverage→truncatedNote 同款模式，把交付核验警告转成用户可读的「部分结论未能核验」标注。不做客户端第二套核验器（遵守报告全局规则：单一真相源在后端）。

**明确不做的**：不动提示词版本、不加协议字段、不改 2% 容差全局值（仅审查金额类指标的舍入口径）。

### 3.2 AI01：正式版本能力清单（文档产出，不动代码）

产出一份《正式版本能力与授权清单》，覆盖：

- 个人情境三闸（萃取/检索/规划注入）：普通 Release 不可达，属内部测试态
- 洞察五开关（feedback/learning/rerank/dailySense/actionCandidate）：普通 Release 默认关
- 记忆 rollout：full；回答注入受用户「记忆辅助回答」开关控制（新装默认关）
- Today 减负、云端深度分析、报告追问等已正式可达能力的授权条件与回退方式
- 每条能力标注：用户授权条件 / 当前灰度状态 / 回退开关 / 是否需要后端配合

清单同时给出**灰度建议**（哪些能力建议下一版开灰度、顺序与门槛），但**本轮不改任何开关**——开关变动是产品决策，单独拍板。

### 3.3 E19：截断元数据消费补全（后端小修，随 AI02 同批发版）

`cloudAnalysisQueryEngine.js`：
- 607 行空指标分支：`totalRows` 改为 `dataset.totalRows ?? dataset.rows?.length ?? 0`，警告文案区分「提供 N 行 / 共 M 行（截断）」
- 657 行工具目录 `rows=N` 同理用真实 totalRows
- `coveredFrom` 一并消费：目录/警告注明数据覆盖起点

测试：构造 totalRows > rows.length 的数据集，断言模型可见目录与空结论警告反映真实规模。

## 4. 测试与验收

| 验收项 | 通过标准 |
|---|---|
| R01 复现翻转 | 空数据定性事实 → 不交付（failed 或撤回），不再 completed 带警告 |
| R02 复现翻转 | 引用合法 + 金额 9999（真实 74）→ 错误正文不交付 |
| R03 复现翻转 | 断言对账失败 + 正文同数字 → 正文同步撤回 |
| 既有 82 项后端测试 | 修正期望后全绿（E17 用例翻转为新契约） |
| 回归红线 | 正常事实（合法金额、正确结论）仍正常交付——收紧不能误杀正确答案，用既有全绿测试 + 固定对抗集双向校准 |
| E19 | 截断数据集下模型目录/警告显示真实 totalRows |
| iOS | warnings 标注渲染正常，深度分析正常链路无回归（模拟器单点冒烟） |

对应评测方案 S03/S04/S05 在合成层转绿；真实模型层（60 样本 ×3）属 G3，不在本轮。

## 5. 发版与同步

- **需要后端发版**：AI02（executor 核验契约）+ E19（查询引擎）。同批部署，一次发版。
- 后端先行可独立上线（对旧版 iOS 无破坏：旧客户端不读 warnings，交付收紧对旧客户端同样生效并受益）。
- iOS warnings 消费属增强，随下个 iOS 版本，不阻塞后端发版。
- 发版后按惯例核对生产 release 身份与生效行为。

## 8. 拍板点

1. **是否按 G0 范围开工**（AI02 第一步 + AI01 + E19）——本文档主体。
2. **displayText 数字闸门的松紧**：方案 A 是「不满足三条保留规则的数字 → 整条 claim 撤回」，偏严；备选是「剥离该数字所在句子、保留其余」。建议先按方案 A 实施、用固定对抗集校准，误杀率超标再降级到备选。此项可在实施中自行决断，无需预拍板。
