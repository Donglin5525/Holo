# Holo APP 全面体检与整改白皮书

**体检日期：2026-10-04｜用途：市场推广前整改、后续版本取舍与验收**

东林，这份报告的核心判断是：**Holo 最缺的是一个用户能持续验证价值的使用闭环。** 目前已经有丰富的记录、分析、规划能力，但新用户仍需要自己决定从哪里开始、为什么持续记录，以及看完分析以后如何让生活发生一点变化。功能继续增加，会提高维护和理解成本；先把一个高频场景做到准确、轻松、可回看，才有机会形成留存。

推荐下一阶段围绕一个承诺收敛：**“轻松记下日常消费，每周看清一个值得调整的地方。”** 财务作为首轮入口，想法、习惯、健康、任务与 AI 作为需要时逐步出现的能力。这个推荐结合当前产品通路和既有使用线索，是待验证的市场假设，不是已经证明的产品市场匹配。

同时，当前代码有影响信任的明确缺口。推广前应优先解决设备身份校验、AI 无证据结论、数据保存与恢复、重复任务规则、账号删除。它们比新增模块更重要：用户把财务、健康和想法交给 Holo，信任一旦失去，很难靠新功能补回来。

## 2. 产品结论：应补齐什么，为什么

### 2.1 留存成立的最小条件

用户长期使用一个记录型产品，通常需要四件事同时成立：

1. **需求会再次发生。** 例如真实消费、需要找回的想法、正在推进的事情。
2. **当次收益大于当次负担。** 记录要更省事，纠错要简单，不能先学习一套概念。
3. **累积数据比单次使用更有价值。** 下周回来能看清变化、找回旧信息、继续原来的事。
4. **相信数据和结论。** 保存可靠，结论能核对，出错能恢复，用户能控制数据去向。

Holo 已经有第 1 项的广泛覆盖，也有第 2、3 项的组件；当前短板是把它们连成用户自然走得通的路径，以及把第 4 项做成全局一致的规则。

### 2.2 首轮完整场景

**记录一笔真实消费 → 核对金额、分类、账户 → 当周找回 → 查看有证据的变化 → 用户选择一项调整 → 下周对照结果。**

第一天只承诺准确记录和找回，不在数据不足时强行给洞察；一周有足够记录后，再显示范围明确的回顾；调整可以是“下周留意外卖”，不必每次都创建新任务。所有自动发现都允许忽略、纠正和关闭。

这个场景给其他模块留下自然扩展机会：用户写下消费原因时用想法；主动想调整时用习惯或任务；确有相关记录时才引入健康和个人情境。**不要求用户先完成五个模块的配置，才能体验 Holo 的价值。**

### 2.3 值得保留的基础

- 首页品牌光球、轨道和弧形文字有识别度。应保留品牌资产，通过行动入口和状态层级降低理解成本。
- 记账、习惯、任务、想法的本地能力给断网使用提供基础。AI 应增强这些能力，不能成为手动记录的必经条件。
- Today 的核心排序采用本地确定性规则；任务完成/撤销有统一执行链。继续沿用，不增加另一套完成状态。
- 当前已有 AI 数据授权、结果证据、分析范围、取消与恢复、订阅校验和额度等基础。需要补齐边界，不能把这些能力笼统说成“没有”。
- 已有新人引导、第一步行动卡、首次记录反馈、用户反馈入口、想法分享卡与回收站等。下一步应验证它们是否真正推动首次成功和再次使用。

## 5. 安全、AI 可信度与数据整改

### S01｜设备标识被当成身份凭证（P0，R+C）

**影响：** 设备编号是标识，不是“你有权访问这些数据”的证明。任意构造编号能创建云任务，会影响费用和滥用控制；若他人获得有效编号，还可能进入该编号关联的访问边界。没有证据表明生产已发生泄漏。

**事实：** 当前 `getDeviceId` 先接受 `x-holo-device-id`，后面的 `enforceAppAttest` 检查只处理缺编号情况。本地真实路由在强制配置下，无 assertion、无 session，仍返回 200。E01。

**整改：** 服务端统一验证请求身份；兼容未登录用户的受保护匿名会话，将设备/App Attest 校验结果绑定会话与资源归属；所有 AI、云任务、额度、反馈和关联读取路由复用同一规则。客户端编号只用于关联。采用分阶段升级，避免老客户端突然不可用。

**验收：** 无凭证、伪造编号、跨用户任务 ID、过期会话、重放均被拒绝；合法用户和允许的旧版本按明确策略工作；负例覆盖每种受保护路由。上线前核对生产有效配置与真实请求，禁止只验证 health。

### S02｜无证据结论仍能成为完成报告（P1，R+C）

**影响：** 用户会把个人数字当事实。没有记录时编出开支，比一般措辞不佳更伤信任。

**事实：** 空数据快照配合合成输出“本月支出 99999 元”，真实云执行器保存 completed。结果只有 `NO_TOOL_EVIDENCE` 警告；当前客户端没有按该警告阻断事实交付。已有核验依赖非空指标台账，台账空时有缺口。E02。

**整改：** 事实必须由工具数据、来源和核验结果支持；缺证据时输出“无法判断/记录不足”，一般建议明确标注。不要把整条回答仅靠数字正则过滤：用户自己陈述的数字、日期与目标值要有对应来源类型。将范围、证据、核验状态做成服务端与客户端共享契约。

**验收：** 空数据、伪造数字、错误引用、冲突时间窗、工具失败、用户陈述与实际账目不同等负例不能交付为已核实事实；可信事实可点击核对；实模评测中记录失败类型和实际通过率。合成通过后仍要补真实模型测试。

### S03｜只拿到部分数据，仍缺少完整性说明（P1，C）

**影响：** 活跃用户、长历史用户可能看到口径明确却数据不全的汇总。问一笔消费也可能上传多个无关数据域，增加隐私与成本负担。

**事实：** 云快照默认近 180 天、每个数据集最多 2000 行，按时间截断；数据集仅带 fields/rows，没有原始行数、截断标记和完整性状态。当前已有任务范围冻结，不能说“范围完全没有实现”。E03。

**整改：** 先按用户问题确定必要域和时间，再取最小必要摘要/数据；携带 requestedRange、coveredRange、总量、已提供量、截断与不可用原因。大范围统计先确定性汇总，不用截断明细冒充全量。

**验收：** 2001 条记录、超过 180 天、年报、跨月/跨时区、部分域不可读取时，金额不被截断误算，结果明确说明覆盖范围；无关域不会无必要上传。

### D01｜账户与日程完成保存失败仍可能显示成功（P1，C）

**影响：** 磁盘、数据库或上下文异常时，用户以为账户已创建/修改、日程已经勾选完成，重启后却找不到或状态恢复。没有进行真实故障注入，本轮不声称已发生丢失。

**事实：** `addAccount/updateAccount` 使用 `try? context.save()`，调用方创建后关闭页面；日程完成文件也使用 `try?` 编码/写入，随后继续更新界面。失败无法向界面反馈。E04、E27。

**整改：** 统一“持久化成功才能成功反馈”的保存规则；相关操作返回可判断的结果，失败保留输入、展示重试，按业务事务处理回滚。对关键保存链做定向扫查，避免只改账户表单。

**验收：** 注入保存失败后不会关闭表单或显示成功；重试一次只产生一条数据；账户、余额和日程完成状态重启回读一致。正常保存体验不增加额外确认。

### D02｜云结果未确认本地保存就回执销毁（P1，C）

**影响：** 本地保存失败、消息不存在或序列化失败时，云端可能已删除唯一可恢复结果。

**事实：** 普通云分析 finalizer 返回 Void；消息保存仅记日志。轮询 completed 后继续发送销毁回执。规划草案路径已增加回读检查，普通分析仍未共享这条规则。E05。

**整改：** 回执只在结果成功编码、事务保存并可持久回读后发送；用 taskID 实现幂等落库和恢复。失败保留云副本、展示可恢复状态；不能以更新内存快照替代保存证明。

**验收：** 本地保存失败、不存在消息、重复领取、进程中断、重启和回执网络失败下，既不丢结果也不生成重复报告；成功回执后的服务端清理有记录。

### D03｜迁移失败切换空库，用户没有恢复路径（P1，C）

**影响：** 用户升级后可能看到空白 App，以为记录全部丢失。文件备份存在，也不等于用户可以恢复。

**事实：** 当前对 134100–134199 迁移/模型类错误自动改名备份数据库相关文件，再尝试加载空库。三个文件逐一移动，异常时可能部分成功；未见对应的用户恢复流程。其它加载失败仍有崩溃出口。E06。

**整改：** 保留最后可读数据和迁移证据；备份整体校验、可恢复；进入明确的恢复状态，尽量提供只读访问/导出和重试，而不是悄悄把空库当正常成功。每个已发布模型都要有升级路径；云同步不能替代本地备份。

**验收：** 从真实发布版本带数据升级；损坏、模型不兼容、备份部分失败、iCloud 不可用时原数据仍可保护和恢复；用户能知道状态，空库不会伪装成完整恢复。

### D04｜财务“备份”没有恢复闭环（P1，C）

**影响：** 用户导出后相信可以还原，真正换机或修复时才发现不能恢复分类、账户和关联关系。

**事实：** JSON 被标为“完整备份格式，含分类和账户数据”，但导入类型和账单解析链未提供对应 HoloBackup JSON 恢复路径。设置主入口清楚写的是财务交易导出，所以不能把它误报为“承诺全 App 备份”。E07。

**整改：** 短期把不可恢复产物称为“结构化财务导出”，准确说明范围；优先补财务 JSON/附件的完整恢复，包括版本、关联 ID、去重和恢复预览。随后再计划全 App 可迁移备份，作为“个人数据资产”的长期基础。

**验收：** 在空测试库导出—恢复—逐项比对交易、账户、分类、金额、日期、关联与小票；重复恢复不复制数据；新旧格式兼容；全过程不依赖现有 iCloud 副本。

### T01｜重复次数、固定月日不兑现（P1，R+C）

**影响：** 用户选择“重复几次”或“每月 15 日”，得到的任务数量/日期与显示规则不符，影响提醒和长期计划。

**事实：** 当前任务详情允许次数结束；仅月度分支写 untilCount，而生成日期方法仍留有未实现的次数检查。固定月日模式存了 monthDay，计算却直接给原日期加一个月。合成规则 monthDay=15、起始 10 月 4 日，返回 11 月 4 日。E08。

**整改：** 统一可保存配置、规则描述和执行计算；定义次数是否含当前实例、月末缺失日期、提前/延迟完成、时区切换的语义，加入系列实例序号与稳定规则。实现前暂时隐藏不能兑现的选项。

**验收：** 每日/每周/每月/自定义次数限制，月 15 日、31 日、闰年、最后一个星期、结束当天、提前/延迟完成全部按约定生成。旧规则有明确迁移。其它底层异常若没有现行可达入口，按兼容债务处理，不伪报成已发生 UI BUG。

### T02｜下一次重复任务不保留必要内容（P1，C）

**影响：** “每周整理财务”的备注、检查清单等只在第一次存在，下次用户必须重建，削弱重复任务价值。

**事实：** 完成重复任务后，新实例只复制标题、清单、优先级、日期、全天和提醒等；没有复制备注、检查项等内容，也没有明确系列模板。E09。

**整改：** 建立“系列模板—单次实例”规则：哪些内容每次保留、哪些是单次结果、如何重置检查项；明确附件、步骤、预计时长、事项归属和提醒随日期重算规则。沿用统一完成/撤回语义。

**验收：** 带备注和检查项的任务完成两轮，内容保留且勾选状态正确重置；撤回不重复生成；改一次/改以后/改整个系列的影响可理解；事项进度与真实实例一致。

## 6. 隐私、授权与控制感整改

### P01｜删号缺少全生命周期清理（P1，C）

**影响：** 用户认为已经离开 Holo，但部分本机缓存、关联文件或服务端数据仍存在；也可能有在途任务写回新数据。

**事实：** 本机服务删除 Core Data、Holo 主目录、附件、部分临时文件和默认配置；独立 ThoughtAI、日程完成 JSON、Widget 共享数据及后端各类记录没有统一清理编排。设置已经说明 iCloud 删除会继续由系统同步，并非完全没有告知。E10。

**整改：** 按数据类别建立清单和清理责任：先停止在途任务、冻结写入、解除推送绑定，再删除本机/云端派生数据与账号；明确 iCloud、法律/安全必要留存与服务端备份时限。删除任务可恢复、幂等，有最终结果；正常退出登录和删除账号要有不同语义。

**验收：** 测试账户在双设备、断网、服务失败、AI 在途、后台恢复时，删除不会产生新数据；文件与服务端记录逐类查验；残余数据、时限和失败处理符合明确承诺。不在真实用户账号直接测试。

### P02｜Apple 撤销 token 种类错误（P1，C）

**影响：** 本地删除成功，Apple 授权撤销可能未完成，用户的账号退出闭环不完整。

**事实：** 后端向撤销接口发送 identityToken，并设置 `token_type_hint=id_token`。官方撤销接口使用 access token 或 refresh token。E11；[Apple Token revocation](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens)。

**整改：** 登录时交换授权码，安全管理可撤销 token；删除时执行撤销并跟踪结果。对历史账号无法取得 token 的情况，照常处理用户数据删除，提供官方认可的撤销指引，不以撤销失败阻止删除。

**验收：** 测试账号真实完成登录—删除—授权撤销；旧账号、配置缺失、Apple 暂时失败有可重试状态与准确提示。[Apple TN3194](https://developer.apple.com/documentation/technotes/tn3194-handling-account-deletions-and-revoking-tokens-for-sign-in-with-apple)。

### P03｜新人授权说明漏掉保存想法后的自动处理（P1，C）

**影响：** 用户以为只在主动问 AI 或另行开启自动记忆时上传，实际保存想法也可能触发自动整理。已有全局同意，但理解与行为不一致。

**事实：** 新人页说明“使用相关 AI / 主动开启自动形成记忆”；想法智能整理相关设置缺省启用。设置中的授权说明已经补充想法自动处理，新人页仍未一致。当前流水线有全局授权和撤回代际保护，不能据此声称完全无授权上传。E12。

**整改：** 统一版本化授权说明，明确主动处理与自动处理的触发、必要内容和第三方用途；第一次启用想法自动整理时能理解并单独关闭。普通记录不因拒绝 AI 被阻断。

**验收：** 全新安装、拒绝、同意、关闭自动整理、撤回处理中授权、老授权迁移均符合界面承诺，迟到结果不写回。[Apple 审核指南 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing)要求向第三方 AI 分享个人数据时清楚说明并取得明确许可。

### P04｜隐私政策版本与遥测说明不一致（P1，R+C）

**影响：** 中国用户可能从付费页打开英文政策；不同页面对数据处理范围表述不一致，影响信任和审核材料准确性。

**事实：** `/privacy` 是 8 月英文版，`/privacy.html` 是 6 月中文版，均 200，并非坏链接。英文版声明不自动收集设备/使用行为信息，而代码会在启动/前台上传 Agent 技术事件。技术诊断不同于广告追踪；本轮未核验生产是否保存正文。E13。

**整改：** 一个政策事实源、多语言对应版本；统一 App、官网、商店隐私标签。准确披露技术事件、设备关联、AI 必要数据、保留期、第三方与用户控制；核查生产日志开关，避免将业务正文混入诊断。

**验收：** 中文入口打开同步中文版；各语言日期、处理范围和权利一致；生产字段清单与实际抽样日志一致；隐私标签和审核说明逐项核对。不是要求把技术遥测一概删除。

## 7. 留存主线整改

### L01｜从“很多能力”变成“一件值得持续用的事”（P1，J）

**影响：** “人生数据库”描述的是系统能力；陌生用户仍不知道今天为什么装、下周为什么留。

**整改：** 首轮外部推广、商店前几张图、新人入口和第一周回顾统一围绕“省力记消费、看清一个变化”。展示真实前后过程，避免同时宣传五个模块、所有 AI 能力。保持全 App 能力，不用删模块来实现聚焦。

**验收：** 首轮用户能独立说清产品解决什么问题、完成一笔记录并找回；回访能说出一次具体帮助。依据 G01 的真实行为结果决定继续或调整，不以“觉得很酷”通过。

### L02｜激活应是第一次获得价值（P1，C+J）

**影响：** 创建一个尚未打卡的习惯就被判定激活，首页引导消失；完成第一条数据也不等于体验了省力和找回。

**事实：** 新人状态按 Transaction/TodoTask/Thought/Habit 任意未删除实体存在判断，首次庆祝另有财务首笔逻辑。已有引导，不是缺少引导。E14。

**整改：** 区分“完成初始设置”“首次持久保存”“首次找回/理解收益”“再次自主使用”；首轮财务引导只需记录、核对、找回，昵称/主题/通知等不必要决定可后置。不强迫开启 AI 才能进入手动路径。

**验收：** 新用户不由创始人口头提示即可完成；没有创建记录的设置不算激活；保存失败不算成功；不同入口都能回读；记录第一条后下一步具体、可跳过。

### L03｜从建议采用，到回来看它有没有帮助（P1，C+J）

**影响：** 如果 AI 每次只产出更多报告和任务，用户增加了管理负担，却不知道有没有变好。

**事实：** 当前有建议、反馈、任务和结果回看存储基础；本次调用搜索仅发现洞察任务草案的执行记录入口，未发现 pendingReviews/generateReview 的消费调用。不能把已有的洞察反馈、记忆纠正说成不存在。E15。

**整改：** 用户采用一项建议时记录目标、基线、期限、来源和观察方法；之后在原建议/原事项中回看，不新建另一套导航。事实变化与“因建议导致改善”分开表达；无记录就询问，不能推断成功。

**验收：** 同一条建议从采用到下周回看走通；用户可说“有帮助/没帮助/没执行”、修改或停止；没有足够数据不会自动宣布改善。北极星从报告数量变成被用户确认的有效回看。

### L04｜指标围绕价值，不围绕打开次数（P1，V+J）

**影响：** 只看下载、打开和 AI 消耗，会把好奇试用误认为留存，把高成本误认为高价值。

**整改：** 先用经用户同意的最小事件/人工回访建立漏斗：首次独立准确记录、次日/异日自主记录、回读、回顾、核对来源、采用调整、有效回看。只记录事件与结果，不采集原文和金额作为分析必需品。

**验收：** 每个指标有定义、分母、时间窗、版本和来源；手动检查能与事件一致。没有 ASC 与用户级行为数据时保持“未知”，不能给当前留存打分。具体口径见第 11 节。

## 8. 各模块与交互整改

### U01｜保留品牌光球，突出一个下一步（P2，J）

**影响：** 首页五个能力入口和 AI/Today/长廊同时出现，新人需要自己判断起点，老用户需要自己寻找今天最相关的动作。

**整改：** 光球、轨道、默认动效保留。新人只突出首轮场景行动，老用户优先显示一个真实可继续事项或快捷记录；模块入口作为稳定的第二层。空数据不堆假洞察，不用清空品牌来解决层级问题。

**验收：** 无提示找入口、记录一笔、返回和继续能完成；不增加页面体系。减少决策是否有效用实际首轮时间和错误路径观察，不靠审美评分。

### U02｜AI 帮用户说清这次要做什么（P2，J）

**整改：** 保留自由输入，在空态/相关入口用“记一笔”“问问这些记录”“把一件事安排好”等具体提示；结合来源默认合适意图。写入显示可核对字段，用户确认前不宣称执行成功；纯查询不生成任务，简单事情不强行共创。

**验收：** “昨天午饭 35”“本周外卖多少”“国庆旅行怎么准备”“暂时不想安排”分别得到合理结果；模糊时只问会改变结果的问题；避免新增模式切换负担。当前已有意图识别与结构化卡片，整改重在可理解和实模稳定。

### U03｜Today 从查看任务走向开始行动（P2，J）

**整改：** 焦点卡提供可执行的第一步、真实约束和“现在可以做什么”；有分步执行协议时沿用它。当天排不下时给用户选择减负的提案，不自动改截止日期；完成/撤回继续由统一执行器保存。

**验收：** 同一真实任务在 Today、任务详情、事项中状态一致；不制造第二套任务；无 AI、网络失败或未授权时仍可查看、完成、撤回。已有手动减负用例通过，实模与双设备还需补验收。

### U04｜没有预算不能说预算正常（P2，C）

**事实与影响：** Today 把缺预算/不可用映射为“不超支”，展示“预算正常”，给出没有依据的安心感。E16。

**整改：** 区分未设置、读取不可用、正常、接近上限、超支；没有预算时可安静显示“尚未设置预算”或不显示结论，不强迫设置。

**验收：** 无预算、无交易、读取失败与已超支分别准确；与财务模块同一口径。

### U05｜撤销打卡后周报仍可能计入（P2，C）

**事实与影响：** 周报按区间内 HabitRecord 的日期集合统计；打卡取消是 isCompleted 改为 false，记录仍存在，因此取消当天唯一打卡仍可能被计为打卡一天。E17。

**整改：** 使用统一的“当天有效习惯记录”口径，区分打卡型与数值型；数值型有有效记录与达标是两个概念，不能为了修周报又改坏数值习惯语义。

**验收：** 打卡—撤销、数值 0、未达目标但已记录、软删除、多习惯同一天、跨时区分别统计正确。

### U06｜健康页需要诚实表达数据可用性（P2，C）

**事实与影响：** 主仪表盘以数值大于 0 判断 available，否则多为 noData，难以区分真实零、无样本、读取失败/暂不可用。严格 AI 查询已有更细状态，不能泛化为健康系统完全没有错误处理。E18。

**整改：** 从读取服务到仪表盘透传可用性、覆盖日和来源；允许真实零值，失败给重试，未提供数据给设置指引。遵守 HealthKit 隐私边界，不把无法判断的读取授权状态硬说成用户拒绝。

**验收：** 无设备样本、真实零、锁屏/临时不可用、部分权限、旧数据、来源延迟分别准确；AI 与页面口径一致。不提供无依据的医疗诊断。

### U07｜想法的价值是被找回、复用和继续（P2，J）

**整改：** 在轻松保存基础上，优先展示“你之前写过什么”“为什么与这条相关”和原文跳转；人工标签、AI 推荐主题和自动归类的控制关系说清楚。普通用户不需理解语义索引、重建、版本等内部概念。

**验收：** 写入后冷启动可找回；用户按原话能找到旧内容；相关项能解释关联并纠错/排除；关闭整理仍保留原文与人工组织。真实模型关联精度未在本轮验证，不能把自动整理存在当成质量保证。

### U08｜习惯允许中断后轻松恢复（P2，J）

**整改：** 断签后的默认动作是“今天继续/暂时调整”，保留历史，不把一次中断渲染成全盘失败；展示记录频率与目标达成的区别。减少型习惯应按上限/戒除语义解释，不把“少做”当“多完成”。

**验收：** 用户断两天回来仍能一键继续；可暂停和调整未来目标，历史统计不被改写；周报、日历、Today、AI 使用统一语义。

### U09｜目标、事项、任务以用户结果组织（P2，J）

**整改：** 小事直接成为任务；跨天且有多个相关动作的事情使用事项持续推进；长期愿望共创目标，并显示成功证据。对用户解释“这件事—下一步—结果”，尽量隐藏 Matter、框架、投影等内部名词。现有真实实体和关联沿用。

**验收：** 旅行准备不会生成相互重复的两套清单；目标转行动有唯一来源；完成一个动作后各页面一致；更改计划不会把旧状态当新事实。没有完整真实旅程证据前不宣称系统全链路通过。

### U10｜让用户知道 Holo 为什么这样理解自己（P2，J）

**整改：** 洞察与方案旁就近展示采用的记录/用户陈述、推断和未知；已有纠正与记忆控制能力应在需要处可达。提供“不适用于我”“忘记这个判断”“本次不用这个背景”，避免用户被历史记录固定定义。

**验收：** 纠正后下一次不重复错误假设；删除来源后衍生结论失效；借用背景能回到来源；关闭记忆不影响基础记录。相关删除传播还需与 P01/R04 联合验收。

### U11｜通知只承诺可交付收益（P2，J+V）

**整改：** 继续保留现有授权、冷却与去重；加跨模块总量管理、静默时段、用户选择的场景频率。通知说的是确实可打开的结果或用户设定的提醒，而不是用焦虑和红点驱动打开。

**验收：** 周报无有效数据不发，结果已删除/失效不发；跨模块不会集中轰炸；点击能到对应记录；授权关闭和时区变化正常。通知送达需真机验证。

### U12｜分享服务用户成果，并保护敏感信息（P2，J+V）

**整改：** 复用已有想法卡片和品牌装饰，围绕用户愿意表达的片段/成果；涉及金额、账户、健康、姓名和位置的内容先可预览、可隐藏，不默认全量曝光。分享行为可选，不设邀请解锁基础价值。

**验收：** 长文、图片、深色、脱敏、系统分享与保存图片的真实导出正确；分享无需公开整个人生数据。不要把分享按钮存在视为增长飞轮已成立。

## 9. 发布、商业与质量门槛

### R01｜收入项目识别契约发生漂移（P1，R）

**事实：** 后端 1 个失败测试来自生成物一致性；实际 diff 显示客户端 record_income 描述包含 projectCandidate，后端事实源未包含。同一输入不同运行路径可能得到不同字段，不能声称所有意图都失效。E19。

**整改：** 先按最终产品规则确定收入项目归属，更新后端事实源和客户端生成物；同步 Prompt 后备、有效版本及部署身份，禁止手改生成文件绕过检查。

**验收：** 一致性和后端现有全套测试通过；“装修退款/某项目收入/未提项目”在客户端后备与后端有效 Prompt 结果一致；生产真实请求验证最终版本。

### R02｜建立正式版本的唯一验收身份（P1，R+V）

**事实：** 商店、本地工作区、生产后端是不同快照，体检期间源码还在变化。公网返回发布身份，但本轮没有核验生产密钥、验单模式、日志正文开关。E20。

**整改：** 每次发布固定 App build、客户端提交/工作区摘要、后端 commit/digest、有效 Prompt 和 CloudKit 模型；从同一快照运行验收。对外材料只描述正式上线并验收的能力。

**验收：** “本地完成—提交—App 发布—后端部署—生产验收”逐层可追溯。**当前检测到 HoloBackend 改动，后端改动需要发版/部署后端**；本报告没有执行部署，也不以本地 push 代替部署。

### R03｜修复失败用例，补齐真实核心旅程（P1，R）

**事实：** 旧三条 UI 旅程失败，新视觉导航用例通过，想法也已回读。自动化本身不足以稳定判断核心功能。E21。

**整改：** 用稳定可访问标识与当前导航机制更新用例；财务/任务/想法分别补“创建—核对—冷启动—编辑—删除/恢复”；保存失败、取消、重试也纳入。不能靠删断言变绿。

**验收：** 固定发布快照的三条核心旅程可靠通过，关键持久化有真实回读断言；失败原因可定位；再由真机人工完整走一次。截图导航测试不替代数据正确性测试。

### R04｜双设备与升级迁移仍缺本轮实证（P1，V）

**整改：** 验证发布模型从生产版本升级、两台同账号设备的创建/修改/删除/撤回、离线重连、并发编辑、软删除和衍生缓存失效；核对 CloudKit production schema 与各新增实体/字段。

**验收：** 对同一真实 ID 逐项回读，余额、完成、Today 选择与可见性收敛；不会删后复活或出现重复；迁移失败可恢复。当前没有证明线上同步坏，也没有证明已安全通过。E22。

### R05｜真机聊天与低资源红线待实证（P1，V）

**整改：** 按项目红线，在干净固定快照做真机聊天长对话/大报告、中文输入、照片横滑与返回、后台/锁屏、内存压力、磁盘紧张、网络中断和取消恢复；观察卡顿、崩溃、发热与电量，不只看构建。

**验收：** 无重复发送/结果丢失；停止能停止；核心页面可操作；内层照片横滑和返回符合预期；有设备型号、系统、样本量和性能记录。已有真机风险文档只是线索，不作为本轮复现。E23。

### R06｜付费要卖稳定收益，商业链路要实证（P1，V）

**整改：** 基础记录、回读、纠错和必要导出有明确权益；Plus 围绕已验证的高级收益表达，额度用用户能理解的范围说明，失败和重试计费口径一致。现有真实验单实现保留并核验生产模式。建立单次可信分析成本、自动整理成本、用户月度成本及退款后的权益规则。

**验收：** Apple Sandbox/允许的测试环境完成购买、恢复、换设备、续订、过期、退款/撤销、重复回执、账号变化、断网和额度耗尽；App 与后端权益一致，未确认的交易不能开通。真实价格/付费率/收入未获取，本报告不提供盈利结论。E24。

### R07｜无障碍、宽屏与正式语言承诺（P2，C+V）

**事实：** 静态颜色与部分大字导航通过；本地化目录仍有部分注册键缺少英文/繁体译文，数量不等于实际缺陷数量，部分可不翻译键需要排除。没有全 App VoiceOver 与 iPad 完整验收。E25。

**整改：** 按实际支持语言与设备检查主要旅程；大字保持主要操作可达，语音朗读有动作/状态，减少动态效果遵守系统设置；缺少译文不承诺已完成该语言体验。

**验收：** 新建/确认/取消/删除/撤回均可通过 VoiceOver；最大辅助字号不截断关键按钮；横竖屏/分屏可用；各正式语言主要旅程无原始键和明显混杂。

### G01｜用真实回访，而不是功能数量决定增长（P1，J+V）

**整改：** 四周招募 10 位可以持续联系、确有记账需求的人；先给真实任务，创始人不指导，之后看他们是否自主回来。先不扩大付费获客；每周约 5–8 小时可用于招募、回访、小内容实验和复盘。

**验收：** 每位记录原工具、真实困难、独立首次成功、再次使用日期、具体帮助、停止原因。目标可设为约 5 位在首用后第 2–7 天至少两个不同日期自主记录，这只是实验目标，不是行业留存标准，不足以推断大盘。策略是否成立看第 11 节的行为和访谈一致性。

## 11. 留存指标与四周市场验证

### 最小指标定义

| 指标 | 分子 / 分母 | 用途 |
|---|---|---|
| 独立首次成功率 | 无帮助完成真实保存并回读的人 / 实际开始首用的人 | 看入口和准确性，不用实体存在代替 |
| 首次价值时间 | 从开始尝试到保存、核对、找回完成 | 观察卡点；先收集分布，不捏造当前目标成绩 |
| 异日自主记录比例 | 首用后第 2–7 天至少两个不同日期主动记录的人 / 可观察的首用成功者 | 首轮频率假设；排除创始人催促和测试数据 |
| 回顾价值率 | 能指出一条正确且有用变化的人 / 实际看到回顾的人 | 数据不足的人单独标记，不隐藏在分母里 |
| 有效回看人数 | 采用建议后完成核对并认为有帮助的人数 | 留存主线；不等于因果改善人数 |
| 可靠性 | 保存/回读失败、错误金额、重复数据、错误结论等 / 对应实际操作 | 一次严重信任事故单独记录，不能被平均值掩盖 |
| 商店漏斗 | 曝光→产品页访问→首次下载，按来源和版本 | 使用 ASC；关键词覆盖和评分不能代替 |
| 成本 | 成功交付成本、失败成本、自动处理成本、单用户月成本 | 付费权益与自动化规模的边界 |

### 四周执行

| 周次 | 工作 | 决策依据 |
|---|---|---|
| 第 1 周 | 完成必要信任门槛；招募 3 人独立首用，观察一个场景 | 首次失败在哪；有没有比旧工具省事 |
| 第 2 周 | 累计约 6 人；只修最影响记录和找回的障碍 | 不催促时是否回来；记录可信否 |
| 第 3 周 | 累计约 10 人；让有足够数据的人看一次范围清楚的回顾 | 能否核对、能否指出具体帮助 |
| 第 4 周 | 回访、查看建议采用与再次使用；比较两类内容素材 | 继续使用和停止的真实原因；来源转化 |

首轮记录优先人工表格，不为了 10 人先搭复杂增长平台。每次只测试一个变化，保留版本和接触记录。

**决策规则：** 找不到入口就改首次体验；能用但不再回来，查需求频率与替代工具；持续记录却不看回顾，查回顾价值，不能用通知强推补救；能核对、有具体帮助且自主回用，才扩大相同人群。10 人只能发现机制与卡点，不能计算稳定的总体留存率或证明市场规模。

## 12. 整改执行顺序与发布门槛

### 第一阶段：守住数据与信任

优先 S01、S02、D01、D02、D03、P01–P04、R01。对准备正式推广的重复任务/备份路径，同时完成 T01、T02、D04，或者准确限制承诺、暂时关闭不可兑现选项。S03 在对外承诺深度统计前完成。

这一阶段可以并行处理不同模块，但鉴权、删除、迁移等需要一个统一规则与测试，不建议拆成大量表面修补。每项以验收关闭，不以“代码已写”关闭。后端项本地测试后仍需明确授权部署，再做生产验证。

### 第二阶段：交付一个留存版本

完成 L01–L04、U01–U03 及财务首轮相关问题，运行 G01。版本卖点就是“省力记录、可信周回顾”，不同时宣传全场景 AI 生活管理。回顾以实际记录为基础；用户没有数据时允许安静为空。

### 第三阶段：按使用收益扩展

修 U04–U12、R07；对真实用户正在使用的模块提级。想法复用、习惯恢复、事项继续各有单独闭环验收，再扩展跨域联动。全 App 可迁移备份应进入长期基础建设，而不是成为又一个无人验收的功能。

### 发布门槛

| 门槛 | 放行条件 | 不能替代它的证据 |
|---|---|---|
| 安全 | 受保护路由身份/归属负例通过，生产有效配置核对 | health 正常、设备编号存在 |
| 数据 | 保存失败不报成功、恢复可用、删除生命周期明确 | 正常条件下一次保存成功 |
| AI | 事实有证据、范围完整性诚实、实模负例通过 | Prompt 写了“不许编造”、合成正例 |
| 核心旅程 | 正式快照主要操作、冷启动和失败重试通过 | 构建成功、导航截图 |
| 同步/迁移 | 已发布模型升级与双设备关键操作通过 | 单设备模拟器通过 |
| 商业 | 真实测试交易与生产验单/额度身份验证 | mock 验单测试、付费页能打开 |
| 产品 | 陌生目标用户独立首次成功，能指出回用理由 | 功能数量、创始人演示、点赞 |

不能证明某个高风险能力安全时，先限制该能力的推广和开放范围；基础手动场景可以在自身门槛通过后进行小样本招募。不要为了“全面”一次实施 37 项，也不要带着已确认信任缺口投放放大流量。

## 13. 关闭整改项的统一规则

每个编号建立独立记录：负责模块、最终规则、影响版本、变更文件、正/负例、真实回读、后端部署身份、未覆盖范围。P0/P1 的关闭需复核相邻链路：例如修云保存要一起验领取/回执/重启，修打卡统计要一起验日历/Today/周报。

发布后持续记录真实投诉与异常，依据用户影响调整优先级；本报告中 J 项可被用户行为证伪，V 项必须补证据，R/C 项由具体修复与验收关闭。**最终目标是让用户少做决定、放心留下记录，并在下一次打开时得到可核对的帮助。**
