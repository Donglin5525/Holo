# 目标跨模块行动与反馈闭环：产品可行性与能力补齐

日期：2026-10-11。状态：产品建议，尚未确认实施；本轮只读核查源码，没有修改业务代码、运行 App 或核验生产。

## 1. 产品结论

可行。目标应承担「确定要得到的结果 → 组织行动与限制 → 从日常记录观察结果 → 复盘调整」的职责。任务、习惯、财务继续承担各自的执行和记录职责，目标负责把它们围绕同一件事组织起来。

价值假设：用户不必自己把愿望翻译成多个模块的设置，也不必重复汇报执行情况；打开目标就能知道做得怎样、结果是否改变、下一步值得调整什么。是否有价值，需要跨周使用行为验证，创建数量不能证明效果。

基本结构：

> 目标 = 成功标准 + 行动计划 + 约束条件 + 数据来源 + 复盘规则。

不是每个目标都要用到所有模块。仅纳入会改变行动或判断的关联，第一版默认一个主要结果指标、少量行动、可选限制。

## 2. 用减肥场景定义正确的对象

下表是产品结构示例；次数、金额、期限和结果目标由用户确认，不构成健康建议。

| 用户表达 | 建议承载方式 | 对目标的作用 | 判断依据 |
|---|---|---|---|
| 想减到自己确定的体重 | 目标的主要结果指标 | 判断结果是否达到 | 起点、目标值、测量日期、阶段趋势、完成标准 |
| 记录体重 | 数值习惯，测量类 | 给结果指标提供事实 | 最新观测与趋势；不能把体重相加 |
| 每周健身三次 | 周频习惯 | 追踪持续行动 | 当周已完成次数 / 当周目标次数 |
| 周三去上已预约的健身课 | 有时间的任务 | 安排一次具体执行 | 该次任务的完成情况 |
| 早睡 | 有明确时点的打卡习惯，或后续接入健康观测 | 追踪辅助行动 | 先确认何为早睡；自报打卡与设备观测要标明来源 |
| 戒奶茶 / 少喝奶茶 | 戒除或上限规则的习惯 | 行为限制 | 杯数或明确的未饮用记录；未记录不等于零杯 |
| 奶茶每月不超过自己确定的金额 | 财务分类预算 | 消费限制 | 指定账本、分类、周期内的预算与支出 |
| 取消奶茶订阅、准备替代饮品 | 一次性任务 | 降低执行阻力 | 一次完成即可，不代表长期戒除 |

关键决策：

- 「每周三次」先用现有周频习惯承载。具体预约才进任务；若以后自动排课，任务完成与习惯记录必须引用同一个执行事实，避免重复统计。
- 「戒奶茶」不应成为一个完成一次就永久达成的普通任务。
- 杯数和金额是两个限制。交易笔数不能代替杯数，一单可能多杯，购买也不等于本人饮用；免费或他人购买的饮品也不会出现在账本中。
- 宵夜分类不能直接当奶茶分类。用户确认匹配范围；第一版优先明确分类，混合分类则说明无法单独统计，不能只按商家名称猜。
- 体重记录可以沿用数值习惯入口，但记录行为本身不参与行动达标评分，测量值也不等于“好习惯完成率”。

### 作息的定义与来源（2026-10-11 原型评审补充）

不使用没有定义的「早睡记录」。用户确认时间阈值和观察对象后，分别呈现：

- **按时上床（自报）**：不晚于约定时间上床并准备睡觉。记录用户可执行的行为，不断言已经入睡。未打卡保持未知。
- **按时入睡（健康记录）**：读取该晚主睡眠首次入睡时间，按用户确认的阈值判断。只知道总睡眠时长、只有睡眠计划或只有在床记录时，不能宣称实际按时入睡。

有授权且字段可用时，建议关联健康记录并由用户确认；没有有效来源时可选择自报上床。来源切换需要明示，因为两者观察对象不同，不静默混算。健康方式不再创建重复的手动早睡打卡。

统计区分达标、超过约定和未知。例如一周只有五晚入睡记录，其中三晚达标，则显示「3/5 晚有记录达标，2 晚缺记录」，不把它写成「3/7 晚达标」并隐含其余都失败。跨午夜的 00:20 应属于同一睡眠夜，晚于 23:30；小睡不替代主睡眠。

当前源码基础：`Models/HealthRepository.swift:604` 的 `bedtime` 取主睡眠睡着区间的最早起点，可用于实际入睡的观察。尚需接入目标关联与评估规则，不代表已完成目标模块集成。HTML 已增加自报/健康两种来源的交互演示，健康记录均为合成样例。

## 3. 完整用户旅程

### 3.1 说出愿望与补关键事实

延续现有目标共创，只问会改变方案的问题：成功标准与期限、当前起点、能承担的行动和限制。先复用用户授权范围内的现有记录，避免重复问答；已知事实、用户选择和 AI 假设分别表达。

创建时先在本地或用户授权的数据范围内匹配本次目标所需的习惯，不要求把全部习惯及历史记录发送给 AI。匹配需核对实际记录含义、数值类型、单位、聚合方式、有效状态和既有目标归属，不能只凭名称判断。一个明确候选给关联建议，多个候选请用户选择；没有合适候选则把新建习惯纳入同一份计划，确认时一起保存。

区分「没有体重习惯」与「已有体重习惯但没有测量记录」：前者新建，后者复用且等待记录。当前体重可暂缺，不阻塞行动计划；未建立起点时不显示虚构的结果进度，首次测量按事先确认的规则建立起点。原型已增加三种创建情境切换，覆盖关联、新建和空记录分支。

如果缺少结果起点，可先保存行动计划，并提示补一次测量。在此之前结果状态为“待建立基线”，不能编造进度或完成日期。

### 3.2 预览一份可以直接启用的计划

确认页按用户意图呈现：

1. **我要达到什么**：主要结果、期限、成功标准与数据来源。
2. **我准备怎么做**：周频运动、早睡等少量行动。
3. **我要控制什么**：奶茶杯数上限、分类金额预算等可选限制。
4. **什么时候一起回顾**：首个复盘日期及哪些变化需要注意。

每一项标明「新建 / 关联现有 / 修改现有」，允许删掉不想执行的建议。已有体重习惯优先复用；已有预算展示原额度和拟修改额度，不静默覆盖。

用户一次确认后，创建或关联选中的对象并绑定数据来源。保存失败不能留下半套计划；重试不能重复创建。提醒仅在保存成功后登记。

### 3.3 在原模块完成日常行动

用户仍在习惯里打卡、任务里完成事项、财务里记账。目标直接读取这些记录，不要求每天再回来填一遍。相关事项显示来源目标，便于理解用途和返回。

目标页可以提供快捷记录入口，但最终写入同一个原始记录源。记录的补录、纠错、删除和同步，都应反映到目标当前结果。

### 3.4 目标页回答三个问题

- **结果变了吗**：当前值、阶段变化、目标值、最后记录日期。
- **行动跟上了吗**：本周运动次数、按约定口径的早睡记录、可确认的执行缺口。
- **限制守住了吗**：当期消费预算、杯数限制；每项显示自身周期。

首页摘要突出一个有依据的结论与一个下一步。来源、范围、记录明细可展开查看。结果、行动、限制分别显示，不强行合成一个百分比。

### 3.5 定期复盘并让调整生效

以周复盘作为第一版建议节奏，周期由目标类型与用户选择确定。计算层先产出事实，AI 再解释和提出少量调整。

建议采用以下判断矩阵：

| 行动情况 | 结果情况 | 产品反馈 |
|---|---|---|
| 按计划执行 | 按约定方向变化 | 继续当前方案 |
| 未按计划执行 | 变化较慢或暂无改善 | 优先检查计划是否过重、安排是否可行 |
| 按计划执行 | 充分观测下未见预期变化 | 提示重新审视方案假设，不能简单要求加码 |
| 任意 | 关键结果记录缺失或过旧 | 说明能判断行动、暂时无法判断结果 |

一次异常测量不直接判失败。比较窗口、最低观测要求、数据有效期、允许偏差按指标定义；健康结果不套用从起点到现在的简单线性外推作确定承诺。

复盘建议应形成可确认的差异预览，例如运动频率改变、替换行动或调整期限。确认后更新相应模块并留存版本；不能只给一段文字。未采纳时不改现有计划。

## 4. 需要补齐的六项产品能力

| 能力 | 第一版要补什么 | 不补的用户后果 |
|---|---|---|
| 结构化成功标准 | 主要指标、起点及日期、目标方向、期限、完成规则；支持手动确认类目标 | AI 写了“减肥成功”，系统仍不知道怎么判断 |
| 带作用的关联 | 区分结果来源、行动、约束；配置筛选范围和统计周期 | 所有记录混在一起，打卡多就被当作目标接近完成 |
| 跨模块计划确认与保存 | 新建/复用/修改预览、草案内指标绑定、预算接入、一次保存、重试去重 | 用户仍需自己补配置，或得到重复对象和半套计划 |
| 统一事实与统计口径 | 测量取最新/趋势、计数求和、消费按预算规则；区分未知与明确零 | 体重相加、交易笔数算杯数、没记录当没消费 |
| 目标状态评估 | 结果、行动、约束、数据充分程度分别判断 | “按期可完成”变成缺乏依据的承诺 |
| 复盘与计划调整 | 周期复盘、证据化建议、差异确认、执行更新、版本历史 | 创建后无人维护，AI 建议无法影响日常行动 |

不需要先建设一个支持任意模块、任意关系的复杂系统。先把上述语义和读写边界立住，再逐步扩大数据源。

## 6. 实施顺序

### 第一阶段：一条可实际使用的闭环

用减肥作为首个验证场景，支持一个主要体重指标、周频运动习惯、可选早睡习惯、可选奶茶杯数限制、可选分类金额预算。

交付范围必须覆盖：共创澄清 → 计划预览 → 新建或复用 → 绑定结果源 → 原模块记录 → 目标展示结果/行动/约束 → 周复盘 → 用户确认一项调整并写回。

目标类型和语义保持通用；第一阶段限定场景是为了验证体验与判断可信度，不把“减肥”写成全局特例。基础规则完成后，用一个非健康目标检查模型能否复用。

### 第二阶段：减少执行负担

按用户反馈补具体时间安排、任务完成与习惯记录联动、授权健康观测、已有目标计划更新，以及多个目标共享同一记录源。依据是否减少重复设置和重复记录决定优先级。

### 第三阶段：有证据的个性化

在已有多期记录和真实反馈后，依据用户执行阻力与历史选择提出适量调整。先证明用户会采纳且能执行，再投入更复杂的主动推荐和跨域关系分析。

## 7. 边界与验收

- 不要求每个目标可数值化。阅读、职业等可以用里程碑和用户确认成果；同样分清行动与成果。
- 暂停目标停止目标专属提醒，保留历史；已有共享习惯和预算继续依其原设置运行。删除目标不连带删除原始生活记录。
- 解绑、归档或删除指标源时说明“来源不可用”，保留目标与计划历史，不把进度清零伪装成退步。
- 结果达到阈值与目标完成状态分开；根据事先确认的完成规则判断候选达成，再由用户确认收尾。预算达标不替代结果达标。
- 结果测量缺失、行为未记录、明确零次、消费记录为空分别表达。记账不完整时，预算显示“已记录支出”，不宣称覆盖全部真实消费。
- 同期变化只描述同期发生，不能据此断言早睡或某项消费导致体重变化。
- 修改共享预算需明确影响其他目标；撤销计划不撤销已经发生的交易，历史复盘保留当时的计划规则。
- 不重复创建对象，不静默覆盖预算，不意外转移旧目标归属；补记、退款、删改、跨周期、暂停、双设备同步均需专项验收。
- 实施涉及后端共创协议/Prompt 时，iOS 后备与后端同步、升级版本并发版核验；本地提交或 push 不代表生产生效。

## 8. 哪些证据决定继续投入

优先观察真实行为：用户能否完成计划确认；是否在后续数周继续从原模块记录；是否回来查看或参与复盘；是否采纳并执行调整；是否减少重复操作；能否理解“行动达标但结果仍待观察”。

如果用户创建后持续执行并愿意复盘，继续扩大场景。如果用户执行但不看目标，先缩短目标摘要与复盘入口。如果用户认为计划过重，先减少默认行动和记录要求。如果确认后仍不执行也不回顾，缩小为共创与轻量跟踪，暂缓复杂自动优化。

这些是待验证的产品假设；本轮没有真实用户样本，不能给出提升比例或证明目标达成率会提高。
