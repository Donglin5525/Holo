## Phase 1：稳定路由与失败语义（2026-09-10 完成，后端+iOS）

### 后端（已本地完成，⚠️需发版才线上生效）

1. `src/intentResponseStabilizer.js` 新增「事件准备规划」确定性分支：
   - 只认语义结构组合（FUTURE_EVENT_PATTERN 未来事件信号 ∧ PLANNING_REQUEST_PATTERN
     准备/规划类请求），**无目的地/领域词表**（遵守方案 §5.4 禁令）；
   - 单项写操作双重拦截（既有 EXECUTION_PATTERN + 新 PLANNING_BLOCK_PATTERN
     「创建/新建/添加…任务|待办|提醒|日程」）；
   - 规划分支放在 OWN_EXTERNAL/第三方排除之前：「我的项目上线前」「孩子考前」这类
     用户为执行主体的准备是正例；规划分支不要求自我指涉（录屏原句无「我」字）。
   - 实测修正：「下个月」需独立词条（`下[周月天年]` 匹配不到中间的「个」）。
2. 所有确定性路由返回 `routeSource`/`routeReasonCode`（planning=EVENT_PREPARATION_PLAN，
   query=SELF_RECENT_STATUS_QUERY）；Swift 端 JSON 解码天然忽略未知字段，旧 iOS 向后兼容。

### iOS

1. `ConversationCoordinator` 规划分流两处 `try?` 全部移除，改类型化 do/catch：
   - `PlannerError.gateClosed`（能力未开启）→ 按既有产品规则降级普通聊天（保持原行为）；
   - 其余失败 → 新 `ContextPlanningFailure`（6 个稳定错误码 + 明确文案 + retryable），
     显式降级定稿，**绝不静默滑入普通流式回答**。
2. `ConversationProcessResult` 增 `contextPlanningFailure` 字段（默认 nil，全部旧调用点兼容）。
3. `ChatViewModel` 在规划成功分支后接住失败分支：同一占位消息定稿为失败交代文案
   （「这条回答不是个性化方案」+ 重试指引），早于所有后续分流，杜绝伪装。
4. 「一次请求只生成一个 assistant 占位消息」不变量：文本路径结构上本就满足
   （sendMessage 先建唯一占位，规划成功/失败都在同一消息上收尾），已核验，无需改动。

### 实施中发现并绕开的既有缺陷（非本轮造成，建议挂 QA 第 10 轮）

1. **`PersonalContextIntegrationTests.swift` 从未挂进 HoloTests target**（pbxproj 0 次出现）：
   该包装文件桥接的 8 个 standalone 套件源文件本身也不在 target 里，挂上即编译失败
   （文件头注释已知此事，明确推迟到 QA-10 收口）。本轮曾尝试挂载，撞到符号缺失后按
   其注释纪律回滚（pbxproj 四处锚点已还原，文件还原到 HEAD）。后果：test_001–008
   只能靠 `scripts/run-personal-context-standalone.sh` 手动跑，XCTest 全量不含它们。
2. **既有失败用例**：`ChatCardDataTests.testUnmatchedFinanceConfirmationDoesNotShowUnableToRecognizeWarning`
   在不含本轮改动的 HEAD 状态同样失败（已用 git stash 对照实验证明）。根因：断言硬编码
   简体「待分类」，而 `FinancePendingCategory.currentName` 在单测宿主里走「当前语言就近
   解析」（宿主无固化种子语言键 + xcstrings 源语言不生成 lproj 的已知坑族）。
   与本轮改动无关，未修。
