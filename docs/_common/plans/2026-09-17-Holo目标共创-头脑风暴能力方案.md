# Holo 目标共创：把头脑风暴能力融入目标系统

> 状态：产品与实施方案，尚未开发、构建或上线。基于 2026-09-17 工作区源码；工作区已有大量其他未提交改动，本方案不改动它们。

## 1. 产品结论

需求合理，而且补的是当前目标功能的关键缺口。现有系统擅长保存目标、关联任务和习惯、展示进度；但在创建前，Holo 尚不能稳定帮助用户判断“真正想达成什么、哪条路径适合自己、这个计划为什么可行”。直接增加更多任务或更长的回答，不会解决这个问题。

建议将 AI 入口升级为**「一起想清楚目标」**：先探索和收敛，再制定行动；用户仍可用「手动创建」快速记下明确的目标。它是现有 Goal 的创建和调整流程，不另造一个与目标脱节的聊天产品。

用户得到的变化：输入“我想提升英语”后，Holo 不急着列学习任务；它先弄清用途、当前基础和可投入时间，提出有取舍的路径。用户选定后得到可核对的成功标准、第一步和复盘节点，确认后才写入目标与行动。

## 2. 现状与根因

| 当前已具备 | 当前缺口及证据 |
| --- | --- |
| 「我的目标」可手建、AI 规划；Goal 有期望结果、动机、截止时间，支持任务/习惯关联与进度。 | `GoalPlanningSession.defaultMaxTurns = 3`，`GoalPlanningPromptBuilder` 按第一、二、三轮固定追问，再要求精简模式产出 2–4 个任务、1–2 个习惯。它优化的是“尽快填满草案”，不是“先选对目标与路线”。 |
| AI 草案可确认后保存，目标详情可继续管理。 | `GoalDraftReviewView` 当前主要编辑标题、说明、领域并勾选任务/习惯；草案中的 `desiredOutcome`、`motivation`、`deadlineText`、`missingInfoWarnings` 没有在该确认页呈现和核对。 |
| 规划入口在聊天中，草案卡片可打开确认页。 | `GoalPlanningCoordinator` 只有追问或 `DRAFT_READY` 两种结果，没有“问题定义 → 备选路径 → 选择理由 → 方案校验”的结构；`activeGoalPlanningSession` 只在 `ChatViewModel` 内存中持有，退出后难以可靠续接。 |
| AI 可通过已有上下文获得部分个人信息，目标自身有 `allowAIContext` 开关。 | 规划 Prompt 仅显式放入日期和本次回答，没有列出可追溯的相关事实、推断和未知项；“了解用户”是否实际改变方案，当前无法从草案判断。 |

这些是源码能力判断，不能等同于对线上用户行为或模型效果的实测结论。

## 3. 从 Superpower 迁移什么

参考本机保留的 `brainstorming` skill。迁移其**思考方法**，不照搬开发工作流、文件提交和逐节审批：

| 头脑风暴方法 | Holo 中的用户体验 |
| --- | --- |
| 先了解背景与真实意图 | 用用户已说过且获授权的信息形成“我理解的是……”，标明待确认的假设。 |
| 一次问一个关键问题 | 只追问会改变目标定义或路径选择的缺口；用户可跳过、纠正或直接看初稿。 |
| 给 2–3 种路线和取舍 | 对复杂或有分歧的目标给不同投入、速度、风险的路径及推荐理由；路径明显时直接说明推荐，不机械凑三个。 |
| 分段确认、允许回退 | 先确认目标定义，再确认路径，最后审行动；任何一步可修改，不必重新从头聊。 |
| 写下设计与执行计划 | 生成可保存的目标决策摘要、成功标准、阶段节点和第一步，之后能回看与重规划。 |

目标规划涉及个人生活，Holo 的追问应适度：不把用户当项目需求方盘问，也不把“跳过”当失败。

## 4. 方案选择

| 方案 | 效果 | 代价与问题 |
| --- | --- | --- |
| A. 只加强当前 Prompt | 最快改善文案和问题质量。 | 固定三轮、直接生成任务、确认页信息缺失和会话易丢仍在；体验很难稳定。 |
| **B. 目标共创流程（推荐）** | 把澄清、路径比较、用户选择、行动生成和保存连成同一条可恢复的流程；复用 Goal、任务、习惯。 | 需要补结构化会话、确认页和评测，投入中等。 |
| C. 完全交给通用 Agent 自由对话 | 灵活，理论上可处理任何人生议题。 | 过程不稳定、成本难控，确认与写入边界难以保证；不适合直接作为目标默认入口。 |

选择 B。保留通用聊天的自然语言外观，但关键决策由明确的流程和数据契约承接。

## 5. 用户流程

### 5.1 创建新目标

1. **入口**：「我的目标」的新建菜单显示「一起想清楚」和「手动创建」；HoloAI 中的「规划目标」进入同一流程。用户可输入一句模糊愿望，也可粘贴已有想法。
2. **理解**：Holo 用一句话复述目标，并提一个最有价值的问题。先判断结果、动机、现状、时间/资源、硬约束中哪些已知；已知的不重问。用户可选“先给我一个初稿”。
3. **探索**：当路径有实质差异时，展示 2–3 个可选方向，每个写明适用条件、投入和主要代价；推荐其中一个并解释原因。用户可选、组合、改写，或指出遗漏。
4. **收敛**：展示“我理解的目标”：期望结果、如何判断达成、时间边界、采用的路径、关键假设/未知。用户改完后才进入行动草案。
5. **行动**：按所选路径生成第一步、阶段节点和必要的任务/习惯。任务与习惯数量由目标决定，允许 0 个习惯；第一步最好能在 48 小时内开始。每个行动应能解释它服务于哪个节点。
6. **确认并保存**：用户在一页中核对成功标准、路径、时间、未知项、任务/习惯及 AI 可见性。只有点击确认才创建 Goal 和所选行动；失败显示原因并保留草案供重试。

例子：用户说“想把英语练好”。若用途是工作会议、每天只能投入 20 分钟，Holo 可建议“先练会议听说”和“先补词汇语法”两条路线，说明前者更快贴近使用场景但基础漏洞需边用边补；用户选前者后，才制定一周内能开始的练习与一个可观察的阶段结果。若用途或基础未知，明确写成待确认假设，不假装已经了解。

### 5.2 调整已有目标

目标详情增加「一起调整计划」。Holo 先展示当前目标、真实进度及可用的关联行动，再问“结果变了、时间不够、方法无效，还是只是暂停？”输出修改前后差异。改 Goal 核心字段、停用旧行动、创建新行动，均先由用户逐项确认。旧进度、记录和用户手建内容保留；AI 不静默删除。

### 5.3 中断与轻量使用

用户可以跳过问题、退出后继续、放弃草案；未确认草案不影响现有目标。问题不设硬性三轮：只要重要不确定性已经足够低就收敛；超过有限追问仍不清楚时给带假设的初稿，交给用户决定。聊天额度不足或网络失败时保留本地草案并提供手动创建入口，不让已回答的信息消失。

## 6. 产品与数据契约

- **会话状态**：`understanding → exploring → choosing → reviewing → saved / abandoned`。持久保存会话 ID、关联 Goal ID（新建为空）、阶段、用户原话与确认后的事实、假设、路径备选、所选路径、草案版本、更新时间。聊天消息可呈现对话，但不能作为唯一状态来源。
- **事实来源**：每项影响建议的个人情况区分“用户本次明确说的”“经授权读取且仍有效的记录”“AI 推断”“未知”。推断须可纠正；敏感信息遵守现有 AI 上下文、访问与遗忘规则。用户关闭某目标的 `allowAIContext`，不能在别的目标共创中偷用该目标资料。
- **输出结构**：目标定义（结果、成功证据、期限、约束）、路径选项（适用条件/代价/理由）、所选路径、假设、阶段节点、第一步、可选任务/习惯。对用户可读，对程序可校验；模型输出只是候选，客户端校验日期、引用、重复项、数量和关联对象。
- **保存规则**：目标的结果、动机、期限与最终选择必须在确认页可见并可改；先形成草案，保存前重查目标/任务/习惯是否仍存在以及授权是否仍有效。新建与修改分开处理，重复点击或网络重试不能重复建 Goal/任务/习惯。失败不能出现“看似保存成功”的提示。
- **可回看**：目标详情展示用户选定路径、成功标准、下次复盘点和关键假设；重规划生成新版本与变更摘要，保留旧版本供解释，不改写历史事实。避免把长对话原文塞进 Goal 主页。

## 7. 实施边界与分期

### P0：建立可信的目标共创闭环

1. 在当前 `GoalPlanningCoordinator` / `GoalPlanningPromptBuilder` 上拆出“理解、探索、收敛、行动”状态与结构化输出校验，移除固定轮次话术和固定任务/习惯配额；保持现有手动创建链路。
2. 扩充 `GoalPlanningSession` 的持久化与恢复；聊天页只负责呈现和输入，避免继续把完整流程状态堆在 `ChatViewModel`。
3. 为路径选择、目标定义和最终草案提供轻量卡片；改造 `GoalDraftReviewView`，显式显示并可编辑期望结果、动机、截止时间、未知项。复杂视图拆独立 `View` 类型，遵守项目的 ChatView 真机入口门禁。
4. 增加“目标决策摘要/版本”存储，保存路径、成功标准、假设及阶段节点；写入动作仍复用 `GoalRepository`、`TodoRepository`、`HabitRepository`。
5. 先覆盖新目标创建和中断恢复；用户可从已有手动目标开启共创，但 P0 只生成修改建议，不自动覆盖旧字段或动作。

### P1：已有目标重规划与复盘

1. 目标详情展示决策摘要、第一步、阶段节点与调整入口。
2. 支持已有目标修改前后差异、逐项确认、旧任务处理和版本回看。
3. 在用户主动查看或约定复盘时，用真实进度询问是否调整；不因短期没打卡就自动改目标或频繁提醒。

### P2：个人情境增强与质量优化

按相关性和用户授权召回可能改变方案的既有事实，展示“这条信息如何影响推荐”；优先验证真实收益，再扩大召回范围。通用个人情境方案已规划的能力需要以当时实际代码和权限状态核对，不能当成现成功能直接依赖。

**技术落点**：现有 `GoalModels.swift`、`GoalPlanningCoordinator.swift`、`GoalPlanningPromptBuilder.swift`、`GoalDraftReviewView.swift`、`GoalRepository.swift`、`GoalDetailView.swift`、`ChatViewModel.swift`。若新增或修改后端 Prompt/意图契约，必须同步 iOS 与 `HoloBackend` 的版本和校验，并完成后端部署及生产验证；仅本地改动或推送不会上线。

## 8. 验收与发布门槛

1. **用户价值**：用“学英语”“准备考试”“减脂”“存钱”“长期方向不清”及已有目标受阻等跨领域样本验证。至少比较旧流程与新流程：用户能否说清成功标准、是否看懂路线取舍、是否愿意确认第一步；不把“生成了更多任务”当成功。
2. **质量**：冻结独立留出场景，检查已知事实是否真的改变路径；刻意加入冲突、资料过期、时间不足、用户纠正和目标不适合立刻拆任务的案例。无来源事实不得冒充用户情况；关键约束冲突应先提示或重设目标。
3. **可靠性**：覆盖跳过/修改答案、中断恢复、额度不足、网络失败、重复保存、跨设备旧数据、授权关闭和遗忘后继续；旧 Goal 必须兼容。确认前没有业务写入，确认后实际 Goal/任务/习惯与页面回执一致。
4. **成本**：记录每次成功保存所用模型请求和 token；优先一轮解决一个关键问题，不为了凑轮数消耗额度。新流程的额度提示应在开始前说明，不能回答到一半才发现无法产出草案。
5. **工程发布**：先做结构化契约和状态测试，再做 iOS 模拟器端到端；涉及 HoloAI 聊天入口和真机装包时，按 `HOLO/AGENTS.md` 完成五大入口冒烟及真机 AI 入口门禁。后端有改动时，另做版本、真实请求与生产端点验收；本方案文档不代表功能已上线。

## 9. 范围判断

本轮只增强个人目标的“想清楚 → 选路径 → 开始行动”，不做团队 OKR、通用项目管理、自动执行大量跨模块操作，也不强迫每个目标有习惯。默认采用渐进追问与用户确认；如果用户已经有清晰目标，允许直接生成可编辑初稿。
