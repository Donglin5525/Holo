## 一、交付总览

连续追问功能让用户可以在一份已完成的分析结果上继续提问，系统自动建立父子血统关系、继承上下文、判断追问意图，并把追问结果正确地展示出来。本次交付覆盖 Phase 0–5 的全部代码层，Phase 6（真机/灰度）需要东林发版验证。

| Phase | 内容 | 状态 |
|-------|------|------|
| Phase 0+1 | 显式追问闭环（血统模型 + UI + child Job 链路） | ✅ |
| Phase 2 | 上下文继承基础设施（Snapshot + Guard + 事务闸门 + hash v2） | ✅ |
| Phase 3 | relation 路由 + Follow-up Router + 结果转待办 | ✅ |
| Phase 4 | 自然相邻追问（隐式解析 + 确认窗口 + circuit breaker） | ✅ |
| Phase 5 | 展示与详情（追问角标 + 变化标签 + expired reanalyze） | ✅ |
| Phase 6 | 真机/灰度门禁 | ⏳ 待东林验证 |

## 四、后端发版同步

**本次代码改动不需要后端发版。**

理由：
1. 追问血统（lineage）、上下文快照、关系路由全部是客户端本地逻辑，不涉及后端接口
2. child Job 的创建复用现有 Agent 执行链路（Scheduler → Runtime → 后端 LLM 调用），后端接口无变化
3. 后端已有的 `injectServerPrompt`（按 purpose 注入 system prompt）继续生效，追问 child Job 的 purpose 仍是 agent_loop，后端无需感知 lineage

## 五、Phase 6 门禁清单（需东林完成的真机/灰度验证）

以下项无法在模拟器/编译层面验证，需要真机或灰度环境确认：

### 数据兼容性
- [ ] 旧版本 App 产生的历史消息（无 lineage / agentJobID 字段）在新版本能正常展示，不崩溃
- [ ] 旧消息的 AgentDeepAnalysisCard 不展示「继续追问」按钮（缺身份字段时自动隐藏）—— 已在 `canContinueFollowUp` 保证
- [ ] 旧 checkpoint 的 inputSnapshotHash 在 v2 升级后不误判输入变化—— 已在 `inputSnapshotMatches` 按 schema 版本处理，但需真机确认恢复行为

### 功能验证
- [ ] 在一份完成的分析上点「继续追问」→ 输入框出现锚定条 → 发送 → 新结果带追问角标
- [ ] 连续追问 3 层以上，每层 lineage.depth 正确递增
- [ ] 输入「为什么步数变少」→ relation 判定为 explain
- [ ] 输入「换成今年」→ relation 判定为 changeScope
- [ ] 输入「那消费呢」（父是健康分析）→ relation 判定为 crossDomain
- [ ] 在有建议的结果上输入「按这个建议建待办」→ 出现待办确认卡
- [ ] 不点按钮直接输入「那步数呢」→ 自动隐式锚定（4 小时窗口内）
- [ ] circuit breaker：误判后 1 小时内不再自动隐式锚定

### 性能/稳定性
- [ ] 追问链深度达到 20 时正确触发 rolling root（不无限递归）
- [ ] 事务闸门 journal 文件在正常流程下不残留（Reconciler 启动时清理）
- [ ] cleanup 三开关在真实数据量下行为符合预期
