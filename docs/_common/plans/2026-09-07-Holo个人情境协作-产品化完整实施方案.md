## 1. 产品目标：用户具体能感知什么

用户不需要理解“语义记忆”“Agent”或维护个人档案。他应在原有 Holo 入口感受到三件事：

1. **少重复解释背景**：之前在想法、对话或业务记录里说过的重要情况，需要时能够被找到。
2. **建议更适合眼下的自己**：Holo 能说明某个真实情况如何改变安排；无关背景不会硬塞进回答。
3. **上次的选择能接着用**：接受、拒绝、已安排、实际完成和后续反馈有区别，下一次能够正确续接。

完整路径为“提出需求 → 读必要记录 → 给出有依据的方案 → 修改或确认 → 获得真实保存结果 → 按约定回看”。允许用户停在任何一步，只看建议也算正常使用，不以创建更多任务作为成功目标。

### 1.1 三个月范围

| 交付对象 | 本次范围 | 明确边界 |
|---|---|---|
| 理解与生成 | 聊天、今日安排、目标规划和深度分析共享必要个人情境 | 不要求先填档案；不为旅行、宠物等单独写触发词模板 |
| 受控操作 | 新增待办、调整既有待办日期/计划时段、调整预算、调整数值型好习惯目标 | 模型提出候选；程序解析目标实体；用户看过具体变更后确认 |
| 共同经历 | 本次需求、采用的操作、用户明确反馈、真实结果的可追溯记录 | 不把拒绝建议推断成人格；不编造情感或因果故事 |
| 回看 | 用户约定的应用内回看；通知需单独同意 | 不依赖 iOS 后台准时生成；不自动替用户继续改数据 |
| 入口 | 复用聊天、今日看板、记忆画廊及现有模块详情 | 不新增一个与现有功能竞争的“超级 Agent 模式” |

暂不扩展任意写工具、交易删除/转账、对外发送消息、自动执行外部事务、新模型训练、图数据库或整套 Agent 协议迁移。现有周计划仍由原 LifePlan 流程管理，本能力为它提供情境和共享执行规则，不抢建另一份目标。

### 1.2 产品验收原则

- 有背景与无背景相比，方案必须在优先级、事项、时间、约束或提问上出现合理变化，不能只多一句“结合你的情况”。
- “已保存”必须对应可打开的业务对象；“已完成”必须来自完成记录或明确用户反馈。
- 已安排的事情不再反复要求安排；已拒绝的建议在同一需求下不换个说法重推。
- 读不到资料时给出范围合适的基础回答；不说“你没有”，只说明当前未找到或未获准读取。
- 收集信息只为解决当下缺口。先完成不依赖答案的部分，一次最多突出两个关键问题。

## 2. 五个场景的完整产品规格

以下用户记录、金额和文案均为验收用虚构示例，不是当前真实用户数据或既有线上表现。示例验证通用规则，不进入 Prompt 成为固定业务模板。

### S1：今日看板——帮我把今天安排得更现实

**触发**：今日看板提供轻入口“帮我安排今天”，或用户在聊天中说“今天事情太多，帮我排一下”。入口传日期和当前可见范围，不让 UI 自行组织一套规划逻辑。

**准备数据**：读取实际未完成任务、截止时间、计划时段、关联目标及已授权的日程。没有任务时不造任务；没有日历授权时仍可基于待办给建议，不宣称已经避开所有日程冲突。未记录任务时长就不输出精确到分钟的完整时间表。

**用户先看到**：

> 今天先保留“提交材料”和“准备评审”。材料今晚截止，下午已有评审安排。整理照片可以挪到明天；另一项没有截止时间，先放回待安排。

卡片优先展示两三条建议，每项都能展开“为什么这样排”和打开原任务。日期调整独立显示“计划时间”与“截止时间”，不能把“明天再做”自动解释成延长一个硬截止时间。

**确认预览**：

| 项目 | 预览必须展示 | 操作后的结果 |
|---|---|---|
| 整理照片 | 计划：今天 → 明天；截止日期：保持原值 | 保存成功后看板按计划范围更新 |
| 提交材料 | 保留今晚截止；如改计划时段，展示具体起止时间 | 原截止时间与提醒语义不被悄悄改动 |

对于没有计划时段、只有截止日期的任务，不显示含糊的“挪到明天”。提供“设置计划时间”或明确的“修改截止日期”选择；修改后者需要用户实际选择该字段。

**异常**：确认时任务已经完成、删除、被编辑或日程发生变化，受影响项显示“安排有变化，请重新查看”，不覆盖新状态。可以保存仍有效的独立项，结果按项说明。重复任务、跨日时段和系统日历写入本期不执行，给出原模块入口。

**用户感知验收 S1-A**：无需逐条输入今天任务；建议能反映真实截止约束；确认前零写入；保存结果与看板、任务详情一致。

### S2：想法 → 对话 → 待办——出门前少漏掉真正相关的事情

**触发**：用户曾在想法中写“平时只有我照顾猫，它一直吃原来的粮”。现在在 HoloAI 说“我要离开五天，帮我列一下准备事项”。

**用户先看到**：常规准备之外，出现“确认这几天的照看安排”和“交接日常喂养方式”，并自然说明“你之前提到平时由你照顾猫，所以这里多留了一项交接”。出处可点击查看对应片段、记录日期及当前适用状态。

**纠正与续接**：用户说“朋友已经答应来喂猫”。新方案继续围绕原来离开五天的目标，移除“寻找照看人”，保留交接钥匙、日常方式等仍成立的建议；未知出发日期不会被补成今天。该表达只证明已约定照看，不代表后续五天已经喂过。

**用户操作**：可以勾选要保存的条目、改标题、选择清单、补日期，或标记“已安排”“暂不需要”。主按钮为“添加 2 项待办”，点一次完成此次已展示内容的确认，不再弹第二遍相同确认框。

**保存反馈**：显示“已添加 2 项”，每项提供“查看待办”。部分失败显示“已添加 1 项，另 1 项未保存”，只重试失败项；离开页面或重启后结果仍一致。

**用户感知验收 S2-A**：不重复讲背景；纠正能实际删改建议；不出现猫粮品牌、健康要求等无来源信息；新任务可真实打开且没有重复。

这是首期纵向交付场景。相同机制必须同时通过出差期间植物照料、搬家时设备交接、考试与家庭职责冲突等未用于调试的情境，不能仅让“猫 + 出门”演示成功。

### S3：财务 + 生活记录——看懂开销，再决定怎么调预算

**触发**：“这个月吃饭花多了，帮我看看怎么安排。”现有交易计算显示相同口径的餐饮支出较基线增加 600 元，想法提到父母来住过几天。

**用户先看到**：先展示账本事实、时间范围和明细入口，再说“父母来住可能与这段时间的餐饮增加有关，仅凭记录还不能确定”。模型不得把 600 元全部归因为父母来访，也不能用一句生活记录替代交易统计。

**选择方案**：可以保持预算并查看建议，也可查看“仅本周期提高预算”的候选；预算上调不是默认正确答案。候选金额必须来源于用户输入或清楚标明的建议计算，不能声称已经替用户调好。

**确认预览示例**：“生活账本 · 餐饮 · 2026-09-01 至 2026-10-01（不含结束日）· 本周期额度 1200 → 1800 元；下周期按长期额度 1200 元计算”。有超支结转时另外展示“本周期可用额度”的实际变化。

**实现边界**：现有 Budget 是持续周期配置，直接修改 amount 会影响后续周期。本次“仅本周期”必须有周期覆盖额度，详见第 9 节；在该能力尚未验收的版本中，不出现“仅本月生效”的保存按钮。可提供明确写着“持续调整每月额度”的现有能力，但不替换用户已经选择的临时意图。

**用户感知验收 S3-A**：能分清实际花费、可能原因、预算建议和已保存额度；只修改确认的账本/分类/周期；跨月自动恢复长期规则，无需后台任务恢复。

### S4：目标 + 习惯——把计划调整到能够持续的程度

**触发**：用户有每天英语学习 30 分钟的数值型好习惯，最近明确说“晚上太累了，总是开始不了”，希望调整安排。

**用户先看到**：结合实际记录给出“先试每天 10 分钟”等候选，说明是减轻开始难度的一种试法；不推断懒惰、疾病或固定人格。缺少记录不能说“你一直没坚持”。

**确认预览**：“英语学习 · 每日目标 30 → 10 分钟 · 从今天起生效 · 频率保持每日”。首版只改已有数值型好习惯的目标值，不联动修改健康指标、频率、提醒或关联目标总量。用户要求只周末执行时先给建议和原习惯编辑入口，不伪装已支持频率调整。

**回看约定**：保存成功后提供“7 天后在 Holo 里回看”，默认不勾选；用户确认后建立约定。系统通知另有“到时提醒我”，不与添加回看混在一起。

**七天后**：例如“上一个完整七天有 1 天记录，本次七天有 4 天记录；实际记录总时长分别为 X 和 Y”。若使用达标天数，前后分别写清 30 与 10 分钟的目标，不能把门槛降低带来的变化说成投入翻倍。允许用户反馈“更容易开始了”，这是用户反馈，不是系统因果结论。

**用户感知验收 S4-A**：修改是真的；历史日期仍按当时目标解释；回看用实际记录和明确口径；下一步继续由用户决定。

### S5：记忆画廊——能接着上次共同处理的事情往下走

**触发**：在记忆画廊看到“上次出门准备”，或下一次对话问“上次怎么安排的”。

**卡片只呈现有证据的内容**：“当时准备离开五天；你选择了交接钥匙和准备日常用品；两项待办已标记完成；你后来反馈‘这样放心多了’”。没有反馈就不生成最后一句；当前任务已删除时不再显示可用链接，保留允许留存的历史执行事实并标明状态。

**继续使用**：“这次也可以参考交接清单，照看安排还是和上次一样吗？”旧经历只作为候选依据；当前日期、对象、责任和已完成状态需要重新判断，不一键复制全部旧任务。

**用户控制**：“这次不参考”“不要再提这次经历”“删除这条经历”有不同范围，详见第 11 节。删除经历不自动删除原想法、对话或已经创建的待办。

**用户感知验收 S5-A**：能找回真实的选择与结果；内容与源记录一致；新方案受新情况约束；没有“我们一起成长了”一类虚构叙事。

## 3. 页面、交互与文案的统一规则

### 3.1 沿用三个主入口

| 位置 | 本次改动 | 进入后的行为 |
|---|---|---|
| HoloAI 聊天 | 复用 ContextPlanChatCard，支持来源、续接、逐项确认和结果 | 用户问题仍是入口，不要求先选择专业场景 |
| 今日看板 | 增加轻量的今日安排入口；到期且已约定时显示一张回看提示 | 进入同一聊天运行或回看详情；不每次打开都生成新方案 |
| 记忆画廊 | 增加“共同处理的事”条目，复用详情导航 | 查看采用内容、结果与反馈，必要时继续原需求 |

目标入口继续区分“长期目标/周计划”和“一次准备”。财务分析继续使用现有证据卡，不把所有查询都转换成一张计划卡。普通记账、计数查询保持现有短路径。

### 3.2 方案卡信息顺序

首屏：直接回答 → 最重要的 2–3 条建议 → 可执行条目 → 主要按钮。依据、覆盖说明、更多条目按需展开。整份草案最多 12 项，建议用户第一批选择不超过 5 项；超过时先分组，不能无限生成任务。

- 有影响的个人依据放在对应建议下，显示“因为……，所以这里……”；不暴露内部评分、向量、模型思考过程。
- 查看依据展示必要原文片段和时间，点击打开现有详情。不要只有“来自记忆”徽章却看不到出处。
- 每个新任务默认未选中；用户可“一键选择建议项”并在同一页面检查。既有数据变更必须逐项显示前后值。按钮数量来自真实选择，不能显示固定“全部执行”。
- 未确定日期显示“未设置”，可直接无日期保存普通准备任务。必须依赖出发日期的提醒先不创建提醒；日期控件不能以默认今天制造已确认的错觉。
- “已安排”表示用户声明已有安排，“暂不需要”表示本次拒绝，都不等于业务对象已经完成。撤回这两个选择后重新评估，不永久删除个人事实。
- 用户编辑过的标题、选择和日期在重生成时优先保留；若与新条件冲突则提示差异，不能静默覆盖编辑。

### 3.3 可见状态与可操作性

| 状态 | 文案示例 | 可用行为 |
|---|---|---|
| 查找/生成中 | “正在结合相关记录整理” | 可取消；只有确实读取记录时用此文案 |
| 需要关键补充 | “出发日期会影响交接时间，其他准备先列好了” | 回答问题，或保留无日期事项 |
| 草案可用 | “建议先做这 3 项” | 改内容、看来源、选中并确认 |
| 正在保存 | “正在添加 2 项” | 本次确认按钮禁用；可离开页面 |
| 部分完成 | “已添加 1 项，另 1 项未保存” | 查看成功项；只重试失败项 |
| 来源/对象变化 | “相关记录有更新，请重新查看这项” | 刷新受影响项；独立有效项仍可确认 |
| 结果待核对 | “正在核对刚才是否已保存” | 先核对，不重复执行；无法确定时进入原对象 |
| 取消生成 | “已停止整理” | 保留此前有效草案，不追加迟到结果 |

保存已经开始后，“取消”只停止尚未提交的项，已提交项保留并给出结果；不能显示整批撤销。无网络时仍可查看本地来源和有效草案、保存已经验证且权限仍有效的本地动作；需要新模型生成时说明联网要求。

### 3.4 可访问性和布局验收

iPhone/iPad 复用自适应卡片，较大字号不截断金额、日期和前后值；VoiceOver 能读出来源、选择状态和保存结果；用文案配合颜色区分失败。提供稳定 accessibilityIdentifier 供 UI 测试使用，不把本地化文案当作唯一测试定位方式。

| B02 | followUp 可能把目标替换成一句补充；原 run 丢失时直接按补充重开 | 保存原目标、增量约束和已选事项；缺上下文时不得猜原目标；P0 |

| B09 | 预算 amount 是持续周期值；习惯统计多处读取当前目标 | 单周期预算覆盖与按日期取历史目标；P1A/P1B |
| B10 | OutcomeReviewStore 有生成/待回看接口，未见完整业务调度闭环 | 接约定、到期读取、展示去重与反馈；P2A |

当前工程已经存在 HoloTests、HoloUITests target 和 standalone 桥接，不能沿用旧记忆中“没有 test target”的结论。既有测试文件不自动等于执行通过，按第 15 节实际跑并保留失败退出码与断言数量。

## 5. 总体接线：复用已有系统，贯通一条数据流

~~~mermaid
flowchart TD
    U[聊天 / 今日看板 / 目标入口] --> R[现有意图路由与请求框架]
    R --> C[PersonalContext 检索与当前业务状态]
    M[已有记忆 / 想法 / 对话] --> C
    D[任务 / 预算 / 习惯 / 日程] --> C
    C --> P[规划协调器 / 原 Agent 证据链]
    P --> V[来源与动作校验]
    V --> S[持久化运行与草案]
    S --> UI[统一卡片：依据、修改、确认]
    UI --> E[按项执行器与操作日志]
    E --> REP[现有业务 Repository]
    REP --> ACK[真实对象与保存回执]
    ACK --> S
    ACK --> EP[已有记忆体系中的经历引用]
    EP --> RV[约定回看与记忆画廊]
    RV --> R
~~~

### 5.1 各层唯一职责

- 意图路由决定走普通操作、只读分析、个人规划还是既有目标流程。个人规划不得因为在 batch 中排第二而漏掉写入前的保护。
- HoloPlanningRequestFrame 保存本轮目标与约束；HoloContextRetrievalService 提供允许使用的候选；来源读取和控制统一走现有 AccessPolicy。
- HoloContextPlanningCoordinator 生成可验证草案，原 Agent 仍负责分析任务的 Evidence Ledger 和 Verifier。不能把一段私人背景字符串直接注入后跳过来源校验。
- HoloPlanningRunStore 是本机规划运行、草案、决定和操作日志的单写者；ChatMessage 仅保存关联与兼容展示投影。UI 不自行判断是否已保存。
- HoloContextActionExecutor 校验用户确认内容并调用现有 Repository。模型输出不能直接构造任意 Repository 参数或调用任意工具。
- HoloMemoryRecord 保存可供后续理解使用的经历引用，业务状态仍从原任务、预算、习惯读取，不能复制一份“完成状态”长期当成最新事实。

### 5.2 路由优先级

1. 精确单动作如“午饭 25”、普通计数查询，继续原流程，不额外读取个人资料。
2. 用户明确进入既有周计划/长期目标时，保持原计划实体和确认流程，增加个人情境输入；不得同时创建新 contextual plan 的副本。
3. 明确需要建议、准备、权衡、调整的请求进入个人规划。意图模型可返回轻量 contextRequest；已有结果足够时不重复调用框架模型。
4. 混合查询与执行的请求，必须在任何业务写入之前统一识别。能明确映射到本文支持动作的，先读取并给完整预览；不能明确映射的，保留现有澄清边界。不允许“先执行半句，再提示另半句不支持”。
5. 深度分析内部需要个人情境时复用相同检索和引用；结果仍由原 job/runID 持有消息，聊天流程不抢写 Agent 的结果。

同一用户请求只选一条主要生成路径。生成结果不重新送回普通意图模型再次执行，避免重复计费和意外写入。

## 6. 从记录到真正改变方案

### 6.1 输入准备与开放语义检索

复用基础方案的萃取与索引：从普通生活叙事中提取责任、条件、规则、时间、资源、偏好等开放命题，保留主体和原文支持关系。不得以“我认为/我觉得”等观点词决定是否能形成个人情境，也不要求用户先选分类。

读取顺序：

1. 合并本轮原话、原目标、已确认约束和当前会话明确来源，形成 frame。旧消息只取必要内容，原文作为数据隔离，不执行其中的指令。
2. 在授权集合内取语义、对象、时间重叠、条件依赖和当前会话候选，去重后最多 40 条；最终采用最多 8 条，允许 0 条。
3. 对会改变行动的“已完成/已安排/不再负责”等状态读取当前业务对象或最新明确表达。完成了本月事项，不推出下个月也已完成。
4. 有真正会改变结果的缺口才补查原文。最多一轮、四个片段、合计 8000 UTF-16 字符；“召回少于两条”本身不是补查理由。
5. 语义服务不可用时走现有对象/时间/词法降级，明确记录 degraded；不能用降级结果通过通用语义召回验收。

旧记忆中已满足 advice 权限和来源政策的偏好、约束可以参与，不得只查询 personalContext 非空的新记录；也不得为补覆盖绕过旧 query service 的权限和 relevance 限制。

### 6.2 每条个人依据都必须能解释影响

草案加入 contextEffects。每个 effect 至少说明：采用了哪个来源、影响哪个条目/成功条件、改变了什么、是明确事实还是有限推断、适用条件是什么。

示意：“来源 c1 表明平时由用户照看 → 离开期间存在交接需要 → 增加交接事项”。不保存或展示模型内部思维链，只保存能被来源核查的简短理由。

通用建议可以没有个人来源，但必须标为一般建议；“我知道你……”必须有实际被采用的合法来源。模型给出未知来源 ID、错主体、错时间、与当前完成状态冲突时，移除相关事实和受影响动作或重新生成，不能只把引用徽章隐藏后保留原结论。

### 6.3 追问、纠正和过时信息

- runID 标识同一件事，requestRevision 标识用户新一轮要求，draftRevision 标识已验证草案版本。用户每次真实续问推进 requestRevision；网络重试不推进。
- 原目标和新的约束增量合并，例如“朋友已答应”写进 existingArrangements，不取代“离开五天”的目标。
- 本轮明确纠正优先影响本次方案；它不自动成为永久事实。只有来源政策与学习开关允许时才进入长期情境，保留支持来源。
- 被否定的旧来源可以作为历史记录，但在当前范围内不得继续当正向依据；未来另一时段重新判断适用性。
- 找不到原 run 时，先用消息关联定位可恢复的目标与已确认决定；恢复失败则显示“这条方案暂时无法续接”，让用户从原问题重新整理。不能仅凭“已经安排了”生成新目标。
- 已保存条目重生成后仍保持稳定 logicalItemID。标题改了不代表新任务；需要改已保存对象时生成显式变更候选。本期不支持该字段修改时，提供详情入口，不创建替代副本。

### 6.4 萃取覆盖与原文变化

新建、编辑、批量导入、删除、回收站恢复及 CloudKit 同步变化统一进入原有来源修订/失效机制。队列按源 ID 与修订去重，分批补建，不能阻塞输入。来源删除先使引用不可用，再清缓存；恢复原文不撤销用户遗忘。

读取前、模型请求前、模型返回后、呈现来源时和保存前，重新核对允许使用的来源版本。远端更新不只靠 updatedAt 时间游标发现，保留源 ID 对账和漏事件补偿。更多萃取细则沿用基础方案，不再建一个与想法整理平行的分类系统。

## 7. 类型化契约与持久化

### 7.1 在已有模型上增量扩展

以下是必需语义，不要求机械地按每一行建立新类型；复用已有 Codable 类型和命名，增加 schemaVersion 与兼容解码。

| 对象 | 必需字段/增量 | 约束 |
|---|---|---|
| HoloPlanningRequestFrame | 原 goal、当前 utterance、成功条件、范围、已有安排、未知、检索方向、referenceTime、timeZoneID | 相对时间只解析一次；增量合并保留用户明确值 |
| HoloPlanningRun | runID、originDeviceID、parentMessageID、request/draftRevision、state、frame、accessGuard、budgetByRevision | 权限和预算来自实际请求；旧回调不能推进新状态 |
| HoloContextPlanDraft | schemaVersion、answerText、items、usedContextRefs、contextEffects、unknowns、dependencies、coverage | 无个人依据时也可交付一般方案 |
| ContextSourceRef | sourceKind/ID、record/versionID、sourceRevision、subject、有效时间、角色、适用状态、locator | 来源正文按需读取；不得存整篇原文快照替代权限读取 |
| PlanItem | itemID、logicalItemID、kind、title、reason、sourceRefs、preconditions、日期意图、用户编辑字段 | 模型不能自行声明已经保存；未知 kind 只读展示 |
| UserDecision | runID、logicalItemID、decisionVersion、selected/arranged/declined、用户改动、时间与范围 | 本次决定和永久事实分离；只有执行成功产生 saved |
| ActionProposal | operationID、actionType、targetRef、expectedTargetVersion、before/after、来源 guard、依赖、确认内容 digest | 金额用 Decimal 字符串；日期有精度和时区；实体由代码解析 |
| ActionReceipt | operationID、状态、实体类型/ID、appliedAt、before/after digest、业务版本、失败原因码、notificationState | 只有真实落库后写 succeeded；当前状态变化单独展示 |
| ReviewAgreement | agreementID、episode/runID、动作引用、观测窗口、metric 定义、dueAt、notificationConsent、状态 | 保存成功且用户接受后建立；无成功动作不创建假回看 |

所有 ID 为程序生成或从真实数据获得。模型可引用候选 ID，不能凭空创造目标实体 ID。用于摘要和日志的哈希不替代权限判断，不把原文做成容易反查的短词哈希上传。

### 7.2 运行存储的默认实现

新增 HoloPlanningRunStore actor，采用本机 Application Support 下受系统文件保护的版本化文件存储，按 run 分文件原子替换。每次关键状态推进先成功持久化，再更新 UI。维护轻量索引，启动时可重建；写盘失败即阻止依赖该日志的操作。

存储：frame、已验证草案、用户决定、来源引用、调用预算、操作日志和回执。未筛选候选原文、模型内部推理、整个个人档案不写入 checkpoint。草案内仍可能含个人信息，因此同样受保护、清理和禁用政策约束。

ChatMessage 保存 runID、草案版本与兼容 answerText 投影，结构化内容以 run store 为准。投影更新失败不推翻已经发生的业务保存；页面重新打开时以 run store 重建。禁止形成 run store 和聊天 JSON 各自推进版本的双真相源。

运行草案默认保留 90 天；超过期限移除可重新生成的中间版本。未核对操作不得按数量截断；成功操作保留最小回执，直到关联经历删除或用户清理时按政策处理。来源遗忘后的内容失效优先于保留期。退出账号/清空相关 AI 数据按账号分区清理，防止下一账号读取上一账号运行。

### 7.3 旧数据兼容与迁移

- 新字段用 decodeIfPresent 和明确默认值；未知 schemaVersion 只读展示兼容文本，不允许保存动作。
- 旧 UserDefaults run 数据单次导入新 store，验证后记录迁移版本；导入中断可重复，不删除未验证的旧副本。旧空 saveDraft 不作可靠草案来源。
- 旧“标题指纹回执”缺少真实实体 ID，不升级成成功回执。显示“历史保存结果需核对”，查实体证据后再建立关联；不能按同名任务自动认领。
- 本机运行和经历元数据首版不做跨设备自动执行。业务对象继续沿用既有同步；另一设备的聊天投影只读，显示“在创建此方案的设备继续操作”。不得承诺离线多设备全局只执行一次。
- 重新生成到新设备是新请求，先查当前对象并提示疑似重复；没有可靠逻辑身份的相似项不能自动合并。

## 8. 确认、执行、恢复与撤销

### 8.1 有限动作目录

| 动作 | 支持字段 | 保存前必须成立 |
|---|---|---|
| createTask | 标题、必要备注、清单、优先级、明确截止日期/全天属性、有效计划时段、子清单 | 内容已预览；未设置日期不补今天；相对时间有锚点 |
| updateTaskSchedule | 计划时段 set/clear；截止日期 set/clear；全天属性 | 指向真实未完成任务；修改哪个字段已明确；重复任务不支持 |
| setBudget | 真实预算/账本/分类、Decimal 金额、持续或仅指定周期、币种与范围 | 不隐式换账本；周期范围可解析；结转口径已展示 |
| updateHabitTarget | 已有数值型好习惯的正目标值、原单位、生效日期 | 不改单位/频率/提醒；历史目标可解析；目标类型匹配 |

系统日历只读；当前未支持的动作只显示建议和原模块入口，不显示可执行主按钮。创建预算可作为 setBudget 的明确 create 模式，但目标唯一性需通过现有 Repository 检查，不能自动复制已有周期预算。

### 8.2 一次确认的精确边界

用户点击带具体数量和前后值的按钮即确认这些操作。生成、展开依据、聊天中“不错”均不构成执行确认。确认载荷包含草案版本、决定版本、所选操作和展示内容 digest；执行时内容变化则使该确认失效。

确认后按照依赖拓扑逐项执行。父任务与子清单在同一次 Repository save 内原子保存；不同业务对象采用按项结果，不做没有事务支持的“整批全成功”承诺。前置失败时后续依赖项标 blocked，独立项可以继续。

### 8.3 执行步骤与幂等

1. 按 operationID 在本机 actor 中串行占位；查询现有成功/待核对回执，重复点击不会启动第二份执行。
2. 重读当前权限、用户决定、草案版本、来源修订和目标对象版本。只比较当前决定真正依赖的来源；不因无关记录变化阻断整份计划。
3. 持久化 prepared 日志，包括用户确认的 before/after、目标 UUID、操作 ID 和必要预期版本。写日志失败则零业务写入。
4. 在隔离的可注入 Core Data context 中重新查目标、校验并保存。复用现有 Repository 校验和日期规则；不能调用会把其他编辑页未保存内容一并提交的共享 context.save。
5. 创建任务预先分配稳定 UUID，与操作标记同一次业务 save 保存；更新对象写 lastContextOperationID，和业务字段同一次 save 保存。失败只回滚本次隔离 context，不能全局 rollback 用户其他编辑。
6. 保存成功后记录真实实体 ID、业务版本和 appliedAt，再刷新业务列表、看板、聊天投影。提醒调度在提交之后进行，独立记录结果，不因提醒失败重建任务。
7. 进程崩溃后先恢复 prepared/inFlight：按预分配 UUID、操作标记和当前实体读取核对；确定已提交则补回执，确定未提交且前提仍成立才可重试。无法证明结果时标 unresolved，停止自动重复写入。

相同 logicalItemID 已有成功对象，后续草案只能关联它或提出明确修改。内容指纹用于发现变化，不能承担身份。查重覆盖真实目标集合，包括归档/删除记录的身份；同名只提醒，不能静默去重或认领。

更新对象的 lastContextOperationID 是本机恢复证据，不是跨设备锁。同一对象有未核对操作时，不启动另一条 AI 更新；普通用户编辑保留操作标记但更新业务版本。远端冲突可能让结果不可确定，此时进入 unresolved，不能假称全局事务保证。

### 8.4 失败与撤销策略

| 事件 | 必须行为 |
|---|---|
| 本地保存失败 | 该项 failed，显示可理解原因；不写成功回执、不安排回看 |
| 保存成功、回执写盘失败 | 从已持久化 prepared 和对象标记恢复，暂显“正在核对”；不重建 |
| 保存成功、提醒失败 | 显示“已添加；提醒未设置成功”，重试提醒，不重试业务创建 |
| 用户已在其他入口编辑对象 | 标记 conflict，展示当前值和建议值，重新确认后再改 |
| 来源已忘记/禁用/过时 | 阻止相关未提交操作；更新卡片，已创建业务对象保持原样 |
| 连点、重开页面、重启应用 | 同一操作返回已有结果；不重复创建 |
| 后台中止 | 恢复持久化状态，前台核对；不无限显示“运行中” |

首版不提供会跨多个模块回滚的总撤销。允许对本次新建且未被编辑/完成的任务使用现有删除/撤销入口；需要确认的删除沿用原规则。预算、习惯和日期修改提供“恢复原设置”的新预览，重新读取当前版本并确认，不能用旧 before 强行覆盖后续用户编辑。

## 9. 业务语义：日期、预算和习惯不能只改一个数

### 9.1 任务日期与计划时段

复用 TodoTaskDatePolicy 和 Repository 的 set/clear/unchanged 语义。截止时间、全天日期和计划起止分别存储；不从一段展示文案反向解析日期。

没有时刻的“周五前”先按现有日期规范解析为可确认的全天截止；没有明确哪周则结合 frame 的 referenceTime 并展示具体日期。跨时区使用创建请求冻结的时区解释，保存前用户改了时区则重现预览，不再次静默解析成另一天。

计划起止必须成对、开始早于结束并满足当前同一天限制。AI 输出不合法时返回校验错误，不能让模型内容触发现有 preconditionFailure 崩溃。调整日期涉及既有提醒时，预览说明提醒是否跟随；提交后重新调度，失败只影响提醒状态。

### 9.2 单周期预算覆盖

**数据模型选择**：复用 Budget，新增可选、版本化的 amountPolicyJSON 字段，保存长期额度修订与指定周期覆盖。旧 amount 作为兼容基值；不为每个月复制一条 Budget，也不安排下月自动改回的后台任务。

策略包含：

- schemaVersion、policyRevision、policyTimeZoneID；
- legacyBaseAmount：首次迁移时的既有长期额度；
- recurringChanges：生效周期起点、Decimal 金额、operationID；
- periodOverrides：指定周期的起止、金额、operationID；
- 周期身份由真实 Budget ID、既有周期类型、冻结时区下的实际周期起点共同确定。

周期从现有 startDate 和 BudgetPeriod 推进，不假定所有月预算都从自然月 1 日开始。单周期覆盖必须严格匹配一个实际预算周期；用户说“这个月”而预算周期并非自然月时，预览实际范围并让用户确认，不能后台偷偷选择另一个周期。

新增统一 BudgetAmountPolicy：

1. 先按现有周期推进规则确定目标周期和冻结时区。
2. 查该周期覆盖；存在则使用覆盖额度。
3. 否则取该周期之前最后一次长期变更；无变更取 legacyBaseAmount。
4. 严格预算的可用额度 = 本周期额度 − 按既有政策允许扣除的上周期结转，下限为零。
5. 上周期是否超支必须使用上周期当时的额度，不能继续拿当前 amount 计算。

当前严格预算只对总预算结转、债务只传一期等既有规则保持一致；分类预算预览不能凭空出现结转。聊天卡、预算设置、财务汇总、今日看板、超预算通知和分析工具统一调用 policy，不能一处显示 1800、一处仍按 1200 报超支。

仅本周期修改只增改 periodOverride，不修改长期基值；长期修改新增 recurringChange 并更新旧 amount 兼容镜像，历史查询仍使用策略。普通手动预算编辑也必须经过同一策略，不能成为绕过历史规则的第二入口。用户修改预算起始日而既有覆盖存在时，旧覆盖保持原历史范围，当前不再匹配的覆盖不自动迁移，编辑页展示受影响项。

**并发与兼容**：确认前比较完整 policyRevision 与内容 digest；同周期冲突重新预览。JSON 在 CloudKit 中仍是单字段同步，不声称可自动合并离线并发编辑；同步后发现冲突按当前真实值重核。旧客户端不能正确展示新周期覆盖，因此对外开启前必须验证支持版本的 iPhone/iPad 组合，并在相关设置明确旧版本兼容限制；不能把新版能力宣传为所有历史客户端一致支持。

验收至少包含：自然月/自定义起点、月末 clamp、跨年、闰日、时区变化、连续两次临时调整、长期调整后的历史查询、结转、负数/过多小数位、跨账本与多币种隔离。

### 9.3 习惯目标按日期生效

**数据模型选择**：复用 Habit，新增可选 targetPolicyJSON。包含 schemaVersion、policyRevision、policyTimeZoneID、legacyTarget、targetChanges。每条变更记录 effectiveLocalDate、原单位、目标值和 operationID。已有 targetValue 作为当前目标兼容镜像。

首版生效日期只支持今天，用户预览清楚“从今天起”；不安排后台在未来某天修改。若用户需要明天开始或只改周末，提供原模块调整建议，下一批能力再扩展。今天之前的记录按 legacyTarget 或当时变更解释；今天的数据按今天新目标计算，预览说明“今天已记录的进度将按新目标计算”。

新增 HabitTargetPolicy.target(on:)，统一替代涉及历史达标计算时直接读取 habit.targetValue 的路径。覆盖 HabitRepository+Stats、习惯图表/热力图、今日看板、Agent 习惯数据源及回看计算。普通手动改目标同样写目标历史，否则不能承诺历史口径稳定。

原始打卡、数值记录、时长不改写。迁移前从未存过的目标变更无法恢复，旧历史以迁移时可得目标为基线并标记“此前目标历史不可核对”；不能把推测出的旧目标写成事实。

首版仅数值型好习惯正向目标，保留原单位与聚合方式。坏习惯、健康数值目标、单位变更、频率变化、目标关联策略不进入该动作目录。这样可以明确验证“英语 30 → 10 分钟”，避免把不同方向的健康/行为指标混成一个 targetValue 修改。

## 10. 共同经历和约定回看

### 10.1 经历如何形成

同一 run 中有真实成功操作或用户明确反馈，且长期学习政策允许时，才形成可供未来回答使用的经历。仅生成草案、不采用、不反馈的尝试，不自动成为“共同完成的事”。

复用 HoloMemoryRecord 的版本化 payload 扩展 collaborationEpisode，不另建一个脱离遗忘规则的记忆库。字段包括：episodeID/runID、目标简述、原消息引用、采用/拒绝决定引用、成功操作及实体引用、发生时间、反馈引用、适用范围、访问控制与修订。默认本机存储，遵循已有 memory repository 的边界。

经历与业务真相分开：

- “当时添加了两项任务”来自成功回执，是历史事实。
- “现在两项都完成了”来自本次读取的任务状态，是当前快照。
- “安排让我安心”只能来自用户明确反馈。
- 没有记录时可以说“暂无后续记录”，不能说用户没做或方案无效。

“记住我上次怎么选”不等于永久复用。新请求先检索相关经历，再核对时间、对象、责任与当前情况，把仍适用的经验作为候选依据。

### 10.2 回看约定的建立

动作保存成功后，用户可选择回看，明确看什么、何时看。默认模板：

| 场景 | 默认观测窗口/时点 | 读取内容 |
|---|---|---|
| 一次准备 | 用户明确的活动结束后，或用户指定日期 | 采用的待办当前状态；用户反馈 |
| 习惯调整 | 修改后 7 个完整当地自然日 | 有记录天数、原始记录量、各日目标、用户反馈 |
| 预算临时调整 | 该预算周期结束后 | 实际支出、该周期额度、结转口径、是否有后续编辑 |

无结束日期的准备方案不擅自建立精确回看时间，可让用户选择日期。建立 ReviewAgreement 必须写入约定范围与版本；用户后来改习惯/预算，回看标记其影响并按真实分段解释。

### 10.3 调度与展示

扩展现有 OutcomeReviewStore 的能力边界，由统一 run store 持久化新协议，旧 API 作为兼容适配。只保留一份新约定状态，不在两个 UserDefaults key 中分别计时。

到期检测接应用前台恢复、相关数据变化和已有观察器；后台机会触发只作补充。检测先做本地条件检查，无到期项不调用模型。到期后读取当前允许的数据，生成事实结果；仅在需要自然语言归纳时调用模型，数值由程序计算。

同一 agreementID + evaluationRevision 最多产生一份结果。任务仍未达到观测窗口、数据暂不可读取时保持 due/awaitingData，不标 reviewed。来源失效、对象删除、用户取消分别进入明确状态。

应用内默认只在今日看板显示一张待回看提示，可在画廊查看全部。已读、稍后、取消有独立状态：稍后默认 3 天后重新出现；每个约定最多一次主动应用内再提示，之后留在画廊供用户主动查看，不形成催促循环。

通知只有用户选择“到时提醒我”且系统权限已授予才调度；通用文案“有一件约好的事可以回看了”，不在锁屏泄漏个人事项。未授予通知权限不影响应用内约定；到期通知只提示打开，不承诺后台已经生成结论。

### 10.4 回看结论与后续动作

结果按“实际记录 → 与当时约定比较 → 用户反馈 → 可选下一步”呈现。没有新的有用信息就简短结束，不强行提出第二轮任务。

新增动作仍回到草案预览与确认；用户说“保持这样”只记决定，不重复保存相同目标。删除或修改过去的记录后，结果标记为需要刷新；刷新产生新的 evaluationRevision，不默默覆盖原回看里可追溯的历史版本。

## 11. 权限、遗忘与日志

### 11.1 控制关系

沿用“自动形成记忆”“记忆辅助回答”“AI 数据处理同意”，不要求用户为每条自然记录确认标签。内部灰度开关不替代用户同意。

| 控制 | 关闭后的效果 |
|---|---|
| 自动形成记忆 | 停止新萃取/历史补建/长期经历沉淀；已允许的旧记忆可按辅助回答开关读取 |
| 记忆辅助回答 | 停止旧个人记忆的检索、注入和原文补查；保留仅基于本轮输入的普通帮助 |
| AI 数据处理同意 | 停止文本/向量外发及相关在途消费；不能自动重开请求 |
| retrieval kill | 新个人情境检索与 injection 同时关闭，不能利用旧缓存继续注入 |
| planningInjection kill | 关闭回答中的新情境使用；若做 shadow 只保留脱敏计数且需原授权 |
| rawFallback kill | 停止原文补查，不影响已授权且有效的结构化候选 |
| action/review kill（新增） | 关闭未提交的新动作/回看生成；仍能查看既有结果并恢复核对已提交操作 |

现有 allowsPlanningInjection 需与 allowsRetrieval 建立依赖。控制快照每次从当前设置重新读取，不能在初始化闭包捕获后一直使用。用户撤销同意后，已经发出的网络数据不能假称被收回；本地停止消费迟到结果并按提供方真实政策处理。

最小操作日志服务于已经确认操作的恢复，不是长期画像。关闭自动学习不应损坏已提交操作的核对；但不得据此继续建立可供推荐使用的经历。关闭辅助回答后的普通单任务创建沿用旧流程；含旧个人情境的过期草案需去除背景并重新预览，不能绕过保存前检查。

### 11.2 用户控制的不同含义

| 操作 | 生效范围 | 对既有业务对象的影响 |
|---|---|---|
| “这次不参考” | 当前 run 排除此来源/经历 | 不改原记录和已保存业务对象 |
| “这项已安排” | 当前对象和时间范围的用户声明 | 不伪造任务完成记录 |
| “暂不需要” | 本次建议，不重复推荐 | 不推导永久偏好 |
| “不要再提这次经历” | 对该经历增加 suppression，禁止自动召回 | 可在管理页查看并恢复使用 |
| “忘记这个情况” | 沿用已有遗忘政策，阻止等价情境重新学习与引用 | 不删除用户原文或独立业务对象 |
| 删除经历 | 清理经历及其衍生可恢复文本、索引和回看约定 | 不连带删除原任务、交易、习惯 |

来源删除、遗忘或权限失效时，按 sourceRef 失效索引清理检索缓存、embedding、运行可恢复内容、经历和回看派生内容。新的结构化卡片隐藏相关个人片段与动作；旧混合 answerText 无法安全局部处理时，相关 AI 回答投影显示“这条回答引用的背景已移除”，不凭字符串替换继续保留泄漏内容。

历史用户消息和独立业务对象属于原有数据，不能为了遗忘自动大范围删除。新建任务的备注默认仅保留用户确认的执行说明，不复制整条私人依据；来源引用单独存储并受访问控制。

### 11.3 后端、缓存、日志的一致保护

已有四个 personal_context purpose 默认 metadata-only 仍不够：本能力可能经过普通 chat、目标规划和 agent_loop。网关必须给含个人情境的请求附加可信 privacyClass，服务端在任何热缓存、持久日志和错误记录之前执行内容最小化；不能只在 SQLite 写入时过滤，留下热缓存全文。

允许观测：随机请求关联 ID、版本、模型返回身份、token、耗时、候选数量、是否降级、动作类型、结果码。默认不记录原文、用户目标、任务标题、金额、来源片段、整份 Prompt、模型原始私密答案。测试原始响应只使用合成数据，单独存放、限定访问和保留期限。

现有云分析若上传授权快照，服务端能够处理解密后的内容。产品说明不得写成“所有数据绝不离开设备”或“服务器完全看不到内容”。本方案不扩大现有云任务正文保留期；本机运行存储、聊天投影、模型服务处理和后台日志分开说明。

## 12. 模型、后端协议、成本与性能

### 12.1 模型调用预算

按一次用户请求修订统计，所有自动修复和超时重试共享预算：

| 环节 | 默认上限 | 决策规则 |
|---|---:|---|
| 请求框架 | 0–1 次 | 意图结果已给足 frame 时为 0；明确入口缺框架时为 1 |
| 查询 embedding | 最多 1 批 | 合并最多 4 个方向，缓存命中可为 0 |
| 方案生成 | 常规 1 次，最多 2 次 | 第二次仅修复实际校验失败或确有价值的补查 |
| 原文补查 | 最多 1 轮 | 本地受限读取；触发后的模型再生成仍占上述名额 |
| 强模型升级 | 占用第二次生成名额 | 有证据的推理失败、额度足够才升级；不因“个人化”统一升级 |
| 保存动作与事实回看 | 0 次 | 程序完成落库、读取、计算和模板反馈 |
| 回看解释 | 0–1 次 | 有可归纳的新事实且用户已约定才调用 |

单次修订最多 3 次文本请求，不加一个不计费的“核验模型”隐藏在外面。语义支持通过既有萃取验证、程序约束、模型结构化输出及真实语义评测保证；需要额外核验调用时必须扣减同一预算。

用户新续问重置该修订预算；自动重试、重启恢复不重置。每 run 默认最多保留 20 个活跃请求修订，达到后引导从保留摘要继续新请求，累计费用仍按账号计算，不以换 runID 绕过额度。

### 12.2 商业额度与技术成本分开

复用现有 chat/分析等商业额度池，不另加一个用户难理解的“记忆点数”。一次用户规划修订视为一个商业动作，其内部框架/修复请求共享 operationGroupID，后端 reservation/commit/release 防止重复扣用户次数；模型服务产生的真实成本逐次记录，不能因为不重复扣次数就视为免费。

后台萃取复用现有队列和技术预算，不挤占用户主动对话次数，但有每日/每用户成本上限。权限关闭、原文未改变、索引可复用时不得重复调用。自动升级、补查和回看都必须在服务端执行预算限制，不能仅相信客户端计数。

**预算目标而非当前实测**：常规个人规划含所有新增请求、embedding 和重试的平均增量费用目标不超过 ¥0.05/次，P95 不超过 ¥0.10/次；回看解释平均不超过 ¥0.03/次。单修订预估累计超过 ¥0.10 时停止可选升级/再生成，回退到已验证可用部分。误差来自实际计费 token 时如实记录并修正估算，不能事后隐去长思考费用。

前份诊断中的 ¥0.0244/¥0.0463 是特定调用数量与价格假设，**不能直接当本文整条链路的实测单价**。本次多了框架、检索等潜在成本，按上线时实际提供方价格重算：

~~~text
单修订成本 =
  每次模型调用的实际输入/缓存输入/输出及计费思考 token 成本之和
  + embedding 成本 + 真实重试成本

单用户月增量成本 =
  规划修订数 × 实测均价
  + 回看解释数 × 实测均价
  + 本月萃取与索引的实际成本
~~~

已有深度分析成本单列，不能把整单旧成本重复归因于新增情境，也不能遗漏升级、失败与并发请求。没有生产账单分布前不承诺毛利提升。

### 12.3 延迟与故障默认值

以下为验收目标，需要在指定真机、网络、模型版本上实测：

- 用户提交或确认后 300ms 内出现对应状态；输入保存不等待萃取。
- 已建索引的本地候选准备 P95 ≤ 500ms；网络 embedding 独立记录。
- 常规方案端到端 P50 ≤ 6 秒、P95 ≤ 15 秒；20 秒仍无结果提示可继续等待/取消，30 秒自动调用预算截止并处理已有结果。
- 本机 5 项普通任务保存 P95 ≤ 1 秒，不包括系统提醒完成时间；UI 显示真实按项结果。
- 回看在进入前台后检测，不做每秒轮询；分页读取业务记录，不全库拉取。
- 来源集合大、数据加载慢或网络降级时优先减少非必要上下文，不裁掉决定真实性和权限的字段。

各端超时使用同一 requestRevision 与 operationGroupID。客户端超时不假设服务端未计费；迟到结果须经版本核对后才能消费。

### 12.4 双端协议与上线

复用 personal_context_request、personal_context_planning、personal_context_extraction、personal_context_verification；扩展 frame/draft/contextEffects 协议，并在 iOS AIProvider/HoloBackendAIProvider 与后端配置同时接线。保留普通 Provider 的真实兼容分支，不依赖不支持的 JSON response_format 参数。

每次 Prompt 修改同步 iOS PromptManager 后备模板、后端 defaultPrompts 和 promptRegistry 中实际版本定义。版本号必须高于开工时当前值，不能固定重写为本文快照的 v1。后端 SQLite 管理版本可能覆盖打包默认，发布证据必须说明最终加载来源。

新增兼容能力声明包含 schema 版本、支持动作、灰度配置版本和请求预算能力；旧后端缺字段则保守回退。声明只反映真正启用的功能，不用模型名称冒充能力。生产验证走实际可访问的 release status 和受保护的管理/请求证据；此前公开 /v1/prompts/meta 为 404，不能把它当必然存在的验证地址。

## 13. 关键架构决策与取舍记录

| 决策 | 采用方式 | 代价与控制 |
|---|---|---|
| ADR-01 复用还是重建 | 延续 PersonalContext、原 Agent Evidence、原 Repository 和记忆管理 | 要补齐入口差异；用统一契约与真实入口测试避免各自解释 |
| ADR-02 开放理解与有限执行 | 模型开放理解个人情境，程序只执行四类已验证操作 | 某些建议暂不可一键保存；UI 如实给原模块入口 |
| ADR-03 原子性边界 | 单业务操作原子保存，整批按项结果；本机日志支持恢复 | 不承诺跨域总事务或离线多设备全局幂等 |
| ADR-04 运行持久化 | 本机 actor + 受保护原子文件；聊天为投影 | 需要迁移、失效索引和崩溃注入测试；不把大量私密状态放 Defaults |
| ADR-05 临时预算/历史目标 | 在原 Budget/Habit 上增加版本化可选策略字段 | 必须统一所有消费者，验证同步、迁移和旧客户端限制 |
| ADR-06 回看触达 | 用户约定、前台补偿、应用内优先，通知单独同意 | 不承诺后台准时生成；有价值时才再次调用模型 |
| ADR-07 泛化证据 | 冻结未见情境 + 反事实 + 无关背景 + 人工盲评 | 比演示耗时，但能区分真实个性化与关键词表演 |

**总取舍**：宁可少开放一种动作，也不删真实回执、来源核查、用户确认或反事实评测。某动作未过门禁时只关闭该动作；已经完成的普通问答和安全只读建议仍可交付。

### 15.2 五场景 UI 与真实入口验收

修复既有 walkthrough 为真正的 XCTAssert 断言，覆盖以下端到端路径；另保留少量真实模型走查，不用网络输出当唯一 UI 测试数据源。

1. S2：从真实想法存储注入合成记录 → 实际检索 → 展示依据 → 补充“已安排” → 草案变更 → 选择两项 → 保存 → 打开任务 → 重启 → 不重复。
2. S1：今日看板进入 → 读取任务/日程 → 预览计划与截止 → 外部编辑一个对象 → 只阻断冲突项 → 其余保存后看板更新。

5. S5：生成有真实回执的经历 → 下一次请求引用 → 当前条件改变后不照搬 → 忘记来源 → 画廊/聊天/检索/回看全部按政策失效。

### 15.3 模型泛化与个性化增益

**评测数据**：保留公开示例做开发/回归，另冻结至少 40 组未见基础情境，来自不少于 8 个不同领域/组合。每组构造三种输入：

- A：真实相关背景；
- B：只改变一个关键条件的反事实，例如责任已转交、出发取消、原事项已完成；
- C：保留 A 的关键背景，添加容易分心但无关的个人记录。

共 120 个变体。每个变体用相同问题、模型、预算和输出契约分别跑“真实情境链路”和“无个人情境对照”，各重复 3 次，合计 720 份输出。费用和调用预算在执行前按该数量核算；不足时报告未跑完的具体数量，不能把 20 组结果称为 40 组全量通过。

真实链路必须从源记录经历萃取/状态读取/检索/规划/校验，不能直接把人工候选塞给模型冒充召回。对照保持当前用户问题与必要业务查询相同，仅去掉历史个人情境；确保不是换模型或给不同 token 预算造成差异。

金标来源、关键约束和评分理由在独立冻结步骤保管，Prompt 调试不看逐题答案。根据某套留出结果改 Prompt 后，该套降为回归集；下一次宣称泛化需使用新留出集。外部模型评委可辅助，关键结论由人工盲评复核，不以关键词出现、JSON 可解析或 answerText 非空作为语义成功。

**发布门禁**：

| 指标 | 口径 | 阈值 |
|---|---|---:|
| 个性化有实际作用 | A 中至少一项合理改变优先级/行动/时间/关键问题，且有来源 | ≥80% 基础情境 |
| 反事实响应 | B 中该改变的建议确实改变，其余关键条件不丢 | ≥85% 基础情境 |
| 无关信息稳健 | C 不因无关背景改变核心决定或增加无关任务 | ≥90% 基础情境 |
| 个人事实受支持 | 最终回答中个人事实与真实合法来源语义一致 | ≥95%；关键事实错误为 0 |
| 对照净胜 | 人工盲评“更有帮助”的比例减“更差”的比例 | ≥20 个百分点，且更差 ≤10% |
| 权限/保存严重错误 | 越权、假成功、重复写入、错对象/金额/日期、未经同意通知 | 0 |

每组以至少 2/3 次重复满足对应标准计通过，同时报告三轮各自分数和波动，不能只选最好一轮。百分比必须附分子/分母和失败类别；范围不适用的题单独标记，不能随意从分母删除失败题。未经验证的实时外部事实、医疗/财务因果和他人身份推断列为关键错误。

**失败定位**：追加“人工提供理想合法证据”的诊断组，只用于区分检索与规划问题，不替代上述门禁。理想证据仍失败则修目标理解/应用；真实读取失败而理想证据成功则修覆盖/检索；两者通过但用户不采用则回到需求和交互，不用新增功能掩盖。

### 15.4 用户试用与产品指标

从已同意参与的 10–20 位用户开始，连续观察至少两周；样本不足时如实报告，不包装成统计显著结论。个人对话原文不默认上传，必要样本由用户明确提供。

记录：实际接触次数、方案采用/修改/拒绝、操作成功、重复解释背景的反馈、回看打开/取消，以及“这次是否更适合我”。采用率按有行动需求的会话计算，普通查询不进入分母；反馈未回答单列，不能当满意或不满意。

技术指标全量记录脱敏计数：真实成功率、冲突率、unresolved 数、来源失效率、模型修复率、P50/P95 延迟、每修订真实成本。目标是提高有用性并减少重复解释，不以记忆数、生成字数、通知数或任务数增长作为成效。
