## 产品结论

目前有证据支持的结论是：**功能能够触发，也生成过候选；但已有修复没有完整进入当前发布代码，真正跑完的一次又未达到发布条件，界面没有把这些结果讲清楚。**

所以「继续改一个触发条件，再说应该可以」不足以解决问题。先恢复已经存在的可靠链路，再用真实记录验收最终可见结果。当前没有证据证明模型能力完全不够，也没有证据证明恢复代码就必定每天产出。

这轮交付：服务端只读诊断、当前代码与修复分支对拍、可复跑的 Swift 样本验证、可点击的产品效果预览。没有修改 App 或后端业务代码，没有部署、删库、改配额或改变用户开关。

## 已查实：跑完的一次为什么还是没显示

11-03 的真机文件日志已保存在 `/private/tmp/holo-disc/disp-diag-1103.log`，与线上 run ID 和时间一致：

```text
00:09:52.646 async completed: run=D6A8B1F1… polls=17
00:09:52.656 gate: received=2 survivors=1 diagnostics=[quote_mismatch,sensitive_inference]
00:09:56.740 publish rejected: [insufficientIndependentEvents(required: 2, actual: 1)]
```

服务端同一 run 的核验日志：一条候选 accept，两个 claim 均 supported；另一条 reject。最终手机发现可发布候选只引用到一个独立事件，发布策略要求至少两个，所以没有发布。

这不能解释成“你总共记录太少”：同批扫描 102 个引用、25 个材料块、20 个独立组。**总材料够，模型选出的这条具体观察的独立支持不足。** 也不能把这个拒绝直接定性为 bug：如果两段话实际来自同一经历，放行会把一次经历夸成重复规律。

需要改进的是生成端应尊重相同的独立事件口径，并让“任务完成但没有可靠结果”与“任务没跑完”区分显示；不能为了出现第一条而关闭真实引用、独立来源或用户撤权检查。

## 推荐实施顺序

1. **先修交付版本**：按 Discovery 路径范围把既有修复带回当前发布线，保留当前分支其他业务改动。不要再次只合提交历史，也不要全分支覆盖。客户端恢复异步提交/取件、重启恢复、同 ID 副本处理、持久化结果状态；本地后端代码与实际生产能力对齐，避免下一次部署倒退。
2. **再验第一条完整结果**：用合格材料跑完整 Coordinator → 本机保存 → 原生胶囊 → 详情 → 依据 → 续聊。首条验收以“真的可见且有原始依据”为准；服务端 200、verify accept、模拟样本通过，分别报告。
3. **然后调真实材料产出**：统计每层剩余候选、独立来源数与拒因，不记录正文。优先修生成与发布对“独立事件”的口径，不用降低真实性要求制造产出。确实没有合格发现时，展示已完成的事实；服务失败时，展示恢复安排。
4. **最后观察稳定性**：再验锁屏/断网/被回收后取件、次日运行、关闭和撤权。每日自动整理不等于每日必须给结论。

手机未连接，因此本轮无法确认当前安装包身份、最新本机门禁分支，以及真实记录下的最终展示。能够从服务端与现有代码证实的诊断已完成；恢复代码和真实设备验收仍是后续实施工作，不应标记为“功能已修好”。
