# Holo 全量代码体检（2026-09-07）

状态：本轮代码体检完成；4 处小缺陷已修复，主工作区合并构建与相关回归通过。重大整改等待东林决策。本报告记录一轮覆盖全部产品模块的代码风险排查，不代表真机、商店和生产全场景验收通过。

## 产品结论

**有明确硬伤，需要先补齐商业化与数据可信链路，再继续扩大功能范围；没有证据要求推倒 SwiftUI / Core Data / Hono 技术栈重做。**

最急的是：后端真实 Apple 验单没有实现；普通用户接口依赖客户端自报设备 ID；云端分析与本地分析的额度、证据、取消规则不一致。另有账号删除覆盖不全、正文日志保留、保存失败仍按成功推进、数据库异常时无法进入 App、重复任务规则失效等问题。

底层已有可复用的基础：统一财务计算、导入批次和去重、健康数据聚合、记忆权限与遗忘标记、Agent 状态与证据模型。主要架构债务是这些规则没有贯穿所有执行入口，部分流程只完成了表面步骤，缺少“已验证身份、已成功保存、已彻底删除”的可靠完成条件。

本轮直接修复 4 个边界清楚的缺陷，未提交、推送、部署或操作生产用户数据。严重问题的影响、证据强度和建议决策如下。

## 三、重大问题与建议决策

### M1 · P0：真实购买无法完成后端验单

**影响：** 正式 Apple 交易进入 `/v1/subscription/sync` 会收到 503，无法由购买凭证开通/恢复后端权益。当前客户端可能显示“购买已成功，会员状态同步中”，但等待不会补上缺失的验证实现。尚未查询真实受影响交易数，不能据此声称已经发生某笔扣款事故。

**证据：生产确认 + 本地复现。** `createAppleReceiptVerifier.verify` 只支持 `test` 分支的字面量 `test-valid`，其他模式一律 `SUBSCRIPTION_VERIFICATION_UNAVAILABLE`。生产有效模式为 disabled。Xcode 本地测试购买走调试权益覆盖，所以“模拟购买成功”会掩盖正式链路未完成。

**建议决策：** 作为第一修复优先级，接入 Apple 官方签名交易验证并建立交易与有效身份的归属；覆盖环境、商品、有效期、撤销/退款、续订及换机恢复。不要把正式配置切成 test。是否暂缓销售入口或推广付费，需要东林根据当前商品状态决定。

**完成条件：** 真实 Sandbox 购买、恢复、过期/撤销状态变化、重复交易与换设备测试通过；后端部署后验证有效配置和真实请求。只修改客户端或只跑模拟订单不能关闭此项。

### M2 · P0：普通用户接口缺少可验证身份

**影响：** 调用者可以自行更换设备 ID 获得另一份设备额度。若同时知道某个云端任务 UUID 和其设备 ID，就能冒用身份取结果或操作任务。随机 UUID 降低了发现目标的可能性，但不能替代权限校验。本轮未发现或宣称真实数据泄露，也没有枚举真实用户。

**证据：生产确认 + 本地复现。** `getDeviceId` 先直接信任 `x-holo-device-id`，仅在头缺失时检查 `enforceAppAttest`；因此即使把开关设为 true，任意自报 ID 仍能通过。`/app-attest/challenge` 返回随机数但未建立完整挑战验证；assert 为未实现分支。已有内部诊断/管理员认证不能覆盖普通用户 API。

本地证明：无设备头 401，自报任意 ID 200；错误拥有者 404，复制合成拥有者 ID 后同一任务返回 200。文件与生产一致。

**建议决策：** 建立统一的已验证设备会话/账户身份，额度、订阅、云任务、推送令牌、举报/反馈均绑定此身份。明确游客、Apple 登录、换机后权益与数据归属规则。技术上不能仅改开关；必须设计现有版本兼容升级，避免所有旧客户端突然失效。

**完成条件：** 伪造设备 ID、重放挑战、过期会话、跨拥有者读写全部拒绝；正常老用户迁移和换机不会丢权益。

### M3 · P1：云端深度分析缺少与本地一致的可信规则

**影响：** 云端可能在深度分析额度不足时继续执行，输出没有资料依据的事实结论；用户取消之后还可能继续产生模型调用。涉及健康或更早历史的分析，也可能被送到数据不完整的执行路径。

**证据：生产确认 + 本地复现 + 代码确认。**

1. `deep_analysis` 执行分支没有调用成功动作额度账本；`period_replay` 则有额度检查。云端 start 的 6 次/分钟、30 次/天属于技术限流，不等价于会员权益额度。本地注入一个“永远拒绝额度”的账本后，深度分析仍完成，账本调用次数为 0。
2. `final_claims` 通过结构校验即完成，没有本地 Claim Verifier 的事实证据验证。空数据集也能把“本月支出 99999 元”、零证据的模拟输出存成完成结果。这证明无依据结果能穿过系统，不代表真实模型每次都会这么回答。
3. 取消删除任务行，执行器仍持有内存中的问题/快照且不持续检查取消。合成模型第一轮取消后，第二轮调用仍发生，执行函数仍返回 completed；数据库任务实际已不存在。
4. 客户端云端快照固定近 180 天、每数据集最多 2000 行，截断缺少完整覆盖说明；日期被编码为 UTC 日期字符串，时分信息丢失。健康不在深度分析快照目录，但入口没有按问题范围强制路由。周期回放是另一条含健康摘要的路径，不能混为一谈。
5. 客户端云端功能默认开启（仍需云端隐私同意），并非代码默认关闭的未启用实验；生产云端密钥也已配置。

**建议决策：** 保留后台完成分析的方向，先统一“数据范围/不足说明、额度、事实证据、取消、结果落地”规则。资料不覆盖的问题应补取或清楚说明；不能把最近部分数据当作全部事实。是否在整改期限制云端分析适用范围，由东林决定。

**完成条件：** 相同问题在本地/云端得到相同的权限和范围判断；无证据事实不展示；额度不够不调用模型；取消后不再启动下一次调用；大数据、跨时区、跨 180 天与健康问题有明确处理。

### M4 · P1：账号删除、独立存储和日志保留没有形成完整闭环

**影响：** “删除账号与数据”完成后，仍可能保留部分本机衍生数据、桌面快照、后端记录及 Apple 授权。生产普通 AI 正文日志的保留也没有接入用户删除流程。

**证据：代码确认；日志配置生产确认、存储行为本地复现。**

- `AccountDataDeletionService` 清主 Core Data、`Application Support/Holo`、任务附件和部分临时文件，但未覆盖 `Application Support/ThoughtAI`、`Documents/schedule-completions.json`、App Group 小组件快照；敏感记忆库所在目录被直接移除前没有关闭其持久化容器。
- 删除前没有统一冻结后台写入、取消 Agent/记忆工作和重置所有仓库缓存；也没有后端账号/设备数据删除接口来处理云任务、推送 token、反馈、用量等记录。不能仅凭本地清空完成就宣称所有副本都已清除。
- Apple 撤销发送的是 `identityToken`，并设置 `token_type_hint=id_token`；Apple 撤销接口要求有效的 access token 或 refresh token。失败只记录日志，App 仍进入已注销状态。
- 生产开启 AI 内容日志。普通聊天请求/响应可以入库；本地 Agent 请求已做元数据摘要，但模型响应正文仍能入库。日志库保留期写死为 30 天，普通正则脱敏只处理邮箱、手机号、长数字、部分令牌，不能抹掉用户的经历和观点。内存热缓存也需要同一策略约束。
- 想法整理/通用个人情境部分 purpose 已强制 metadata_only；云端异步执行器的模型调用日志也仅传技术摘要。不能把正文日志问题扩大描述成所有路径都记录完整快照。

**建议决策：** 默认业务日志只留排障所需技术字段；需要正文调试时定义明确授权、时限和访问边界。明确账号删除应清除哪些云端内容、哪些交易/审计记录需按业务政策保留，以及用户如何看到处理中/失败重试。按完整数据清单实施一个可重试的删除流程，并正确交换 Apple 授权码获取可撤销令牌。

**完成条件：** 删除后用合成数据逐一检查主库、敏感库、索引、文件、Widget、云任务、反馈及日志；删除中断可继续，后台不能重新写回；Apple 撤销收到有效结果。不在本轮擅自删除生产日志或改变销售/隐私承诺。

### M5 · P1：部分操作以“执行过步骤”代替“数据已可靠保存”

**影响：** 磁盘或保存异常时，用户可能看见成功但数据没有真正保存；少见的中断窗口可能导致 AI 确认重试后重复记账/建任务，或云端结果过早销毁后无法找回。

**证据：代码确认，尚未进行真实磁盘满/进程强杀注入。**

- 财务添加/编辑账户存在 `try? context.save()`；部分仓库修改共享 context 后保存失败，没有完整撤销或向界面传递失败结果。
- AI 创建业务记录与写入 `aiSourceMessageId/aiSourceItemId` 是分开的保存操作。若在中间崩溃，恢复流程依赖来源标记对账，却无法找到已创建的记录，可能再次执行。
- 云端结果接收后，`finalizeAgentMessage`/回放 finalizer 不向调用者返回持久化成功凭证；随后仍发送 ACK 让服务端销毁结果。聊天仓库 `save()` 捕获错误，消息不存在时 finalizer 也可直接返回。此时“已保存到本地”的前提不成立。

**建议决策：** 用户创建/修改操作只有在持久化成功后才显示完成；业务记录与 AI 来源标记同一次提交；远端结果 ACK 必须依赖本地已成功落库的确认。网络确认失败允许重试，重复确认不得重复生成业务记录。该问题需要跨仓库的一致提交契约，不能只改提示文案。

**完成条件：** 保存失败、中途杀进程、重复确认、消息已被删除、ACK 网络失败分别注入；最后状态只能是成功一次或明确未完成，不能出现静默丢失与重复写入。

### M6 · P1：数据库打不开时 App 无恢复入口

**影响：** 用户设备数据库若因损坏、空间不足或不兼容而加载失败，启动就 fatalError，可能反复打不开 App。不是已证明普遍启动崩溃，而是故障发生后的恢复通道缺失。

**证据：代码确认。** `CoreDataStack` 加载失败无条件终止。程序化模型使用轻量迁移本身不等于必然迁移失败：本轮用带 persistent history 的旧/新 SQLite 模型做通用实验，新增可选字段后旧记录仍可读取。没有将未经证实的迁移猜测列成已发生事故。

**建议决策：** 增加保留原库的恢复界面，支持重试、空间问题提示、导出诊断/备份恢复；不能自动删库重建来换取“能启动”。恢复策略涉及用户数据取舍，需先确认。

**完成条件：** 真实旧版库升级、损坏库、只读/空间不足场景均有可理解且保数据的处理；恢复动作不能破坏原始副本。

### M7 · P1：重复任务承诺与下一次生成不一致

**影响：** 选择“重复 N 次”之后不会按次数停止；完成一次后生成的下一项仅保留标题、列表、优先级、到期日、全天和提醒，说明、检查清单、标签、目标等未继承，用户需要反复补录。

**证据：代码确认。** `RepeatRule.nextDueDate` 的 untilCount 只有 TODO，界面描述却支持“重复 N 次”；`TodoRepository.completeRepeatingTask` 创建下一项仅传上述少数参数。每月“第 N 个星期几”分支也固定取下个月，未使用间隔值。没有用真实用户任务做完成操作。

**建议决策：** 建立重复任务模板与每次执行记录的关系；默认继承说明/标签/清单结构/目标，重置完成状态；补齐次数与间隔。附件、来源链接和计划时间段如何继承，及次数是否包含首次，需确定产品口径并处理已存在的重复规则。

**完成条件：** 每天/每周/每月/自定义、次数/截止日、月末/跨年、清单与目标继承均有表驱动回归。

### M8 · P2：跨设备变更到页面刷新的机制不统一

**影响：** 另一个设备新增/删除记录后，当前页可能继续显示旧列表，要退出页面、重开或下一次本地操作才更新。

**证据：代码缺口，用户可见时机待双设备验证。** Habit 等部分仓库监听了远端变更；Todo 的 activeTasks/lists、Anniversary 的缓存、Goal 的列表主要依靠本地调用重载。Core Data 自动合并已有对象，不保证这些自行维护的数组自动加入新对象。不能据此推断 iCloud 本身丢数据。

**建议决策：** 统一数据库变更通知到各模块缓存/页面的刷新边界，不逐页叠加临时刷新。作为稳定性修复排期；验收使用两台真实设备，涵盖当前页停留、后台回前台、新增、删除和冲突。
