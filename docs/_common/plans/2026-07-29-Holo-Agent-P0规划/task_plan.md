## 关键问题

1. 连续追问应当复用上一条聊天消息、上一份 Agent Result，还是直接续跑原 Job？
2. 哪些追问可只读复用结果，哪些必须重新查数，哪些应恢复原 Job？
3. 如何避免把完整历史聊天或敏感原始数据重复发给模型？
4. 如何让指标语义兼容动态查询和固定工具，而不再依赖字符串猜测？
5. 自动化、真实模型、真机和 TestFlight 各自承担什么验收职责？
6. 如何证明线上运行的确切 release、Prompt、协议和工具版本？

## 已定原则

| 决策 | 原因 |
|---|---|
| 只做方案，不修改业务代码 | 用户当前要求规划与复杂度评估 |
| 复用现有 Job、Result、Evidence、Message 与 Scheduler | 避免建立第二套 Agent 会话/状态系统 |
| 连续追问不等于把完整聊天历史塞给模型 | 隐私、成本和上下文污染风险不可接受 |
| P0 以用户可见闭环和真实放量证据为完成标准 | 编译、fixture 或组件存在不能代表可用 |
| 自然追问和显式锚定必须同时支持 | 自然输入保证流畅，显式锚定解决历史分支与歧义 |
| 方案必须区分当前已实现、计划新增与放量门禁 | 避免把设计目标误报为现状能力 |
