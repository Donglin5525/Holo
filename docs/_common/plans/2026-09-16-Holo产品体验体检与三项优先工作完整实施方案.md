## 0. 产品结论与执行顺序

Holo 当前最重要的工作是兑现已有能力的用户体验：**稳定地完成一次操作、第二天能继续推进同一件事、AI 回答值得相信**。三个方向都已有部分代码和方案，GLM 的任务是核准当前状态、完成真实验收、修复验收暴露的根因，并建立后续发版可复用的门槛。

| 顺序 | 工作 | 用户可感知的结果 | 本轮完成证据 |
|---|---|---|---|
| G0 | 冻结事实基线与在途改动 | 不因并行修改造成新故障 | 代码/测试/模拟器/真机/生产分层状态表 |
| G1 | 体验质量与发版门槛 | 主要路径不崩、不假成功、失败后能恢复 | P0/P1 清零；关键旅程回归和设备记录 |
| G2 | 记录 → 今天行动 → 完成 | 第一天记录的事，第二天仍能找到并推进 | 新用户与日本旅行两条真实旅程通过 |
| G3 | HoloAI 可信情境与回看 | 回答准确、引用相关背景、建议可执行 | 固定样本评测、真机反馈、后端生产证据 |
| G4 | 内部连续试用与发布判断 | 连续使用中问题可发现、可回退 | 7 天试用记录、残余风险、发布决策包 |

G0 先于其他阶段。G1 的基础回归在每次 G2/G3 改动后重跑。G2 与 G3 按用户旅程交叉验收，不把三个方向做成互不相干的功能包。

## 2. 工作一：建立版本级体验质量门槛

### 2.1 产品目标

用户完成高频动作时，不遇到崩溃、无响应、假成功、数据消失或无法恢复的等待。一个入口修好后，其他入口不会保留同类问题。

### 2.2 GLM 执行任务

1. 对齐十轮 QA 计划与台账。第 1–3 轮只抽验易回归问题；从第 4–10 轮补齐未完成专项。对近期新增的想法图片、Today、iPad、记忆迁移和云端叙事改动增加定向回归。
2. 建立一张**跨模块真实旅程矩阵**，每行都写起点、操作、预期落库状态、可见反馈、失败恢复、设备与证据。至少覆盖：
   - 全新安装 → 引导 → AI 一句话记录 → 财务回读 → 重启；
   - 想法文字/图片新增、编辑、删除、回收；
   - 任务新增、改日期、移回收件箱、完成、删除；
   - 习惯打卡与撤销、统计即时更新；
   - Today 主行动、Matter 详情与方案逐项保存；
   - 聊天普通回答、深度分析、取消、失败重试、冷启动恢复；
   - 长廊的滚动、手势、日回放与数据刷新；
   - 小组件、通知深链、权限拒绝、双设备同步。
3. 网络路径用正常、断网、弱网、超时、中途取消四种状态验证。每种状态应有明确终态、可理解的原因和可执行的下一步；取消后的旧任务不得“复活”。
4. UI 路径覆盖浅/深色、简/繁/英、小屏 iPhone、常规 iPhone、iPad 常见窗口宽度和大字号。真实手感、系统权限、锁屏、小组件和 CloudKit 必须留到真实设备验证。
5. 每个问题记录编号、严重度、复现步骤、用户影响、根因、修复范围、回归证据、剩余风险。修复相同类型的第二个问题时，检查是否需要统一规则或共享组件；避免逐页复制修补。

### 2.3 分级与出口

- **P0**：崩溃、数据丢失或损坏、隐私错误；发现后立即处理并回归。
- **P1**：主要操作不可用、假成功、明显卡顿、流程断裂、失败后无法恢复；本轮必须清零。
- **P2**：可完成操作但有认知负担、文案、视觉或发现性问题；记录影响、修复时机和负责人，设计改版先给东林可审的方案。

G1 出口：P0/P1 清零；每条关键旅程至少有相关测试、模拟器实走和明确的真机状态；所有“成功”必须回读真实业务对象；十轮 QA 台账状态与实际执行一致。`Executed 0 tests`、`BUILD SUCCEEDED` 或截图不能单独写成旅程通过。

## 3. 工作二：验收从首次记录到持续行动

### 3.1 产品目标

用户第一次知道该做什么；记录成功后能看到结果；第二天回来，Holo 能指出与这件事有关的下一步，并让用户在当前入口完成操作。

### 3.2 两条必须跑通的旅程

**旅程 A：全新用户。** 全新安装 → 看完或跳过引导 → 首页第一步气泡 → AI 预填但不自动发送 → 用户发送并完成第一条记录 → 在对应模块回读记录 → 首页首次反馈只出现一次 → 次日打开「今天」有清楚的行动出口。分别测有数据老用户升级、手动关闭气泡、断网失败、重复发送、冷启动。不得把“进入 AI 聊天”计为激活成功；以业务对象真实落库和用户继续操作为准。

**旅程 B：日本旅行。** 用户说“国庆要去日本，要提前准备什么” → 得到有依据的个人情境方案 → 用户选择“开始整理” → 逐条加入签证等任务 → 每条任务有真实 ID、来源与 Matter 关联 → 「今天」显示最值得推进的一项 → 完成该任务后主行动变化 → 从 Matter 继续讨论“酒店订好了”且无需重述背景 → 重启仍保持正确状态。用真实 Context Plan 入口生成，不能以 `MatterDemoSeed` 替代主验收。

### 3.3 关键产品约束

- Today 排序和是否过期由本地确定性规则决定，打开页面不等待模型或网络。
- 建任务、改状态、完成事项以 repository 的真实回执为成功依据；重试要幂等，不能生成重复任务。
- “下一步”须有可打开的真实目标；资料不足时显示查看/确认入口，不生成假任务或假风险。
- 不用任务标题猜 Matter 归属；使用真实实体 ID 和来源关系。来源变化后，旧投影不能作为当前事实展示。
- 用户明确输入、修改和撤销优先于 AI 推断；模型建议不直接修改高影响业务数据。

### 3.4 验收与观察

先跑两条真实旅程，再补 0/1/多 Matter、任务已删、重复点击、保存失败、stale 投影、跨日、冷启动、双设备冲突等边界。小屏与常规 iPhone 都要实走；iPad 未测须明确列为未测。G4 内部连续试用时，逐日记录主行动是否被采用、是否真实完成、用户点“稍后/不相关”的原因、任务关联是否正确、是否需要重述背景。没有统一埋点基础设施时，用最小诊断事件与手工试用表，不为本轮引入新的外部分析系统。

G2 出口：两条主旅程全程可重复；完成/失败/撤销后的页面状态与数据库一致；真实来源关系在冷启动后仍成立；边界场景的 P0/P1 清零，P2 有明确处理决定。连续使用的效果在 G4 判断。

## 4. 工作三：收口 HoloAI 的可信、有情境的回答

### 4.1 产品目标

用户问事实时得到直接、可核对的答案；讲个人处境时，Holo 只使用相关且获准使用的背景；用户愿意行动时，给出一个可开始的步骤，并在用户主动约定后回看实际结果。

### 4.2 按现有方案逐层推进

**A. 先收口 P0 叙事契约。** 核实当前在途代码是否已把服务端 `narrativeSummary`、`keyInsight`、claim `interpretation` 完整传至最终卡片。用现有冻结样本和盲评材料复核服务端结果、领取结果、iOS 解码与展示四段；旧结果、缺字段、坏字段必须安全降级。完成现有方案的门槛：可用叙事字段传递率 100%，数字、依据、时间范围和建议顺序零回归，20 条固定样本的自然表达盲评胜率达到方案阈值。已有实现直接验收和修根因，不重写第二套 Renderer。

**B. 再推进 P1 相关情境。** 复用当前 Memory Query、用户纠正、目标、权限策略，在本机选最小必要背景；绑定请求、来源与修订信息。后端只把背景当数据，不当新指令。用户撤回权限、删除来源或纠正内容时，后续请求和迟到结果都不能继续引用。采用现有方案的相关背景反事实、无关背景抗干扰与伪个性化门槛；默认不上传完整历史和未获准的短原文。

**C. 最后评估 P2 表达与 P3 最小回看。** 让事实与表达分层：表达只能重组已验证结果，不能新增数字、事实、因果或动作。先覆盖“直接查数、专业分析、低能量倾诉、继续上次事项”四类姿态。建议最多突出一个优先小行动；只有用户确认后才写入真实业务对象。回看先采用用户主动约定、应用内可见的形式，到期重读真实数据，仅描述变化，不把并发变化说成因果。系统通知、自动执行、高敏感原文上云另行呈现证据供东林决策。

**D. 记忆低确认成本作为当前能力验收。** P0–P6 已有在途代码和测试；本轮检查真实记忆上的存量迁移、用户已确认/纠正/拒绝记录是否不变、按需澄清是否只问关键未知量、“不再使用”是否不会复活、旧设备是否出现相反口径。不要重复建设确认队列。

### 4.3 固定评测集与硬门槛

建立事先冻结的代表性问题集，覆盖财务、任务、习惯、健康、想法、目标、跨域、无数据、错误来源、用户纠正、续问和低能量表达。至少包含“账内有记录但模型误报没查到”的关键词检索回归样本。每条保留问题、授权状态、期望直接答案、允许引用的证据、禁止结论、实际三段输出与人工判定。

- 数字、日期、范围、来源和成功状态与真实数据一致；出现事实性错误即阻断该场景放量。
- 没有来源的“我记得你一直……”为 0；权限关闭、撤回和迟到结果泄漏为 0。
- 数据不足时明确边界，不把缺数据写成用户异常，不将相关性写成因果。
- 固定样本盲评自然度和“是否真正回答问题”；评审者不知道新旧版本。
- 同时记录响应时长、完成率和成本。自然度提升不能以事实、隐私或稳定性下降交换。

G3 本地出口：P0/P1/P2 各自门槛有样本与结果；P3 若实施，必须有真实行动回执与回看样本。后端或 Prompt 有变化时，先完成本地契约、测试和发布包；经东林授权部署后，再核对 `/v1/release/status`、`/v1/prompts/meta`、来源摘要及真实请求，作为生产出口。只看 `/v1/health` 返回成功不算生产生效。Prompt 变更遵守双端模板、版本号和生产验收规则。

## 5. 统一验证与发布证据

GLM 每阶段报告都按以下层级分开写，不得用上一层替代下一层：

| 层级 | 要回答的问题 | 最低证据 |
|---|---|---|
| 代码/契约 | 当前实现了什么；是否复用单一真相源 | diff、调用链、相关契约 |
| 自动化测试 | 哪些规则被锁定；实际执行了几项 | 真实测试数、失败数、命令与日志路径 |
| 模拟器 | 用户能否沿路径操作 | 设备/系统版本、步骤、回读结果 |
| 真机 | 手势、相册、锁屏、权限和实际网络是否正常 | 设备、系统、复现记录；未测就写未测 |
| 双设备/CloudKit | 数据和状态是否按预期同步或冲突处理 | 两设备、账户、操作顺序、重启后结果 |
| 后端/生产 | 线上版本与 Prompt 是否生效 | release、Prompt、来源摘要、真实请求响应 |
| 内部试用 | 连续使用是否有价值 | 7 天事件、问题台账、采用/放弃原因 |

G4 在 G1–G3 的候选版本上开展 7 天内部连续试用。每天记录至少一条真实记录或行动、Today 焦点是否有用、AI 是否直接回答并引用正确背景、失败能否恢复；按用户旅程统计问题，不拿页面曝光或聊天字数代替有效帮助。试用期内 P0/P1 必须清零；若出现事实错误、数据损坏、错误使用记忆或不可恢复操作，暂停扩大范围，修复后重跑受影响旅程。试用结束产出发布建议包。

发布建议包必须包含：用户可见变化、P0/P1/P2 未结清项、真机/双设备/生产状态、涉及的功能开关和回退步骤、是否需要 App Store/CloudKit/后端发布、建议放量范围。需要提交、推送、部署、生产灰度或数据迁移的最终操作，由东林审阅具体结果后决定；方案和本地构建都不代表获得发布授权。

## 6. 应暂停并交东林决策的边界

在可逆、低风险的实现和修 bug 范围内，GLM 按上述默认方案直接推进。以下选择到达实施门槛时，先提供用户影响、证据、推荐方案和回退路径：

1. 向云端上传用户明确选择的记忆或想法短原文，或扩大个人数据的默认使用范围；
2. 让 AI 未经确认自动创建、完成或修改高影响业务对象；
3. 将陪伴回看从应用内扩展到系统通知或锁屏触达；
4. 改动首页/Today 已定稿的信息架构、品牌视觉或入口语义；
5. 上线所需的后端部署、CloudKit schema 变更、生产放量、提交与推送。

## 7. GLM 交付格式

每完成一个阶段，交一份短报告，顺序固定为：

1. **产品结论**：用户体验改善了什么，哪个核心旅程现在能完成；
2. **问题和决策**：发现的问题、根因、修法、需要东林拍板的点；
3. **实际修改**：文件、功能开关、数据/Prompt/后端影响；
4. **分层证据**：代码、测试、模拟器、真机、双设备、后端、生产、试用逐项标注通过/失败/未测；
5. **残余风险和下一阶段**：可复现的问题、回退办法、下一阶段开工条件。
