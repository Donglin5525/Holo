## 0. 产品结论

### 0.1 要解决的不是“多放一张图片”，而是统一用户身份

Holo 目前有昵称、Apple 登录账号卡、个人页和 Holo AI 用户消息头像，但这些位置没有共用一份“用户资料”。本功能要建立唯一的 Holo 用户头像资产：用户设置一次，所有真实身份展示位立即一致，随后通过个人 iCloud 同步到其他设备。

Apple 的登录凭证不提供用户头像，也不能让 Holo 回写 Apple ID 头像。因此，“Apple 登录那里的预置头像同步更改”的正确实现是：Apple 登录账号卡改为显示 Holo 用户头像，并用一个小状态徽标表达 Apple 登录状态；不是尝试读取或修改 Apple ID 头像。

### 0.2 首版拍板

| 决策 | 首版方案 | 原因 |
|---|---|---|
| 头像主数据 | Holo 自有头像，存本机并同步到用户个人 iCloud | 与现有本地优先架构一致，不引入后端图片库 |
| 主入口 | 设置 → “个人资料” | 账号、昵称、头像在一个稳定入口管理 |
| 次入口 | 个人页身份卡，进入同一个编辑器 | 方便发现，但不产生第二套保存逻辑 |
| 图片来源 | 从相册选择、拍照、移除头像 | 覆盖常用路径，现有基础设施可复用 |
| 裁剪 | 首版提供拖动、双指缩放的方形取景器，并用圆形蒙版实时预览 | 圆形头像尺寸虽小，但自动居中容易截掉偏离中心的人脸，用户必须能决定保留区域 |
| 同步范围 | 设置页账号卡、个人页、Holo AI 用户气泡 | 都是具体用户身份展示位 |
| 不替换 | 底部导航、iPad 侧边栏、日志角色图标、资料域图标、Holo AI 自身头像 | 这些是功能/角色/品牌语义，不是用户照片 |
| Apple 登录关系 | 登录与退出不清除头像；删除账号与数据才清除 | 与当前“退出登录不删除数据”的产品承诺一致 |
| AI 使用边界 | 头像不传给 AI、不进入 HoloProfile、不参与模型推理 | 头像只服务界面身份感，避免扩大隐私范围 |

### 0.3 用户可见完成定义

1. 用户在设置或个人页可选择照片、拍照、更换和移除头像。
2. 保存后，设置账号卡、个人页、Holo AI 中自己的消息立即显示新头像，无需重启。
3. Apple 登录后仍显示同一张 Holo 头像，登录状态通过徽标/副标题表达。
4. 未设置头像时显示昵称首字；连昵称也未设置时显示当前默认人形图标。
5. 开启 iCloud 时，头像可在另一台设备恢复、更新和移除；无 iCloud 时本机功能照常可用。
6. 退出 Apple 登录不删除头像；“删除账号与数据”会同时删除头像。
7. 头像不出现在 AI 请求、日志正文、导出文件或 Holo 后端。

## 3. 产品体验合同

### 3.1 设置页：唯一写入口

把现有 `SettingsSection.nickname` 升级为 `profile`，标题改为“个人资料”。内容顺序：

1. 头像区：80pt 圆形头像，右下角小相机/铅笔徽标；下方文案“更换头像”。
2. 昵称行：沿用“怎么称呼你”，继续走 `UserPreferenceRepository.setDisplayName`。
3. 说明：头像和昵称保存在本机；iCloud 可用时会同步到其他设备。

点击头像弹出操作菜单：

- 拍照；
- 从相册选择；
- 移除头像（仅已有自定义头像时出现，destructive）；
- 取消。

选图完成后进入头像裁剪页，而不是直接自动截取：

- 中央固定一个圆形可见区域，圆外使用半透明遮罩；圆形外接正方形就是最终保存区域；
- 单指拖动图片调整位置，双指缩放，缩放范围始终保证裁剪区域没有空白边；
- 默认缩放采用 `aspectFill`，让图片刚好覆盖裁剪区域；提供“重置”回到默认位置；
- 顶部“取消”不改变旧头像，底部“使用此照片”才生成并保存头像；
- 确认前同时展示 32pt、56pt、80pt 三种圆形效果，确保在 Holo AI 小头像、账号卡和个人页中都清楚；
- 方形照片也进入裁剪页，允许用户重新构图；不做人脸识别或自动跟脸。

### 3.2 个人页：展示与快捷编辑

### 3.3 Apple 登录账号卡

账号卡头像改用统一 `UserAvatarView`：

- 有自定义头像：显示照片；
- 没有头像、有 Holo 昵称：显示昵称首字；
- 都没有：显示默认人形图标；
- 已通过 Apple 登录：头像右下角显示小型勾选/Apple 登录状态徽标，但不替换头像本身。

账号卡名称优先级：

1. 用户主动设置的 Holo 昵称；

退出 Apple 登录只清理认证会话，头像与昵称保持；账号卡退回“本机模式”。

## 4. 数据与同步合同

### 4.1 新实体：`UserAvatarEntity`

新增独立实体，避免把二进制图片塞进 `UserPreferenceEntity.value`，也避免与 AI 的 `HoloProfile` 混淆。

| 字段 | 类型 | 默认/可选 | 说明 |
|---|---|---|---|
| `profileKey` | String | `"primary"`，非可选 | 单例逻辑键；不使用 CloudKit uniqueness constraint |
| `stateRaw` | String | `"unset"`，非可选 | `unset / custom / removed` |
| `avatarData` | Binary Data | 可选 | 仅保存处理后的单份 512×512 JPEG |
| `revision` | Int64 | `0`，非可选 | 本地每次变更递增，辅助诊断与测试 |
| `updatedAt` | Date | 默认当前时间，非可选 | 跨副本冲突主排序 |
| `mutationID` | String | `""`，非可选 | 每次变更新 UUID 字符串；同时间戳时作稳定排序 |

CloudKit 约束：所有非可选字段提供默认值；不加唯一约束；新实体加入共享数据模型；旧库以新增实体方式轻量迁移。

### 4.2 状态语义

- `unset`：从未设置，展示 fallback。
- `custom`：`avatarData` 必须可解码；不可解码时展示 fallback、记录诊断，但不擅自覆盖数据。
- `removed`：用户主动移除，`avatarData=nil`。这是可同步的删除意图，不能直接删掉整行，否则离线旧设备可能把旧头像重新带回来。

### 4.3 图片处理合同

新增 `UserAvatarImageProcessor`，不直接依赖“任务附件”概念：

1. 输入只接受能被 ImageIO/`UIImage` 解码的图片数据；
2. 读取阶段先按 EXIF 修正方向，并将超大图降采样到最长边不超过 2048px，避免相机原图在裁剪页造成内存峰值；
3. 裁剪页只保存本次编辑期内的 `AvatarCropState`：归一化中心点与缩放比例；不把原图或裁剪参数写入长期数据；
4. 拖动与缩放必须被约束在有效范围内，任意状态下圆形预览的四周都不能露出空白、黑边或透明棋盘格；
5. 用户确认后，按圆形预览的外接正方形渲染一张 512×512 方图；真正显示时由 `UserAvatarView` 使用圆形蒙版裁切，不能保存带透明圆角的 PNG；
6. JPEG 编码，目标质量约 0.82，最终不超过 512KB；超过则受控降低质量，仍超限时报错；
7. 输出统一为 sRGB，不保存 EXIF、GPS、拍摄时间等元数据；透明图片先合成到与界面兼容的固定背景，不能出现黑底；
8. 不保存用户原图；取消裁剪或处理失败时释放临时图并保持旧头像；
9. 解码、降采样和最终渲染在后台执行，手势状态与 UI 更新在主线程完成。

首版不做人脸检测、智能取景、美颜和旋转，避免隐私扩大与不可解释裁剪；构图权由用户通过拖动和缩放掌握。

### 4.4 仓库合同：`UserAvatarRepository`

`@MainActor final class UserAvatarRepository: ObservableObject`，对 UI 暴露不可变快照，不让 View 直接读 Core Data。

核心状态：

- `@Published private(set) var snapshot: UserAvatarSnapshot`
- `@Published private(set) var isProcessing: Bool`
- `@Published var errorMessage: String?`

核心 API：

```swift
func setup() async
func setAvatar(rawData: Data) async throws
func setAvatar(image: UIImage) async throws
func removeAvatar() throws
func reloadFromStore()
```

行为：

- `setup()` 必须等待 Core Data store ready，修复重复行，加载 winner，并监听远端变更。
- 保存采用一次 `context.save()`：写 `custom + data + revision + updatedAt + mutationID`。
- 移除采用一次 `context.save()`：写 `removed + nil + ...`。
- 远端变更防抖后重新取 winner；UI 通过 `@Published` 自动刷新。
- 内存只缓存一张解码后的 `UIImage`，避免每条消息重复解码。
- 不写 HoloBackend、不写 Keychain、不写 HoloProfile.md。

### 4.5 重复与冲突规则

由于不同设备可能离线创建各自的 `primary` 行，必须实现重复修复：

1. 按 `profileKey` 分组；
2. winner 按 `updatedAt` 新者优先；
3. 时间相同按 `mutationID` 字典序稳定决胜；
4. 采用 winner 的完整状态，删除其余副本并保存；
5. `removed` 与 `custom` 完全按同一规则比较，不能让“有图片”天然压过用户更晚的移除操作。

同一设备快速连续更换时，处理完成前禁止重复提交；若异步旧任务晚返回，以本次编辑 token 校验，旧结果不得覆盖新选择。

### 4.6 数据生命周期

| 用户动作 | 头像结果 |
|---|---|
| Apple 登录 | 保持原头像；账号卡增加登录状态 |
| 退出 Apple 登录 | 保持头像与昵称 |
| 关闭/失去 iCloud | 保持本机头像，暂停跨设备恢复 |
| 重新开启 iCloud | 按冲突规则同步 |
| 移除头像 | 同步 `removed`，所有界面回退首字/默认图标 |
| 删除账号与数据 | Core Data 全删，头像一并删除 |
| 卸载重装 | iCloud 可用则随私有库恢复；不可用则默认头像 |

## 9. 关键测试用例

### 9.1 图片处理

1. 竖图、横图、带 EXIF 旋转图输出方向正确。
2. 主体位于左上/右下时可通过拖动放入圆形可见区，不能被强制中心裁掉。
3. 最小缩放、最大缩放和四角拖动都不出现空白边；重置能回到默认 `aspectFill`。
4. 10MP 大图先降采样，裁剪过程不阻塞主线程，输出固定尺寸与上限。
5. 取消裁剪、快速连续重选、后台处理迟到都不能覆盖当前头像或更新选择。
6. 非图片/损坏 Data 返回可读错误，旧头像保持。
7. 透明 PNG 转 JPEG 后背景策略一致，不出现黑底异常。
8. 输出不保留 GPS/EXIF 元数据。
9. 32pt、56pt、80pt 圆形预览与最终三个消费点构图一致。

### 9.2 仓库与冲突

1. 首次 set 建立 `custom`。
2. replace 更新同一逻辑资料，不新增无限副本。
3. remove 写 `removed` 且 Data 为空。
4. `removed` 比较时间更新时压过旧 `custom`。
5. 两条相同 `updatedAt` 用 `mutationID` 稳定决胜。
6. 远端通知多次到达只防抖刷新，不循环保存。
7. avatarData 损坏时 fallback，不崩溃、不把损坏数据传入 Image。

### 9.3 产品旅程

1. 本机模式上传头像 → 三处立即刷新。
2. 登录 Apple → 头像不变，状态徽标出现。
3. 退出 Apple → 头像不变，状态徽标消失。
4. 移除头像 → 昵称首字 fallback；清空昵称后 → 默认人形。
5. AI 长对话滚动 → 头像稳定、无频繁闪烁和明显掉帧。
6. 账号数据删除 → 冷启动无头像、无旧数据回流。

## 10. 风险与治理

| 风险 | 用户影响 | 治理 |
|---|---|---|
| 把 Apple 登录误当头像来源 | 做不到或资料不稳定 | 明确 Holo 头像为唯一真源，Apple 只表达认证状态 |
| 头像 Data 过大 | 同步慢、数据库膨胀 | 512×512 单图、≤512KB、不存原图 |
| 每个消息重复解码 | AI 对话滚动卡顿 | 仓库单例内存缓存、组件只消费快照 |
| 自动中心裁剪截掉人脸 | 用户上传后头像不可用 | 首版提供拖动/缩放裁剪和三尺寸圆形预览，不做不可控自动跟脸 |
| 相机大图进入裁剪页内存暴涨 | 裁剪卡顿或闪退 | ImageIO 按目标降采样到最长边 2048px，再进入裁剪状态 |
| 删除后旧图复活 | 用户失去控制感 | `removed` 墓碑 + 冲突排序 + 双设备离线测试 |
| 两设备各建 singleton | 同步后出现副本 | 逻辑键 + 启动/远端变更后重复修复 |
| 修改任务图片组件引发回归 | 附件功能受损 | 只抽通用加载/相机能力，头像处理器独立 |
| schema 未部署生产 | App Store 版不同步或报错 | Production schema 作为发版硬门 |
| 隐私文案落后 | 审核和信任风险 | 同版本更新政策、权限说明和 ASC 判断记录 |
| 并行脏改冲突 | 覆盖其他在途功能 | 精确文件审查与 scoped staging，不做广泛格式化 |

## 11. 回退方案

1. UI 回退：所有消费点都具备 fallback；仓库不可用时恢复昵称首字/默认图标，不影响登录和聊天。
2. 代码回退：可撤回编辑入口和展示接线；新增 Core Data 实体保留为未使用的附加 schema，不做破坏性降级迁移。
3. 数据回退：不自动删除用户已同步头像；重新上线时仍可恢复。只有用户移除或账号数据删除才清除。
4. 发布回退：Production schema 只做 additive 变更；不得通过删除 record type/字段回滚。
5. 不需要回滚后端，因为本功能不修改后端。
