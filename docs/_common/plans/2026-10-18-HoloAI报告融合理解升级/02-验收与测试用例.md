## 1. 试评材料与隔离

先用合成报告、合成业务记录和隔离仓库验证规则；之后再用明确范围的真实 Holo 记录，从现有入口验证效果。不得自动向东林日用库写入合成报告或测试记忆，不得清空 CloudKit 开发环境。

评估材料中的用户行为、状态和数字必须先冻结。模型输出不作标准答案；事实由程序核算或人工核对原始记录。真实材料只放 local-only，匿名派生夹具经过复核才可入库。

| R26 | “这个月总支出多少”且存在上月报告摘要 | 查当前业务统计，不用旧报告数字回答 | I/E |
| R27 | 问题与已有理解无关 | 正常回答，无强行个性化或无关私人信息 | E |
| R28 | 报告已保存，进程在登记/消费前退出 | 重扫恢复，最终仅写一次，原报告仍可读 | I |

| R30 | 新链路关闭或未知载荷版本被旧端回写 | 旧报告可读；新语义保守降级；用户裁决不丢失 | U/I |
| R31 | 日常萃取管线已存在命题「外卖支出增多」，报告链路再提取同命题 | 按 README §6.6 合并为同一命题身份；证据按底层事件去重，不按两链路计两次 | U/I |
| R32 | 报告链路与日常萃取同命题、结论方向冲突 | 按 README §6.3 冲突规则处理；不因报告更晚生成而默认报告优先 | U/I |

任何数字、来源、授权、遗忘或删除传播用例失败，都不能以“整体通过率高”放行。语义理解测试不能只断言某个固定句子，需核对命题、用途、时间、来源与禁止推断。

## 4. 效果对照方法

冻结至少 20 个问题及对应数据：12 个需要相关历史理解，8 个无关/过期/冲突控制场景。至少三分之一留出不参与调参，题目跨周期回放和深度分析两类报告，覆盖事实、条件、变化和用户纠正。

每题成对运行：

- A：现有链路与现有背景。
- B：同一问题、同一业务数据、同一模型/配置，增加新理解链路。

尽量固定 Prompt/模型/数据；若财务 S2 同时改变分析方法，追加 C=新分析方法但无新增报告理解，以区分方法收益和记忆收益。不能把其他项目带来的提升归功于报告融合。

人工盲评维度：

1. 事实、来源、时间是否准确。
2. 是否少问了用户已经明确说过的内容。
3. 建议是否因相关约束发生有价值的变化。
4. 是否知道旧判断可能过期或有反例。
5. 是否避免编造动机、人格、因果与执行结果。
6. 是否自然，是否增加无关背景或隐私暴露。

每题记录 prefer A / prefer B / tie，理由须指向实际内容。先用规则门槛剔除硬错误，再比较帮助性。V1 目标为相关组至少 9/12 明确改善，控制组无明显退化；样本较小，只支持试点结论，不能外推全部用户效果。

## 5. 真实入口生命周期脚本

### E1 周期回放延续

1. 在隔离环境准备可核算的记录及一条明确用户背景。
2. 走现有周期回放入口生成报告，记录报告 ID、范围、版本和事实依据。
3. 等待后台维护并检查其处理状态，关闭重开 App。
4. 提出相关问题，确认使用有效理解，并能回查来源。
5. 生成下一期回放，核对延续/变化，不把旧统计当本期事实。

### E2 深度分析与精准统计

1. 用明确范围的真实 Holo 记录从当前深度分析入口建立基线。
2. 新链路接入后同数据重复，对照相关背景是否确实改善解释。
3. 再问当前精确金额，确认回到业务统计，而非复制报告数字。
4. 保留来源覆盖/截断信息；删除报告后再测，确认相关来源和缓存处理正确。

### E3 纠正、遗忘与在途结果

1. 准备一条可定位的错误候选和一个延迟返回的提取请求。
2. 用户通过既有入口纠正，随后释放旧请求，检查未被覆盖。
3. 发起相关提问，再忘记该理解；交付前复查阻止旧版本泄漏。
4. 冷启动、重扫报告与恢复旧报告，均不能复活被遗忘命题。
5. P3 在两台设备重复相同流程，记录离线与同步到达时间；不宣称离线设备可瞬间获知删除。

## 6. 测试工具与执行边界

- **测试基建复核（2026-10-19）：** 当前工程有常规 HoloTests unit-test target，Holo scheme 也包含该目标；既有记忆 standalone 套件通过 HOLO_XCTEST_BRIDGE 与 StandaloneExecutableBridgeTests 接入。正式 U/I 验收使用实际编入 HoloTests 的用例和桥接执行；swiftc 可作开发探针和补充证据，不能替代仓库/消费入口集成验收。此处不声称本轮运行了测试，也不以源码文件总数代表实际执行数。
- 新测试文件须核对 PBXBuildFile、PBXFileReference、group 与 Sources 登记；桥接形式还需核对 XCTest/@Test 执行入口。以实际执行的测试名称和数量与预期清单一致为准，0 tests 或漏套件不算通过。
- 需要 Core Data 的用例采用隔离仓库或现有集成测试机制；不要声称普通 App build 已运行测试。
- 后端按实际变更运行相关 purpose/预算/Prompt/兼容测试；业务实现后再做必要 App 构建。
- 此任务不改 UI，不要求界面原型或截图视觉验收；实际入口和数据/同步验收仍然必要。
- 真实模型调用须单独记录实际 usage、失败与成本，不复用其他方案的单份价格作本次证明。
- 测试输出与真实报告全文不提交版本库；代码和脱敏夹具是否入库另行审查。
- 🔧 修订C：试点期按处理键统计跨设备重复模型调用占比，作为 README §8.4 放量门槛的输入；多设备场景的评估记录必填 duplicateCalls/duplicateRatio。

## 7. 评估记录最小格式

每次运行记录：caseID、sourceReportIDs/revisions、sourceDataManifest、memoryVersions、policy/prompt/extractor/modelVersions、currentQuestion、expectedBoundary、actualFindingVerdicts、retrievedIDs、declaredUsedIDs、latency、usage/cost、totalCalls/duplicateCalls/duplicateRatio/retryCalls/repairCalls/duplicateCost/totalCost/duplicateCostRatio/observationWindow/deviceCoverage（多设备场景必填；定义见 README §8.4）、failureReason、reviewerDecision、notes。

模型声称使用某条记忆只是诊断信号；收益以原始事实核验与盲评为准。


## 8. 摘要预算修复专项验收（P0 定规格，启用前通过）

本组独立于 32 个报告核心场景，覆盖 GLM 提出的存量预算问题。源码确认 Prompt 类型与计费 purpose 不同，不能只测试配置集合。

| ID | 测试 | 预期 |
|---|---|---|
| B01 | 直调 replayDigest 经真实应用路由与 wrapped provider | 有可信主体、调用前预留、usage 结算；日/月个人和全局预算耗尽时均不调用上游 |
| B02 | 云端 replay_digest 启动、排队、worker 执行及进程恢复 | 每次真实尝试都恢复正确主体并预留，不能依赖已结束 HTTP 上下文；Prompt 类型不作为计费身份 |
| B03 | 云端预算拒绝后客户端尝试直调回落；合法上游失败后重试 | 预算拒绝不切轨道绕过；合法重试仍逐次预留，缺 usage 不退回可能已产生的成本 |
| B04 | 旧 build 的直调和云端摘要启动/恢复 | 版本闸门可预期、客户端不反复回落重试；不新加无法恢复主体的悬挂任务 |
| B05 | 主动聊天、深度分析、用户主动周期报告 | 不因通用 agent_loop 被列为后台而误扣/误拒，原计费/额度保持既有规则 |
| B06 | 重复调用统计 0 调用、合法重试、格式修复、两设备冗余 | 分母、分类和预留成本符合 README §8.4，0 分母为 N/A，不以比率替代总预算 |

真实入口与 mocked provider 的路由集成需要都覆盖；仅证明“集合里有某个字符串”不算修复通过。本次未运行 B01–B06，也未部署后端。
