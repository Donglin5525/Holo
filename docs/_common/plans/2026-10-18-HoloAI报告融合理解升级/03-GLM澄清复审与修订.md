## 2. 为什么不能只把 replay_digest_consolidation 加入预算集合

当前源码路径如下（仓库相对路径）：

| 层次 | 当前值/行为 | 依据 |
|---|---|---|
| Prompt 模板类型 | replay_digest_consolidation | HoloBackend/src/prompts/serverPromptPolicy.js:20，将 replayDigest 映射到该模板 |
| iOS 直调 purpose | replayDigest | Services/AI/HoloReplayDigestService.swift:348 与 HoloBackendAIProvider 的枚举 |
| 直调转发 purpose | 仍用请求 purpose | HoloBackend/src/app.js:825–826 的 upstreamRequest |
| 云端任务类型 | replay_digest | HoloBackend/src/app.js:1808–1819 |
| 云端摘要调用日志 | cloud_replay_digest | HoloBackend/src/agent/cloudAnalysisExecutor.js:867 |
| 云端实际 provider 请求 | 固定 agent_loop | 同文件 callProvider:580 |
| 入口后台守卫 | 仅匹配 BACKGROUND_PATHS 或 chat/completions 的 purpose | HoloBackend/src/app.js:375–387 |
| provider 后台守卫 | 按 request.purpose 判定；预留依赖 AsyncLocalStorage 的 subject | HoloBackend/src/usage/backgroundCostGuard.js:89–104、131–142 |

因此，单独增加模板类型并不能命中直调或云端实际调用。若粗暴把 agent_loop 全列入预算，还会影响主动深度分析；若只修改云端 purpose 却未建立主体，会触发缺失预算上下文错误。这是完整调用边界问题，须对真实路径做集成验收。

这里只确认当前本地源码的保护缺口。未查询线上部署，不推断生产服务器一定相同，也不将既往高消费归因于这一处。

## 3. 对“增量理解”的修正

假设日常萃取已经记住“晚间任务容易延期”，报告进一步发现“仅在工作日晚于 22 点且连续加班时发生，周末并无此模式”。它仍是同一命题家族，但条件更准确，规划可能明显改善。

所以命题可归并、关系没有新增，不等于产品价值低。使用报告前已有记忆作基线，区分信息有无新增、是否更可验证、是否改变后续帮助；防止为了追求“新增记忆数”制造重复命题。

## 4. 对实施与评审负担的修正

- 共享一份背景摘要是合理工程边界；让财务全部等待报告理解闭环不是必要条件。
- P2a 工程候选可先交付，但不能取代 P2b 的用户效果验证；未做盲评时如实写“效果待验证”。
- 实施者负责测试、隔离数据、入口验证和评估材料。东林关注产品价值、偏好评审和必要真机反馈，避免所有工程验收都卡在东林身上。
- 32 个场景、预算专项和已有项目验收规范共同决定放行，不以“拆阶段”减免原门槛。
