## 2. 认可信号：HoloEndorsementService（S2）

### 2.1 为什么不新写控制逻辑

确认 / 否定已经有三套服务，各自带幂等、撤销、墓碑与 CloudKit 镜像：

| 服务 | 粒度 | 文件 | 记忆中心何时用 |
|---|---|---|---|
| `HoloKnowledgeControlService` | 命题（propositionID + 语义指纹） | `Services/AI/Knowledge/HoloKnowledgeControlService.swift` | "等你确认"、已记住列表里的知识条目（`performKnowledge`） |
| `HoloMemoryUserControlService` | 记录（recordID + 内容版本） | `Services/AI/MemoryRepository/HoloMemoryUserControl*.swift` | 详情页里的确认 / 过时 / 停用 / 恢复（`perform`） |
| `HoloMemoryFeedbackService` | 记录 | `Services/AI/HoloMemoryFeedbackService.swift` | 旧反馈入口 |

**HoloEndorsementService 只做两件事：① 把"来自某个入口的用户动作"翻译成"对哪条记录 / 哪个命题做什么"；② 调用上面已有的服务。** 它不写任何新的决策、墓碑或幂等逻辑。

### 2.2 契约

新文件：`Services/AI/Endorsement/HoloEndorsementService.swift`（新目录；`Holo/` 是同步文件夹，自动入工程，不碰 pbxproj）。

```swift
/// 用户认可信号的来源入口（只用于日志与幂等 operationID 前缀）

protocol HoloEndorsing: Sendable {
```

### 2.3 路由规则

| 目标 | 动作 | 落到哪 |
|---|---|---|
| `.proposition` | confirm / reject / correct | `HoloKnowledgeControlService.apply`，action 映射：confirm→`.confirm`；reject→`.markInaccurate(reason:, scope:)`（scope 取记忆中心"不对"按钮当前使用的值 **[S0 核实]**）；correct→`.correct` |
| `.record` | confirm / reject / correct | 先推导 propositionID（§2.4）：命中已有命题 → 按 `.proposition` 走；未命中 → `HoloMemoryUserControlService.apply`（confirm→`.confirm`；reject→`.markInaccurate`；correct→`.correct`） |
| `.record` / `.report` / `.replayCard` | markValued / unmarkValued | 写记录上的 `userValueSignals`（§3），**不调用控制服务**（收藏不是决策） |
| `.report` | confirm / reject | **不允许**（返回 `.notAllowed("reportLevelDecision")`），整份报告不能被一键判对错 |
| `.replayCard` | confirm / reject | 用 lineage 找到该卡产生的记录（§2.5），逐条按 `.record` 走 |
| `.portraitKey` | 任意 | S5 前：①照旧更新 PortraitStore（保持现有界面行为）；②找到该画像条目同步过去的知识库记录（anchor value = `portrait_<key>`，见 `HoloPortraitSynthesisRuntime.makeMemoryRecord`），存在则按 `.record` 走；不存在且动作为 confirm → 先用 `makeMemoryRecord` 的同一翻译写入一条（**不受 `understandingPromotionV1` 限制**——用户亲手确认的东西不需要灰度保护），再 confirm |

撤销（undo）**不经过本服务**：记忆中心已有的撤销回执机制不变。聊天"这次参考了"条不提供撤销，用户去记忆中心改。

### 2.4 记录 → 命题的推导 **[S0 核实]**

命题 ID 由语义决定：`HoloKnowledgeIdentity.propositionID(for: semantic)`（`Models/AI/HoloKnowledgeContract.swift:629`），语义由 `HoloKnowledgeIngestion` 从记录推导（`Services/AI/Knowledge/HoloKnowledgeIngestion.swift` 内 `assessment.propositionID` 的生成路径）。执行模型要：

1. 找到 ingestion 里"记录 → semantic"的函数，确认它是纯函数（不读库）。
2. 在 `HoloEndorsementService` 里复用它，不复制逻辑。
3. 推导出的 propositionID 用 `resolvedKnowledge(propositionID:now:)`（`Services/AI/Knowledge/HoloKnowledgeRepository+CoreData.swift:372`）确认存在；不存在 → 走记录层。

### 2.5 按 lineage 找记录

报告与回放卡产出的记录，证据 `lineageKey` 格式已固定：

| 来源 | lineageKey 格式 | 生成位置 |
|---|---|---|
| 深度分析 / 回放（新链路） | `report-evidence:<canonicalReportID>:<evidenceID>` | `HoloReportFindingExtractor.swift:118-120` |
| 回放卡证据 ID | `insight:<insightID>:<cardID>:ev<n>` | `HoloReportSourceAdapter.replayDescriptor` |

因此：

- 报告收藏 → 前缀 `report-evidence:analysis-<messageID>:`
- 回放卡 → 前缀 `report-evidence:replay-<insightID>:insight:<insightID>:<cardID>:`

新增仓库方法（`CoreDataHoloMemoryRepository`，参照已有的 `deleteRecordsDerived(fromThoughtIDs:)` L630 写法）：

```swift
/// 返回证据 lineageKey 以任一前缀开头的、未删除的记录（只读）
func recordIDs(withLineagePrefixes prefixes: [String]) async throws -> [String]
```

实现：在 `HoloMemoryEvidenceMO` 上 `lineageKey BEGINSWITH %@`（该属性已建索引）+ `deletedAt == nil`，取 `recordID` 去重；再过滤掉记录本身已删除的。

### 2.6 收藏的补拆

收藏时若 `recordIDs(withLineagePrefixes:)` 为空，并且报告理解台账里这份报告不是终态（`HoloReportUnderstandingCoordinator.sharedLedger`，**[S0 核实]** 查询接口名）：

1. 从 `ChatMessage.agentResultJSON` 解码出 `HoloRenderedAgentResult`（解码方式参照 `ChatViewModel.encodeAgentResult` 的逆操作，**[S0 核实]**）。
2. 调 `HoloReportSourceAdapter.analysisDescriptor(messageID:rendered:)` + `HoloReportUnderstandingCoordinator.process(descriptor:evidence:)`。
3. 再查一次 lineage，命中则打关心标记；仍为空返回 `.nothingToApply`（界面照常显示"已收藏"，不报错——收藏本身已经成功）。

补拆受 `reportUnderstandingExtractionEnabled` 与 `longTermMemoryWriteEnabled` 约束（S1 开启后为真；用户关了自动记忆就不补拆）。

## 3. 关心标记：HoloMemoryUserValueSignal

### 3.1 存储

在 `Models/AI/HoloMemoryRecord.swift` 的 `HoloMemoryRecord` 上加一个 Optional 字段（随 `recordData` blob 存，**不改 Core Data schema**）：

```swift
/// 用户「关心」信号（收藏等）。不是决策：不改变 userDecision / 证据数 / 水位。
var userValueSignals: [HoloMemoryUserValueSignal]?

nonisolated struct HoloMemoryUserValueSignal: Codable, Equatable, Sendable {
    enum Kind: String, Codable, Sendable { case favoritedReport }
    var kind: Kind
    /// 来源对象（canonicalReportID），用于取消收藏时精确撤销
    var sourceID: String
    var createdAt: Date
}
```

要求：

- `HoloMemoryRecord` 若有自定义 `init(from:)` / `CodingKeys`，必须同步加键并用 `decodeIfPresent`；`validate()` 不校验此字段。**[S0 核实]** 记录的编解码方式。
- 写入用 `replaceRecordForUserControl`（`CoreDataHoloMemoryRepository.swift:565`），**不**抬 `recordVersion`、**不**改 `updatedAt` 以外的字段——避免被当成内容修订触发重新确认。若 `replaceRecordForUserControl` 强制抬版本，改为新增一个窄方法 `updateUserValueSignals(id:signals:)`，只改 blob 内这个字段。
- 同一 `sourceID` 只保留一条（幂等）；取消收藏删除该 `sourceID` 的条目，数组空了置 nil。

**多设备旧版本风险**：旧版 App 解码时会忽略这个键，若旧版又写回这条记录，字段会丢失。影响仅为"关心"效果消失，不影响正确性；在 05 列为已知限制，不做兼容代码。

### 3.2 效果落点

| 效果 | 改哪里 | 规则 |
|---|---|---|
| 排序加分 | `HoloMemoryRelevanceRanker.score`（`Services/AI/HoloMemoryContextEnvelope.swift:43`），以及统一查询服务里实际决定排序的打分处 **[S0 核实：`HoloMemoryQueryService` 用的是哪个打分器]** | `userValueSignals` 非空 → 在原分数上 +1（与"高置信 3 / 中 2 / 低 1"同量级，只能在同等相关时决胜，不能让无关条目挤进来） |
| 不随时间淡出 | `HoloMemoryScorer` 的新鲜度计算（`Services/AI/MemoryCore/HoloMemoryScorer.swift`） | 新鲜度下限 0.6（**[S0 核实]** 当前淡出阈值，下限须高于"不再注入"的阈值） |
| 优先进"等你确认" | 记忆中心 ViewModel 的待确认排序 | 见 02 §4.3 排序规则 |

### 5.2 数据结构

```swift
nonisolated enum TrendMetric: String, Codable, Sendable, CaseIterable {
    case sleepHours, bedtimeMinutes, lateSleepRatio        // 睡眠
    case steps, activeMinutes, workoutCount, standHours    // 活动
    case restingHeartRate, hrv                             // 身体指标
    case weeklySpend                                       // 消费总额
    case categorySpend                                     // 分类消费（带 subject）
    case habitCompletions, habitNumericAverage             // 习惯（带 subject）
    case tasksCompleted                                    // 任务（tasksOverdue 口径不清，v1 不做，见 06 R7）
}

/// 一周一格。weekStart = 该周周一 00:00（Calendar 用 zh_CN、firstWeekday=2）
nonisolated struct TrendWeekCell: Codable, Equatable, Sendable {
    var weekStart: Date
    var value: Double?        // 周均值（日均类）或周合计（次数/金额类）；无数据为 nil
    var daysWithData: Int     // 本周有数据的天数 0-7
}

nonisolated struct TrendSeries: Codable, Equatable, Sendable {
    var metric: TrendMetric
    var subject: String?      // 分类名 / 习惯名；总量类为 nil
    var unit: String          // "小时" "分钟" "步" "次" "元" "bpm" "ms"
    var weeks: [TrendWeekCell] // 按时间升序，最多 66 格（同比需要 52+13=65 周，见 06 R5）
}

nonisolated enum TrendComparison: String, Codable, Sendable {
    case recentVsBaseline     // 近4周 vs 之前12周
    case yearOverYear         // 近13周 vs 去年同期13周
}

nonisolated struct TrendFinding: Codable, Equatable, Sendable, Identifiable {
    var id: String            // "\(metric)|\(subject ?? "-")|\(comparison)" —— 稳定，便于连续周计数
    var metric: TrendMetric
    var subject: String?
    var domain: String        // "health" | "finance" | "habit" | "task"
    var comparison: TrendComparison
    var recentValue: Double
    var baselineValue: Double
    var changeRatio: Double   // (recent - baseline) / baseline；入睡时刻类用分钟差，见 5.3
    var consecutiveWeeks: Int // 同方向连续周数
    var coverageNote: String? // 有缺失时的说明
    var sentence: String      // 最终给 AI 的一句话（≤60 字）
    var magnitudeScore: Double// 用于排序
    var firstSeenAt: Date     // 首次出现时间（短期→长期提名用）
}

nonisolated struct TrendDigestSnapshot: Codable, Equatable, Sendable {
    var schemaVersion: Int    // = 1
    var computedAt: Date
    var series: [TrendSeries]
    var findings: [TrendFinding]
    var dataGapNotes: [String]// 例如「近4周有12天没有睡眠记录」
}
```

### 5.3 结论规则（v1 数值，集中放在 `HoloTrendFindingRules.Policy` 常量里，便于调）

**窗口**（以"本周之前的完整周"为终点，本周未过完不参与）：

- recent = 最近 4 个完整周；baseline = recent 之前的 12 个完整周。
- yoy：recent13 = 最近 13 个完整周；lastYear13 = 往前 52 周对应的 13 周。

**覆盖门槛**（不满足 → 不出结论，必要时出缺口说明）：

| 指标类 | recent 窗口最少有数据天数 | baseline 窗口最少有数据天数 |
|---|---|---|
| 健康日均类（睡眠、步数、活动、站立、心率、HRV） | 16 / 28 | 48 / 84 |
| 次数 / 金额类（运动、消费、习惯、任务） | 窗口内该指标至少出现过 1 次记录 **或** 用户在该窗口有任意记账/打卡行为（证明在用 App） | 同左 |

**显著性门槛**（满足任一即算显著）：

| 指标 | 门槛 |
|---|---|
| sleepHours | 差值 ≥ 0.5 小时 |
| bedtimeMinutes | 差值 ≥ 30 分钟 |
| lateSleepRatio | 差值 ≥ 0.25 |
| steps / activeMinutes / standHours | 相对变化 ≥ 20% |
| workoutCount | 4 周合计差 ≥ 3 次 且 相对变化 ≥ 30% |
| restingHeartRate | 差值 ≥ 4 bpm |
| hrv | 相对变化 ≥ 15% |
| weeklySpend | 相对变化 ≥ 25% 且 绝对差 ≥ 周均 100 元 |
| categorySpend（只看 baseline 或 recent 中周均前 5 的分类） | 相对变化 ≥ 40% 且 绝对差 ≥ 周均 50 元 |
| habitCompletions | 4 周折算差 ≥ 3 次 且 相对变化 ≥ 30% |
| habitNumericAverage | 相对变化 ≥ 15% |
| tasksCompleted | 相对变化 ≥ 40% 且 4 周折算差 ≥ 4 个 |

**持续性门槛**：recent 的 4 个周里至少 3 个周与 baseline 均值同方向偏离。yoy 不要求持续性，但 recent13 与 lastYear13 各自覆盖都要 ≥ 50%。

**连续周数**：从最近一周往回数，连续多少周与 baseline 同方向偏离；跨日计算时复用上次快照里同 `id` 的 `firstSeenAt`（新出现则 = now）。

**排序分 `magnitudeScore`**：`|changeRatio| / 该指标显著门槛`（时刻类用分钟差 / 30），再 × 1.2（若 consecutiveWeeks ≥ 6）。

**句子模板**（只允许下面这些句式，禁止拼接原因词）：

| 情况 | 模板 |
|---|---|
| 日均类 recentVsBaseline | `{域名}｜近4周{指标名}约 {recent}{单位}，比之前3个月{多/少}约 {变化}{；连续N周偏{高/低}}{（有数据 a/b 天）}` |
| 入睡时刻 | `睡眠｜近4周平均入睡 {HH:mm}，比之前3个月{晚/早}约 {分钟} 分钟{；连续N周偏晚}` |
| 次数 / 金额 | `{域名}｜「{subject}」近4周{合计/周均} {recent}{单位}，之前3个月平均每4周 {baseline}{单位}` |
| yoy | `{域名}｜和去年同期比，{指标名}{多/少}约 {变化}` |
| 缺口说明 | `数据｜近4周有 {n} 天没有{睡眠/步数}记录，{睡眠/活动}相关结论仅供参考` |

数字格式：百分比取整到 5%（"约三成"由模型自行转述，不在模板里写中文数字）；金额取整到 10 元；时刻用 `DateFormatter`（`zh_CN`，`HH:mm`）。

**域内上限**：每个域最多 3 条结论；全局 findings 最多 12 条（存储用），注入时再按 §5.5 挑。

### 5.4 数据源口径（复用 `HoloLifeFeatureDistiller` 的过滤规则，不另立口径）

| 数据 | 取数 | 过滤 |
|---|---|---|
| 睡眠 | `HealthRepository.fetchSleepDetailRange(from:to:)` | 按醒来日归日；无 bedtime 的天不参与入睡时刻；**入睡时刻求均值必须先转成 `HoloLifeFeatureDistiller.bedtimeMinutesSince1800`（以 18:00 为零点），求均值后再用 `formatBedtime` 转回**，防止跨午夜算错（06 R6） |
| 步数 / 活动 / 站立 | `fetchStepsRange` / `fetchActiveMinutesRange` / `fetchStandTimeRange` | value == 0 视为无数据（未佩戴），与 distiller 口径一致 **[S0 核实]** |
| 运动次数 | 现有 workout 查询 **[S0 核实]** 接口；没有区间接口则 v1 不做此指标 | — |
| 静息心率 / HRV | `fetchVitalsRange(from:to:)` | nil 不计 |
| 消费 | 记账仓库按时间区间取支出 | 排除转账；排除代办/报销（复用 `HoloLifeFeatureDistiller.isProxyOrOrganization` 的规则，若是 private 则提升为 `static` internal 并在实施记录写明）；**排除默认午夜补账不影响金额类**（只影响时段，这里不看时段） |
| 习惯 | 习惯打卡记录 | 只看当前活跃习惯；负向习惯（戒烟类）方向语义相反——结论句里"多/少"照实写，不写"好/坏" |
| 任务 | 待办完成时间 | 已删除不计 |

取数窗口：**近 462 天（66 周）**。数据量：健康类约 460 天 × 6 指标，查询一次约数百毫秒级；放 `.utility` 后台、20 小时节流，不阻塞启动（遵守 Repository `init()` 零 I/O、启动"默认值先渲染"规则）。

### 5.5 聊天注入

`TrendDigestContextSection.chatBlock(_ context: UserContext)`：

- 前置条件：`HoloAIFeatureFlags.memorySummaryInjectionEnabled` 且 `HoloAIDataProcessingConsent.shared.isGranted`；否则 nil。
- 数据：`UserContext` 新增 `var trendDigest: TrendDigestSnapshot? = nil`（Optional + 默认值，不破坏现有初始化调用）；由 `UserContextBuilder.buildContext` 从 `HoloTrendDigestStore.loadCached()` 读（只读缓存，不现算）。
- 挑选：
  1. 按 userText 关键词命中域优先（词表放 section 内常量：睡/觉/困/熬夜/失眠→health.sleep；走/步/运动/锻炼/健身/累→health.activity；心率/心跳/压力→health.vitals；花/钱/消费/支出/买→finance；习惯/打卡/坚持/戒→habit；任务/待办/拖延/效率→task）。**词表只用于排序，不用于判断用户状态**。
  2. 其余按 `magnitudeScore` 降序。
  3. 取前 8 条，总字数 ≤ 600，超出从尾部丢。
  4. `dataGapNotes` 只附与已选结论同域的，最多 2 条。
- 块格式：

```
--- 长期趋势（程序按你的记录计算，和你自己过去比） ---
- {sentence}
- ...
使用规则：这些是程序算出的变化，不是原因。只在与当前话题相关时引用；不要据此推断病因、性格或动机；有「仅供参考」说明的要一并说明数据不全。
```

- 意图识别上下文：`intentBlock` 返回 nil（意图识别不需要趋势）。
- 注册：追加到 `AIContextSectionRegistry.sections` 末尾（预算裁剪优先级 `priority` 设为最大值档，最先被裁）。

**后端 prompt 无需改动**：聊天上下文是 iOS 拼好的 system 文本，后端透传。但人格规范要求"改 prompt 前先读 `docs/standards/PROMPT_GUIDELINES.md`"——本块的"使用规则"文案属于 prompt 文本，执行模型必须先读该规范核对用词（尤其健康安全边界），有冲突以规范为准并回报。

### 5.6 与已有"近期趋势"块的关系

`AIUserContextMessageBuilder` 里已有"--- 近期趋势 ---"（本周支出、本周习惯完成率等，`:51-70`）。v1 **保留不动**：它是"本周"，新块是"近 4 周 / 近一年"，不冲突。命名上新块叫"长期趋势"以示区分。

## 6. 存储收口（S5，吸收 11-20 方案 P4）

目标：PortraitStore 不再是独立真源，降为画像合成过程的缓存；所有读写走知识库。

| 步骤 | 内容 |
|---|---|
| 写 | `HoloPortraitSynthesisRuntime.promoteToMemoryIfEnabled` 去掉 `UnderstandingPromotion.isEnabled` 门（改为只受 `longTermMemoryWriteEnabled` 约束），每轮合成的 upsert 全部进知识库；`retireKeys` → 对应记录 `markOutdated` |
| 迁移 | 一次性迁移（版本号存 UserDefaults `holo_portraitMigrationVersion`）：PortraitStore 现有条目 → `makeMemoryRecord` 写知识库；`isUserConfirmed == true` → 再 confirm；`rejected` 列表 → 写墓碑（anchor = `portrait_<key>`，复用 `HoloMemoryFeedbackService.suppressWithTombstone` 的同构写法）。迁移幂等，失败下次启动重试，PortraitStore 文件**保留不删** |
| 反向防复活 | 画像合成请求里"已否决黑名单"改为从知识库墓碑（anchor 前缀 `portrait_`）读取，不再只读本机 PortraitStore 的 rejected |
