# 主流方案对比与Holo现状适配审查

日期：2026-10-28。对象：融合方案v3.1及当前工作区代码。结论已回写推荐方案v3.2；本轮只审查、运行隔离兼容性探针与改文档，没有实施业务改造。

本文件保留v3.2审查依据；最终实施入口为[08-v3.3最终交接](08-最终实施方案与GLM交接.md)，最新反例及诊断证据见[09最终审查](09-最终对抗性审查与问题闭环.md)。

后续已将五项难点分解为[06解决路径与交付门槛](06-五个困难点的解决路径与交付门槛.md)，并核实后端已有共享成本守卫、来源失效守卫存在局部断点；均已回写v3.2实施要求，未修改业务代码。

## 1. 产品结论

**方向符合Holo，原定首版范围偏重，若按v3.1全部捆绑开工，会增加兼容和交付风险。**

Holo需要的是可靠地理解已经记录的生活，并在问答、规划中帮上忙。来源追溯、具体用途、统一用户控制、实时读取原模块都符合这个目标。现有代码已具备相当一部分知识与检索底座，应修齐和复用，而非重新做一套通用agent记忆基础设施。

当前最难的不是接入向量检索，而是：如何从有噪声的多域历史中形成有用且受证据支持的命题；如何让旧客户端不绕过新限制；以及如何保证来源变化后各消费入口不再使用旧理解。

首版建议完成A/B/C1，再对该范围做D发布验收。大型证据分片、通用长会话压缩、新会话级同步排除、全新句子级引用协议分开推进。后续目标仍保留，不以未开放或全拒绝来冒充已经完成。

## 2. 与代表性主流路径的区别

这里比较已查阅的一手机制，不声称所有产品都采用同一种实现，也不进行未经实测的优劣排名。每条Holo取舍是设计判断。

| 维度 | 一手资料中的代表性机制 | Holo的区别与收益 | Holo承担的代价 |
|---|---|---|---|
| 会话与长期信息 | LangGraph区分thread状态/checkpoint与跨会话namespace/store。[官方文档](https://docs.langchain.com/oss/python/concepts/memory) | 同样分层，但长期理解必须关联财务、任务、习惯等业务事实；不能靠会话摘要维护实时进度 | 接入多个原模块的状态与事件，不是只管理聊天文本 |
| 信息读取 | Anthropic提倡轻量引用、即时取资料和渐进展开。[官方文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) | 基本一致；Holo还要在读取前判断本次用途、权限、语义修订和明确约束 | 来源服务与资格判定要一致；不能为了“按需”每次全库扫描 |
| 持久记忆组织 | Letta当前SDK以版本化仓库和MemFS区分常驻信息与按需读取。[官方文档](https://docs.letta.com/agent-sdk/memory) | Holo使用既有Core Data和CloudKit，便于关联业务实体；行为归纳持续使用前要求用户确认 | 要处理移动端、离线和多设备，不能直接照搬agent自由修改文件的写入权威 |
| 来源与时效 | Zep将事实关联到源episode，并记录有效时间；官方也强调来源不保证事实正确。[来源结构](https://help.getzep.com/graph-overview)、[事实时间](https://help.getzep.com/facts) | Holo这部分与其相近，并非独有创新；进一步把用途、用户纠正和输出版本接入产品 | 证据、语义、授权、使用记录要分别处理，测试比单纯检索更多 |
| 自动形成 | 记忆框架允许应用选择即时或后台写入，具体权威规则由应用决定。[LangGraph](https://docs.langchain.com/oss/python/concepts/memory) | 明确表达可以及时保存，行为推断成熟后才确认；适合用户需要归因的生活数据 | 确认带来延迟；所以只展示少量有用归纳，跳过后仍能做原始事实分析 |
| 适用场景 | 上述文档提供通用agent/框架或服务机制 | Holo是带明确事实归属的生活记录产品，单次流水与精确查询仍属于原模块 | 领域语义不能全部交给通用记忆SDK自动决定 |

因此，Holo方案的差异主要是**业务事实归属、用户可核对、用途与控制、移动端数据约束**。它不是比主流方案多加几个记忆层就更先进，而是用额外约束换取适合自身场景的可信度。

## 4. 实施难度与真正的阻塞

难度为相对工程判断，未据此承诺具体工期。

| 项目 | 难度 | 原因 | 降低风险的做法 |
|---|---|---|---|
| 单条来源和统一详情 | 中 | 多种sourceKey/实体/软删和预览路径不一致 | 共同类型化定位器；先测裸UUID、前缀、定义/打卡、对话与原模块状态谓词 |
| 同一投影、分页、停止错误署名 | 中 | 多入口已并存，但改动范围相对明确 | 复用现有中心与来源组件；只移除假署名，保留模型显式引用与明确不足 |
| 具体用途与命题收敛 | 高 | 程序不能仅凭字段存在判断“有用”，同主题并非同命题 | 双端Prompt加程序结构约束；固定正反例、改写和未见实体盲评，保留用户控制 |
| 规律证据供给 | 高 | 要正确计算机会、缺失、时间窗与反例，不能只调阈值 | 完成实际支持的模板；八域来源同标准，不支持的规律不假装成熟 |
| 历史兼容、迁移与多设备限制 | 很高 | 旧客户端已在读写，CloudKit同步不能由新客户端单方改规则 | 首版优先既有控制语义；新增范围控制等能力要先有可证明兼容策略 |
| 版本化使用与所有消费接线 | 高 | 同一个结论经过多个摘要/请求协议，旧引用没有当时版本 | 适配现有规划依据与普通聊天标记；新输出固定版本，旧历史诚实标未保存 |
| 大型证据分片与通用压缩 | 高且收益待证 | 会新增同步、仓库、provider窗口和工具链复杂度 | 延后，不成为来源可信和首个使用闭环的前置条件 |
| 性能、后台与总成本 | 中至高 | 现有全量读取，后台机会与多条AI通道的预算不同 | 先测当前调用量/解码量/耗时，核验命中项，复用调度，不增加独立反思任务 |

### 4.1 隔离兼容性探针：已经复现

本轮从当前`HoloKnowledgeContract.swift`提取操作枚举、反例状态枚举与证据快照声明，以最小依赖替身编译，检验格式边界。替身仅补证据引用和ID计算的类型依赖，不参与被测枚举/未知字段行为；不是完整App集成测试。

探针文件：`/private/tmp/holo-memory-v31-compatibility-probe.swift`。

运行：

```sh
xcrun swiftc -parse-as-library -module-cache-path /private/tmp/holo-memory-v31-compatibility-modules /private/tmp/holo-memory-v31-compatibility-probe.swift -o /private/tmp/holo-memory-v31-compatibility-probe
/private/tmp/holo-memory-v31-compatibility-probe
```

结果：

```text
operation evidenceManifestChunk: decode rejected
operation sessionMemoryExclusion: decode rejected
future manifest preserved after decode/encode: false
```

仓库`knowledgeStoreSnapshot`对无法解码操作逐行跳过；因此新增的会话排除操作可能完全不进入当前解析器。原字节未必已经从存储删除，但当前类型回写也不保证保留未来字段。此结果不代表真实库已经发生数据损坏，代表“不改物理表就能安全升级”的假设不成立。

### 4.2 历史不可恢复的边界

现有引用经常只存ID、短摘要或聚合摘要，没有完整旧原文/成员值。编辑后的原模块不能自动还原过去；迁移也不能补造历史版本。

新记忆按新契约记录，旧记忆分成当时片段、当前来源、无法还原。新回答固定当时修订；旧回答只有ID时标历史版本缺失。用户重新确认形成的是当前新依据，不回填为过去已经确认。

### 4.3 同步与隐私不能只靠命名保证

相关设备尚未理解新控制语义时，单方写新操作无法让旧端尊重它；不能承诺新客户端可直接把其他旧客户端变只读。需要全端可验证的兼容策略，否则维持已知协议并不开放新限制功能。

本机敏感记忆容器只约束那部分数据。普通业务主容器配置CloudKit，消息和规划结果有现有保存链路；新引用正文若塞进普通消息JSON，就可能进入其同步范围。新增敏感证据/使用片段留本机，外部模型处理和聊天全文仍按各自授权核对；不能宣称整个健康聊天始终不出设备。

## 5. v3.2已作的范围修正

1. 保留本地知识仓库，统一门面作为现有检索/规划/资格的薄适配层，避免平行框架。
2. A/B/C1先交付可核对、有用、可使用的完整路径；八域来源和用户控制同一标准，自动规律按成熟模板开放。
3. 大型清单分片不预定写进操作表，首版用有界完整证据和原模块分页核验；不完整就如实限制。
4. 通用自动压缩、新SessionDigest仓库、新会话同步排除和逐句引用协议放C2，分别验证再开放。
5. 引用从新输出开始固定版本；普通聊天先复用显式ID，规划复用已有逐项依据；完整草案用`contextPlanJSON`。
6. 修正总预算和性能假设：先登记多通道的实际调用/tokens与全量读取成本；不添加独立后台反思任务，也不将100ms写成已经实现。
7. 区分记忆敏感分区、模型外发与聊天结果保存，不将新敏感证据写入普通同步消息元数据。

## 6. 首版最小但完整的验收路径

**路径一：明确约束改变实际规划。** 用户明确表达一个持续约束 → 来源可核对、保存/修改可见 → 从已有情境规划生成不同安排 → 展示原有planEffects/逐项依据与固定版本 → 改变约束后新方案不继续沿用旧值。普通聊天能回查回答级标注明确记忆，失败与未引用阶段如实区分。

**路径二：多条记录形成可靠理解。** 用有充分时间窗、机会分母和反例覆盖的隔离正例 → 实际供给模板所需证据 → 形成少量有用途候选 → 用户确认准确命题 → 相关聊天/规划/发现可以引用 → 来源变更或否定后各入口一致收敛。搭配相近但不成立的反例，不能全拒绝或只跑已构造的最易样本。

这两条贯通样本不缩小其他领域的权限/来源要求；至少八域来源、全局开关、原模块查询和用户控制都有正反样本。首版不承诺全面自动发现所有生活规律。

每批发布范围列出已开放、未开放、未执行的验收项；后续能力不能算绿灯，也不阻止与其无关且已安全验收的单点修复交付。涉及数据资格、迁移或新自动写入的批次，兼容/控制门槛不能豁免。
