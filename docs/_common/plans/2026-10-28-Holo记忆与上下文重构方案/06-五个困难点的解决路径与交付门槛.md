# 五个困难点的解决路径与交付门槛

日期：2026-10-28。对v3.2的实施补充，逐项回答“困难是否能解决”。本轮只核代码、复算失效守卫真值并改文档；没有修业务代码或执行真实迁移/部署。

最后修订已收敛到[v3.3最终实施交接](08-最终实施方案与GLM交接.md)。本文件保留解释；身份/纠正、有效快照、复核并发、遗忘清除、事务和敏感使用存储按08冻结，新增具体反例见09。

## 0. 结论

五项都有可执行的处理路径：语义质量通过分工与评测逐步提高；兼容、失效与成本控制落实到具体边界；旧历史缺失只能补建现有来源能够支持的部分，无法恢复从未保存过的原文或版本。

不再增加一套平行架构，不用更大模型或新增云记忆服务替代这些工作。沿用A/B/C1与各批发布门槛，以下措施进入对应工单，而非只把难点列成风险。

## 1. 从碎片形成有用理解：模型提出，程序核证，任务检验

### 实施办法

1. **来源先规范化**：八域都提供真实主体、关系、时间、源修订与原文/程序事实；普通流水保持来源身份，AI输出不产生新的独立事件。
2. **模型只提出候选**：明确陈述及其条件、支持片段、反例和具体用途；可以返回无候选。希望、实际行为、阶段变化和个人解释分别表达，不凑一份人格画像。
3. **程序负责可验证部分**：核引用确实存在、原话匹配、数值/单位/分母、独立事件去重、时窗/覆盖和授权。补齐现有桥接的nil覆盖与验证周期供给；未检索过反例不能说未发现反例。
4. **按命题收敛**：先用已有实体/语义检索缩小相近候选；相同语义只更新证据，条件或时间不同则保留区别/产生新修订。不确定是否同一命题时不自动合并，主题层可一起展示。
5. **作用具体化**：候选必须说明触发哪类任务、预期影响何种选择。明确原话及时保存；行为归纳成熟后只请用户确认少量准确命题。无需用户认证算术，也不要求每天清候选。
6. **离线评测验证收益**：复用固定80条语义样本和20个任务对照，加入改写、未见实体及相近反例。无需每轮在线生成两份答案做“价值检测”，避免增加延迟和费用。

### 可以达到什么

可以明显减少流水复读、错误合并、数字编造和无用途候选，并保留重要单次经历。不能用程序完全证明自由语言理解总是正确；语义精度与帮助程度仍按固定评测、真实任务和用户纠错检验。

### 交付门槛

普通流水反例不能误入，明确保存/重要经历/合格规律正例必须能产出；同主题不同关系不丢失。至少一条理解能改变实际规划，并能在被纠正后改变后续结果。对应B与现有B组、G03–G07及任务对照验收。

## 2. 旧客户端与多设备：先兼容桥接，再启用新语义

### 实施办法

**第一步：明确可用协议，而非只看表结构。** 冻结当前14类操作、语义/证据载荷、控制代际与旧记录镜像的共同协议；区分能读、能写、能执行控制。未知字段可选并不等于可以丢弃。

**第二步：桥接版本先修读取边界。** 仓库读取返回可用、不可理解和损坏项，以及受影响的命题/控制范围；保存原始字节。无法理解的控制不能静默跳过后继续认定该命题可用。当前MO已存命题ID，可在整条操作解码失败时仍定位受影响范围。

**第三步：减少重写。** 不可变修订与操作保持追加；旧计数等局部更新只修改明确字段，不能用较旧类型重编码整条未来载荷。遇到语义可能受未知字段影响的项，保留只读并限制使用，不作推断性改写。验证未来字段decode/encode和实际仓库写入两层。

**第四步：优先使用共同控制语义。** 能用已有disable/forget等操作表达的决定，沿用相同限制与必要旧别名镜像。不能表达的会话级排除等新语义，等相关读写端具备能力后才开放，不用一个新客户端的开关假装控制所有旧设备。

**第五步：验证升级与同步顺序。** 至少覆盖新旧端交错、两端离线分别修改、旧确认晚到、恢复未见过限制、重试与恢复备份。当前设备立即生效，其他离线设备在收到限制前不能承诺即时停止；恢复同步先收敛限制再消费。

后端已有后台请求最低build守卫，可作为旧后台调用限制的一部分；它不覆盖所有本机读取和普通聊天，不能当作已经具备全设备协议隔离。相关端能力无法确认时不开放新语义，原始生活记录继续按现有兼容规则工作。

### 可以达到什么

可以避免新字段被新实现继续抹掉、未知控制被静默忽略、晚到旧决定复活内容。无法远程修改一份从未升级的离线旧程序；这是需通过兼容协议与功能开放条件处理的实际边界。

### 交付门槛

真实仓库必须保留未来字段/未知原字节，识别受影响范围并限制授权，再跑新旧客户端读写。旧enum无需认识一切未来操作；小探针暴露其边界，不能仅追求把decode rejected改成recognized。纠正、停用、遗忘和恢复均不能因同步回退。涉及新载荷/新写入的批次必须先通过，不能留到最后D才补；对应F02/F03/F04、E04/E08和原99场景。

## 3. 多入口一致与来源失效：统一出口、规范化依赖、请求版本核验

### 实施办法

1. **统一资格出口**：在现有仓库/Resolver与检索上做薄适配，向消费者返回准确语义、来源状态、允许用途和版本。聊天、Agent、分析、回放、规划、发现、管理逐一登记接线；萃取去重池的all读取不当作消费入口。
2. **统一来源身份**：SourceKey规范化服务同时供产生者、路由、核验和失效通知使用。不能一处用裸UUID、一处用thought:UUID，或把habit-checkin与Habit定义混为同一实体。
3. **可重建的依赖映射**：source+revision → 受支持命题/语义修订 → 引用它的请求和输出。来源变化只重核受影响项；剩余支持足够可继续使用，独立用户纠正不连坐删除。
4. **请求携带版本**：组装时固定来源修订、语义修订和控制代际；提交及呈现/执行前检查受影响版本。输出中发生控制变化时停止失效部分并给出更新状态；已显示内容作为历史，不继续成为下一轮有效背景。
5. **通知负责调度，读取边界负责核实**：来源事件去重、合并和增量重核；当远端通知无法给出具体来源时，用持久历史或当前来源核验找受影响集合。避免每次同步就全库写一轮unknown。请求仍对命中项与适用硬约束做有界核验，不只相信事件一定送达。

### 当前代码的两个具体接缝

`HoloKnowledgeInvalidationService.handleRemoteChange`传入空来源集合与`conservative=true`。当前`applyInvalidation`第157行条件为：

```swift
guard !conservative || !(revisedRefs.isEmpty && deletedRefs.isEmpty) else { return }
```

布尔真值复算：远端变更、仅Habit定义变化这两类输入均提前返回；已知task来源变更可继续。本轮没有运行完整App或真实同步，这证明的是该局部条件与调用输入的断点。

另外，HabitRecord通知构造habit/habitEvent键，而个人情境来源可使用habit-checkin键；部分想法来源仍为裸UUID。按未经规范化的字符串精确匹配依赖，可能漏掉命题。

**修复目标**：保守变更可以进入重核调度；无任何变化的普通事件才直接结束。修好这个条件还要验证规范化来源键、增量合并和命中项核验，不能仅反转一行guard后给所有记忆反复全量降级，就宣称问题解决。

### 交付门槛

同一来源的修改/删除、撤权与用户纠正，在所有实际消费入口上结果一致；覆盖生成进行中、原文更新、远端变更与通知重复。新回答绑定当时版本；规划复用contextPlanJSON，不扩大轻运行信封。对应A/E组、C08、D06、G02与原失效/并发场景。

## 4. 历史不能完整还原：分级补建，保留映射，不伪造过去

| 历史状况 | 处理 | 用户看到的状态 |
|---|---|---|
| 有当时片段/修订，现有证据可验证 | 保留原始时间与依据；补展示与正确路由 | 当时保留的依据及当前变化 |
| 原来源仍存在，但缺过去快照 | 用当前来源重核，产生当前新证据快照；不补造过去字段 | 当前来源支持；历史版本未保存 |
| 原来源不可核对，只有旧摘要/确认标记 | 留历史待核，不当当前事实；在影响任务时允许用户重新表达或核对 | 来源暂不可核验；新确认按当前时间记录 |
| 已否定、停用、遗忘或来源撤权 | 先导入限制，再做其他补建；阻止同义复活 | 对应控制状态，保留合规的最小阻断 |

只要原始生活记录还在，就能按当前证据重新整理出更有用的理解；这是当前重建，不是恢复旧回答当时的依据。新旧命题/证据通过别名和处理收据关联，不能重复计算独立事件。

按Store/分区/旧ID/修订/策略分批处理，提交成功才推进；重复运行幂等。迁移前在隔离副本给出分类、原项到新项映射和保留/分流/不足/失败分母，再按已有授权推进真实库。保留原始业务数据和用户控制，不按句式或条数配额删除。

### 交付门槛

二次迁移不重复产生理解；中断可恢复；确认和限制不丢；每个旧项都能解释去了哪里。没有保存过的原文和历史统计明确标缺失。对应F01/F04、G05/G07及分层30条对账。

## 5. 性能和成本：复用已有守卫，测量后做有界读取与增量任务

### 实施办法

1. **先量真实开销**：记录一次问答的两分区fetch/解码量、知识快照读取量、来源查询数、候选/选入数、网络调用和tokens；区分冷/热缓存、端侧与远端耗时。用隔离真实规模与合成大库验证，不先承诺100ms全链路。
2. **查询有界**：复用40候选/最多8条预算；共用控制与资格快照，按命中来源重核。适用的明确硬约束独立检查，不能为提速丢失。根据实测使用按命题/来源的查询与可重建索引，减少每次反复解码全库。
3. **缓存按版本**：来源修订、语义修订和访问/控制代际参与缓存键；变化精准失效。不能只凭“缓存还没过几分钟”继续输出已撤权资料。列表分页和分组计算复用已有优化。
4. **整理只处理变化**：按source+revision去重、合并短时间变更、控制每批字符与任务量，失败/未提交不错误推进游标；跨域、报告与发现避免对同一输入反复生成。后台按系统机会运行，前台有界续跑，不新增独立全库反思任务。
5. **复用后端共享成本守卫**：`HoloBackend/src/usage/backgroundCostGuard.js`已包含个人情境提取/验证、领域记忆、跨域、发现、回放等purpose，具备成本预留、结算、输入/输出限制及日/月/全局额度；`app.js`已创建守卫并包装provider、接入口检查。后续应核每条真实调用路径和部署配置，不另造一套记账系统。
6. **端侧与服务端预算分工**：端侧10次是领域调度次数限制；服务端成本守卫按真实输入/输出用量核账，两者不是同一指标。预算主体当前有购买身份与设备回退，不能笼统承诺所有设备都按同一账户归并。核覆盖、并发预留和限额响应，再按现有后台任务公平性调参数。

### 可以达到什么

可以把多数日常操作限制在相关资料范围，减少重复生成并对后台支出设置明确上限。速度、缓存收益和额度是否合理必须测量；源码有成本守卫不等于所有生产路由已经生效，也不保证外部模型永不延迟。

### 交付门槛

现有预算下能完成合格正例，后台队列不会让某个域长期饿死；低电/高热不抢前台；重复来源不重复付费；所有相关purpose和provider真实经过预留与结算，超限时有明确状态。对应F05–F07、C06/C07与成本核账。

## 6. 执行顺序

1. **A先做共同来源与控制读取、路由/预览和失效断点修复**；同时建立当前可复跑基线与消费清单。
2. **新增载荷/自动写入前过兼容桥接**；B同步生成端防碎片、用途准入、实际统计供给与隔离迁移，不能只抬门槛。
3. **C1贯通聊天/规划/发现的实际使用与纠正**；性能、后台覆盖和成本测量随实现同步完成，D对实际发布范围验收。
4. 后续复杂能力按需求证据开放，不拿它们阻塞已安全完成的单点修复，也不把未开放项算通过。

本文件不增加一组新的测试数量目标。56项补充与原99场景继续使用，新增具体断点作为已有场景的必含输入；业务改造完成后必须附实际执行证据。本次没有修改或部署后端，B的Prompt及任何预算接线变更仍需双端契约验证和后端发版。
