## 〇·一、开工实测（2026-11-20，P0 第一步）

**重大发现：C 方案新引擎从 11-07 起从未在生产运行。** `config.js` 的 `loadConfig()` 没有并入 `DEFAULT_CONFIG.deepReportEngine`，运行时总闸恒为 `undefined`，`resolveRoutedTaskType` 永远返回 `deep_analysis`。证据：① 生产容器内用线上配置调用路由函数，返回 `deep_analysis`；② 近 45 天 `ai_call_logs` 中 `cloud_deep_report_*` 为 0 条，旧引擎 `cloud_deep_analysis` 有 111 条；③ `agent_cloud_analysis_tasks` 只有 `deep_analysis` 类型。当时漏掉的原因：单测手动传入配置，绕过了 `loadConfig`；上线核验只看了 env。

## 一、结论先行（产品语言）

**Holo 已经很会「算」，也开始会「记」；但负责「讲」的深度分析，几乎看不到 Holo 记住的东西。**

- 深度分析报告的写作模型，只拿到两样东西：程序算好的数字清单 + 用户手写的档案。Holo 画像里的五个维度、用户确认过的规律、想法原话、目标的初衷，**一样都没进去**。
- 而且 prompt 明令「不要主动添加跨域联想或原因猜测」「用户没说过的动机不去猜」。这两条当初是为了压事实错误（3.5→1.06/份，有效），代价是报告只能写成「数字很准、但谁都能写」的样子。
- 「懂我」的感觉主要来自三类内容：**用户自己的话**、**言行之间的落差**、**跟过去的自己比**。目前前两样在深度分析里结构上不可能出现，第三样只覆盖到数字层面。

因此本方案不另造引擎。做的是：**把已有的理解层接进深度分析，再加一层有依据的解读**，同时把三套各管各的「理解存储」收成一套。

### 2.1 深度分析看不到理解层（含一个实锤断链）

| 现象 | 证据 |
|---|---|

| 想法只上传「每天几条」，没有内容 | `factComputator.js` L507 `thought.daily` 计数；事实清单自己写「内容不在数据里，原因不能判断」 |

| 写作档位天花板 | C 方案六轮评测：root_cause 3.44-3.94、warmth 3.56-3.75，结论是「qwen-flash 表达上限」 |

### 2.2 三套理解存储各管各

| 存储 | 生产者 | 同步/防复活 | 谁在读 |
|---|---|---|---|
| 统一知识库（Core Data `HoloMemoryKnowledgeRevision`） | 记忆萃取、一个发现确认、理解引擎晋升 | ✅ CloudKit + 墓碑 + 准入 | 记忆中心、聊天 envelope、深度分析快照（但后端没读） |
| PortraitStore（本机 JSON，`UnderstandingShadowRunner.storageDirectory()`） | `portrait_synthesis` 每 72h 一轮；一个发现 v4 反馈回写 | ❌ 单机、无 CloudKit；黑名单仅本机 | 聊天注入、一个发现 v4 候选 |
| 理解引擎影子台账（水位 + 三标记） | `UnderstandingShadowRunner` | 晋升走知识库，**M3 最后一公里未通**（交接文档 11-17） | 无正式消费方 |

后果是同一个人在聊天、一个发现、深度分析里，Holo「认识」的版本不一样。用户在一处纠正过，另外两处未必知道。PortraitStore 桥接知识库还受服务端开关 `understandingPromotionV1` 控制。

### 2.3 已有、可以直接复用的能力

- 事实清单 + 双道核对 + 保守删句（深度分析 C 方案）：解读层要靠它兜住事实准确。
- 水位政策 `SufficiencyPolicy`（命题类型 × 自述轨/行为轨）：决定一条理解够不够格被引用。
- 画像三态置信度 + 黑名单（`HoloPortraitSynthesisModels.swift`）、一个发现 v4 的「准/不准/放一放」反馈。
- 想法语义检索（`HoloContextSemanticSearchRuntime` / `ThoughtEmbeddingStore`）和 AI 可见过滤 `ThoughtAIAudience.aiVisibleOnly`。
- 目标跨模块绑定（`GoalPlanContract` / `GoalMetricEvaluator`）：「说过想做 X」和「实际做了多少 X」的对应关系已经存在。
- 补问协调器 `HoloMemoryClarificationCoordinator`。
- 评测脚手架：`scripts/discovery-insight-eval.js`、C 方案实验 harness、M1 合成数据集。

## 三、「懂我」的判定标准（先定尺子）

沿用一个发现 v4 的及格线思路，扩成深度分析的评分维度。每份报告由盲审打 1-5 分：

| 维度 | 问的问题 | 反例 |
|---|---|---|
| **K1 换人测试** ⭐ | 把这段话套到另一个用户身上还成立吗？成立 = 不懂我 | 「注意劳逸结合」「支出有所上升」 |
| **K2 原话回应** | 有没有接住用户自己说过的话（想法、目标初衷、档案） | 全文只有数字 |
| **K3 言行对照** | 有没有指出「说的」和「做的」之间的一致或落差，且有依据 | 只讲做了什么 |
| **K4 纵深** | 有没有跟用户自己的过去比，包括「上次出现这种情况是什么时候、怎么走出来的」 | 只比上期 |
| **K5 解释力** | 对最大那件事给出可能的「为什么」，标明推测，并且排除过至少一个替代解释 | 只描述现象，或武断归因 |
| **K6 克制** | 一个核心发现 + 一个开放问题；不说教、不诊断、不贴标签 | 罗列七八条建议 |

硬底线不变：事实错误 ≤ C 方案现状（≈1.2/份）。安全边界以 PROMPT_GUIDELINES 为准。

**主指标**：K1 + K2 + K3 均分（「懂我分」）。现状基线要在 P0 实测。按 2.1 的结构推断，K2、K3 在现状下应接近 1 分。

## 五、分期实施

### P0 · 「懂我」评测集与基线（先做，约 1 天）

**做什么**
1. 在 C 方案实验 harness 上加 K1-K6 打分 rubric。盲审评审员换家，沿用 deepseek-v4-pro。每格采样 2 次以降低噪声，这是 C 方案吃过的亏。
2. 样本：东林真实快照 4 题（数据留在 `~/Desktop/holo-deep-analysis-exp-*`，不进仓库），加 M1 合成数据集里 4 个人设。每个人设都要预埋可被发现的「言行落差」和「原话」，用来检验 K2/K3 能不能被触发。
3. 跑现状基线，落 `…/01-基线打分.md`。
4. **成本基线**：从 ECS `ai_call_logs` 拉最近 30 天 `cloud_deep_report_*` 的 `usage`（已逐调用落库），统计单份报告的输入/输出/缓存命中 token 和调用次数的 p50/p90，作为 §九 的真实分母。评测集每份也记录 token。

**验收**：基线表出炉。之后 P1-P3 每一步都用同一套样本对比，凭体感说「更懂了」不算数。

### P1 · 接通理解层（约 2 天，双端）⭐ 最快见效

**做什么**
1. **修断链（后端）**：`writerUserContent()` 拼入 `confirmedKnowledgeBrief`；checker 输入同步带上，避免引用被误判为「无依据」。
2. **新增 `understandingBrief` 快照字段（iOS）**，内容依次为：
   - 画像条目：confirmed 全量 + inferred 中与问题相关的 Top 8（复用 `HoloPortraitContextInjector` 的打分），带「已确认/推测」角标；
   - 活跃目标：标题 + `desiredOutcome`（用户写的初衷）；
   - **问题相关原话**：在 AI 可见的想法里语义检索 Top 6，每句 ≤80 字，带「N 天前」。这一项需要东林拍板（见决策 D1）。
3. **写作规则放宽（后端 prompt，双端同步 PromptManager）**：
   - 删掉默认写法 5 的「不要主动添加跨域联想或原因猜测」；改为「**一句有依据的解读**」（D2）：全文只允许 **1 句**核心解读，单独成段，以「我的理解：」开头。只能基于 ① 事实清单里明确的「一起变化」，② 理解简报条目，③ 原话；必须带「可能/像是」，并在句末用编号标出依据（如 `[F012][S003][Q2]`，mapper 会剥掉编号转成来源标识）。其余段落仍按原规则只描述事实。程序校验：「我的理解：」段 >1 个，或缺依据编号 → 进修复轮。
   - 底线 3 改为「用户没说过、简报里也没有的情绪和动机不去猜」。用户亲口说过的可以呼应。
   - 新增「接住原话」：报告中最多引用 1-2 句原话，必须逐字照抄。
   - 结尾在「数据说明」之前加一个开放问题，作为 K6 的载体。
4. **引用核对（后端程序）**：报告里出现引号的原话，必须是 `understandingBrief` 原话的逐字子串，否则进修复轮。复用 `numberCheck.js` 的删句预算。
5. **来源标识（D2，双端）**：
   - 简报里每一项都带来源域。事实清单 F 编号已有数据集名，可以映射到域；原话 Q 编号 = 想法；画像条目沿用 `sourceDomains`。
   - mapper 给每个 claim 新增可选字段 `sourceDomains: ["thought","finance",…]`，取值由程序按依据编号推导，不由模型自己填，避免模型乱标。「我的理解」段额外标记 `isInterpretation: true`。
   - iOS `AgentDeepReportView`：「我的理解」段用独立卡片样式，上方一行标识「Holo 的理解 · 参考了：想法、财务」，用模块图标 + 中文名，样式取自设计规范现有 chip。普通段落如果引用了原话，段尾加一个弱化的「引自你的想法」。
   - 旧版 App 解码时忽略新字段，「我的理解」段按普通段落显示，内容不变。所以要么后端按 App 版本号决定是否输出这一段，要么接受旧版没有标识。**推荐前者**：旧版本不出解读句，满足「必须明确标识」的要求。

**涉及文件**：`HoloCloudAnalysisSnapshotBuilder.swift`、`HoloPortraitContextInjector.swift`（抽出打分函数复用）、`deepReport/engine.js`、`deepReport/mapper.js`、新 `deepReport/quoteCheck.js`、`defaultPrompts.json`（writer/checker 升版本）、`PromptManager.swift`、`HoloCloudAnalysisService.swift`（CloudResult 解码新增可选字段）、`AgentDeepReportView`（标识 UI）、iOS 契约测试 `DeepReportResultContractTests` 补字段。

**验收**：P0 评测集上 K2 ≥ 3.0；事实错误不劣于基线 +0.2；引用核对零漏放；来源标识与依据编号 100% 一致（程序断言）；**单份成本增幅 ≤ §九 预算**。后端发版走 `holo-backend-deploy`，用 env 开关灰度到东林设备。

### P2 · 自述层 + 言行对照（约 3 天，以 iOS 为主）

这是「直击灵魂」最强的来源：**程序负责对齐，模型负责解释**。

**做什么**
1. **`SelfNarrativeBuilder`（纯函数，iOS）**：汇总用户「说过想要什么」：
   - 目标初衷（`desiredOutcome`）及其绑定的习惯/预算/任务（已有 `GoalPlanContract`）；
   - 习惯本身，自建习惯即意图，复用水位体系「打卡 = 自证」的结论；
   - 档案里的自我介绍；
   - 想法中的意图句：复用已有 `personal_context_extraction` 的「明确表达」快速路径产物，不新开模型调用。
2. **`SayDoLedgerBuilder`（纯函数，iOS）**：对每条能对齐到可测数据的意图，计算：
   - 执行率：本期 vs 用户自己的历史；
   - **在什么条件下掉链子**：按星期、任务逾期日、晚睡日、高支出日分组，看执行率的差异。复用 `CrossDomainCheckupLedgerBuilder` 的对齐口径，门槛沿用对齐 ≥10 天；
   - 输出成带编号的事实段（S001…），与 F 编号并列，进入数字白名单。
3. 后端 `factComputator` 原样采用 `sayDoLedger` 文本段，与 `financeEvidenceLedger` 同模式，不重算以避免口径漂移。
4. writer 规则：「言行对照」只能引用 S 编号的事实，落差写成「观察」，不写成「你没做到」（PROMPT_GUIDELINES 禁止审判语气）。

**验收**：K3 ≥ 3.0；合成人设里预埋的落差召回 ≥ 3/4；「审判语气」盲审命中 0。

### P3 · 竞争解释：并进 writer，不加调用（约 1.5 天，后端）

> v2 修订：原设计单独加一次 `interpreter` 调用，成本 +20% 左右。按 D3（思考升一档）+ 成本约束，改为**在 writer 一次调用内完成**。

**做什么**
1. writer 路由 `HOLO_DEEP_REPORT_WRITER_REASONING_EFFORT` 从 `medium` 升到 `high`（D3）。只升**首次写作**这一次；修复轮（`cloud_deep_report_repair`，目前共用 writer 路由）新拆一个路由，保持 `medium`，因为修复只是改句子，不需要深想。checker 保持 `medium`。
2. writer 输出格式在正文前加一个机器块（程序剥离，不展示）：
   ```
   <plan>{"focus":"F012","hypotheses":[{"claim":"…","refs":["F012","S003","Q2"],"against":["F020"],"verdict":"supported|weak|ruledOut"}]}</plan>
   ```
   控制在 ≤300 字，本身就是 high 档思考的落地形式。
3. **程序校验**：refs 必须存在；`supported` 至少 2 条独立来源（沿用水位规则，同源不重复计数）。「我的理解」句的依据编号必须 ⊆ 某个 `supported` 假设的 refs；不满足就把这一句删掉，改成末尾的开放问题。降级要保守，不再额外调模型。
4. 「我的理解」句可以带半句排除式表达，比如「不太像是…，更像是…」，仍算 1 句。
5. 发版前用 `scripts/latency-benchmark.js` 实测 high 档耗时（CLAUDE.md 要求）。p50 门槛放宽到 **300s**（D3 已同意）。

**验收**：K5 ≥ 3.8（C 方案 root_cause 五轮均值 3.7）；p50 ≤ 300s；调用次数不变；**单份成本增幅（P1+P3 合计）≤ §九 预算**。

### P4 · 理解存储收口（约 4 天，iOS，依赖 M3 最后一公里先修通）

**做什么**
1. 先按 11-17 交接文档修通 M3 断点（候选 A/B 拉库实证）。这是收口的前置条件。
2. PortraitStore 条目整体走 `applyObservationBatch` 进统一知识库。知识修订记录新增两个可选属性 `counterEvidenceSummary` 和 `lastTestedAt`，Core Data 轻量迁移，遵守 AGENTS.md CloudKit 红线：先改开发库 schema，只增不改。
3. 黑名单并入知识库墓碑，跨设备生效。
4. 读侧统一：聊天注入、一个发现 v4、深度分析 `understandingBrief` 都改读知识库 resolver。PortraitStore 降为合成过程的临时缓存。
5. `portrait_synthesis` 输入新增「待验证的推测 + 最近反例」，让每轮合成优先**证实或推翻**已有推测，而不是从零开始。

**验收**：同一条纠正在三处入口和第二台设备上一致停用；双设备同步无冲突；`run-understanding-standalone.sh` 全绿 + 新增迁移测试。

### P5 · 时间纵深：人生章节（约 2 天）

**做什么**
1. 复用 `HoloReplayDigestService` / `replay_digest_consolidation` 的周期摘要，按月沉淀为「章节」：状态标签、主要变化、当时用户说过的话（引用 ID）。本机存储，走知识库。
2. `SayDoLedger` / factComputator 增加「相似时期」事实：当前组合信号（如晚睡 + 习惯中断 + 支出上升）在历史章节里出现过的月份，以及那次是怎么恢复的。
3. writer 可以写「上次出现这种情况是 X 月，那时你…」，前提是有章节引用。

**验收**：K4 ≥ 3.5；相似时期误配率人工抽检 ≤ 1/10。

### P6 · 闭环：段落反馈 + 末问回答（约 2 天，iOS）

**做什么**
1. 报告每个解读段提供「说中了 / 不太对」两个轻按钮，映射到对应的知识条目：说中了 → confirm 或加强；不太对 → 降级并记反例，多次不太对就进墓碑。复用一个发现 v4 的 `DiscoveryInsightFeedbackBridge` 语义。
2. 报告末尾的开放问题可以直接回复，回答走 `HoloMemoryClarificationCoordinator`，作为自述轨证据入库（水位：自述一次即足）。
3. 埋点：`deep_report_paragraph_feedback`、`deep_report_question_answered`，沿用自建埋点。

**验收**：真机走查闭环。下一份报告能引用上一份末问的回答。

## 九、成本预算（东林约束：费用不能明显上升）

### 9.1 现状基线（待 P0 实测替换）

C 方案记录：单份报告约 **4.1 次调用、约 6 万 token**。按 config 默认单价（输入 ¥3 / 输出 ¥9 / 缓存 ¥0.1 每百万 token，**是代码默认值，线上实际单价未核对**）粗估，约 **¥0.2-0.3/份**。P0 用 `ai_call_logs` 真实 usage 替换这个数。

### 9.2 各项改动的增量估算

| 改动 | 增量来源 | 估算 | 控制手段 |
|---|---|---|---|
| P1 理解简报 + 原话 | 简报进入 writer、修复轮、checker 的输入 | 简报 ≤1500 token × 约 3 次 ≈ +4.5k 输入（+约 8% token，费用 +约 5%） | 硬上限：画像 ≤8 条、原话 ≤6 句 ×80 字、目标 ≤4 个；超限按相关度截断。修复轮沿用原 messages 前缀，命中缓存时按 ¥0.1 计 |
| P2 言行对照 | 事实清单变长 | S 编号段 ≤800 token × 约 3 次 ≈ +2.4k 输入（费用 +约 3%） | 只输出 ≤5 条意图、每条 ≤2 行 |
| P3 写作思考 medium→high | 首写一次的思考 token 增加 | 预计首写输出 +50%~100%，约 +2k-4k 输出（费用 +约 8%-15%，**最大单项，需实测**） | 只升首写，修复轮和 checker 不升；`<plan>` 块 ≤300 字；`maxTokens` 不变 |
| ~~P3 单独解读调用~~ | — | 原本 +约 20%，**已取消** | 并进 writer |
| P5 章节事实 | 事实清单变长 | ≤400 token（+约 2%） | 只给最相似的 1 个时期 |
| P6 反馈闭环 | 本机写回，不调模型 | 0 | — |

**合计预估：+约 15%-25%/份**，绝对值约每份多几分钱。

### 9.3 预算闸（写进代码，不靠自觉）

1. **上限**：P0-P3 全部开启后，单份报告平均费用增幅 **≤ +25%**（以 P0 实测基线为分母）；p90 增幅 ≤ +35%。
2. **评测期**：P1、P3 各自的评测都要报告「K 分提升 / 成本增幅」。如果 high 档带来的 K5 提升 < 0.2 分而成本 > +10%，就回退到 medium，env 改一行即可。
3. **运行期自动降级**：后端在组装 writer 输入时估算 token，超过「基线 p90 × 1.35」就按顺序丢弃：章节事实 → 推测态画像 → 原话降到 3 句。日志记 `DEEP_REPORT_BRIEF_TRIMMED`。
4. **观测**：`/admin` AI 指标页按 purpose 已有用量统计；上线首周每天看 `cloud_deep_report_*` 的单份 token 均值，超线就关 env 开关回旧版写作（免发版）。
5. 深度分析本身受会员额度约束，次数不会因为这次改动变多；改动只影响单份成本。

### 9.4 顺带的降本机会（可选，不影响效果）

- 修复轮从 writer 路由拆出后保持 medium，比现状不变，还为以后降到 low 留了余地。
- 检查 provider 是否支持前缀缓存：修复轮的 messages 和首写前缀完全一致，命中后输入费用接近 0（¥0.1/百万）。P0 顺便从 usage 里的 cached 字段核实。
