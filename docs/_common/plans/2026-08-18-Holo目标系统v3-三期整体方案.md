# Holo 目标系统 v3 —— 三期整体方案

> 日期：2026-08-18
> 状态：方案设计完成，待东林评审后动工
> 前置：目标系统 v2 已上线（2026-08-14，commit a1be4260），本方案是 v2 的延续

## 0. 背景与三个已拍板的决策

v2 之后目标模块与任务/习惯的打通已较深（数据双向关联、进度自动汇总、页面双向可见、AI 可读可写），剩余缺口与本期规划一一对应：

| 缺口 | 归属 |
|---|---|
| 手动关联/解除无 UI 入口，只有 AI 一条腿 | 一期 |
| 习惯没有「关联到目标」的 AI 意图（任务有） | 一期 |
| 多目标歧义只有文本反问，无选择卡 | 一期 |
| 「主动提醒」只影响 AI 话术，不落系统通知 | 二期 |
| 不支持量化型目标（跑 300km / 存 5 万 / 减到 70kg） | 三期 |

**2026-08-18 东林拍板的三个决策（三期量化目标的定调）：**

1. **数据自动来**：存钱目标自动读账本、健身目标自动读体重习惯——本方案将其抽象为「数据源」概念（见 §3.1）。
2. **累积型与达标型都做**（「攒到多少」和「降到/达到多少」）。
3. **与数值习惯打通**：数值习惯作为目标的数据源，自动累计。

## 1. 全局架构：三期怎么分工

```
一期（地基收尾）        二期（主动触达）         三期（能力升维）
──────────────         ──────────────          ──────────────
```

- 三期内部再分两批：3a 手动源（模型+UI+进度）、3b 自动源（习惯+账本+AI）。

### F1.2 任务/习惯详情页的归属栏可编辑

现状：`TaskDetailView.swift:1251` 的 `goalRow` 注释明确「只读，由目标模块设置」；`HabitDetailView` 头部只展示目标标题。

改造：归属栏整体可点 → 弹**单选目标 sheet**（活跃目标列表 + 「无归属」项），选中即 link，选「无归属」即 unlink。与 F1.1 是同一套仓库方法，仅交互方向相反（从条目侧找目标）。

### F1.3 AI 意图：link_habit_to_goal

镜像现有 `link_task_to_goal` 六步清单（后端 `HoloBackend/src/prompts/intents.json` 是单一事实源，iOS 侧 `IntentDescriptor.swift` 程序化生成不可手改）：

1. `intents.json` 加 `link_habit_to_goal`（requiredFields: `["habitName","goalTitle"]` + few-shot 例句）
2. 跑 `node scripts/generate-intent-descriptors.mjs` 重新生成 iOS `IntentDescriptor.swift`（过 `intent-registry-consistency.test.js` 对拍护栏）
3. `AIModels.swift` `AIIntent` 加 `case linkHabitToGoal` + `chatDisplayLabel`
4. `ChatCardData.swift` 卡片映射 switch 加 case
5. `IntentRouter.route()` 加 case + `handleLinkHabitToGoal`（镜像 `handleLinkTaskToGoal`，习惯侧匹配 `HabitRepository` 活跃未归档习惯；落库调已存在的 `GoalRepository.linkHabit`）
6. `ConversationCoordinator.shouldRouteToDeepAgent` 的 `executionIntents` 集合加入，防止被 Agent 分流

**⚠️ 此项需要后端发版**（intents.json 变更）。客户端可先行合入——意图未上前 AI 链路对该意图无感知，不影响其他功能。

### F1.4 多目标歧义：结构化选择卡

现状：`IntentRouter.matchGoal` 命中多个活跃目标时返回 `.ambiguous`，走 `goalDisambiguationResult` 纯文本反问。v2 备注的「pending 卡片由 ConversationCoordinator 处理」实际未做。

改造（新 pendingKind，复用现有 pending 卡状态机）：
- ConversationCoordinator 在 `linkTaskToGoal/linkHabitToGoal`（以及 `update_goal_field`）路由前预判 `matchGoal == .ambiguous`：不执行，往 renderData 写 `pendingKind: "goalChoice"` + 候选 goalId/标题列表，item 以 `.skipped` 进 `AIExecutionItem`。
- 卡片 UI 在现有「确认/取消」两态卡基础上新增候选行按钮（N 选 1）。
- 用户点选后：把选中 `goalId` 注入 extractedData 重放 `IntentRouter.route` —— `matchGoal` 第一级就是 `goalId` 精确匹配，天然闭环，无需新匹配逻辑。
- ChatViewModel 侧复用 `confirmPendingTask` 的 `pending → confirming → confirmed/failed/cancelled` 状态机与 `persistConfirmationStatus` 落库防重。

## 3. 三期（核心）：量化型目标

> 先写三期再写二期，因为三期是本轮的产品主体；二期见 §4。

### 3.1 核心抽象：目标类型 × 数据源

东林决策的抽象提炼——**量化目标 = 「类型 × 数据源」矩阵**：

**两种类型**（回答「进度怎么算」）：

| 类型 | 语义 | 进度公式 | 例 |
|---|---|---|---|
| 累积型 cumulative | 从 0 往目标攒 | Σ(起始日以来的记录值) ÷ 目标值 | 跑 300km、存 5 万、读 24 本 |
| 达标型 target | 当前水平到达/降到目标值 | (基线−当前)÷(基线−目标)，方向由基线与目标大小自动决定 | 减重到 70kg、引体做到 15 个 |

**三种数据源**（回答「数字从哪来」）：

| 数据源 | 语义 | 例 |
|---|---|---|
| 手动 manual | 目标页/AI 对话记一笔，通用兜底 | 读书数「+1 本」 |
| 数值习惯 habit | 挂一个数值型习惯当数据源，自动读 | 跑量←「跑步」习惯；体重←「体重」习惯 |
| 账本 ledger | 财务流水自动算，零记录成本 | 存钱目标 |

关键发现（调研证实）：**习惯模块已有的 `HabitAggregationType` 与目标类型天然同构**——`sum`（计数类，当日累加）对应累积型，`latest`（测量类，取最新值）对应达标型。所以「打通数值习惯」不是硬接，是把两套已有的口径对上：

```
累积型 × 习惯(sum)    ：跑量目标 ← 跑步习惯记录从目标起始日求和
累积型 × 账本         ：存钱目标 ← 净结余(当前) − 净结余(目标创建日)
累积型 × 手动         ：读书目标 ← 手动记一笔笔累加
达标型 × 习惯(latest) ：体重目标 ← 体重习惯最新值 vs 目标值（基线=创建时快照）
达标型 × 手动         ：引体目标 ← 手动记当前水平
```

### 3.2 数据模型（Core Data 轻量迁移，全部新增可选字段，旧数据零影响）

`Goal` 新增字段：

```
goalKind       String   // "process"(默认，现有任务习惯型) / "cumulative" / "target"
metricUnit     String?  // km / kg / 元 / 本…
targetValue    Double   // 目标数字
baselineValue  Double?  // 达标型：创建时的基线快照（如当时体重 75kg）
baselineDate   Date?    // 累积型：累计起点（默认=目标创建日）
metricSource   String   // "manual" / "habit" / "ledger"
sourceHabitId  UUID?    // habit 源指向的数值习惯
ledgerScope    String?  // v1 固定 "all"（全账本），预留单账户口径
```

新增实体 `GoalMetricLog`（仅手动源使用；自动源不写任何中间记录）：

```
id / goalId / date / value: Double / note / createdAt
```

**单一事实来源原则**：Goal 不存 currentValue。进度每次展示时实时从源计算——习惯源读习惯记录、账本源读交易、手动源读 GoalMetricLog。源数据被删改，目标进度自动跟随，不存在双写同步问题。

### 3.3 进度计算与预测（新 GoalMetricEvaluator，与现有 GoalProgressEvaluator 并列）

| 格子 | 计算 | 现成依赖 |
|---|---|---|
| 累积×habit | `getDailyAggregatedData(for:)` 按日聚合后从 baselineDate 求和 | `HabitRepository.swift:885` |
| 累积×ledger | `getCumulativeBalance(now) − getCumulativeBalance(before: baselineDate)` | `FinanceRepository+Accounts.swift:191`，口径=全账本(未归档)期初+净流，与净资产页一致 |
| 累积×manual | GoalMetricLog 求和 | 新实体 |
| 达标×habit | `getLatestValue(for:)`（需补一个 before 参数版本，用于创建时取基线） | `HabitRepository.swift:619` |
| 达标×manual | GoalMetricLog 最新一条 | 新实体 |

**预测**（量化目标的灵魂，现有体系完全没有）：
- 累积型：日均速率 = 当前值 ÷ 已过天数；预计达成日 = 今天 + 剩余量 ÷ 速率。与 deadline 比较输出「按当前节奏预计 11 月 2 日达成 ✅ / 无法在截止前达成 ⚠️」。
- 达标型：日均速率 =（基线→最新记录）全程日均外推（口径与累积型统一）。原方案写「近 14 天变化率」，实施时改为全程口径：手动源记录稀疏，短窗口常凑不出可比的两个点；习惯源记录密时全程口径同样稳定，且两种源口径一致更可解释。
- 进度过半前的低速段预测波动大，进度 <10% 时只显示累计值不显示预测，避免打击用户。

### 3.4 UI

**创建/编辑（GoalEditForm 扩展）**：
- 顶部加「目标类型」三选：过程型（默认，现有形态不变）/ 累积型 / 达标型。
- 选量化后展开：目标值 + 单位输入 → 数据源三选（手动 / 选数值习惯 / 账本）。
  - 选习惯源：只列 `type == .numeric` 的活跃习惯；累积型建议 `sum` 型、达标型建议 `latest` 型，选错口径给行内提示不硬拦。
  - 选账本源：文案明示口径「按全账本净结余计算（含信用卡负债）」。
- 达标型创建时自动抓基线（习惯源取创建前最新记录，抓不到让用户手填一次）。

**详情页**：
- 量化目标头部换成**大数字进度区**：当前值/目标值 + 环形进度 + 预计达成行。
- manual 源显示「+ 记一笔」按钮；habit/ledger 源显示数据来源标签（「数据来自：跑步习惯 / 账本」），点击可跳源。
- 达标型显示「已减 2.5kg / 共 5kg」的基线视角文案，而不是从 0 开始的百分比。

**列表页**：量化目标行显示 `128/300 km` 数字进度替代六档状态文案；过程型目标保持现状。

### 3.5 AI 三件事

1. **读**：`UserContextBuilder.buildGoalContext` 注入量化字段（当前值、速率、预测结论）；`HoloDefaultGoalDataSource` 的 goal 工具快照加 metric 指标。受 `allowAIContext` 过滤，与现状一致。
2. **记**：新意图 `log_metric_value`——「今天跑了 5 公里」「体重 72.4」：
   - 挂了习惯源的目标 → 记到习惯（`addNumericRecord`），单一事实来源不破坏；
   - manual 源目标 → 记到 GoalMetricLog；
   - 现有 `handleRecordWeight`（`IntentRouter.swift:502`）就是这个模式的体重特例，通用化即可。
   - **⚠️ 需后端发版**（intents.json 新增意图，同 F1.3 链路）。
3. **答**：预测类问题（「照这个速度年底能跑完吗」）靠读到的预测结论即可回答，无需新链路。

### 3.6 三期内部分批

- **3a**：模型迁移 + GoalMetricEvaluator + GoalEditForm 类型/数据源 + 详情页大数字 + manual 源记录。（地基，先做）
- **3b**：habit 源 + ledger 源接入 + AI 读写 + 列表页/看板适配。

### 三期验收标准

- [ ] 建累积型目标「跑 300km」挂跑步习惯，习惯里记 5km，目标进度立即 +5，无需任何手动刷新口径。
- [ ] 建存钱目标 5 万，记一笔收入后目标进度变化正确；账本删除该笔交易后进度自动回退。
- [ ] 建达标型目标「减到 70kg」基线 75，记录 72.5 后显示「已减 2.5/5kg」。
- [ ] 对话说「今天跑了 5 公里」，AI 记录到正确目标并可撤销口径错误（后端意图上线后）。
- [ ] 全部旧目标显示为过程型，行为与升级前完全一致。

## 4. 二期：主动提醒落地系统通知

### F2.1 GoalNotificationService（新服务）

结构抄 `MemoryInsightNotificationService` 的「薄服务 + 开关 didSet 排程 + init 恢复」，深链抄 `TodoNotificationService`：

- 新 category `GOAL_RISK` 注册进 `TodoNotificationService.registerNotificationCategories()`（全 App 唯一 delegate，必须借道）；`didReceive` 的 category switch 加分支读 `userInfo["goalId"]` 跳 `.goalDetail`（深链通路现成，只差这一个分支）。

**排程策略（iOS 本地通知文案在排程时固定，不能触发时现算，所以核心是「重排时机」）**：
- 重排时机 = App 启动 + 前台任何 goal 写操作（create/update/delete/link/状态切换）后。每次重排按**当时**的数据生成文案并排具体时间点的通知（`UNCalendarNotificationTrigger` 一次性，同任务提醒模式）。
- 两类风险信号，判定逻辑从 `GoalAnalysisContextBuilder` 现有规则抽出复用：
  - **截止风险**：deadline ≤7 天且进度 <50%（量化目标则用预测结论「无法按期达成」）→ 排 deadline 前 3 天的上午 10 点提醒。
  - **停滞**：连续 14 天无关联行动完成且目标活跃 → 排次日上午 10 点一条。

**频率克制（硬约束）**：
- 同一目标同一类提醒 **7 天内不重复**（Goal 记 lastRiskNotifiedAt，或 UserDefaults 按 goalId+kind 记）。
- 每日全局上限 1 条目标提醒（多目标同日命中时取风险最高的）。
- 总开关直接复用 `Goal.proactiveNudge`（详情页 Toggle 已存在），语义从「AI 话术」升级为「AI 话术 + 系统提醒」；文案同步微调，让用户知道这个开关现在也管通知。

### 二期验收标准

- [ ] 制造「7 天后截止 + 进度 30%」的目标，收到一条提醒，点击直达目标详情。
- [ ] 14 天不打卡的活跃目标触发停滞提醒；同一目标 7 天内不重复收到。
- [ ] 关闭目标的「主动提醒」开关后不再收到该目标的任何通知。
- [ ] 开启通知权限被拒时静默降级（只在 AI 话术层生效），无报错。

## 5. 不做什么（明确排除）

- **不改首页结构**（v2 已拍板的原则延续）：量化目标不新增首页入口，走个人中心-目标列表。
- **不做数值习惯的隐式自动创建**：挂习惯源时只允许选已有习惯，找不到就让用户先建（避免隐式建出孤儿习惯）。
- **不做账本单账户口径**：v1 只做全账本净结余，`ledgerScope` 字段预留。
- **不做目标间依赖/子目标**：本期不碰。
- **想法↔目标打通**：v2 已明确跳过，维持。
