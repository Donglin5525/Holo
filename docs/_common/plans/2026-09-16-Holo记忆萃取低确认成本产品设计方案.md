- 状态：**第一性原理对抗性审查通过，待实施**

## 1. 产品结论

Holo 的记忆能力不应该成为一项需要用户每天维护的任务。

新方案不再把“AI 萃取出候选”直接等同于“用户需要确认”，而是让系统先完成证据校验、风险判断、限定表达、等待补证和无价值淘汰。只有某个尚未确认的信息正在影响用户眼前的回答、规划或高影响决策，而且系统无法从已有证据中消除歧义时，才向用户问一个最小问题。

用户最终感知应从：

> Holo 每天整理一批关于我的判断，让我逐条审批。

变为：

> 我正常使用 Holo，它会自动形成和更新对我的理解；偶尔在真正拿不准且会影响结果时，才问我一句。

本方案不是取消安全确认，而是重新分配判断责任：**系统承担证据判断，用户只处理不可替代的个人选择。**

## 2. 当前问题与根因

### 2.1 用户问题

当前体验存在四层成本：

1. **每天出现任务感**：记忆回执最多每 24 小时可再次展示，并带“待确认”“去确认”入口。
2. **存量反复出现**：界面统计的是当前全部 `candidate`，不是本次新产生、且此刻必须决定的事项。
3. **按类别粗切风险**：身份、人生节点、永久事实、假设、首次跨域等整类进入确认，没有继续判断这条内容是否已经被用户明确说过、是否有直接证据、是否真的会影响当前服务。
4. **确认对象过大**：用户被要求判断整条 AI 总结“对/不对”，而不是只补充真正缺失的变量。

这些机制会把记忆系统变成审批系统。即使单次只需几十秒，长期也会形成确认债务，最后用户选择不再处理。

### 2.2 当前实现的关键口径冲突

当前代码已经存在两层不同语义：

- `HoloMemoryRecord.state` 表示记忆生命周期，`candidate` 不天然等于必须确认；
- 通用个人情境还有 `admission = adviceEligible / confirmationOnly / forbidden`，其中 `candidate + adviceEligible` 明确允许作为限定建议背景，并且不应进入批量确认。

但统一收件箱和确认队列仍然只用 `state == candidate` 判断待确认，没有读取 personal-context admission。结果是“后台可限定使用的观察”可能重新出现在“想和你确认的”队列里。

因此根因不是缺少自动采用，而是四种概念混在了一起：

- 这条记忆处于什么生命周期；
- 是否有权把它保存为派生长期记忆；
- Holo 可以怎样使用它；
- 是否值得打扰用户。

### 2.3 为什么不能简单把所有 candidate 改成 active

直接批量激活虽然能消灭确认队列，但会带来新的严重问题：

- 推断可能被当成确定事实；
- 敏感或高影响内容可能污染回答；
- 反证、过期来源和未核验内容可能绕过现有政策；
- 自动记忆可能被误解为用户亲自确认；
- 个人情境 advice-only 的限定表达边界会丢失。

所以正确做法不是取消状态，而是建立更准确的决策层。

## 3. 产品目标与非目标

### 3.1 产品目标

1. **零日常审批**：取消每日批量确认作为默认产品路径。
2. **绝大多数自动处理**：通过校验的候选，至少 90% 在不要求用户操作的情况下被自动采用、限定使用、继续观察或丢弃。
3. **只问关键差异**：确认问题只针对会改变当前结果的未知点，不让用户审核 AI 总结全文。
4. **记忆可纠正、可遗忘、可追溯**：自动化不能牺牲用户控制权。
5. **记忆和行动分权**：记忆可以自动形成，但真实业务写入仍按行动风险单独授权。
6. **不增加前台等待**：记忆决策不得给聊天关键路径增加新的串行 AI 请求。

本方案的目标函数不是单独追求“自动处理率”，而是：

> 记忆净价值 = 个性化带来的结果改善 − 用户被打扰成本 − 静默误用损害 − 隐私代价 − 系统复杂度。

因此，只有同时满足“用户掌握系统无法获得的关键信息”“不同答案会实质改变眼前结果”“没有能保留主要价值的安全替代路径”时，询问才有正收益。其余不确定性由系统观察、限定使用或放弃。

### 3.2 非目标

本期不做：

- 不让模型凭自报的数值 confidence 决定是否生效；
- 不新增“自动/半自动/手动”复杂用户设置；
- 不要求用户训练词表、管理规则或定期清理候选；
- 不因为记忆自动采用而自动创建任务、改预算、改习惯目标或执行其他动作；
- 不新建图数据库或第二份记忆事实源；
- 不以删除全部旧候选作为迁移方案；
- 不把“方案完成”视为代码、真机或生产完成。

## 4. 核心产品原则

### 4.1 不确定不等于要问用户

系统发现不确定内容时，优先顺序为：

1. 从已有来源和反证自行核验；
2. 等待后续自然证据；
3. 限定表达，只用于低风险建议；
4. 没有价值则丢弃；
5. 只有眼前任务确实依赖它时才询问用户。

### 4.2 用户明确表达不应被二次审核，但“说过”不等于“同意长期保存”

以下内容不应再要求用户二次点击“对”：

- “请记住我周五不安排早会”；
- “我不吃香菜”；
- “我现在住在杭州”；
- 用户对旧记忆的主动纠正；
- 用户刚刚在当前对话中明确回答过的澄清问题。

系统需要保留“用户曾明确表达”的来源属性，但不能再机械重复确认。同时必须把两件事分开：

- **语义确认**：这句话确实是用户对自己的直接陈述；
- **持久化授权**：Holo 是否有权把它加工成长期记忆。

只有以下内容可以按用户明确表达自动成为长期记忆：

- 用户明确说“记住 / 以后请 / 以后不要 / 这是对旧记忆的纠正”；
- 普通非敏感陈述通过主体、语气、时间和范围校验，且“自动形成记忆”总开关已开启；
- 已获来源权限的结构化数据，只形成有时间边界的客观统计。

以下内容即使来自用户原文，也不能按“明确陈述”直接永久化：

- 假设、反问、否定、讽刺、引用或转述他人；
- “今晚 / 这次 / 最近”这类临时选择，却缺少对应有效期；
- 描述过去状态，却被改写成当前状态；
- 关于第三方的敏感信息；
- 用户只是谈论敏感事实，但没有明确要求 Holo 记住，且不存在覆盖该来源的清晰持久化授权。

敏感自由文本默认只留在原始来源和当前会话范围，不额外生成可长期召回的派生记忆；只有明确记忆请求或已经清晰说明范围的来源授权才可进入敏感记忆 Store。这样消除逐条确认，同时不把一次聊天等同于无限期存储同意。

### 4.3 类型不是风险代理

不能继续使用“身份 / 健康 / 人生事件 / 首次跨域”作为一刀切确认理由。

同一种内容可能有完全不同的确认策略：

- 用户明确说“我已经换工作”——可作为用户声明自动记住；
- 从两条模糊想法推断“用户已经换工作”——不能自动成为事实；
- HealthKit 显示最近 14 天平均睡眠减少——是有时间范围的客观统计；
- AI 由睡眠减少推断用户存在健康问题——应直接禁止，而不是交给用户批准。

### 4.4 记忆采用不等于行动授权

记忆的作用是帮助 Holo 理解和建议。它不能替代任务、财务、健康、日历等动作自己的授权政策。

例如：

- 可以自动记住“最近餐饮支出上升”；
- 可以在建议里说“从记录看，最近餐饮支出有所上升”；
- 不能因此自动降低预算或创建控制饮食任务；
- 真正写预算、建任务时仍走原来的草案、预览、确认和执行回执。

### 4.5 只询问“最小未知量”

错误问题：

> Holo 认为你工作日更适合早上运动，这条记忆对吗？

正确问题：

> 为了安排这周运动，你更希望放在早上还是晚上？

用户不需要理解内部的“记忆候选”，只需要回答与当前事项直接相关的问题。

## 5. 新的五路决策模型

每条通过基础结构校验的记忆候选，必须被统一决策器路由到以下五种结果之一。

| 结果 | 产品含义 | 是否使用 | 是否提醒用户 | 典型内容 |
|---|---|---|---|---|
| `factEligible` | 证据明确、边界清楚，可作为事实 | 可作为有来源的事实使用 | 不提醒 | 用户明确偏好、结构化客观状态 |
| `qualifiedAdvice` | 有依据但仍是有限推断 | 仅用于低风险建议，必须限定表达 | 不提醒 | “从近期记录看，可能更适合……” |
| `observeOnly` | 证据暂时不足，等待自然补证 | 不使用 | 不提醒 | 单次现象、尚未稳定的模式 |
| `askWhenRelevant` | 存在会改变当前结果的关键歧义 | 未回答前不作为事实使用 | 只在相关场景问一次 | 相互冲突的时间偏好、高影响推断 |
| `discard` | 无支持、无价值、越界或不可安全表达 | 不使用、不保存；仅可留不含正文的审计计数 | 不提醒 | 人格诊断、伪因果、无证据总结 |

### 5.1 四个独立治理维度

新方案不再让一个 `state` 同时承担所有语义，而是拆为四个维度：

1. **生命周期 `state`**：candidate / active / disputed / archived / suppressed / deleted；
2. **持久化权限 `persistencePermission`**：durable / sourceScoped / sessionOnly / blocked；
3. **使用权限 `useLevel`**：factEligible / qualifiedAdvice / observeOnly / blocked；
4. **打扰策略 `attentionPolicy`**：silent / askWhenRelevant / neverAsk。

核心约束：

- `candidate` 可以是 `qualifiedAdvice + silent`，绝不能因此进入待确认队列；
- 语义可信不自动授予 durable 权限，尤其是敏感自由文本和第三方信息；
- `askWhenRelevant` 只有在有当前使用上下文时才成立，后台没有“现在就必须问”的概念；
- `active` 也不等于用户亲自确认，必须保留 automatic / userConfirmed 来源；
- `sensitivity` 负责存储与隐私边界，不能继续单独决定是否打扰用户；
- `impact` 负责错误后果，和隐私敏感性分开判断。

真实业务动作授权是第五道、位于记忆系统之外的独立门；任何记忆状态都不能越过它。

## 6. 决策所需的四类输入

### 6.1 来源权威性 `sourceAuthority`

由程序从来源和证据类型计算，不由模型自行声称。

| 层级 | 定义 | 示例 |
|---|---|---|
| `explicitMemoryRequest` | 用户明确要求记住、忘记或纠正 | “请记住我不吃香菜” |
| `explicitUserStatement` | 用户直接陈述自身事实、偏好或安排 | “我周五一般不安排会议” |
| `structuredObservation` | 业务数据可以直接证明的有界事实 | 最近 14 天平均睡眠、预算执行率 |
| `repeatedIndependentEvidence` | 多时间窗或独立来源一致支持 | 多周稳定打卡节奏 |
| `modelInference` | AI 在多个事实之上形成的解释 | “可能更适合早上运动” |
| `unknown` | 来源无法确定或证据映射失败 | 旧数据、缺修订、缺引用 |

首版程序映射建议：

- 当前用户明确说“记住 / 以后请 / 以后不要”或来自澄清回答：`explicitMemoryRequest`；
- `explicitUserStatement` evidence、个人情境 `epistemicStatus == declared`：`explicitUserStatement`；
- aggregateSnapshot、业务对象状态、HealthKit 聚合：`structuredObservation`；
- 至少两个不同窗口或独立 lineage 支持同一稳定命题：`repeatedIndependentEvidence`；
- personal context inferred、cross-domain association/tension：`modelInference`；
- 缺 evidence kind、来源修订冲突或旧格式无法还原：`unknown`。

优先级从上到下不是简单覆盖：如果“用户明确陈述”包含假设、引用他人或条件句，仍必须由时间、主体和条件校验把命题限制在原文范围内，不能因为出现“我”就自动放行。

`explicitUserStatement` 的首版确定性门禁必须同时通过：

- 来源角色是当前用户，不是 assistant、示例文本或导入模板；
- 命题主体确实是用户本人，不是第三方；
- 不是引用、转述、假设、反问、否定或明显讽刺；
- 原始来源仍存在，revision 未变化，且可回到对应文本/业务对象；
- 时间、条件和适用范围没有被扩大；
- 临时回答默认采用最窄范围，不能自动推成永久偏好。

### 6.2 证据核验 `evidenceVerdict`

沿用已有离散结果，不新增模型数值置信度：

- `supported`：来源直接支持命题的主体、范围、时间和条件；
- `qualified`：大体支持，但必须保留时间、概率或适用范围限定；
- `insufficient`：证据不足，等待更多证据；
- `contradicted`：存在未解决反证；
- `unsupported`：原文不支持、夸大或越界；
- `unreviewed`：核验未完成或响应缺失。

结构化领域记忆优先由确定性代码核验；自由文本个人情境复用已有 extraction + verification 两段式流程。模型只返回离散 verdict 和必要限定，最终路由仍由本地程序执行。

### 6.3 错误影响 `impactLevel`

| 等级 | 判断标准 | 示例 |
|---|---|---|
| `low` | 记错只影响排序、表达或低风险建议，容易纠正 | 兴趣、内容偏好、普通节奏 |
| `medium` | 会明显改变规划，但不直接产生不可逆结果 | 时间偏好、阶段状态、持续责任 |
| `high` | 涉及健康安全、身份归属、重要金钱决策或现实行动 | 用药过敏推断、重大人生状态、预算动作依据 |

影响等级由命题用途和目标场景决定，不能只按领域决定。健康客观统计可以是低或中影响，普通对话里的身份推断也可能是高影响。

首版影响等级采取“保守且可解释”的程序规则：

- 明确带 `highImpact`、涉及诊断/用药/安全、或会成为重要财务行动依据：high；
- 身份变化、持续照护责任、硬时间约束、人生节点：medium；若来自推断或存在冲突则提升为 high；
- 有时间范围的聚合事实、普通偏好、低风险习惯和内容排序：low；
- 无法判断时按 medium；影响分级只会限制用途，不得把 unsupported 内容升级为可确认内容。

### 6.4 冲突与时效

决策前必须检查：

- 是否与用户已确认/纠正的记忆冲突；
- 是否与更新版本的来源冲突；
- 是否出现独立反证；
- 是否已经过期或仅适用于过去阶段；
- 同一个问题是否已问过、被跳过或被用户拒绝；
- 是否有新证据足以改变上次决策。

## 7. 统一决策矩阵

### 7.1 主决策表

| 来源与核验 | 低影响 | 中影响 | 高影响 |
|---|---|---|---|
| 用户明确要求记住，且无冲突 | `factEligible` | `factEligible` | `factEligible`，保留“用户声明”属性，使用时仍受领域安全门约束 |
| 普通用户明确陈述，`supported` 且持久化获授权 | `factEligible` | `factEligible` | `factEligible`，不得扩写，必须能回源 |
| 敏感或第三方用户陈述，但无派生记忆持久化授权 | `discard`（不写派生记忆） | `discard`（原始来源仍按自身权限使用） | `blocked` |
| 结构化客观事实，`supported` | `factEligible` | `factEligible`，保留时间范围 | `qualifiedAdvice` 或领域数据直查，不让记忆替代专业判断 |
| 独立重复证据，`supported` | `factEligible` | `qualifiedAdvice` | `askWhenRelevant` |
| AI 推断，`qualified` | `qualifiedAdvice` | `qualifiedAdvice`；若当前计划依赖则 `askWhenRelevant` | `askWhenRelevant`，未回答前 blocked |
| 证据不足或未核验 | `observeOnly` | `observeOnly` | `observeOnly`，不使用 |
| 有冲突 | `observeOnly` | 相关时 `askWhenRelevant` | 相关时 `askWhenRelevant`，否则 blocked |
| unsupported / 越界 / 伪因果 | `discard` | `discard` | `discard` |

### 7.2 特殊类别的新规则

#### 身份与 Profile

- 用户明确说过、明确维护过：直接作为“用户声明”自动采用；
- 从间接材料推断身份：不自动成为事实；
- 只有当前规划依赖该身份差异时才询问；
- 旧 Profile 与新明确陈述冲突时，新陈述不能被旧档案静默覆盖。

#### 人生节点与永久事实

- 明确陈述的已发生事件：自动采用，保留发生时间与来源；
- 模糊表达或间接推断：observeOnly；
- 会影响当前计划时问具体差异，例如“这是已经确定，还是还在考虑？”；
- 不再使用“lifeEvent 一律待确认”的规则。

#### 健康与敏感内容

- HealthKit 客观统计：自动采用有界事实，保留时间窗口；
- 用户明确要求“记住”的敏感事实，或已有清晰来源授权的有界敏感事实：进入本地敏感 Store，可自动记住，但不能扩写成诊断；
- 普通聊天中提到的敏感自由文本不等于同意形成长期派生记忆，默认仅在当前会话/原始来源范围使用；
- 第三方敏感信息默认不得形成长期记忆，除非用户明确要求、确有服务必要性且可限定到最小范围；
- AI 推断的疾病、心理、人格或医疗因果：直接 discard，不能通过用户点击“对”洗白；
- 高影响健康信息只有在相关回答或行动需要时才询问，并优先让业务数据源实时查询。

#### 首次跨域结论

- “首次”不再天然等于要确认；
- 有独立证据且只是相关性：`qualifiedAdvice`，用“同期出现”“从记录看”表达；
- 重复独立证据可以晋升，但仍不能改写成因果；
- 涉及健康、重大金钱或身份的高影响解释：`askWhenRelevant` 或 discard；
- 没有共同时间窗、共同锚点和独立 lineage：discard。

### 7.3 决策伪代码

```swift
if !structureValid || !evidenceTraceable || prohibitedInference {
    return .discard
}

if userExplicitlyRejectedOrForgotten {
    return .suppressWithTombstone
}

if sourceAuthority == .explicitMemoryRequest &&
   persistencePermission.allowsDerivedMemory &&
   !hasNewerConflict {
    return .factEligible
}

if evidenceVerdict == .unsupported {
    return .discard
}

if evidenceVerdict == .insufficient || evidenceVerdict == .unreviewed {
    return .observeOnly
}

if hasUnresolvedConflict {
    return impactAffectsCurrentOutcome ? .askWhenRelevant : .observeOnly
}

if !persistencePermission.allowsDerivedMemory {
    return .discard(reason: .derivedPersistenceNotAuthorized)
}

if sourceAuthority == .explicitUserStatement &&
   evidenceVerdict == .supported &&
   assertionGuardsPassed {
    return .factEligible
}

if sourceAuthority == .structuredObservation && claimIsBoundedFact {
    return impactLevel == .high ? .qualifiedAdvice : .factEligible
}

if evidenceVerdict == .qualified || sourceAuthority == .modelInference {
    return impactLevel == .high ? .askWhenRelevant : .qualifiedAdvice
}

return repeatedIndependentEvidence ? .factEligible : .observeOnly
```

## 8. 用户体验设计

### 8.1 后台形成记忆

用户正常记账、写想法、完成任务、记录习惯、使用健康数据或与 Holo 对话。后台萃取完成后：

- `factEligible` 自动进入“Holo 会参考”；
- `qualifiedAdvice` 进入“会谨慎参考”，不能伪装成确定事实；
- `observeOnly` 进入内部“观察中”；
- `askWhenRelevant` 暂存为可能的澄清点；
- `discard` 不出现。

整个流程不弹窗、不要求进入页面、不阻塞保存，也不在聊天回复前增加等待。

### 8.2 首页与聊天不再出现每日确认任务

取消以下默认体验：

- “待确认 N 件”；
- “几十秒就能清完”；
- “去确认”；
- 因旧候选库存每天重新出现的胶囊；
- 红点或角标催促用户清空记忆队列。

保留透明感，但改为非任务式表达：

- 第一次成功形成有效记忆时，可出现一次：“Holo 会根据你的记录逐渐了解你，你可以随时查看或纠正。”
- 后续常规自动记忆只在记忆管理内显示“最近整理”，不主动打扰。
- 不设置每日、每周或其他定时“记忆更新”提示；透明感通过记忆管理页和相关回答中的来源说明实现，而不是再造一个低频维护任务。

### 8.3 记忆管理页

普通用户只需要两个主要分组：

#### Holo 会参考

- 包含 `factEligible` 和 `qualifiedAdvice`，因为两者都会影响回答或建议；
- `factEligible` 标记为“明确记忆”，`qualifiedAdvice` 标记为“可能相关，会谨慎参考”；
- 展示“来自你的记录 / 你曾明确说过 / 自动整理”等来源标签；
- 支持“准确”“纠正”“不准确”“不再使用”；
- 自动采用不能显示成“你已确认”。

#### 观察中

- 仅包含当前不会进入回答的 `observeOnly` 与尚未触发的 `askWhenRelevant`；
- 默认折叠，不显示强提醒数量；
- 用户可以主动打开并纠正，但没有清空义务；
- 文案：“这些内容目前不会用于回答，Holo 会继续观察。”

删除“想和你确认的”作为每日主分组。为了兼容历史数据，可以在 Debug 或迁移期保留只读入口，但不出现在普通主流程。

### 8.4 按需澄清

只有同时满足以下条件才显示澄清：

1. 当前回答、规划或高影响建议真实依赖该信息；
2. 不同答案会改变结果；
3. 现有证据无法自行消除歧义；
4. 没有被用户回答、拒绝或处于冷却期；
5. 本次流程没有更重要的一个澄清问题。

呈现结构：

> 为了不把周末安排错，我想确认一件事：你现在每周日都需要陪父亲复诊，还是只限这个月？

操作：

- “每周都需要”
- “只限这个月”
- “暂时不确定”
- “不要使用这条信息”

规则：

- 一次用户主动发起的规划流程最多问 1 个记忆澄清问题；
- 所有普通入口共享一个注意力预算：默认滚动 7 天最多展示 1 个记忆澄清；用户主动进入记忆管理或明确要求 Holo 核对个人情况时不受此预算限制；
- 这个上限只针对“记忆澄清”；用户本次需求天然缺少的日期、人数等规划参数仍走现有 unknowns 规则，但必须与记忆问题去重，不能把同一缺口问两次；
- 同一个 `logicalQuestionKey` 在用户选择“暂时不确定”、关闭或跳过后冷却 30 天，除非出现实质新证据；新证据必须改变候选答案，不是单纯刷新时间戳；
- 用户关闭或跳过后，不在首页、通知或次日再次催促；
- 如果提问预算已用完，系统排除该记忆并给保守结果，不阻塞整个回答；
- 可独立完成的部分先完成，只暂停真正依赖未知量的部分；
- 记忆澄清本身不得触发真实业务写入。
- 澄清只允许出现在解锁后的 App 内，不进入通知、锁屏、Widget 或 Siri 朗读；涉及敏感信息时问题文案只说当前任务所需的最小变量，不复述完整记忆正文。

### 8.5 用户回答后的状态

| 用户动作 | 记忆结果 | 后续行为 |
|---|---|---|
| 选择明确答案 | 生成与回答范围一致的新版本 | 默认只适用于当前事项/当前周期；只有回答明确表达长期或重复规则时才生成 durable `active + userConfirmed` |
| 输入纠正 | 生成 `active + corrected` 新版本 | 旧版本 suppressed，不再召回 |
| 暂时不确定 | 保持 observeOnly | 30 天内不重复询问，除非有实质新证据 |
| 不要使用 | suppressed + 语义 tombstone | 不召回，不通过换 ID 或同义改写重生 |
| 关闭页面 | 不改变事实状态 | 视为跳过，进入冷却，不制造“未完成任务” |

## 9. Holo 场景示例

### 9.1 财务客观状态：自动采用

证据：近 30 天餐饮支出较前一周期上升，来自结构化交易聚合。

结果：`factEligible`。

用户感知：不需要确认；在问“这个月钱花哪了”时，Holo 可以引用这条有时间范围的事实，精确金额仍实时查询账本。

### 9.2 健康客观统计：自动采用

证据：HealthKit 最近 14 天平均睡眠时长下降。

结果：`factEligible`，敏感存储，本地处理，表达限定在统计范围。

禁止扩写：“你有睡眠障碍”“睡眠下降导致消费增加”。

### 9.3 首次跨域相关：限定使用，不询问

证据：睡眠较少的几天与外卖支出较高同期出现，两个独立来源、共同窗口成立。

结果：`qualifiedAdvice`。

表达：“从近期记录看，睡眠偏少和外卖支出较高曾同期出现，可以再观察。”

不要求用户判断这条统计“对不对”，也不能写成因果。

### 9.4 单次习惯变化：继续观察

证据：用户本周第一次连续三天早起。

结果：`observeOnly`。

系统不问“你是不是已经成为早起型的人”，等待更多时间窗口。

### 9.5 明确偏好：直接记住

用户：“以后周五不要给我安排早会。”

结果：`factEligible`，来源为用户明确陈述。

系统不再要求用户去记忆管理点击“对”。真正创建或调整日程时，仍按日程动作规则执行。

### 9.6 影响当前计划的冲突：按需问一句

旧记录：“周日上午通常陪父亲复诊。”

新记录：“这个月开始周日空出来了。”

当用户要求规划周末旅行时，两个答案会改变时间安排。

结果：此刻触发 `askWhenRelevant`：“周日上午现在已经可以安排旅行了吗？”

在用户没有规划周末事项时，不主动询问。

### 9.7 高影响无支持推断：直接丢弃

AI 从几条情绪想法推断用户存在焦虑症。

结果：`discard`。

这不是让用户点击“对/不对”就能转正的内容，而是系统不应生成的越界推断。

## 10. 数据契约设计

### 10.1 保留现有事实源

继续使用 `HoloMemoryRecord`、统一 Repository、证据、版本、反证、墓碑、权限代际、遗忘和敏感存储。不得新建平行记忆库。

### 10.2 新增可选决策元数据

建议在 `HoloMemoryRecord` 增加可选 `decisionMetadata`，整体继续编码在现有 `recordData` 中，避免新增 Core Data 属性。

```swift
struct HoloMemoryDecisionMetadataV2: Codable, Equatable, Sendable {
    var schemaVersion: Int                 // 2
    var policyVersion: Int                 // 4
    var sourceAuthority: SourceAuthority
    var evidenceVerdict: EvidenceVerdict
    var impactLevel: ImpactLevel
    var persistencePermission: HoloMemoryPersistencePermission
    var useLevel: HoloMemoryUseLevel
    var attentionPolicy: HoloMemoryAttentionPolicy
    var reasonCodes: [HoloMemoryDecisionReason]
    var evaluatedAt: Date
    var evidenceRevision: String
    var clarification: HoloMemoryClarificationMetadata?
}

struct HoloMemoryClarificationMetadata: Codable, Equatable, Sendable {
    var logicalQuestionKey: String
    var missingVariable: String
    var impactSummary: String
    var options: [String]
    var lastPromptedAt: Date?
    var cooldownUntil: Date?
    var promptCount: Int
    var materialEvidenceRevisionAtLastPrompt: String?
}
```

约束：

- 全部新增字段必须可选或有安全默认值；
- decision metadata 必须使用带 schemaVersion 的容错信封；未知枚举或未知版本原样保留并整体降级为 blocked/observeOnly，不能依赖 Swift 合成 Codable 兑现前向兼容；
- reason 只能记录枚举和 metadata，不记录用户原文；
- `logicalQuestionKey` 由主体、关系、适用范围、缺失变量的规范化签名生成，不能使用显示文案；
- `evidenceRevision` 变化只有达到 material-change 门槛才解除冷却；
- `confidenceScore` 继续用于内部排序，但不得直接决定采用或展示为事实概率。
- `persistencePermission` 只表达派生记忆的保存权，不替代原始业务数据自身的权限。
- `decisionMetadata` 是新版本唯一裁决结果；`personalContext.admission` 仅作为旧数据输入和兼容投影，由 decision metadata 单向派生，不得在新写入中独立裁决。
- `observeOnly` 不能无限积累：复用现有 currentState/phase/durable 的 freshness 半衰期与 minimumFreshness，在低于阈值时归档；Compaction 必须覆盖 candidate + observeOnly，而不再只清理 active。未获明确记忆请求/用户确认的记录不得使用 permanentFact 逃避衰减。

### 10.3 缺失元数据的安全降级

新客户端读取没有 `decisionMetadata` 的旧记录时：

1. 用户已 confirmed/corrected/rejected/forgotten 的决定优先保留；
2. 能从现有证据、claimKind、personalContext admission 确定的，按 v4 本地重算；admission 只作为 legacy input；
3. 无法重算的旧 active 可以继续按旧召回政策，但不得自动升级用途；
4. 无法重算的旧 candidate 默认 observeOnly，不进入用户确认队列；
5. 高影响未知内容默认 blocked，而不是自动使用。

旧客户端回写时可能剥掉新字段，因此新字段不能成为唯一安全门。字段缺失必须导致更保守，而不是更开放。

## 11. 系统架构与职责

```text
业务记录 / 想法 / 对话 / 健康 / 目标
                 │
                 ▼
          候选萃取与结构校验
                 │
                 ▼
       证据核验 + 冲突/时效检查
                 │
                 ▼
        HoloMemoryDecisionPolicy v4
       ┌─────────┼─────────┬─────────┬─────────┐
       ▼         ▼         ▼         ▼         ▼
   确定事实    限定建议    继续观察   按需澄清    丢弃
       │         │                     │
       ▼         ▼                     ▼
  普通记忆召回  个人情境建议策略      当前规划/聊天
       └─────────┴──────────┬──────────┘
                            ▼
                  统一来源标注与用户反馈
```

### 11.1 统一决策器

`HoloMemoryDecisionPolicy` 是唯一负责五路决策的纯逻辑组件。领域 Validator、个人情境 Reconciler、跨域 Fusion 不得各自重新定义“要不要问用户”。它们只提供结构化输入。

已有 `HoloMemoryActivationPolicy` 不再保留另一套矩阵：实施时要么由 DecisionPolicy 替换，要么降为调用 DecisionPolicy 的薄兼容适配器。`personalContext.admission` 同样只能由统一结果派生。任一入口出现两个可独立变化的最终结论都视为实现失败。

### 11.2 使用策略

- `HoloMemoryRecallPolicy`：只允许 factEligible 的 active 事实进入普通记忆召回；
- `HoloContextAccessPolicy`：只允许 qualifiedAdvice 进入低风险建议背景，并强制限定表达；
- observeOnly / askWhenRelevant 在用户回答前不能走普通事实召回；
- 业务明细问题继续实时查业务数据，不由记忆替代。

### 11.3 打扰策略

新增 `HoloMemoryAttentionPolicy`，成为所有 UI 判断“是否需要用户处理”的唯一入口。

禁止继续使用以下判断：

```swift
record.state == .candidate
```

判断必须包含：

- attentionPolicy；
- 当前使用上下文；
- 是否真的改变结果；
- 用户决策与冷却；
- 新证据是否实质变化。

### 11.4 按需澄清协调器

新增 `HoloMemoryClarificationCoordinator`，职责仅为：

1. 接收当前目标、计划草案和会影响结果的 unknowns；
2. 从 askWhenRelevant 候选中选出最多一个最高影响问题；
3. 验证冷却、用户控制、来源修订和使用权限；
4. 生成结构化澄清卡；
5. 将用户回答写回统一记忆仓库；
6. 产生回执但不直接执行任何业务动作。

它不得：

- 自己调用业务写工具；
- 在后台主动发通知；
- 把多个问题打包成审核清单；
- 使用旧结果绕过新的 access generation；
- 在用户回答前把候选作为确定事实注入计划。

问题文案优先来自后台已经形成的 `openQuestions/missingVariable`，或复用当前规划请求已经返回的 unknowns；不得为了“问一句”在聊天关键路径上额外串行调用一次模型。确需润色时只能与当前规划调用合并，失败则使用本地模板。

## 13. 后端与 Prompt 边界

### 13.1 P1 确定不改 Prompt；P2-P4 以契约能力证明为门禁

P1 的“停止每日确认与修正 pending 口径”确定只改 iOS，不需要后端部署。

P2/P3 只有在冻结 fixtures 证明现有字段足以稳定计算 sourceAuthority、限定范围和持久化权限时，才保持纯 iOS。P4 只有在现有 `openQuestions` / planning unknowns 能稳定给出 `missingVariable + options + applicability` 时，才可不改 Prompt。

- 领域记忆已有结构化 evidence、claimKind 和本地 Validator；
- 个人情境已有 `personal_context_extraction` + `personal_context_verification` 两段式离散核验；
- 跨域已有独立 lineage、共同窗口、共同 anchor 和禁止因果规则；
- 新问题的主要根因在本地采用策略和 UI 待确认口径。

这些是优先复用的基础，不是“全阶段一定无需改 Prompt”的结论。若评测不能证明上述结构化能力，P4 不得以自由文本猜测补齐，必须进入 Prompt vNext；但这不阻塞 P1 先上线降本。

### 13.2 何时才允许改 Prompt

只有冻结评测显示现有字段无法可靠区分以下情况时，才进入 Prompt vNext：

- 用户明确陈述 vs 模型推断无法在本地识别；
- qualified 所需限定无法表达；
- 缺失变量无法形成结构化 clarification；
- 领域输出长期把状态夸大成永久事实。

如需修改：

1. 同步 iOS fallback Prompt；
2. 修改 `HoloBackend/src/prompts/defaultPrompts.json`；
3. 升 `promptRegistry.js` 对应版本；
4. 补 provider/contract tests；
5. 获得部署授权后发布 ECS；
6. 验证 `/v1/release/status`、`/v1/prompts/meta` 和真实请求；
7. 仅 health 成功不能视为新 Prompt 已生效。

不得新增“confidence: 0.92”作为通行证。模型只能给离散支持结论、必要限定和证据引用。

### 13.3 非功能要求

| 维度 | 要求 |
|---|---|
| 前台性能 | 本地五路决策 p95 < 10ms；统一记忆查询继续满足现有 p95 < 100ms 目标 |
| 网络 | 聊天关键路径新增串行网络请求数为 0 |
| 后台成本 | 不因新决策额外增加领域萃取调用；个人情境复用既有 verification |
| 可靠性 | 批次幂等；迁移中断可续跑；用户决定与墓碑 RPO 为 0 |
| 隐私 | 敏感内容继续进入敏感本地 Store；日志、trace、指标只记录 metadata |
| 权限 | 自动记忆开关、AI 数据处理授权、遗忘和 access generation 继续作为总闸 |
| 兼容 | 新字段缺失走保守策略；旧客户端回写不能导致权限放宽 |
| 可维护性 | 五路决策为纯逻辑单一事实源；UI、召回、规划不得复制决策矩阵 |
| 可回滚 | 通过 feature flag 停用新使用/澄清行为，不清库、不回退用户决定 |

## 14. 存量迁移方案

迁移版本建议为 `memory decision policy v4`，每个用户、每个 Store 只执行一次，带 journal，支持重试和回滚。

### 14.1 不动的记录

- 用户 confirmed / corrected：保留用户决定，不降级；
- rejected / forgotten / markedIrrelevant：继续阻止召回；
- tombstone：继续拦截同义重生；
- archived / superseded：不伪装成新记忆；
- 已有时间、新鲜度、证据、版本与 predecessor：全部保留。

### 14.2 candidate 重评估

按以下顺序：

1. `personalContext.admission == adviceEligible`：仅作为 legacy evidence input，仍由 v4 重算；满足正常权限与证据门禁时才标为 qualifiedAdvice + silent，不进入确认；
2. 明确用户陈述且原始来源可读、来源修订有效、断言门禁和持久化权限全部通过：factEligible；
3. 结构化有界事实且无反证：factEligible；
4. 低影响推断且 qualified：qualifiedAdvice；
5. 高影响推断或未解冲突：askWhenRelevant，但不立即展示；
6. 证据不足：observeOnly；
7. 无证据、越界或已过时：discard / archive；
8. 无法判断：observeOnly，绝不能因为迁移失败进入每日确认。

迁移过程禁止调用网络或 LLM，也不得仅凭旧 evidence kind 把记录提升为明确用户事实。原始来源不可读、revision 不完整或主体/范围无法还原时，一律 observeOnly/blocked。

### 14.3 回执处理

- 将旧 `needsConfirmation` 未读回执标记为已迁移，不继续触发每日胶囊；
- 不为每条迁移记录产生新回执；
- 不主动产生迁移汇总提示；结果仅在用户进入记忆管理页时被动可见；
- 不刷新 `createdAt` / `lastSupportedAt`，避免旧内容冒充今天发生；
- 迁移后重新读取 Store 验证五路数量和用户决策未变化。

### 14.4 多设备兼容

- 迁移用 `policyVersion + stableID + recordVersion` 幂等；
- 同 ID 不同 revision 不得任意保留一条；
- 新客户端遇到旧客户端剥掉 decision metadata 时重新保守计算；
- 旧客户端看不懂新 attention metadata，仍可能把 CloudKit 中的 candidate 当作待确认；新版本无法远程修复这一 UI。产品承诺必须限定为“升级到支持 v4 的客户端后不再出现每日确认”，不得宣称所有旧设备同步安静；
- 不能为了让旧客户端安静而把 adviceOnly / blocked 记录提升为 active；安全优先于旧版本体验；
- 全量前必须完成活跃旧版本占比评估。若仍有多设备旧版本用户，需通过最低兼容版本/升级引导或旧版已经具备的远程开关解决；不存在可用旧版开关时，明确接受旧客户端仍提示的限制；
- Development/Production CloudKit schema 不因 JSON 内可选字段自动宣称无风险，仍需双设备验证 recordData 回写。

## 15. 指标与成功标准

### 15.1 北极星

记忆能力的价值不是“用户确认了多少条”，而是：

> Holo 在不增加维护负担的前提下，利用可信个人记忆改善回答和规划的次数。

### 15.2 上线硬指标

| 指标 | 首版门槛 |
|---|---:|
| 每日主动批量确认提示 | 0 |
| 无需用户操作完成决策的候选占比 | ≥ 90% |
| 相比无记忆基线，合格记忆对回答/规划的有效改善覆盖 | 不下降；冻结评测集必须有正向净提升 |
| 同一 logicalQuestionKey 30 天内无新证据重复询问 | 0 |
| 单次用户主动规划流程中的记忆澄清 | ≤ 1 |
| 普通入口全部记忆澄清 | 滚动 7 天 ≤ 1 |
| 高影响 unsupported 内容进入事实召回 | 0 |
| 用户明确表述后又被要求二次确认 | 0 |
| 聊天关键路径新增串行记忆 AI 调用 | 0 |
| 迁移造成用户决定丢失 | 0 |
| 已曝光自动事实被纠正/否决率 | 用户反馈 + 分层抽检双口径；任一口径持续高于 3% 则停止放量 |

“自动处理率 ≥ 90%”必须与有效改善覆盖和高影响错误率一起判定，禁止通过把候选全部 discard/observeOnly 来达标。

### 15.3 本地聚合指标

仅记录 metadata，不记录记忆正文：

- decision_fact / qualified / observe / ask / discard 数量；
- decision reason code 分布；
- clarification eligible / shown / answered / dismissed / cooledDown；
- repeatPromptPrevented；
- autoFact used 后 30 天内 corrected / rejected；
- 自动事实曝光数，以及按来源/影响分层的人工抽检错误率；
- 与不使用记忆的 counterfactual 结果相比，记忆是否实质改变且改善了计划；
- candidate 库存按 useLevel 分布；
- 旧 pending 回执迁移数量；
- 决策耗时 p50 / p95；
- chat path 串行网络调用数。

设备本地保留完整诊断；若要支撑 10%/50% 全量灰度，只能在用户允许分析的前提下上报不含正文、sourceID、稳定身份和敏感类别明细的聚合计数。没有合法聚合遥测时，只能对内部测试账号做人工导出评估，不能声称已验证全量人群指标。

### 15.4 失败止损

出现任一情况立即停止灰度：

- 高影响推断被当作确定事实；
- 用户选择“不再使用”后同义内容重生；
- 同一问题无新证据仍反复询问；
- 关闭自动记忆或撤回授权后仍产生新派生记忆；
- 旧设备回写导致用户纠正丢失；
- 记忆决策增加聊天等待或后台 AI 调用失控。
- 自动处理率上升但 counterfactual 有效改善覆盖下降，或 discard/observeOnly 占比异常跃升。

## 16. 验收场景

### 16.1 决策策略测试

至少覆盖：

1. 普通结构化财务事实自动采用；
2. 普通健康统计自动采用且保留时间范围；
3. 用户明确身份陈述不再二次确认；
4. 用户明确要求记住的敏感陈述本地存储、可追溯、不扩写；普通敏感聊天不生成长期派生记忆；
5. 单次模式进入 observeOnly；
6. 低影响 qualified 推断进入 advice-only；
7. 首次普通跨域相关不进入确认队列；
8. 伪因果和医疗诊断直接 discard；
9. 高影响推断只有相关时才可生成澄清；
10. 反证存在时不得事实召回；
11. 用户 corrected / rejected / forgotten 迁移后不变；
12. 缺 decision metadata 走保守降级；
13. old client 风格重编码后新客户端可重算；
14. 同 ID 不同 revision 冲突隔离；
15. 权限代际变化使在途结果失效。
16. 假设、否定、引用他人、临时选择、过去状态不会被误判为永久明确陈述；
17. 第三方敏感信息默认 blocked；
18. “不再使用”产生语义墓碑，同义改写与换 ID 不能重生；
19. qualifiedAdvice 实际参与建议时，在“Holo 会参考”中可见且使用语气受限；
20. DecisionPolicy、ActivationPolicy adapter 与 personal-context admission 不会产生冲突结果。
21. observeOnly 候选随 freshness 衰减被归档，不能因 candidate 状态绕过容量治理。

### 16.2 UI 测试

- 首页和聊天不再出现“待确认 N 件 / 去确认”；
- 新自动记忆不会要求点击；
- “观察中”默认折叠且无红点；
- qualifiedAdvice 位于“Holo 会参考”并标记“可能相关，会谨慎参考”；
- 当前使用记忆可查看来源、纠正、不准确、不再使用；
- 按需澄清一次只出现一个问题；
- 关闭澄清后次日不重复；
- 用户回答后计划重新生成或继续，但不自动执行业务动作；
- Voice / 普通聊天 / Context Plan 三入口遵循同一政策。

### 16.3 存量迁移测试

- 迁移前后 count、stableID、recordVersion、用户决定对账；
- adviceEligible candidate 不再进入 pending 计数；
- 旧 pending receipts 被一次性消化；
- 第二次迁移写入数为 0；
- 主 Store 与敏感 Store 分别验证；
- 模拟旧客户端回写后重新读取；
- 旧客户端仍可能显示 candidate 的限制有版本证明，不以批量 active 规避；
- iPhone 与 iPad 同账号验证 CloudKit 合并行为；
- 失败中断后可续跑，不产生半迁移假汇总。

### 16.4 真实样本评测

至少准备 160 条候选，八个领域各不少于 20 条；其中一半冻结为留出集，不参与规则调整。必须包含：

- 用户明确陈述；
- 结构化客观事实；
- 单次现象与重复模式；
- 生命周期变化；
- 首次和重复跨域；
- 敏感但明确的内容；
- 高影响推断；
- 反证、修订、他人经历、模糊时间；
- 无价值统计与越界推断。

人工金标准标注五路目标、允许用途、是否应打扰、必要限定和理由。模型输出 confidence 不计入金标准。

### 16.5 分层完成证明

交付必须分别说明：

- 纯逻辑 standalone 测试实际执行结果；
- Xcode build 与 XCTest 实际用例数，`Executed 0 tests` 不算通过；
- 模拟器真实 UI 点穿；
- 真机存量迁移与重新读取；
- 双设备 CloudKit 验证；
- 若有后端修改，生产 prompt version 与真实请求验证；
- App Store/生产发布状态，不能用本地完成替代。

## 17. 分阶段实施计划（交给 GLM）

### P0：基线与测试护栏

目标：在改行为前锁定现状和失败样本。

交付：

- 统计当前 candidate 中 personalContext admission 分布；
- 统计 adoption reason、旧 receipt、重复展示路径；
- 建立五路决策纯逻辑 fixtures；

- 建立迁移前后快照工具；
- 增加 feature flags，但不改变用户行为。

完成定义：能用测试稳定复现“adviceEligible candidate 被收件箱当作待确认”的问题。

### P1：立即取消错误的每日确认负担

目标：先解决用户最直接的问题，不改变普通召回安全边界。

交付：

- 新增统一 `HoloMemoryAttentionPolicy`；
- pending 计数不再直接等于 `state == candidate`；
- adviceEligible / observeOnly 不进入确认队列；
- 首页与聊天移除每日“去确认”任务式入口；
- 旧 needsConfirmation 回执停止反复唤起；
- 记忆管理先移除任务式确认入口；“Holo 会参考 / 观察中”的完整信息架构在 P5 收口。

本阶段不改后端，不开放新的高影响记忆使用权限。

完成定义：真实运行一天、多次切前后台和打开聊天，均不会因为候选库存再次要求用户清队列。

### P2：统一五路决策策略 v4

目标：让领域、跨域和个人情境共享同一决策模型。

交付：

- decision metadata v2；
- sourceAuthority / evidenceVerdict / impactLevel / persistencePermission 计算；
- 五路决策纯逻辑策略；
- DecisionPolicy 作为唯一裁决者；ActivationPolicy 降为适配器，personal-context admission 改为兼容投影；
- RecallPolicy、ContextAccessPolicy、Fusion 与 Validator 接入；
- reason code 和 metadata-only 指标；
- 旧策略对照日志，先不迁移存量。

完成定义：同一 fixture 在三个入口得到相同结果；旧策略与新策略差异可解释。

### P3：存量幂等迁移

目标：消化历史确认债务，不丢用户控制。

交付：

- v4 reconciler、journal、回滚；
- 主/敏感 Store 分区迁移；
- 旧 receipts 迁移；
- 旧客户端回写兼容与旧版仍可能提示的明确版本边界；
- 真机备份、迁移、重新读取验收。

完成定义：二次执行零新增；用户 confirmed/corrected/rejected/forgotten 数量与内容不变；v4 客户端待确认库存为 0；未用批量 active 掩盖旧客户端限制。

### P4：按需澄清

目标：只在结果真正依赖未知点时询问一次。

交付：

- clarification model 与 coordinator；
- logicalQuestionKey、30 天同问题冷却、滚动 7 天全局一问预算、material evidence 解锁；
- Context Plan / 普通聊天接入；
- 最多一问、独立部分继续、跳过后保守降级；
- 回答按最窄适用范围写回统一记忆，只有明确长期表达才 durable；不执行业务动作。

完成定义：测试中不相关的 askWhenRelevant 永不出现；相关冲突只问最小问题；跳过后 30 天不重复。

### P5：用户控制与可解释性收口

目标：自动化后仍让用户看得懂、改得动。

交付：

- 来源标签、自动采用与用户确认区分；
- 纠正/不准确/不再使用全链路；“不再使用”必须写语义 tombstone；
- 反证与来源失效传播；
- Debug 记忆实验室展示五路决策、reason 和冷却状态；
- 普通用户不显示置信度和内部 reason code。

### P6：评测、灰度与发布

目标：验证真实降本且没有把错误转成静默污染。

交付：

- 160 条评测集和冻结留出集结果；
- 自动处理率、有效改善覆盖、打扰率、曝光后纠错率、分层抽检错误率和高影响错误报告；
- 内部账号 → 10% → 50% → 100% 灰度；
- 回滚演练；
- 若无后端改动，明确写“无需 ECS 部署”；若有则按生产证据闭环。

## 18. Feature Flag 与回滚

建议至少提供：

- `memoryDecisionPolicyV4Enabled`
- `memoryDailyConfirmationInboxDisabled`
- `memoryJustInTimeClarificationEnabled`
- `memoryDecisionPolicyShadowLoggingEnabled`

### 18.1 灰度顺序

1. shadow：同时计算 v3/v4，只记 metadata 差异，不改状态；
2. 内部账号关闭每日确认入口，高影响仍全部 blocked；
3. 内部账号启用五路策略，不启用按需澄清；
4. 内部账号启用按需澄清；
5. 10% 灰度，观察至少一个完整周周期；
6. 50% 后复查纠错率、重复提问和 CloudKit；
7. 全量。

### 18.2 回滚顺序

1. 先关闭按需澄清；
2. 再关闭 v4 使用策略，新内容走保守 observeOnly；
3. 保持每日批量确认入口关闭，不把回滚变成重新骚扰用户；
4. 保留 decision metadata、用户反馈、墓碑、版本和证据；
5. 不清库、不回退用户决定；
6. 修复后从 shadow 重新验证。

## 19. 风险与缓解

| 风险 | 用户影响 | 缓解 |
|---|---|---|
| 自动事实记错 | Holo 回答被错误个性化 | 必须可回源；反馈立即抑制；自动采用与用户确认明确区分 |
| advice-only 被当事实 | 推断语气过强 | 独立 useLevel；强制限定表达；不得进入普通事实召回 |
| 不再确认导致高影响信息永远不用 | 个性化收益下降 | askWhenRelevant；未接入前保守不用，不恢复每日队列 |
| 按需问题仍过多 | 用户感到被审问 | 单流程最多 1 个；普通入口滚动 7 天最多 1 个；同问题 30 天冷却；跳过后保守结果 |
| 存量迁移误改用户决定 | 信任受损 | 用户决定优先、journal、备份、二次执行零写入、真机重读 |
| 多设备旧版本剥字段 | 策略反复、旧端仍提示 | 缺字段保守重算；policy/version 幂等；双设备验收；明确最低兼容版本，不批量 active |
| 语义确认被当成存储授权 | 用户说过一次的敏感信息被长期加工 | 独立 persistencePermission；敏感自由文本默认 session/source scoped |
| 敏感与高影响继续混用 | 要么过度打扰，要么不安全 | sensitivity 管存储位置；persistence permission 管能否派生保存；impact/use policy 管用途 |
| 为判断再调一次 AI | 成本和时延上升 | 复用现有 verification；前台零新增串行调用 |
| 低价值记忆大量积累 | 存储和检索噪声 | observeOnly 自动过期；UsefulnessPolicy；无价值直接 discard |
| UI 与查询各用一套口径 | 数量和行为矛盾 | AttentionPolicy、RecallPolicy、ContextAccessPolicy 各自唯一职责并做集成测试 |
| 自动处理指标被“全丢弃”作弊 | 看似降本但个性化失效 | 自动处理率必须和 counterfactual 有效改善覆盖、分层抽检一起过门 |

## 20. 架构决策记录（对抗性审查后建议采纳）

### ADR-1：使用权限与用户注意力分离

**背景**：当前 `candidate` 同时被解释成未生效、待确认和用户任务，造成确认泛滥。

**决策**：生命周期、持久化权限、使用权限、打扰策略四维分离；UI 不得再按 state 单独判断。

**正向结果**：可以安全地后台观察和限定使用，不把用户变成审核员。

**代价**：需要新增决策元数据，并改造多个旧查询口径。

**否决方案**：所有 candidate 批量 active；保留每日队列但增加“一键确认”。前者不安全，后者只缩短单次操作，没有消除长期维护成本。

### ADR-2：取消每日批量记忆确认

**背景**：记忆是后台能力，不是用户主动事项。

**决策**：普通用户不再收到每日待确认计数和清队列 CTA；只在当前任务相关时澄清一个关键未知量。

**正向结果**：用户使用成本接近零，问题与当下目标相关，回答意愿更高。

**代价**：部分不确定记忆会在 freshness 到期前处于 observeOnly，之后自动归档；系统必须接受空结果。

### ADR-3：不用模型自报 confidence 放行

**背景**：数值 confidence 不能代表真实准确率，也无法稳定跨模型校准。

**决策**：采用来源权威性、证据核验、冲突、时效和错误影响的离散决策；模型只提供结构化候选与离散 verdict。

**正向结果**：策略可测试、可解释、可回滚。

**代价**：需要维护确定性规则和冻结评测集。

### ADR-4：记忆授权与业务动作授权分离

**背景**：放宽记忆自动采用可能被误解为可以自动执行。

**决策**：记忆只提供上下文；任务、预算、习惯、财务等写操作继续走各自 typed payload、预览、确认、幂等和回执。

**正向结果**：可以大幅降低记忆确认成本而不扩大行动风险。

**代价**：用户可能看到 Holo 已理解，但执行前仍需确认；文案需解释这是两个不同阶段。

### ADR-5：语义可信与派生记忆持久化授权分离

**背景**：用户说出一句话，能证明“这是用户表达”，但不能天然证明“用户同意把敏感或第三方信息长期加工成记忆”。

**决策**：新增 persistencePermission。普通非敏感内容由总开关授权；敏感自由文本默认 session/source scoped，只有明确记忆请求或清晰来源授权才可派生持久化。

**正向结果**：无需逐条审批，也不会用降低交互成本换取隐私越界。

**代价**：部分敏感个性化只在相关会话或实时数据查询中生效，长期召回覆盖会更低。

### ADR-6：统一决策结果只有一个事实源

**背景**：DecisionPolicy、旧 ActivationPolicy 和 personal-context admission 若都能独立给出最终结论，会再次产生 UI、召回和规划口径分裂。

**决策**：DecisionPolicy 是唯一最终裁决者；ActivationPolicy 仅作薄适配，admission 仅作 legacy 输入和兼容投影。

**正向结果**：同一记录在所有入口得到同一权限和注意力结论。

**代价**：需要一次明确的适配迁移，不能只在 UI 上打补丁。

## 21. GLM 实施纪律

1. 开工前重新读取当前代码和本方案，不从历史文件照抄旧“类型必确认”规则。
2. 先写能够复现当前错误口径的测试，再改 UI 和策略。
3. 只使用统一 Repository；不新增平行 JSON 事实源。
4. 所有新 Codable 字段做旧数据和未知枚举兼容测试。
5. `Dictionary(uniqueKeysWithValues:)` 遇重复 ID 会 fatal；来源、verdict、revision 映射必须容重复并隔离冲突。
6. P1 不改 Prompt；P2-P4 先用冻结 fixtures 证明现有契约够用，不够时必须按 Prompt vNext 流程补齐，不能用自由文本猜测字段。
7. 如修改 Prompt，必须双端同步、升版本、部署和生产验证。
8. 工作区存在大量无关修改，必须精确文件范围，不覆盖、不暂存、不提交无关内容。
9. 方案中的 90%、同问题 30 天、普通入口滚动 7 天最多一问、单流程最多一问是首版产品契约，不得私自改成“尽量”。
10. 每阶段交付当前代码、测试、模拟器、真机、后端和生产状态，不能混写。
11. “不再使用”必须走语义 suppression/tombstone，禁止继续只调用 `deleteRecord`。
12. 存量迁移不得联网、不得调用 LLM、不得仅凭旧 evidence kind 晋升为用户明确事实。
13. 新增 enum/metadata 必须做未知值与未知 schemaVersion 容错测试；“属性 optional”不等于枚举前向兼容。
14. GLM 实施时所有表内路径以前述 App 源码根目录为基准；不得误改 build 产物中的同名索引文件。

## 22. 完成定义

只有同时满足以下条件，才能宣布本方案完成：

- 普通用户入口不存在每日待确认任务；
- adviceEligible / observeOnly 不再进入待确认计数；
- 五路决策由同一个纯逻辑策略控制，旧 ActivationPolicy/admission 不再形成第二结论；
- 通过主体、语气、时间、范围和来源修订门禁的用户明确陈述不会被二次确认；
- 敏感自由文本没有持久化授权时不生成长期派生记忆；
- 首次跨域不再一律确认；
- 高影响 unsupported 推断不能通过任何确认卡洗白；
- 按需澄清只有在当前结果依赖时出现，单流程最多一个、普通入口滚动 7 天最多一个，跳过后同问题冷却 30 天；
- 记忆回答与真实业务执行权限分离；
- 存量迁移幂等，用户决定、墓碑、证据和时间不丢；
- “不再使用”会形成语义墓碑，同义或换 ID 不重生；
- standalone、XCTest、模拟器、真机、双设备 CloudKit 按实际结果分层通过；
- 如修改后端，已取得 production prompt version 和真实请求证据；
- 灰度指标满足第 15 节门槛，且自动处理率没有通过全量 discard/observeOnly 作弊，回滚演练完成；
- `CHANGELOG.md`、实施记录和未完成项与真实状态一致。

## 24. 第一性原理对抗性审查记录

### 24.1 审查方法

本次不以“方案章节是否齐全”为通过标准，而是从四个不可替代的问题反推：

1. 这次询问是否必须由用户回答，系统有没有安全替代路径；
2. 静默采用出错时，最坏损害是什么，是否可发现、可纠正、可撤回；
3. 用户说过、允许保存、允许用于建议、允许执行行动是否被错误合并；
4. 指标、迁移和兼容机制是否可能让实现表面达标、实际伤害信任。

审查范围包含产品目标、权限边界、状态模型、UI、现有 Swift 实现、数据迁移、旧客户端、Prompt 边界、指标与灰度。

### 24.2 发现与处置

| 级别 | 攻击点 | 原方案问题 | 已写入的修订 |
|---|---|---|---|
| 阻断 | 语义确认与存储同意混淆 | “用户明确表达即可自动记住”会把敏感聊天误作长期保存授权 | 新增 persistencePermission；敏感自由文本默认 session/source scoped |
| 阻断 | “不再使用”无法阻止重生 | 当前实现只 `deleteRecord`，与原方案承诺 tombstone 冲突 | 明确改为 suppression + 语义 tombstone，并加入再生测试 |
| 阻断 | 策略存在多个事实源 | DecisionPolicy、ActivationPolicy、admission 可能各自裁决 | DecisionPolicy 唯一裁决；其余仅适配/投影 |
| 高 | 显式陈述误判 | 假设、否定、引用、临时选择、过去状态可能被永久化 | 增加主体、语气、时间、范围、revision 六道门禁 |
| 高 | qualifiedAdvice 被 UI 隐藏 | 实际影响建议，却被放进暗示“不会使用”的“了解中” | 改为“Holo 会参考”，明确标记“可能相关，会谨慎参考” |
| 高 | 旧客户端无法理解新 attention | 新端修复后旧端仍可能按 candidate 催确认 | 明确版本边界，禁止批量 active；上线前评估最低兼容版本 |
| 高 | 指标可被全丢弃作弊 | 90% 自动处理不代表记忆有价值 | 增加 counterfactual 有效改善覆盖与分层抽检联合门槛 |
| 高 | 纠错率存在幸存者偏差 | 仅统计主动反馈会低估静默错误 | 改用已曝光分母 + 用户反馈 + 分层人工抽检 |
| 中 | 澄清预算只限单流程 | 用户一天多次规划仍可能被连续问 | 增加普通入口滚动 7 天全局最多一问 |
| 中 | 澄清回答被过度泛化 | 为一次旅行回答可能被记成永久偏好 | 默认最窄适用范围，只有明确长期表达才 durable |
| 中 | 迁移可能靠旧标签误晋升 | 旧 evidence kind 不足以证明原文语义 | 迁移禁止联网/LLM；原文或 revision 不全即保守观察 |
| 中 | “首版不改 Prompt”过度承诺 | P4 可能缺结构化 missingVariable/options | 限定 P1 确定本地完成；P2-P4 以冻结 fixtures 为门禁 |
| 中 | Codable 前向兼容承诺不足 | optional 属性不能保护未知 enum 解码 | 要求 schema 信封、未知值原样保留并整体保守降级 |
| 低 | 定时非任务提示仍是维护成本 | 每周提示仍会形成注意力税 | 删除全部周期性记忆提示，只保留被动透明入口 |
| 低 | 实施路径有歧义 | 文件表未说明嵌套源码根目录 | 明确 App 源码绝对根目录 |

### 24.3 审查结论

修订前方案**不应直接实施**；以上 15 项中有 3 项阻断问题。修订后，产品目标、用户权责、静默失败、迁移、兼容、指标防作弊和工程单一事实源已经闭环，当前没有未处置的规格级阻断项。

结论为：**方案通过实施前对抗性审查，可以作为 GLM 的唯一产品与架构实施依据。**

这不等于代码已经安全上线。实施仍必须逐阶段满足 P0-P6 的测试、真机、双设备、灰度和（如涉及 Prompt）生产证据门禁；其中旧客户端停止提示只能在兼容版本范围内成立。
