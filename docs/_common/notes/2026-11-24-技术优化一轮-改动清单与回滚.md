## 一句话结论

- **构建**：AI 会话的构建现在会排队并给东林让路，产物目录固定复用；新增「编译缓存」，**清空后全量重编从约 80 秒降到约 20 秒**。
- **运行**：启动后那段约 0.8 秒的主线程卡死消失（优化后 8 次冷启动没有一次出现超过 0.5 秒的卡死，优化前 3 次都有）。
- **稳定**：30 处「遇到 iCloud 重复数据会崩」的写法清零。
- **解耦**：新增机器守门，模块间 5 类牵连只许减不许增。
- **测试安全网**：57 个此前从未被自动测试执行的文件接入；全量回归与优化前逐条对比，**没有真回归**。

## 实测效果

**构建耗时**（同一台 Mac，隔离副本，Debug）

| 场景 | 优化前 | 优化后 |
|---|---|---|
| AI 会话默认构建（清空后全量） | 152.6 秒（每个文件编两遍） | 79 秒 |
| 东林的习惯：清空 → Run | 83～183 秒 | **约 20 秒**（编译缓存，首次建缓存约 94 秒） |
| 不清空的增量构建 | 约 24 秒 | 约 24 秒（其中 11.8 秒是单模块重新生成模块信息，属结构性代价） |

**启动主线程卡顿**（模拟器带真实数据量，同一规程冷启动）

| 指标（启动后前 15 秒） | 优化前（3 次） | 优化后（8 次） |
|---|---|---|
| 最长一次卡死 | 756～871 毫秒 | 361～451 毫秒 |
| 出现超过 500 毫秒卡死的启动 | 3 / 3 | 0 / 8 |
| 主线程累计忙碌（中位） | 3088 毫秒 | 2409 毫秒 |

**构建时给界面让路**（计算型探针模拟界面线程，同一次全量重编约 80 秒，两组构建耗时相同）

| 约束 3800 帧里 | 构建低优先级（现在） | 构建普通优先级（以前） |
|---|---|---|
| 掉帧（一帧的活超过 8 毫秒） | 22 次 | 57 次 |
| 整帧丢失（超过 16 毫秒） | 1 次 | 5 次 |

单个构建在 15 核机器上本来就不至于把界面卡死；把机器拖卡的主要是多个会话同时构建再叠加内存压力，那靠排队锁解决。叫醒延迟型探针测不出差别，不要拿它当「让路」的指标。

**界面**：同一台模拟器、同一份数据，优化前 / 优化后 / 优化前各走一遍逐页截图。想法、任务、财务、习惯、健康、设置、今日看板、HoloAI 九个页面**逐像素一致**；首页只有光球动画区有差异，量级与「优化前 vs 优化前」两轮之间的天然差异相同。

**回归**：全量 2920 个用例（优化前 2822 个，多出的全是新接入的测试），失败 63（带编译缓存重跑的那次是 64，差异全是抖动）、跳过 7～8。逐条对比后的差异全部做了对照实验：时序抖动、全新模拟器首次启动状态、以及一个优化前就失败的过期走查。单元测试层面只剩优化前就红的那几个。

**合并预演**：把本分支合进当前的 1.2.0（已被别的会话推进 19 个提交）——自动合并无冲突，工程文件完整性核对通过，五道守门全绿，单元测试只剩 5 个优化前就有的红。

## 新规矩（怎么用）

### 构建与测试：一律走 `BuildScripts/holo_build.py`

```bash
python3 BuildScripts/holo_build.py build      # 默认具体模拟器；产物目录按工程路径固定一份，跨会话复用
python3 BuildScripts/holo_build.py test       # 默认并行 4 worker；--only HoloTests/类名；--expect N 防假绿
python3 BuildScripts/holo_build.py ls         # 看有哪些产物目录、多大、多久没用
python3 BuildScripts/holo_build.py gc         # 回收 14 天没用过的产物目录
python3 BuildScripts/holo_build.py archive    # 出归档包（默认 Release，存到 Xcode 归档目录）
```

- **不要再每个任务新开一份 DerivedData**（曾堆到约 100GB、硬盘 95%）。不传 `--dd` 就是对的。
- **不要绕过它直接跑 `xcodebuild`**：绕过去就没有排队和让路，而且可能把编译失败当成成功。
- **不需要每次清空再构建**：产物目录固定复用后增量是可靠的；确实要清空，有编译缓存兜底。
- 输出边跑边写日志，长测试随时能看进度。

### 写测试

- 新测试文件要挂进工程：`python3 BuildScripts/pbxproj_surgery.py mount --file HoloTests/<路径>.swift`。
- 「独立脚本式」套件必须有执行入口（进自动生成的桥接 `StandaloneExecutableBridgeTests.swift`）；三步见 `HoloTests/Support/StandaloneSuiteBridge.swift` 头注释。断言失败走 `XCTFail`，不要用 `fatalError` / `precondition` / `exit` 当断言。
- 已知失败的套件登记在 `StandaloneSuites.knownFailing`：默认跳过并显式可见，修好就从表里删。

### 改代码

- 模块间不要新增耦合：非界面层不许依赖功能界面、数据层不许依赖业务服务、功能界面之间不直接引用、视图不直接拿数据库栈、界面层不加全局单例。规则与例外写法见 `docs/standards/开发规范.md` §17。
- `uniqueKeysWithValues` 零容忍。

## 发现但这一轮没做的

| 事项 | 为什么没做 |
|---|---|
| 把 41 万行拆成多个真正独立的模块 | 能把增量构建的 11.8 秒「重新生成模块信息」压下来，但要给上万处声明加标注，是独立专项；这一轮先用守门把耦合扭成「只减不增」 |
| 个人情境萃取的取数还在主线程 | 要动 5 个数据适配器的线程模型，属中等风险，需要配合萃取链路整体验证 |
| 习惯页回前台会全量重算 | 直接去掉会带来「小组件打卡后回 App 显示旧状态」的风险；要做需先设计便宜的变化检测 |
| 启动链上的一串单例初始化 | 耗时弥散，没有单段超过 400 毫秒的同步块；要重构启动文件（别的会话正在改） |
| 首页看板入口按钮的重复绘制（约占启动期 App 侧主线程时间的 15%） | 该文件别的会话有在途改动，避开 |
| 超重页面拆分（想法编辑器 2412 行、想法列表、首页） | 涉及真机栈溢出类风险，必须在真机门禁上验证；手机没连电脑时不能声称完成 |

**暴露出来的既有问题**（都不是这一轮引入的，需要各自的负责人）

- Agent 评测基线 177 条里 80 条不达标（`HoloAgentEvalRunnerTests`，此前从未进自动测试），已登记跳过，需 Agent 线归因。
- `HoloAgentAnswerObservabilityStandaloneTests`：旧目录兜底的计数为 0，待 Agent 线确认是目录漂移还是夹具过期。
- 优化前就红的单元测试：`HoloMemorySettingsStandaloneTests`（观察者二级深挖默认值与断言不一致，产品口径待定）、`DailySenseSnapshotTests`、`FullScreenCoverEdgeSwipeBackAuditTests`、`MozeMergeRehearsalTests`、`TaskPendingEditTests`；`TaskClassificationMigrationTests` 单独跑能过、并行跑偶发失败。
- 约几十个界面走查测试长期失败（优化前后都在），其中有「全新模拟器首次启动状态下按钮不出现」这类环境问题。
- `ProviderContractTests` 检查的 4 个旧 purpose 早已从 App 删除，已移除；`GalleryPhotoStackWalkUITests` 的截图种子不再产出多图卡，待想法线确认多图卡现状后重写。
- `ThoughtSemanticStoreStandaloneTests` 等测试靠「往上找名为 HOLO 的文件夹」定位夹具，副本目录名不含 HOLO 时会假失败。

## 踩过的坑（给后来人）

- **对外报数先算后写**。这一轮我一度把「从未执行的测试」误报成 147 个，实情 57 个：检查时正则写死了带 `Standalone` 字样的调用，漏掉了自动生成的桥接文件。说「某类测试从未执行」之前，必须拿执行证据（测试日志或桥接文件清单）。
- **改写脚本的扫描范围要写死**。批量改写有一次是从仓库根跑的，顺手动了 3 个第三方库文件，提交前清点才发现。第三方库（`Vendor/`）一律不动。
- **ZCode 宿主里 `find` 不是系统自带的那个**，`-newermt @时间戳` 会报错并输出为空；「最近有没有用过」这类判断用 Python 自己读时间，判断出错按「在用」处理。
- **工程文件的备份要按工程分目录**。多副本共用 `/tmp` 时，「最新一份备份」可能是别的副本的。
- **测量前先看机器负载**。有一轮启动卡顿数值突然变大，查下来是系统负载 42～88（别的会话在跑重活）污染了测量，不是回归。
- **并行测试的控制台不显示断言详情**，失败原因要去结果包里读：`xcrun xcresulttool get test-results tests --path <.xcresult>`。
- **判「真回归」前用优化前的代码同机同条件对照**。这一轮 3 个新失败，对照之后全是环境或时序问题。
