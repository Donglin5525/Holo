## 一、P1（4 条：升级拒开 / 成本旁路 / 收入旁路 / 幽灵通知）

### S1 ✅复核 P1 升级白名单只认「恰好本轮两张知识表」，跨版本老设备整库拒开
- `Models/CoreDataStoreUpgrade.swift:10-15`（`additions == knowledgeEntityNames` 严格相等）+ `Models/CoreDataStack.swift:194-224`（指纹预检，任何其他差异即 `.mismatch` 拒开）+ `:270-300`（拒开路径，原库原地保留）。
- 轻量迁移通道已被预检整体拦死：任何不是「恰好加这两张表」的模型差异（多跳升级如代码注释自述的 10-6 构建 59 实体→当前 65 实体、或未来任何一轮忘记扩白名单的 schema 改动）都触发 fail-closed 拒开——**不丢数据，但受影响设备功能硬停进恢复说明页，只能人工救援**。东林自己处于中间构建的日用设备升级即中招；且以后每轮改 schema 都必须记得扩静态白名单，漏一次全体老用户拒开。
- 待产品决策：发中间构建逐级过渡 / 扩白名单为「已知增量集合」/ 恢复受控轻量迁移。

### D1 ✅复核 P1 会员额度幂等键可被客户端复用，绕过全部次数池
- `HoloBackend/src/usage/quotaActionLedgerStore.js:79-92`（reserve 见已存在记录直接 `allowed:true` 不计数）+ `src/app.js:2735-2742`（`resolveQuotaActionId` 直接采信客户端传的任意 `usageActionId`）+ `src/app.js:1500`（ASR 同型）。
- 恶意客户端每次请求带同一个 `usageActionId` → 第一笔 commit 后所有 chat/agent_loop/insight/ASR 的 reserve 全部命中「重复」放行——**免费档等于无限额度，上游 AI 成本照付**。修法方向：额度键绑定请求内容哈希（同键不同内容不放行）。

### D2 ✅复核 P1 订阅收据无原始交易号归属绑定，一份 Plus 凭证解锁任意多台设备
- `HoloBackend/src/subscription/entitlementStore.js:44-56`（upsert 只按 device_id 写，无 original_transaction_id 归属校验）+ `src/app.js:746-757`（sync 直接落库）；全仓库无 App Store Server Notifications webhook。
- StoreKit 2 JWS 是不记名凭证：同一份已购 JWS 提交到 N 台设备，每台各享完整 Plus 配额池（`entitlementResolver.js:22` 按 deviceId 分 subject）；退款/撤销只能等客户端下次主动 sync 才被感知。直接对应收入损失。修法方向：订阅表加 original_transaction_id 唯一归属校验。

### A1 ✅复核 P1 清空任务模块后，已删任务的提醒通知永远不会被取消（幽灵通知）
- `Services/RecycleBinService.swift:584-598`：通知 ID 真实格式是 `"<任务UUID>-<提醒UUID>"`（`TodoNotificationService.swift:275`），任务 UUID 自带 4 个连字符；`firstIndex(of: "-")` 截出的是 UUID 前 8 个字符，与完整 36 位 UUID 前缀集合永远不匹配 → 过滤器恒空，一条通知都取消不掉。清空任务模块/回收站彻底删除后，待发提醒照常推送。
- 修法：按 `identifier.hasPrefix("\(uuid)-")` 匹配或 `identifier.split` 后取前 5 段重组。
