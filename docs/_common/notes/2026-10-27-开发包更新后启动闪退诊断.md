## 已确认结论

iPhone 刚安装新开发包后，数据库指纹预检拒绝打开原有数据库；启动流程却把「等待装载已结束」当成「数据库已可用」，继续执行首页默认图标的保存。Core Data 对从未成功打开的 coordinator 抛出 Objective-C 异常，进程立即退出。

这是本次启动闪退的直接原因，已用匹配构建 UUID 的真机堆栈和同次启动日志闭环。早上 08:46 的 CloudKit 结构上报阻塞属于另一个故障，不能混为一案。

## 启动日志补证

在只监听 Holo `CoreDataRecovery` 分类的情况下，启动手机上已经安装的 App 取证。15:03:45 同一进程依次出现：

1. `指纹预检拒绝打开（原库原地保留，绝不自动迁移）`，原因是当前数据模型与原数据库结构不同。
2. `Core Data 存储加载失败……进入可恢复失败状态`。
3. 控制台：`Illegal attempt to save to a file that was never opened`。
4. 未捕获异常：`This NSPersistentStoreCoordinator has no persistent stores (unknown). It cannot perform a save operation.`

错误提示中 `_database_corrupted` 是系统方法名，不能仅据此判断用户数据库损坏；本次第一条真实错误是本地指纹保护主动拒绝装载。

## 代码机制

- `CoreDataStack.storeFingerprintRejection` 要求实体集合及所有实体版本哈希完全一致，任一差异都拒绝装载，原库原地保留。
- 当前开发中的通用知识功能向 `CoreDataStack+HoloMemoryEntities.swift` 增加了 `HoloMemoryKnowledgeRevisionMO` 和 `HoloMemoryKnowledgeOperationMO` 两个实体。使用生产预检原文的独立临时库实验，已复现仅新增这两张表也被拒绝。真机日志证实指纹不同，但未输出具体实体哈希差异，不把隔离实验的差异列表冒充手机实读结果。
- `waitUntilReady()` 在成功或失败终态都会返回，目的是让上层展示失败，而不是永久等待。
- `HomeView.task` 在返回后直接执行仓库 setup，没有检查存储是否真正成功就绪；`HomeIconConfig.seedDefaultConfigs` 会尝试保存。
- `try? context.save()` 不能捕获这类 Objective-C 异常，恢复提示尚未完成呈现就已退出。

## 修复边界

应同时处理两层：存储失败时阻止任何业务仓库进入读写；对明确支持的旧版本升级设计有备份、有验证的兼容路径。不能直接删除指纹保护、清空数据库、伪造就绪或强制重建空库来消除闪退。

最初取证阶段只诊断、未改手机数据。随后因用户继续报告卡死，按 self-check 复查并落实以下修复；不能把最初的诊断结果当成修复已交付。

## 已落实的第二轮修复

- 对已知的 63→65 升级只放行两张知识表的新增，要求全部既有实体哈希完全一致，仍拒绝未知差异、字段变更和降级。不是删除指纹保护。
- 升级前以 SQLite backup API 获取含已提交 WAL 的一致性副本，同时保留 Core Data 外置 BLOB；备份失败即停止。任何装载失败都不再自动重建空库。
- 指纹优先读取实时 WAL；独占锁场景实测无条件 immutable 兜底会返回可能过期的指纹。有非空 WAL 时现已禁止该兜底；仅确认前后均无待合并 WAL 时，允许读取完整主文件，兼容系统 SQLite 在正常关闭后缺少 SHM 的情况。
- 建模、预检、备份与存储装载放后台。根部存储门等真正成功后才挂载整个业务页面与生命周期任务，Debug / Release 均在成功后装配启动服务；失败终态只展示可复制的说明页。
- 后台任务统一入口等待加载并抛出加载错误，避免失败库继续收到保存。
