# 截图记账开放「转账/红包」识别方案（一期 · A 类）

> 2026-11-06 · 东林拍板 · 分支 1.1.6
> 前置调研：记忆档 `screenshot-transfer-booking-open-analysis-1106`；原设计 `docs/plans/2026-09-09-screenshot-receipt-billing-plan.md` §3.3、`docs/finance/plans/2026-09-14-Holo图片账单快捷指令自动记账完整方案.md` §8.3

## 0. 一句话

把「转账/红包」从截图记账的拦截名单里拆成两类：**钱真的进出你口袋的（A 类）放开记账**，**自己账户之间挪钱的（B 类）继续拦**。快捷指令和聊天发图两个入口一起改，老版本 App 行为不变。

## 1. 拍板口径（东林 11-06）

| 问题 | 拍板 |
|---|---|
| 范围 | 先做 A 类（对外转账、红包），B 类继续拦截，二期再议「账户间转账」 |
| 待对方收款 | 照常记，并提示「被退回记得删掉」 |
| 收到的 AA 款 | 照常记成收入，用户在确认页自己改 |

## 2. 识别口径

### 2.1 A/B 类边界（模型说明书 + 后端契约 + App 三处同口径）

| 类别 | 图型 | 例子 | 处理 |
|---|---|---|---|
| A 类：钱真的进出你的口袋 | `personal_transfer`（新增） | 微信/支付宝转账给别人、收到别人转账、发红包、收红包、群红包、收款码收到别人付款 | **记账**：转出/发出=支出，收到=收入 |
| B 类：自己账户之间挪钱 | `transfer_screenshot`（收窄语义） | 信用卡还款、花呗/白条/借呗还款、零钱/余额提现、给零钱/余额充值、零钱通/余额宝/理财申购赎回、转到自己名下的卡 | **继续拦截**，文案改准 |
| 消费（不变） | `payment_screenshot` | 扫码付款给商户/个人收款码、话费/会员/游戏充值 | 不变 |

注意区分：**「话费/会员充值」是消费**（payment_screenshot），**「给零钱/余额充值」是 B 类**。

### 2.2 A 类状态处理

| 图中状态 | 处理 | 用户看到 |
|---|---|---|
| 对方已收款 / 你已收款 / 已存入零钱 / 红包已领取 | 记一笔 | 正常确认页 |
| 待对方收款 / 待你收款 / 红包未领完 | 记一笔，标记「待收款」 | 确认页该笔下方提示：转出→「对方还没收款，如果被退回，记得删掉这笔。」收到→「你还没收款，如果过期退回，记得删掉这笔。」 |
| 已退还 / 已退回 / 已过期退回 / 转账失败 | 不记 | 「这笔转账或红包已退回或没有完成，不用记账。」 |
| 看不出状态 | 记一笔，走既有「支付状态不确定」复核 | 正常确认页 + 既有提示 |

### 2.3 方向与分类

- 方向：钱从用户这里出去（转账给别人、发红包、付别人的群收款）= 支出；别人给用户（收到转账、领到红包、收款码收款）= 收入。关键原文：「对方已收款/XX已收款」= 用户是转出方；「你已收款/已存入零钱/已领取」= 用户是收款方。
- 默认分类（用户库里找不到时落「待分类」，与现状一致）：

| 方向 × 类型 | 默认分类 |
|---|---|
| 支出 · 转账 | 其他 → 转账 |
| 支出 · 红包 | 人情 → 红包礼金 |
| 收入 · 转账 | 人情来往 → 转入 |
| 收入 · 红包 | 人情来往 → 红包 |

- 有转账说明（如「房租」「生活费」）时，说明优先参与分类（可能直接落到「居住→房租」）。
- 复用既有「个性化科目学习」：分类候选原文=对方名称，用户把「张三」的转账改成「居住→房租」一次，下次同一人自动套用（学习键 `type|primary|candidate` 已天然支持，零改动）。

### 2.4 账户

- 说明书统一渠道写法：微信零钱写「微信零钱」、支付宝余额写「支付宝余额」（原写法「零钱」匹配不到微信账户，现状会落默认账户）。收到的钱写到账位置（「微信零钱」「支付宝余额」「招商银行储蓄卡1234」）。
- **本条同时改善现有零钱付款的账户匹配**（老版本 App 也受益，属行为改进，需评测确认无回归）。
- 自有卡判定（B 类兜底）：转账对象带银行卡尾号且与用户自己某账户名里的尾号一致 → 视为转给自己 → 该笔按 B 类拦截。逻辑与现有尾号匹配账户同一规则（账户名包含尾号）。

## 3. 前后端接口变更（契约 v4）

### 3.1 请求：新增能力声明

```json
{ "image": "<base64 JPEG>", "text": "可选附言", "capabilities": ["personal_transfer"] }
```

- 新版 App 固定带 `capabilities: ["personal_transfer"]`；老版本 App 不带。
- 后端 body 无 schema 校验，老后端忽略未知字段（新 App + 旧后端安全）。

### 3.2 响应：理解单 v4（`UNDERSTANDING_SCHEMA_VERSION = 4`）

- `imageType` 新增取值 `personal_transfer`。
- 每笔交易新增 `transfer`（非转账为 `null`，后端恒输出该键）：

```json
"transfer": {
  "kind": "transfer",              // "transfer" | "red_packet"，后端钳制，非法值→"transfer"
  "counterparty": "张三",           // 对方名称/群名，≤60 字，可为 null
  "counterpartyAccount": null,      // 对方银行卡（如「招商银行(1234)」），≤40 字，可为 null
  "awaitingReceipt": false          // 恒为布尔
}
```

- 其余字段语义不变；转账类 `merchant`=对方名称，`note`=转账说明/红包留言原文（无则 null），`categoryCandidate`=对方名称。

### 3.3 后端放行规则（`normalizeUnderstanding(raw, { allowPersonalTransfer })`）

`allowPersonalTransfer = 总开关开 && 请求声明了 personal_transfer`

| 情况 | 处理 |
|---|---|
| 允许 + 状态 completed/unknown | 保留交易与 transfer 信息 |
| 允许 + 状态 pending | 视为「待收款」：paymentStatus 改 completed、每笔 awaitingReceipt=true，记 guard（不走原「待付款清空」） |
| 允许 + 状态 refunded/failed/cancelled | 清空交易，**图型保持 personal_transfer**，rejectReason=已退回/未完成 |
| 不允许（老 App 或总开关关） | 降级为 `transfer_screenshot` 并清空交易 + guard——**与今天完全一致** |
| 非 personal_transfer 图型 | 每笔 `transfer` 强制 null |
| `transfer_screenshot`（B 类） | 照旧清空（护栏四不变） |

**执行顺序（审核 P1，必须钉死）**：字段归一化（逐笔 transfer 仅在图型为 personal_transfer 时生成）→ **转账块**（能力门降级并清空 / pending→completed+awaitingReceipt / refunded·failed·cancelled 清空保图型）→ 既有护栏一（外币）→ 护栏二（未完成支付）→ 护栏三 → 护栏四（`BILLABLE_TYPES` 增补 `personal_transfer`）。理由：护栏二会把 pending 的交易清掉并把图型改成 pending_order、把 failed/cancelled 改成 unrelated；护栏四会清掉非可记账图型的交易——转账块不前置，放行结果会被既有护栏静默击败。转账块之后：已钳制的 pending 不再触发护栏二；已清空的交易不再触发护栏一/二；外币转账照旧被护栏一拦截。单测按此顺序逐条断言。

**能力解析（审核 P3）**：`capabilities` 非数组、元素非字符串、空数组，一律视为未声明（走降级，安全侧）。

### 3.4 总开关

- env `HOLO_VISION_PERSONAL_TRANSFER_ENABLED`，默认开（`!== "false"`，同 `HOLO_PROFILE_CHANNEL_ENABLED` 模式）。
- 关闭=所有客户端按老口径处理转账（新 App 会看到 B 类文案，属应急态可接受）。关闭方式：env 加一行 `=false` + 重建容器，免发版。

## 5. iOS 改动清单（需要发新版）

### 5.1 共享识图层 `HoloVisionExtractionService.swift`

- 请求加 `capabilities`；模型加 `HoloVisionTransferInfo`（kind: String、counterparty/counterpartyAccount: String?、awaitingReceipt: Bool）与 `HoloVisionTransaction.transfer`（Optional）。kind 与 imageType 同用 String（后端类型即 string；新增 kind 不致老包整包解码失败）。
- `isBillable` 加 `personal_transfer`。
- **自有卡判定**：`extract` 解码后对 personal_transfer 逐笔检查 `counterpartyAccount` 尾号是否命中自有账户名；命中的笔剔除，全部剔除则整单按 B 类处理（客户端护栏，两入口共享）。尾号规则抽到 `FinanceTransactionDraftResolver` 与现有账户尾号匹配共用一处。剔除必须可观测（审核 P3）：追加一条客户端 guard（`own_account_transfer_removed`）并写日志——部分剔除时快捷指令门禁因 guard 存在自动转「识别结果有异常，请人工核对」，用户不会无感少一笔。
- `rejectionText`：B 类新文案；personal_transfer 无交易→「已退回或没有完成」。
- `stage2Text`（聊天喂给记账管道的文字）：转账笔改写为「转账给「张三」」「收到「李四」的转账」「发给「X」的红包」「收到「X」的红包」+ 有说明时「说明「房租」」，让聊天管道落到正确分类。

### 5.2 快捷指令通道

- `ReceiptBookingPolicy`：personal_transfer 可记账；无交易→新拒绝码 `rejectTransferNotCompleted`（先于支付状态分支判断，避免落「支付失败」文案）；**转账一律人工确认**：personal_transfer 始终追加复核原因 `reviewTransferConfirm`（排在其他原因之后，页面首条提示优先显示更具体的原因；也避免空原因被注入「识别信息不完整」）。多笔早退路径同样追加（审核 P3）：`[reviewMultipleTransactions, reviewTransferConfirm]`。
- `ReceiptBookingReason`：新增 `reviewTransferConfirm`、`rejectTransferNotCompleted` 及其文案；B 类 `rejectTransfer` 文案改准。**文案映射五处都要补 case**（审核 P2：这些 switch 都有 `default:`，漏了编译器不报）：共享拒识文案 `rejectionUserText`、结果行 `ReceiptBookingResultRow`、确认页页面级 `pageReasonText`（:584）、快捷指令结果文字 `reviewText(for:)`（Intent:205-236）、复核列表行短原因（`ReceiptReviewListView`:157）。
- 草案与确认页：`StoredDraftItem` / 复核快照逐笔新增可选字段（转账类型、对方、待收款），旧草案可解码。
- 分类兜底：转账笔在既有候选全部落空后，按「方向×类型」用种子三语词（`SeedTerm.allValues`）找用户库里的对应分类（父+子同时匹配），仍找不到才落「待分类」。种子词表补 `cashGifts`（红包礼金）、`transferIn`（转入）两个静态词并让层级定义引用它们。
- 多笔结果文字修正：快捷指令结果与通知的「N 笔支出」改为按方向（全收入→「N 笔收入」）。

### 5.3 确认页（`ReceiptReviewDetailView`）

- 转账笔卡片顶部加一行：方向胶囊（转出/发出=支出色，收到=收入色）+「转账/红包」+ 对方名称；方向跟随用户在卡内切换的收支实时变化。
- 待收款笔下方加一行提示（见 2.2）。
- 新 UI 放独立叶子 struct 文件（View 限重红线），颜色字体走设计规范语义色，深浅色都过。

### 5.4 聊天通道（`ChatViewModel`，不动 ChatView）

- 待收款时，在记账卡后追加一条助手提示（沿用现有「可能重复」提示的发送方式）。

### 5.5 文案（简中源 + 繁中 + 英文，文本级插入 xcstrings）

约 22 条：B 类新拒识×3（聊天/共享/结果行）、未完成拒识×3、转账复核提示×3（确认页/快捷指令结果/列表短原因）、转账行词×5（转出/发出/收到/转账/红包，已存在则复用）、待收款提示×2、聊天转账短语×6、多笔收入×2。旧 B 类三条词条随文案替换移除（文本级切除）。
