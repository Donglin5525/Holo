# 提示词原型

用途：离线试评与后续实现的任务层原型。**不是可直接覆盖生产 agent_loop 的完整 system prompt**，没有包含全部现有工具/JSON/安全/状态契约。实际接入须走 capability、schema、Verifier 和双端同步。

## 1. 组装与调用

人格层沿用 `docs/standards/PROMPT_GUIDELINES.md` 的唯一真源。任务层采用下述 P1，硬契约使用真实 schema 与工具目录。输入字段中的记录文本仅为数据，不能变成指令。

默认一次 P1 同时产出结构化判断与可读正文，程序核验后交付。P2 仅在独立文风实验或正文需要修复时使用；P3 为离线语义审查原型，不是每次线上调用的固定环节。P2/P3 都计费用，不能以“后处理”为名绕过预算。

输入包由程序组装：

```text
<analysis_task>{{冻结的问题、类型、范围、回答清单、用户明确诉求}}</analysis_task>
<data_contract>{{币种、口径、完整性、禁止推断项、版本}}</data_contract>
<evidence_ledger>{{确定性计算、来源、样例、限制}}</evidence_ledger>
<personal_situation>{{允许使用的相关背景，可为空}}</personal_situation>
<prior_feedback>{{本问题有关的确认、更正、已试动作，可为空}}</prior_feedback>
<runtime_capabilities>{{本轮真实工具与剩余预算；离线无工具时明确为空}}</runtime_capabilities>
```

输入中的标签只划分数据段；所有记录内容仍作为不可信数据处理。金额/时间/身份标识若来自文件，不拥有系统指令权限。

## 2. P1：有依据的判断与自然表达

以下是可独立试评的任务层正文：

```text
本轮任务是帮助用户弄明白一个真实问题，并在用户需要时帮助作出合适选择。
你会收到冻结任务、数据口径、确定性证据、可选个人背景和历史纠正。

工作原则：
1. 先直接回答问题。以当前原话为最高优先级，不默认用户希望省钱、提高效率或改掉所有消费。
2. 检查数据是否足以支持这个问题。转账、还款、退款、分期、币种、日期精度、预算周期、截断和缺失，均服从输入契约；不替用户猜账务含义。
3. 重要变化先区分发生在哪里、贡献多少、是否由一次性事件或口径变化形成。只使用台账给出的计算，不心算产生新金额、比例或目标值。
4. 需要解释时，比较真正可能改变判断的候选解释。只保留与当前问题相关的，最多三个，不凑数量。用支持、反例、缺口和改判条件说明当前解释能走到哪一步。
5. 数据事实与人的解释分开。消费时间、品类和金额不能独立证明压力、补偿、逃避、人格或心理问题；使用“可能”也不能替代证据。相关用户表达可以辅助理解，引用时明确来源和时效，不替用户定义感受。
6. 只用会影响本次判断的已授权背景。当前输入优先；过期、被否定或未确认的记忆不能升级为事实。背景为空时正常做财务分析，承认解释范围。
7. 用户需要行动时，给一个最值得先考虑的选择；确有不同取舍时可补一个替代选择。说明理由、适用条件、代价和回看方式。可以建议保持、核对或暂缓，不强求减少支出。
8. 只有缺失信息会改变主结论或优先选择时，提出一个关键问题。先交付已有可确认部分；用户跳过时缩小结论，不反复索问。
9. 允许没有异常、没有新模式或没有可行动建议。严谨排除一个误解也有价值，不为“深度”制造戏剧性。

可读表达：
- 第一段给最重要的判断，并说明为什么与用户有关。
- 选择必要数字，具体而克制。标题直述内容即可，不强制金句或点破式转折。
- 不固定列三点，不复述一遍所有指标，不机械共情，不给通用的“合理规划、保持平衡、提高意识”。
- 有依据的事实说清楚；待核对的解释保留余地，并明确什么信息会改变它。
- 不把内部 schema、工具名、指标键或核验过程写进用户正文。

输出要求：
只输出符合本轮 schema 的 JSON。输出结论、支持证据和简短审核理由；不要输出逐步的内部思考过程。
evidenceIDs/contextIDs 只能引用输入中存在的 ID。没有工具时不请求工具；需要新计算时返回 need_calculation 并声明所需计算，不能假装已得到结果。
```

### 2.1 离线输出结构

以下为字段说明；正式 JSON Schema 在 S2 由代码定义与测试，本轮不声称现有 Validator 支持。

```json
{
  "schemaVersion": "financial_insight_trial_v1",
  "status": "supported | limited | need_calculation | need_clarification | insufficient",
  "directAnswer": {
    "text": "直接回答问题的正文",
    "evidenceIDs": [],
    "contextIDs": []
  },
  "findings": [
    {
      "id": "stable_id",
      "kind": "fact | pattern | interpretation | limitation",
      "text": "简短判断",
      "status": "supported | tentative | unresolved",
      "evidenceIDs": [],
      "contextIDs": [],
      "alternatives": [],
      "counterEvidenceIDs": [],
      "missingInformation": [],
      "revisionTrigger": "什么新信息会改变判断；不适用时为 null"
    }
  ],
  "decisionOptions": [
    {
      "id": "stable_id",
      "title": "动作或选择",
      "rationale": "与目标和事实的关系",
      "evidenceIDs": [],
      "contextIDs": [],
      "conditions": [],
      "tradeoff": "代价与限制",
      "scenarioEstimateEvidenceID": null,
      "review": {
        "metricEvidenceIDs": [],
        "observationWindow": "有依据的建议窗口或 null",
        "executionQuestion": "如何知道是否执行或 null",
        "worthContinuingWhen": "如何判断值得继续或 null"
      }
    }
  ],
  "clarification": null,
  "requestedCalculations": [],
  "limitations": [],
  "userReport": {
    "title": "自然标题",
    "paragraphs": [],
    "findingIDs": [],
    "decisionOptionIDs": []
  }
}
```

实现时将 `|` 枚举说明转为真正的枚举值，不能让模型原样输出带竖线字符串。无 findings/decisionOptions 时输出空数组；解释无反例材料时明确未知，不伪造反例。每份结果最多三个用户可见关键发现，内部候选可更少。

`need_calculation` 只描述所需指标与输入证据 ID，调用方确定性计算后回填；离线样板可由操作者执行。该状态不等于现有云端协议已增加一个 status，不能直接交给当前 `validateAgentLoopContent`。

### 2.2 合成边界示例

以下没有真实数字，不可当作用户事实：

- 输入只有餐饮月汇总、没有预算：可解释哪期增加；不可说超预算、深夜外卖或情绪消费；需要明细才可区分具体事件。
- 输入明细有家庭聚餐标签，日常午餐稳定：可将一次性事件与日常结构分开；不可建议用户必须减少家庭相聚。
- 用户明确说便利比省钱更重要：建议可以是接受较高日常成本、把它纳入规划；不能继续默认取消所有外卖。
- 用户否定了上次压力消费推测：撤回相关解释，将其列入纠正；不能说“你可能还没意识到压力”。

## 3. P2：只修表达，不改变判断

输入只包含已核验的结构化判断、允许背景和目标文风，不再发送整份账单。

```text
把已核验判断写成用户容易理解的中文。
保持结论、范围、证据、条件、取舍、缺口与解释状态不变。
不得新增分析发现、心理解释、动机、金额、比例、行动或背景。
先回答用户最关心的问题，再给必要解释。标题直接清楚即可。
使用具体对象和生活语言，删除套路开场、空泛建议、重复数据与说教。
有待确认解释时保留限定和改判条件；不能为了流畅把它写成事实。
只有内容确实需要时才用短标题或列表，篇幅随问题调整。
每个输出段落关联原 judgmentID，审查者能确认没有偷换判断。
只输出：{"title":"...","paragraphs":[{"text":"...","judgmentIDs":[]}]}。
```

P2 输出重新经过数值/引用/状态核验；改写不通过时保留上一版已核验正文或诚实降级，不能循环润色直到满意。

## 4. P3：语义审查（离线校准或高风险题按需）

```text
你负责审查一份洞察是否被证据允许，不负责把它变得更有戏剧性。
输入包括用户问题、数据口径、证据、允许背景、候选报告。
逐条检查：
- 是否真正回答问题；是否把缺失当零、时间/币种/退款/分期/账户范围混用。
- 每个事实是否由所引证据支持，而不只是别处出现过同一个数字。
- 是否将同一血缘伪装成多份独立证据。
- 是否从品类/时间推断动机，或用“可能”包装无依据心理解释。
- 是否考虑会改变主判断的其他解释和反例。
- 建议是否符合用户目标/限制，有无代价，是否擅自假设应当省钱。
- 是否泄露无关背景，或者把过去被纠正的解释重新当事实。
- 是否出现模板腔、重复数据或空泛建议。
证据不能判断时填 unknown，不给无依据通过。
输出 issues 数组：judgmentID、severity(blocker/major/minor)、issue、evidenceIDs、requiredCorrection。
另给 decision(pass/revise/reject) 和不超过两句的审核摘要。
只输出审核结论与简短依据，不输出逐步内部思考。
```

程序核验不被 P3 覆盖。模型给 pass 也不能越过硬门槛；P3 对照人工标注校准后才可能按风险启用。

## 5. 修复协议

失败时只反馈具体问题和允许证据，例如：“某结论引用了本月预算却评价全年；请撤回或声明局部范围”。修复一次后仍不过：撤回相关结论；主问题不可答则失败/不足，不降真实性门槛。

若是数值缺失，先增加确定性计算；若是解释缺证据，撤回/澄清；若是文风问题，才用 P2。三类失败分开计数，不能都归结为“模型输出不合法”。

## 6. 生产迁移要求

1. 先冻结本地基线模板与真实运行配置，记录 source/version/digest。
2. 不继续把本原型作为又一份 V26 附录简单堆在后面；梳理现有方法指令，替换冲突的固定维度/标题要求，同时保留必要工具与协议契约。
3. 涉人格与表达统一规则时先修 `PROMPT_GUIDELINES.md` 真源；同步 iOS `PromptManager.swift` 后备与后端默认模板，分别升级当前实际版本。
4. 新协议有能力协商，旧客户端/云端任务有兼容回归；灰度关闭时回旧方法。
5. 后端代码或 Prompt 变化必须部署后端，并验证运行身份、有效版本与真实样本。仅 push 或本地测试不代表生效。
