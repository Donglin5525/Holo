# HOLO 账单周期与信用卡类型方案

> 日期：2026-08-10
> 状态：方案待评审 → 自主实施
> 决策人：东林

## 一、背景与问题

### 1.1 现状

HOLO 财务模块**完全没有"账单周期"概念**。整个模块里所有"月"都是**自然月（每月 1 号到月底）**，且这个写死逻辑分散在 7+ 个文件、10+ 处独立计算。

具体表现：
- **统计页**：`TimeRange.month`（`FinanceAggregation.swift:57`）取 `now.startOfMonth`，写死自然月
- **账户详情"本月"**：`getAccountMonthlySummary`（`FinanceRepository+Accounts.swift:301-329`）用 `dateComponents([.year, .month])` 算月首
- **全局月度交易**：`getTransactions(for month:)`（`FinanceRepository.swift:157-170`）同样写死
- **预算**：技术上支持任意起始日滚动周期（`BudgetRepository.currentPeriodRange`），但 UI 默认填本月 1 号，且建好后起始日锁死不可改（`BudgetSettingsSheet.swift:230-237`）
- **账本页环比**：`CalendarState.loadPreviousPeriodComparison` 也按自然月

信用卡在数据模型里只是 `AccountType.card`（显示名"银行卡/信用卡"），与储蓄卡共用一个类型，**没有任何专属属性**（无账单日、还款日、额度）。"还款"只是一个普通支出分类，不是专门流程。

### 1.2 核心矛盾

用户记账时心里有一个"我的消费周期"概念，它往往不是自然月：

> 信用卡账单日是 5 号的人，他的"一期账单"是 5 号→下月 4 号。但 HOLO 用自然月统计，把他的一个完整账单周期劈成两半。于是 HOLO 说"本月花了 8000"，信用卡 APP 显示"本期账单 6000"，两个数永远对不上。

**账单周期的本质价值：让"我这个周期花了多少"这个数字，贴合用户真实的消费节奏，而不是被日历强行切断。**

### 1.3 东林的决策

- **范围**：第一期（全局周期）+ 第二期（信用卡专属）**一起做**
- **起始日范围**：1-31（贴合真实信用卡账单日，月底问题由算法处理，不做回避）
- **信用卡类型**：从 `card` 里**单独拆出来**成独立类型 `creditCard`

## 二、整体设计

### 2.1 两个层次

| 层次 | 概念 | 作用于 | 默认值 |
|------|------|--------|--------|
| **全局记账周期** | "记账周期起始日"，一个整数 1-31 | 统计页、预算默认起始日、账户详情的"本月"、账本页概览卡 | 1（= 自然月，向后兼容） |
| **账户级账单周期** | 信用卡的账单日、还款日、额度 | 信用卡账户详情的"本期账单"视图、还款提醒 | 无（仅信用卡类型可设） |

### 2.2 信用卡类型拆分

`AccountType` 新增 `creditCard`，`card` 改名含义为纯"储蓄卡/借记卡"：

```swift
enum AccountType: String, CaseIterable {
    case cash = "cash"
    case digital = "digital"
    case bank = "bank"
    case card = "card"              // 储蓄卡/借记卡（原"银行卡/信用卡"拆分后保留为储蓄卡）
    case creditCard = "creditCard"  // 信用卡（新增）
    case other = "other"
}
```

- 显示名：`card` → "储蓄卡"，`creditCard` → "信用卡"
- 图标：`card` 用 `bankcard` 或保留 `creditcard`；`creditCard` 用 `creditcard.fill`
- 颜色：`card` → "#6366F1"（蓝），`creditCard` → "#F59E0B"（橙，原 card 颜色，符合信用卡视觉印象）
- **新增 `sortOrder: Int` 属性**：AccountListView 按 rawValue 字母序排序会导致 creditCard 位置错乱，加显式排序（cash=0, digital=1, bank=2, card=3, creditCard=4, other=5）

**编译影响极低**：穷举 switch AccountType 的地方全在 `AccountType.swift` 内部（displayName/icon/defaultColor 三处），补完即编译通过。外部无穷举 switch。

**净资产无需改**：`getTotalNetWorth` 按余额正负判断资产/负债，与类型无关，信用卡天然按欠款计入负债。

**导入逻辑同步改**：`FinanceRepository+Import.swift` 的 `guessAccountType` 把"信用卡"关键词从判 `.card` 改判 `.creditCard`。

### 2.3 数据迁移（向后兼容）

- **账户类型迁移**：旧数据里所有 `type == "card"` 的账户，需迁移到 `creditCard` 还是保留 `card`？
  - **决策**：种子数据里的"信用卡"账户（isDefault 种子）迁移为 `creditCard`；其他用户自建的 `card` 账户**保留为 `card`（储蓄卡）**，因为用户建的时候大概率是当储蓄卡用的。
  - 用 UserDefaults flag 惯用法（项目已有此模式，见 `Category+CoreDataProperties.swift:722`）：`hasMigratedCardToCreditCard_v1`，在 `FinanceRepository.setup()` 里跑一次。
  - 实际上更简单：种子账户里叫"信用卡"的那个（名字判断）迁移，其余不动。

- **新字段**：加 `billingDay / dueDay / creditLimit` 都是 optional，Core Data 轻量级迁移自动兼容旧库，无需手动迁移代码。

## 三、核心难题：起始日 1-31 的风险与处理

这是本方案最需要讲透的地方。东林要求支持 1-31，这会带来几个真实的风险，必须逐一设计处理。

### 3.1 风险一：月底月份天数不足

**问题**：账单日设成 31 号，但 2 月只有 28 天、4 月只有 30 天。31 号在这些月份不存在。

**处理策略：cap 到当月最后一天。**

定义一条规则：**"当月账单日"= `min(设定的账单日, 当月总天数)`**。

举例（账单日 = 31）：
- 1 月：账单日算 1/31，周期 1/31 → 2/28（2 月没 31 号，本期结束于 2 月最后一天）
- 2 月：账单日算 2/28，周期 2/28 → 3/31
- 4 月：账单日算 4/30，周期 4/30 → 5/31

**关键**：这个 cap 逻辑必须集中在**一个地方**（新建 `BillingCycleCalculator`），所有计算周期范围的地方都调它，绝不散落。

### 3.2 风险二：周期边界漂移

**问题**：如果每个月都 cap，31 号的周期可能会出现长度不一、甚至重叠/跳变的边界。

**处理策略**：以"起始日为锚点逐月推进"而非"固定日期"。参考现有 `BudgetRepository.currentPeriodRange` 的循环推进逻辑——从锚点开始，每次加一个月，找到包含 `now` 的区间。这样无论中间月份天数怎么变，区间始终连续不重叠。

**算法（伪代码）**：
```
给定 billingDay（1-31）、参考日期 now：
1. 算出"本月有效账单日" = date(年, 月, min(billingDay, 当月天数))
2. 如果 now >= 本月有效账单日：
     本周期 start = 本月有效账单日
   否则：
     本周期 start = 上月有效账单日  // 即 now 落在上月账单日到本月账单日之间
3. 本周期 end = start 的下一个月有效账单日（同样 cap）
4. 返回 [start, end) 半开区间
```

**验证用例**（billingDay=31）：
| now | 本月有效日 | 上月有效日 | 周期 start | 周期 end |
|-----|-----------|-----------|-----------|---------|
| 2/15 | 2/28 | 1/31 | 1/31 | 2/28 |
| 3/15 | 3/31 | 2/28 | 2/28 | 3/31 |
| 5/10 | 5/31 | 4/30 | 4/30 | 5/31 |

边界连续、不重叠、不跳变。✓

### 3.3 风险三：还款日的"跨月"问题

**问题**：账单日 5 号、还款日 25 号还好说。但账单日 25 号、还款日 5 号呢？还款日在账单日之前，意味着还款日落在**下一个自然月**。

**处理策略**：还款日相对账单日计算，不绝对。
- 如果 `dueDay >= billingDay`：还款日在账单日**同月**（账单日 5，还款日 25 → 同月）
- 如果 `dueDay < billingDay`：还款日在账单日**次月**（账单日 25，还款日 5 → 次月 5 号）
- 同样需要 cap 到当月天数

这个逻辑只在信用卡"本期账单"视图里用，不影响全局统计。

### 3.4 风险四：全局周期与多账户汇总的口径

**问题**：如果未来允许每个账户设不同账单日，多账户汇总（统计页"总支出"）按谁的周期？

**处理策略（本方案决策）**：
- **全局统计（统计页、首页卡片、预算）统一用全局记账周期**，不用账户级账单日。
- **账户级账单周期只用于该信用卡账户详情页的"本期账单"视图**，是个增强展示，不参与全局聚合。
- 这样多账户汇总永远有统一口径，逻辑不会崩。

| `creditLimit` | decimal | true | nil | 信用卡额度，可选 |

#### 4.1.2 AccountType 枚举变更

#### 4.1.3 全局设置

新建 `Utils/FinancePeriodSettings.swift`，单例 + UserDefaults（参照 `FinanceDisplaySettings` 模式）：

```swift
@MainActor
final class FinancePeriodSettings: ObservableObject {
    static let shared = FinancePeriodSettings()
    @Published var billingCycleStartDay: Int  // 1-31, 默认 1
```

### 4.2 核心工具：BillingCycleCalculator

新建 `Models/BillingCycleCalculator.swift`，集中所有"按起始日算周期范围"的逻辑。这是整个改造的核心枢纽——**所有算"月"的地方都改调它，消灭散落的 `startOfMonth`**。

```swift
struct BillingCycleCalculator {
    /// 给定起始日（1-31）和参考日期，返回包含参考日期的周期 [start, end)
    static func currentCycleRange(startDay: Int, reference: Date) -> (start: Date, end: Date)

    /// 给定起始日和参考日期，算前一个周期范围（用于环比）
    static func previousCycleRange(startDay: Int, reference: Date) -> (start: Date, end: Date)

    /// 周期平移（统计页左右切换）：给定一个周期 start，算 ±N 个周期后的 start
    static func shiftedCycleStart(_ start: Date, startDay: Int, offset: Int) -> Date

    /// 月底 cap：min(day, 当月天数)
    private static func effectiveDay(_ day: Int, year: Int, month: Int) -> Int

    /// 信用卡还款日计算（处理跨月）
    static func dueDate(billingDay: Int, dueDay: Int, forCycleStart: Date) -> Date
}
```

**算法要点**：
1. `effectiveDay` 用 `Calendar.range(of: .day, in: .month, for:)` 拿当月天数，做 `min`
2. `currentCycleRange`：先算本月有效日，判断 now 在它之前还是之后，决定 start 用本月还是上月
3. 所有返回值都是半开区间 `[start, end)`，与现有 `getAccountMonthlySummary` 等口径一致

### 4.3 改造范围与边界（Review 后修订）

> **关键决策：改造范围限定为"统计汇总类"场景，账本页日历浏览保持自然月。**
>
> 理由：账本页（`FinanceLedgerView` + `CalendarState`）的核心交互是翻日历看每天交易明细，日历天然按自然月翻页。强行让账本页跟随账单周期，会导致"日历停在 3 月，但数据是 2/15-3/14 的"这种割裂，且 `CalendarState` 环比逻辑改造风险极高、收益低。
>
> 因此账单周期只作用于**统计页、账户详情"本期"统计、预算默认起始日**这些"算一个月汇总数字"的地方，不作用于"翻日历看明细"。

## 七、风险登记

| 风险 | 等级 | 处理 |
|------|------|------|
| 改动面大（10+ 处月份计算），漏改导致口径不一致 | 高 | 集中到 BillingCycleCalculator，grep 排查所有 startOfMonth |
| 31 号在短月份的周期漂移 | 高 | cap 到当月最后一天 + 循环推进锚点，写测试用例 |
| 环比对比逻辑（CalendarState）周期长度不固定 | 中 | 取 min 天数对齐，参照现有逻辑 |
| 信用卡种子账户迁移误伤用户自建账户 | 中 | 只迁移名字匹配"信用卡"的种子账户，用 UserDefaults flag |
| Core Data 加字段后 CloudKit 同步 | 低 | 新字段全 optional，CloudKit 兼容 |
