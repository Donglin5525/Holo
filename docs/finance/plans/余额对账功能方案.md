# 余额对账功能方案（一期+二期合并）

> 2026-09-01 · 东林拍板：一期（对账闭环）+ 二期（导入对账联动）合并实施，三期（习惯化/自动化）暂缓在档。
> 纯客户端功能，不需要后端发版。Account/Transaction 加字段，发版前置 = CloudKit schema 部署 Production。

## 0. 结论摘要

对账 = 定期拿银行/支付宝的**真实余额**核对 App 里**算出来的余额**，发现并修正中间漏记、错记的账。Holo 已有「调整余额」功能（声明式对账的主体动作），本方案不做新机制，而是给它补上缺失的闭环：

1. **锚点**：记录「上次对账时间 + 对平后的余额」，让余额从「一个数」变成「一个有可信度的数」。
2. **状态可视化**：账户详情/列表展示「✓ 3 天前对平 / 对账基准已变动，建议重新对账」。
3. **调整流水退出收支统计**：对账补差不再虚增当月支出（余额计算不受影响）。
4. **导入对账联动**：余额列入库 + 导入完成页一键「以账单为准」拉平，根治「导入历史账单后余额从 0 起算必失真」。
5. **期初余额放开编辑**：给「差额来自更早历史」的用户一条正路（改期初而不是堆调整流水）。

## 1. 背景与问题

### 1.1 余额机制

Holo 账户余额 = `initialBalance + 已发生收入 − 已发生支出`，实时计算（`FinanceRepository+Accounts.swift:174 getAccountBalance`），不存余额字段。任何一笔漏记/多记/错记都会让余额**永远错下去且用户无感知**。

### 1.2 现状盘点（已核实）

**已有**：
- 期初余额 `Account.initialBalance`（创建时填写，编辑不可改）
- 「调整余额」：长按账户/详情页菜单 → 输入真实余额 → 差额生成一笔挂系统分类「余额调整」的普通交易（`AdjustBalanceSheet.swift`、`FinanceRepository+Accounts.swift:249`）

**缺失（按伤害排序）**：
1. 无对账锚点——无法回答「余额可信到哪天为止」
2. 导入账单：新账户期初恒为 0、银行账单余额列丢弃（FieldMapping 无余额列）→ 导完余额必错且无引导
3. 期初余额创建后改不了（`updateAccount` 无该参数，AddAccountSheet 编辑模式隐藏输入）
4. 调整流水计入月度收支/预算/AI 统计 → 对账一次，当月支出虚高
5. 功能藏在长按菜单叫「调整余额」，无对账心智

## 2. 核心设计

### 2.1 对账闭环模型

```
用户输入真实余额（银行 App 说的）
        ↓
系统算差额 = 真实余额 − 记账余额
        ↓ 三种出路
① 差额 = 0        → 确认对平，写锚点
② 说不清差额来源    → 生成「对账调整」流水抹平 → 写锚点
③ 知道是哪笔记错   → 引导去补记/修改（不写锚点，改完再来对）
        ↓
锚点 = (lastReconciledAt, lastReconciledBalance)
此后余额可信，直到用户动过锚点之前的账（自洽检测发现）
```

### 2.2 调整流水的双重身份（关键口径）

| 口径 | 是否包含对账调整流水 | 原因 |
|---|---|---|
| **余额计算**（getAccountBalance / getCumulativeBalance / getTotalNetWorth / 趋势图余额轴） | **包含** | 不包含则调整失去意义，余额必错 |
| **收支统计**（月收支卡 / 分类聚合 / 预算已花 / 趋势图收支轴 / AI 快照统计 / 看板 / 小组件） | **排除** | 调整不是真实消费，计入会虚增支出/收入 |
| **明细列表**（账单页日历 / 账户详情流水 / AI dynamic_query 明细行） | **显示** | 用户需要能看到「钱为什么变了」 |

识别方式：**Transaction 加 `isReconciliationAdjustment` 布尔标记，不按分类识别**——因为库里可能同时存在两个「余额调整」分类（种子一级 + ensure 二级，见 §8），且「待分类」同为 isSystem，按 isSystem/名字过滤都有脆性。标记在创建时写入，手动记账即使误选「余额调整」分类也不会被误伤。

### 2.3 锚点与自洽性检测

- 写锚点时机：仅当对账页内达成「当前实时余额 == 用户输入的真实余额」（本来就平，或生成调整流水后）才写；用户选「去修那笔账」离开不写。
- 自洽检测：`理论锚点余额 = initialBalance + 锚点时刻之前已发生流水净额`（用 `occurredPredicate(asOf: lastReconciledAt)` 口径，参照 `getCumulativeBalance` 写法）。若 ≠ `lastReconciledBalance`，说明用户改/删过对账前的账（或撤回了导入批次）→ 状态显示「对账基准已变动，建议重新对账」。
- 现有 `adjustBalance` 的调整交易 date 恒为 `Date()`（落在「现在」），回溯锚点前净额时天然不被污染，此特性保持。

## 3. 数据模型改动

### 3.1 新增字段（4 个）

| 实体 | 字段 | 类型 | CloudKit 合规 |
|---|---|---|---|
| Account | `lastReconciledAt` | Date?（可选） | 可选，OK |
| Account | `lastReconciledBalance` | NSDecimalNumber?（可选） | 可选，OK |
| Transaction | `isReconciliationAdjustment` | Bool（**默认 false**） | 非可选必须默认值（isAICreated 先例） |
| Transaction | `importBalance` | NSDecimalNumber?（可选） | 可选，OK |

写法惯例照抄 `creditLimit`（`CoreDataStack+FinanceEntities.swift:393-398`）：NSAttributeDescription + isOptional/defaultValue → append 进数组；`Account.swift` / `Transaction.swift` 同步 `@NSManaged` 声明。无需新索引（`isReconciliationAdjustment` 查询都伴随日期/账户条件，量级无感）。轻量迁移已开启，DEBUG 下跑 `validateCloudKitSchemaDryRun` 校验。

### 3.2 存量迁移（一次性，UserDefaults flag 惯例，参照 migrateCardToCreditCard）

旧「调整余额」产生的交易（分类 isSystem 且 name == 「余额调整」）批量补 `isReconciliationAdjustment = true`，让老用户统计立即修正。谓词命中两份同名分类均可（语义一致）。

## 4. 一期：对账闭环

### 4.1 对账页 ReconcileSheet（新文件，吸收替代 AdjustBalanceSheet）

```
┌ 对账 · 招商银行储蓄卡 ────────────┐
│  账本余额          ¥8,432.10      │
│                                  │
│  银行 App 里的实际余额             │
│  [ ¥8,389.60        ]（空值禁确认）│
│                                  │
│  ⚠ 账本比实际多记了 ¥42.50         │
│                                  │
│  [ 用调整流水补齐差额 ]  ← 主按钮  │
│  生成一笔「对账调整」，不影响收支统计 │
│                                  │
│  差额来自更早的历史？改期初余额 →   │
│  我知道是哪笔记错了，去修改 →      │
└──────────────────────────────────┘
```

- 差额 = 0 态：「✓ 已对平」+「确认无误，记录对账」→ 写锚点。
- 差额 ≠ 0 态：三个动作如上。「改期初」跳 AddAccountSheet 编辑模式（§4.5）；「去修改」关闭 sheet 不写锚点。
- 完成态：✓ 动画 + 「已对平 · 今天」。
- 仓储层：`adjustBalance` 增加 `isReconciliationAdjustment = true` 写入（note 保持「[余额调整]」→ 改「[对账调整]」，新交易起生效）；新增 `markReconciled(account:balance:)` 写锚点。

### 4.2 锚点读写与自洽检测（仓储层）

- `markReconciled(_ account: Account, balance: Decimal)`：写两字段 + updatedAt。
- `getAccountBalance(_ account: Account, asOf date: Date) -> Decimal`：单账户历史口径（`occurredPredicate(asOf:)` 组合，参照 `getCumulativeBalance(before:)` :198-225 的写法），供自洽检测。
- 自洽检测 + 「锚点后新增笔数 count(date > lastReconciledAt)」打包成 `getReconciliationStatus(_ account:) -> ReconciliationStatus` 供 UI 用：

```swift
enum ReconciliationStatus {
    case neverReconciled                      // 从未对账
    case reconciled(date: Date, balance: Decimal)          // 已对平（可信）
    case reconciledWithActivity(date: Date, newCount: Int) // 已对平，其后有 N 笔新账（仍可信，新账未验证）
    case broken(date: Date)                   // 基准已变动（动过锚点前的账），建议重新对账
}
```

### 4.3 状态可视化

- **AccountDetailView**：余额大字下方（:299 后、:301 胶囊行前）加状态行，整行可点进 ReconcileSheet。文案：
  - 已对平：「✓ 已对平 · 3 天前」；其后有新账：「✓ 已对平 · 3 天前 · 此后 12 笔」
  - 基准变动：「⚠ 对账基准已变动，建议重新对账」（暖橙）
  - 从未对账：「建议对账：与银行 App 核对一次，余额更可信」（中性灰，不营造批评感）
  - 数据在 `loadData()`（:847）一并取，不在 body 查库（既有铁律）。
- **AccountListView**：行内余额右侧/下方 11pt 小字，只显示两态「✓ 已对平」/「⚠ 需重新对账」；从未对账不显示（避免列表噪音，新用户满屏「未对账」是负面氛围）。**实施约束：行高不变优先**（账户页列表化改版的教训——一屏看全是硬要求），必要时并入名称行尾部小字而非加高行。

### 4.5 期初余额放开编辑

- `updateAccount` 加参数 `initialBalance: Decimal?? = nil`（双层 Optional 区分「不改」与「改为 0」，与 creditLimit 惯例一致）。
- AddAccountSheet 编辑模式放开 `balanceSection`（删掉 :69-72 的 `if !isEditMode`），显示当前期初，修改时下方实时预览「当前余额将从 ¥8,432.10 变为 ¥8,389.60」，保存前 alert 确认（余额会直接跳变）。**若账户已有对账锚点，确认文案追加「修改期初会使已有对账基准失效，建议修改后再对一次账」**——改期初必破自洽检测（initialBalance 变了→理论锚点余额变了），必须提前讲清，避免「系统引导我改的、系统又说我基准变了」的自相矛盾体验。
- 产品语义引导（ReconcileSheet 的「改期初」入口负责讲清）：**改期初** = 「账从某时刻开始记，之前的钱是历史存量」（适合导入历史账单后校正）；**调整流水** = 「中间发生了一笔说不清的差异」（适合日常对账）。

### 4.6 入口调整

- AccountDetailView 菜单（:88-92）与 AccountListView 长按菜单（:333-340）：「调整余额」改名「**对账**」，图标 `arrow.triangle.2.circlepath` → `checkmark.seal`。
- 详情页余额卡状态行 = 第二入口（点击进对账）。
- AdjustBalanceSheet.swift 删除（被 ReconcileSheet 替代）。

## 5. 二期：导入对账联动

### 5.1 余额列支持

- `FieldMapping`（ImportExportModels.swift:246-280）加 `balanceIndex: Int?`。
- 导入管线（streamImportTransactions / batchImport 两条路径）解析余额列 → 写 `transaction.importBalance`（解析失败留 nil，不阻断导入）。
- BillTemplateDetector：微信/支付宝账单无余额列，不动；银行模板探测到余额表头时自动映射（BillExcelReader:152 已把「余额」当表头识别信号，此处只取值）。
- FieldMappingEditor 补余额列下拉（顺带清掉「未加账单新列编辑」的旧遗留）。

### 5.2 导入完成页对账引导

ImportResultSheet（Views/Settings/ImportResultSheet.swift）在统计行下方新增「余额核对」区块：

- 按 `importBatchId == batchId` fetch 本批交易按账户分组（undoImportBatch :776 已是现成范例）。
- 每个账户组：若组内末笔交易有 `importBalance`（= 账单末行余额 = 导入结束时刻的真实余额），展示「账单余额 ¥X ↔ 当前账本余额 ¥Y，差 ¥Z」；无余额列的账单则仅对「本批新建账户」（importBatchId 命中）提示「新账户从 ¥0 起算，建议核对」。
- 动作：
  - **「以账单为准」**：已有账户 → 生成对账调整流水 + 写锚点；本批新建账户 → 直接设 `initialBalance`（差额 = 账单末行余额 − 本批净流水，等价于把期初补到账单开始前，无需生成流水），**设完期初后同样写锚点**（此时余额恰好等于账单末行余额，锚点即成立）。
  - **「稍后处理」**：跳过，详情页的「从未对账」引导仍在。

### 5.3 账单连续性校验

- 对有余额列的账单，逐笔验证 `balance[i] − balance[i-1] == amount[i]`（金额符号按收支类型归一）。
- 不连续处 → 导入结果提示「第 N 行起余额不连续，账单可能缺行（如两笔同秒交易只导出一行）」，提示不阻断导入。
- 边界（实现时验证）：中性交易（无收/支标记的资金变动，如零钱通划转）可能打破连续性，校验只对 income/expense 行生效，中性行跳过并累计其金额差。

## 6. 边界与不做（三期展望，在档不实施）

- 对账日提醒（账单日/固定周期推送）
- 疑似漏记清单（账单流水 vs 手记账持续软匹配 + 一键入账，可复用导入软去重逻辑）
- AI 感知对账状态（HoloFinanceTool 能答「上次对账什么时候」「最近可能漏账吗」）
- 交易级「清算/未清算」勾选状态（复式记账软件的对勾模型，对 Holo 用户过重）

## 7. CloudKit 与发版

- 4 个新字段全部可选或带默认值，符合 CloudKit 约束（taskId 必填规则的坑不踩）；轻量迁移自动生效。
- **发版前置：CloudKit schema 部署到 Production**（与 v1.0.1 在档的 systemCalendar/categoryLearning 前置同批处理即可）。
- 多设备语义：余额是确定性计算（期初+流水），锚点字段随账户同步，两端自洽检测结论一致，无冲突设计。
- **不需要后端发版**（AI 出口随 iOS 端过滤自然生效）。

## 8. 顺手项（探索发现的既有问题，单独知会东林）

1. **编辑账户切类型不落库**（既有 bug）：AddAccountSheet 编辑模式 `selectedType` 可切换，但 `updateAccount` 无 type 参数，类型改动静默丢失（仅影响信用卡区块显隐）。建议本批顺手修（加 type 参数或编辑模式禁用类型切换，实施时按影响小的做）。
2. **双「余额调整」分类**：种子一级（CategoryPicker 一级列表已隐藏、选不到）+ ensure 二级（CategoryPicker 二级可选，用户手动记账可能选到）。本功能用 isReconciliationAdjustment 标记识别，**不被此问题阻塞**；分类去重作为独立清理项在档，不在本批做。
3. AdjustBalanceSheet 的 noBalanceChange 报错路径随旧 sheet 消亡，ReconcileSheet 差额=0 走「确认对平」分支，不再报错。
