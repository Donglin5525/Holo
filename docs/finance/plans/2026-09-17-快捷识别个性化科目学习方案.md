# Holo 快捷识别：个性化科目学习实施方案

日期：2026-09-17  
状态：供 GLM 实施；本文件是产品与工程规格，不代表功能已开发或上线。

## 1. 产品结论

快捷识别应把「商户」「买了什么」「支付方式」分开理解。支付方式只决定账户线索；商户可提供默认科目建议；商品和用户亲自确认过的规则决定更具体的科目。**不扩充商户词库，不从一笔交易推断这个商户永远只卖一类商品。**

用户可见的闭环：识别账单 → 展示建议科目与依据 → 用户改正 → 可一键选择「记住同类」 → 下次符合相同条件时优先使用该规则。用户以后补充「这次在这家店买了什么」，也能在交易详情建立同一类规则。

本方案优先提升分类正确率和可解释性。金额、收支、支付状态、账户、项目、去重与自动写账资格继续由现有安全门禁决定；分类不确定时可记到「待分类」并给一键修正入口，不因分类猜测阻断一笔本来安全的账。

## 2. 当前代码事实与缺口

- 视觉接口已分别返回顶层 `merchant`、`paymentChannel`、`items`，逐笔返回 `categoryCandidate`、`normalizedCategoryCandidate`、`semanticCategoryHint`。后端 Prompt 要求分类只给语义候选，最终科目在 iOS 本地匹配。
- `FinanceTransactionDraftResolver.matchCategory` 已由聊天和快捷识别共用，顺序为旧学习映射、AI 标准科目、本地科目与 catalog、语义兜底、待分类。
- 旧 `CategoryLearnedMapping` 的键是 `type|primary|candidate`。它无法区分候选词是商户、商品还是备注；同一商户买不同商品可能互相覆盖。
- 快捷识别自动写账只将 `categoryCandidate ?? note` 存进 `Transaction.aiCandidate`；交易没有独立的商户和商品字段。复核草案虽暂存商户，确认后的交易无法可靠重建「商户 + 商品」上下文。
- `ReceiptReviewDetailView` 允许改科目，但确认时没有写入学习规则。普通交易编辑与部分聊天确认路径会自动写旧映射，行为不一致，且可能意外形成宽泛的商户规则。
- 当前视觉评测以金额、商户、支付状态和拦截为主；没有覆盖真实小票的科目正确率及同商户多品类冲突。

实施前先核对上述源码的最新状态，保留工作区已有改动。不要把现有未提交文件一起暂存或提交。

## 3. 关键产品决定（ADR）

### ADR-1：分类在本地完成，模型只提取证据

**决定：**继续使用现有识图服务提取商户、商品、支付状态和语义候选；iOS 的同一个科目决策器组合用户规则与现有科目。首期不改后端 Prompt，不增加每次识别的第二次模型调用。

**理由：**用户科目与个人规则在本地；用一次模型输出直接决定最终科目，既无法稳定尊重用户纠正，也难以解释或回滚。后续只有当真实样本证明现有商品字段不足时，才升级视觉契约与 Prompt。

**代价：**只有付款商户、没有可靠商品信息时，不会凭空知道买了什么；用户需要补充信息或选择商户默认规则。

### ADR-2：规则有明确作用范围，默认不静默学习商户

**决定：**新增两种用户确认规则：

1. `merchantItem`：同一商户 + 用户确认的商品词 → 指定二级科目。优先使用。
2. `merchantDefault`：同一商户在没有可靠商品证据时 → 默认二级科目。用户必须明确选择；系统不从一次改科目自动推断。

一笔交易的分类修改先保存本笔；只有用户点「记住同类」后才写新规则。不能将普通手工交易、未确认的 AI 猜测或整个历史账本自动训练成商户规则。

**理由：**盒马、山姆、便利店、电商等同一商户可对应多种科目。旧候选词映射保留兼容，但不得覆盖更具体、带商品证据的新规则。

### ADR-3：不确定时显示建议，不做宽泛自动套用

**决定：**只有一条明确、目标科目仍有效的规则可以自动套用。单一商品优先使用具体商品规则；多商品只有在全部可判定商品指向同一科目时才可套用。多商品跨科目、同级规则冲突，或商品证据与商户默认相矛盾但没有唯一商品规则时，转「待分类」或展示待确认建议。不要用最近一次分类覆盖历史规则。

**理由：**错误科目会污染预算、分析和 HoloAI 后续判断。一次明显的待分类比长期静默记错更容易恢复。

### ADR-4：规则属于用户的私人数据

**决定：**规则和最小必要识别上下文存于现有 Core Data / 私有 CloudKit 链路；不上传个人规则清单给模型，不长期保存自动成功的原图。用户可查看、修改、停用或删除每条规则。

## 4. 用户流程

### 4.1 快捷识别与复核

成功结果或复核页显示科目与简短依据，例如「日用 · 按你设置的『盒马 + 洗衣液』规则」或「超市 · AI 建议」。不要把模型置信度当作「用户规则」标签。

用户改科目后，保留原来的保存动作；在科目行下增加不打断操作的「记住同类」选择，默认关闭。开启时展示完整预览：

- 有商户与可靠单一商品词：`以后在「盒马」买「洗衣液」→ 购物 / 日用`。
- 有商户、无可靠商品词：只提供明确标注范围的 `以后付款给「盒马」时，默认 → 购物 / 超市`。该默认规则在出现商品证据时只能做建议，不能压过商品判断。
- 商户或商品识别模糊、多笔或多品类：不提供自动生成的具体商品规则；可只保存本笔，之后在交易详情补充商品再创建。

首次自动入账后，用户从结果或账本点开该交易改科目，也能看见相同的规则预览。新规则从下一笔开始生效，不静默批量改写已有流水。

### 4.2 用户后来才知道买了什么

交易详情展示已识别商户，并提供「这次买了什么」的可编辑短文本。用户填入如「洗衣液」、改到「购物 / 日用」、选择「记住同类」后保存，形成 `merchantItem` 规则。此处的商品词由用户亲自输入，优先级高于模型猜测。原图已经清理也不影响建立规则。

### 4.3 HoloAI 对话教学（第二阶段）

支持「以后在盒马买洗衣液算日用」之类的表达，但 HoloAI 只生成**规则预览卡**：商户、商品词、目标科目、作用范围。用户确认卡片后才入库；商户或目标科目有多个候选时要求用户点选。对话教学与复核页使用同一个规则仓库和决策器，不另建 Prompt 内的个人词库。

## 5. 分类决策契约

把现有 `matchCategory` 扩展为接受结构化上下文，并返回 `categoryID + reason + matchedRuleID? + needsConfirmation`。不要在多个 UI 里重复实现排序逻辑。

输入至少包含：收支类型、商户原文、图片商品明细、用户附言或后来填写的商品、逐笔语义候选、交易日期。`paymentChannel` 仅供账户解析，绝不参与科目规则键。只有票面明细或用户明确输入可标记为 `reliableItemEvidence`；模型仅根据商户推导出的归一品类不算商品证据。

确定性优先级：

1. 已确认的 `merchantItem` 规则，商户与商品词都明确命中；有冲突则待确认。
2. 用户明确商品对应的现有分类映射，以及商品对本地科目 / catalog 的唯一明确匹配。
3. 用户确认的 `merchantDefault`，只在没有可靠商品证据时自动生效；有商品证据但尚无可靠科目时只作为建议。
4. 旧候选词学习映射与现有语义候选。候选词若等于商户，且有不同的可靠商品证据，不得让旧商户映射覆盖该商品。
5. 无唯一可靠结果 →「待分类」。

一张小票含多个商品时，仍只生成一笔消费。若商品规则指向不同科目，不能自动拆账或任取第一个；展示待确认建议。餐次判断使用**交易发生时间**，不能用当前运行时间重算历史交易。

## 6. 数据与兼容方案

### 6.1 交易上的最小上下文

给 `Transaction` 增加可选的 `aiMerchantRaw`、`aiItemText` 和 `aiItemSource`（`image` / `user`；限制长度，商品字段只存用于分类的简短文本，不存 OCR 全文、图片或完整购物清单）。自动写账与复核确认均在既有原子写账路径内同时保存这些字段，继续保留 `aiCandidate` 兼容旧学习逻辑。旧交易字段为 `nil`；不凭备注或旧 `aiCandidate` 反向猜出商户和商品。

若 Core Data / CloudKit 模型的可选字段迁移在当前架构中有约束，GLM 可采用同一私有库内按交易 UUID 关联的独立上下文实体，但必须保证首次写账原子性、删除交易时清理及重装恢复。实现前以现有模型迁移机制为准。

### 6.2 新规则实体

新增独立于旧 `CategoryMappingRecordEntity` 的规则实体：`id`、`type`、`merchantKey`、`itemKey?`、`scope`、`targetCategoryID`、`sourceTransactionID?`、`createdAt`、`updatedAt`、`isEnabled`。目标使用真实二级科目 UUID；命中时校验科目仍存在且收支类型一致。已删除或失效科目的规则不套用，在规则管理页提示修复。

规则键仅做保守归一：去首尾空白、统一全半角与大小写、折叠空白和不影响身份的标点。不要自动去掉分店名、把不同商户合并成品牌，也不要做模糊相似商户命中。商品词由用户确认，采用规范化后的完整短语包含匹配；相同商户下优先较长的明确商品词，同优先级不同目标则冲突待确认。

CloudKit 对同一规则键可能产生多行：目标科目相同时按 `updatedAt`，再按稳定 `id` 选唯一版本；目标不同时标为冲突、暂停自动套用，并在管理页让用户处理。不要用模型或最后一次写入静默覆盖两台设备的不同意图。旧映射只读兼容并保持原管理入口；不自动升级为 `merchantDefault`。

### 6.3 个人规则管理

在现有「分类学习映射」页增加「我的商户规则」分组，可查看条件、目标科目和生效状态；支持搜索、修改、停用、删除。规则预览文案必须让用户看得出它覆盖的是「这家店 + 这类商品」还是「这家店的默认科目」。

## 7. GLM 实施顺序与代码位置

1. **纯决策器与测试。** 在 `Services/Finance/ReceiptBooking` 或共享财务分类目录新增结构化输入、规则匹配和来源结果；复用 `FinanceTransactionDraftResolver`，不要新建第二条分类链。先覆盖冲突与优先级测试。
2. **规则持久化。** 扩展 `CoreDataStack+CategoryLearningEntities.swift` 与 `CategoryLearningStore.swift`；新增可等待完成且会报告失败的规则保存接口，不能沿用旧映射「改内存缓存后异步尝试落库」的成功口径。规则写入以用户明确动作触发，读写处理多设备重复键与科目失效。
3. **保留识别上下文。** 贯通 `HoloVisionExtractionService` → `ReceiptBookingCoordinator` / `ReceiptReviewDetailView` → `ResolvedTransactionDraft` → `FinanceTransactionCommandService` / `FinanceRepository.bookTransactionAtomically`。图片成功后仍按既有策略清理。
4. **学习入口。** 复核页、自动入账后交易编辑页接入同一个「记住同类」预览和写入动作。检查 `TransactionSaveHandler`、`ChatViewModel` 的旧自动学习调用，防止它们同时写出更宽泛且覆盖新规则的候选词映射。
5. **管理与解释。** 分类依据显示在结果或交易详情，规则管理页支持修改、停用、删除；错误分类可以一笔改正并纠正规则。
6. **对话教学。** 等前五步稳定后接入 HoloAI 规则预览卡；模型只抽取用户想设置的条件，不直接写规则。

首期不改 `HoloBackend/`。若真实样本证明商品证据抽取不足，再升级 `vision_extraction` 契约与双端 Prompt 版本，按后端发布流程部署并验证；本地构建或提交不算线上生效。

## 8. 必须通过的验收场景

| 场景 | 期望 |
|---|---|
| 微信支付给盒马，只看到商户；用户未设规则 | 不因「微信」决定科目；可显示 AI 建议或待分类 |
| 用户确认「盒马 + 洗衣液 → 日用」后再次识别 | 自动命中日用，回执写明「按你的规则」 |
| 同时存在「盒马默认 → 超市」与「盒马 + 洗衣液 → 日用」 | 买洗衣液用日用；只见商户时用超市 |
| 盒马小票同时有洗衣液和水果，分别命中不同科目 | 不任意选一个、不自动拆账；转待确认 / 待分类 |
| 用户只改本笔、没有点「记住同类」 | 下次不产生新规则 |
| 复核页改科目且明确点「记住同类」 | 当次写账成功后再保存规则；规则写入失败要提示重试，不谎称学会；写账失败不留孤立规则 |
| 旧 `candidate=盒马` 映射与新商品证据冲突 | 不覆盖商品规则；旧记录仍可在管理页看到 |
| 规则目标科目删除或类型改变 | 规则停用 / 待修复，不落到错误科目 |
| 相同商户名不同分店或近似名称 | 未确认别名时不模糊套用 |
| 重复触发同一快捷指令、双设备同步 | 不重复记账；规则读取结果确定；用户删除规则后不再生效 |
| 历史交易截图在晚上才识别早餐 | 餐次按交易时间或明确票面时间，不按识别时刻 |
| 退款、转账、待支付、外币 | 原有拒识 / 复核规则不因分类改造而放宽 |

## 9. 验证与发布口径

- 用至少覆盖单一商户多品类、商品明细缺失、别名不同、混合购物、用户改正、退款等情况的脱敏真实截图集评估：**最终科目正确率、错误自动分类率、待分类率、用户改正次数、规则误命中数**。现有 24 张合成图的金额 / 支付安全跑分不能代替这组分类评测。
- 先运行纯决策器测试，再跑快捷识别内核回归与 iOS Simulator build；随后真机验证快捷指令、后台自动入账、复核、交易编辑、iCloud 双设备规则同步。分别报告结果，不能把编译通过写成真机或线上通过。
- 先让新规则仅给建议，使用真实截图对照并修正冲突；达到「无已知错误自动套用」后再开放唯一明确规则自动分类。分类错误应能通过编辑交易和删除 / 修改规则恢复，不批量改写历史交易。
- 完成定义：用户在一笔账上确认商品与科目并选择记住后，下一笔同条件交易正确分类；同商户其他商品不被污染；规则可解释、可修改、可删除，且原有财务安全门禁和幂等行为不退化。
