## 一、一句话定义

用户主动开启的全局预算约束模式：开启后，当期总预算超支的金额会从**下一个周期**的额度里扣除——「只罚不奖、债务只传导一期」的约束型预算。

产品意图：普通预算是「仪表盘」（告诉你花了多少），严格模式给预算装上「牙齿」（这个月花超了，下个月真的会少）。靠规则本身制造约束感，而不是靠提醒轰炸。

## 二、已定稿的五个决策（2026-08-14 东林拍板，重述）

1. 开关放**全局**：财务设置页一个总开关，一开全开。**→ 已修订（2026-08-18 三批）：改为账户粒度**——预算本身按账户设置，开关跟随账户；设置页「严格预算模式」section 内按账户逐行开关，各账户独立开启/起算。
2. 只作用于**总预算**：各分类小预算保持每期独立，不结转。**「分类严格」经评估一期不做**（见 §10）。
3. 历史不追溯：从开启当期起算（账户粒度后 = 每个账户各自的开启当期）。
4. 周 / 月 / 年预算同规则（各管各的周期：周超支扣下周、月扣下月、年扣下年）。
5. 有效额度下限为 0，不显示负数预算。

## 三、核心规则细化

### 3.1 基本公式

```
有效额度 = 本期原始预算 − 上一期超支结转     （下限 0）
上一期超支 = max(0, 上一期支出 − 上一期原始预算)
```

- **只罚不奖**：上一期省钱了，本期额度不变。
- **只传导一期**：上一期没超，本期恢复原始预算，债务不累积。

### 3.2 「不超」的判定口径（核心规则中唯一需要拍板的歧义点）

「上一期超支」按**原始预算**判定，不按有效额度判定。即：只要上期支出 < 上期原始预算，就算「没超」，本期恢复原始额度。

案例（月预算 ¥10,000）：

| 月份 | 原始预算 | 有效额度 | 实际支出 | 结果 |
|------|---------|---------|---------|------|
| 1 月 | 10,000 | 10,000 | 13,000 | 超支 3,000 |
| 2 月 | 10,000 | **7,000** | 9,000 | 花超了有效额度，但 < 原始预算 → **不算超** |
| 3 月 | 10,000 | **10,000（恢复）** | — | 债务清零 |

理由：定稿原话「下个月不超就恢复原额度——不做成永久债务越滚越多（避免压抑感）」。若按有效额度判定，连续每月花超一点的用户会月月被扣、债务无限传导，违背「避免压抑感」的初衷；且原始口径实现上无需递归追溯，简单可靠。

⚠️ 待拍板点 ①：2 月花 9,000 超出了有效额度 7,000，但按本口径 3 月不被扣。展示上 2 月进度条会是红的（129%）。接受这个「看着超了却不扣」的边界吗？（推荐接受，如上理由；完整用例见下）

### 3.2.1 完整用例（2026-08-18 应东林要求补充，用于拍板口径①）

人物：阿哲，月总预算 ¥10,000，1 月 15 日开启严格预算模式。

**12 月（开启前）**：花了 ¥15,000，超支 ¥5,000。
→ 这笔超支**不会**扣 1 月（历史不追溯）。开启前的账翻篇。

**1 月（开启当月）**：额度 ¥10,000。换手机 + 过年，共花 ¥13,000。
→ 月内进度条在花过 ¥10,000 那天变红，显示「已超支 ¥3,000」。
→ 规则记账：1 月超支 3,000（13,000 − 10,000）。

**2 月（被扣月）**：额度 ¥7,000。
→ 月初打开 App，预算卡显示「¥7,000」+ 小字「上月超支结转 −¥3,000 · 原额度 ¥10,000」。
→ **花到 ¥7,000 的那天进度条就红了**（不用等 ¥10,000）——红色提前出现，正是严格模式的牙齿：你在吃上个月的债。
→ 阿哲收了点手，月底共花 ¥9,000。卡片显示红色「已超支 ¥2,000」、进度 129%。
→ 规则判定：9,000 < 原始预算 10,000 → **2 月「不超」**。

**3 月（恢复月）**：额度回到 ¥10,000，结转小字消失。
→ 只要 2 月没花过 ¥10,000，债务到此清零，翻篇。

**对照：如果「不超」按被扣后的额度（7,000）判定，同一个故事会这样走：**

| 月份 | 额度 | 实际支出 | 判定 | 下月额度 |
|------|------|---------|------|---------|
| 2 月 | 7,000 | 9,000 | 超 2,000 | 8,000 |
| 3 月 | 8,000 | 9,000 | 超 1,000 | 9,000 |
| 4 月 | 9,000 | 9,000 | 超 0 | 10,000 |

阿哲连续三个月花的钱**都不到自己定的 ¥10,000**（从未破自己的规则），却连续三个月 App 红着、额度被压着，要三个月才能爬回 10,000。极端情况（某月大超把额度扣到 0）链条会拖得更长：之后花一分钱都算「超」，压抑感持续发酵。

**本用例揭示的口径①本质**：红色警告和扣款判定用的是两把尺子——警告用紧的尺子（7,000，更早变红、逼人收敛），判定用松的尺子（10,000，回到自己定的规则内就翻篇）。对照口径则是一把尺子到底，惩罚更连贯，但对「没破自己规则」的用户连坐多期。

### 3.3 展示口径与结转口径分离

- **进度条 / 剩余额 / 超支提示**：分母用**有效额度**——用户感知「我这个月还能花多少」，这是严格模式存在的意义。
- **结转计算**：分子基准用**原始预算**（见 3.2）。

两者并存不冲突：进度条爆红是「体验警告」，月底结不结转是「规则判定」。

### 3.4 起算与关闭

- **开启当期**（包含开启日期的那个周期）：有效额度 = 原始预算，**不**被开启前的超支扣（历史不追溯）；但开启当期自己的超支会传导到下一期。
- 实现：记录开启时间点（精确到 Date），某周期 P 应用结转的条件是「P 的上一期起点 ≥ 开启时间所在周期的起点」。
- **关闭即失效**：关闭后所有周期立即恢复原始额度；关闭当期的超支不再传导。重新开启则按新的开启时间重新起算。
- 简化表述：**这个开关控制的是「从现在起要不要记账」，不是「 historical 债务清偿」**。

### 3.5 边界情况清单

| 场景 | 行为 |
|------|------|
| 上一期不存在预算实体 / 无支出数据 | 不扣（超支 = 0） |
| 上一期支出 < 原始预算 | 不扣 |
| 结转额 ≥ 本期原始预算 | 有效额度 = 0，不显示负数 |
| 有效额度 = 0 且本期有支出 | 进度按已超支展示，百分比封顶处理（避免除零） |
| 开启严格模式后又修改预算金额 | 上一期超支按**当前金额**回溯计算（预算实体无历史金额，接受此失真；改预算是小众操作） |
| 严格模式与记账周期起始日 | 互不干扰：结转的「上一期」按预算自身周期锚点（budget.startDate）推导，不跟随记账周期设置变化 |
| 分类预算 | 完全不受影响，分母不变（决策 2） |
| 多账户 | 各账户总预算**各自结转**（A 超支只扣 A）；全局聚合值 = 各账户有效额度之和，与现有「全局 = 聚合」架构一致 |
| 周预算 / 年预算 | 同规则，按各自周期推进逻辑推「上一期」 |

### 3.6 数据落库策略：**不落库，纯实时计算**

- 结转额每次展示时现算（上一期支出是既成事实，支出统计函数已有，直接复用）。
- 不落库的理由：落库需要「周期切换时写快照」的触发时机，跨期时 App 没开就得做补偿计算，复杂度陡增；而实时计算无触发问题、无数据迁移、删掉开关即完全还原。
- 代价见上表「修改预算金额」行，已知并接受。

## 四、技术设计

### 4.1 开关存储：新建 `FinanceBudgetSettings`（`APP/Utils/`）

照 `FinancePeriodSettings` 惯例：`@MainActor ObservableObject` 单例 + `@Published` + `didSet` 写 UserDefaults。

```swift
final class FinanceBudgetSettings: ObservableObject {
    static let shared = FinanceBudgetSettings()
    /// 严格预算模式开启时间；nil = 关闭。开启时间即「起算点」。
    @Published var strictModeEnabledAt: Date?
}
```

用 `Date?` 而非 `Bool`：开启时间本身就是 3.4 起算逻辑的判断依据，一个字段同时承载「开没开」和「从哪期起算」。

### 4.2 计算层：`BudgetRepository` 扩展

1. **`previousPeriodRange(for budget:)`**：现有 `currentPeriodRange(for:)` 是从 `budget.startDate` 逐周期推进到包含 now——把推进过程暴露出「上一期」（推进循环的倒数第二步），周/月/年统一走 `BudgetPeriod.calendarComponent`，**不能**用 `BillingCycleCalculator`（那是记账周期口径，锚点不同）。
2. **`carryoverDeduction(for budget:) -> Decimal`**：算 3.1 的结转额。内部复用 `computeBudgetStatus` 的支出统计 predicate（同账户、同范围、type == expense、分类预算含子类），并套 3.4 的起算条件。严格模式关闭时直接返回 0。
3. **`BudgetStatus` 增加两个字段**（`APP/Models/BudgetStatus.swift`）：
   - `carryoverDeduction: Decimal`（本次扣减额，0 = 无结转）
   - `effectiveAmount: Decimal`（= budgetAmount − deduction，下限 0）
   - 同时把 `remainingAmount` / `progress` / `isOverBudget` / `isWarning` 的计算基准改为 `effectiveAmount`（在构造处统一算好）。
   - `budgetAmount` 字段**保持原始额度语义不变**，避免 AI 快照等既有消费方语义漂移。
4. **聚合层** `computeGlobalTotalBudgetStatus(period:)` 同步：对每个账户的总预算分别算 deduction 后再求和，全局 `totalBudgetAmount` 语义改为各账户有效额度之和（并暴露全局 deduction 合计）。

这样设计的收益：所有读 `progress` / `remainingAmount` / `isOverBudget` 的消费方**自动**切换到有效额度口径，只有直接显示 `budgetAmount` 的位置需要手动换成 `effectiveAmount`，改动面最小。

### 4.3 展示层三处适配（关键：让用户看懂「设了 10,000 为什么显示 7,000」）

| 位置 | 改动 |
|------|------|
| `AccountDetailView.budgetProgressCard` | 金额显示 `spent / effective`；`deduction > 0` 时卡片内加一行说明：「上月超支结转 −¥3,000 · 原额度 ¥10,000」；「已超支 ¥x」的 x 按 effective 计算 |
| `BudgetSummaryCard`（账本页紧凑卡） | 分母换 effective；因空间紧凑，仅当全局 deduction > 0 时在金额下方加一行 11pt 小字「含上月超支结转 −¥x」 |
| `KanbanBudgetSection`（今日看板） | `BudgetCardData` 的 budget 基准换 effective；`overAmount` / `overPercent` 相应换算（effective ≤ 0 且有支出时百分比封顶展示）；「日均可用」自动随新 remaining 联动；deduction > 0 时 overview 加说明行 |

进度条颜色梯度（`budgetProgressColor`）无需改动，progress 换基准后自动生效。

### 4.4 AI 链路

- `HoloFinanceDataSource.snapshot()` 走 `computeGlobalTotalBudgetStatus`，改底层后自动拿到有效额度；`HoloFinanceBudgetSnapshot` 增加 `carryoverDeduction` 字段，摘要文案补一句「其中因上月超支结转扣减 ¥x」，让 AI 能向用户解释额度为何变少。
- **顺手修复已核实的 bug**（随本功能一批）：`FinanceAnalysisContextBuilder.buildBudgetPerformance`（`FinanceAnalysisContextBuilder.swift:354、374`）查预算时传了 `UUID()`——每次生成随机新 UUID，predicate `accountId == 随机值` 永无匹配，导致 AI 的「预算表现分析」**恒为空**。修复：改用 `computeGlobalTotalBudgetStatus` 聚合口径（参照 `HoloFinanceDataSource` 的正确用法）。

## 九、AI 全链路覆盖补齐（2026-08-18 二批，应东林「让 AI 理解预算超支」要求）

AI 读预算共四条链路，首批实施只覆盖了「用户主动问」的对话工具链路，本批补齐其余三条（全部客户端改动，**不需后端发版**——已验证后端洞察 prompt 为「整块 JSON 上下文注入」模式，客户端 context 加字段模型即可读到）：

| 链路 | 触发场景 | 首批状态 | 本批改动 |
|------|---------|---------|---------|
| Agent 对话工具 `budget_status` | 用户主动问预算/超支归因 | ✅ 数值+语义全有 | 无需改 |
| 深度分析上下文 `FinanceBudgetItem` | 深度洞察/分析 | 数值✅ 语义❌ | 加 `originalAmount`/`carryoverDeduction` 字段并填充 |
| 记忆洞察上下文 `BudgetPerformanceSummary` | 周报/月报 AI 回放 | 数值✅ 语义❌ | 加 `originalBudget`/`carryoverDeduction` 字段；「总预算已超支」异常的 evidence 补结转说明 |
| 记忆信号 `FinanceMemoryBudgetInput` | 长期记忆萃取（预算偏离信号） | ❌ **口径 bug：用的还是原始额度** | `budgetAmount` 改填有效额度 + 加 `carryoverDeduction` 字段进 numericFacts |

记忆信号 bug 的影响：严格模式下用户额度被扣到 7000、花 9000，信号层用原始 10000 判定（0.9 < 1.15 阈值）不产生「预算偏离」记忆——AI 记忆系统感知不到真实超支。

已知边界（有意不处理）：有效额度被扣到 0 时不产生预算偏离信号（除零保护，`budgetAmount > 0` guard 挡住）——该月的爆超在上月信号中已体现，债务不重复记账。后端 prompt 不加结转指令提示，靠字段名自解释，待实际效果验证后再决定是否需要后端配合（若加则需发版）。

## 十、三批改造：账户粒度 + 文案与视觉修订（2026-08-18，应东林走查反馈）

- `FinanceBudgetSettings` 重构为 `[UUID(账户): Date(开启时间)]` 存储（UserDefaults JSON），各账户独立开启、独立起算；删除账户的残留 key 不清理（无人读取，无害）。
- `carryoverDeduction(for:)` 改读 `enabledAt(for: budget.accountId)`。
- 结转计算本就是「各账户各自结转、全局=各账户有效额度之和」，计算层仅换开关来源，聚合/展示/AI 链路零改动。
- 设置页 section 改为账户列表：每行「账户圆底图标 + 账户名 + Toggle」（样式对齐 AccountListView 账户行惯例），无账户时整节隐藏。

**2. 说明文案重写**（旧版满篇「计入下一期额度」「从开启当期起算」式记账语言，普通用户读不懂）：
> 超支多少，下个月的预算额度就扣多少（最低扣到 0）；省下的钱不累积，下月不超支就自动恢复原额度。

砍掉的信息：「仅对总预算生效/分类不受影响」（分类严格本就不做，用户无需预先知道边界规则）、「开启当期起算/关闭即恢复」（拨开关看效果即懂，不必预先说明）。

**3. 去掉说明文字旁的 info.circle 图标**（突兀），改为纯左对齐小字。

**4. 「分类预算严格」一期不做的理由**：总预算严格 + 分类严格叠加后两套结转并行（总超扣总、类超扣类），用户心智负担重；分类预算定位是软约束工具，全严格压抑感过强；且开关粒度再加一层（预算编辑 sheet 内）入口分散。建议等账户粒度上线看使用反馈再评估。技术上不难（`carryoverDeduction` 去掉 `categoryId == nil` 限制 + 开关粒度扩展），保留可行性。
