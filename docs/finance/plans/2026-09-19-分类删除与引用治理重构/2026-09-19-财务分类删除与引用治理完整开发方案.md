# Holo 财务分类删除与引用治理完整开发方案

> 日期：2026-09-19  
> 性质：产品规则 + 交互 + 数据契约 + 实施与验收计划  
> 当前状态：方案完成，未实施、未构建、未真机验收  
> 适用范围：iOS 财务分类管理；无后端改动

## 1. 产品结论

当前问题的核心不是“删除按钮不够明显”，而是系统没有建立一条统一的分类退出规则：

- 预设来源被错当成了不可删除权限，导致大多数分类没有删除入口。
- 页面右上角垃圾桶是“清理导入分类”，却被包装成了全局删除，用户无法理解作用对象。
- 分类不只被账目引用，还被预算、固定支出和智能分类规则引用；当前删除逻辑没有给用户完整告知。
- 一级分类是“分组”，二级分类才是“账目归属”；两者不能使用同一套删除方式。

目标体验收敛为一句话：

> 所有用户可见的非系统分类都能从分类行侧滑删除；无引用时简单确认，有引用时先把影响讲清楚，再让用户选择转移或一并删除，且整个操作可恢复、不留悬空数据。

## 2. 需要直接拍板的产品决策

### D1：`isDefault` 不再控制删除权限

- `isDefault`：只表示“这是 Holo 初始提供的预设分类”，供种子数据、图标迁移和诊断使用。
- `isSystem`：才表示“系统内部不变量，用户不可编辑/删除”，例如余额调整。
- UI 删除条件统一改为 `!category.isSystem`。

用户影响：餐饮、交通、购物等预设分类不再被强制留在用户账本中。

### D2：右上角只保留新增，移除垃圾桶

- 页面右上角保留“+”，用于新增一级分类。
- 删除必须从具体分类行侧滑发起，使作用对象明确。
- 原“清理导入分类”能力暂从分类页下线。如仍需保留，改到“设置 → 数据管理 → 清理导入分类”，使用文字行，且只处理 `importBatchId != nil` 的分类。

### D3：删除账目不是默认动作

- 默认选项：保留账目及关联配置，转移到其他分类。
- 危险选项：账目与分类一并移入回收站，需二次确认并精确展示数量与金额。
- 不使用“删除”作为两种处理的通用确认文案。主按钮需写成“转移 23 笔并删除分类”，危险按钮写成“删除 23 笔和分类”。

### D4：一级分类和二级分类走不同的删除流程

- 二级分类：处理该分类下的账目和配置去向。
- 一级分类：优先处理子分类去向，而不是把全部账目压到一个二级分类。

### D5：删除进入 30 天回收站

- 分类、选择一并删除的交易、预算和固定支出统一标记同一 `deletedBatchId`。
- 分类删除完成后提示“已删除，30 天内可从最近删除恢复”。
- 不做物理删除，避免误操作无法恢复，也避免预设分类在启动补种时复活。

## 3. 目标交互

### 3.1 分类列表

- 所有 `!isSystem` 分类行支持侧滑露出“删除”。
- 保持 `allowsFullSwipe = false`，避免滑动过头直接触发高风险操作。
- 系统分类不显示删除；如用户从辅助功能尝试触发，返回明确原因“此分类用于系统账务调整，不能删除”。

### 3.2 二级分类删除

#### 场景 A：无任何引用

1. 用户侧滑点击“删除”。
2. 简短确认：“删除「咖啡」？30 天内可在最近删除中恢复。”
3. 确认后软删除，列表原地更新，底部 toast 提示成功。

#### 场景 B：有账目或关联配置

打开“删除「咖啡」”影响处理页：

1. 顶部影响摘要：
   - 23 笔账目，合计 ¥680.50；
   - 1 项预算；
   - 2 项固定支出；
   - 3 条智能分类规则。
2. 默认方式“转移后删除分类”：
   - 必须由用户选择一个同收支类型的二级分类；
   - 不预先选中“待分类”，避免用户没看懂就确认；
   - 选择器中“待分类”置顶，作为主动选择的安全暂存位。
3. 次要危险方式“账目与分类一起删除”：
   - 选中后再弹二次确认；
   - 精确列出将删除的账目、预算、固定支出数量；
   - 确认文案不声称“无法恢复”，而是告知 30 天回收站。
4. 账目明细区：
   - 展示日期、账目名/备注、账户、金额、导入来源/分期标记；
   - 按日期倒序，支持分页而不是只显示前 100 笔的无入口截断；
   - 点击明细可进入只读账目详情，帮助用户辨认。

### 3.3 一级分类删除

一级分类是子分类的容器，不直接挂账目。处理页首先展示：

- 16 个子分类；
- 328 笔账目；
- 关联预算、固定支出和智能分类规则数量。

提供两种互斥处理：

#### 方式 1：保留子分类，移到另一个一级分类（默认）

- 用户选择同收支类型的目标一级分类。
- 所有子分类修改 `parentId`，账目、预算、固定支出和学习规则仍指向原二级分类，语义损失最小。
- 子分类颜色统一跟随新父分类，保持页面视觉一致。
- 如目标一级分类已有同名子分类，显示冲突页，让用户选择“合并到已有分类”或“保留两个并重命名”。

#### 方式 2：删除整个分组

- 不允许用一个目标分类承接所有子分类账目。
- 用户按子分类逐项选择“转移到某二级分类”或“一并删除”。
- 提供批量快捷操作“全部转到待分类”，但必须由用户主动点击，不默认勾选。
- 所有子分类完成去向设置后，才允许提交。

### 3.4 特殊边界

| 边界 | 目标行为 |
|---|---|
| 只有空子分类的一级分类 | 确认页告知将删除 N 个空子分类，不显示账目处理 |
| 没有其他同类型二级分类 | 可选“待分类”；如不存在，在预检阶段创建，但不在纯浏览选择器时隐式写库 |
| 分类在处理页开启后被 CloudKit 改变 | 提交前重做预检；引用数已变更则停止提交并刷新影响报告 |
| 转移目标在确认前被删除 | 执行失败，不做任何部分写入，要求重选 |
| 交易收支类型与分类不一致 | 视为旧数据异常，在影响页标记“需修复”，禁止静默转移 |
| 软删除中的历史账目仍引用该分类 | 预检单独计数；移动分类时同步改指，删除整组时保留同批恢复契约 |

## 4. 统一引用治理规则

### 4.1 预检报告必须是单一事实源

UI 不再自己只查交易，仓库也不得在执行时偷偷补删其他数据。新增一个预检契约：

```swift
struct CategoryDeletionImpactSnapshot: Sendable, Equatable {
    let sourceCategoryID: UUID
    let sourceRevision: CategoryDeletionRevision
    let scope: CategoryDeletionScope
    let childCategories: [CategoryImpactItem]
    let liveTransactions: [TransactionImpactItem]
    let recycledTransactionCount: Int
    let budgets: [BudgetImpactItem]
    let spendingProjects: [SpendingProjectImpactItem]
    let learnedMappings: [LearnedMappingImpactItem]
    let blockers: [CategoryDeletionBlocker]
}
```

`sourceRevision` 至少由分类 ID、父 ID、更新快照和各类引用数摘要组成；提交时重算并比较，用来拦截过期处理页。

### 4.2 执行请求必须完整表达用户决策

```swift
enum SecondaryCategoryDisposition: Sendable, Equatable {
    case moveAll(toCategoryID: UUID)
    case deleteWithReferences
}

enum PrimaryCategoryDisposition: Sendable, Equatable {
    case moveChildren(toParentID: UUID, conflicts: [UUID: ChildConflictResolution])
    case disposeChildren([UUID: SecondaryCategoryDisposition])
}

struct CategoryDeletionCommand: Sendable, Equatable {
    let sourceCategoryID: UUID
    let expectedRevision: CategoryDeletionRevision
    let disposition: CategoryDeletionDisposition
}
```

仓库入口改为 ID + 值类型指令，不跨弹层长时间持有 `NSManagedObject`，避免对象在 CloudKit 合并或删除后失效。

### 4.3 各类引用处理

| 引用 | 转移分类 | 一并删除 | 特殊冲突 |
|---|---|---|---|
| 正常交易 | `transaction.category = target` | 标记同一回收站批次 | 目标必须同收支类型且为二级 |
| 已在回收站的交易 | 同步改指，保证未来恢复可用 | 保留原批次或按恢复引擎的依赖规则处理 | 不能遗留恢复后无分类的交易 |
| 预算 | 改指 `categoryId` | 进入同一批次 | 目标已有同账户+周期预算时，要求用户选择合并金额或保留目标 |
| 固定支出/一次性购买 | 改指 `categoryId`，未来自动记账继续有效 | 进入同一批次，明确告知将停止未来自动记账 | 不允许留下无效 `categoryId` |
| 智能分类映射/归纳规则 | 改指目标；旧名称模型同步更新目标一/二级名 | 删除规则并生成 tombstone，防止 CloudKit 旧副本复活 | 后续升级 UUID 目标后只改指 ID |
| 分类本身 | 一级迁移时改 `parentId` | 标记同一批次 | 同名子分类需先解决合并/重命冲突 |

### 4.4 原子性与恢复

一次分类删除提交只允许两种结果：

1. 所有交易、预算、固定支出、学习规则和分类全部处理成功；
2. 任何一项失败，整次 `context.rollback()`，用户的任何数据都不变。

回收站恢复时：

- 整批删除：恢复分类和同批交易/预算/固定支出；
- 转移后删除分类：只恢复分类本身会形成空分类，不自动把已转移的数据抢回来；回收站摘要要写清“数据已转移到××”。

## 5. 需要废弃的当前实现方式

1. 废弃 `!category.isDefault && !category.isSystem` 的删除入口判断。
2. 废弃页面右上角无标签垃圾桶。
3. 废弃使用 `isDefault == NO` 猜测“导入分类”。
4. 废弃转移目标中允许一级分类。
5. 废弃删除一级分类时将所有账目打平转到单一目标。
6. 废弃在 `deleteCategory` 中静默物理删除预算。
7. 废弃 `context.delete(transaction/category)` 作为用户可见删除的默认终态。
8. 废弃让弹层长时间持有可失效 `Category` 对象的请求形态。

**输出**

- 建立“分类删除前置报告”测试样本，覆盖空分类、有账目、有预算、有固定支出、有学习规则、一级分类和 iCloud 重复行。

**验收**

- 测试能稳定复现当前缺口；不以 UI 截图代替数据断言。

### Phase 1：建立纯值类型删除策略核心

**建议文件**

- `Models/Finance/CategoryDeletionPolicy.swift`
- `HoloTests/Models/CategoryDeletionPolicyStandaloneTests.swift`

**输出**

- 上文的 impact snapshot、command、disposition、blocker 和 conflict 类型。
- 无 Core Data 依赖的候选过滤与提交可用性规则。

**验收**

- 一级分类绝不能作为交易转移目标。
- 收入和支出绝不互转。
- 所有子分类都有去向前，一级分类整组删除不可提交。

### Phase 2：实现统一预检与原子执行仓库

**建议文件**

- `Models/FinanceRepository+CategoryDeletion.swift`
- `Models/CategoryLearningStore.swift`

**输出**

- `categoryDeletionImpact(categoryID:)`
- `executeCategoryDeletion(_ command:)`
- 一次 context transaction 内完成交易、预算、固定支出、学习规则和分类处理。
- 对同 ID CloudKit 重复行做统一归并，但不把不同 ID 的同名分类自动当成同一对象。

**验收**

- 每种处理都没有无分类交易、悬空预算/固定支出和指向已删分类的学习规则。
- 人为注入保存失败后，所有对象保持原状。

### Phase 3：重构分类管理 UI

**建议文件**

- `Views/CategoryManagementView.swift`

**输出**

- 移除右上角垃圾桶。
- 所有非系统分类开放侧滑删除。
- 二级分类影响处理页和一级分类子分类去向页。
- 预检、提交中、成功、失败/过期的完整状态。

**验收**

- 用户从任意非系统分类行都能找到删除。
- 看到的精确数量与仓库预检一致。
- 不会因删除 NSManagedObject 后 SwiftUI 仍渲染而崩溃。

### Phase 4：回收站、CloudKit 和补种收口

**输出**

- 分类删除批次在“最近删除”中有可理解摘要。
- 恢复分类及同批数据时保持引用完整。
- 删除预设分类后冷启动不复活；回收站过期物理清理后，也必须通过持久化 tombstone/用户分类隐藏偏好阻止重新补种。

> 重要：现有软删除行在 30 天内可阻止补种，但物理过期后该行会消失。要长期尊重“用户删过预设分类”，必须额外保留一份同步的预设分类 tombstone，或把补种改为只在真正新用户首次初始化执行，不再按缺失项补齐。推荐后者：种子是初始模板，不是持续强制的系统清单。

### Phase 5：真实数据旅程验收

**输出**

- 完成下文测试矩阵的自动化与手工旅程。
- 真机双设备 CloudKit 验收记录，包含冷启动、离线操作后合并和恢复。

## 7. 测试矩阵

### 7.1 策略核心测试

1. 预设非系统分类可删；系统分类不可删。
2. 转移目标只包含同类型二级分类。
3. 源分类、其子分类和已删分类不进入候选。
4. 一级分类整组删除中，任一子分类未选去向则不可提交。
5. 一级分类迁移后交易仍指向原二级分类。
6. 同名子分类冲突必须显式解决。

### 7.2 Core Data 集成测试

| 用例 | 断言 |
|---|---|
| 删除空自定义二级分类 | 分类有 `deletedAt/deletedBatchId`，其他数据不变 |
| 删除空预设二级分类 | 操作成功，冷启动不复活 |
| 有交易的二级分类转移 | 全部正常/历史软删交易指向正确目标，收支类型不变 |
| 一并删除 | 分类、正常交易、预算和固定支出进入同一批次 |
| 预算转移无冲突 | `categoryId` 改指，金额/周期不变 |
| 预算转移有冲突 | 未提供冲突决策时整体不提交 |
| 固定支出转移 | 下一次自动生成的交易使用新分类 |
| 智能规则转移 | 后续相同商户/商品命中新分类 |
| 保存中途失败 | 所有对象 rollback，无半转移/半删除 |
| 同 ID 存在 CloudKit 重复行 | 预检和执行数量一致，不留幽灵分类 |

### 7.3 UI 旅程测试

1. 从预设分类和自定义分类都能侧滑看到删除。
2. 右上角只有新增，不再出现语义不明的垃圾桶。
3. 无引用分类在一次确认后消失，并出现可恢复提示。
4. 有引用分类的影响摘要和明细列表数量一致。
5. 未选目标分类时，“转移并删除”不可点击。
6. 选择“删除账目”后出现第二次精确确认。
7. 一级分类迁移和整组删除的界面、文案和结果明确不同。
8. VoiceOver 能读出分类名、删除动作、影响数和当前处理选项。

### 7.4 真机双设备/CloudKit

1. A 设备删除分类，B 设备观察分类、账目、预算和固定支出同步结果。
2. A 设备离线打开影响页，B 设备更改相关数据，A 联网后提交必须检测 revision 过期。
3. A/B 设备同时对同一分类做不同转移，必须可确定性收敛，不留无分类账目。
4. 恢复删除批次后，两台设备的分类层级和引用一致。
5. 卸载重装并等待 iCloud 回流后，用户删过的预设分类不复活。

## 8. 发布和回退

### 发布策略

1. 先上线统一预检与新仓库，但保持 UI 入口受 feature flag 控制。
2. 内部数据执行自动化矩阵，完成真机单设备验收。
3. 完成双设备 CloudKit 和回收站恢复验收后再开放全部非系统分类删除。

### 回退策略

- 关闭新删除 UI 入口，不回滚已产生的软删除数据。
- 已进入回收站的批次仍按统一恢复引擎处理。
- 不恢复旧的物理删除方式；如新执行器有问题，暂停删除比退回不可恢复的旧方式更安全。

## 9. 完成定义

只有同时满足以下条件，才可将这项工作标记为完成：

- [ ] 所有非系统预设/自定义分类均可侧滑删除。
- [ ] 右上角垃圾桶已移除。
- [ ] 二级分类有引用时能看到完整账目和配置影响。
- [ ] 一级分类不再把所有子分类账目压到单一目标。
- [ ] 交易转移目标只能是同类型二级分类。
- [ ] 预算、固定支出和智能分类规则不存在悬空引用。
- [ ] 删除引用回收站批次，可恢复，不做不可逆物理删除。
- [ ] 删除预设分类后，冷启动、CloudKit 合并和卸载重装后均不复活。
- [ ] 策略核心、Core Data 集成、UI 旅程和真机双设备验收全部通过。

## 10. 给开发执行者的边界

- 不覆盖或回滚当前工作区中 `CategoryManagementView.swift` 和 `FinanceRepository+Categories.swift` 的未提交改动；必须在当前 diff 上收敛重构。
- 不将“编译成功”当成数据闭环完成；必须检查真实对象 ID、关系、软删除批次和冷启动结果。
