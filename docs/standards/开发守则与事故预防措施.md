# Holo 开发守则与事故预防措施

> **本文档是硬性规定，不是建议。**
> 每次开始做需求前，必须先通读本文档；做完需求、交付前，必须对照「交付前自检清单」逐条确认。
>
> 来源：2026-08-05 纪念日模块「保存后界面无响应」事故复盘。该事故连续四轮误判未修复，
> 根因是交付流程中缺失「观察证据 → 验证行为」环节，只以「编译通过」作为交付标准。

## 一、事故复盘（为什么会反复改不好）

### 事故现象

纪念日模块保存后整个界面无响应（能显示、点不动、只能重启 App）。连续修改四轮仍未解决。

### 真正的根因

`HoloToastCenter.show()` 创建了一个全屏、最高层级、永不销毁的 `ToastPassthroughWindow`，
内部占满全屏的 `Color.clear` 没有加 `.allowsHitTesting(false)`，导致这个看不见的视图
吃掉了所有触摸事件——**界面没有死锁、没有阻塞，纯粹是触摸被拦截**。

### 四轮误判的错误模式（必须引以为戒）

| # | 错误做法 | 为什么错 |
|---|---------|---------|
| 1 | 把用户描述当「事实」而非「待验证假设」 | 用户说「卡死」，就默认是死锁/阻塞，只往这个方向找；实际是触摸拦截，属于完全不同的诊断分支 |
| 2 | 证据与假设冲突时忽略证据 | `sample` 采样显示主线程完全空闲（不是死锁），与「卡死」矛盾，这本是决定性线索，却绕了一轮才回头 |
| 3 | 以「编译通过」作为交付标准 | 编译通过 ≠ 行为正确。从未真正跑通「保存→不卡死」的完整验证就把代码交付，等于把验证责任推给用户 |
| 4 | 盲从「对齐参考模块」却没找到最小差异 | 财务模块从不卡死，机械照抄了 Task/isSaving 结构，却漏掉最关键差异：**财务保存成功从不弹 toast，纪念日每次都弹**。参考对比必须找到「好/坏之间的唯一行为差异」 |
| 5 | 没有证据的破坏性重构 | 为了「防阻塞」把 Repository 改成后台上下文 + 主线程直接调用（违反 Core Data 线程安全），引入了新 bug 源。禁止在没有证据时做大重构 |

## 一之二、事故复盘（2026-08-06 键盘避让，同一错误模式重演）

### 事故现象

想法模块首页点搜索框，键盘弹出时搜索框（连同整页）被整个顶起，看不到输入内容。
用户连续反馈「没修好」共三轮。

### 真正的根因

iOS 17 的 SwiftUI 键盘避让对「**不在 ScrollView 内的聚焦 TextField**」会直接**平移整个
hosting view**（不是通过 safeArea 调整）。因此 `.ignoresSafeArea(.keyboard)` 对这种场景
**不可靠**（Apple 论坛 658432 多年未修）。HomeView 是 ZStack 常驻架构（所有模块叠放），
系统避让把整个图层推出屏幕，顶部搜索框首当其冲。

**正确修复**：UIKit 层 `UIHostingController.safeAreaRegions = .container`（去掉 `.keyboard` 区域），
iOS 16.4+ 官方 API。已沉淀为可复用组件：`Utils/KeyboardAvoidanceDisabler.swift`（`disableKeyboardAvoidance()`）。

### 三轮误判的错误模式（与纪念日事故同源）

| # | 错误做法 | 为什么错 |
|---|---------|---------|
| 1 | 没复现就凭代码推断根因 | 三轮都在猜「safeArea 被压缩」，实际是 hosting view 平移，完全不同的机制 |
| 2 | 同一条路反复走 | `.ignoresSafeArea(.keyboard)` 换三种写法（不带 edges / 带 bottom / 挪层级），方向错了再多变体也没用 |
| 3 | 没先确认现象细节 | 用户说「压缩」就默认是高度变小，实际是「整页顶起」。**第一轮就该用提问确认现象**，省掉两轮无效修改 |
| 4 | 没用外部资料验证机制 | 第三轮才用 WebSearch 确认「ignoresSafeArea(.keyboard) 对 UIHostingController 不可靠」是已知问题。**换方向前先查证** |

### 新教训（本次新增）

1. **「编译通过 + 逻辑自洽」≠ 行为正确**：前两轮代码逻辑都说得通，但根因机制就是错的。改 UI 交互类问题，必须先确认现象细节（提问），再找机制证据（外部资料/工具），最后才动代码。
2. **同类布局一起查**：顶部搜索框（想法/任务/财务）在 ZStack 常驻架构下都有此隐患，一次全局修复，不要只补一个页面。

## 二、核心方法论：复现 → 观察 → 假设 → 验证 → 根治

任何问题（尤其「卡死/无响应/白屏」类），按以下顺序执行，**禁止跳过观察直接改代码**：

```
复现 → 观察 → 假设 → 最小化验证 → 根治 → 全量验证
```

### 1. 复现（先跑起来）
- 在模拟器/真机实际复现问题，不要只看代码猜
- 记录复现步骤和触发条件（如：首次保存？每次保存？）

### 2. 观察（看到事实再动手）
iOS「界面无响应」至少分四类，先区分是哪种：
- **主线程阻塞/死锁**：用 `sample <pid>` 抓主线程栈，看是否卡在业务代码
- **触摸被拦截**：主线程空闲但点不动 → 用 `lldb` 打印 `UIApplication.shared.windows`，检查是否有非隐藏的全屏 window 盖在顶层
- **动画/presentation 状态卡死**：sheet/fullScreenCover 状态未复位
- **纯性能问题**：CPU 高、掉帧

**工具**：
- `sample <pid> 5 -file /tmp/x.txt` → 看主线程栈
- `lldb -p <pid>` → `expr -l objc -O -- [[UIApplication sharedApplication] windows]` → 看窗口层级
- `xcrun simctl spawn <udid> log show --last 5m --predicate 'process == "Holo"'` → 看日志

### 3. 假设（基于证据，不是猜测）
- 每个假设必须能从观察结果推导出来
- **证据与假设冲突时，立即怀疑假设，而不是忽略证据**（第 2 条错误）

### 4. 最小化验证（一次只改一处）
- 先做最小改动验证假设（如：加一行 `.allowsHitTesting(false)`）
- 禁止一次改多个不相干的地方，否则无法归因

### 5. 根治（修根因，不修表面）
- 根因修复后，检查是否还有**同类隐患**（如：修纪念日 toast 后，还要检查其他模块是否也踩同一个坑）
- 禁止「哪里报错补哪里」，也禁止「没有证据的大重构」

### 6. 全量验证（交付前必须做）
- 在模拟器跑通完整操作流：进入 → 新增/编辑 → 保存 → 返回 → 再次操作
- 用 `sample` 确认主线程无异常
- **确认行为正确后才交付，不是编译通过就交付**

## 三、交付前自检清单（每次交付前逐条过）

- [ ] 编译通过（必要不充分）
- [ ] 在模拟器/真机**实际跑通**核心操作流（新增→保存→返回→再操作）
- [ ] 若涉及保存/网络/IO：确认保存后界面可继续交互（用 `sample` 验证主线程空闲）
- [ ] 若涉及弹窗/sheet/fullScreenCover：确认关闭后无残留层（用 `lldb` 检查 window 层级）
- [ ] 若涉及输入框 + 键盘：确认键盘弹出时布局稳定、输入框不被顶起/遮挡；「顶部输入框 + 底部键盘」互不重叠时**不需要避让**，直接用 `disableKeyboardAvoidance()`
- [ ] 若参考其他模块：确认找到了「好/坏模块之间唯一的行为差异」，不是机械照抄
- [ ] 改动是否引入了新的跨线程/跨上下文风险（Core Data 对象、UIKit 对象）
- [ ] 删除/清理调试用的临时代码、日志、打印

## 四、踩过的坑速查表（遇到直接查）

| 症状 | 第一嫌疑 | 验证方法 |
|------|---------|---------|
| 保存后界面无响应，能显示点不动 | 全屏透明视图/窗口拦截触摸（`Color.clear` 未禁命中、Toast/overlay window 残留） | `lldb` 打印 windows；检查 `allowsHitTesting` |
| 键盘弹出时顶部输入框/整页被顶起，看不到输入内容 | iOS 17 keyboard avoidance 平移整个 hosting view（聚焦 TextField 不在 ScrollView 内时），`.ignoresSafeArea(.keyboard)` 对此不可靠 | 挂 `disableKeyboardAvoidance()`（见 `Utils/KeyboardAvoidanceDisabler.swift`，`safeAreaRegions = .container`）；或把 TextField 放进 ScrollView 内 |
| 主线程卡死 | 同步锁、`DispatchQueue.main.sync`、Core Data 主线程 save 阻塞 | `sample` 看主线程栈 |
| sheet/fullScreenCover 关闭后界面异常 | 同一视图挂多个 `.sheet`；presentation 状态未复位 | 检查 sheet 修饰符数量；检查绑定状态 |
| Core Data 崩溃/数据错乱 | 跨上下文使用托管对象；private queue context 在主线程直接调用 | 后台操作用 `performBackgroundTask`；对象传值不传引用 |
| SwiftUI 状态不同步 | `@StateObject` 包单例、`@Published` 与通知混用 | 对照财务/任务模块的成熟模式 |

## 五、写作与协作约定（沿用 AGENTS.md）

- 通俗解释优先：面向产品经理讲清「为什么」，再补充必要术语
- 客观陈述事实：有问题说问题，不掩盖、不美化
- 全局性思维：改动从整体结构出发，禁止打补丁
- 少写防御性代码：只在确有必要的边界做校验，让问题尽早暴露
- 需要后端发版时，主动同步告知改动内容、是否发版、影响范围
