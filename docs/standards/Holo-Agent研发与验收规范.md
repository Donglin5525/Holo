## 1. 产品完成标准

一个 Agent 功能只有同时满足以下条件，才算“完成”：

1. **用户问题被直接回答**：首屏先给结论，不以数据罗列代替回答。
2. **结果可行动**：用户问“怎么优化”时，必须给出有依据、可执行、按优先级排列的建议。
3. **数据可信**：时间、金额、单位、样本、统计口径和数据边界与真实数据一致。
4. **不确定性诚实**：缺数据、覆盖不足或能力受限时，只描述真实边界，不制造虚假警告。
5. **结果可读**：相同语义使用相同视觉层级，主范围与局部范围清楚，信息不堆砌。
6. **任务状态真实**：运行、等待、恢复、完成、失败和取消必须与持久化任务状态一致。
7. **线上确实生效**：涉及后端 Prompt 或协议时，必须完成生产部署与线上行为验证。

“代码能编译”“模型返回了文字”“工具查到了数据”都不能单独作为 Agent 可用的证明。

## 2. 核心架构原则

### 2.1 每种语义只能有一个真相源

| 语义 | 唯一真相源 | 其他层的职责 |
|---|---|---|
| 用户问题与回答目标 | `HoloAgentAnswerTask` / Job | Renderer、UI 不重新猜用户想问什么 |
| 主时间范围、baseline、快照日 | Job / `HoloAgentAnswerContext` | Tool 执行，Renderer 展示，UI 只消费 |
| 数据形态与覆盖语义 | Tool / Data Source | Verifier、Renderer 按类型化语义执行策略 |
| 数值事实和血缘 | Evidence Ledger | LLM、Composer、Verifier只能引用，不能重算另一套 |
| 是否可交付 | Verifier | UI 不自行放宽或升级结论 |
| 建议顺序和优先级 | 类型化 `recommendations` | 卡片不从自然语言和 `sections.kind` 推断 |
| 任务运行状态 | 持久化 Job + Message | 页面内存态只做缓存 |

**禁止在下游建立第二套解释器。**  
如果 Renderer、UI 或 Prompt 需要重新解析年份、覆盖率、建议序号或任务状态，说明上游契约缺字段，应修契约而不是补字符串判断。

### 2.2 确定性规则归代码，开放性判断交给模型

必须由代码决定：

- 时间窗口和快照截断；
- 已发生与未来计划的边界；
- 金额、比率、均值、增减方向和单位；
- 覆盖率是否适用于该数据形态；
- Evidence ID、数值一致性和禁止因果边界；
- 建议结构、排序和展示层级；
- 状态机、预算、幂等和恢复。

可以交给模型：

- 选择下一步需要查询的工具；
- 在证据范围内解释“为什么值得关注”；
- 对多个已验证事实做克制的归纳；
- 生成自然、符合 Holo 人格的表达。

**Prompt 不能替代数据契约、状态机或验证器。**

### 2.3 数据链路必须保留语义，不只传字符串

工具结果不能只留下 `value + unit + displayText`。至少要能表达：

- 数据领域与数据集；
- 指标与统计操作；
- 当前值、基线值和结果值各自扮演的角色；
- 维度、分组、方向和显示单位；
- 时间范围、快照日和覆盖语义；
- Evidence 血缘；
- 敏感度与可推断边界。

下游如果只能看到自然语言，就只能猜；一旦开始猜，跨领域结果一定会漂移。

## 3. 时间与历史事实规范

1. 用户明确指定的时间优先于默认时间。
2. Job 创建时冻结主范围、baseline 和 `snapshotCutoffAt`。
3. Renderer 和 UI 不得再次解析用户原话推导时间。
4. 历史事实查询使用 `[start, min(requestedEnd, snapshotCutoff))`。
5. 未来分期、未来任务、未来计划不能计入“已发生”“已经花了”“完成了多少”等历史结论。
6. 用户询问尚未结束的自然年时，展示为“2026年 · 截至7月26日”等明确口径。
7. 某条建议引用的范围不同于主范围时，必须在该建议上显式标注局部范围。

### 必测边界

- 当前年、上一年、显式年份；
- 当前月、上月、跨月比较；
- 今天、最近 N 天、自定义范围；
- 完整未来范围；
- 跨时区的日边界；
- 年度问题引用本月预算等局部证据。

## 4. 数据覆盖规范

覆盖率必须先声明数据形态，再决定是否展示：

| 数据形态 | 示例 | 覆盖策略 |
|---|---|---|
| `eventRecords` | 交易、任务、想法、打卡事件 | 没有事件也可能是真实事实；禁止用日历天数判断完整度 |
| `dailyObservations` | 步数、睡眠、每日体重 | 可以展示日度覆盖，并据此限制趋势结论 |
| `currentSnapshot` | 当前余额、当前任务状态 | 不使用日历覆盖率 |

强制规则：

1. 未声明覆盖语义时，默认不推断、不警告。
2. `132/365` 只有在“预期每天都有观测”的数据上才有意义。
3. 覆盖不足不能自动等于“数据不可用”；应区分可给事实、可给弱趋势、必须拒绝三种状态。
4. 覆盖文案、限制说明和 Verifier 判断必须共用同一策略，禁止各写一套阈值。

## 5. 答案与建议规范

### 5.1 回答结构

专业分析默认遵循：

1. **直接答案**：一句话回答用户最关心的问题。
2. **优先建议**：用户要求优化、规划或行动时展示。
3. **关键依据**：只放支撑结论的少量事实。
4. **数据边界**：确有必要时才展示。
5. **证据入口**：需要核对时可下钻到原始明细。

禁止用固定的“事实/变化/模式/建议”模板机械堆满所有卡片。

### 5.2 建议必须类型化

每条建议至少包含：

- 稳定 ID；
- 动作标题；
- 解释正文；
- 优先级；
- Evidence ID；
- 置信度；
- 与主范围不同时的局部范围标签。

同一条建议只能有一个展示来源。禁止：

- 把建议 1 放进开场大字、建议 2 放进卡片；
- 从“建议1（高优先级）”等自然语言中长期解析结构；
- UI 根据正文长度、序号文字或 `sections.kind` 自行重排。

旧消息兼容只能在一个适配边界完成，适配后统一转换为新结构。

### 5.3 “查询”和“建议”要区分

- 用户只问“多少、哪些、什么时候”时，准确回答即可，不附送泛泛建议。
- 用户明确问“如何优化、怎么改善、下一步做什么”时，必须给有证据的建议。
- 没有足够依据时，不用“合理控制、保持规律、继续加油”等通用话术充数。

## 6. 证据、验证与降级规范

每条用户可见结论必须可追溯到 Evidence。

Verifier 至少检查：

- Evidence 是否存在；
- 指标、数值、单位、时间窗口是否一致；
- 样本和覆盖语义是否允许该结论；
- 是否重复引用同一血缘伪装成多证据；
- 是否把相关性写成因果；
- 是否越过医疗、心理或其他高风险边界。

交付状态使用三态思维：

- `verified`：可直接交付；
- `degraded`：事实可交付，但必须说明具体边界；
- `rejected`：关键事实无法验证，不得包装成正常结论。

降级文案必须说清“缺什么，因此不能判断什么”，不能只写“证据覆盖不足”。

---

## 7. 运行可靠性与状态规范

1. 坏 JSON、SSE 截断、旧协议字段或单轮格式错误属于可恢复故障，不能立即终止整个任务。
2. 恢复必须受 Job 总预算约束，不能由独立的局部重试次数提前失败。
3. 同一 `runId + stepId + requestHash` 必须幂等，恢复不能重复调用工具或重复扣费。
4. Checkpoint 必须包含继续执行所需的真实状态；“把状态改回 running”不等于恢复。
5. UI 状态从持久化 Job、Message 和 Result 推导，不能依赖全局 latest result。
6. 后台执行是 iOS 的 best-effort 能力；系统 expiration 后转为可恢复状态，回前台或冷启动后真正重启执行。
7. completed、failed、cancelled 和陈旧进度必须有统一清理策略，灵动岛不能长期残留幽灵任务。

---

## 8. UI 是答案契约的一部分

UI 不是最后“美化一下”，而是语义交付层。

强制规则：

1. 同类信息必须使用同一组件和同一字号层级。
2. 主结论、建议、依据和限制必须视觉可区分。
3. 重要性由结构化优先级决定，不由文本长短决定。
4. 主范围放在标题附近；局部范围贴近对应事实或建议。
5. 首屏不能用超大正文重复建议内容。
6. 卡片摘要和详情页必须消费同一结果结构，不能各自解析一遍。
7. 长文本必须使用真实 SwiftUI 首帧或真机检查换行、密度、滚动和截断。

## 9. Agent 研发标准流程

### 第一步：把问题变成可验收的回答任务

开发前写清：

- 用户到底问了几个子问题；
- 期望的时间与统计口径；
- 需要哪些数据源；
- 哪些是事实，哪些是建议；
- 结果缺什么时应如何降级；
- 用户第一屏应该看到什么。

### 第二步：追踪完整调用链

必须核对：

`入口 → Router → Job → Runtime → Tool Registry → Data Source → Evidence → Verifier → Composer → Renderer → Card / Detail → Persisted State`

Repository 里有数据，不等于 Tool 暴露了数据；Tool 能返回数据，也不等于最终答案会使用正确。

### 第三步：先建事故回归，再改代码

每个线上或真机问题都要转成可重复 fixture，至少包含：

- 用户原问题；
- 容易误导下游的冲突数据；
- 期望结果；
- 禁止出现的结果；
- UI 层级断言。

例如年度财务事故应故意同时放入：

- Job 范围为 2026 年；
- Evidence label 为“近30天”；
- 财务覆盖为 `132/365`；
- 尚未发生的未来分期；
- 两条不同优先级建议；
- 一条只针对本月的局部建议。

如果这个对抗 fixture 不能通过，不能声称问题已解决。

### 第四步：实现公共契约

优先补类型、策略和单一真相源，再改具体领域。  
财务修复必须检查健康、习惯、任务、观点和跨域是否会触发同类路径。

### 第五步：分层验证

| 层级 | 目的 | 最低要求 |
|---|---|---|
| 单元 / standalone | 时间、覆盖、数值、建议结构 | 断言真实边界和反例 |
| 组合回归 | Tool → Evidence → Renderer | 使用冲突 fixture，不只测 happy path |
| UI 模型 | 顺序、去重、范围标签 | 两条以上建议与长文本 |
| 真实 SwiftUI / 真机 | 字体、密度、滚动、状态 | 查看真实首帧，不靠读代码猜 |
| 全工程构建 | 验证真实依赖和 target | `BUILD SUCCEEDED` |
| 生产验证 | Prompt、协议、路由是否线上生效 | release、prompt meta 和真实请求 |

`Executed 0 tests`、局部文件能编译、后端 health 为 200，都不能替代对应层级的验证。

### 第六步：记录剩余边界

交付时明确区分：

- 已通过的自动化回归；
- 已完成的全工程构建；
- 已完成的真实 UI / 真机验证；
- 已完成的生产验证；
- 尚未覆盖的设备、数据或生命周期场景。

## 10. 跨领域最低回归矩阵

每次修改 Agent 公共链路，至少覆盖：

| 领域 | 必测场景 |
|---|---|
| 财务 | 显式年份、未来分期、大额单笔、分类趋势、事件覆盖 |
| 健康 | 每日覆盖、缺失天、睡眠阶段缺失、单位与隐私 |
| 习惯 | 事件记录与每日计划的区别、零记录、数值型习惯 |
| 任务 | 无截止日期、已完成/未完成、未来任务、当前快照 |
| 观点/想法 | 稀疏事件、无记录、引用原文边界 |
| 跨域 | 时间窗口一致、重复证据、相关不等于因果 |
| 运行态 | 后台、锁屏、回前台、冷启动、取消、系统 expiration |
| 展示 | 0/1/2/3 条建议、长标题、局部范围、旧消息兼容 |

---

## 11. 禁止的修复方式

- 看到“近30天”就替换文案；
- 对某个财务页面单独关闭覆盖提示；
- 只在 Prompt 里增加更多“必须/禁止”；
- 只调字号，不修建议数据结构；
- 让多个 Renderer / View 各自解析自然语言；
- 只看代码推测效果，不跑 fixture 和真实 UI；
- 只测用户报告的唯一问法；
- 为新功能再建一套平行状态、反馈或验证系统；
- 把开发环境故障误报为功能通过或功能失败；
- 本地 Prompt 改完但没有核对生产生效版本。

---

## 12. Definition of Done

公共 Agent 改动合入前，必须全部满足：

- [ ] 用户问题已转换成明确的回答任务与验收标准
- [ ] 时间、覆盖、事实、建议、状态各有唯一真相源
- [ ] 没有新增自然语言字符串解析作为长期协议
- [ ] 历史事实已排除快照日后的未来数据
- [ ] Evidence、数值、单位和范围可追溯
- [ ] 用户问建议时有具体建议；未问建议时无泛泛行动话术
- [ ] 财务、健康及至少一个事件型领域完成组合回归
- [ ] 原始事故已进入永久回归集
- [ ] 卡片摘要与详情页顺序、去重和层级一致
- [ ] 查看过真实 SwiftUI 首帧或真机界面
- [ ] standalone / 定向测试有非零断言并通过
- [ ] 全工程构建通过，或明确记录与本改动无关的环境阻塞
- [ ] 如涉及 Prompt / 后端：已双端同步、升版本、部署并生产验证
- [ ] 失败、取消、陈旧任务和灵动岛状态可正确清理
- [ ] 交付说明列出已验证范围与剩余风险
