# Holo iPad 完整可用性改造方案

> 交付对象：GLM 实施；产品负责人：东林  
> 方案日期：2026-09-16  
> 状态：待实施。本文是实施规格，不代表代码已完成、真机已验收或功能已上线。

## 1. 产品结论与目标

Holo 已有 iPad 侧边栏、部分双栏、顶部模块切换、弹层限宽和键盘快捷键，但整体仍像多个独立的手机页面放进大屏。核心问题是：布局用整个窗口宽度判断，而侧边栏先占用 232pt；模块之间的详情承载方式不一致；财务和 AI 的关键任务仍要求用户反复切换页面，不能持续看到上下文。过去的 iPad 走查修复过局部布局与习惯导入刷新，但跨设备真实可靠性仍需真机确认。

**产品目标**：让 iPad 成为 Holo 的“回顾、核对、规划、处理”工作台。用户能在一屏内看见当前对象、相关上下文和下一步动作；在竖屏或窄窗口中仍能完成相同任务；从 iPhone 带来的数据状态可信。

本次成功不按“做了多少双栏”判断，而按四条完整任务验收：

1. 在 iPad 竖屏快速记一笔，并能回到账本确认金额、日期、分类和账户。
2. 在 iPad 横屏核对一周账目：切换记录时保留账本位置、筛选和所选日期。
3. 从今天进入任务，边看任务清单边修改安排，再回到今天确认结果。
4. 在 AI 对话中查看一条分析的证据或报告，追问后仍可回看同一份依据。

以上四条还要覆盖旋转、窄窗口、空数据、正在同步、同步失败、深色模式和较大字号。

## 3. 统一设计规则：先建立，再改页面

### 3.1 按“可用内容宽度”决定呈现

定义三层宽度，而非把 iPad 等同于 regular：

- `windowWidth`：当前场景窗口宽度，只用于外壳决定侧边栏能否常驻。
- `contentWidth`：扣除实际显示的侧边栏、安全区、分隔与页面边距后，业务模块真实拿到的宽度；模块布局只看它。
- `detailAvailableWidth`：列表、详情各自真实宽度；卡片网格、图表、富文本和工具栏按本栏宽度调整。

建议起始契约（数值可由实拍微调，调整须保持同一公式）：

| 模式 | 判定 | 导航 | 内容 |
| --- | --- | --- | --- |
| 窄 | 内容不足以容纳两列，或窗口不足以让侧边栏常驻后留出舒适内容 | 侧边栏收成工具栏入口，点开以临时覆盖方式显示 | 单列；详情进入同一导航层，返回保留列表状态。 |
| 标准 | 主内容足以放下 360pt 列表＋440pt 详情＋间隔和内边距（建议从约 860pt 实得宽度验证） | 是否常驻侧边栏由扣除 232pt 后能否仍满足内容最低宽度决定 | 可显示列表＋详情；两栏各有最小宽度。 |
| 宽 | 主内容显著超过两栏最低宽度 | 侧边栏常驻且可收起 | 双栏或模块内网格；阅读正文仍限舒适行长，图表和卡片可展开。 |

关键示例：834pt 竖屏不能固定留 232pt 后把主内容压成约 602pt；1024pt 窗口不能因为达到旧断点，就把扣除侧边栏后的约 792pt 强行分为两栏。用户主动收起侧边栏后，同一窗口可以重新评估双栏。旋转或调整窗口时只改变呈现，不清空所选记录、筛选、输入草稿、滚动位置或正在运行的 AI 会话。

**工程实现**：在 `ContentView`/`HoloAdaptiveLayout` 建立统一的容器宽度环境与布局决策；`HoloListDetailSplit` 改用容器宽度和最小栏宽，不再由全局 `holoWindowWidth` 独断。逐个迁移调用方，避免在业务视图里新增散落的 `1024`、`720`、`232` 判断。SwiftUI `horizontalSizeClass` 只当辅助信息，不作为 iPad 独占判断。

### 3.2 全 App 统一对象详情规则

- 宽时：左侧列表或时间线保持原位，右侧显示所选对象详情；切换对象只刷新右栏。
- 窄时：点对象进入详情页；返回时保留筛选、列表位置和选中对象。
- 新建/轻量修改：采用适合表单的居中弹层；富文本、复杂配置与长报告使用足够宽的独立阅读页。关闭或取消要明确保留/丢弃草稿。
- 从今天、AI、通知、搜索进入同一对象，路由到同一详情模型；关闭时回到原入口，不意外跳回“今天”。
- 删除当前对象后清掉右栏选中并展示合理空位；同步导致对象变化时不展示过期详情。

### 3.3 排印与视觉规则

- 阅读正文以可读行长为约束；概览、图表、时间轴和卡片按列展开。禁止把整个模块一律包进 720pt 阅读列，也禁止把长段文字通铺到整屏。
- 标题、正文、辅助说明、数值、操作只用现有设计系统排印层级；把长廊现有的宽屏字号经验收敛为统一规则，不在每个页面手工乘系数。
- 同一层级的顶部工具栏、筛选、空态、弹层宽度一致。颜色不是状态的唯一表达。
- 保证 Dynamic Type、VoiceOver、触控至少 44pt 的主要操作目标；浮动键盘、外接键盘、指针状态下都能看到主要操作。

## 4. 分阶段实施与交付门槛

### 阶段 0｜可复现基线与契约（先完成）

1. 核对当前脏工作区和正在并行修改的文件，不覆盖别人的在途改动；锁定本方案涉及文件的差异。
2. 为四条核心任务录制当前行为，记录设备、系统、构建、数据来源、屏幕宽度、步骤与问题；不要把商店宣传截图当运行画面。
3. 定义布局决策的纯逻辑输入输出：窗口宽度、侧边栏显隐、主内容实得宽度、栏最小宽度、当前对象状态。
4. 给现有关键入口补稳定的 accessibility identifier，供后续真正的操作测试使用，不用本地化文案做唯一定位。

**通过门槛**：能重复看到旧问题；布局决策有可测试契约；原有 iPhone 主流程没有被改坏。

### 阶段 1｜外壳、导航与宽度政策（P0）

目标文件：`ContentView.swift`、`HoloSidebarView.swift`、`HoloAdaptiveLayout.swift`、`HomeView.swift`，以及直接使用旧全局断点的入口容器。

1. 侧边栏按可用空间自动常驻或临时展开，并提供明确的显示/收起入口；选中目的地始终可见、可恢复。
2. 将“是否双栏”“顶部/底部页内导航”“网格列数”“卡片最大宽度”改为由真实业务容器宽度决定。先处理今天、任务、想法、设置，再处理财务、习惯、健康、长廊。
3. 统一各模块根视图的关闭/返回语义，避免侧边栏切换和内部返回互相打架；保留常驻模块中的滚动、筛选与 AI 对话状态。
4. 旋转与窗口尺寸变化时不重建业务状态。对单列↔双栏切换写状态迁移规则：已有选中仍保留；双栏右栏消失时可在窄屏进入对应详情，不能直接遗失对象。

**通过门槛**：iPad 11 竖屏、13 竖屏和两种横屏无横向裁切、无无意义巨幅空白、无半屏弹层；四条核心任务在旋转往返后可继续。

### 阶段 2｜把高价值流程变成 iPad 工作台（P1）

#### 2A. 财务：一边核对账本，一边看记录

目标文件：`FinanceView.swift`、`FinanceLedgerView.swift`、财务记录详情/编辑相关视图与路由。

- 标准/宽模式：左侧保留日期、筛选和账目列表，右侧显示所选记录的完整信息与编辑入口；必要时在列表上方显示当前周期合计，不复制一整套财务页面。
- 无选中给出有用的默认状态：本日/本周期摘要和“选择一笔查看”；不能出现大片空白占位。
- 新增记账仍可用合适宽度的表单；保存后列表和合计即时更新，并在新记录上有清楚反馈。
- 统计分析下钻到账目时保留原来的时间范围和分析维度；返回继续看同一图表，而不是从财务首页重来。
- 窄模式沿用单列，点击详情后返回时保持日期、筛选、滚动和搜索词。

#### 2B. AI：一边对话，一边核查依据

目标文件：`ChatView.swift`、`ChatReportTabView.swift`、报告详情路由及已有分析卡组件。

- 标准/宽模式提供按需出现的“依据/报告”侧栏：用户点聊天中的报告、账单分析、回放或证据卡时，在旁边打开对应内容；聊天消息和输入框仍可见。
- 右栏不是第二份聊天历史，也不自动占位。关闭右栏后恢复舒适的聊天阅读列；继续追问时保留当前依据，切换依据只改变右栏。
- 对可回到源记录的事实，提供明确“查看原始记录”动作；没有事实链接时说明只是在查看报告，不伪装为可验证证据。
- 窄模式保留现有聊天/报告切换或独立详情；不因侧栏改造牺牲输入焦点、消息滚动、流式响应、停止生成和语音输入。

#### 2C. 今天与任务：处理后立即回看结果

目标文件：`DailyKanbanView.swift`、`TaskListView.swift`、`TaskDetailView.swift`、`HomeView.swift`。

- 从今天的焦点、日程和 Matter 进入任务详情，宽时保留今天的上下文；窄时可返回原位置。
- 完成、延期、编辑任务后，今天与任务页基于同一真实数据刷新；不额外复制一份状态。
- 既有任务双栏保留，按新容器规则调整宽度；切换选中任务时不误丢编辑内容。

**通过门槛**：四条核心任务全通；财务、AI 的“查看依据/详情→行动→回看”无需重复找回原对象；数据读写与 iPhone 逻辑一致。

### 阶段 3｜其余模块与输入方式一致性（P1/P2）

1. **想法与知识树**：保留已有想法列表＋详情；知识树按实际内容宽度显示主题与内容，不把宽屏强行锁成 720pt；富文本编辑器在竖屏、横屏、浮动键盘和较大字号下可读可操作。
2. **记忆长廊**：保留现有日/周/月、轴档与 920pt 修复成果；通览内容可展开，长叙述保持舒适行长；筛选、聚焦日期与档位在旋转后不丢。
3. **习惯与健康**：磁贴/指标依容器宽度排布，不按全窗口宽度猜列数；详情阅读宽度一致；空态、加载和授权状态要明确下一步。
4. **设置与个人**：复用已有设置双栏；窄屏回退单列，宽屏分组切换保留合理位置。会员、登录、账号与同步状态不要有横向拉满的超长表单控件。
5. **键盘与指针**：核对已有 ⌘1–9、⌘N、⌘F、⌘W 是否在侧边栏展开/收起和弹层出现时仍作用于正确页面；为可编辑列表补合理的 Esc 关闭、Tab 焦点路径和指针反馈。不要为了“像桌面软件”增加与触控语义冲突的快捷键。
6. **拖入内容**：优先仅在有明确接收目标的地方实现图片/文件拖入，例如想法附件或凭证识别；落点与结果必须可见。跨模块拖拽排序、复杂窗口并排属于后续迭代，不阻塞本次可用性发布。

**通过门槛**：所有侧边栏目的地完成竖横屏、浅深色、空态/有数据走查；主要可点击控件有键盘和触控通道；无单独“只有 iPad 会坏”的详情页。

### 阶段 4｜跨设备可信度与多任务窗口（发布门槛）

**同步**：使用现有 `ICloudSyncStatusService` 与 `CloudImportRelay`，先验真实双设备：iPhone 新增/改/删任务、习惯、账单、想法，iPad 前台与后台恢复后均能看见正确结果；反向再测一次。分别记录账号状态、导入/导出事件、页面刷新和最终业务记录，定位失败是在云端没到、到了没刷新，还是详情残留旧对象。空态只能在确认数据确实为空时说“还没有记录”；初次导入和失败要说真实状态。任何“同步成功”文案都要以相应真实事件为依据，不能承诺固定秒数必达。

**窗口**：布局在可调整窗口下稳定后，移除或迁移 `UIRequiresFullScreen` 兼容配置；按实际支持的 iPadOS 版本验证分屏/台前调度/窗口缩放、键盘出现、侧边栏收起与恢复。先完成并验证动态布局，再改工程开关。Apple 迁移说明：<https://developer.apple.com/documentation/technotes/tn3192-migrating-your-ipad-app-from-the-deprecated-uirequiresfullscreen-key>。

**通过门槛**：真实 iPhone＋iPad 数据往返验收；多任务窗口没有内容裁切、错位、丢选中或不可达按钮；失败和恢复状态可解释。

## 5. 验收矩阵与证据格式

| 维度 | 必测组合 |
| --- | --- |
| 尺寸 | iPad 11 英寸竖/横，iPad 13 英寸竖/横；阶段 4 增加窄、中、宽三个窗口尺寸。 |
| 数据 | 真正新装空态；可复现种子数据；长标题/大金额/多条任务；跨设备真实数据。 |
| 状态 | 浅色/深色；正常/加载/失败；离线；首次同步中；账号不可用；删除当前选中项。 |
| 输入 | 触控；妙控键盘；指针；系统大字号；VoiceOver 核心任务。 |
| 路由 | 今天→任务→返回，AI→报告/证据→继续问，财务统计→账目→返回，通知/搜索→对象详情。 |
| 回归 | iPhone 首页、记账、任务、想法、AI 对话；不同尺寸之间往返保持状态。 |

每阶段提交一张简短验收表：`场景 / 设备与系统 / 构建版本 / 操作 / 预期 / 实际 / 截图或录像 / 结论`。自动化测试只覆盖有稳定业务断言的路径；纯视觉判断用当前 Debug 模拟器截图和真机人工走查。`BUILD SUCCEEDED`、截图存在或单独测试通过，只能证明对应层级，不能写成真机、CloudKit 或生产通过。

## 6. 实施边界与风险控制

- 优先复用现有数据模型、Repository、导航状态和设计系统；这次是 iPad 呈现与交互改造，不顺手重写财务、AI、同步业务规则。
- 工作区已有大量在途修改；每阶段只改本阶段文件，提交前逐文件审查差异，不广泛暂存或夹带他人改动。若文件同时被其他工作修改，先定位差异再合并。
- 先做外壳与布局契约，再做页面。不可用一次全局替换把所有 720pt 限宽去掉；阅读页和通览页有不同宽度需求。
- 不以 seed 数据替代真实双设备 CloudKit 验收；模拟器不能证明 iCloud 同步。
- 本方案不要求后端改动。如果实施中确有 `HoloBackend/` 改动，单独说明生产部署与验收需求，不把本地代码完成写成线上生效。
- 不在本任务内制作或上传 App Store 截图，也不提交审核；产品体验通过后再使用当前可复现 Debug 界面更新宣传素材。

## 7. GLM 执行指令
