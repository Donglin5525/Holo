## ① 四指控逐节

### 指控 1 · 明示排除未生效（用户移出后 AI 归属把它归回）

**现状机制（通俗）**：用户在某条笔记上移出某主题时，系统在这对「笔记×主题」关系上写一块「墓碑」（永久拒绝标记）。AI 后续判定这条笔记时，召回阶段会先查墓碑、被拒主题根本不进候选；网络请求回来、正式落库前还会再查一次墓碑和用户手动决定。三层守卫实际都在。

**代码证据**：

1. 召回侧墓碑压制（请求发出前）——`AI3/ThoughtTopicCandidateEngine.swift:83` 取墓碑集合，`:88`（脉络通道）与 `:179`（类别通道）双双过滤：

```swift
let rejected = await rejectedPairTopicIDs(thoughtID: thoughtID, context: context)
...
for topic in threadTopics where !rejected.contains(topic.id) {
```

墓碑查询本身（`ThoughtTopicCandidateEngine.swift:223-230`）按逻辑 UUID 匹配 `state == "rejected"` 的 link 行。

2. 落库守卫（网络返回后、写库前复查）——`AI3/ThoughtTopicVerifier.swift:225-243`：commit 块在网络往返结束后的 `context.perform` 内执行，先 `refreshAllObjects()` 并重验正文 hash（`:226-231`），再逐候选调用投影层写入；投影层入口第一件事就是复查当前墓碑——`APP/Services/Thoughts/ThoughtTopicLinkProjection.swift:128-130`：

```swift
static func recordAIV3Decision(...) -> Bool {
    if isUserRejectedPair(thought: thought, topic: topic) { return false }
    let link = upsertLink(thought: thought, topic: topic)
    if isUserDecision(link) { return false }
```

`isUserRejectedPair`（`ThoughtTopicLinkProjection.swift:146-152`）重新 fetch 该 pair 全部行、任一行 `rejected` 即拒绝；`isUserDecision` 同时挡「用户手动移入的 active 行」。

3. V2 旧通道同守卫——`APP/Data/Repositories/TopicRepository.swift:505` 在旧 AI 归类写回前同样早退。

4. 用户移出入口全部接通墓碑：`TopicRepository.remove`（`TopicRepository.swift:429-436`，`:435` 调 `recordManualRemove`）；主题详情成员移出 `Views/Thoughts/TopicDetailView.swift:752`；选分类页「移出到未归类」`Views/Thoughts/TopicPickerView.swift:145`；启用分类时的同想法换绑 `TopicRepository.swift:176`。

5. 测试锁定（静态读，未执行）：`HoloTests/Services/Thoughts/ThoughtTopicLinkProjectionStandaloneTests.swift:81-82` 断言 `recordAIV3Decision` 在墓碑前返回 false（「用户拒绝不得复活」）；`HoloTests/Services/AI/SemanticV3/ThoughtSemanticSafetyTests.swift:401`（V3 通道墓碑不复活）、`:188`（墓碑压类别候选）、`:423`（用户 active 不被降级）。

**但有两处真实缺口（指控的实质部分）**：

- **规则级承诺无机制（实锤）**：徽章「为什么归这里」面板向用户承诺「移出会成为 AI 的反例，同类内容以后不会再收进来」（`APP/Views/Thoughts/ThoughtCardView.swift:643`）。实际机制只有 pair 级墓碑；「同类内容」级别的排除唯一可能路径是移出样本喂给 AI 类别理解再概括成 brief——`AI3/ThoughtCategoryBriefMaintainer.swift:148-165` 取 rejected link 作移出反证（≤3 条、最近优先），`AI3/ThoughtCategoryBriefClient.swift:115-123` 合并排除项。而 brief 的 `exclusions` 数组**从不参与判定**：全库检索其消费点只有校验/合并/存库三处，`ThoughtTopicVerifier.swift:120-125` 只读 `brief.definition`，`exclusions` 无任何读取方。真正进模型的判据是「用户 definition 优先、AI brief definition 兜底」（`ThoughtTopicVerifier.swift:159-162`），兜底是否记得住某次移出全凭 AI 概括，非硬规则。
- **同 id 副本行身份错配（存疑）**：落库守卫的 `isUserRejectedPair` 与 `upsertLink` 按 `thought == %@ AND topic == %@`（对象身份）fetch（`ThoughtTopicLinkProjection.swift:31`、`:147-150`）；落库行解析用 `Topic.resolveValid`（可见行优先+物理行号去重，`ThoughtTopicLinkProjection.swift:419-424`），而用户移出入口用 `TopicRepository.fetchTopicById`（按逻辑 id 取 `.first`，`TopicRepository.swift:567-572`）。同 id 多行副本是 documented 长期库况（`ThoughtTopicLinkProjection.swift:406-411` 注释「9-8 库迁事故后…长期库况」）。若移出写在物理行 A、落库解析出行 B，复查会看不到墓碑。触发窗口窄（recall 后 commit 前的移出 + 副本库况同时发生）。**下一步验证法**：内存库造同 id 两行 Topic 副本，用 `fetchTopicById` 解析的行对象调 `recordManualRemove`，再用 `resolveValid` 解析的另一行对象调 `isUserRejectedPair`，断言返回 false 即证实。
- 补充（按设计、非缺陷）：移出后笔记回到孤儿池，可被聚簇收进**新**主题（`AI3/ThoughtAutomaticTopicDiscovery.swift:112` 只挡同名重建）——pair 作用域语义，方案 A03 明确认可「作用域永不自动扩大」。

**触发条件**：字面指控需要「移出与 AI 判定在飞同窗口 + 副本行错配」同时发生；规则级缺口则在每次移出后同类新笔记判定时都存在（仅当类别无用户定义且 AI brief 恰好概括到时才间接生效）。

**方案对应修复条款**：§4 A1.1（落库守卫服从当前人工移入/移出，差量写入）、§2 A03（点拒绝与类别规则分开、UI 承诺收口）、§2 A02（存量 AI 排除项不升格为规则，改用 `categoryDefinition` 表达纳入与排除）、§3 D1（点拒绝用既有 `ThoughtTopicLink`）。

**结论**：**部分实锤、部分存疑**。守卫链三层齐备且有测试锁定，指控字面（落库前不复查）**不成立**；实锤的是它的规则级反面——「同类内容以后不会再收进来」承诺无对应机制、AI brief exclusions 存而不用；副本行错配存疑（验证法如上）。

### 指控 2 · 已有大类的旧笔记无法参与新发现

**现状机制（通俗）**：自动形成新主题的原料只有「没有任何主题归属的孤儿笔记」。已经在大主题里的笔记，无论内容多合适，永远不会进入聚簇候选——新主题只能在孤儿堆里长出来。

**代码证据**：

1. 聚簇引擎输入 = 孤儿集合。`AI3/ThoughtTopicClusterEngine.swift:131-137`：

```swift
let request = Thought.fetchRequest()
request.predicate = NSPredicate(format: "deletedAt == nil AND isArchived == NO")
return ((try? context.fetch(request)) ?? []).filter {
    ThoughtTopicLinkProjection.effectiveTopics(for: $0).filter(\.isVisibleTopic).isEmpty
}.map { ... }
```

只要投影上有一个可见主题就不是孤儿；`:144` `guard orphanIDs.count >= minClusterSize`，`:147` 再过滤无向量者。

2. 发现入口同一口径。`AI3/ThoughtAutomaticTopicDiscovery.swift:30-36` 先取 orphanIDs（`:34` 同款过滤）；`:45-53` 组装命名请求样本时再过滤一次孤儿，且按 `createdAt` 倒序 `prefix(8)`（`:50-53`）——**最近优先**，旧孤儿代表性进一步被压缩。

3. 时间偏差的另一处：判据代表例正文只取每条笔记**开头 240 UTF-16**（`AI3/ThoughtTopicVerifier.swift:152-155` `ThoughtSemanticText.prefix(..., maxUTF16: 240)`），结论藏在末尾的旧笔记取不到；无任何时间分层采样。

**补充精确化（relate 侧现状，避免夸大）**：新主题建成后，旧笔记**并非永远进不了新主题**——`AI3/ThoughtSemanticChangeFeed.swift:231-235` 的 relate 入队去重以 `evaluationVersion`（含全目录指纹：所有主题的 id|title|status|summary|categoryDefinition，`ThoughtTopicVerifier.swift:83-92`）查 `hasRelationRecord`；目录变化后旧记录版本失配即全部重入队，`ThoughtAutomaticTopicDiscovery.swift:131` 建主题后主动调 `reconcileAllThoughts()`。即旧成员会经 relate **重评**获得 `same_thread` 归入新主题的机会。但这不是「参与发现」：它不改写「新主题只能由孤儿聚簇而成」的事实，且触发方式是目录指纹变化驱动的全量重评（正是方案 §2 A09 要防的「全量历史重跑」形态在现状的真实存在）。

**触发条件**：任何大主题（分类或脉络）只要有 ≥1 个有效成员，其全部成员即永久退出聚簇输入；只有孤儿参与新主题的「出生」。

**方案对应修复条款**：§5 B1（试点主题成员入池 ≤120、早/中/新三段各 ≤40 分层采样）；§2 A12（时间分层与局部取证）；§2 A01（旧发现链保持原触发语义不动，新脉络走独立通道——即修复不改旧链，而是新增 B 通道）。

**结论**：**实锤**（孤儿过滤 file:line 齐全）；附带发现 relate 侧存在「目录版本变化→全量重评」的现状机制，方案 A09/R05 的边界设计需把它计入基线。

### 指控 3 · 两段相似却非延续被硬凑成簇

**现状机制（通俗）**：成簇的唯一判据是「向量相似度过线」，并且 A 像B、B 像 C 就把 A、B、C 连成一簇（传递闭包）。「延续」「对照」「修正」这类关系类型在整条链路里根本不存在，模型返回的只是「同一脉络」加一句自由文本主题。

**代码证据**：

1. 建边只看相似度、成簇靠并查集传递。`AI3/ThoughtTopicClusterEngine.swift:70-75`：

```swift
guard neighbor.similarity >= threshold else { continue }
...
union(i, j)
```

`:96` 内聚度=边相似度均值；`:92` 仅要求 ≥3 名成员。无锚点、无逐成员共同问题证据、无关系类型核对。阈值取 `ThoughtSemanticCalibration` 召回值（`ThoughtTopicClusterEngine.swift:127`）。

2. 现行测试把「链式传递成簇」锁定为**预期行为**——`HoloTests/Services/Thoughts/ThoughtTopicClusterStandaloneTests.swift:75-92` 用例名即「链式相似（A~B~C，A⊥C）经并查集传递归簇」，断言三笔记归成一簇。方案 A05 要改掉的恰是被该测试锁死的行为，W1 实施时须同步改写此用例。

3. 关系枚举无延续/对照/修正。客户端 `AI3/ThoughtTopicVerifier.swift:79-80`：

```swift
private static let committingRelations: Set<String> = ["same_thread", "fits_category"]
private static let allowedRelations: Set<String> = ["same_thread", "fits_category", "related", "none", "insufficient"]
```

后端同枚举：`GW/src/thoughts/semanticRelateSchema.js:28-30`。方案 §6 C1 的 `continues/adds_example/contrasts/revises` 四类型在两端都不存在。

4. `same_thread` 唯一的「共同性」核对是 `sharedSubject` 非空自由文本（`ThoughtTopicVerifier.swift:203-206`；后端 `semanticRelateSchema.js:233-235` 仅限 ≤120 字符）。无本人立场、时间先后、延续性核对。

5. 主题命名链路同样无结构化共同问题校验：`ThoughtAutomaticTopicDiscovery.swift:73-86` 只核验成员 quote 逐字、3–8 人、名称/定义形状；「共同问题」完全托付模型自觉。

**触发条件**：任意两条向量相似度 ≥ 阈值的边即可传递成簇；话题相近但无延续（同书、同关键词）、反问/引述/计划均可能被 `same_thread` 硬收。

**方案对应修复条款**：§5 B2（同一簇须共用锚点、每条成员直接回答同一问题的逐成员证据；存在相同词或桥接的两条边不足以生成脉络）；§2 A05/A06；§6 C1（四关系枚举与各自证据要求、`revises` 须双侧本人立场）。

**结论**：**实锤**。且现行 standalone 测试与方案方向相反（锁定传递成簇为预期），属实施时必须一并翻案的断言面。

### 指控 4 · 超量按 UUID 截断 + 未入选项整批 supersede

**现状机制（通俗）**：一次判定最多允许 3 个自动归属；候选最多可达 12 个（类别通道保险丝 9 + 脉络 3）。超了怎么办？现状是按主题 UUID 的字母顺序排排队、取前 3——跟内容质量无关。剩下 9 个里哪怕模型刚判过「符合」，也照样被算作「落选」；更狠的是，本轮压根没被召回的主题上已有的旧 AI 归属，也会在这时被一并撤销。

**代码证据**：

1. UUID 截断。`AI3/ThoughtTopicVerifier.swift:218-219`：

```swift
// 双通道允许重叠归属：类别（≤类别上限）+ 脉络（≤2）合计放宽到 3。
let results = Array(resultsByTopic.values.sorted { $0.topicID.uuidString < $1.topicID.uuidString }.prefix(3))
```

排序键只有 `topicID.uuidString`，无质量/规则/价值排序。候选上限 12 来自 `ThoughtTopicCandidateEngine.swift:46`（`categoryChannelLimit = 9`）+ `:173`（脉络 `prefix(3)`）。

2. 整批 supersede。`ThoughtTopicVerifier.swift:232-236`：

```swift
let links = thought.topicLinks as? Set<ThoughtTopicLink> ?? []
let selected = Set(results.map(\.topicID))
for link in links where link.sourceEnum == .aiV3 && link.stateEnum == .active {
    if let topic = link.topic, !selected.contains(topic.id) { link.stateEnum = .superseded; link.updatedAt = Date() }
}
```

被 superseded 的包括三类：① 被召回且模型判正但输掉 UUID 排序的；② 本轮低于召回阈值没被送判的；③ 类别通道保险丝（>9）截掉的。投影层 `recordSuperseded` 的用户决定保护（`ThoughtTopicLinkProjection.swift:87`）在此不设防——本循环直接改行、绕过该函数（好在只碰 `aiV3` 来源行，用户行 `sourceEnum` 不同，实际不会误伤）。

3. 截断的落选正项连影子记录都没有：`ThoughtTopicVerifier.swift:259-264` 的 `recordRelationCandidate` 只遍历截断后的 `results`（≤3），判正落选者在 SQLite 诊断层也不留痕，只进 `decisions` 诊断 JSON（`:272-276`）。

4. 徽章两枚侧确认：`APP/Views/Thoughts/ThoughtCardView.swift:408` `prefix(2)`；排序真源在 `ThoughtTopicLinkProjection.swift:214-217`（createdAt 升序 + UUID 平局）——「创建较早的两枚」属实。

**触发条件**：任何一次 relate 判定产出 >3 个归属型结论，或该笔记既有 AI 归属数 >3 且本轮目录/正文版本变化触发重评时，即按 UUID 顺序裁决去留。

**方案对应修复条款**：§4 A2 上限段（「先保留仍有效且本轮没有明确负向结论的已有自动关系，再按『明确引用用户规则的类别匹配、双侧有证据的同脉络、代表例匹配』给新正向结果排剩余名额……超出只记容量原因。验证器不能继续整批把未入选项 supersede」）；§2 A10（「落库超量时按 UUID 截断」→ 按规则和内容价值排序、记录被限额原因）。

**结论**：**实锤**，file:line 与方案 §2 A10/§4 A2 的描述逐字吻合，是该批四指控中最干净的一条。

## ③ 与方案描述不符之处

1. **「当前类别输入仅取 brief.definition」（方案 §8 顺序 2）与代码不符**。现状是「用户 `categoryDefinition` 优先、AI brief 兜底」：`ThoughtTopicVerifier.swift:159-162`，且用户写过定义后 brief 维护者永不维护该主题（`ThoughtCategoryBriefMaintainer.swift:86`）。方案把兜底链写成了唯一来源。W1 的 schema 4 改造对象应以实际链为准（判据 `definition` 字段 = 用户定义 ?? brief 定义 ?? 无）。
2. **「AI 归属在落库守卫中再次服从当前人工移入/移出」（方案 §4 A1.1）被列为待建，pair 级守卫实际已存在**（Verifier:241 → Projection:128/130，另有 V2 通道 TopicRepository:505），且被 `ThoughtTopicLinkProjectionStandaloneTests:82`、`ThoughtSemanticSafetyTests:401` 双测试锁定。W1 真正要做的是把这套语义扩到 schema 4 的差量写入与 `excludes_category` 撤销路径，而不是从零建守卫。
3. **方案 §5 B1「相似度下限先用 ThoughtSemanticCalibration 当前召回值并在 W0 冻结」——冻结值即 seed 0.55**，非校准产物；`marginMinDelta` 虽在配置中但无消费者，若 W1/W2 需要歧义 margin 判定需重建消费点。
