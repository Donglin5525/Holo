# 想法自动整理增强实施方案

2026-11-16 · 供东林评审与执行模型实施 · [可复制的执行提示词](执行模型提示词.md) · 仓库基线 `ecfbe9e524abf867ebd5a2545e89746fe2f3cf6c`，分支 `1.1.8`

本文件是本批唯一实施规格。可以按下列阶段在本地开工，发布和实际质量分别过闸。产品目标是用户写下一条想法时，Holo 能按他的习惯归档，并在日后读到这条时带回有直接关系的旧想法。首个验收场景是选一个已有的大主题，测出「之前找不到、现在能读回」以及「我改过规则、下一条确实有变化」。

## 1. 产品范围与交互

| 场景 | 首版行为 | 用户控制 |
|---|---|---|
| 现有分类及 #标签 | 手动标签、正文行内标签、用户选的主题和现有自动整理继续从原入口使用。 | 用户手动归属与移出决定优先于 AI。 |
| 纠正归类 | 列表徽章长按 →「从这条移除」。明确提示「已从这条想法移除」，操作完成即生效。主题详情成员移出、编辑器更改分类等入口使用同一关系仓库。 | 一次移出仅改变这一对关系。改主意时手动加回。保留既有多个分类之间的手动更改语义。 |
| 教 Holo 以后怎么归 | 在分类主题详情现有「这个主题收什么」卡编辑规则，同一输入框支持纳入与排除的日常语言。提示「例如：收录我对产品的判断。纯会议纪要不收，有自己的反思可以收。」规则只在用户点保存后生效。 | 编辑器展示当前已保存规则。没有规则就给空输入和示例。保存失败保留输入和重试，关闭时按现有编辑器约定。清空等于撤回规则。旧版已有 AI 草稿，试点规则卡只读用户正文，无正文时显示无规则与示例，避免草稿继续被误认作生效。 |
| 从一个大主题回看 | 在已有主题详情「你加入 / Holo 找到」下、现有摘要前，至多显示两条「值得回看的脉络」。卡片显示主题句和支持笔记数。点击查看按时间排好的 3–5 条来源，每条显示日期、角色及原文片段，点开复用现有想法阅读入口。 | 试点入口在选定主题内部，不新增首页入口、主题、标签、通知或自动用户归属。点「隐藏这条脉络」当设备立即生效。 |
| 读一条笔记时想起旧事 | 复用编辑器已有「相关旧想法」区域，试点内优先展示至多两条已核对的关系，含关系理由及原文入口。例如「补上了上次没有定的确认条件」。 | 「不相关」过滤这一对，相关区与脉络遵守共享反馈。用户继续编辑时，变化的旧判断即时退出显示。 |
| 没有发现、正在处理、暂不可用 | 没有已核对结果时隐藏试点脉络区。已有主题页、旧相关笔记入口与原文可立即使用。试点状态只在设置诊断中给「等待整理」「已核对」「稍后重试」和手动重试入口。 | 记录、保存和阅读不依赖模型。未验证的旧近邻仍按现有「按内容相关推荐」提示显示，使用与核对关系分开的样式。当用户明确关闭相关笔记时，两种相关结果都隐藏。 |

演示样例均为合成数据。早期「默认让 AI 替我决定」、随后「出错难以纠正」、最后「低风险自动，高影响先确认」。三篇仍在「产品思考」，可产生「AI 做决定的边界」。如果第三篇只是转述别人的原则，关系只能显示有来源的转述或普通相关，不能写「你改了主意」。单篇提到两个独立问题可以参与多个脉络候选，显示预算取最有价值的两个。

## 2. 对抗审查及定案

| 编号 | 反例或失效方式 | 审查后写入规格的决策 |
|---|---|---|
| A01 | 把所有有主题的笔记送进现有自动建主题链路。一个大类生成几十个近义主题，历史数量、徽章和其他设备同步随之变化。 | 旧的自动形成主题链保持原触发语义。新脉络是既有主题下的本机衍生视图，首期只处理一个明确选定的主题，无 Core Data 写入。 |
| A02 | 把此前存下的 AI 排除词直接发给模型作硬规则。草稿可能来自一次移出、历史算法或后来被排除的笔记，错误会扩散。 | 存量 AI 排除项不升格为规则。点拒绝与类别规则分开。复用用户明确保存的 `categoryDefinition` 表达纳入与排除，带来源送判，规则可编辑撤销。 |
| A03 | 一条笔记移出等于一类都不许进。手动换分类也可能产生拒绝记录，但理由是归档选择。 | 拒绝按想法 ID × 主题 ID 处理，作用域永不自动扩大。当前未接通的排除项与过强的 UI 承诺一起收口。 |
| A04 | 把「碎碎念」的个人表达规则用在所有类别，例如用户特意创建「会议纪要」。 | schema 4 使用独立模板，用户定义优先。无定义看现有可用类别语义与用户纳入例，资料或主观内容本身都不是通用强制条件。 |
| A05 | A 和 B 相似，B 和 C 相似，A 与 C 其实讲两件事。多设备各算一批以后还会有重复。 | 同一簇须共用锚点并有逐成员的共同问题证据。去除重复文本及重复摘录，高重叠候选在同一主题内压制，生成物只在当前设备显示。 |
| A06 | 同样提到 AI 或同一本书，话题相近但没延续。反问、计划、引述和假设被误读为立场转换。 | 只在可核对的关系类型内输出。观点修正必须找到明确的本人旧立场、新立场及改判依据。其他情况按补充或对照处理，证据不足留空。 |
| A07 | 模型给出两段看似真实的引文，但来自同一篇、同一复制品、早晚顺序相反，或脱敏改动了范围。 | 结构校验和语义评测分开。后端与客户端都校验白名单、唯一引用、逐字范围和来源，时间由客户端冻结。高亮只用能定位到原文的映射。 |
| A08 | 处理途中编辑、删笔记、加「不参与 AI」、切主题、关开关、撤回授权或销毁索引。旧结果晚到并重新显示。 | 上传前、提交前、投影时用统一资格和版本校验。索引按来源回收派生结果。重启后也先验证才能显示。 |
| A09 | 升级导致全量历史重跑，或处理过的空结果每次打开都重算。后端停用导致旧功能跟着坏。 | A 使用可区分的评估版本和有界试点，B/C 复用一个请求结果和有终态的本机回执。禁能仅影响对应增量能力，旧客户端契约独立保留。 |
| A10 | 可见徽章只取创建较早的两枚，落库超量时按 UUID 截断。给更多关系并不能带来更多可见价值。 | 本批脉络显示在已有主题详情与相关区，不卡入徽章名额。schema 4 写入仍按既有自动归属总上限，按规则和内容价值排序，记录被限额的原因。 |
| A11 | 旧设备继续生成同一个 AI 归属，覆盖新设备刚判定的结果。合并主题后旧定义或排除范围被错搬。 | 第一批只在隔离库与同版本验证设备打开实际写入。生产启用前做新旧设备互操作验证；无法保护同步结果时，只开放本机脉络或让归类继续观察模式。合并保留主主题规则，禁止自动拼接或迁移试点 ID。 |
| A12 | 代表片段只取最近笔记的开头，结论藏在末尾或很早的笔记里。覆盖不足时模型装作看过全部。 | 限预算内做时间分层和局部取证，单条新近结果不能宣称长期变化。试点证明能找回旧证据，再谈扩大规模。 |
| A13 | 后端配置关了，客户端还拿缓存显示。未授权却因为 capability 请求偷传正文。 | 能力口只传状态，缓存资格到期、撤回或关闭即隐藏。服务端暗开与客户端试点都成立才可出网。 |
| A14 | 一个模型生成脉络，又用它自己打分，报告「准确率达标」；合成例通过被当成用户收益。 | 人先标，再按时间留出，盲看基线和新结果。安全事件零容忍。没有用户授权的真实样本时签出工程结果，产品效果暂未验收。 |

代码证据见第 8 节。审查通过的是修订后规格的边界，可以有序实施。是否达到质量、延迟、预算和双设备门槛由第 9 节的证据决定。

## 3. 架构决策

| 决策 | 背景与采用的结构 | 代价与理由 |
|---|---|---|
| D1 · 类别规则只保留一个权威来源 | 复用已同步的 `Topic.categoryDefinition`。自由文本既能写收什么，也能写排除和例外。点拒绝用既有 `ThoughtTopicLink`。类别代写保留为辅助信息。 | 首版采用用户自写一两句规则，避免另建规则实体、同步冲突和把旧派生词条迁成永久规则。用户明确的自然语言由模型判断，规则语义用真实样本验收。 |
| D2 · 脉络是已核对关系的本机视图 | 只读现有成员。复用语义向量和现有主题 UI，复用同一批经核对的 note-to-note 关系给相关区和主题页。 | 本机结果可能不同时出现；来源和手动归档仍走原同步链路。试点阶段避免写入同步主题目录、二次记忆或新的全局知识图谱。 |
| D3 · 对证据做两端校验 | 程序负责版本、引用、范围和用户权限。模型负责共同问题和语义关系。按时间采样，实证缺口给空结果。 | 证据逐字成立只能证明引用有效。观点有无变化、给出的信息是否帮得上用户，均由留出样本的人工验收决定。 |
| D4 · 版本和发布解耦 | 当前路由增量支持新版归类，单独启用新核对端点。旧协议默认仍工作。新数据仅增加本机 SQLite 表。 | 独立灰度和回滚有额外状态管理，能将后端尚未准备好、试点达标和客户端安装分开。 |

数据方向为「现有 Topic / Thought 及用户决定 → 本机资格筛选和召回 → 网关核对 → 本机可追溯结果 → 主题详情、相关旧想法」。原文与用户决定的事实源仍在现有仓库，索引、AI 草稿、关系和脉络均可从来源重建。

## 4. A 阶段 · 让类别规则可教、可退

### A1. 入口与规则来源

1. 继续经过 `TopicRepository.remove/assign` 与 `ThoughtTopicLinkProjection`。逐条核对列表徽章、主题详情列表、选分类页和清理页的入口。全量复用拒绝记录。AI 归属在落库守卫中再次服从当前人工移入/移出，不依赖请求发出时的快照。
2. 复用类别定义编辑器，在 `TopicRepository.updateCategoryDefinition` 调用前抓当前有效分类 ID 与编辑前定义。保存时以有效行和预期原定义重读核对。远端已改、已隐藏、已合并或已删则拒绝覆盖，提示重新打开并保留当前输入供复制。仓库写失败不要先关 sheet。无变化跳过保存。
3. 新输入限制为裁剪外缘空白后 ≤240 UTF-16，说明剩余长度。历史超限定义保持原文。编辑时允许复制、缩短与重新保存，后台若遇超限，不静默截断或降级为无定义；对该类别跳过评判，保留当前 AI 归属及用户决定，留诊断 `category_definition_too_long`。
4. AI brief 的 `definition/exclusions` 结束自动扩权。首版保留存量草稿及旧路径。试点的生效规则卡隐藏自动草稿；未记录来源版本的存量草稿继续留在本机，禁止作为新规则显示或使用。schema 4 不把旧草稿、旧排除数组、AI 自己归入的成员当作类别规则或正反例。类别无用户规则时只给标题和当下仍合规的主动移入/接受样本（至多 3 条，每条 ≤240 UTF-16）。样本为空时给 `insufficient`。自动草稿生成器可沿用旧版供旧行为使用；本期不新增推断排除的任务，也不搬运历史反例正文。
5. 规则优先级是当前人工关系决定 → 用户已保存的定义 → 用户归档例和类别名 → 依据不足。例与用户定义冲突以定义为准。纳入、排除两句互相矛盾且无法解释例外时返回依据不足。编辑规则只影响自动判定的范围；手动放入的笔记仍可留在类别中。
6. 替换理由面板「同类内容以后不会再收进来」。就这条使用「移出后，Holo 不会再自动把这条归到这里」。长期规则引导进同一个定义编辑器。文案同步简中、繁中、英文，使用现有本地化基础。

### A2. 兼容协议与写入

继续使用 `POST /v1/thoughts/semantic-relate`。保留 schema 1/2/3 校验、旧提示词、字段及语义。新客户端仅在双端开闸后为选定样本请求 schema 4；沿用 schema 3 envelope 与候选上限。三种客户端模式是 legacy、shadow、live。legacy 运行旧逻辑；shadow 在隔离样本中保存诊断且不改变既有关系；live 才提交新版结果。模式和能力检查由共同路由策略处理，队列去重和验证器使用同一结果。变更如下。

| 字段 | schema 4 约束 |
|---|---|
| `candidate.kind` | 必填 `category` 或 `thread`。 |
| `candidate.definitionSource` | 必填。类别为 `user` 或 `none`。内容脉络为 `none`。 |
| `candidate.definition` | `user` 时传用户当前完整规则经既有脱敏后的文本（非空，≤240 UTF-16）。原文 hash 或规范摘要只留本机作版本依据，目标、代表例与定义按同一规则脱敏，校验以实际送审文本为准。脱敏使规则无法判读时按依据不足处理。其他情况为 null。类别不传 AI 主题摘要作为默认证据。 |
| `candidate.representatives` | 类别仅传合规的用户纳入例。每次只在一次候选判定中使用，按现有脱敏规则传输。内容主题沿用原有合规样本。 |
| `decisions[].relation` | 保留旧枚举，新增 `excludes_category`，只允许 schema 4 的 `category + user`。类别禁止 `same_thread`，内容脉络禁止 `fits_category/excludes_category`。 |
| `excludes_category` 的证据 | 同时带目标 `quote/rangeUTF16`、`representativeRef: "definition"` 和 `representativeQuote`。引用能回到整句明确排除条款，模型按目标上下文核对例外。后端和 Swift 校验 ref、kind、source、两侧范围。证据不全不得当作排除。 |
| `deferred` 或协议错误 | 保留现有错误封套映射，缺字段/版本错位标协议错误，既有归属保留，不生成空结果回执。 |

新增独立 Prompt purpose `thought_semantic_relate_v3`（服务端路由及费用仍挂 `thought_semantic_relate_v1`）。iOS `PromptManager.swift` purpose、版本和默认模板与后端同步。规则示例必须覆盖「会议纪要类别明示收纯纪要」「碎碎念跨对象归入」「当前夹了自己的反思而命中排除例外」「同对象但未延续」「相互冲突返回 insufficient」。模型只见数据字段，忽略笔记和规则中的指令式注入。模板、契约与模型路由单独核验，Prompt 版本从实际 registry 读取，日志不能写死一个误导版本。

落库按本次**实际覆盖到的主题**做差量，单个请求未召回或因容量、长规则未送判的主题保持既有决定。正向新关系入选后写 AI 归属，类别只有 `excludes_category` 可撤销已有 AI 归属，普通 `none` 只拒绝新增。内容主题的 `none` 只在检查过该主题且所有送审段一致给明确负向时撤销既有 AI 归属。撤销前对应主体、候选和规则仍须当前。`related/insufficient` 不新增归属，也不把未看清的存量自动删除。长文结果聚合时，明确反证和正向命中冲突、或便于误读的跨段例外缺证时，返回 `insufficient`。删除、撤授权和正文改版仍走现有失效规则。

上限沿用每条最多 3 个自动归属，手动关系不占用也不修改。先保留仍有效且本轮没有明确负向结论的已有自动关系，再按「明确引用用户规则的类别匹配、双侧有证据的同脉络、代表例匹配」给新正向结果排剩余名额。同档按现有召回质量，最后用稳定 ID 平局。超出只记容量原因。验证器不能继续整批把未入选项 supersede。若历史超限，本轮只移除明确负向的已有 AI 归属，不加新项。

W1 在隔离评测模式固定允许的笔记 ID 集合和角色清单。capability 启用时只给这组笔记使用 schema 4，其余按 schema 3。不要把最新 capability 或账号白名单本身当成全量重评许可。规则修改使评估所依赖的规则摘要变动。沿用 `relationEvaluationVersion`，同一函数给队列、评估回执与去重，用规范编码生成有效目录/规则版本，跟踪 `schema + policy + effective candidate scope + contentHash`。shadow 版本与 live 版本分隔。请求发出和落库之间还须核对授权、采样正文 hash 和候选规则快照；过期重排当前批。完成态包括本次已判定且空结果。禁用时不以「v4 已完成」污染 v3 回执。已选择 shadow/live 的样本若发现服务端关闭或版本不可用，停新版请求，不对这些样本立即补发旧协议或重写已有关系，恢复旧策略使用 W4 的定向回滚。其他样本仍按 v3 处理。试点只用明确选定的隔离样本范围，不随一次规则保存无界重排所有资料。上线后的增量重评必须走现有后台分批、版本去重、取消恢复，确认无循环后才扩大。

## 5. B 阶段 · 一个既有主题内发现脉络

### B1. 试点范围、召回与限额

- 本机配置仅一个稳定 `pilotTopicID`。需现有 AI 处理授权、智能整理总开关、自动形成新主题开关、试点开关和服务器能力均有效才计算/展示脉络。相关区还需现有显示相关笔记开关。开关变化递增既有授权代数或当前试点代数，消费者读同一状态。透明展示范围名称，可从诊断切换和关闭。生产配置默认为空。主题改名继承同 ID。隐藏、合并或删除停止处理并立即退出显示，切换到其他主题需重新选择。
- 取当前有效、未删未归档、AI 可见且非空正文的主题成员。可复用 `TopicRepository.fetchThoughts(byTopic:)` 的成员语义与 `ThoughtTopicLinkProjection`；仓库读在其上下文内完成，传 actor 值快照。过滤合规对象后再排位和送判，避免先取前几条再丢弃导致漏召回。归档/回收与普通用户标签含义不重写。
- 校验现有向量的正文 hash、活跃模型版本与维度，索引只召回候选。主题内取 ≤120 条入池，按创建时间和稳定 ID 对合规成员排序，分为数量近似的较早、中段、较新三段，各至多 40 条。段内按索引等距取样，保留该段首尾；不足按实际数量。读候选范围只分页拿 ID、日期和资格快照，取到样本后再加载有限的正文与向量。超过上限只对采样范围输出，诊断记覆盖，不宣称找全。无需重嵌入老笔记。向量缺失复用已有入队，不另起全库生成。
- 每个待核对锚点从有相似度过门槛的同主题笔记召回最多 4 条，优先留较早和中段各一名，剩余按相似度和时间稳定选择；相似度下限先用 `ThoughtSemanticCalibration` 当前召回值并在 W0 冻结。范围内直接比较有限快照的现有向量并保持邻居门槛即可，避免改 USearch 协议；比较工作在后台。拒绝 pair、相同全文 hash、标准化后相同的摘录不同时作为独立成员。同样原文的局部重复由后端与人工样本再判。
- 初始种子按新中旧分层，从较新的独立锚点开始，每天最多 4 次新核对（含重试，每次最多 1 次自动重试，按设备日），每轮 1 次、同设备同一时刻 1 次。输入最多 5 条（含锚点），总正文 ≤6000 UTF-16、请求 ≤32 KiB；默认输出上限 1200 tokens，独立可关闭。后端继续执行现有主体费率、总后台预算和供应商隐私限制，任何一个打满即延期。不得通过手动入口或重复开页绕过新核对上限。高峰期沿用项目后台窗口，已缓存结果立即可读。
- 对短正文取连续全文。长文每条最多提供两个不重叠的连续窗口，各 ≤600 UTF-16。现有正文分段工具定位内容片段，优先固定头部并从剩余段按与锚点头尾的归一化字词重叠程度选一段，复用可用的现有分词；若仓库没有可复用入口，使用去标点后相邻双字符集合的 Jaccard，稳定同分选较晚片段；没有命中用末段。锚点本身用头尾。选择前脱敏，按脱敏全文计算 UTF-16 窗口 offset 和范围，不截断 surrogate pair。不引入额外的片段 embedding 调用，不把两个窗拼成可引用的一段。可用视野有限时让判断留空。

### B2. 核对输出如何形成卡片

一个请求以一条锚点为中心，核对锚点与每条候选的独立关系。结果可生成零条或一条共同问题，至少由锚点及两个已验证成员支持。存在相同词或桥接的两条边仍不足以生成脉络，须每条成员直接回答同一个问题。组可以只选有充分证据的候选子集。模型返回的标题和说明只作展示。

设备内一条脉络有独立 local UUID，不能拿标题当身份。相同父主题下，完全相同成员集合共用一个展示 ID，保留最近有效且有支撑的版本。不同集合的交集 ≥2 且 Jaccard ≥0.6 时按疑似重复压制展示，保留各自身份、证据和反馈；标题不参与判断。首版接受同一组笔记里两个独立问题可能只显示一个的取舍。排序先按有效支持数、再按最近证据时间、最后按稳定 ID，每个主题至多两个。已隐藏的卡按展示 ID 或上述重叠条件先压制；证据发生实质变化、低于重叠阈值的新脉络可单独出现。

固定 `taskKey = SHA256(canonical(scopeID, anchorID, sorted(noteID, hash, windowsDigest), policyVersion, redactionVersion, embeddingModelVersion))`。相同键的 `verified/no_result` 都是终态，重复打开和重启不调用。输入局部变化或显式算法升级只重算受影响锚点，受限额控制。正常无结果不会因为刷新设置页重新请求。只重算因失败而可重试的键或证据更新后的新键。

## 6. C 阶段 · 相关旧想法复用同一批核对

### C1. 关系与对照的产品语义

| 枚举 | 展示措辞 | 证据要求 |
|---|---|---|
| `continues` | 延续了这个问题 | 同一具体对象/问题，较晚有新增的一步或直接续写。 |
| `adds_example` | 补了一个新的例子 | 较晚给同一判断新增具体经历、条件或反例。在说明中清楚区分正例与反例。 |
| `contrasts` | 对同一问题给出了不同判断 | 双方有确切差异。不能从差异推定用户本人改主意。 |
| `revises` | 调整了先前的判断 | 两侧均为本人立场，且较晚明确回应/修正旧判断，能说明改变的条件。仅前后语气不同不成立。 |
| `none` | 无卡片 | 同关键词、同场景但不同问题，或只复述。 |
| `insufficient` | 无卡片 | 可能有关，但出处、对象、归因、时间或表达不充分。 |

关系按冻结的 `createdAt` 严格从早到晚，时间相同仅允许对照，并不声称先后变化。日期用笔记当前可核验的记录时间，不把记录时间当事件发生时间。不用长度、字数或生成的置信度作语义证明。`revises` 与 `contrasts` 不自动成为全局用户长期偏好。

主题卡和相关区读同一张 evidence 关系投影。相关区只在当前笔记有效且位于试点范围时读取，展示从较早记录回看当前记录的证据，每条最多取两条，优先明确的修正、关键对照和补充。尚无经核对的旧关系时，继续走原有的本机相关查找。编辑器有未保存的正文变更，旧结论立即隐藏，保存后通过既有变化流重新调度。点「不相关」沿用 `related_feedback`，新版试点先用同一双向拒绝与 AI 可见性过滤，不论读新组件还是回退旧近邻；同一拒绝不因改写标题、重新排序或版本升级而复活。若某个脉络失去用作支撑的关系，有效独立证据跌破 3 条时隐藏整卡。隐藏整卡是仅针对这个卡片的独立本机操作，不记作所有成员彼此不相关。

### C2. 新端点契约

新增 `GET /v1/thoughts/organization-capabilities` 与 `POST /v1/thoughts/verify-followup`。现有 `topic-name` / `topic-summary` 继续各自服务旧行为。能力端点与 POST 均按已有设备鉴权、可信主体解析和试点白名单判断，客户端本地选择还要成立。服务端分别设置默认关闭的 `HOLO_THOUGHT_SCOPE_RULES_ENABLED`、`HOLO_THOUGHT_FOLLOWUP_ENABLED`，以及仅配置可信主体的试点白名单 `HOLO_THOUGHT_ORGANIZATION_PILOT_SUBJECTS`。客户端开关或自报设备 ID 不能替代服务端检查。错误不回显配置或主体标识。

能力的 200 封套字段固定为 `schemaVersion: 1`、`categoryRulesVersion: 0 | 4`、`followupVersion: 0 | 1`、`policyVersion: String`。版本为 0 表示对应能力关闭。加 `Cache-Control: no-store`，客户端仅在内存中为当前主体留最多 5 分钟，通过现有 APIClient。授权撤回、切换身份、试点关闭、到期或收到功能禁用响应立即清掉。旧后端 404 视为不支持，禁止探测正文请求。离线且能力过期时隐藏新增派生卡，原主题及原文照常。关闭带来的远端最长可见窗口是 5 分钟；本机控制即时，后台重新前台时检查有效期。

请求为以下形状。正式 operationId 是 UUID，ref 是本次请求内的短编号，时间为 UTC Unix 毫秒整数。不发送笔记、主题真实 ID、整库目录或未取样全文。主题标题只作为核对背景（按既有规则脱敏后 ≤32 UTF-16），不提供给模型当共同证据。

```json
{
  "schemaVersion": 1,
  "operationId": "9f2bb45b-5dd4-457d-88cc-d619aad2eba7",
  "policyVersion": "thought-followup-1",
  "scopeTitle": "产品思考",
  "anchorRef": "N2",
  "notes": [
    {"ref":"N0","createdAtMs":1767225600000,"windows":[{"ref":"W0","text":"我原先想让 AI 自动做决定。"}]},
    {"ref":"N1","createdAtMs":1769904000000,"windows":[{"ref":"W0","text":"我发现自动决定出了错难以纠正。"}]},
    {"ref":"N2","createdAtMs":1772323200000,"windows":[{"ref":"W0","text":"我修改了自动决定的原则。高影响决定要先确认。"}]}
  ]
}
```

受控输出示例。协议示例是设计契约，实施时由实际后端代码产出 fixture，再驱动两端测试。

```json
{
  "schemaVersion": 1,
  "operationId": "9f2bb45b-5dd4-457d-88cc-d619aad2eba7",
  "policyVersion": "thought-followup-1",
  "decisions": [
    {
      "otherRef":"N0","relation":"revises","reason":"把自动决策收紧为高影响时先确认。",
      "anchorEvidence":{"windowRef":"W0","quote":"我修改了自动决定的原则。高影响决定要先确认。","rangeUTF16":[0,22]},
      "otherEvidence":{"windowRef":"W0","quote":"我原先想让 AI 自动做决定。","rangeUTF16":[0,15]}
    },
    {
      "otherRef":"N1","relation":"continues","reason":"针对自动决定出错后的问题加了一项确认条件。",
      "anchorEvidence":{"windowRef":"W0","quote":"我修改了自动决定的原则。高影响决定要先确认。","rangeUTF16":[0,22]},
      "otherEvidence":{"windowRef":"W0","quote":"我发现自动决定出了错难以纠正。","rangeUTF16":[0,15]}
    }
  ],
  "thread":{"title":"AI 做决定的边界","question":"哪些决定可以交给 AI 自动执行？","memberRefs":["N2","N0","N1"]}
}
```

- 每个非锚点 ref 恰好一个决定，`reason` 最多 100 UTF-16。四种成立关系双侧证据必填，`none/insufficient` 的 reason、两侧证据均为 null。没有任何可信关系时 200 返回全部非命中及 `thread: null`。只有一条配对成立时，相关区可用，主题脉络仍为空。
- 每个 `evidence` 引用对应 note 内的 window，quote 1–120 UTF-16，`rangeUTF16` 为窗口内半开区间。输入每 note 1–2 个 window，window ref 在 note 内唯一。服务端根据送审窗口取回逐字 canonical quote。可复用 `quoteAlignment.js`，只允许已定义的轻微排版对齐，拒绝拼接或歧义定位。Swift 再按同一窗口核对范围和逐字内容。Swift 校验 response envelope 与请求一致。
- `thread` 为 null 或对象。标题 2–32 UTF-16，question 4–100 UTF-16。成员 3–5 个唯一输入 ref，必须包含锚点。其余必须逐条有有效关系。排序日期由客户端从冻结数据重新算。标题相似不能派生归属。结构/证据协议错时整批返回失败，禁止把畸形响应标为 `no_result`。
- 请求长度限制检查实际字节数，覆盖无 Content-Length 和分块请求，限制须放在 JSON 解析及调用供应商之前，兼顾既有后台入口中间件的解析顺序。入模前再核对后台预算、主体限流、供应商隐私闸、审核以及当前接口版本。错误沿用 `createErrorResponse`，采用 `THOUGHT_FOLLOWUP_DISABLED`（503）、`INVALID_REQUEST/INPUT_TOO_LARGE`、现有审核映射、配额/限流、上游暂不可用或 `MODEL_OUTPUT_INVALID`。能力失败/隐私闸关闭禁止继续源文调用，不经过旧聊天端点兜底。
- 新 purpose `thought_followup_v1` 走专用无状态服务，复用已批准的现有网关供应商路由及 `topicInsightService` 的用量/审核结构。登记后台 path、purpose、metadata-only 强制集合、Prompt registry、server policy 与 iOS fallback。日志只记录计量、版本、错误码和笔记数等元数据。禁写原文、规则正文、模型输出、请求 JSON 到调试日志、埋点、报错详情或后台表。DeepSeek 只能使用 `deepseek-flash`，沿用合规现有通义设置。
- 防止客户端反复提交造成重复花费。持久化任务 key、operationId 和已开始次数，调用前原子标记。重启后要先识别未完成尝试，仅在既有退避和剩余上限都允许时重试，复用该键的 operationId。不要求网络 exactly-once，中断的请求可能已在网关计费，仍计入次数。持续协议错误只在新策略版本或定向人工复测下解冻，不能改 operationId 绕过后台冷却。

### C3. 本机状态、读写一致性和清理

新协调器消费既有谷时段心跳，只负责领取少量待处理任务及启动受控子 Task。避免在 heartbeat 中等待新增网络请求，使原 embed/relate 可以继续。应用进入后台或索引 shutdown 取消该 Task，重启或回来后根据存储中的领取时间与预算恢复。

用 `ThoughtSemanticStore` 现有 SQLite migration 加表，基于当前末代递增，保留向量与现有回执。拟用 `thought_followup_result`、`thought_followup_source`、`thought_followup_dismissal`，具体迁移编号以执行日基线为准。无 Core Data model、CloudKit schema、索引文件格式或后端数据库新表要求。

| 数据 | 必要内容与读写约定 |
|---|---|
| Result | 主键 taskKey，scope ID、anchor ID、状态、policyVersion、operationId、运行时限和下次重试、尝试次数、created/verifiedAt。成功后保存有界判定数组（双侧引用位置和简短说明）、可选 thread local ID/title/question/memberIDs。结果主体仍可能含私人推断，只留设备语义库。 |
| Source | 主键 taskKey × thought ID，索引 thought ID 与 scope ID。**记录该请求中所有输入**，每个有正文 hash、冻结创建时间、窗口起点/长度或等价可重建索引和摘要。结果有效性与清理以所有输入为准，包括最终没进入卡片的输入。 |
| Dismissal | 本机 scope ID × thread local ID，另保存确认展示过的成员 ID 集合用于高重叠压制，无内容。相关 pair 使用现有 `related_feedback`。清除设备索引按现有入口清掉本机反馈；日常重算与回滚保留拒绝。 |
| 持久状态 | `pending → running → verified / no_result / waiting / failed`。网络、上游超时可有界重试；配额等下个设备日或后端重试时刻；撤权、版本变更或范围退出取消旧运行。领取、输入映射、成功落库各用 SQLite 事务。任何失败保留最近有效结果而且不能更新到当前无效版本。 |

每份可显示证据至少带 source ID、content hash、文本处理版本、窗口位置与长度、范围。读侧根据当前合规正文按版本重建脱敏窗口并检查窗口 digest 与引用范围。用现有阅读器打开原文。只有能将范围唯一映射到原文时高亮，否则直接打开原文并保留卡片上的可核对片段。调用与显示句柄不要从模型响应字符串拼接跳转目标，只从当前本机 source 映射绑定。刷新和投影共用一个资格函数，避免主题和编辑器各藏一份状态。

统一收口给 `ThoughtSemanticChangeFeed`、`ThoughtAIExclusionService` 和 index destroy。编辑/进出主题/加排除/归档/删除/远端合并必须覆盖，观察 Thought、Topic、ThoughtTopicLink 及现有标签排除变化，对同一变更做防抖和定向清理。所有上传与落库时检查当前授权/epoch、主题有效性/稳定 ID、关系投影、当前参与资格及正文版本。新 UI 每次读取前再检查，打开中的视图收到失效事件立即撤掉旧证据。对象跨 actor 仅传值快照。无跨库原子事务时，以读侧校验防迟到写产生的瞬时泄漏，随后按索引清理。异步过程中任何一个来源丢失，共用上下文生成的整个批次失效，依现有节流重算。

撤授权时取消在途并清除新增派生 JSON、新增诊断中的敏感字段和作业。断网重启也先查授权、试点、服务器能力与本机证据有效性再显示。按来源删除/排除时清对应派生记录和索引引用，拒绝记录若仅含稳定 ID 可在验证需要时保留；硬删或清设备索引按现有政策清理。人工归类规则及拒绝关系仍走现有同步事实。证据正文派生的结果持有最多 30 天或每主题 200 个批次（取先触发，运行中的不强行淘汰）。过期先隐藏，再清可重建内容。每个当前计划锚点只保留最新完成凭证和 taskKey（最多 120 个），与结果主体分开计；只因过期、容量清理或重复开页不会重试同一个键。重进试点或换范围走有界的明确重建，不从 UI 生命周期触发。缓存失败或本机表损坏只停新增展示/写入，交给设置现有修复入口。禁止自动删库重建。
