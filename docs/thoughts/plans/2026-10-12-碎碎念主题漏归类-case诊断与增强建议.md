# 「碎碎念」主题漏归类：三条真实 case 诊断与增强建议

日期：2026-10-12。范围：只读真机数据、当前工作区代码与 Prompt，未改代码、未重跑线上 AI、未改真机记录、未部署。

## 产品结论

当前自动整理主要解决「哪些笔记讨论同一个具体对象、持续活动或问题」，东林本次期望则是「按自己的归档习惯，把生活随记、吐槽和个人感悟放进碎碎念」。现有实现没有充分区分这两种组织方式，因而会把用户认为自然的分类判为缺乏共同主题。

此外，真机中存在同一主题 ID 对应有效记录与已合并记录的情况，而关联链路按 ID 取第一条再检查有效性。这是与当前数据直接相遇的实现缺陷，应优先修复。现有记录不足以证明它就是三条样本每一次漏归类的唯一原因。

## 原因与证据

### 1. 主题身份解析缺陷，可能让正确候选在调用 AI 前消失

`ThoughtTopicCandidateEngine.swift:168` 与 `ThoughtTopicVerifier.swift:114` 均按 `id + deletedAt == nil` 查询，再取 `.first`，随后检查 `isVisibleTopic`。查询未先排除 merged，也未统一解析同 ID 的有效记录。

如果先取到 merged 旧记录：前者拿不到主题成员画像，后者直接丢掉候选；后者即使丢光候选也能正常完成并记录 no_match。当前数据库确实满足这一触发条件，但没有当次 fetch 的记录，不能断言历史调用取到哪一条。

建议：使用统一的有效主题解析入口，候选、画像、模型上下文、落库共用同一主题身份。保留同步历史与用户关系，不靠删库或重置 CloudKit 解决。

### 2. Prompt 把「个人归档类别」当成了「具体内容脉络」

当前源码中生效端模板 `HoloBackend/src/prompts/defaultPrompts.json` 的 `thought_semantic_relate_v1` 要求 same_thread 对应「同一个具体对象、持续活动或实际问题」，并要求双侧共同对象证据。对 Holo 开发、跑步训练这类主题适合；对横跨旅行、吃饭、工作感悟的碎碎念不充分。

`thought_topic_name_v1` 还明确禁止自动发现「碎碎念」这类泛化主题。但这是**新主题发现规则**，不是「已有碎碎念一定被直接禁用」的证据。需要区分：限制 AI 自创空泛目录，与尊重用户已有目录，可以同时成立。

本次核对了本地服务端模板与 iOS 后备模板，未读取线上托管覆盖版本，也未重放真实模型；因此不声称已证明线上每次使用的 Prompt 内容或模型准确率。

### 3. 用户的分类标准没有作为独立规则传给模型

真机「碎碎念」没有定义。关联请求只传 title、summary、最多三条代表笔记，没有传「这是一种表达方式分类」、用户认可的纳入/排除标准或正反例。

代表笔记按最近更新时间选，且每条仅取前 240 UTF-16 单位；该主题当前最近三条有效候选内容主要是出门喂猫、上架后的推广感受、Holo 过审里程碑。它们不能完整表达这个跨话题分类的边界，也不等于三条都由用户明确确认过。

建议：将用户分类定义与 AI 内容摘要分开；代表例优先用户确认、覆盖不同内容场景，避免 AI 自己的历史错误成为定义。

### 4. 最多三个候选的筛选方式不利于跨话题分类

当前先按主题成员平均向量和相似笔记筛选，再只保留三个主题。内容混合的分类并不天然拥有一个集中、稳定的内容中心；即使 Prompt 改对，未进入候选的主题也无法被核对。

用当前真机向量做离线近似复算、选用有效主题成员后，三条对「碎碎念」成员中心的相似度分别约为：东京 0.591、Agent 0.632、食堂 0.643，均高于源码种子召回阈值 0.55。这说明「内容与碎碎念毫无关联」并非合理解释，也不支持直接归因为阈值太高。

这些是当前副本的离线诊断值，不是历史 Top3、不等于实时 USearch 输出，更不是归类置信度。没有做降低全局阈值的质量验证。

建议：用户分类按类别定义独立召回；当前只有 12 个可见主题，可为用户启用的分类提供完整或分批核对，内容主题继续走相似度筛选。不要让表达方式分类与内容主题争同三个名额。

### 5. 结果与重评机制不够可诊断

当前 no_match 混合了「候选没有召回」「候选构建被过滤」「模型没有接受」等原因。空结果缓存有效期为 14 天，是否重评还受本地引擎版本、目录指纹、正文版本影响；仅部署服务端 Prompt 不保证这些历史笔记马上重评。

建议：保留本地最小诊断元数据，包括候选 ID、筛除原因、每个候选的关系决策、Prompt/规则版本；避免上传或长期记录完整私人正文。新规则发布后按版本对受影响的旧 no_match 重评，尊重手动归属与明确拒绝。

## 对三条样本的推荐产品判定

| 样本 | 按本次用户定义的归档 | 内容找回入口（仅候选，不要求创建主题） |
|---|---|---|
| 东京观景随记 | 碎碎念：个人经历与当下感受 | 东京 / Shibuya Sky |
| Agent 决策力反思 | 碎碎念：个人观察与感悟；可同时属于已有且匹配的产品思考 | Agent / 决策力 |
| 食堂价格吐槽 | 碎碎念：具体生活事件后的主观吐槽 | 食堂消费 |

第二条单看正文也很适合「产品思考」，不能把某个通用模型未选碎碎念一概当成常识错误。本次用户明确表达了自己的归档方式，系统应能吸收这一规则，而不以篇幅长、包含专业概念或有完整论述为由排除。

不建议把碎碎念改成所有无法分类内容的兜底；纯转载、清单、代码片段、客观会议纪要、无主观体验的流水账应作为反例核对，而不是自动全部归入。

## Prompt 与能力增强建议

推荐先增加「用户类别规则匹配」这一判断能力，保留既有内容主题关联能力。界面仍可继续叫「主题」，不必把内部类型暴露给用户。

建议规则草案：

> 对用户主动建立或启用的归档类别，依据其分类定义与用户确认的正反例判断是否符合；不要求不同成员讨论同一个具体对象。对自动发现的内容主题，仍要求共同对象、活动或问题。分别独立判断，允许重叠归属。
>
> 本用户的「碎碎念」包括个人生活片段、即时感受、吐槽，以及由生活或工作触发的个人观察与反思；不限篇幅，不因包含 AI、产品等专业内容而排除。不能只因为找不到其他主题就归入。纯转载、纯资料、任务清单等是否归入，按明确排除规则判断。
>
> 类别匹配给出原文依据与命中的分类规则；内容主题关联给出共同对象与双方依据。不能用历史笔记里具体谈到的对象，替代用户对整个类别的定义。

这不是只加一句 Prompt：候选数据需包含分类类型、用户规则与正反例；输出及校验需能区分「符合类别定义」与「同一内容脉络」，不应把两者都硬塞成 same_thread。个人规则作为数据传递，不写成对所有用户生效的全局特例。

实施顺序：

1. 修复同 ID 的有效主题解析，并补齐候选消失原因记录。
2. 接入用户类别定义和相应候选通道，完善两种关系的 Prompt 与校验契约。
3. 用这三条作为已标注正例，再配纯资料、专业报告、生活流水账等反例和多主题例；同时衡量该归入而漏掉、以及不该归入却误收，不能只验这三条全通过。
4. 使用未参与改 Prompt 的真实留出样本验证后，再升级规则版本并重评受影响笔记。

后续若实施 Prompt 修改，必须同步 iOS `PromptManager.swift`、后端 `defaultPrompts.json` 与版本号，并部署后端、核验线上实际版本；只改 iOS 后备模板不会保证生效。本次没有产生后端代码改动或部署。
