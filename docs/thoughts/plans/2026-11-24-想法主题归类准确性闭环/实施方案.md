## 0. 一页纸摘要（产品语言）

**目标**：用户随便记，Holo 自动把每条想法放进对的主题；放得准、放了不乱动、用户纠正一次就记住、拿不准就先问。

**东林已拍板的三条产品决定（2026-11-24）**

| 编号 | 决定 | 本方案的落地口径 |
|---|---|---|
| D1 | 一条想法最多 3 个分类 | AI 自动归入 + 待确认建议，合计只把一条想法的主题数补到 3；用户手动放入不设上限、也不被 AI 挤掉 |
| D2 | 拿不准的放「待确认」 | 新增本机「待确认」队列：AI 拿不准的归入、AI 认为放错的移出、AI 发现的新主题，都先问，用户一键确认或驳回 |
| D3 | 除非用户主动，已有归属一律保留 | AI 永不自行删除/替换任何已显示的归属；AI 认为不对时只能提「建议移出」进待确认 |

**要做的五件事（按顺序）**

1. **先做尺子**（P0）：用东林真实想法标一套金标集，量出现在到底准不准，以后每次改动都拿它过闸。
2. **止住乱动**（P1）：落库改「只加不删」、改字不再让徽章消失、重判只看变化的部分、手动放入不再清掉其他分类。纯客户端，可先单独发。
3. **判得对**（P2）：分类按自己的含义判（不再一律按「碎碎念」口径），带上用户纠正过的反例，模型给出「明确 / 拿不准」两档。
4. **待确认**（P3）：拿不准、建议移出、新主题都进同一个待确认页。
5. **新主题不泛滥**（P4）：AI 发现的新主题先确认再建，近义主题不重复建，成簇不再「链式拉人」。

## 1. 不变量（所有阶段必须同时满足，测试逐条锁定）

| 编号 | 不变量 | 违反示例 |
|---|---|---|
| I1 | AI 只把一条想法的可见主题数（用户 active + AI active + 待确认·加入）补到 3；用户手动关系不计入 AI 的撤销范围、也不被挤出 | 第 4 个 AI 正项把旧 AI 归属替换掉 |
| I2 | AI 永不自行把任何 active 关系改成 superseded/rejected；AI 发起的移出只能以「待确认·建议移出」出现 | 重判没再选中 → 撤销 |
| I3 | 用户决定（移入 / 移出 / 确认 / 驳回 / 保存规则）立即生效、经 Core Data 跨设备同步，优先级高于任何 AI 结果 | 用户驳回后 AI 又加回 |
| I4 | 用户每个决定都成为后续判定的输入（正例 / 反例 / 规则） | 移出只挡这一对，同类下一条照收 |
| I5 | 待确认只来自「用户刚产生的内容或动作」（新写、编辑、保存规则、新建分类、用户主动发起的体检）；后台迁移/回填不得往待确认里塞东西 | 引擎升级后待确认涌入 300 条 |
| I6 | 重判只针对变化的范围：想法正文变 → 重判该想法；某分类规则变/新建 → 只判该分类。与之无关的目录变化不触发重判 | AI 新建一个主题，全库重问模型 |
| I7 | 类别边界只从用户确认过的证据学：用户规则、用户放入/确认的成员、用户移出/驳回的反例。AI 自己归入的成员不得作为代表例或定义来源 | AI 错收 → 成代表例 → 定义带偏 |
| I8 | 任何判定逻辑/提示词/阈值变更，先过金标集评测闸（§8），不达标不放量 | 凭体感改 prompt 直接发版 |

## 3. 总体设计

```
                 ┌──────────── 触发（带 trigger 标签）────────────┐
 新写/编辑 ──► note_new / note_edit        保存规则/新建分类 ──► rule_change / category_created
 AI 新主题确认 ──► topic_created            引擎升级 ──► engine_migration（仅后台，静默）
                 └────────────────────────────────────────────────┘
                                   │
                       ① 召回（本机向量，不变）
                                   │
                       ② 判定（schema 5：分型口径 + 反例 + certainty）
                                   │
                       ③ 落库策略（纯函数 decideCommit，唯一真源）
              ┌──────────────┬──────────────┬───────────────┐
           自动归入        待确认·加入     待确认·移出      静默记录
       (clear 正项,     (borderline 正项, (既有 AI 归属 +   (超额 / 迁移负项 /
        名额内)          trigger∈用户类)   明确负向 + 用户类) 不确定)
                                   │
                       ④ 用户决定 → Core Data 关系（同步） → 下一次判定的正例/反例
```

### 3.1 关键设计取舍（含理由）

1. **待确认存本机 SQLite，不进 Core Data。** `ThoughtTopicLink.stateEnum` 对未知值回落 `.active`（`ThoughtTopicLink+CoreDataClass.swift` `LinkState(rawValue:) ?? .active`），新增 `suggested` 状态会让旧版本设备把建议当成已归入显示。待确认是可重算的派生物，本机存储足够；用户的确认/驳回写成正式关系（同步）。代价：待确认不跨设备同步，可接受（§9 R7）。
2. **落库策略与 schema 解耦。** P1 的「只加不删 + 证据排序」对 schema 3 的结果同样生效，止血不依赖后端放量。
3. **去掉「全库指纹」去重，改 pair 级评估记录。** 每对（想法 × 主题）记录「判定时的正文 hash + 主题规则版本 + 引擎版本」，只有这三者变化才重判这一对。
4. **「拿不准」用模型给的离散两档（clear / borderline）+ 结构信号**，不要数值 confidence（沿用现有「不得输出数值 confidence」口径）。两档是否有区分力由 P0 尺子验证，不行就启用备选信号（§9 R1）。
5. **停用 AI 类别理解（brief）维护器。** 它的产物在新判定中不使用（I7），又是全库重判的主要触发源（F3）。主题详情「这个主题收什么」只展示用户规则，无规则时显示空输入和示例（复用 W1 已做的试点口径）。

**P0.4 指标定义（报告必须全部给出）**

| 指标 | 定义 |
|---|---|
| 自动正确率 | 自动归入的 pair 中属于 gold 的比例 |
| 召回 | gold pair 中被「自动或待确认·加入」覆盖的比例 |
| 待确认率 | 产生 ≥1 条待确认的想法占比 |
| 待确认命中率 | 待确认·加入中属于 gold 的比例（应明显低于自动正确率，否则说明分档无效） |

| 空归类率 | gold 非空但无任何自动/待确认的想法占比 |
| 单次成本 | 平均输入/输出 tokens × 现行价，换算每千条费用 |

### P1 · 止住乱动（纯客户端，可独立发版）

**P1.1 落库策略纯函数 `decideCommit`（新文件 `AI3/ThoughtTopicCommitPolicy.swift`）**

输入（值类型）：
```swift
struct CommitInput {
  var verdicts: [Verdict]            // 本轮送判候选的结论：topicID, kind, relation, certainty(clear|borderline|nil), citesUserRule, quote, range, recallScore, consistentNegative
  var existingAIActive: Set<UUID>    // 该想法 ai/v3 active 关系（含正文已变的 stale）
  var userActiveCount: Int           // 用户 active 关系数（含 user/manual、user/acceptedSuggestion、legacy active）
  var pendingAddCount: Int           // 该想法未决的待确认·加入数
  var rejectedPairs: Set<UUID>       // 墓碑
  var trigger: Trigger               // note_new | note_edit | rule_change | category_created | topic_created | engine_migration | user_audit
  var limit: Int = 3
}
struct CommitOutput {
  var autoAdd: [Decision]            // 写 ai/v3 active
  var reaffirm: [Decision]           // 既有 AI 归属续期（刷新 basisTextHash/证据）
  var suggestAdd: [Decision]         // 待确认·加入
  var suggestRemove: [UUID]          // 待确认·建议移出（只针对 existingAIActive）
  var silent: [(UUID, reason)]       // capacity / migration_negative / insufficient 等
}
```
规则（逐条单测）：
1. 永不输出撤销（I2）。负向结论只可能进 `suggestRemove` 或 `silent`。
2. 既有 AI 归属：本轮正项 → `reaffirm`；明确负向（类别 `excludes_category`，或脉络所有分段一致 `none`）且 `trigger ∈ {note_edit, rule_change, user_audit}` → `suggestRemove`；其余 → 保留不动（迁移负项记 `silent: migration_negative`，供 P3「主动体检」读取）。
3. 剩余名额 `slots = limit - userActiveCount - existingAIActive.count - pendingAddCount`，≤0 时不新增任何东西。
4. 新正项排序：引用用户规则的类别匹配 > 双侧证据的同脉络 > 其他类别匹配；同档按 recallScore 降序，再按 topicID 稳定平局（不再用 UUID 作为主排序）。
5. 新正项分流：`certainty == borderline` → 仅当 trigger ∈ {note_new, note_edit, rule_change, category_created} 才进 `suggestAdd`，否则 `silent: borderline_background`；`clear` 或 schema 3 无 certainty → `autoAdd`。
6. `rule_change / category_created` 的 `autoAdd` 与 `suggestAdd` 都占名额，名额用尽 → `silent: capacity`。
7. 墓碑 pair 一律跳过（与落库守卫 `recordAIV3Decision` 双保险）。

同一份规则写成 `docs/.../eval/commit-policy-vectors.json`（≥25 组输入→期望输出），Swift 单测与 JS 移植都跑这份向量，保证两端一致。

**P1.2 接入落库**
- `ThoughtTopicVerifier.evaluateLegacy` 与 schema 4/5 路径的 commit 段都改为调用 `decideCommit`：删除 `:304` 的 UUID 截断和 `:320` 的整批 supersede；schema 4 的 `selectSchema4Outcome` 中 `revokedTopicIDs` 改为输出 `suggestRemove`（schema 4 只剩试点，统一迁到新函数后删除 `selectSchema4Outcome`，同步改写其测试）。
- `suggestAdd / suggestRemove` 在 P3 之前写入 `pair_evaluation`（P1.4）的 verdict 字段，不展示；P3 上线后由 P3.2 规则回放成待确认（仅回放 30 天内、trigger 属用户类的记录）。

**P1.3 改字不再让徽章消失（F4）**
- `ThoughtTopicLinkProjection.isCurrentActive`：`ai/v3 active` 不再要求 `basisTextHash == 当前正文`，一律视为有效。
- 「为什么归这里」面板（`APP/Views/Thoughts/ThoughtCardView.swift` 相关段）：hash 不一致时证据区显示「依据来自修改前的版本，Holo 正在重新核对」，不展示可能错位的引文高亮。
- 跨版本：旧版本设备仍按 hash 隐藏 stale 关系，只会少显示、不会错显示，可接受。

**P1.4 pair 级评估记录与定向重判（F3、I6）**
- `ThoughtSemanticStore` 新表（`CREATE TABLE IF NOT EXISTS`，本机）：
  ```sql
  pair_evaluation(thought_id BLOB, topic_id BLOB, content_hash TEXT, topic_rule_version TEXT,
                  engine_version TEXT, relation TEXT, certainty TEXT, outcome TEXT,
                  trigger TEXT, evaluated_at REAL, PRIMARY KEY(thought_id, topic_id))
  thought_evaluation(thought_id BLOB PRIMARY KEY, content_hash TEXT, engine_version TEXT, evaluated_at REAL)
  ```
  `topic_rule_version = sha256(kind | categoryDefinition)` 前 8 字节十六进制；**不含标题**（改名不触发重判，§9 R12）。
- `semantic_job` 加列 `trigger TEXT`（`ALTER TABLE ... ADD COLUMN`，先查 `PRAGMA table_info` 防重复）和 `topic_scope BLOB`（可空：非空表示只判这一个主题）。
- 入队规则（`ThoughtSemanticChangeFeed`）：
  - 正文新建/定稿编辑：`thought_evaluation` 无记录或 hash/引擎不同 → 入队全候选 relate，trigger 由「是否首次评估」决定 `note_new / note_edit`。
  - 回前台/远端变更对账 `reconcileAllThoughts`：只按上一条规则补漏，不再用全库目录指纹判断（删除 `hasRelationRecord` 的目录版本比较与 14 天过期判断）。
  - 引擎版本升级：缺当前引擎记录的想法入队 `engine_migration`，优先级最低，只在谷时段跑（复用 `HoloAIWindowPolicy`），本机每日上限 150 次请求（常量 `migrationDailyRequestCap`）。
  - 新建分类 / 保存或修改分类规则：入队一个「主题回填任务」：按（标题+规则向量与想法向量相似度降序，再按最近）取至多 200 条，逐条 `topic_scope = 该主题` 单候选判定，trigger = `category_created / rule_change`；该主题既有 AI 成员全部包含在内（用于产生建议移出）。

在 v3 基础上改写类别段（要点，执行模型写正文后须过 P0 dev 集）：
- 类别判定先看用户规则（definitionSource=user，规则优先于一切，沿用 v3 五个示例）。
- 无规则时**按标题本身的含义判断**：标题是领域（如「工作与事业」「健康」「读书」），就看目标是否属于该领域，资料、摘抄、清单、纪要都可以收；标题是表达方式（如「碎碎念」「随想」「吐槽」），才按表达方式判断。**删除 v2/v3 中「必须有用户自己的表达，纯资料不符合」的通用强制条件**。
- 反例：counterexamples 是用户亲手移出的内容；目标与反例属于同一种内容且规则没有写明例外时，判 none；只是话题相近、内容性质不同时不受反例影响。

- certainty：clear = 原文直接满足标题/规则/纳入例的核心含义，不需要推测；borderline = 只部分满足、需要推测用户意图、与反例相似但有差异、或标题含义宽泛且没有规则与纳入例时的边缘匹配。拿不准宁可 borderline。
- 一条想法同时符合多个类别时都可以判正（落库层负责名额），不要为了只选一个而压低其他判断。
- 保留：数据非指令、逐字引用、双侧证据、thread 的「同对象不等于延续」。

### P3 · 待确认

**P3.1 存储（本机 SQLite，`ThoughtSemanticStore`）**
```sql
topic_suggestion(id BLOB PRIMARY KEY, thought_id BLOB, topic_id BLOB, kind TEXT,   -- add | remove | new_topic
                 reason TEXT, quote TEXT, range_utf16 TEXT, content_hash TEXT,
                 batch_key TEXT, state TEXT, created_at REAL, decided_at REAL,
                 UNIQUE(thought_id, topic_id, kind))
topic_proposal(id BLOB PRIMARY KEY, name TEXT, definition TEXT, member_ids TEXT,
               member_quotes TEXT, cluster_fingerprint TEXT, state TEXT, created_at REAL)
```
- `state`：`pending | accepted | dismissed | invalidated | expired`。
- `reason`：`borderline | edited_negative | rule_excludes | rule_includes | audit_negative`。
- `batch_key`：规则回填产生的同主题建议共用一个 key，用于分组展示。

**P3.2 生成规则**
- `decideCommit.suggestAdd / suggestRemove` → upsert `topic_suggestion(state=pending)`。
- 去重：同 (thought, topic, kind) 已有 pending 只刷新证据；已 dismissed 的不再生成（加入被驳回已有墓碑兜底；移出被驳回 → 关系已转为用户关系，不会再进入 AI 撤销范围）。
- 上限：全局 pending ≤ 50，超出不再新增（新写/编辑来源优先保留，回填来源先丢）；同一 batch 单次 ≤ 30。
- 过期：pending 30 天无操作 → `expired`（不改任何关系；加入类等于没归，移出类等于保留）。
- 读时再验：展示前校验 pair 当前状态（已是用户决定/墓碑/主题已删除或隐藏/想法已删除 → `invalidated`）。
- P1 期间记录在 `pair_evaluation` 的建议，在 P3 首次启动时按本节规则回放一次（仅 30 天内、trigger 属用户类的记录）。

| 待确认率（新写场景） | ≤ 15% | 超出说明 borderline 定义过宽 |
| 待确认命中率 | 比自动正确率低 ≥ 15 个百分点 | 否则两档无区分力 → 启用 §9 R1 备选 |
| 稳定性（3 轮） | ≥ 95% | |
| 规则样本（11-16 eval 的 14 条 + 本批新增反例样本 ≥ 8 条） | 通过率 ≥ 90% | |
| 每千条费用 | 报告即可，东林确认 | 仅 deepseek-flash |

门槛在 legacy 基线出来后允许东林**调整一次**，之后冻结；holdout 集只用于最终过闸，不用于调 prompt。

## 9. 对抗性审查（第一性原理）

审查方法：对每个设计问三件事——它真的让「准」变好了吗？用户什么都不做时会发生什么？最坏情况下会把用户的数据弄成什么样？

| # | 攻击 | 结论 | 写入规格 |
|---|---|---|---|
| R1 | 模型自报的 clear/borderline 没有校准，可能两档正确率一样，「待确认」就成了随机抽查 | 成立，属关键不确定性 | §8 设「待确认命中率比自动低 ≥15 点」硬闸。不达标的备选：仅对 note_new/note_edit 做两次独立判定，两次不一致 → borderline（成本约 ×2，只作用于新写），其他 trigger 不用 certainty 一律走 clear 路径 |
| R2 | 用户从不看待确认，拿不准的永远没归，违背「随便记录自动分类」 | 部分成立 | borderline 只是少数（≤15% 闸）；clear 照常自动归；不理会的后果仅是「没归」，不是「归错」，符合「准」优先。30 天过期防堆积；不用红点和通知，避免打扰 |
| R3 | AI 永不撤销 → 早期错归永久留着 | 成立，是 D3 的直接代价 | ① 放量前正确率 ≥90% 闸；② 编辑/改规则后的负向结论进「可能放错了」；③ 设置页「检查可能放错的」由用户主动触发，把迁移期静默负项拿出来 |
| R4 | 迁移期全库重判费用 | 可控 | 谷时段 + 每日 ≤150 次 + 只跑一遍；pair 级去重后日常只判新写/编辑。P0 报告给出每千条费用，东林确认后才放量 |
| R5 | 「改字后旧归属仍显示」可能已经不对 | 接受 | D3 明确保留；几分钟内重判，负向 → 建议移出。证据区标明「来自修改前版本」，不误导 |
| R6 | 去掉全库重判后，新建分类时旧笔记进不去 | 不成立 | 新建分类/改规则触发单主题回填（≤200 条，按相似度与时间优先），专门覆盖这个场景 |
| R7 | 待确认只存本机，多设备看到的不同 | 接受 | 待确认是派生物；用户决定写 Core Data 同步；另一台设备读时再验自动失效，不会出现「已确认的又来问」 |
| R8 | 旧版本设备的 legacy 路径仍会 supersede AI 关系并同步过来 | 成立、无法从新版本侧阻止 | 记录为残余风险；东林两台开发设备同时升级；对外用户随版本更新收敛 |
| R9 | 反例导致过度排除（一次移出把相近但不同的都挡掉） | 部分成立 | 反例 ≤2 条且只来自明确的用户动作；提示词限定「同一种内容且无例外才排除」；P2 新增 ≥8 条反例样本（含「话题近但性质不同不应排除」）进闸 |
| R10 | 历史墓碑里混着单选清理产生的「非真实拒绝」，会误当反例 | 成立 | 反例只取带 decisionReason 的新墓碑；历史墓碑只挡 pair，不作反例 |
| R11 | 停用 brief 后，无规则、无用户成员的分类只剩一个标题，判不准 | 部分成立 | 预设分类标题都是清晰的领域词，标题判定在 v4 提示词下是正确的依据；宽泛标题的边缘匹配会被标 borderline 进待确认，用户的确认又成为纳入例，形成闭环（I4/I7）。由 P0 尺子验证 |
| R12 | 改名不触发重判，改名改变了含义怎么办 | 接受 | 改名多为措辞调整；含义变化应写进规则（会触发回填）。D3 下已有成员本就保留 |
| R13 | 名额按「用户 + AI + 待确认」算，用户手动放满 3 个后 AI 不再给任何建议 | 符合 D1 | 用户手动不设上限；AI 不往已满 3 个的想法里加 |
| R14 | 新主题先确认会降低「自动」程度 | 取舍 | 新建主题是结构变化，错一次就要用户手动清理一整个主题，代价远高于单条错归；默认走确认（§10 Q1，东林可改） |
| R15 | 金标集只有东林一个人的数据，可能过拟合 | 接受 | 这是当前唯一真实数据；用 11-16 合成集（43 找回 / 15 硬负例 / 14 规则）补充；holdout 冻结不调参 |
| R16 | P1 先发、P3 未上时，负向建议无处展示 | 已覆盖 | P1 写入 pair_evaluation，P3 上线首次启动时回放（只回放 30 天内的用户类 trigger），符合 I5 |
| R17 | 单候选回填请求失去「多个候选对比」的上下文，判定口径可能和全候选不一致 | 部分成立 | 类别判定本就逐个独立（提示词要求逐候选独立判断）；P0 尺子加一项「单候选 vs 全候选一致率」，< 90% 则回填改为带全部类别候选 |
| R18 | 本方案是否又在堆工程而不是解决准确率 | 自查 | 真正提升准确率的只有三处：判定口径分型（F1）、反例与只学用户证据（F6）、拿不准不落库（F7）；其余都是让准确率不被稳定性问题抵消。P0 尺子保证每一步都能被证伪 |

## 11. 给执行模型的约束

1. 按 P0 → P1 → P2 → P3 → P4 顺序，每阶段完成标准全部满足、回填 `实施记录.md` 后再进入下一阶段。P1 可在 P0 标注期间并行开发，但 P2 放量必须等 P0 基线。
2. 先写失败测试（TDD），核心纯函数覆盖率 ≥80%。
3. 遵守 `CLAUDE.md` 编码约定（禁 `!`、禁 `print`、Logger、DateFormatter + zh_CN、ScrollView 隐藏滚动条等）与 `AGENTS.md` 红线（CloudKit 开发库、DeepSeek 只用 flash、后端发版只走 `holo-backend-deploy`）。
4. 真实用户正文不得进入 git、日志或后端诊断表；评测私有目录必须先 gitignore。
5. 每阶段只暂存本批文件（工作区有其他会话的在途改动），commit 格式 `feat(thoughts-ios): …` / `feat(thoughts-backend): …`。
6. 任何与本方案冲突的发现（代码与本方案描述不符），先在 `实施记录.md` 记「方案失实」条目并按代码事实调整，不得硬套本文。
7. 发版、开生产 env、CloudKit schema 部署、真机验证，每一项都需东林当次点头。
