## 1. 产品结论与成功标准

### 1.1 一个真实例子

用户写下三条想法：“想带妈妈去日本”“查了一下东京住宿”“假期可能只有五天”，其中第二条主动写了 `#旅行/日本`。

- **想法**：三条原文分别保留，用户可以单独编辑、搜索、引用。
- **#标签**：只代表用户主动输入、手动加上或明确确认的标签。点 `#旅行/日本`，找回有这个标签的想法；不因 AI 判断相近就偷偷给另外两条加上这个标签。
- **主题「日本旅行」**：可以包含这三条，即使其中两条没有 `#旅行/日本`。点主题先看到“为何在一起、最早到最近、有哪些来源想法”，再看完整时间流。主题名与标签名相同也不自动共用身份。

用户不需要学习“标签层级”和“主题分类池”。默认动作仍是记录想法；#标签是可选的自定义捷径；主题的价值是**不打标签也能把跨时间的相关原文找回来**。

### 1.2 用户必须显著感到 AI 主题归类已生效

一次成功归类必须同时满足以下四项，少一项不能算完成：

1. 新想法保存后无需人工点“整理”；高可信关联在后台落库。
2. 想法卡片出现有来源语义的主题行，例如 `Holo 已归入 · 日本旅行`；用户手动放入时显示 `已加入主题 · 日本旅行`。AI 来源不能冒充用户决定。
3. 点主题名直接进入主题详情；侧栏主题条数和详情想法列表包含这条新想法，时间跨度与首尾记录同步更新。
4. 从该主题移除或更改后，卡片、侧栏、详情立即一致；同一正文版本不被 AI 再次归入被拒绝的主题。

正确的“没有归类”也允许存在：内容不足、没有相关主题、证据含糊、离线、未授权或预算暂停时，不强行套主题。详情页可轻量显示真实状态或说明，首页不放永久进度条、不生成待审核任务箱。

### 1.3 不做的事

- 不让 AI 创建、改名、合并或删除用户 `#标签`。
- 不把每条想法塞进一个唯一大类；主题是可重叠的长期方向，一条想法允许关联 0–N 个主题，卡片默认展示最多 2 个，其余在详情查看。
- 不把“AI 主题归类”做成每次都要用户确认。**已存在主题的高可信关联自动弱展示、可一键纠错；新主题创建才需要确认。**
- 不为了提高覆盖率降低质量阈值、把相似文本误写成观点一致、把候选或 shadow 结果当成已归类。
- 不因 UI 开关打开就自动放行隐私、供应商、成本和模型质量闸门。

### 1.4 决策记录与取舍

| 决策 | 选择及理由 | 代价与约束 |
|---|---|---|
| D1 导航 | 保留一条想法时间流，标签与主题是两种范围；主题另有回顾详情 | 需要设计真实交集入口，不能只换图标或把两者都做普通筛选。 |
| D2 关系事实源 | `ThoughtTopicLink` 是唯一产品事实，旧关系仅作兼容镜像 | 需要迁移、对账与旧 UI 回滚验证；不能只改一处查询。 |
| D3 自动化强度 | 既有主题的 high 关系自动弱展示，用户可纠错；中低结果不打扰 | 覆盖率必须和精确率同时实测；没有校准结果不能以“显著生效”为由降门槛。 |
| D4 新主题 | 只提出带来源的建立建议，由用户确认 | 冷启动不会在第一条想法后立刻出现主题；避免大量空主题和错误命名。 |

## 3. 信息架构与交互规格

### 3.1 单一主内容流，两个清楚的浏览入口

继续使用已有侧栏，不恢复“想法 / 主题”双首页。侧栏固定分为：

```text
想法
  全部想法

我的 #标签                 自己标记的找回词
  #旅行/日本
  #工作/Holo

主题                       Holo 串起的长期方向
  🍃 日本旅行   3 条想法
  🍃 Holo 产品   8 条想法
  [建议建立「跑步训练」· 4 条原文]  建立 / 忽略

管理主题 · 已归档
```

“我的 #标签”只读用户认可的逐条 assignment；AI 主题结果绝不长进标签树。主题列表只展示有有效成员的正式主题，空预设和停用主题留在管理页；主题数量与详情、卡片按同一有效关系计算。置顶项保留 `#` 或主题图标与来源字样，不能把两种对象混成同一外观。

### 3.2 想法卡片与编辑页

- 标签位写 `#旅行/日本`，只呈现用户输入/确认的标签。正文内已高亮的行内标签不重复堆在底部。
- 主题位单独一行：`🍃 Holo 已归入「日本旅行」`（AI 高可信弱关联）或 `🍃 已加入「日本旅行」`（用户手动/接受建议）。别只靠绿色、叶子图标区别，VoiceOver 也要读出来源。
- 轻点主题名进入主题详情；更多菜单提供 `为什么归在这里`、`更改主题`、`从这条移除`。证据可回到原文；若只有索引相似度、无可解释证据，不写“因为你说过……”的伪理由。
- 保存先反馈 `已记录`。AI 成功后，在仍打开的该条想法上给一次短暂、准确的内容回执 `已归入「日本旅行」`；离开页面后仍可从卡片主题行找到结果。不要用持续旋转进度或“正在理解你”掩盖未运行/失败。
- AI 没有高可信结果时不出现假主题。想法详情可显示 `暂无匹配主题`；离线、未授权、暂停等要与“没有匹配”区分，且只在用户查看详情或相关设置时说明。

### 3.3 主题页必须比标签筛选多出价值

主题页首屏按顺序包含：主题名、成员数和真实时间跨度 → `从最初到现在` 的最早/最近来源 → 可选的、已验证且标记更新时间的 AI 回顾 → 完整时间流。主题头部还要如实显示 `你加入 N 条 · Holo 找到 M 条`，让自动归类的贡献可见；历史未知来源不计入任一类，单独按“历史归集”处理。已有首尾记录实现可复用；让 AI 回顾成为增量价值，不能因摘要端点失败让主题页退成空壳。

标签页只显示 `按你写下的 #标签找回` 和匹配原文列表；不显示 AI 回顾，不暗示标签是 AI 理解。一个想法可同时出现在某 #标签和某主题，页面用各自的来源文案解释为什么出现。

**把两者的关系直接摆出来，但不混为一物。** 在某 #标签范围内，如果匹配的想法同时属于主题，显示最多 3 个真实交集入口，如 `其中 2 条也在「日本旅行」`；点开进入主题页。主题详情则显示该主题成员实际使用过的最多 3 个用户 #标签及对应条数；点 #标签进入标签范围。交集计数只由当前有效关系与逐条用户认可标签计算，不能把“同名”当成关联，也不能把 AI 关键词当 #标签。没有交集就不显示提示，不讲空泛的概念课。

### 3.4 新主题发现

当至少 3 条独立、确有共同方向的想法构成候选，且其中至少有跨日记录时，提供**一条**情境式建议：名称、成员数、两条可点开的代表原文、`建立主题` / `忽略`。建议可出现在主题分组顶部，并可在用户浏览相关原文时出现一次；无证据、短句或同一天重复粘贴不硬凑。建立前不是正式侧栏主题，建立后原子写入这些想法的用户接受关系，后续相关新想法才进入自动归类。忽略和拒绝有冷却/墓碑，不反复骚扰。

### 3.5 状态、可达性与视觉

复用 Holo 的颜色、字级、间距、圆角和图标 token；主题来源字样是主要区分，颜色只是辅助。正常、空、加载、无网络、未授权、服务受限、预算暂停、已拒绝、刚收到新关联都要有确定文案。44pt 命中区，动态字体下允许两行，VoiceOver 按“主题、名称、AI 归入/手动加入、可查看”朗读。减少动态效果下仍保留内容回执，不依赖位移动画表达成功。侧栏纵向滚动、标签树横向手势及卡片滑动继续遵守 2026-09-26 手势修复规则。

## 4. 数据契约：一个事实源，所有表面同口径

### 4.1 身份与有效性

`Thought` 是不可被 AI 改写的原文。`ThoughtTagAssignment` 是逐条标签关系的事实：`manual`、`inline`、`confirmedAI` 属用户认可；纯 `ai` 和 `rejectedAI` 不得进“我的 #标签”。`ThoughtTopicLink` 是想法—主题关系的唯一产品事实；有效 UI 投影按 `(thoughtId, topicId)` 裁决，先过滤已删/归档对象与无效正文版本，再按用户决定、拒绝墓碑、AI、历史来源的优先级取状态。AI 的 `weakVisible` 只对通过校准的 high 结果显示；`internalOnly`、medium、shadow 不进入卡片/侧栏/主题页。用户手动关联和接受建议优先于 AI；手动拒绝必须同步并压制同版本复活。

`TopicRepository` 应提供统一查询：`effectiveTopics(for:)`、`effectiveThoughts(in:)`、`effectiveCount(in:)`、`membershipSource(...)`。卡片、侧栏、详情、搜索、建议、AI 召回与数量一律消费该投影；查询不得一处读 `Thought.topics`、一处读 link。旧 `Thought.topics` 可在兼容期作为**可重建镜像**与 link 同一 Core Data 事务维护，供旧 UI/回滚读路径使用；它不再拥有独立业务判断。迁移和对账须能报告差异为零，异常时保留原数据并关闭 AI 可见写入。

### 4.2 改变关系的原子命令

- AI 归入既有主题：只有 high、未拒绝、正文 hash/授权代数/模型与校准版本都仍有效时，原子写 link + 兼容镜像 + topicRevision；保存成功后发带 thoughtId/topicId/source 的刷新事件。事务失败则三处均不变。
- “为什么归在这里”的 quote/range 来自脱敏请求时，必须有可验证的区间映射并重新对照当前原文；映射不可靠就只显示可回源的整条想法，不把脱敏文本偏移直接用于原文高亮。
- 用户更改/移除：写 `userManual` 或 rejected 墓碑；同屏卡片、主题数量和详情在一次提交后刷新；后台旧结果不得回写。
- 接受新主题建议：创建 Topic、关联被展示且仍有效的成员、记住用户接受、移除候选建议，作为一个原子操作；并发/双设备下按稳定候选指纹和主题归一化名幂等，冲突不制造两个同名主题。
- 编辑或软删想法：旧 AI link 按 `basisTextHash` 失效，主题成员数与摘要 revision 同步更新；恢复时重新评估。**不要清除用户手动主题决定**，除非用户明确移除或主题被删除。
- 主题改名/合并/删除：仅操作 Topic 与它的关系，不按名称前缀改用户 `ThoughtTag` 或正文内 `#标签`。存量 `主题/子标签` AI 路径保留为内部历史兼容，先做迁移报告，不盲目批量改名；删除侧、恢复侧、读路径遵守数据沙箱隔离红线。

### 4.3 标签范围口径

侧栏节点出现、点入结果、计数、搜索命中解释均以**该想法自身**的 `manual/inline/confirmedAI` assignment 为准；同名标签实体上别人的纯 `ai` assignment 不得搭车出现。路径比较用完整规范化路径，点父路径包含其全部子路径；`工作/想法` 和 `生活/想法` 不能因叶段同名混合。无 assignment 的历史关系需先分类迁移或给显式 `legacyUnknown` 策略；不能为了“兼容”把所有纯 AI 关系当用户标签。

## 5. AI 归类执行契约

### 5.1 保存与后台处理

```text
保存 Thought 成功
  → 本机变更队列记录正文版本
  → 上传前验证授权、删除态、正文版本与预算
  → 最小必要内容脱敏并生成/读取 embedding
  → 独立 relate 任务检索现有主题候选
  → 后端返回离散关系 + 原文证据
  → 客户端校验 ref、quote、UTF-16 区间和当前版本
  → 校准规则决定 high / medium / low
  → high 原子提交有效 link，局部刷新 UI
```

“embed 已存在”只能跳过重新生成向量，**不能跳过 relate**。新增独立 relate 工作项，幂等键至少包含 `(thoughtId, contentHash, engineVersion, topicCatalogRevision, consentGeneration)`；触发来源覆盖新建、正文实质编辑、旧向量首次开启 relation、主题新增/合并/更名、校准版本升级、授权恢复、CloudKit 远端合并。先最近/打开过/已有主题的想法，分批补跑并支持暂停、恢复和失败重试。不要因 AI 自己写入 link 就无限递增目录版本、循环重评估；只对有意义的主题目录变更触发受控重评。

候选召回不得直接落关系。无成员的空主题可以用名称作**建议候选**，但不能仅凭标题自动归入；首条成员由用户手动放入或接受建议建立后，才参与高可信自动归类。候选不超过 3 个；模型不返回自报置信度，校准层根据独立检索信号和逐字证据判定。high 自动弱关联，medium 仅内部候选，low/无证据为空结果。不得把所有想法强制塞入现有分类主题。

### 5.2 校准、质量与覆盖

先冻结至少 120 条去标识化、经人工标注的真实场景样本，另留一组从未参与调参的最终留出集。样本必须包括：主题相近但不是同一方向、跨主题、多标签无主题、同名标签/主题、反讽或观点转变、短句、图片占主、跨日重复、编辑/删除、已有用户拒绝。报告每种场景的 TP/FP/FN，而不是只报整体准确率。正式 `ThoughtSemanticCalibration.json` 必须带 modelVersion、校准版本、样本集身份和结果记录；文件存在本身不等于校准通过。

可见自动归类发布门：high tier 精确率 **≥95%**、严重误归 **0**；在人工标注“确属某既有主题、且正文足以判断”的样本中，召回率目标 **≥60%**，否则“显著生效”尚不成立。若质量与召回不能同时过门，继续 shadow 与改候选/证据链，不降阈值硬出结果。真实模型的端到端测试要证明：至少一个已有主题的新想法在后台归入后，卡片、侧栏数和主题详情一致；已有向量补跑也能得到同样结果。

### 5.3 隐私、预算与实际可用性

客户端在**上传前**核验授权，不只在 embedding 返回后核验；撤回授权时取消任务、作废代数，迟到返回不落库。后端 `thought_embedding` 的“旧整理已审核”假设已不适用于 V3 默认停 V2 的路径；GLM 必须明确补上该 purpose 的内容审核和供应商隐私闸门，并检查日志、trace、缓存、审核副本、重试和上游留存。未经核实的真实供应商路由保持关闭；mock 只验证协议。`semantic-relate` 的隐私闸门、限流和预算保持有效，不能为了演示绕过。

分别实测单条日常处理、历史补跑、主题命名/摘要的 token、金额、P50/P95 延迟、失败和重试。目标是日常单条 AI 主题归类总成本在**几分钱以内**，以实测 p95 与预算阈值给结论；后台补跑另设按日上限和网络/电量条件，不能一次性上传历史。网络失败/配额耗尽只影响后台归类，不影响记录、手工标签、手工主题和字面搜索。

## 6. 分阶段实施与决策门

### P0：把“已归入”做成真实一致的结果

1. 先做只读审计：当前构建、Debug/Release、所有 flag、授权、校准文件、后端路由/Prompt/隐私闸门的实际状态；列出当前卡片、侧栏、详情与旧关系/link 的真实读写路径。用内存库构造“link 有、old relation 无”和相反两种差异，复现错位。
2. 建立统一有效关系投影与原子命令；迁移旧关系，记录无法判定来源为 `legacyUnknown`，不得伪装用户手动。新路径的手动加入和 AI 关联按 0–N 主题执行，移除旧 `classification` 单选清空其他主题的副作用；V2 `applyClassification` 只留在明确的旧版兼容边界。对账卡片/数量/列表/详情/AI 候选，差异必须为零。
3. 给已有向量增加独立 relate 工作队列与补跑，解决开关开启后历史不动的问题；先在 shadow 走通结果、失败、重试和成本。
4. 修正上传前授权与后端 embedding 审核/隐私闸门。后端代码如有修改，**需要单独发版**；没有东林对生产发布的明确授权前只做本地、测试环境和可复核发布包。

**P0 完成门：** 不开启视觉新样式，也能用测试数据证明 high link 写入后四处一致、拒绝不复活、旧向量补跑生效、撤回授权零新外发、软删不泄漏。真机/生产仍分层标注。

### P1：让用户一眼知道标签与主题的不同

1. 侧栏标签/主题来源与数量、想法卡片双行、主题轻点导航、纠错菜单、详情首尾记录/证据/时间跨度按第 3 节实现。优先复用已有侧栏和 `TopicDetailView`，不再造第二主首页。
2. 把新主题建议与正式主题分开；建议只在达到门槛且有可点原文时出现，用户确认后原子建立。无建议不占位。
3. 标签名称、列表、计数改用逐条认可来源；主题改名/合并/删除停止改写用户标签。给已有同名和历史 AI 标签做保守迁移与回滚验证。
4. 主题归入成功给一次短暂内容回执；失败、无结果、暂停按真实状态呈现，不用永远“AI 正在整理”。

**P1 完成门：** 不看说明书，用户能在测试旅程中回答“这条的 #标签是谁写的、主题是谁归的、点进去有什么、错了怎么改”；能从真实交集理解“同一想法既可有 #标签也可属主题”。同名对象和 0/1/多主题情况均无误导。东林真机检查首屏、长标签树、卡片手势、动态字体、深色与 VoiceOver。

### P2：真实模型评测、灰度与回退

1. 冻结样本并校准，先内部 shadow，再小比例 `relation=on`，达到 §5.2 质量及覆盖门才扩大。把“新 UI 可见”和“AI 归类可用”拆成独立能力状态；Release 默认关闭不等于已上线。
2. 在经授权的真机测试账号跑自然旅程：现有主题自动归入、无主题建议、手工纠错、编辑后失效、离线恢复、双设备同步与拒绝墓碑。至少 20 次侧栏/卡片/主题往返和后台补跑后无错位、误触、闪退。
3. 核对生产后端 release、路由 env、`/v1/prompts/meta` 的 source/version/digest、真实 provider 和最小真实请求；后端改动须完成授权发布与发布后核验。未发布时不得报告“AI 主题归类已在生产生效”。
4. 回退演练：关 relation 停新自动关联，保留用户已确认关系与原文/#标签；关新 UI 返回旧导航；后台候选/向量可重建。已展示的 AI 关系如何保留或隐藏须由版本化投影规则决定，不得仅靠关 flag 留下半套 UI。

**P2 完成门：** 真实模型质量报告、真机自然旅程、CloudKit 双设备、成本、隐私/供应商证据、后端发布身份和回退演练均有独立结果。任一缺项标“未验证”，不进入 Release 放量。

## 8. 必测验收矩阵

| 场景 | 预期 |
|---|---|
| 新建有证据且匹配已有主题的想法 | 保存立即成功；后台自动归入；卡片、侧栏数、详情成员及回顾一致。 |
| 已有 embedding，随后开启 relation 或升级校准 | 不重做向量也能补跑 relate；有结果则同样归入。 |
| 一个想法涉及两个长期方向 | 两条有效 Topic link 可共存；卡片最多展示 2 个，详情能看全部。 |
| 想法有 `#旅行/日本`，主题也叫“日本旅行” | 两者仍独立；AI 归主题不自动给想法添加/修改 #标签。 |
| 标签范围与主题范围存在部分交集 | 标签页和主题页互相给出真实交集条数与可点击入口；不把两集合当成相同，也不漏掉未打标签而被归入主题的想法。 |
| 同名标签有 manual 与纯 AI assignment | “我的 #标签”只返回逐条获认可的想法；数量和列表一致。 |
| 用户移除错误主题，AI 旧任务晚到 | 拒绝立即生效；同版本不复活；另一设备合并后也不复活。 |
| 编辑、软删、恢复、永久删除 | 旧 AI 关系按正文版本失效，归档/回收站不计入活跃主题；恢复按策略重评，手动决定保留。 |
| 改名/合并/删除主题 | 用户标签文字、行内 # 和其他主题不被连带改写；关系与计数原子更新。 |
| 主题无成员 / 只有一条 / 多条跨日 | 空主题留管理页；单条不编造变化；多条可从最早/最近回原文。 |
| 无相关主题、短句、图片为主、语义含糊 | 合法空结果；不强制归类、不假称已整理。 |
| 离线、429、预算耗尽、服务隐私闸门关闭 | 想法照常保存；后台停/重试状态准确，不在用户界面伪装“AI 已归入”。 |
| 授权撤回或保存后立即编辑 | 上传前阻断/迟到返回不落库；不泄漏旧正文对应结果。 |
| 新主题建议被接受/忽略 | 接受后只建立一个正式主题且有真实成员；忽略后不重复骚扰。 |
| 旧导航回退与双设备 CloudKit | 手工标签、用户决定、拒绝墓碑和原文不丢；旧/新 UI 的主题数量不矛盾。 |

## 9. 交付格式

GLM 每阶段交付一张结果表：**产品旅程现象 → 修改文件与 commit（若获授权提交）→ 数据不变量证据 → 单测/模拟器/真机/双设备/真实模型/后端/生产各自状态 → 精确率与召回率 → 单次、后台、摘要成本 → 隐私与发布身份 → 未通过项 → 回退结果**。用真实 thoughtId/topicId 做测试时只在本机安全日志记录去标识化 ID，不把用户原文复制到普通日志或文档。任何还没执行的项明确写“未验证”。
