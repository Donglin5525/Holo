# 待整理 104 条长期不下降：诊断与修复

## 产品结论

不是漏开一个设置。已确认的客户端缺陷是：已有类别理解时，整理成功记录的版本与再次入队查询的版本不一致，成功的笔记会被当成未处理，再次进入队列。截图中「104 条已索引」「7 个主题已代写」「最近整理 19 秒前」与这个缺陷的触发条件吻合；「92 条已归类」也说明并非完全没有整理成果。

本轮无法读取手机明细：CoreDevice 列表显示 iPhone 17 Pro 为 unavailable。因此，已确认代码缺陷及其可复现性，尚未确认手机这 104 条的逐条状态，也未完成手机恢复验收。

## 根因与复现

1. `ThoughtSemanticChangeFeed.enqueueRelateIfNeeded` 用 `ThoughtTopicVerifier.evaluationVersion(context:)` 生成目录版本，交给 `hasRelationRecord` 判断是否处理过。
2. 原 `ThoughtTopicVerifier.evaluate` 在同一目录版本后额外拼上 `:brief=<全部类别理解版本键>`，将完整版本写入 `relation_candidate.engine_version`。
3. 原 `hasRelationRecord` 对版本做精确相等比较，却没有补上 brief 版本。只要本机至少有一份 brief，检查就无法命中已有成功记录；有关系和 `no_match` 空结果均受影响。
4. Core Data 保存、全量核对、App 再启动等路径会再次核对，成功笔记因此反复排队、调用模型，既维持待整理数量，也占用后台预算。

standalone 使用真实 `ThoughtSemanticStore` SQLite 实现、7 份合成类别理解与 104 条完成回执复现：修复前第一次检查将 **104/104** 条误判为需要重跑（断言失败，退出 133）。这些是合成测试数据，不是手机数据库。

## 本轮修复

- 在 `ThoughtSemanticStore.relationEvaluationVersion(catalogVersion:)` 统一拼接完整版本；入队去重查询与执行器写入使用同一实现。
- 保留既有版本字符串格式，直接识别历史成功回执，无需改正文、清空索引或迁移 CloudKit。
- 读取类别版本失败时由现有队列重试，不再吞掉错误后写入一个不完整版本。
- 正文、目录或类别理解版本变化仍触发重评，14 天过期语义保持原规则。

修复后 standalone 全部通过：104 条记录连续三轮检查均为已处理；正文、目录、类别理解版本变化仍判定需要重评。补充 `ThoughtSemanticSafetyTests.testCategoryBriefEvaluationReceiptPreventsRequeue` 覆盖原生测试路径。

- 线上当前模型为 `qwen3.7-flash`。从运行容器白名单读取到：整理模块单独日金额上限为 0（该模块不限额）；统一后台预算仍为每主体 **0.30 元/天、2 元/月**，全站 3 元/天、60 元/月。两层规则同时生效，因此「整理模块不限额」不代表统一后台预算被关闭。
- 预算按调用前保守预留判断，未到 0.30 元也可能因为下一次预留超过余额被拦截。应先消除重复调用，再根据正常回填量评估额度，不能先靠放大额度掩盖循环。
- `ThoughtSemanticRetryPolicy` 尚未单独识别 `BACKGROUND_BUDGET_EXCEEDED`，目前走普通 429 的 60 秒重试，提示也落入通用网络文案。这是待补齐的错误码契约，不是本次版本统一修复的覆盖范围。
- 类别理解今天另有 1 次引用校验失败、42 次 429。该路径包含失败冷却，不能把这些 429 全部当成费用耗尽。

## 恢复后的验收

1. 安装经过验收且包含本次客户端修复的包，记录包身份。
2. 先只读备份手机语义库，核对当前正文、完整版本、任务状态和回执命中情况。
3. 让现有队列按正常入口继续，成功的笔记不得再被原样排入；剩余项按真实校验失败、额度等待和内容暂缓分别核验。
4. 观察同一批笔记至少两轮核对及一次重启：成功数量保留，待整理持续收敛，不以强制归类所有笔记或单纯改显示数字作为通过标准。
