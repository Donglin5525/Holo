# 想法模块五轮全方位体检清单

**日期：** 2026-09-26
**背景：** 东林真机实报侧栏手势冲突与标签树掉帧后，要求「全方位体检 5 轮以上，每轮修上一轮排查出的问题」。
**规则：** 每轮覆盖一个面向 → 产出问题清单（P0 闪退级/手势级、P1 体验、P2 打磨）→ 当轮修复 P0/P1 → 回归 → 进下一轮。累计 3 个自然轮无 P0/P1 新发现即视为收敛，可提前结束。

## 2026-09-26 想法、#标签、主题关系复核

**后续整改执行稿：** [想法标签与AI主题归类显著生效整改方案-GLM.md](2026-09-26-想法标签与AI主题归类显著生效整改方案-GLM.md)。本清单记录手势与导航修复；AI 主题归类的读写一致性、用户可见反馈和发布门以该执行稿为准。

**产品结论：东林感受到的“主题和标签没区别”成立。** 想法是原始记录；`#标签` 是用户写下或确认的找回词，斜杠路径形成标签树；主题是把多条想法归到同一长期方向的集合。两者可以同名，但不是同一个对象，也不应因同名自动等价。当前侧栏点标签、点主题都只筛同一条内容流；新侧栏没有进入已有 `TopicDetailView` 的入口，主题卡片上的点击只弹“更改/移除”，因此主题的时间跨度、回顾和来源无法自然被用户看见。

**本轮已改：** 保持单一想法流，选中主题后显示“主题脉络”入口，进入现有主题详情；详情在两条以上想法时直接呈现最早与最近两条记录，并可回到原文。空的预设主题留在管理页，不再占据侧栏。标签仍是即时筛选，不增加另一套主页面。AI 摘要仍受语义索引和能力开关约束，缺结果时只展示真实记录，不伪造回顾。

**尚未收口的数据语义：** 旧 `classification` 主题在 `TopicRepository.assign` 中互斥，一条想法只能落入一个这类主题；历史/语义主题关系又允许重叠。`renameClassificationTopic`、`mergeClassificationTopics`、`deleteClassificationTopic` 会按主题标题前缀重命名标签路径，可能触及用户手动的同名 `#标签`。另外，侧栏标签名称按手动/正文/已确认来源筛选，但 `fetchThoughtsByUserTag` 按标签实体的所有想法关系取回，若同名词还有纯 AI 关联，范围内可能混入未获用户认可的想法。这与新界面“标签是用户表达，主题是集合”的契约冲突。后续应先用内存库和真实数据形态覆盖手动、正文、确认过的 AI、纯 AI、无来源记录的旧关系及跨设备合并，再拆开主题操作与用户标签变更，并统一标签名称、列表和数量的来源口径；在完成前，不能对用户承诺主题改名/删除绝不影响标签，也不能声称 `#标签` 范围只包含用户亲自标记的想法。此项为 P1 数据语义债，不计入本轮手势修复完成。

## 2026-09-26 13:11 录屏复核与方案修订

**产品结论：原清单不能作为“标签树已修好”的验收结论。** 原有 G0–G6 主要覆盖侧栏开关、卡片操作和编辑器弹层；没有覆盖标签是否容易找到、深层标签是否可点、长列表滚动的安全区，以及隐藏退出手势与卡片收起的竞争。R2 将性能项判为“等真机证据”是合理的，但真机录屏现已提供新的可见证据，应重新进入修复与验收。

R3 用静态截图像素值否定“顶部亮带”，只能说明那张截图的亮色来自系统时钟；本次录屏可见**滚动中的主题文字进入状态栏区域**，这是另一项真实布局缺陷，原来的“未再复现”结论不适用于滚动状态。

| 录屏/代码证据 | 用户影响 | 修订 |
|---|---|---|
| 录屏约 3–7 秒：侧栏先铺满主题，`我的 #标签` 要滚过约十个主题才能看到 | 高频标签入口埋在长列表下，打开侧栏后无法直接找标签 | 顶部固定 `#标签 / 主题` 切换，默认展示标签树；置顶保留在当前列表顶部，归档保留在底部 |
| 录屏约 7 秒：侧栏滚动文字进入状态栏/灵动岛区域 | 内容叠在系统状态上，可读性和完成度明显受损 | 固定标题、全部想法和分组切换；只让中间列表滚动并裁切在其区域内 |
| 录屏约 9–11 秒：侧栏收起后状态栏上方仍残留滚动过的文字 | 侧栏关闭并不等于内容不绘制，用户看到重影 | 关闭态侧栏同步隐藏显示、触摸和无障碍焦点；滚动区域裁切防内容越界 |
| `TagTreeNodeView` 每层既给子树加 22pt，又在行内再加 22pt | 深层标签缩进递增过快，文字和点击区被挤出侧栏 | 每行按深度计算一次缩进，三层后限幅；展开箭头扩大到 44pt |
| 原方案左缘右滑打开侧栏、中部右滑退出模块，同时卡片右滑用于收起操作层 | 同一方向被拆成三种含义，用户必须记起手位置，且 window 手势与卡片竞争 | 左缘右滑恢复为全 App 一致的返回 Holo；侧栏由顶部菜单/标题打开；中部右滑不退出模块，留给卡片操作 |
| 侧栏关闭拖动原先只挂在右侧露出的内容层，且未判断纵横方向 | 从标签树内向左滑无效；纵向滚动的横向抖动可能让侧栏跟着晃 | 侧栏全区域用项目既有 `HorizontalGestureLock` 判断向左横滑；纵向滚动继续由列表处理 |

**调整后的验收口径：** 进入侧栏立即看见标签入口；点箭头只展开/收起，点标签名进入含子标签的范围；切换主题后再切回标签无需重滚；快速上下滚动时状态栏无文字穿透、侧栏不晃；从标签树内向左滑可关闭；卡片左滑露操作、右滑收起时模块不退出；侧栏关闭时不露出卡片操作。代码构建、模拟器门禁、真机手感与帧率分别记录，任何一项不能代替另一项。

**本次验证记录：** Debug 模拟器构建通过；在单独创建、只含项目自带虚构数据的 iPhone 17 Pro 模拟器上，G0–G8 九条手势门禁全部通过。最后追加“关闭态侧栏隐藏”后，重新构建并单独回归 G1/G7/G8，三条均通过。最初在无想法数据的 QA 模拟器上，G3 因没有可滑动卡片失败；已给 G3 增加前置卡片断言，并在有虚构卡片的隔离模拟器重跑通过。录屏定位了标签入口埋没及状态栏穿透；本轮尚未做真机跟手、掉帧、深色模式动态字体及双设备验收，不能写成“真机已修好”。

以下 R0–R5 保留为 GLM 当时的执行记录，其中“七条门禁全绿”和“待真机验收”的状态只代表修订前版本，不再代表本次修订后的验收状态。

## R1 手势与交互冲突面（2026-09-26 完成主链，门禁 6/6 绿）

**排障实录（重要，上会话结论已被推翻）**：G2 门禁连续失败曾定性为「侧栏关闭瞬间门控翻 true，同一次触摸带出归档按钮」。本轮以三路证据（沙盒门控日志、XCUITest 录屏抽帧、失败断言 xcresult）交叉复核，证明该假设不成立——拖关全程门控稳定 false、pan 手势零启动。真凶两个：

1. **AX 幽灵按钮（G2）**：SwipeActionView 操作层闭合态 opacity(0)+禁触摸，但元素常驻无障碍树；iOS 26 的 XCUITest automation 树里 `exists`+`isHittable` 双真（`accessibilityHidden` 对 automation 树无效，对 VoiceOver 有效）。7 张卡的归档/删除幽灵同时是 VoiceOver 可聚焦看不见按钮的产品缺陷。
2. **手势互斥缺委托（G4，真 bug）**：MiddleSwipeBackModifier 与 SwipeActionView 同款 window pan 挂载，但漏实现 `shouldRecognizeSimultaneouslyWith` → 与 ScrollView 内建 pan 互斥，滚动容器先开始即把它判死 → **中部右滑退出在列表页永不触发**（失败截图实证模块纹丝未动）。R0 模拟器冒烟假绿。

**修复（两项产品级 + 一项门禁判别通道）**：
- SwipeActionView 闭合态补 `.accessibilityHidden`（VoiceOver 修复）
- MiddleSwipeBackModifier.Coordinator 补 `shouldRecognizeSimultaneouslyWith → true`（根治退出失效）
- 门禁泄露判定弃用 label+isHittable（AX 遮挡语义不可靠），改用随露出翻转的 `swipe-archive-revealed` / `swipe-delete-revealed` 标识符
- 诊断日志（SwipeActionGateLog 全部 6 处）已移除；G2/G4 失败现场 dump+截图附件保留（仅失败时输出）
