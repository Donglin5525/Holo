## 1. 产品结论

### 1.1 一句话

> 用户只负责记录；Holo 在本地持续建立理解，在真正有价值的时刻把相关旧想法、长期主题和认知变化重新呈现给用户。

最终心智只有：

- **Thought｜想法**：用户原始记录，包含文字、图片、语音转写、主动 `#标签` 与主动引用。
- **Topic｜主题**：多条想法长期形成的认知线索，不是文件夹，不要求每条想法都归类。

### 1.2 成功标准

这次重构不是追求“AI 标签更多或更准”，而是同时实现：

1. 保存永不等待 AI，记录完成路径不增加任何步骤。
2. 正确结果静默产生价值；不确定结果不制造用户待办。
3. 无主题是正常状态，一条想法允许关联 0–N 个主题，UI 默认最多展示 2 个。
4. 用户能一秒移除或更改错误主题，且同一错误不会立即重现。
5. 主题页能说明“这些想法为何在一起、最近发生了什么变化、有哪些旧想法值得重看”。
6. 3 万、5 万乃至 10 万条数据仍能渐进索引、暂停恢复和快速检索。
7. Holo 不建立用户正文云端资料库；云端 AI 只处理本次最小请求，结果回到设备。

### 1.3 非目标

- 不做云端向量库、云端用户画像库或服务端长期记忆。
- 不追求 100% 分类覆盖率，不把“未归类”做成错误或进度负债。
- 不让用户维护 AI 词表、分类主题、置信度、待确认池或标签治理后台。
- 不在首版自动创建 Topic、自动合并 Topic、自动改用户命名或自动移动用户手动关系。
- 不在首版为纯图片想法调用视觉模型；纯图片合法保存但可暂不进入语义索引。
- 不承诺“供应商全链路零留存”，除非合同、配置与实测证据全部成立。

## 2. 对原对话方案的校准

| 原方向 | 结论 | 本方案调整 |
|---|---|---|
| 本地是记忆，云端是一次性算力 | 保留 | 原文、向量、关系、队列、游标和反馈都在设备；云端只收最小批次 |
| Thought + Topic 两个核心概念 | 保留 | 用户 `#标签` 作为表达能力保留，但不是第三层知识结构 |
| Embedding 只回答相似性 | 保留 | 向量只召回候选，永不直接决定用户可见关系 |
| 高置信自动归 Topic | 有条件保留 | 不能使用模型自报 confidence；必须经过向量候选 + 语义验证 + 本地策略 + 留出集校准 |
| 中等置信内部保留 | 保留 | 只参与搜索、聚类和后续证据累积，不显示、不待确认 |
| 新主题从多条想法长出来 | 保留 | 只生成一个情境式建议，用户确认后才创建 Topic |
| Optimistic AI | 收窄 | 可逆的既有 Topic 弱关联可乐观执行；创建、命名、合并和批量迁移需确认 |
| Topic centroid 两层召回 | 保留 | 加上通用本地 ANN，避免未归主题数据和跨主题搜索漏召回 |
| JSON + 全量 cosine 扩展到几万条 | 否决 | 改为独立本地语义索引；默认验证 HNSW，保留协议化 fallback |
| 云端用完即丢 | 作为强约束保留 | Holo 侧可编码保证；供应商侧必须单独核实，未核实则生产闸门关闭 |

### 2.1 为什么不继续 V2 可见自动标签

当前 V2 已把 0–2 个 AI 标签直接展示，并在第 3 条形成自动合集。这虽然减少了逐条确认，但仍让 AI 生产了一套用户需要看到、纠正、合并和治理的结构，与“用户只负责表达”冲突。

V3 的迁移规则是：

- `manual`、`inline`：继续作为用户标签展示和筛选。
- `confirmedAI`：视为用户曾明确接受的历史标签，保留可见，迁移标记为 `legacyAccepted`。
- `ai`：停止作为卡片标签和筛选入口展示，转为可重建的内部语义信号。
- `rejectedAI`：保留为反馈/抑制事实，不恢复展示。
- V2 自动合集：不再作为终局结构；满足条件的合集只能转成 Topic 候选，不能静默创建 Topic。

## 4. 最终用户体验

### 4.1 想法首页

```text
想法

[ 搜索你的想法… ]

[ 想法 ] [ 主题 ]

今天
────────────────────────
最近觉得自动打标签本身可能就是错的。
#Holo                         Holo 产品设计
────────────────────────
```

只保留：时间流、搜索、用户 `#标签` 筛选、Topic 筛选和新增。删除主路径中的：

- AI 自动整理进度、失败、配额和置信度；
- 未归类数量与待整理数量；
- AI 标签、AI 建议标签和标签治理；
- 低置信主题确认队列；
- 分类主题/启用分类；
- 批量 AI 整理和独立审批中心。

AI 故障不进入主页面。只有用户主动进入设置中的“设备智能索引”时，才看到概括状态，例如“最近内容已可用，历史内容仍在逐步整理”。

### 4.2 保存

保存完成即退出编辑器并显示“已记录”。同步流程只写 Thought、用户标签、引用和附件；不得同步等待 embedding、主题判断、摘要或搜索索引。

之后后台按序执行：

```text
本地变更事件
  → 队列去重
  → 生成/复用 embedding
  → 本地召回候选 Topic 与近邻 Thought
  → 必要时云端做一次受控语义判断
  → 本地校验与关系分层
  → 更新搜索、候选簇和 Topic centroid
```

### 4.3 已有 Topic 的关联

- 高可信：卡片底部弱展示 1–2 个 Topic；不弹窗。
- 中可信：只保留内部候选，参与搜索与证据累积；UI 无变化。
- 低可信：丢弃。
- 用户点击 Topic 可“更改主题”或“从这条移除”。更改后的用户决定优先级永久高于 AI。

### 4.4 新 Topic 建议

主题页顶部一次最多展示一张：

```text
✦ 最近有 5 条想法形成了新的脉络
「AI 产品体验」
5 条想法 · 持续 18 天
[建立主题] [改个名字] [以后再说]
```

- `建立主题`：创建 Topic，并把本次候选关系写成用户接受来源。
- `改个名字`：用户命名后创建，`titleSource=user`，以后 AI 不自动改名。
- `以后再说`：至少冷却 30 天，或候选簇新增 2 条有效想法后才可再出现。
- 二级操作 `不再建议这个方向`：保留本地拒绝 tombstone，除非用户主动恢复。

### 4.5 Topic 详情

首版至少包含：

1. 标题、图标、想法数、持续时间。
2. AI 摘要（明确标注是可重建摘要，不冒充用户结论）。
3. 反复出现的 2–4 个观点，均可跳到来源 Thought。
4. 时间脉络：按时间展示本主题想法。
5. 相关旧想法：默认最多 3 条，用户可展开。
6. 添加/移除想法、重命名、归档和删除。

AI 生成摘要失败时只隐藏摘要区，不影响 Topic 与想法列表。

## 5. 数据归属与隐私边界

### 5.1 数据放在哪里

| 数据 | 位置 | 是否进入 Holo 服务端持久化 |
|---|---|---|
| Thought 原文、用户标签、用户引用、Topic、用户确认关系 | Core Data + 用户私有 CloudKit（沿现有能力） | 否 |
| embedding、候选关系、候选簇、队列、局部搜索索引 | 本机独立语义库 | 否 |
| AI 自动关系的可同步事实 | `ThoughtTopicLink`，只存 ID、来源、状态、版本，不复制原文 | 否 |
| 单次 AI 请求正文与代表片段 | HoloBackend 内存态转发 | 否；日志/缓存必须剔除内容 |
| 模型结果 | 响应返回设备，服务端只保留无内容计量元数据 | 否 |

“Holo 不保存”不等于“任何第三方都不处理”。生产开启前必须核实模型供应商的缓存、审核、日志、训练和删除政策，并在用户说明中如实写接收者与处理边界。

### 5.2 最小发送原则

- embedding：单批最多 16 条；每条只发经脱敏、长度受限的正文文本。
- 已有 Topic 判断：1 条目标 Thought + 最多 3 个候选 Topic；每个 Topic 最多 3 条代表片段，单片段最多 240 UTF-16 单元。
- 新 Topic 命名：最多 8 条代表 Thought，不上传整个候选簇。
- Topic 摘要：最多 12 条代表 Thought；大 Topic 采用分层摘要，永不一次上传全部。
- 不上传图片二进制、附件元数据、全量标签目录、全量 Topic 目录、设备通讯录或其他模块数据。

### 5.3 授权、撤回与遗忘

引入单调递增 `consentGeneration`：每个任务和结果都记录发起时 generation。上传前与落库前各校验一次；用户撤回后：

1. 取消所有在途请求；旧 generation 返回结果全部丢弃。
2. 新任务不再上传，保存与本地关键词搜索继续可用。
3. 已存在的用户 Topic、手动关系和用户标签保持不变。
4. 提供“删除设备智能索引”，销毁 embedding、候选、簇、队列和 AI 派生缓存；不删除 Thought 原文。
5. 账户删除/清空数据必须调用同一销毁入口。

### 5.4 服务端不可绕过护栏

新增 purpose 必须加入 `adminLogStore.js` 的强制 `metadata_only` 集，白名单发生在序列化、截断、hot cache 和错误处理之前。请求/响应正文不得进入：

- SQLite 日志、任务库、快照、审核详情、错误 message；
- 内存 hot cache、重试队列、调试 dump；
- APM breadcrumb、代理访问日志或结构化 trace。

所有响应加 `Cache-Control: no-store`。Prompt 把 Thought 文本明确包在数据字段中，不执行其中指令、不调用工具，并使用严格 JSON schema。

## 6. 目标架构

```text

│ Core Data + Private CloudKit                                      │
│ Thought / Topic / UserHashtag / ThoughtTopicLink                  │
│                                                                    │

│                                                                    │
│ SemanticPipeline                                                   │
│ change feed → embedding → recall → verify → relation → discovery  │
└──────────────────────────────┬─────────────────────────────────────┘
                               │ 最小临时请求
                               ▼
┌──────────────────────── HoloBackend ──────────────────────────────┐

│ 鉴权、限流、预算、schema、moderation、metadata-only、no-store       │

                               ▼

```

核心不变量：

1. 云端没有用户级语义库，也不能通过 operationId 重建用户内容。
2. 向量只召回候选；可见关系必须通过第二信号与本地校验。
3. 用户决定不可被 AI 覆盖。
4. 所有派生数据可删、可重建、可按 modelVersion 隔离。
5. 编辑、删除、恢复、同步和授权变化全部进入同一个 change feed。

## 7. 数据模型

### 7.1 新增 `ThoughtTopicLink`（Core Data / Private CloudKit）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 稳定 ID；同一 thought/topic 组合采用确定性生成，防多设备重复 |
| `thought` / `topic` | relationship | 两端关系 |
| `source` | String | `user/manual`、`user/acceptedSuggestion`、`ai/v3`、`legacy/ai`、`legacy/unknown` |
| `state` | String | `active`、`rejected`、`superseded`；未生效 candidate 只留本机语义库 |
| `visibility` | String | `internal`、`weakVisible`、`userVisible` |
| `basisTextHash` | String? | AI 关系对应的正文版本；用户关系为空 |
| `engineVersion` | String? | 产生关系的引擎版本 |
| `decisionTier` | String? | `high/medium/low`，不是模型 confidence |
| `evidenceRange` | String? | 本地可解释范围；禁止复制整段原文 |
| `consentGeneration` | Int64 | 迟到结果与撤权守卫 |
| `createdAt/updatedAt` | Date | 生命周期 |
| `rejectedAt` | Date? | 用户移除/拒绝时间 |

优先级：`user manual/accepted > user rejected > ai active > legacy`。同一 pair 只能有一个有效投影；用户移除 AI 关系后写 rejected tombstone，不做物理删除。

### 7.2 扩展 `Topic`

新增：

- `titleSource`: `user/ai/legacy`；用户命名后不可被 AI 自动覆盖。
- `originClusterFingerprint`: 用排序后的代表 Thought ID + engineVersion 生成，辅助多设备去重。
- `summaryVersion`、`summaryBasisRevision`、`summaryUpdatedAt`。
- `topicRevision`: 标题、成员和用户决定变化时递增。

废弃语义：不再新写 `classification`；新代码只使用 `active/archived/merged`。旧 `candidate/classification/hidden` 在迁移层映射，字段先保留至少两个发布版本，不做 CloudKit 破坏性删列。

### 7.3 用户标签与内部语义分离

短期复用现有 `ThoughtTag`/`ThoughtTagAssignment`，但统一投影必须保证：

- UI 可见：`manual`、`inline`、`confirmedAI → legacyAccepted`。
- UI 不可见：新旧 `ai`、`rejectedAI`、内部 semantic concept。
- Topic 匹配可读取用户标签作为强本地信号，但 AI 不再创建可见 `ThoughtTag`。
- 新内部 concept 放入本机语义库，不再扩张 CloudKit 标签目录。

### 7.4 本机 `SemanticStore`

使用独立 SQLite 元数据库，文件放 `Application Support/ThoughtSemanticV3/`，不进入 Core Data/CloudKit。至少包含：

```text

              vector_key, state, priority, last_accessed_at, updated_at)
semantic_job(id, thought_id, content_hash, kind, priority, state,
             attempt_count, next_attempt_at, consent_generation, last_error_code)
topic_centroid(topic_id, model_version, vector_key, member_revision, weight_sum)
```

错误只存枚举 code，不存服务端 message 或正文片段。

## 8. 本地向量索引

### 8.1 技术选择

定义协议：

```swift
protocol LocalSemanticIndex {
    func upsert(id: UUID, vector: [Float], metadata: IndexMetadata) async throws
    func remove(id: UUID) async throws
    func search(vector: [Float], topK: Int, filter: IndexFilter?) async throws -> [Neighbor]
    func checkpoint() async throws
    func validate() async throws -> IndexHealth
    func destroy() async throws
}
```

默认路线：用固定版本的 **USearch Swift Package** 封装 HNSW 索引。其官方 Package 当前声明 iOS 15+，但这只说明接口兼容，不代表 Holo 已验证。Phase 0 必须先完成 arm64 真机、Simulator、Release archive、持久化重开、批量删除/更新、内存峰值、并发与损坏恢复 spike。

不直接采用当前仍为 0.x alpha、移动端集成边界较大的 sqlite-vec。若 USearch spike 未通过，使用 `Float16 + Accelerate` 分块扫描作为 fallback；fallback 也必须通过 5 万/10 万条门禁，未通过则 V3 不放量，不能回到 JSON + `[Double]`。

### 8.2 存储规则

- 向量统一 L2 normalize，以 Float16 保存；计算时转 Float32。
- 1024 维时原始向量约 2 KiB/条：5 万条约 98 MiB，10 万条约 195 MiB，另加索引开销。实际报告必须按真实 dimension、索引参数和设备测量。
- 索引文件用 `completeUntilFirstUserAuthentication`，只允许保存不可直接展示的向量与图结构；原文仍沿 Core Data 的保护策略。设置页明确显示占用空间并允许删除重建。
- 写入采用临时 generation + 原子切换；损坏时从 SQLite manifest 与 Core Data 重建，不因索引损坏删除任何用户数据。
- 编辑/删除采用 tombstone，空闲时 compact；compact 过程保留旧 generation，成功校验后再切换。

### 8.3 模型升级

`modelVersion + dimension + normalizationVersion` 共同定义索引代际。升级时：

1. 旧索引继续提供能力。
2. 新索引独立回填，不能清空旧索引后让产品长时间失能。
3. 最近/活跃数据达到可用阈值并通过抽样一致性后原子切换。
4. 切换后保留旧 generation 7 天供回滚，再由受控清理删除。

## 9. 新想法处理管线

### 9.1 统一事件源

以下动作都写入 `ThoughtSemanticChangeFeed`：创建、正文实质编辑、用户标签变化、Topic 手动关系变化、软删、恢复、永久删除、远端 CloudKit 合并、授权变化、模型版本变化。

事件必须以 `thoughtId + contentHash + changeRevision` 去重。不能依赖“遍历到第几条”的单一游标，因为优先级、编辑与同步会改变顺序。

### 9.2 步骤

1. **本地快照**：读取未删除 Thought；纯图片或无可分析文本合法完成为 `textUnavailable`。
2. **版本判定**：相同 contentHash/modelVersion 已完成则跳过。
3. **上传文本构造**：移除格式控制，按现有规则脱敏邮箱、手机号和长数字；用户 `#标签` 单独作为本地信号，不需要随正文目录上传。
4. **embedding**：加入最多 16 条的小批次；返回向量立刻落本机。
5. **候选召回**：查 Topic centroid Top 5 + 全局 Thought 近邻 Top 20；排除已拒绝 pair、删除/归档 Topic 和旧正文关系。
6. **是否需要云端验证**：没有候选或信号太弱则结束；候选明确时只发 Top 3 Topic 的最小上下文。
7. **协议校验**：operationId、textRevision、schema、枚举、quote/range 和候选 ref 白名单全部通过。
8. **本地决策**：计算 decisionTier；high 可弱展示，medium 仅内部，low 丢弃。
9. **原子落库**：再次校验 contentHash、consentGeneration、Topic revision、用户反馈与删除状态。
10. **派生更新**：更新 centroid、候选簇、搜索索引和无内容指标。

任何一步失败都不得回滚 Thought 保存，也不得切回旧 V2 可见自动标签通道。

## 10. 关系决策规则

### 10.1 不使用模型自报 confidence

模型只返回离散关系：`same_thread / related / none / insufficient` 与可核对证据。客户端根据独立信号决策：

- embedding 相似度与第一、第二候选 margin；
- verifier 离散结论；
- evidence 是否逐字存在；
- 用户标签/手动引用是否支持；
- Topic 内代表样本是否一致；
- 是否存在用户拒绝、相反关系或候选歧义；
- engine/model/正文/Topic revision 是否仍一致。

### 10.2 分层结果

| 层级 | 条件 | 动作 |
|---|---|---|
| `high` | verifier=`same_thread`、证据有效、检索阈值和 margin 均过线、无拒绝/歧义 | 写 `ai/v3 active + weakVisible` |
| `medium` | 有较强候选但缺一项独立条件，或 verifier=`related` | 写本机 candidate，仅参与搜索/聚类 |
| `low` | 证据不足、冲突、越界或 `none` | 不建立关系 |

数值阈值不得散落在代码里。Phase 0 可提供仅供 shadow 的种子配置，但生产配置必须由开发集校准后固化为带版本的 `ThoughtSemanticCalibration.json`；文件缺失或 modelVersion 不匹配时，自动可见关联强制关闭。

### 10.3 用户纠正

- “从这条移除”：pair 写 `user rejected`，AI 不得在相同正文版本重建。
- “更改主题”：旧 pair rejected，新 pair 写 `user manual active`。
- 用户手动添加 Topic：立即 active，不经过 AI。
- 正文大改后可重新评估旧 rejected pair，但默认仍抑制；只有用户主动清除反馈才恢复自动建议。
- AI 不自动移除用户关系，不自动把一个 Topic 合并到另一个 Topic。

## 11. Topic centroid 与主题发现

### 11.1 Topic centroid

- 只用当前 modelVersion、未删除 Thought 的有效 active link 计算。
- 用户手动/接受关系权重高于 AI 弱关系；内部 candidate 不进入正式 centroid。
- 成员新增、移除、编辑或恢复时增量更新；无法可靠做减法时按成员 revision 异步重算。
- 一个 Thought 可进入多个 Topic，但每个 Topic 独立维护 centroid；UI 仍只显示最相关 1–2 个。

### 11.2 候选簇

未进入已有 Topic 的向量进入本机增量候选簇：

1. 先找相邻 prototype；超过 shadow 校准阈值才加入。
2. 每簇保留 centroid、成员 ID、首末时间、凝聚度和代表样本，不保存第二份原文。
3. 代表样本取 medoid、最早、最新、边界样本，避免只看最相似的同义句。
4. 编辑/删除导致成员不足时自动降级或消失，不打扰用户。
5. 同一 Thought 可为最多 2 个候选簇提供证据，防止强迫单选。

### 11.3 产生建议的默认资格

以下是 shadow 初始规则，最终仍由留出集校准：

- 至少 4 个不同 Thought；
- 至少跨 2 个自然日且时间跨度不短于 48 小时；
- 凝聚度和最近邻纯度达标；
- 不与现有 Topic 构成高可信同一脉络；
- 不含被拒绝成员或已 dismissed fingerprint；
- 通过云端命名器的证据/边界校验。

达到资格只生成候选卡，不直接创建 Topic。候选标题最多 12 个中文字符，并附一句“为什么这些想法在一起”；标题和理由都必须能回溯到代表 Thought。

## 12. 搜索、重新遇见与 Topic 摘要

### 12.1 混合搜索

搜索在本地完成：现有文字匹配 + semantic Top K + Topic/用户标签关系 + 时间/归档过滤。排序使用稳定的 rank fusion，不把不同量纲的 BM25/substring 分数与 cosine 生硬相加。

- 输入防抖 250–350ms；旧查询任务可取消。
- 未完成向量索引的 Thought 仍可被普通文字搜索找到。
- 命中理由只展示“文字匹配/相关想法/同一主题”等用户语言，不展示 cosine。
- 搜索结果不得因 semantic index 损坏而为空，始终有文字搜索 fallback。

### 12.2 重新遇见

首版只做低打扰入口：Topic 详情中的“相关旧想法”和可选的每日看板卡片，不推送。候选必须满足：与当前 Topic/Thought 高相关、至少 30 天未打开、未删除/归档排除规则通过；同一 Thought 30 天内不重复推荐。

### 12.3 摘要更新

- Topic 达到 5 条才生成首个摘要。
- 成员 revision 变化且新增至少 3 条，或距上次摘要 14 天，才允许更新。
- 最多上传 12 条代表文本；大 Topic 采用本地代表性采样 + 旧摘要作为输入，不上传全量。
- 用户编辑过摘要后标 `titleSource/summarySource=user`，AI 不再覆盖。
- 摘要必须返回来源 Thought refs；refs 失效则对应表述不展示。

## 13. 大数据量与历史回填

### 13.1 不一次上传

30,000 条历史数据拆成可恢复任务。任何一次 embedding 请求最多 16 条；任何语义判断通常只看 1 条目标 + 1–9 条代表片段。服务器永远不接收“该用户全部想法”。

### 13.2 优先级

1. 最近 90 天。
2. 最近打开、搜索、编辑、引用过的历史 Thought。
3. 已属于活跃 Topic 的代表 Thought。
4. 其余冷数据，按时间分片渐进处理。

先达到“最近内容可用”，不等待全量完成。主 UI 不显示造成焦虑的全量百分比；设置页可显示最近数据是否就绪、待处理数量、占用空间和暂停原因。

### 13.3 调度与资源

- 前台空闲可小批执行；后台使用 `BGProcessingTask`，调度不保证到点。
- 默认只在 Wi‑Fi、非低电量、热状态正常时回填；用户新建/编辑永远优先于历史任务。
- 每轮最多处理 64 条，批间根据 429、热状态和耗时动态节流。
- 当前后端默认 20 请求/分、120 请求/日；按 16 条/批计算，30,000 条理论下限约 16 天。实施时改为按 token/条目计量的独立 backfill 预算，并以成本测算决定是否提高额度，不得静默挤占对话额度。
- 建议默认目标：首日完成最高优先级 500–1,000 条；之后在预算允许时约 2,000 条/日。它是产品目标，不是未测即承诺。

### 13.4 暂停恢复

每条任务持久化 `state/attemptCount/nextAttemptAt/contentHash/modelVersion`。App 被杀、断网、429、额度耗尽或模型升级后从任务事实恢复；不能从第 1 条重跑。永久协议错误进入终态并留无内容 code；网络错误指数退避。相同 operationId 的底层重试必须服务端幂等。

## 14. 全生命周期一致性

| 场景 | 必须行为 |
|---|---|
| 编辑正文 | 旧 AI link、embedding、candidate 和摘要证据按 hash 失效；用户 link 保留；新版本重新入队 |
| 软删 | 上传前取消任务；从索引、centroid、cluster 和召回结果隐藏，不立即破坏用户可恢复关系 |
| 恢复 | 原 hash 可复用向量，否则重新生成；恢复关系前重查 Topic 状态 |
| 永久删除 | 删除本机向量、任务和候选；Core Data 关系按现有删除规则处理 |
| 撤回授权 | generation 失效、取消在途、禁止新上传；用户数据和手动结构保留 |
| CloudKit 远端变更 | 进入同一 change feed；以对象 revision 处理，不另开旁路 |
| 模型升级 | 双 generation 构建与原子切换；旧索引保留 7 天回滚 |
| Topic 改名 | 只增加 topicRevision，不需重算 Thought embedding；摘要与 verifier 上下文失效 |
| Topic 合并 | 只允许用户确认；关系迁移幂等，保留 merged tombstone 防多设备复活 |

## 15. 多设备与 CloudKit

- 每台设备独立生成 embedding 和本机索引；不通过 CloudKit 同步 vector、ANN、queue、candidate cluster。
- Topic、用户标签、用户决定和正式 `ThoughtTopicLink` 走现有 Private CloudKit。
- `ThoughtTopicLink.id` 对 `thoughtId + topicId` 确定性生成，配合投影优先级去重，避免多设备重复 pair。
- 新 Topic 候选默认本机；用户接受后才同步 Topic。用 `originClusterFingerprint` 辅助识别重复候选，但不得仅凭标题自动合并。
- 双设备冲突规则：用户决定胜 AI；较新用户决定胜较旧用户决定；无法判定则保留两条候选并等待用户，不静默丢数据。
- CloudKit Production schema 未部署前 feature flag 必须关闭；Development 双设备同步至少完成一轮编辑、删除、合并和离线重连验证。

```text
thought_semantic_v3_index: off/shadow/on
thought_semantic_v3_relation: off/shadow/on
thought_semantic_v3_ui: off/on
thought_semantic_v3_discovery: off/shadow/on
thought_semantic_v3_resurfacing: off/on
```

开启顺序固定：index shadow → relation shadow → 内部评测 → relation 小流量 → 新 UI → discovery → resurfacing。不能先开 UI 再补索引。

回滚只切 flag：恢复旧 UI/旧读路径，保留 V3 实体和本机索引；不得回滚时删除用户新建 Topic 或手动关系。后端新端点可独立关闭，iOS 自动降级为文字搜索与手动 Topic，不回退到旧含内容日志通道。

## 20. 测试、评测与发布门禁

### 20.1 真实样本

建立至少 120 条去标识化真实样本：60 条开发集、60 条冻结留出集。覆盖短句、半句话、否定、状态变化、同义/相关但不同、多主题、用户 `#标签`、引用、编辑、纯图片、多语言、敏感数字和 prompt injection 文本。

每条人工标注：可关联的已有 Topic、不可关联 Topic、是否应为空、可形成的新主题簇、证据范围。原始样本不提交 Git；提交 schema、脱敏样例与聚合报告。

### 20.2 质量门禁

- 自动可见既有 Topic 关系 precision ≥95%。
- 明确越界/幻觉 = 0；用户拒绝 pair 重现 = 0。
- 新 Topic 建议簇 precision ≥90%；重复 Topic 建议 ≤5%。
- coverage 只监控，不设强迫下限；空结果是合法。
- 冻结留出集只在候选版本完成后跑，不得反复调参污染。
- pilot 7 日移除/更改率 ≤5%；若超过 10% 自动关闭 relation flag。

### 20.3 性能门禁

在最低支持设备、主流设备各测 5k/50k/100k：

- 保存同步路径新增耗时 p95 <20ms，且无网络等待。
- 50k warm semantic search p95 <150ms；100k <300ms。
- 50k cold open 首次查询 <800ms；主线程卡顿 >100ms 为 0。
- 索引 upsert p95 <100ms（后台）；内存峰值增量 <100MiB。
- 索引损坏可重建；杀进程 100 次不得丢用户数据或重复上传已完成版本。

达不到时先优化/替换索引，不降低质量阈值硬上线。

### 20.4 工程测试

- Core Data 轻量迁移、幂等回填、双写投影、CloudKit 合并。
- link 优先级、rejected tombstone、正文 hash、consentGeneration、Topic revision 竞态。
- ANN 与 flat topK 对照 recall；删除、更新、checkpoint、损坏恢复和 generation 切换。
- queue 的断网、429、超时、崩溃、跨天、预算、取消和 partial batch。
- 后端 schema、ref 白名单、quote UTF-16、prompt injection、metadata-only 哨兵、预算幂等。
- UI：保存不阻塞、无 AI 待办、关联纠正、建议冷却、无索引 fallback、动态字体和 VoiceOver。
- 全量 `xcodebuild test`、standalone 测试、后端新增测试与 `npm test`。报告必须区分新增套件、全量套件和未登记测试，`Executed 0 tests` 不算通过。

### 20.5 真机与生产门禁

1. 真机新建/编辑/删除/恢复/断网/锁屏/重启完整走查。
2. 两台设备 CloudKit 冲突与离线重连。
3. CloudKit Development schema 验证后部署 Production schema。
4. 后端部署并核对 release/status、prompts/meta、真实最小请求和日志无正文。
5. 供应商留存边界书面核实，隐私闸门才可设 true。
6. 真实账号小流量观察 7 天，再开启 discovery。

## 21. 指标、成本与可观测性

只记录无内容指标：索引覆盖分层、队列状态、请求次数/token/费用、各 decisionTier 数量、关系修改率、建议接受/改名/稍后率、搜索后打开率、旧想法重访率和索引健康。

北极星：**30 天内被重新使用或重新遇见的 Thought 比例**。辅助约束：记录过程整理操作次数接近 0。

模型成本按 purpose 分开计量。embedding、relation、name、summary 都有单任务/单日/回填预算；新功能不得占用聊天额度。先记录真实 token 和失败率，再定生产上限，不沿用旧 V2 的估算值冒充实测。

## 附录 A：首批验收 Use Cases

1. 新建普通文本 Thought：立即退出；数秒后可能出现已有 Topic，也可能保持无主题。
2. 明确跨两个主题的 Thought：允许关联两个；卡片最多显示两个。
3. 半句话或含糊内容：不强行归类、不弹确认。
4. 用户主动 `#碎碎念`：标签原样可筛选；AI 不创建同名可见标签。
5. 用户移除错误 Topic：当前正文版本不再出现；重启和另一设备同步后仍成立。
6. 编辑已关联 Thought 为完全不同内容：旧 AI 关系即时失效，用户手动关系保留。
7. 连续多日写同一方向：主题页只出现一张候选卡；接受/改名/稍后/不再建议均正确。
8. 断网写 20 条：全部保存；联网后按新内容优先渐进处理，不重复上传。
9. 30,000 条历史数据首次升级：最近内容先可用，杀 App 后继续，主页面无全量进度焦虑。
10. 撤回 AI 数据处理授权：在途结果不落库，新内容不上传；手动 Topic 和标签不消失。
11. 索引文件损坏：文字搜索和记录仍可用；语义库静默重建，无用户数据丢失。
12. 后端隐私闸门关闭：V3 静默降级，不调用旧 V2 内容通道。

## 附录 B：关键停损规则

- 留出集 precision <95%：自动可见关系不开，只保留 shadow/搜索候选。
- pilot 纠正率 >10%：服务端/本地 flag 自动回到 shadow。
- 50k/100k 性能不达标：不得用缩小支持数据量掩盖，回到索引选型阶段。
- 供应商留存未核实：生产隐私闸门保持关闭。
- CloudKit 迁移出现数据丢失/重复：停止新 UI 灰度，保留双写，先修投影。
- 成本超预算：降低历史回填速度或摘要频率，不降低隐私/质量门禁，不影响保存。
