## 一、北极星与设计准则

**北极星：用户接触萃取记忆的每一个瞬间——聊天、长廊、回放——都产生「它真的很懂我」的感觉。**

「懂我感」从哪来？四条体验准则，所有设计对照检查：

| 准则 | 含义 | 反模式（毁掉懂我感） |
|---|---|---|
| **具体 > 泛泛** | 「你上周说在控制外卖」才是懂；「我了解你的消费习惯」是客套 | 泛泛夸赞、模板化总结 |
| **成线 > 散点** | 把相关记忆连起来呈现：「你说过要控制外卖 + 这周账单确实降了」＝把你的话和你的行为对上了 | 一堆孤立条目像数据库转储 |
| **可核对 > 黑箱** | 每句理解有出处、可点开看、可纠正 | 无出处的断言；用户质疑时拿不出证据 |
| **克制 > 表演** | 只在相关时开口；说错比不说更伤懂我感 | 为引用而引用、高频刷存在感、被观察感 |

三条机制守则（怎么落地不越界）：
1. **能力发生时自带署名，不发公告**——感知挂在回答/回放/记忆本体上，不新增推送式提醒。
2. **署名要轻、可收起、可关**。
3. **召回与判定分层**（向量推荐 V1/V2 翻车教训）：关联只能用「便宜线索召回（同锚点/同主题/同时间窗）+ LLM 判定（宁缺毋滥、允许 0 条）」的范式，禁止文本相似直出。

## 二、地基盘点（全部代码核实过，本方案做「接线」不「重建」）

| 地基 | 现状 |
|---|---|
| 使用信号 | 模型回复末尾自报 `[[HOLO_MEMORY_IDS:]]`，客户端解析出真实使用清单（防伪造白名单）——署名/计数的数据源 |
| 来源指针 | 每条记忆带 evidenceRefs（sourceID 指向原始记录/原话）、锚点、血缘——跳转与分组的原料 |
| 锚点结构 | 每条记忆挂归一化锚点（habit:running / 财务分类 / 想法主题…）；**查询服务支持按锚点取数但调用全传空、注入时锚点被丢弃** |
| 显式关联 | 跨域融合产出 association/tension 记忆，记录 upstreamMemoryIDs（记忆→记忆连线）；每周最多 1 次、四道门，量极少 |
| 版本演化链 | supersedesMemoryID / predecessorVersionID + 用户纠正记录——「理解的更新史」原料 |
| 洞察设施 | 长廊 VM 的周/月/季加载、配额、精准打开全在；视图层 Hero 卡是死代码 |
| 详情路由 | transactionDetail / taskDetail / thoughtDetail / habitDetail / goalDetail 等 DeepLink 路由现成 |
| 注入链路 | 现为按单条分数排序的**平铺清单**，模型看不到任何结构 |

**一句话诊断：它一直在干活、存了理解一个人的全部原料，但从不开口、也从不把原料连成线。**

## 三、体验设计：三个时刻

### 时刻 1 对话：「它记得我说过的话」

用户问「这周外卖花得多吗」——

- 回答自然带出记忆：**「你之前提过想控制外卖支出，这周账单里它确实降了 20%」**（记忆注入块按主题分组渲染 + 指令「相关时自然口吻点到，无关不引用」）。
- 回答气泡下「引用了你 2 条记忆」可展开，**每条可点进记忆详情**，详情里证据行可点直达**原始账单/当时那句话**——具体到可核对。
- 新旧记忆若被跨域融合判定为张力（P2 起在记忆详情「相关记忆」区可见，注入侧矛盾追问随 P3 融合加强再做）。

### 时刻 2 长廊：「它对我的理解是一张网，而且在长」

打开长廊洞察 Tab——

- 记忆区从「按模块分堆的条目列表」升级为**「Holo 对你的理解」档案**：模块内按锚点聚簇（「关于跑步 · 3 条」「关于外卖支出 · 2 条」），每簇置顶一条主线理解，点开看支撑证据。
- 顶部是**接回的 AI 回放**（叫「洞察」的 Tab 终于有洞察）。
- 单条记忆详情升级为四块：内容与出处（证据行可跳）／**相关记忆**（同锚点兄弟 + 跨域连线）／**理解的更新**（「它曾以为 X → 你纠正后 → 现在理解为 Y」版本演化线）／**被使用**（「已帮你 7 次，最近一次 8月17日」）。

> 「理解的更新」是最能产生懂我感的组件：用户看见 Holo 的理解会因自己的纠正而改变——被听见、被记住、还会改。

### 时刻 3 回放：「它把我的话和我的行为对上了」

周回放详情尾部：「本期参考了你的 3 条记忆」——用户点开看到「你说过要控制外卖 × 本期支出趋势」这样话与行为对上的连线。质量档升级后，洞察正文直接说「结合你之前告诉我的…」。

## 四、工程分期

### P1 对话时刻 + 跳转闭环（纯客户端，一批可编译可提交）

**1.1 署名可核对**
`MemoryAttributionBadge` 展开列表按主题分组渲染（复用 1.2 的分组数据），每条可点 → sheet 弹 `HoloMemoryRecordDetailView`（复用现有详情，无需新路由）。

**1.2 记忆注入信封改造（落点已审查精确化）**
- **改的是 `render(_ summary:)`**（仅此重载有生产消费方：chat 用户上下文构建 `AIUserContextMessageBuilder:100` + 分析路径 `ChatViewModel:464`；`render(_ context:)` 无生产调用，不动）。
- **分组渲染**：`HoloMemorySummaryEntry` 增加可选 `anchorGroupLabel`（Codable 可选字段，双向兼容），由 `HoloMemorySummaryProvider.makeSummary` 从 `record.anchorRefs` 计算；锚点中文标签兜底链＝`anchor.displayLabel`（finance 信号已填分类名）→ 无则归入现有域级标题组（不硬造标签）。渲染按组加「关于 X：」行，**条目行格式逐字保留**（`[memory_id=…]` 结构不动）。
- **内容化指令**：marker 规则行**原文保留**（三处剥标记消费方依赖它），独立追加一行「记忆与当前问题真正相关时，回答中用自然口吻点到；无关时不得为引用而引用」。
- **矛盾标注移出 P1**（审查结论）：tension 数据被「每周一次+四道门+确认制」掐得极稀，summary 层也无矛盾数据可渲染，P1 做了几乎不可见。矛盾感知改到 P2 相关记忆区呈现 tension 连线，注入侧矛盾标注进 P3 随融合加强再做。
- 信封文本是客户端拼装，**无需后端发版**；marker 遵从度跑典型对话样本回归，不达标则单独收回内容化指令（1.2 各项互相独立可摘）。

**1.3 跳转闭环**
- 记忆详情「查看来源」证据行按类型分派：entityRef → 复用现有 DeepLink 详情路由；explicitUserStatement → 原话卡片 sheet（按 sourceID 取原文+时间）；aggregateSnapshot → 明示「一段时间的汇总」不可跳（如实展示口径，无死胡同）；洞察转存记忆 → 按 insightID 跳 `.memoryInsight`。
- 个人中心胶囊「新记住 N 件」（无待确认时）：从跳设置页改为跳长廊洞察 Tab 并定位高亮新记忆（DeepLinkTarget.memoryGallery 带 focus 参数，长廊 newMemoryIDs 高亮已有，补进入时定位）。
- 兜底：sourceID 对应数据已删 → 退化为现有 summary 展示。

**1.4 被使用计数（写入侧，路径已审查严格化）**
- `HoloMemoryRecord` 增加 `usageCount: Int?` / `lastUsedAt: Date?`——**必须可选型**（合成 Codable 自动 decodeIfPresent）。红线：写成非可选又不带自定义 init(from:)，旧数据解码 keyNotFound 会让 fetchRecord 抛错、**整库记忆读不出来**。
- 写入走 repository **新开专用方法** `recordUsage(ids:now:)`：withMutationLock + 单 background context + `stableID IN` 批量取 + 只改两字段重编码 recordData + 一次 save。**不 bump recordVersion/predecessorVersionID、不改 updatedAt（改了会污染萃取合并的 userControlIsNewer 判定）、不写 lastObservationKey、绝不走 upsert/applyObservationBatch**（会写 observationKey 并生成 observation run 行）、不触发 dirty registry（已核实 dirty 由业务信号 digest 驱动，与记忆写入无连线，零萃取调度副作用）。
- 触发点＝`ChatViewModel.consumeMemoryUsageMarker` 解析出 usedMemoryIDs 后 fire-and-forget。
- 已知代价（接受）：非敏感记忆在 CloudKit 同步范围，每次计数上行一条 recordData 覆盖；按答案批量+只重写 recordData 列（不动 evidence 行）把 churn 压到最低；多设备并发计数 last-writer-wins 丢增量可接受（展示文案不得暗示精确计数，用「参与过 N 次 AI 回答」）。

**1.5 目标规划标记泄漏修复（审查新发现的现有隐患，随 P1 顺手堵上）**
- 现状：目标规划追问链路（`ChatViewModel:2208/2269` → GoalPlanningCoordinator → 默认 completeGoalPlanning → chatStreaming(userContext) → `build(.chat)` 注入含 marker 规则的文本）返回的追问文本**直接 addMessage、不剥标记**——模型若照规则在末尾追加 `[[HOLO_MEMORY_IDS:]]`，原文会漏进聊天气泡。这是今天就存在的隐患，1.2 的内容化指令会放大其概率，必须同批修复。
- 修法：该路径输出套用现有 `HoloMemoryUsageMarker.parseAndStrip`（allowedMemoryIDs 取该次 userContext.memorySummary.sourceIDs），剥净后再 addMessage；顺手接入 1.4 计数。
- 同类排查：周计划/灵活查询规划在自定义 OpenAICompatible Provider 下有同款风险，但生产默认 HoloBackend 有 override 不注入——记录在案不在本期修。

### P2 长廊「理解档案」（纯客户端，可与 P1 分两批提交）

> 实施基线：长廊记忆区当前有**未提交**的确认队列改造（MemoryConfirmationQueueView/DomainMemorySection），P2 一律以工作区现状为基线叠加，不按 HEAD。

**2.1 记忆区锚点聚簇重构（DomainMemorySection）**
模块分组保持，组内按锚点聚簇：簇标题＝锚点语义标签（兜底链同 1.2），簇内置顶主线记忆（置信度/被使用次数优先），其余折叠一行「另有 N 条相关」。纯展示层，不新增 AI 调用。

**2.2 记忆详情四块升级（HoloMemoryRecordDetailView）**
- 相关记忆：同锚点兄弟（repository 按锚点取）+ upstreamMemoryIDs 双向连线；**tension 关联在此呈现**（「这两条被连起来了：张力/关联」）——矛盾感知从注入侧移到这里落地（审查修正）。
- 理解的更新：版本链时间线（旧版本结论 → 纠正/演化 → 当前结论，含用户纠正标记）。数据全有，纯渲染。
- 被使用：「参与过 N 次 AI 回放/回答，最近一次 X月X日」（文案不暗示精确）。
- 出处（P1 已建）：证据行可跳。

**2.3 AI 回放接回洞察 Tab**
洞察 Tab 顶部加轻量入口行（「AI 回放 · 最近一期标题 · 查看」），点开复用 `MemoryInsightHeroCard`（死代码复活）+ 现有 VM 设施；「去聊天继续问」已有 buildContinueInChatPrompt。消除「洞察 Tab 没有洞察」的名字陷阱。

**2.4 洞察反向引用**
- 停止档（纯客户端，随 P2 上）：洞察详情尾部「生成本期回放时参考了你的 N 条记忆」+ 列表——数据直接取 context.longTermMemoryIDs（就在洞察 context 里），零 prompt 改动零回归。红线：**洞察用的 renderBackground 绝不加 marker 式指令**（洞察 JSON 链路无剥离器，marker 进 JSON 字段会原样上卡片）。
- 质量档（需后端发版，随批走）：审查发现**客户端接收端已建好**（MemoryInsightPayload.usedMemoryIDs 可选字段 + longTermMemoryIDs 白名单过滤 + 回执记录，MemoryInsightService:264-278），只缺触发源——后端 memory_insight_generation prompt 的 JSON schema 加 usedMemoryIDs 字段+一句「确实使用记忆时在 usedMemoryIDs 里列出」。客户端零改动，成本大降。

**2.5 计数展示**
长廊记忆簇行尾 N>0 时「已帮你 N 次」；P2.2 详情展示最近使用时间。

### P3 供给侧与暂缓（明确不在本方案范围）

- **跨域融合加强**（需后端评估提频/放宽门）：当前每周 1 次处于饥饿状态；待 P1/P2 验证「关联呈现」的消费价值后再投入供给侧。
- **语义关联探索**：复用想法域两段式经验（embedding 只当第四候选源 + LLM 判定），等想法域 Gate（40 条标注 + 10pp）验证后再决策；禁止向量相似直出。
- **周计划对账时刻**：等 LifePlan 落地。
- **主动提醒带记忆口吻**：须频控设计，单独立项。
- **输入白名单放宽**（conversation/thought 关键词筛→语义判断）：供给侧质量，独立批次（纯客户端）。
- **萃取 prompt 放宽产出洞察**：不做，保持「稳定事实」定位，洞察归洞察链路。

## 五、懂我感守则（实现时的对照清单）

1. 引用必须具体到锚点/事件，禁止「我了解你」式空话进注入块与 UI 文案。
2. 引用频率护栏：内容化指令含「无关不引用」；署名行轻量可收起；不新增公告式提醒。
3. 矛盾呈现＝提问不是仲裁：模型/界面只说「可能矛盾」，判断权交用户（接确认队列）。
4. 记忆可能错：详情页「不准确/纠正」入口保持一级可达——**认错并修正反而是懂我感的加分项**。
5. 分组与邻居全部来自已存锚点/连线，**本方案不新增任何自动推断的关联**（推断类增强全押在 P3 的分层范式里）。

## 六、验收：用户剧本走查

以「跑步习惯 + 控制外卖」剧本贯穿三个时刻（真机自测脚本）：

1. **对话**：问「这周外卖花得多吗」→ 回答自然提到「你之前说想控制外卖」→ 气泡下署名展开分组列表 → 点任一条进详情 → 证据行直达原始账单/原话卡片 → 返回无损。
2. **矛盾（P2 走查）**：构造被融合连线的两条记忆 → 详情「相关记忆」区呈现张力/关联卡 → 确认后记忆状态更新、版本链多一节。
3. **长廊**：个人中心胶囊「新记住 N 件」→ 直达洞察 Tab 高亮新记忆；记忆区按「关于跑步/关于外卖支出」聚簇；详情四块（出处/相关/更新史/使用）齐全。
4. **回放**：洞察 Tab 顶部 AI 回放入口 → 周回放尾部「参考了 N 条记忆」→ 点击可看列表。
5. **计数**：时刻 1 对话后，对应记忆「已帮你 N 次」+1。
6. **边界**：已删记忆不回归现有「可能已被删除」文案；聚合类证据点开有口径说明；无记忆用户全链路无空壳；本方案不新增任何付费墙。

## 九、风险与红线（三轮审查新增）

**三条「不能出错」红线（违反即事故级）：**
1. **Codable 红线**：HoloMemoryRecord 新字段必须可选型——非可选会让旧数据整库解码失败（fetchRecord 抛 persistenceFailed）。
2. **marker 规则行红线**：render(_ summary:) 的 marker 规则原文保留，只追加不修改；三处剥标记消费方依赖其原文语义。
3. **renderBackground 红线**：洞察/年度回顾的注入不加任何 marker 式指令——洞察 JSON 链路无剥离器。

**既有风险（延续 v2）：**
- 被观察感：准则 2/3 全程约束；内容化指令独立可摘。
- 提示遵从度：marker 机制已验证遵从良好；1.2 各项独立，回归单项收回不影响其余。
- token 膨胀：分组只改呈现，条目数不变；不额外拉邻居（邻居扩展只在 P2 相关记忆区做）。
- CloudKit churn：计数写入按答案批量、只重写 recordData 列，代价已评估接受。
- 新旧双记忆模型遗留：计数/详情统一走现有 repository 路径，不新开分叉。
- 过度承诺：只呈现已存锚点/连线/版本链，不新增自动推断——推断增强全部后置 P3 分层范式。

**审查遗留观察项（记录在案，不在本期）：**
- 目标规划标记泄漏（1.5 修复）；周计划/灵活查询规划在自定义 Provider 下的同款风险。
- 洞察 prompt 加 usedMemoryIDs（P2.4 质量档，后端）。
- ChatViewModel 属多会话共用大文件，P1 改动收敛在 consumeMemoryUsageMarker 与目标规划两小段。
