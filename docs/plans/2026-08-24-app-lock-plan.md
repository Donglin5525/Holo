- 日期：2026-08-24
- 状态：已拍板并实施完成（2026-08-24 东林拍板：D1=方案 A 系统验证；D2=三档可选，默认 5 分钟；D3 遮罩随锁一并做）。编译绿 + 7/7 单测过，待真机验收（清单见 §8）
- 性质：**纯客户端（iOS）功能，无需后端发版**

## 1. 背景

Holo 里存的是用户最私密的数据：记账、想法、长期记忆、AI 对话。目前任何人拿到解锁状态的手机都能直接翻看。应用锁是这批数据的最后一道门。

现状摸底（2026-08-24）：

- 全源码搜索 `LocalAuthentication / LAContext / FaceID / appLock / passcode` 等关键词**零命中**，功能需从零新建。
- 已有 `KeychainService`（`Services/Security/KeychainService.swift`，存 AI API Key 用），可复用（仅方案 B 需要）。
- 工程权限描述走 pbxproj 的 `INFOPLIST_KEY_*`（已有相机/健康/麦克风四条），**没有** `NSFaceIDUsageDescription`，需照惯例补一条。
- App 入口 `HoloApp.swift` 已有 `scenePhase` 前后台监听（Agent 续跑在用），锁的触发可以搭同一班车，不需要新建生命周期监听。
- 设置页 `SettingsView.swift` 是自绘卡片分区 + 自定义开关行（`.tint(.holoPrimary)`），子设置页用 sheet 弹出，照抄惯例即可。

## 2. 两种「密码键盘」的本质区别（D1 的背景）

「密码键盘」有两种做法，差别很大，需要先拍板：

| | 方案 A：系统密码 | 方案 B：App 独立密码 |
|---|---|---|
| 用户输入的密码是 | 手机开机/解锁的那个密码 | 用户在 App 里自己单独设的密码 |
| 类比 | 用大门钥匙开卧室门 | 卧室另配一把新锁 |
| 密码存在哪 | 苹果系统管，App 碰不到 | App 自己存（Keychain + 哈希） |
| 忘记密码怎么办 | 不关我们的事（找 Apple） | **产品难题**：只能靠 FaceID 兜底，FaceID 也失败就只能清数据（类似 iPhone 备忘录忘了密码谁都救不了） |
| 谁知道密码能打开 | 知道手机密码的人（家人、帮你解锁的人） | 只有设密码的人 |
| 实现量 | 小（系统把验证界面、密码键盘、失败回退全包了） | 大（要自建：设密码流程、改密码、自绘数字键盘、防暴力尝试） |
| 业界惯例 | 银行类 App 多用这个 | 日记/私密笔记类（Day One、备忘录）用这个 |

iOS 系统验证的原生行为恰好就是需求描述的样子：**先弹 FaceID；FaceID 不可用或失败后，自动转成手机密码键盘**，两种方式一套代码全包。

## 3. 决策点

### D1 解锁方式（最关键）
- **A（推荐）：系统级验证**。开启后回 App 先弹 FaceID，FaceID 失败/不可用自动转手机密码键盘。实现小、体验原生、无忘记密码负担。
- B：App 独立数字密码（4 或 6 位），FaceID 作为快捷方式可选。隐私隔离更强（知道手机密码也打不开），但忘记密码是个产品死结，实现量也大。
- C：分期——v1 先上 A，v1.x 视反馈再补 B。

**推荐 A**。理由：Holo 的数据在本机 + iCloud，方案 B 的「忘记密码清数据」等于让用户拿隐私换密码安全，对记录型 App 代价太重；先上 A 能覆盖 90% 的「防他人翻看」诉求。

### D2 锁定时机
- **立即锁定（推荐 v1）**：退到后台（回主屏、切其他 App、锁屏）再回来，一律验证。规则最简单、最好解释。
- 三档可选（立即 / 离开 1 分钟 / 离开 5 分钟）：体验更宽松（短暂切走回来不用重验），实现只多一个时间戳判定，若东林在意「切出去回个微信就要重验」的打扰，v1 直接带上也不难。

### D3 后台快照遮罩
- **跟锁一起做（推荐）**：App 在后台时，多任务切换器（上滑停顿那一下）里只显示一片遮罩 + App 图标，看不到最后停留的页面。这是隐私锁的标配细节，实现量约 30 行。
- 不做：锁了 App 但切换器里还能瞄到内容，体验上自相矛盾。

## 4. 产品行为设计（以推荐方案 A 为基准）

### 4.1 设置入口

设置页新增「**隐私与安全**」分区（放在 iCloud 同步分区之后、法律与隐私之前），内含一行：

- **应用锁** Toggle。打开瞬间先做一次验证（相当于「试用一下再开启」）：
  - 验证通过 → 开关打开；
  - 用户取消验证 → 开关弹回关闭；
  - 设备既没设密码也没录 FaceID → 弹提示「设备未设置密码，无法开启应用锁」并弹回（避免开出一把谁都解不了的锁）。
- Toggle 下方副标题显示当前方式，如「使用面容 ID 或设备密码解锁」。

锁定时机若按 D2 带「立即 + 宽限」三档，在此分区内加一行「锁定时机」选择。

### 4.2 锁定触发

- 开启应用锁后：
  - **冷启动**（点图标打开）→ 必须验证；
  - **回前台**（切走再回来）→ 按锁定时机判定；
  - **锁层表现**：全屏遮罩，App 图标 + 「Holo 已锁定」+ 解锁按钮，深浅色模式都适配。
- 验证时机：回前台**自动弹一次** FaceID（最顺手）；用户取消或失败后，停在锁屏，显示「点击解锁」按钮，**绝不会取消验证就直接放行**（这是此类功能最常见的 bug，列入验收红线）。

### 4.3 解锁体验

- FaceID 验证成功 → 锁层淡出，回到离开时的页面（状态原样保留）。
- FaceID 连续失败/用户点「输入密码」→ 系统自动转手机密码键盘（系统 UI，无需自建）。
- 设备无 FaceID（老机型/未录入）→ 直接弹密码键盘，功能照常可用；设置页副标题相应显示「使用设备密码解锁」。

### 4.4 边界场景（设计时一次说清，避免实现时各写各的）

| 场景 | 行为 |
|---|---|
| 锁定状态点通知/Widget 深链进 App | 先解锁，解锁后正常跳到目标页（现有 DeepLinkState 挂起机制天然支持，验收必测） |
| 后台任务（Agent 续跑、洞察生成、各类提醒排程） | **完全不受影响**。锁是纯 UI 层，不挂任何业务暂停/恢复逻辑 |
| 锁屏期下拉通知中心/控制中心（App 变 inactive） | 不算离开、不锁定；只有真正回不到前台（background）才计入 |
| FaceID 权限首次调用 | 系统弹「允许 Holo 使用面容 ID 吗」授权框（文案见 §5.2） |
| 关闭应用锁 | 关 Toggle 即关，无需验证（开关本身在系统设置体系内已受设备保护） |

## 5. 技术设计

### 5.1 新增文件（4 个，预计 500–700 行）

| 文件 | 职责 |
|---|---|
| `Services/Security/AppLockSettings.swift` | 配置存取（开关、锁定时机），ObservableObject + UserDefaults，照 `MemoryInsightScheduleSettings` 惯例 |
| `Services/Security/AppLockManager.swift` | @MainActor 单例；`@Published isLocked` 状态机；scenePhase 驱动；包装 `LAContext.evaluatePolicy(.deviceOwnerAuthentication)`；开启前预检（设备是否设了密码） |
| `Views/Lock/AppLockOverlayView.swift` | 锁屏层（遮罩 + 图标 + 解锁按钮 + 后台快照遮罩复用同一层） |
| `Views/Settings/AppLockSettingsView.swift` | 若 D2 带时机选择则建子页 sheet；否则并入主设置页分区，此文件可省 |

### 5.2 改动点

| 位置 | 改动 |
|---|---|
| `project.pbxproj` | 加 `INFOPLIST_KEY_NSFaceIDUsageDescription`（照现有相机/麦克风四条的写法）。建议文案：「用于快速解锁 Holo，验证身份后即可查看你的数据」 |
| `HoloApp.swift` | `appRoot` 外层挂锁层；现有 `scenePhase` onChange 里加一行调 `AppLockManager`（退后台记时间/上遮罩，回前台判定锁定）。不新建生命周期监听 |
| `SettingsView.swift` | 新增「隐私与安全」分区（约 40 行，复用现有 settingsRow/toggle 惯例） |

项目用 PBXFileSystemSynchronizedRootGroup，新建 .swift 自动编译，无需登记 pbxproj（既有结论）。

### 5.3 关键实现细节（三个最容易翻车的点）

1. **冷启动防闪现**：`isLocked` 初始值必须在**首帧渲染前同步**从 UserDefaults 算出（开=锁）。绝不能先渲染业务页再异步上锁——那等于每次冷启动把最近页面闪给旁看的人。锁层用 ZStack overlay 常驻视图树（不用 fullScreenCover，它有呈现时序，首帧可能来不及）。
2. **后台快照遮罩**：SwiftUI 在 scenePhase 变 background 时仍会渲染一次，`background 或 locked 时显示遮罩层` 一个条件即可，遮罩与锁屏共用一个视图。
3. **失败不放行**：LAContext 回调里 `.cancel / .userFallback / 系统错误` 一律保持锁定，只有 `.success` 解锁；「解锁」按钮永远可点（重试验证）。

### 5.4 测试

- `AppLockManager` 状态机单测（宽限判定、冷启动初始态、各 LAError 分支保持锁定）：LAContext 本体不好 mock，只测纯状态机部分。
- 真机验收为主（见 §7），模拟器虽可模拟已录入 FaceID，但按现行规矩验收交东林真机复验。

## 6. 风险清单

| 风险 | 说明 | 对策 |
|---|---|---|
| FaceID 权限描述缺失 | 缺 `NSFaceIDUsageDescription` 时真机调 FaceID 系统直接杀 App | 列为动工第一项，写进验收前置检查 |
| 冷启动内容闪现 | 见 §5.3-1 | 锁层常驻 + 初始值同步读 |
| 验证取消后放行 | 见 §5.3-3 | 验收红线，单测覆盖状态机 |
| 深链与锁交互 | 锁定期进深链，解锁后应直达 | DeepLinkState 挂起机制天然兼容，验收必测项 |
| iOS 版本差异 | `.deviceOwnerAuthentication` 自 iOS 8 起稳定，无版本风险；FaceID 模拟依赖真机 | 无需处理 |
| 方案 B 特有：Keychain 卸载残留 | 卸载重装后 Keychain 里密码还在但开关被清，可能出现「锁状态错乱」或「数据无锁暴露」 | 仅 D1 选 B 时需专项设计（开关状态也入 Keychain），本方案 A 无此问题 |

## 8. 验收清单（真机）

1. 开启开关 → 立即弹一次验证；取消 → 开关弹回。
2. 设备未设密码 → 开启被拦并有明确提示。
3. 冷启动 → 首帧即锁屏，**无任何内容闪现**。
4. 切后台再回 → 自动弹 FaceID；取消后停在锁屏，点「解锁」可重试，**任何取消路径都不放行**。
5. FaceID 失败两次 → 自动转密码键盘，输手机密码解锁成功。
6. 锁定期点通知（如任务提醒）→ 解锁后直达对应页面。
7. 多任务切换器 → 只见遮罩不见内容。
8. 后台任务不受影响：锁屏状态下 Agent 任务/提醒排程照常跑。
9. 深浅色模式下锁屏样式正常；VoiceOver 可操作解锁按钮。

## 9. 若拍板方案 B（独立密码）的增量说明

在方案 A 基础上追加：

- **设置流程**：开启时先设 6 位数字密码（输两遍确认），之后可改；FaceID 开关独立可关（只留密码）。
- **存储**：密码加盐哈希（PBKDF2）存 Keychain，**开关状态一并存 Keychain**（防卸载重装后锁状态错乱，见 §6）。
- **忘记密码**：只能引导用户通过 FaceID 解锁后重设；两者都失守 = 数据无法在本机解锁（需在设置密码页明示，不可事后扯皮）。
- **防暴力尝试**：连续错 5 次递增冷却（1 分钟起步）。
- 自绘数字键盘（锁屏页 + 设置页复用），不引入第三方库。
