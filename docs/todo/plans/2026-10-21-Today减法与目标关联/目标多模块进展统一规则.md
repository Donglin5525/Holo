# 目标多模块进展统一规则

2026-10-21。待产品评审；本轮新增设计规则与对话内交互示例，没有改原生代码、数据模型、真实记录、Prompt 或后端。

本文修正此前原型把单一资金进度当成目标通用模板的问题。与同目录旧说明有差异时，以本文关于**进展语义与展示**的规则为准。10 月 20 日最终交接中原模块记录、目标与 HoloAI 共用报告、用户确认修正等边界继续有效；多项独立成果的数据契约是本轮新增待实施范围，不能视为旧代码已支持。

## 1. 产品结论

一个目标可以关联财务、多个习惯、任务、健康观测与反馈。**模块是数据来自哪里，角色才决定它算什么。** 关联三个模块不代表有三个可以平均的进度；关联三个习惯也不代表它们一定只是行动。

目标回答三个独立问题：

1. **想得到的结果到了哪里？** 可以是金额、累计量、若干共同条件、阶段交付或真实成果证据。
2. **为此约定的行动做了没有？** 按各自频率、时间窗口、实际记录分别呈现。
3. **投入与约定是否需要回顾？** 如预算、奶茶/宵夜上限、时间投入；不与成果做加减平均。

全局不生成「目标综合完成率」「生活改善得分」或跨模块加权百分比。结果、方法、约束可以同时出现不同状态，界面应如实保留这种差异。

## 2. 关联角色由本目标定义，不由对象类型写死

| 同一对象 | 在目标 A 的作用 | 在目标 B 的作用 | 应读取什么 |
|---|---|---|---|
| 跑步习惯 | 「月跑 40km」的成果来源 | 「规律作息」的一项方法 | 原始里程、有效记录日期；累计量与行动次数分别计算 |
| 阅读习惯 | 「本周阅读 90 分钟」的一项成功条件 | 「能够独立交流方案」的练习行动 | 分钟数；不能把练习分钟换算成交流能力 |
| 体重习惯 | 减重目标的结果观测 | 其他目标中的背景信息 | 最新真实测量及趋势，不相加，不用打卡率代替体重 |
| 财务账户 | 已确认专用于旅行的资金结果 | 另一目标中只作为背景 | 用户确认的资金口径；不重复承诺同一笔钱 |
| 预算 | 普通存钱目标的方法约定 | 「在约定预算内完成旅行」的必要成功条件 | 已发生支出、窗口、上限；是否为达成门槛须明确约定 |
| 一次会议任务 | 英语目标的一次验证行动 | 「完成这场会议」目标的交付证据 | 真实完成与反馈，不让对象类型限制业务含义 |

必要成功条件、可选方法和参考信息必须有明确区分；AI 可建议角色，启用计划时由用户确认。不能把所有绑定都默认为达成门槛，也不能因为一个行为看起来积极就自动认定它改善了成果。

## 3. 按成果结构选择展示，不套一张通用进度条

| 成果结构 | 首屏怎样显示 | 什么情况下可以用条 |
|---|---|---|
| 单一可累计成果，如旅行资金、月跑量 | 指标名称、当前量/目标量、剩余、来源时间 | 同一指标、同一单位、可靠数据、目标已确认时，给该指标单独的条 |
| 当前水平，如体重、入睡时间 | 当前观测、目标、变化或窗口趋势、覆盖 | 默认不把当前值直接除以目标；已有确认起点且进度定义合理时保留该指标的原有合法进度 |
| 多项共同条件，如规律生活 | 条件逐项显示，写明本周/本阶段哪些已满足、哪些待观察 | 不把条件平均成整体百分比；局部同单位指标可独立显示 |
| 成果与阶段交付，如英语方案交流、完成作品 | 当前阶段、必要交付、真实成果证据与待确认项 | 不把任务数量或练习时长换成能力百分比 |
| 维持或控制，如每周不超过上限 | 本周期真实数量与约定、周期是否结束、缺记录情况 | 不画「越花越满」的成功条，不用无记录推导控制成功 |
| 来源未授权、缺失或过期 | 显示具体未知、最后观测与来源问题 | 不显示伪 0%、伪失败或继承另一个来源的旧百分比 |

进度条不是被取消；它只描述**命名清楚的一项真实成果**。即使页面有资金条，名称也必须是「旅行资金」，不能叫整个人生愿望的「目标总进度」。

### 多条件的达成规则

- 用户确认「都要满足」时逐项检查；只有所有必要条件具备有效证据后，才能提示「条件已满足，待确认达成」。
- 只有明确存在替代路径时才使用「任一满足」，如选择飞机或高铁中的一种；不自行把必要条件变成替代项。
- 多做阅读不能抵消缺少运动，预算余量不能抵消成果证据缺失。
- 方法未做到不抹掉已经发生的成果。例如资金达到 18,000，奶茶超约定时同时显示「资金已备齐」与「约定需回顾」；除非用户事先把该约定明确设为必要条件，否则不阻止资金结果成立。
- 本周条件满足，不等于四周目标已完成；观察期、维持期和最终成果分别判断。
- 用户仍可沿既有功能完成或结束目标，记录原因；手动结束不能反写所有观测为满额或达标。

## 4. 一套页面结构，避免把多个模块变成多张看板

### 目标详情

1. **目标标题 + 一句当前判断**：如「资金还差 13,200；两项方法需要回顾」。由事实生成，不给一个混合分数。
2. **想达成什么**：按第 3 节展示真实成果。多个必要条件独立呈现；默认显示关键项，必要条件总数和展开入口可见，不把未展开条件当作不存在。
3. **行动与约定**：一份连续列表，先露出当前需要处理的项，其余展开；显示对象用途、窗口、事实值和去原模块记录的动作。不要每个模块各造一个标题、一张卡和一张统计图。
4. **回顾与下一步**：解释成果与行动的关系、证据缺口和可确认调整；沿用目标/HoloAI 的同一报告。

财务、习惯、任务或健康来源都是行内的出处/跳转，不成为目标详情的子模块 Tab。目标不复制原模块记录表单。

### 今天与目标列表

- 今天只显示已选行动及目标的一条相关事实，不挂整个多指标看板。单资金结果可写「资金 4,800/18,000」；多条件目标可写「运动与上床记录待回顾」；未知就写待观察，不强取一个指标当全局分数。
- 原目标列表保留入口，使用一句最有用的事实摘要；列表的数值必须标明指标。单指标可保留原合法条，多条件改用条件与阶段摘要。
- 无目标的日常任务照常可用；多个目标共享同一任务时，今天按真实任务 ID 只显示一次，目标入口可展开选择。
- 默认展示少量关键事实，不能以「减法」删除原任务多视图、目标记录、设置、提醒、历史与归档能力。

## 5. 需要提前覆盖的完整场景

| 场景 | 成果 | 行动 / 方法 / 约定 | 必须呈现的结论 |
|---|---|---|---|
| 旅行资金 + 多个习惯 + 预算 + 任务 | 资金 4,800/18,000 | 消费回顾、奶茶/宵夜上限、餐饮预算、核对资金 | 资金差距、执行情况、超约定分别成立；不平均 |
| 多习惯共同构成目标 | 运动 3 次、上床约定 5 晚、阅读 90 分钟，各自为本周条件 | 原习惯记录 | 条件独立检查；阅读超额不能填补运动与缺记录 |
| 多项出发准备 | 资金、必要材料、行程确认 | 财务、任务、反馈 | 钱够但材料没齐仍待准备；不用资金 100% 宣布旅行准备完成 |
| 英语真实交流 | 在约定场景独立表达方案的真实尝试与自评 | 听读、口语练习、会议任务、可选课程预算 | 练习全做也可能成果待验证；没有虚构的能力百分比 |
| 健康观测缺失 | 实际入睡时间的有效记录 | 自报上床、放松行动 | 自报上床不能冒充实际入睡；缺两晚不按失败两晚计 |
| 共用一条跑步记录 | 月跑量与周跑步次数分别计算 | 同一原始记录 | 一次写入两个合法投影，不重复创建打卡、相加相同来源或改全局归属 |
| 全部方法完成、成果没变化 | 原真实成果仍成立 | 行动已完成 | 回顾方法/观察期，不继续堆任务制造「进度」 |
| 成果已达到、方法超约定 | 真实成果已达到 | 方法需回顾 | 不倒扣成果；是否影响最终达成由预先确认的必要条件决定 |
| 行动和指标跨周期 | 真实窗口与阶段 | 日任务、周习惯、月预算、长期成果 | 不把不同窗口计数拼成「本周目标 80%」 |
| 没有目标条件或没有近期证据 | 尚未确定 / 待观察 | 先做少量探索和必要观测 | 不强行数值化，先约定怎样知道下一步是否有帮助 |

示例中的资金、次数与时间均为合成数据，不是对东林的健康、财务建议或真实账户读取。

## 6. 共享、重复与缺失的统一规则

- 来源以真实记录 ID、类型、窗口、来源版本识别。多个视图或绑定引用同一记录时只计一次。
- 同一指标存在手动/健康/习惯候选来源时先确定主来源或去重规则；不能把两个设备同步来的同一活动相加。
- 一个习惯在不同目标里可以有不同角色和要求；只写一次记录，各目标按自己的窗口与规则解释。
- 暂停、调整、结束某目标只改变本目标的绑定与要求；不全局暂停/改名一个共享习惯，不删除其他目标需要的记录。
- 真实 0 有意义，缺记录是未知，尚未到期是进行中；三者不能混用。完整周期上限不能在周期中间提前宣布最终成功。
- 缺少部分必要成果时，显示已知与未知；可选背景缺失不能阻断整个目标。
- 每项成果显示来源与观测时间；失效、过期、权限关闭、删除和同步失败保留各自语义。
- 旧报告冻结原事实与计划版本。新记录或新规则出现后，让旧调整待刷新，不直接改写历史结论。

## 7. 当前实现边界与后续契约

本轮重新核实当前工作区：

- `Models/GoalPlanContract.swift` 已有 `GoalPlanBindingRole.result/action/constraint/context` 和多个有效绑定，方向正确；不应另造并行关系。
- 同文件 `GoalPlanPayloadV2.resultSource` 仍是单个可选来源，`constraints` 是数组。
- `Services/AI/Goals/GoalEvaluationSnapshotBuilder.swift` 的 `buildResult` 与 `snapshot.result` 也按单项结果处理。

因此：**单成果 + 多行动/约束可沿现有契约扩展投影；多项独立必要成果不能只靠 UI 换行假装已支持。** 后续设计与实现需增加可兼容的成果/条件描述和逐项观测，明确必要/可选以及组合关系。

建议以「目标成功约定 → 有效绑定 → 原始观测 → 每项判断 → 一句总体状态 → UI」生成同一纯值快照。每项包含稳定 ID、业务名称、角色、是否为必要条件、来源、单位、窗口、聚合与比较规则、观测/覆盖/时效状态。总体只派生状态与待处理项，不派生跨单位加权分数。

旧单 `resultSource` 兼容为一项主要成果，旧目标不强迫重新设置。组合条件、阶段和规则修正需要版本化；改变成功标准必须单独确认。模型改动按增量兼容演进，实施前再审 CloudKit 与备份要求。本轮不迁移数据，不改变签名和容器。

## 8. 实施与验收门槛

先确认语义和多种形态，再改统一快照与渲染，最后接记录/共享/报告链路，避免为旅行、减重、英语分别写一套互不相容的页面。

必须验证：

1. 一个目标含财务、三个习惯、预算和任务时，没有跨模块总百分比，所有关联可找到。
2. 同一模块对象在不同目标担任不同角色时，展示和判断正确。
3. 多条件中一项超额、另一项未达或未知时，不发生抵消；本周达标不自动完成四周目标。
4. 完成/撤销任务只改变对应事实；成果只随合法来源变化；成果达成与方法违约能同时显示。
5. 同一条跑步记录只保存一次，月里程与周次数各自更新；重复导入不重复计数。
6. 预算/控制型习惯不因无记录显示成功；真实 0、缺记录、未来窗口、过期均有明确表示。
7. 目标暂停或解绑共享行为不破坏其他目标；删除/恢复/来源不可用遵守既有规则。
8. 今日、目标列表、详情和报告引用同一事实与窗口；历史与待刷新建议不混用。
9. 320/360px、长标题、大字号、单一关联与大量关联不溢出；主成果与例外优先、其余可展开。

本轮交互示例只用于产品评审。原生编译、真机、iPad、双设备和生产链路不能由示例通过替代。

## 9. 本轮示例验证

对话内 `holo-goal-multi-module.html` 可切换七种情形，默认先展示多习惯共同条件。全部使用合成数据，原模块页面为简化跳转与记录示意，不作为重做原模块布局的依据。

浏览器实际点击并观察到：

- 财务 + 多个习惯 + 预算 + 任务共存时，只有命名为「旅行资金」的一项成果有条，五个行动/约定可展开；没有加权总条。
- 多习惯、英语交流、健康缺观测三类没有伪造总进度条。将阅读从 110 改为 900 分钟，运动仍是 2/3，缺失的上床记录仍待补。
- 资金由 4,800 记为 18,000 后，「资金目标成果条件已满足」与「两项方法约定需回顾」同时出现；切到出发准备，行程未确认仍阻止提示全部条件满足。
- 一次记录 5 公里后，原始跑步记录由 2 条变 3 条，月跑量由 15 变 20 公里、周次数由 2 变 3；两个目标分别判断。
- 上床自报从 5 晚改为 7 晚后，实际入睡观测仍为未知；口语达到约定次数后，真实交流成果仍待验证。
- 320px 窄屏下多条件页面没有横向溢出，三个来源入口热区均至少 44px；收紧条件名称/数值与来源的排列，避免为每个模块重复造卡。

这些检查不代表当前 iOS 的多项成果模型或同步/报告链路已经实现。历史确认、暂停与去重的原生验收仍按第 8 节执行。
