# 周会需求进度追踪 Skill 使用说明

## 一、这个 Skill 是做什么的

这个 Skill 的核心目的是：**在每周五周会前，自动帮你判断上周提到的那些"下一步计划"到底有没有落实。**

具体来说，它会读取你从需求管理系统导出的 Excel 文件，解析每条需求「跟进记录」中提到的下一个时间节点（比如"6/25评审"、"下周一进入开发"），然后在下一周的数据中检查这条需求的状态是否真的按预期变更了。最终生成一列「AI进度判断」，告诉你每条需求是按期推进了、延期了、还是有进展但没达到预期。

---

## 二、使用前的准备工作

### 2.1 Excel 文件格式要求

你需要维护一个 Excel 文件（`.xlsx` 格式），按照以下规则组织数据：

**Sheet 命名规则：** 每周一个 sheet，sheet 名称用 4 位数字表示当周周五的日期。例如 8 月 21 日那周的 sheet 就叫 `0821`，8 月 28 日那周的就叫 `0828`。脚本会自动按日期排序，取最后两个 sheet 分别作为「本期」和「上期」进行比对。

**表头要求（固定 18 列）：** 每个 sheet 的第一行必须是以下表头，顺序不能变：

> 编号 | 系统模块 | 跟进记录 | 需求名称 | 状态 | IT标签 | 实际完时 | 业务标签 | 耗时(天) | 第一提出人 | 提出日期 | 跟进意见 | 任务工时(h) | 业务跟进人 | IT跟进人 | 类型 | 紧急度 | 预计完时

其中最关键的三个字段是 **编号**（唯一标识）、**跟进记录**（包含下一节点时间）和 **状态**（用于比对变更）。

### 2.2 每周操作流程

每周五周会前，按以下步骤操作：

1. 从需求管理系统导出本周的需求数据（Excel 格式）。
2. 打开你维护的那个汇总 Excel 文件，新建一个 sheet，命名为本周五的日期（如 `0828`）。
3. 将导出的数据粘贴到新 sheet 中（确保表头一致）。
4. 将这个 Excel 文件提供给 AI 工具运行分析。

### 2.3 环境依赖

脚本运行需要以下 Python 包（大多数环境已预装）：

```
pip install openpyxl pandas
```

## 三、在不同 AI 工具中的使用方式

### 3.1 在 Manus 中使用

最简单的方式。直接在对话中上传你的 Excel 文件，然后说：

> "帮我做本周的周会需求进度分析"

或者：

> "用 weekly-meeting-tracker 技能分析这个 Excel"

Manus 会自动读取 SKILL.md 并执行分析脚本。

### 3.2 在 Claude Code / Cline 中使用

1. 将整个 `weekly-meeting-tracker` 文件夹放到你的项目目录中。
2. 在项目根目录的 `CLAUDE.md`（或 `.cursorrules`）中添加引用：

```markdown
## 技能引用
- 周会需求进度追踪：参见 `weekly-meeting-tracker/SKILL.md`
```

3. 在对话中告诉 Claude Code：

> "读取 weekly-meeting-tracker/SKILL.md，然后用 scripts/weekly_tracker.py 分析 data.xlsx"

或者直接运行脚本：

```bash
python weekly-meeting-tracker/scripts/weekly_tracker.py ./data.xlsx
```

### 3.3 在 Cursor / CodeBuddy 中使用

1. 将 `SKILL.md` 的内容复制到 `.cursorrules` 或项目的 rules 文件中。
2. 在对话中上传 Excel 并要求分析即可。

### 3.4 直接命令行运行

不依赖任何 AI 工具，直接在终端运行：

```bash
python weekly_tracker.py your_data.xlsx

# 指定输出路径
python weekly_tracker.py your_data.xlsx --output result.xlsx
```

## 四、跟进记录的书写规范

**这是影响分析准确率最关键的部分。** 脚本的分析质量直接取决于「跟进记录」中时间节点的写法。以下是推荐的书写规范和需要避免的写法。

### 4.1 推荐写法（脚本能准确识别）

| 写法示例 | 解析结果 |
|---------|---------|
| `0820：预计8/25评审` | 节点时间 8/25，动作：评审 |
| `0820：预计25日完成设计` | 节点时间 8/25，动作：完成设计 |
| `0819：下周一进入评审` | 节点时间 8/24（自动推算），动作：评审 |
| `0818 开发中，预计27日上线` | 节点时间 8/27，动作：上线 |
| `0821：已完成需求评审，下周进入研发` | 节点时间 8/26（下周三），动作：进入研发 |
| `0820：预计明天上线` | 节点时间 8/21，动作：上线 |
| `0814：预计0812评审` | 节点时间 8/12，动作：评审 |

### 4.2 可以识别但精度较低的写法

| 写法示例 | 解析结果 | 说明 |
|---------|---------|------|
| `下周跟进` | 节点时间 下周三（默认） | 没有具体星期，默认取下周三 |
| `节后安排` | 无法解析 | "节后"过于模糊 |
| `今天上线` | 节点时间 = 跟进日期当天 | 依赖开头的跟进日期 |

### 4.3 应该避免的写法

| 写法示例 | 问题 |
|---------|------|
| `优先级调整，节后安排` | 没有明确时间节点，无法比对 |
| `有依赖，暂缓` | 没有时间节点 |
| `同意导数需求` | 纯状态描述，无下一步计划 |
| `已对接` | 没有说下一步什么时候做什么 |

**最佳实践：** 每条跟进记录尽量包含 **"什么时候"** + **"做什么"** 两个要素。例如：

> `0821：需求已对齐，预计下周一完成设计，下周三评审`

### 4.4 可识别的动作关键词完整列表

| 关键词 | 期望达到的状态 |
|-------|--------------|
| 评审、需求评审、技术评审、方案评审 | 设计完成 或 待研发 |
| 设计、完成设计、出方案、定方案、输出方案、出草稿 | 设计完成 |
| 研发、开发、进入开发、排期开发、进入研发、介入开发 | 研发中 |
| 上线、发布 | 待上线 或 待验收 |
| 验收 | 待验收 |
| 提测、测试、联调 | 待上线 |
| 需求沟通、需求对接、需求澄清、对接需求、沟通需求 | 已IT跟进 或 设计中 |
| 打标、业务打标 | 已IT跟进 或 设计中 |

如果你的团队有其他常用的动作关键词（比如"灰度"、"发版"），可以在 `scripts/weekly_tracker.py` 的 `ACTION_TO_STATUS` 字典中自行添加。

## 五、输出结果说明

### 5.1 AI进度判断列

脚本会在本期 sheet 的最后新增一列「AI进度判断」，每条需求的判断结果格式如下：

| 标记 | 含义 | 示例 |
|------|------|------|
| ✅ | 按期推进 | `✅ 按期推进｜上期(0821)预计 8/26 评审，本期状态已变为「待研发」，符合预期。` |
| ❌ | 未按期推进 | `❌ 未按期推进｜上期(0821)预计 8/25 完成设计，本期状态仍为「已IT跟进」，延期 3 天，建议关注。` |
| ⚠️ | 有进展但未达预期 | `⚠️ 有进展未达预期｜上期(0821)预计 8/25 上线，本期状态为「研发中」，已推进但尚未达到预期阶段。` |
| ℹ️ | 无明确节点 / 新增 | `ℹ️ 无明确节点｜上期跟进记录未提及具体时间节点，本期状态为「设计中」（上期：已IT跟进），状态有变更。` |
| ⏳ | 节点未到 | `⏳ 节点未到｜上期(0821)预计 9/1 评审，节点尚未到达，待下期验证。` |
| 🔴 | 需求已移出 | `🔴 需求已移出｜编号 229907 在本期跟踪列表中未找到，请确认是否已关闭或转移。` |

Excel 中会用不同的背景色区分：绿色（按期）、红色（未按期）、橙色（有进展未达预期）、粉色（已移出）。

### 5.2 汇总统计

脚本运行结束后会在终端输出一份汇总统计，包括各类判断的数量，以及所有「未按期推进」的需求清单（含编号、需求名称、当前状态、预期动作、延期天数、IT跟进人），方便你直接拿去周会讨论。

## 六、注意事项

### 6.1 数据准备

1. **Sheet 命名必须是 4 位数字。** 比如 `0821`、`0828`、`0904`。不要用 `8月21日`、`第34周` 这样的命名，脚本无法识别。

2. **编号必须是数字且全局唯一。** 脚本用编号作为跨周匹配的唯一标识。如果编号有重复，后面的会覆盖前面的。

3. **表头顺序不能变。** 脚本按列号读取数据（A 列=编号，C 列=跟进记录，E 列=状态），如果你调整了列顺序，解析会出错。可以在 18 列之后自由添加额外的列，不影响脚本运行。

4. **每次导出的数据要完整。** 如果某条需求在上期存在但本期导出时漏掉了，脚本会判定为"需求已移出"。

### 6.2 跟进记录书写

5. **尽量用明确日期而非相对时间。** `8/25评审` 比 `下周一评审` 更准确。相对时间的推算依赖 sheet 日期，如果跟进记录是周三写的但 sheet 是周五的日期，"下周一"的推算基准会是周五而非周三。

6. **避免纯 HTML 内容。** 系统导出的跟进记录有时会包含 `<span>`、`<br>`、`<img>` 等 HTML 标签，脚本会自动清除，但如果整条记录都是 HTML 图片标签（没有文字），则无法解析。

7. **一条记录有多个时间节点时，脚本取最远的。** 比如 `预计0811完成设计，0812评审`，脚本会取 8/12 作为节点时间。这个逻辑适合大多数场景，但如果你想追踪的是最近的那个节点，需要注意。

### 6.3 状态判断

8. **状态流转是单向的。** 脚本假设需求状态按 `待IT跟进 → 已IT跟进 → 设计中 → 设计完成 → 待研发 → 研发中 → 待上线 → 待验收` 的顺序流转。如果实际业务中存在状态回退（比如从"研发中"退回"设计中"），脚本仍会判定为"按期推进"（因为当前状态序号 >= 预期状态序号的逻辑不适用于回退场景）。

9. **"按期推进"的判断是宽松的。** 只要当前状态达到或超过预期状态，就算按期。比如预期是"设计完成"，但实际已经到了"研发中"，也会判定为按期推进。

10. **延期天数的计算基准是本期 sheet 日期。** 延期天数 = 本期 sheet 日期 - 预期节点日期。比如预期 8/25 完成，本期 sheet 是 0828，则延期 3 天。

### 6.4 首期数据

11. **首期只能做基线分析，不能做比对。** 如果 Excel 中只有一个 sheet，脚本会提示"这是首期数据，无法进行跨周比对"。首期的价值在于解析出所有时间节点，为下期比对做准备。

### 6.5 自定义扩展

12. **添加新的动作关键词。** 编辑 `scripts/weekly_tracker.py` 中的 `ACTION_TO_STATUS` 字典即可。格式为 `'关键词': ['期望状态1', '期望状态2']`。

13. **添加新的状态。** 如果你的系统有额外的状态（比如"已关闭"、"已上线"），在 `STATUS_ORDER` 字典中添加并赋予合理的序号即可。

14. **跨年数据。** 脚本会自动处理跨年场景。如果解析出的月份比 sheet 月份早 6 个月以上，会自动判定为下一年。

## 七、常见问题

**Q1：我的 sheet 名不是 4 位数字怎么办？**

需要手动改名。脚本只识别 `MMDD` 格式的 sheet 名（如 `0821`）。如果你的系统导出的 sheet 名是其他格式（如 `Sheet1`），需要在 Excel 中手动重命名。

**Q2：跟进记录里写了时间但脚本没识别出来？**

检查以下几点：（1）时间是否在开头的跟进日期位置（如 `0820：...` 中的 0820 会被当作跟进日期而非节点时间）；（2）是否被 HTML 标签包裹且标签内没有文字；（3）日期格式是否在支持范围内（支持 `M/DD`、`MMDD`、`XX日`、`XX号`、`下周X` 等）。

**Q3：同一个编号在一个 sheet 中出现了两次怎么办？**

脚本会取最后一条。建议在数据导出时确保编号唯一。

**Q4：能不能一次比对多期数据（比如最近 4 周的趋势）？**

当前版本只支持相邻两期比对。如果需要多期趋势分析，可以作为后续迭代功能。

**Q5：脚本报错"表头不完全匹配"怎么办？**

这是一个警告而非错误，脚本仍会继续运行。但如果关键列（编号、跟进记录、状态）的位置变了，结果会不准确。请确认你的 Excel 表头与规定的 18 列一致。
